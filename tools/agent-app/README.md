# agent-app

GitHub Copilot App 風のデスクトップ。ローカルリポジトリを登録し、`agents/*.json` に定義した
エージェント CLI（copilot / claude / codex / kiro / cursor …）と会話形式で作業する Electron アプリ。
GitHub との連携は持たない。見に行くのは登録したフォルダだけで、CLI はこの PC（Windows なら WSL）に
入っているものをそのまま呼ぶ。同じリポジトリの**タスク**（statemachine-use スキルで動くステートマシン、
`.statemachine/<名前>/`）と**ワークフロー**（agent-flow の工程）もこの画面で作り、実行する
（旧 statemachine-maker はこのアプリに統合した。単体アプリは無い）。

設計判断は [`docs/designs/agent-app-design.md`](../../docs/designs/agent-app-design.md)、IPC・設定・
保存形式・tmux 契約・上限は [`docs/specs/agent-app-spec.md`](../../docs/specs/agent-app-spec.md) にある。

- **左**: 主メニューは **会話 / タスク / ワークフロー** の 3 つ。選んだ領域の一覧とリポジトリを同じ
  サイドバーで切り替える。会話一覧では応答中・確認待ちに印が付き、
  別の会話を開いて並行して進められる。会話ごとに **git worktree** で作業フォルダを分けられる
  （同じフォルダを複数の CLI が同時に書き換えて混ざるのを避ける）
- 会話右上の「••• > VS Codeで開く」で、現在の作業フォルダをVS Codeへ渡せます（VS Codeのインストールが必要です）。
- **中央「会話」**: チャット。依頼ごとに起動方針（標準 / 節約 / 品質重視 / 直接指定）と
  権限（確認して実行 / 自動承認 / 読み取り専用）を選ぶ。応答は **思考・進捗 / 回答 / 実行情報** に分かれ、回答は通常の
  チャット吹き出し、詳細は折りたたみで表示する。直接指定なら同じ会話の中で
  claude → codex → claude のように渡り歩ける。
  エージェントの選択肢には、agent-herd 一族（aider / ollama）があれば **`herd`** も並ぶ。`herd` は
  ローカル実行系を 1 語で指す仮想の名前で、一族の共通 TUI（agent-herd）を 1 本開き、Ask なら `/find`、
  作業フォルダのファイルを添えた依頼なら `/edit` を本文の先頭に付けて送る（どのエージェントで直すかは
  agent-herd 側の宣言が決める）。タスク・ワークフローでも `herd` を選べ、agent-herd の既定に任せる
  （設定 > 実行制御の tier にも書ける。規則は `src/main/herd.js`）。
  依頼には**ファイルを添付**できる（「添付」ボタン・ドラッグ＆ドロップ・画像の貼り付け・
  「ファイル」画面で開いているファイル・変更ビューの行）。CLI は **tmux 上で対話起動**され、応答は
  Markdown として描画する。「端末」で CLI の画面をそのまま見て操作できる。ツール実行の許可を
  CLI が聞いてきたら、会話一覧や会話名の横の「確認待ち」を押すと、**答える場所（端末操作）まで
  1 押しで行く**（→「確認待ちに答える」）。入力欄の「定型」には、設定で決めた
  **定型の依頼**が並ぶ（→「共通指示・定型の依頼・起動時アクション」）。完了した回答の下の
  「フォーク」は、そこまでを別のセッション・タスク・ワークフロー・スキルへ分ける。
  会話右上の「••• > テキストに書き出す」で、依頼と回答を並べたテキストファイルを作り、そのまま開く
  （端末の制御文字と飾りの文字、行の前後の空白は落とす。思考・進捗と実行情報は載せない）
- **中央「タスク」**: 定義があるタスク（statemachine-use スキルや手で作った `.statemachine/<名前>/` を含む）は
  **実行詳細**（概要 / 手順 / 履歴）から開き、名前の横に「利用可能」が付く。そのまま実行・定期実行できる。
  **新しいタスクは AI との tmux 会話で作る**——目的を書いて「AIと作成を始める」と、会話と同じ CLI が
  リポジトリで起動し、手動実行の画面と同じく端末がタスク画面の中に埋め込まれる。AI は
  `statemachine-use` スキルの作成モードで `.statemachine/<名前>/` を直接書き、画面操作の見本が
  要るときは `@record` の 1 行で頼んでくる（→「タスクを AI と作る」）。既存タスクの変更は「手順」タブの
  「編集」から同じ会話で続ける。定義があるタスクは会話の途中でも実行できる。
  会話の回答の下の「フォーク」でフォーク先にタスクを選ぶと、その回答までを引き継いで作成を始める。
  設計: [`docs/plans/2026-09-08-agent-app-statemachine-maker-consolidation-tmux-teaching-design.md`](../../docs/plans/2026-09-08-agent-app-statemachine-maker-consolidation-tmux-teaching-design.md)
- **中央「ファイル」**: リポジトリのフォルダツリーと、コード（言語ごとの配色・行番号）／
  Markdown（プレビュー ⇄ ソース切り替え、Mermaid 図）／画像のビュアー。名前検索はフォルダ全体の
  索引（60 秒保持。`node_modules` や `dist` には潜らない）を引くので、2 文字目からは歩き直さない。
  Windows で `\\wsl$\` のリポジトリなら索引は WSL の中の `git ls-files` で作る（9P 越しに歩かない）。
  ツリーの「更新」で索引も作り直す。
  「会話に添付」は直接選べる。既定のアプリで開く・フォルダで表示・再読み込みは、
  ファイル上部の「•••」から選ぶ。
- **右「変更」**: その会話の作業フォルダの差分（`git status` / `git diff`）。1 列と並べて表示を
  切り替えられ、ターンが終わるたびに更新する。ダブルクリックでそのファイルをビュアーで開く。
  worktree の会話では「作業ツリー」（まだコミットしていない分）と「ブランチ」（分岐元から
  積んだコミット）を切り替えられる。行の「会話に添付」で、そのファイルを次の依頼に載せられる

## 起動

```bash
cd tools/agent-app
npm install        # 画面で使うライブラリを src/renderer/vendor/ へ写す（scripts/vendor.js）
npm start
```

テストはユニットテストに加え、利用できる環境では Electron 実機と疑似 CLI の tmux 統合テストも走る:

```bash
npm test
```

### Windows 向け exe を作る

agent-dashboard と同じく electron-builder で **portable exe** と **NSIS インストーラ** を作る
（設定は `package.json` の `build`）。

```bash
cd tools/agent-app && npm install
npm run dist             # portable + NSIS → release/（release/agent-app.exe が portable 版）
npm run dist:portable    # portable だけ
```

- **同梱するもの**: `src/`（`npm install` が写す `src/renderer/vendor/` と、タスク・ワークフローの共有
  ワークベンチ `src/main/automation/` `src/renderer/automation/` を含む）と、本番依存の `yaml`（定義の
  読み書き）。画面用ライブラリ（mermaid / marked / xterm …）は vendor/ に写した分だけ使うので
  `devDependencies` に置き、electron-builder が本番依存として推移的に同梱しないようにする
  （`dependencies` に戻すと d3 / katex … まで入って asar が数十 MB 増える）。
- `npm run dist` は先に `scripts/check-dist.js` で、本番依存・vendor/・アイコンが揃っているかを見る。
- **リポジトリ直下の資源**は `extraResources` で `resources/` に入れる。CLI 定義 `agents/*.json` は
  `resources/agents/`（探索順の最後。`~/.agents/agents/` などに置いた定義が勝つ）、タスク実行に要る
  `.github/skills/statemachine-use` は `resources/app-root/.github/skills/…`（登録リポジトリや
  ⚙ 設定で見つからないときの最後の候補）。参照と同梱指定の対応は `test/packaging.test.js` が突き合わせる。
- **アイコン**は `assets/icon.ico`（`npm run icon` → `scripts/icon.js` が外部ライブラリなしで生成。
  吹き出しに `›_` の図柄で、agent-dashboard とは別物）。差し替えるなら 256px を含む ico を同じ場所に置く。
- Linux 上でも `npm run dist` は通る（electron-builder 26 は wine なしで exe のアイコン・バージョン情報を
  書き換え、NSIS も同梱の物を使う）。署名は行わない。

### 配って更新する（自動更新）

外部サービスは使わない。本体（exe）は**更新元**（みんなが読める共有フォルダ、または社内の HTTP）に
置き、WSL 側の agent-tools は **agent-project の自己更新**（git のリポジトリから取り込む）に乗せる。
ビルドと配置は手元で行う（CI は要らない）。

```bash
cd tools/agent-app
npm run dist:portable                                   # release/agent-app.exe
npm run publish:update -- \\server\share\agent-app      # exe を写し、manifest.json を書く
npm run publish:update -- \\server\share\agent-app --notes "端末の表示を直した"
```

更新元に置かれるのは `manifest.json`（版・ファイル名・sha256）と `agent-app-<版>.exe`（版は
`package.json` の `version`。**上げてから**ビルドする）の 2 つ。

agent-tools の送り手は **git push だけ**。外部サービスを使わないなら、共有フォルダに bare リポジトリを
置いて（`git clone --bare <このリポジトリ> \\server\share\sandbox.git`、以後 `git push`）、各 PC の WSL で
agent-project の設定（`~/.agents/agent-project.yaml`）の `update_repo` に `/mnt/<ドライブ>/…/sandbox.git`
（`net use` したドライブ）や社内 git の URL を書く。取り込む範囲は agent-project の既定で**一族まとめて**
（4 エンジン + agent-herd + agent-loop と `agents/` `commands/`。agent-project の README「自動アップデート」）。

受け手は「設定 > アプリ」で更新元（exe の置き場）を入れる。確認は **起動時**（既定 ON）、**定期**（既定
1 日ごと）、**「今すぐ確認」** の 3 つで、見つかった分は 1 つのダイアログに並び、**「更新する」を押した
分だけ**取り込む（黙って入れ替えない。「あとで」で閉じた内容は次の起動まで自動では出さない）。

| 対象 | 何をするか | できる形態 |
|---|---|---|
| Agent App 本体 | 更新元の exe を隣に置き、終了後に入れ替えて起動し直す（動いている exe は自分で上書きできないので、小さな cmd を切り離して走らせる） | Windows の **portable 版**だけ。開発起動や NSIS 版では案内だけ出す |
| agent-tools | CLI と同じホスト（Windows なら WSL）で `agent-project update --check --json` を叩いて有無を見て、承認後に `agent-project update --now --json` で取り込む（sparse-checkout → `install.sh`）。物差しはコミット SHA で、agent-app は印を持たない | agent-project が WSL に入っていて `update_repo` が解決できるとき。無ければ行を出さない・「更新元の設定なし」と出す |

取得した exe は sha256 を照合してから使う。入れ替えに失敗したら元の exe で起動し直し、経過は
`%TEMP%\agent-app-update.log` に残る。agent-project の取り込みが失敗したときは、その理由（JSON の
`error`）をダイアログに出す。常駐の agent-project が動いている PC では、常駐自身も 6 時間ごとに同じ
更新を見に行く（同じ SHA なら二重には適用しない）。

### 前提

| | Linux / macOS | Windows |
|---|---|---|
| CLI（claude / kiro …） | この OS の PATH（ログインシェル） | **WSL の中**の PATH |
| tmux | `apt install tmux` など | WSL の中に `sudo apt install tmux` |
| git（変更ビュー） | ローカル | WSL の中 |
| Python 3 + PyYAML（タスクの構成確認・agent-loop 無しの実行） | ローカル | 構成確認はこの端末、実行は WSL の中の `python3` |
| agent-tools（任意） | agent-herd / agent-loop / agent-flow を PATH に | WSL の中の PATH に |
| 登録するフォルダ | そのまま | `\\wsl$\<ディストロ>\…` か `C:\…`。tmux の cwd と git には WSL 表記（`/home/…` / `/mnt/c/…`）へ直して渡す |

Windows では `\\wsl$\Ubuntu\…` のリポジトリはパスからディストロが決まる。`C:\…` のリポジトリは
左下の「WSL ディストロ」で指定したもの（空なら既定のディストロ）で動かす。

tmux が無い（または「設定 > アプリ」で対話セッション維持を外した）ときは、従来どおり 1 ターン 1 プロセスの
ヘッドレス実行（`-p` 相当）に倒れる。

タスクの手動実行では、クラウドCLIを1セッションで通す場合、タスクの概要にtmux画面を表示する。
端末へ直接入力でき、停止ボタンで実行を終了できる。tmuxが無い・対話起動の定義が無い・
「対話セッションを維持」が無効の場合は、理由を表示して従来の実行ログへ切り替える。
工程ごとのハーネス実行と構成確認は実行ログを表示する。対話実行の完了はCLIが応答を終えて
入力待ちに戻ったことを示し、タスクの受入条件や確認コマンドの成功を保証するものではない。
終了・停止時には色付きの端末履歴を保存するため、実行プロセスの終了後もスクロールして読める。
終了後はキー入力を受け付けず、保存した履歴は次の手動実行またはアプリ終了まで保持する。

### agent-tools が無くても動く / あると増えるもの

agent-app は **agent-tools（agent-herd / agent-loop / agent-flow）を入れていない PC でも、会話とタスクの
作成・実行が動く。** 要るのは CLI（claude / codex / copilot / kiro …）と tmux、タスクの実行に Python 3 と
PyYAML（`pip install pyyaml`。Windows では WSL の中）だけ。定義 `agents/*.json` は agent-app 自身が読み、
「使える」印もホストの PATH で付けるので、会話で使える CLI がそのままタスクでも使える。

| | agent-tools なし | agent-herd（ローカル実行系） | agent-loop | agent-flow |
|---|---|---|---|---|
| 会話 | ○ | ＋ `herd`（費用 0 のローカル LLM。Ask は読み取り専用が保証される） | — | — |
| タスクを AI と作る | ○ | ＋ `herd` を会話の既定にできる | — | — |
| タスクの手動実行 | ○（クラウドの AI は 1 回で通す。それ以外は同梱の statemachine-use スキルが工程ごとに起こす） | ＋ タスクの AI に `herd` を選べる | 実行の正典がこちらに移る（実行ログ・台帳・受入条件・`check` の昇格） | — |
| 定期実行・実行履歴 | ×（1 行でそう出る） | — | ○ | — |
| AI 支援（ワークフロー教示・工程の見直し） | ○（その CLI を読み取り専用の単発で起こす） | ＋ `herd` なら agent-herd の計画用途（JSON を文法で強制。修正の往復が減る） | — | — |
| ワークフロー（複数 AI の工程） | × | — | — | ○ |
| 集計と監査（使用量・成功率・定型化物の合否） | ×（1 行でそう出る） | — | — | — |

集計と監査には agent-audit が要る（agent-tools の `install.sh` で入る）。入っていない PC では
利用状況の画面が「使えない」と 1 行出るだけで、会話もタスクも止まらない。

### タスクの回し方は、選んだ AI で自動的に変わる

同じタスクでも、選んだ AI によって回し方が変わる。切り替えの操作は無い。

| 選んだ AI | 回し方 | 向く仕事 |
|---|---|---|
| クラウドの AI（kiro・Claude・Codex・Copilot・Cursor） | 最初から最後まで 1 回で通す | 手数を抑えたいとき。長い手順ほど差が出る |
| この端末で動く AI、および自分で道具を使えない AI | 工程で区切り、工程ごとに呼ぶ | 確かさが要るとき |

分けている理由は費用である。工程ごとに呼ぶと、そのたびに起動と読み直しが起きる。手元で動く AI なら
何回呼んでも費用は増えないので区切ったほうが得だが、クラウドの AI では手数がそのまま費用になる。

**1 回で通す回し方は、工程ごとの確認コマンドを実行しない。**工程数の上限も効かない。agent-appからの手動実行は入力条件とログ末尾を履歴に残す。
確認コマンドを書いたタスクをこの回し方で実行するときは、始まる前にその 1 行が出る。確かさを取るなら、
手元で動く AI を選ぶ。

足りないものは「タスク」画面の実行環境（手順 → その他 → 実行環境）に出る。任意の道具は「任意」と出て、
未準備でも本体は止めない。何が増えるかの設計は
[`docs/plans/2026-09-09-agent-app-standalone-and-herd-benefits-design.md`](../../docs/plans/2026-09-09-agent-app-standalone-and-herd-benefits-design.md)。

## 作業フォルダを分ける（git worktree）

同じリポジトリで会話を並行して進めると、1 つの作業ツリーを複数の CLI が同時に書き換えて混ざる。
会話ごとに worktree を生やせば、**別のフォルダ・別のブランチ**で作業でき、本体（登録したフォルダ）は
そのまま残る。

- 置き場は `<リポジトリ>/.worktrees/<名前>` の 1 か所に決め打つ。名前だけを保存すればよく、
  画面から生のパスを受け取らない（`..` を持ち込めない）。Windows でも「登録したパス + `.worktrees` +
  名前」で fs 用（`C:\…`）と git 用（`/mnt/c/…`）の両方を作れる
- 初回に `.worktrees/` を **`.git/info/exclude`**（ローカル限定の除外）へ足す。リポジトリの
  `.gitignore` は触らない。これをしないと本体の変更ビューに worktree が「新規」として並ぶ
- 左下の「作業フォルダを分ける」で機能ごと on / off できる（既定は on）。off にすると画面から
  選択と `…` が消え、新しい会話は常にリポジトリ本体で始まる。既にある worktree と、それで
  始めた会話はそのまま動く（どこで動いているかは会話を開けば見える）
- 上の「作業フォルダ」で会話ごとに選ぶ。**会話を作ったあとは変えられない**（tmux の cwd も
  CLI 側の文脈もそこで始まっているため）。`…` ボタンで作成・削除
- ブランチ名を入れるとフォルダ名は自動で決まる（`feature/foo` → `.worktrees/feature-foo`）。
  既にあるブランチを指定すると、新しく作らずそれを持ってくる
- 削除は未コミットの変更が残っていると git が断る（確認のうえ「変更ごと削除」で押し切れる）。
  ブランチは既定で残す。その作業フォルダを使っている会話の tmux セッションは先に止める
- この画面の外で作った worktree は一覧には出すが、会話の作業フォルダには選べない
- `.worktrees` 自体は本体のツリーと名前検索から外す（リポジトリの写しなので、出すと入れ子の
  複製が並び、検索も worktree の数だけ同じファイルを返す）。中を見るときは「見るフォルダ」で選ぶ

git へ書き込むのはここだけ（worktree の追加・削除とブランチ作成）。変更ビューは読むだけで、
コミット・マージ・push は持たない——それは CLI に頼むか、端末でやる。

## 起動方針とターンごとの実行設定

「設定 > 実行制御」で標準・節約・品質重視それぞれにエージェントとモデルを割り当てる。
指定した方針が利用不能でも、別の方針へ自動で切り替わらない。「直接指定」では次のターンだけエージェントとモデルを選べる。
各依頼には実際に使った起動条件が残る。

**エージェントを最適化する**（設定 > 実行制御。既定 ON）が効いているときだけ、節約・品質重視と small / large
tier が使える。効くのは agent-herd（ローカル実行系）が使えるときで、OFF にするか agent-herd が無ければ、
既定の起動方針は「標準」だけ、ターンごとの起動方針は「標準」か「直接指定」だけになり、選べない項目と
small / large の行は薄くなる（理由は出さない）。保存してある節約・品質重視は、その間は 標準 として扱う。
同様に、agent-flow が無ければサイドバーの「ワークフロー」、agent-loop が無ければタスクの「履歴」タブと
「定期実行」のカードが薄くなる。

- **ヘッドレス**（1 ターン 1 プロセス）は、そのターンの CLI を選んだモデル・モードで起動するだけ
- **tmux**（対話起動）は、動いている CLI と起動条件が違えば、そのターンの前に **CLI を起動し直す**
  （以前の「再起動」ボタンを押す手間が自動になった）。会話・タスク編集・ワークフロー編集は、
  エージェントごとにセッションIDを保存し、アプリや tmux の終了後もそのIDで文脈を復元する。
  Claude・Copilotは起動時、Kiroは起動時の通知、Codexは最初の応答完了通知でIDを記録する。
  Codexは最初の応答が完了する前に終了した場合、IDを記録できない。
  IDが無い場合や再開手段の無いCLIは、新しく起動してこれまでのやり取りを最初の依頼に添える。
  タスク・ワークフロー編集の再開では、CLIの復元後に再開用の説明を送り直さない。
  今回の編集対象が指定されている場合はその指示を送り、別のCLIで進めた履歴は未共有の分だけ添える。
  初回作成やIDのない新規起動では、従来どおり作成・再開の説明を送る。
  生きているtmuxがあれば、そのまま再接続する。
  Codex・KiroのID記録には、CLIが動くホスト（Windowsの場合はWSL）に Python 3.8以上が必要。
  Kiro v3のID記録には未対応で、記録の準備ができない場合は起動時にその理由を表示する。
  CLI自身のセッション履歴を削除した場合は、保存IDだけでは復元できない
- **この会話をフォーク**（会話画面の「•••」）に、新しいセッションへの引き継ぎを統一しています。
  既定では最新の完了した応答までを要約し、現在のAI・モデル・権限で新しい会話を始めます。
  同じリポジトリを選ぶと現在の作業フォルダを使い、別のリポジトリを選ぶとそのリポジトリ本体を使います。
  位置や実行設定を変更したり、タスク・ワークフロー・スキルへ転用したりできます。
  元の会話は残り、CLIセッションIDは引き継ぎません。要約に失敗した場合は新しい会話を作りません。
- **新しいセッションで編集**はタスク・ワークフローの編集画面にだけ表示する。同じ対象に空の会話を作り、
  初回の編集用プロンプトを送る。旧会話の履歴やCLIセッションIDは引き継がず、以後は新しい編集セッションを開く。
- **エージェントを渡り歩く**と、会話は CLI ごとに別のセッションになる。会話は CLI ごとに
  「セッション ID」と「そこまで見たメッセージ数」を覚えていて、別の CLI で進めた分は、戻ってきた
  ときに依頼の前に「あなたのセッションの外で進んだやり取り」として添える（履歴の再送は
  その差分だけで、全部を毎回送り直しはしない）
- tmux の会話は 1 つの tmux セッション（＝ CLI 1 つ）しか持たない。別の CLI へ移ると前の CLI は
  止める（戻るときは resume で続く）。対話定義を持たない CLI（vscode-copilot 等）へ移ったターンは
  ヘッドレスで走る
- 作業フォルダ（worktree）だけは会話ごとに固定のまま（tmux の cwd も CLI 側の文脈もそこで始まっている）

## 共有（同じ LAN の仲間に依頼を回す）

自分の枠が足りないとき、依頼を同じ LAN の別の agent-app に渡し、その人の PC でその人の CLI が
答えを出す。逆に自分の PC が空いていれば、仲間の依頼を受けて自分の枠で答える。中央のサーバも、
git サーバも、共有の API キーも無い。PC 同士が直接やり取りする。

1. 設定 > 共有で「共有を使う」を ON にし、参加者全員で同じ**合言葉**を入れる。
   仲間の PC を 1 台知っていれば「仲間の PC」に書く（ホスト名か IP）。1 台知れば残りは
   その PC から教わる。同じサブネットなら UDP のブロードキャストでも見つかるが、無くても動く。
2. **依頼を出す**: 入力欄の入力先を「共有に依頼」にして送る。会話でも、タスクやワークフローを
   AI と作る会話でも、同じ切替から出せる。実行設定では依頼先（「どれでも」か、参加者の 1 台）、
   エージェント（「どれでも」か、参加者が提供している CLI の名前）、優先度だけを選ぶ。依頼先を
   名指しすると、その PC だけが拾う（ほかの PC には拾えない依頼として見える）。「どれでも」なら
   仲間の誰でも拾う。待っている依頼の依頼先は、共有画面の「自分が出した依頼」からも変えられる。
   答えは同じ会話に、どの PC のどの CLI が答えたかを添えて戻る。待っている間は送信ボタンが
   「取り下げ」になる。
3. **待っている間、相手の画面が見える**: 引き受けた人の端末がそのまま自分の端末ミラーに映る
   （見るだけで、キーは送れない）。どこまで進んだかを画面で確かめられる。
4. **人には話せる**: 端末の下の「やり取り」で、引き受けた人と短いやり取りができる（入力欄が
   そのままひとこと欄になる）。ここで書いたことは AI には渡りません。**何を打つかを決めるのは
   引き受けた人**で、端末に打てるのもその人だけです。自分の PC の AI が確認を求めたら、
   共有の画面で「端末操作」に切り替えて答えます。
5. **依頼を受ける**: サイドバーの「共有」に、仲間が出した依頼と自分が出した依頼が並ぶ。
   選ぶと本文と操作が右に出る。「自動で引き受ける」は設定画面と、共有画面の「参加者」で切り替える。

| 引き受け方 | 動き |
|---|---|
| チェックあり | 空きがあれば列の上から自分で拾う |
| チェックなし | 一覧から選んで「引き受ける」を押したものだけ実行する |

受けるのは agent-app を開いている間だけ。読み取り専用で起こすので、依頼が自分の作業ツリーを
書き換えることは無い。提供する CLI・同時に受ける数・1 日の上限・依頼者 1 人あたりの上限は
設定 > 共有で決める。引き受けている間は、自分の画面にもその端末が出る（打てる。「止める」で止められる）。
「参加者」タブには、同じ合言葉で見つかった PC と、それぞれの受付状況が並ぶ。

順番は全員が同じ規則で決める。優先度が高いもの、次に「今日まだ答えてもらっていない人」の
依頼、最後に投函が早いもの。待ちが 30 分を超えるごとに 1 段繰り上がる。受ける側は同じ人からの
依頼を 1 日に受ける数も決められるので、少数の大量依頼者が列を独占しない。

やり取りは依頼にぶら下がり、依頼が終われば一緒に終わる。読み返しは共有の「今日 完了」から。

投げた依頼の本文（会話の履歴と添付を含む）は、それを拾った参加者に見える。一覧に出るのは
利用者が書いた依頼文だけで、履歴を含む全文は引き受けた人にだけ渡る。秘密を依頼に書かない。
必要な穴は TCP の受け口 1 ポート（既定 47801）だけで、初回に OS のファイアウォールの許可が出る。
仕組みの設計: [`docs/plans/2026-09-11-agent-app-shared-token-pool-design.md`](../../docs/plans/2026-09-11-agent-app-shared-token-pool-design.md)、
契約: [`docs/specs/agent-app-spec.md`](../../docs/specs/agent-app-spec.md) §15。

## 確認待ちに答える

CLI がツール実行の許可や y/n を聞いてくると、会話一覧と会話名の横に「確認待ち」が出る。
**押すと、答える場所まで連れて行く**——その会話を開き、入力先を「端末操作」に切り替えて端末に
焦点を当てる。あとはそのまま打てばよい。

- 答えるのは人。**画面は答え方を用意しない。** `y` が文字として効く CLI（`Proceed? [y/N]` のような
  テキスト入力）と、`y` が無視されて Enter が反転行を確定する CLI（`1. Yes / 2. … / 3. No` の
  選択メニュー）があり、どちらかを見分けるには画面の文言を読むことになる。それは退けた道である
  （→「持たないもの」）。同じ理由で、仮想キー行にも `y` / `n` は置かない
- 何を聞かれているかは端末ミラーにそのまま出ている。画面の同じ場所で読んで、同じ場所で答える

## 受信箱（未読と要対応）

背景で終わったもの・聞いてきたものは、メニューの「受信箱」に集まる。件数はメニューに出て、開くと
登録しているすべてのリポジトリと、会話・タスク・ワークフローを横断して並ぶ。

- **要対応** … 人が答えないと進まないもの。CLI が端末で確認を求めている会話、承認・選択・入力を
  待っているワークフローの実行。答えると消える
- **未読** … 終わってまだ開いていない結果。会話の応答（失敗も）、タスクの実行、ワークフローの実行。
  開くと消える（いま開いている画面に届いたものは、開き直さなくても消える）

項目を押すと、その会話・タスク・ワークフローの画面へ行く（別のリポジトリならリポジトリも切り替わる）。
答え方もフォークも実行も、行き先の画面のものをそのまま使う——受信箱は行き先を指すだけで、新しい操作を
持たない。応答中・実行中のものと、自分で止めたものは出ない。

## 共通指示・定型の依頼・起動時アクション

「設定 > 共通指示」では、すべての依頼へ加える短い指示、推奨スキル、定型の依頼、起動時アクションを
設定できる。生の JSON 編集は行わず、画面のコントロールから `config.json` へ保存する。

- 共通指示はリポジトリ固有・依頼固有の指示を優先する旨とともに各ターンへ付ける
- 推奨スキルは利用可能なスキル／コマンドから選べ、任意の名前も入力できる
- **定型の依頼**は「ボタンの文字」と「依頼の本文」の組を最大 3 つ。入力欄の「定型」に並び、押すと
  本文が**入力欄に入るだけ**で送られない（送るのは人）。既定は「変更をコミットする」と
  「テストを実行する」の 2 つ。コミットも CLI に頼む文で、アプリ自身は git を触らない
  （→「持たないもの」）。行を全部消せば何も並ばない
- 自分が出した依頼の下の「入力欄に戻す」は、本文と添付を入力欄へ戻す（送らない）
- 起動時アクションはスキルまたはシェルコマンド。CLI ごとの新しいセッションで上から一度だけ適用する
- コマンドは作業フォルダで実行し、1 件 60 秒・全体 120 秒。失敗時は「続行」または「停止」を選べる
- 同時実行数は 1〜8。上限時は待ち行列を作らず、その場で再実行を案内する

## 別のリポジトリへ会話を分岐する

会話の途中で、エージェントがいまの作業フォルダの外にある別のローカルフォルダへ書き込む必要に
気づいたときは、自分では書き込まず、返答に `@fork <フォルダの絶対パス>` の 1 行と、そのフォルダで
行う作業の依頼を続けて書く（この作法は「設定 > 共通指示」の「別のフォルダへの書き込みは会話を分岐して
受ける」で依頼のたびに添える。既定 ON）。

- 回答の下に「<フォルダ名> で続ける（新しい会話を分岐）」が出る。押すと、そのフォルダを作業フォルダ
  とする**新しい会話**が分岐先のリポジトリに作られ、元の会話の所在を添えた依頼が最初のターンとして
  自動で送られる。起動方針・エージェント・モデル・権限は元の会話のものを写す
- 分岐先に選べるのは**登録済みのリポジトリ**だけ（このアプリは登録したフォルダの外を触らない）。
  未登録のフォルダなら、押した時点で「リポジトリを追加」のダイアログで登録してから分岐する
- 分岐した会話は、分岐先のリポジトリの会話一覧にふつうの会話と同じ形で並ぶ。行き来は 2 か所の
  リンクで行う: 分岐先の会話ヘッダーの「分岐元: <リポジトリ> › <会話名>」と、元の会話の回答の下の
  「→ <リポジトリ>: <会話名>」
- 分岐先は cwd が違うので CLI の文脈を引き継がない。依頼の本文はエージェントが自己完結した文章で
  書く（元の会話へ戻って続きを頼むこともできる）

## ファイルを添付する

依頼にファイルを付けると、CLI には依頼文の末尾に「添付ファイル: <パス>」として伝わり、CLI 自身の
ファイル読み取りツールで読ませる（画像も同じ。claude / codex / copilot / kiro は画像ファイルを読める）。
`file_flag` を宣言する定義（aider 等）には argv でも渡す。

- **外のファイル**（「添付」ボタン・ドロップ・貼り付け）は userData の `attachments/<ID>/<名前>` へ
  写し、そのパスを伝える。Windows では WSL 表記（`/mnt/c/…`）へ直す。画面は生のパスを持たず、
  以後の参照は ID だけ。上限は 1 つ 25 MB・1 ターン 20 個
- **リポジトリの中のファイル**（「ファイル」画面と変更ビューの「会話に添付」）は写さず、相対パスを
  伝えるだけ。会話の作業フォルダの中にあるものだけ選べる
- 依頼の吹き出しに添付の印が付く。写したものはクリックで既定のアプリ、リポジトリの中のものは
  ビュアーで開く。会話を削除すると写した添付も消える

## CLI の呼び方（tmux）

定義の `interactive` 節（正典は `schemas/agent-cli.schema.json`）で対話起動する。
`interactive` 節を持たない定義は自動的にヘッドレスになる。

```
interactive.command + [continue | resume] + (interactive.write_args | readonly_args) + model_flag model
```

- 会話 1 つ = tmux セッション 1 つ（`agent-app-<会話 ID の先頭 12 桁>`）。tmux サーバは自前の
  ソケット `-L agent-app` に持ち、利用者の tmux とは干渉しない。人が覗くときは
  `tmux -L agent-app attach -t <名前>`（端末上部のエージェント名にマウスを重ねると確認できる）
- 依頼は `send-keys -l`（1 行）か `set-buffer` + `paste-buffer -p`（複数行）で流し込み、少し置いて Enter
- ターンの終わりは定義の `ready_pattern`（末尾 `ready_tail_lines` 行）/ `busy_pattern`（画面全体）/
  `idle_quiet_sec` で判定する。y/n や許可を求めていそうな画面は「確認待ち」として知らせる
- 応答本文は送信前後のスクロールバック（`capture-pane -J -S -`）の差分から、入力欄・枠線・
  フッター・依頼の echo を除いて拾う。読み取れなかったときは端末を見る
- 画面は `capture-pane -e` を 0.25〜1.2 秒ごとに写して xterm に描く（node-pty も attach も使わない）。
  Windows では `wsl.exe -e bash -l` を 1 本常駐させてそこへ流すので、1 回ごとに wsl.exe を起こさない
- 停止は `busy_pattern` に esc が出てくる CLI（claude / codex）には Escape、それ以外は C-c
- CLI の終了コードは、ペインの最後の行として自分で印字したものを読む。tmux は pty が閉じた時点で
  ペインを終了扱いにするが、終了コードはそのまま出てこないことがある（3.4 で実測）
- アプリを閉じても tmux セッションは残り、次に会話を開いたときに再接続する。CLI が終了していたら
  「再起動」か次の依頼で作り直す（エージェント・モデル・モードを変えたターンも作り直す）。
  再開の作法は CLI ごとに違う:

| CLI | 起動 | 作り直すとき |
|---|---|---|
| claude / copilot | こちらで UUID を発行して `--session-id` | `--resume <UUID>` |
| codex | 何も足さない | `codex resume --last` |
| kiro / cursor / ollama | 何も足さない | 再開手段なし（これまでのやり取りを最初の依頼に添える） |

ヘッドレス（tmux なし）の作法は以前のまま（`src/main/agentCli.js` の `SESSION` 表）。Windows では
`wsl.exe -e bash -lc` に載せて WSL の中で走らせる。

## タスクを AI と作る

タスクの作成と変更は、会話と同じ **tmux の端末ミラー**の中で進める。CLI（会話の既定の起動方針で決まる
エージェント）がリポジトリ本体を cwd に起動し、最初の依頼で `statemachine-use` スキルの作成モードと、
保存先 `.statemachine/<名前>/`、見本の頼み方を伝える。AI はこの会話の中で定義（workflow.yaml と
actions/*.md）を直接書き、`run_machine.py --dry-run` で検証してから要約を報告する。定義ができた時点で
「利用可能」になり、確認は「概要」の実行と構成確認で行う（分離した試運転や承認の往復は持たない）。

| したいこと | 操作 |
|---|---|
| 新しいタスクを作る | 「タスク」の ＋ → 目的を書く →「AIと作成を始める」。保存名は空なら目的から決まる |
| AI の質問に答える | 端末の下の入力欄から送る（メッセージ。Shift+Enter で改行）。y/n や矢印キーは「端末操作」に切り替える。端末操作で送信せずに行を足すのは「改行」キー（Shift+Enter / Ctrl+J） |
| ツール実行の確認を省く | 作成設定・編集設定の「権限」を「自動承認」にする（`powershell.exe` の実行なども確認なしで通る）。会話を開いた後に変えても次の依頼から効く。初期値は設定の「会話の既定権限」 |
| 操作を見せる | 「操作の見本」→ 画面（ブラウザ / Windows アプリ）と URL（アプリ名）→ あとは**同じボタンを押していく**。ブラウザは「ブラウザを開く」→（開いた Edge でログインや画面の移動）→「記録を始める」→ 見せたい操作 →「終了してAIへ渡す」の 3 回。Windows アプリは「記録を始める」→ 操作 →「終了してAIへ渡す」の 2 回。押した段だけが AI に伝わるので、**準備の操作は見本に入らない**。取り直すときは「やり直す」。AI が `@record browser <URL>` / `@record windows <アプリ名>` と返したときは、そのカードが自動で開く |
| 自分から操作を見せる | AI が頼んでこなくても、いつでも「操作の見本」から始められる。「ブラウザを開く」と「終了してAIへ渡す」は、AI へ渡す文が**入力欄に入るだけ**で、まだ送られない。何を見せるつもりか・いま見せたものの補足をそこに書き足して「送信」を押す（送るまで次の段へは進まない）。頼んでいない見本を受け取った AI は、いまの作業に区切りをつけ、どの工程のためのものか分からなければ先に聞く |
| 既存のタスクを変える | 実行詳細の「手順」→「編集」。押した時点で AI が起動し、今の定義を読んで要約してから、変えたい点を聞く。「‹ 工程に戻る」で工程へ戻る |
| 毎回変わる値を入れ直さない | 「概要」の「実行条件」は、**前回そのタスクで入れた値**が既定で入る（今回打った値 → 前回の値 → 定期実行の既定値）。覚えるのは値だけで、置き場は agent-app の設定（`config.json`）。前回の値が今と違うときだけ、欄の下に「前回: …」が出る |
| 失敗した実行を直してもらう | 「履歴」の失敗した行の「AIに直してもらう」。「手順」→「編集」と同じ会話が開き、失敗の要点と実行ログの末尾（60 行・2000 字まで）が最初の依頼として**入力欄に入る**。ログがリポジトリの中にあれば所在も添える。何を直したいかを足して「送信」を押す |
| 会話をやり直す | 端末が終了・消失したら「再接続」。会話は `sessions/` に残り、次に開いたときに tmux へつなぎ直す |
| 内部の工程を確認する | 「手順」タブ。従来の工程エディタで、そのまま直して保存もできる |

**見本の取り方は画面の種類で違う。** Windows では AI は WSL の tmux で動いていて、ブラウザや Windows アプリは
Windows 側にある。WSL から Windows 側の `playwright-cli` を起こすことはできないので、次の 2 通りに分ける。

| 画面 | 記録するのは | 流れ |
|---|---|---|
| ブラウザ | **AI 自身**（WSL 側の `playwright-cli`） | ボタン 1 つを 3 回押す。①「ブラウザを開く」で agent-app が Windows 側の Edge をリモートデバッグ付き（`http://localhost:9222`、記録専用のプロファイル）で起こし、そのことを**固定文**（`@recording open` で始まり、接続先を含む）として入力欄に入れる（利用者が確かめて「送信」）。AI は `playwright-cli attach --cdp=…` で接続だけして待つ——ここで利用者がログインや目的の画面までの移動をする。②「記録を始める」で固定文（`@recording start`。いま開いているページを含む）がそのまま渡り、AI が `recording-start` で記録を始めて利用者の操作を待つ。③「終了してAIへ渡す」で固定文（`@recording stop`）が入力欄に入り、送ると AI が `recording-stop` で止めて記録の行を `.statemachine/<名前>/recordings/<時刻>-browser.md` に保存し、それを根拠に工程を組む。途中で「やり直す」を押すと固定文（`@recording cancel`）が渡り、AI は取りかけの記録を保存せずに捨てる |
| Windows アプリ | **agent-app**（Windows 側の `winauto`） | 「記録を始める」で agent-app 自身が Windows 側で記録を起こし、**始まったことは固定文（`@recording start`）で AI へ渡す**（AI は記録の到着まで待つ）。「終了してAIへ渡す」でできた Markdown（`.statemachine/<名前>/recordings/<時刻>-windows.md`。操作の行と毎回変わる値の候補）の所在を WSL 表記（`/mnt/c/…`）へ直して入力欄に入れ、利用者が「送信」で渡す。AI 自身には記録を起こさせない（依頼文でそう伝える） |

ブラウザの見本の流れはすべて依頼文に仕込んであり、AI は固定文が届く前にブラウザを起こしたり記録を始めたり
しない。ボタンを押す番になると AI がそう言う（そのとき見本のカードは自動で開く）。**ログイン・画面の移動は
①と②の間に済ませる**——②を押してからの操作だけが見本になるので、毎回変わらない準備が工程に混ざらない。
Linux / macOS でも同じ流れで、Edge（無ければ Chrome）はこの端末で開く。

**見本は AI が頼んだときだけのものではない。** 見せた方が早いと思ったら、いつでも「操作の見本」から始めて
よい。①と③は AI へ渡す文が入力欄に入るだけなので、そこに「何を見せるか」「いま見せたものの補足」を書き足して
から「送信」を押す（送るまで次の段へは進まない。文の中の `@recording …` の行を消すと、その段は届かなかった
ものとして扱う）。②と「やり直す」は押した時点で渡る。

### 生成する定義の形

statemachine-use の作成モードの原則に沿う（`SKILL.md` ステップ 2）:

- 1 ステート 1 工程。`action_file: actions/<id>.md`。本文の末尾は単一指示。
- 出力契約は `output_validator: startswith:<ラベル…>`（既定は `OK,FAILED`）。
- 分岐は `condition_rule`（`startswith:last_output:<ラベル>`）。`check` を宣言した工程は `equals:check_ok:true` で進む。
- 画面操作は `playwright-cli` / `windows-app-automation` スキルを本文で名指しする。記録した操作は role と名前で載せる。
- 終端は `complete`（完了）と `failed`（失敗）。どこからも行かない終端は書かない。
- `maker.json` は「手順」タブの編集画面が読み戻すための写しで、実行には使わない（AI が書かなくてもよい）。

### 次の工程（「手順」タブ）

工程ごとに、行き先を上から順に並べる。決め方は 4 つ。

| 決め方 | 何を見るか | 書かれるもの |
|---|---|---|
| 回答が指定の言葉で始まる | 出力の 1 行目がその語で始まるか | `condition_rule: startswith:last_output:<語>` |
| 条件に当てはまる | その文にあてはまるか（AI が見る） | `condition: <文章>` |
| 常に | 条件なし | 条件を付けない |
| 詳細条件 | 読み込んだ式をそのまま | `condition_rule: <式>` |

何も足さなければ「できた → 次へ」「できなかった → 中止」になる。行き先は次の工程・完了・中止のほか、
**定義が持つ終わり方**（承認 / 差し戻し / 判別できない…）や、前の工程へ戻ることも選べる。
第 1 行の出力契約を書くのは、行き先が**すべて**回答の先頭で決まるときだけ。

### 記録がうまくいかないとき

ブラウザの見本は、この端末が Edge を起こし、**AI（Windows では WSL）側の `playwright-cli`** が接続して記録する。
Windows アプリの見本は `winauto` を**この端末から直接**呼ぶ（WSL には橋渡ししない）。「手順」→「その他 →
実行環境 → 接続を確認」でこの端末側の道具が呼べるかを先に確かめる。

| 症状 | 見るところ |
|---|---|
| 「Edge か Chrome が見つかりません」と出る | Microsoft Edge を入れる。Windows は既定の置き場（Program Files / ユーザーの AppData）、Linux / macOS は PATH か Applications で探す |
| Edge は開くが「応答しません」と出る | ポート 9222 を別のブラウザやツールが使っている。そのブラウザを閉じてからもう一度「ブラウザを開く」 |
| Edge がいつもと違うプロファイル（ログインしていない）で開く | 記録専用のプロファイルで開く仕様（近年の Edge / Chrome は既定のプロファイルでリモートデバッグを受け付けない）。1 回ログインすれば次回からは残る |
| AI が「接続先に届かない」と言う | WSL のネットワークが既定（NAT）だと、WSL の `localhost` は Windows 側に届かない。`%UserProfile%\.wslconfig` に `[wsl2]` `networkingMode=mirrored` を書いて `wsl --shutdown` する。AI 側に `playwright-cli` が無いときは WSL の中で `npm install -g @playwright/cli@latest` |
| 操作したのに記録が空になる | 記録するのは**アプリが開いた Edge の窓**の中の操作だけ。別に開いていたブラウザで操作しても入らない |
| Windows アプリの見本が取れない | `winauto` は Windows 上でだけ動く（`python tools/winauto/install.py`）。Linux / macOS では見本の画面にそう表示する |
| AI が固定文の前にブラウザを起こそうとする | 依頼文で「固定文が届く前に起こさない」と伝えている。それでも起こしたら、端末操作で止めて（Ctrl+C）「ブラウザを開く」から押し直す |
| 準備の操作まで工程に入ってしまった | ①「ブラウザを開く」の後に②「記録を始める」を押さずに操作している。「やり直す」で取りかけの記録を捨てて、①からやり直す |

agent-app の「手順」タブでは、旧来の「その他 → 操作を記録」は表示しない。ブラウザや Windows アプリの操作を見せるときは
「AIと編集」で tmux を開き、入力欄の「操作の見本」を使う。AI が返答に `@record browser <開始 URL>` または
`@record windows <アプリ名>` を単独行で返した場合も、同じ記録欄が自動で開く。

### 画面の言葉

内部の綴りをそのまま出さない。画面には次の言葉を使う（`test/automation-app.test.js` が検査する）。

| 内部 | 画面 |
|---|---|
| ステートの ID | 工程ID（「詳細設定」の中） |
| 識別名・フォルダ名 | 保存名 |
| `output_validator` の第 1 行 / 出力契約 | 回答が指定の言葉で始まる |
| `check` / 終了コード 0 | 完了確認／確認できたら |
| `check_retries` | 再試行回数 |
| transitions / 遷移 | 次の工程 |
| 既定の OK / FAILED | できた／できなかった |
| `{{key}}` / 入力パラメータ | 毎回変わる値 |
| `--dry-run` | 構成を確認 |
| `--agent-cli`（agent-tools の定義名） | 使う AI |
| 終端ステート | 終わり方（いくつあっても行き先に選べる） |

### 画面を直すときの落とし穴

renderer で **`const api = …` のように preload が公開した名前を宣言してはいけない**。
`contextBridge` が置く `window.api` は再定義できないので、宣言するとスクリプトの実行前に
`Identifier 'api' has already been declared` で落ち、**画面が真っ白**になる。共有ワークベンチ
（`src/renderer/automation/`）は Shadow DOM の中で動くが、`window.api.automation` を読むだけにする。

## 保存先

Electron の userData（macOS は `~/Library/Application Support/agent-app`）を主な置き場にする。

```
config.json          登録リポジトリ、アプリ設定、共通指示・推奨スキル・起動時アクション、実行方針・tier・同時実行数、
                     受信箱で「見た」結果の時刻（項目ごと。作業の状態は持たない）。読めないときは同じ場所に
                     config.json.broken-<時刻> として退避し、既定の設定で起動して最初にそう知らせる
logs/crash.log       メインの未処理の例外・未処理の Promise、画面が落ちた・固まった記録（1 MB で crash.log.1 へ回す）
sessions/<id>.json   会話 1 つ。リポジトリ・次のターンの方針 / CLI / モデル / モード・transport（tmux | headless）・作業フォルダ・
                     メッセージ列（各依頼の起動条件・添付、応答の思考 / 回答 / 実行情報）・CLI ごとのセッション ID と見たメッセージ数・
                     tmux で動いている CLI の起動条件。タスクを AI と作る会話は kind: task で保存名（task.machine）に紐づき、
                     会話一覧には出ない。別のリポジトリから分岐した会話は分岐元（元の会話・そのリポジトリ・分岐した応答）を持つ。
                     エージェントを切り替えたときの端末画面は控え（terminalSnapshots）として最大 12 枚まで同じファイルに残す
attachments/<id>/    依頼に添えた外のファイルの写し
exports/             「テキストに書き出す」で作ったテキスト（会話名と時刻で名前を付ける）
run-history/         タスクとワークフローの実行履歴（リポジトリごとに 1 ファイル・各 100 件まで）
audit-feed/          監査へ渡す申告（日ごと。会話のターン・実行・引き受けた依頼を 1 行ずつ追記する）
audit/               監査が書いた集計と判定（記録・観測・洞察・成果物の合否・レポート）。書くのは監査の側だけ
audit-config.json    監査へ渡す設定（書き先・申告の置き場・Windows 側のホーム）。毎回作り直す
artifact-share/      公開先リポジトリの作業用の写しと、出したブランチの記録
share/               共有の状態。出した依頼・受けた依頼・公開した会話と、引き受けた依頼の台帳（ledger、日ごと）、
                     引き受けた作業の作業場（scratch/<依頼 ID>/。実行が終われば消える）
updates/             自動更新で取得した配布物
```

userData の外に置くものもある。

| 置き場 | 中身 |
|---|---|
| `~/.local/state/agent-app/cli-sessions/<会話 ID>/<CLI>/` | codex / kiro を再開するための控え（セッション ID と、kiro に渡す一時的なエージェント定義）。Windows では WSL 側のホーム |
| `~/.agents/flow/bus/`、`~/.agents/flow/logs/` | ワークフローの実行の投函・実行状態・起動ログ。agent-flow と共有する（`AGENT_APP_FLOW_BUS` で変えられる） |

リポジトリ側に置くのは、作業フォルダを使うときの `.worktrees/<名前>`（git の管轄）と
`.git/info/exclude` の 1 行、タスクの定義 `.statemachine/<名前>/`（AI との会話で書く。下書きの印
`teaching.json` と見本の記録 `recordings/` を含む）、ワークフローの定義 `.agents/workflows/`。
CLI 自身のセッションログ（`~/.claude/projects` など）は CLI の管轄。

## 保存データを整理する

「設定 > 保存データ」で、アプリが作ったファイルを種類ごとに数え、選んだ種類だけ消す。
タブを開くと数え始め、それぞれの大きさが行の右端に出る。消しても作業に影響しないものは
最初から選ばれていて、選んだ分の合計が足元に出る。「削除する」で消し、空けた大きさを返す。

| 種類 | 消すもの | 既定 |
|---|---|---|
| 使い終わった一時ファイル | 一時フォルダに残った、AI とのやり取りの出力・画面操作の記録・更新の入れ替えの記録。いま動いている自分のものは残す | 選ぶ |
| 参照されていない添付ファイル | どの会話からも参照されていない添付の写し | 選ぶ |
| 終了した会話の再開情報 | 消えた会話に対応する、CLI を再開するための控え | 選ぶ |
| 登録を外したフォルダの実行履歴 | いま登録していないリポジトリの実行履歴 | 選ぶ |
| 取得済みの更新ファイル | 入れ替えが終わった配布物 | 選ぶ |
| 古い共有の記録 | 30 日より前に引き受けた依頼の台帳と、残った作業場 | 選ぶ |
| 古い監査への申告 | 30 日より前の申告。監査が書いた集計・洞察は残す | 選ぶ |
| 端末画面の控え | 会話に残した実行中の画面。やり取りの本文は残す。動いている会話の分は消さない | 選ぶ |
| 記録用ブラウザの保存データ | 記録専用のプロファイル。消すと次の記録でログインからやり直しになる | 選ばない |

**リポジトリの中は消さない。** 作業フォルダ（`.worktrees/<名前>`）は会話の「作業フォルダ」から、
タスクとワークフローの定義・下書き・見本の記録はそれぞれの画面から消す。利用者の成果物と
隣り合っていて、消してよいかの判断が一覧の 1 行では足りないため。ワークフローの実行の記録
（`~/.agents/flow/`）も、agent-flow と共有する置き場なのでここでは触らない。

## 持たないもの

- GitHub 連携（PR・Issue・クラウドセッション）
- ツール呼び出しの逐次承認 UI。何を聞かれているかを読み解くのも、答えを決めるのも人。
  「確認待ち」が足すのは**答える場所までの近道**だけで、答え方（はい／いいえ、`y` の 1 押し）は
  用意しない——CLI によって `y` が効いたり無視されたりし、見分けるには文面の解析が要るため。
  自動で `y` を送る仕組みも持たない（自動承認は CLI 自身の起動引数で行う）
- 応答の完了・確認待ちを OS の通知で知らせる以上のこと（通知に本文や操作は載せない）
- 受信箱のための通知・予定・待ち受けの仕組み。受信箱は会話・実行・確認の記録から「未読」「要対応」を
  導くだけで、自分の状態を持たない
- タスクの試運転・承認の往復（AI の候補を JSON で受けて試運転してから昇格する仕組み）。定義は会話の中で
  書き、確認は実行と構成確認で行う
- 差分の適用・取り消し、コミット・マージ・push。変更ビューは読むだけ（git へ書くのは
  worktree の追加・削除とブランチ作成だけ）
- ファイルの編集。ビュアーは読むだけ（「••• > 既定のアプリで開く」で外部アプリへ）

### コマンドタスク

「新しいタスク」画面の「新しいコマンドタスク」から、タスク名、コマンド、タイムアウト、繰り返し（毎日・毎週・一定間隔）を入力して保存します。保存先はこのリポジトリまたは共通設定を選べます。作成後はそのタスクが選択されます。

タスクの概要にある「名前・コマンドを編集」で内容を変更でき、「今すぐ実行」で一度だけ実行できます。AI は使用しません。環境変数やフックなどの既存設定は保持します。複雑な cron の予定も、実行条件を維持したまま名前とコマンドを編集できます。

「有効にする」は個別の予定の有効・無効です。「定期実行を開始／停止」はリポジトリ全体のスケジューラーを操作し、そのリポジトリの有効な予定に共通して作用します。状態ラベルの「有効」は予定が有効であることを示し、実行中という意味ではありません。

空白を含む引数は引用符で囲み、パイプ等が必要な処理はスクリプトにまとめて指定してください。


コマンドの文字列は、改行で複数のコマンドを指定できます。空行は無視し、上から順に実行します。終了コードが0以外、タイムアウト、起動失敗のいずれかで停止し、後続のコマンドは実行しません。各行は同じ作業ディレクトリ・環境変数を使う別プロセスです（シェルの `cd` や `export` で行をまたぐ状態変更はできません）。タイムアウトは各コマンドに適用します。WindowsではWSL側のagent-loopも複数行対応版へ更新してください。

```text
python3 scripts/prepare.py
python3 scripts/check.py
```

定期実行の「予定を編集」では、自動実行のエージェントとモデルを予定ごとに指定できます。空欄は実行環境の既定値を使います。詳細設定の予定も「現在の設定を維持」で実行条件を残しながら編集できます（実行環境の agent-loop も更新してください）。手動実行の結果とログは、アプリを開いている間、リポジトリ・タスクごとに保持します。


## 作業を再利用する

- 会話の「••• → この作業を定型化」で、AIが会話中の訂正を含めて手順を整理します。知識・判断基準を再利用するものにはスキル、1つの担当が順に進める作業にはタスク、複数担当の分担・独立レビュー・並列処理が必要な作業にはワークフローを提案します。理由と内容を確認して種類や文章を編集し、保存先のリポジトリを選択（またはフォルダを追加）して「新しいセッションで作成」を押してください。元の会話を継続せず、新規セッションで作成します。スキルは保存先の配置規約に従い、規約がなければ `.agents/skills/<name>/SKILL.md` に保存します。
- タスクの履歴にある「この条件を使う」で、その実行の入力値・AI・モデルを概要へ戻せます。実行はボタンを押してから始まります。過去の手順そのものを戻す機能ではなく、現在の手順で実行します。条件が記録されていない古い履歴には操作を表示しません。ワークフローでは実行詳細の「同じ内容で再実行」を使えます。
- 実行条件と予定の入力欄で「今日」「昨日」「今月」「前月」を選ぶと、実行時の日付から値を決めます。「固定値」に戻せば直接編集できます。日付は実行する端末の現地日付です。定期実行にも使う場合は、実行側のagent-loopとagentcoreも今回の変更を含む版へ更新してください。
- AIの回答やタスクの実行結果に作業フォルダ内のファイルへの相対リンクがあれば、ファイル名を押して既定のアプリで開けます。ファイルが移動・削除されている場合はエラーを表示します。

定型化の検討は選択中のAIを読み取り専用で呼び出します。会話が長すぎる場合は省略せず、範囲をまとめ直すよう案内します。AIの判断と成功の判定が正しいかは、引き継いだ手順と完了条件で確認してください。

### 集めた記録を見る（設定 > 利用状況）

会話とタスクの実行の記録から、使用量と成功率を出す。集めるのは 1 時間ごと（間隔は変えられる。
0 にすると「今すぐ集める」だけ）。会話や端末が動いている間は集めないので、作業の邪魔にならない。

| 面 | 見えるもの |
|---|---|
| 利用枠 | AI ごとのサービス上限に対する使用率・リセット日時・取得日時。手動上限は別記 |
| 使用量 | 今日・今月・全期間（UTC 基準）の実測・推定トークンと成功率。AI・用途・モデル別の内訳 |

利用枠は期間の選択によらず最新の観測を表示する。取得できない値は「取得できず」、リセット日時を過ぎた観測は「更新待ち」と表示し、トークン数からサービスの使用率は推測しない。収集の設定は折りたたみで開く。

数字は agent-audit が出す。入っていない PC では「見つかりません」と 1 行出るだけで、会話も
タスクも止まらない。

### 定型化したものを公開し、実測で直し続ける

**言葉の使い分け**: 同じLANの参加者に作業を依頼したりセッションを見せたりするのが「共有」、
リポジトリへ出して人に渡すのが「公開」です。設定も画面も、この 2 つを分けています。

公開先のリポジトリは「設定 > スキル」に入れます。個人のリポジトリなら「公開先のmainへ直接出す」
を選べます。入れていない間は、どの画面にも公開の操作は出ません。

公開はどの画面からでも、そのものが居る場所で押せます。

| 出すもの | 押す場所 |
|---|---|
| スキル | 設定 > スキル。一覧の行の「公開する」 |
| タスク | タスクの「概要」。定期実行の下の「公開」 |
| ワークフロー | ワークフローの「概要」。いちばん下の「公開」 |

まだ公開していないものには、名前の右に「未公開」が付きます。スキルの一覧では未公開のものを
先頭にまとめます。公開したあとで中身を直すと「未公開の変更」に変わり、「公開し直す」で出せます。
中身が同じままなら二度は出しません（更新時刻ではなく中身で見ます）。

押すと `share/<種別>-<名前>` ブランチとして公開先へ出ます。出所（元のリポジトリ・コミット・会話）は
成果物の隣に残ります。取り込むかどうかは人が決めます（マージはこちらでは行いません）。

同じものの実行が続くと、実測から合否（基準を満たす / 様子見 / 使わない）が付きます。基準を割った
ものには同じ場所に「改善案を出す」が出て、失敗の証跡を渡して直させた案が `improve/<種別>-<名前>`
ブランチとして出ます。未取り込みの改善案があるうちは、同じものに次の案を出しません。

### 使えるスキルを見る（設定 > スキル）

リポジトリとAIを選ぶと、そのAIが読むスキルを名前・説明・版で一覧にします。そのAI専用の置き場と、
どのAIも読む共通の置き場の両方を見ます。同じ名前があれば、選んだリポジトリの中のものを優先します。

公開できるのはリポジトリの中にあるスキルだけです。共通の置き場にある個人のスキルは一覧に出ますが、
公開の操作は出ません。

### 過去の会話を検索して引き継ぐ

サイドバー上部の「会話を検索」から、アプリ内の会話とCodex・Claude・Copilot CLI・Kiro・VS Codeの保存済み会話を探せます。検索の入口はこのボタンに統一しています。

タイトル・本文に加え、エージェント、日付、リポジトリで絞り込めます。「絞り込み」では取得元・モデル・アーカイブも指定できます。検索を閉じると元の画面へ戻り、入力中の文章は保持されます。

会話を選択して内容を確認し、末尾または途中の応答の「フォーク」を押します。ダイアログでフォークする位置、リポジトリ、エージェント・モデル・権限、フォーク先を選択します。フォーク先が「セッション」なら指定位置までの文脈を新しい会話へ渡します。「タスク」「ワークフロー」は専用の作成画面、「スキル」は新しい会話画面で、その形の作り方として整理して作成を開始します。元の会話、ファイル変更、実行中の処理は複製・変更しません。

開いている会話も「••• → この会話をフォーク」と、完了した回答の下の「フォーク」から同じダイアログでフォークできます。フォークする位置はダイアログで選び直せます。

外部の履歴取得にはPython 3が必要です。通常の履歴保存先を自動検索し、保存形式が未対応・破損・サイズ上限超過の場合は取得エラーとして表示します。VS Codeの「Chat: Export Chat...」で保存したJSONは、「絞り込み → 会話のJSONを取り込む」から追加できます。追加した保存先は次回起動時にも使用します。画像やツールの内部状態は引き継ぎ対象に含みません。

外部会話の読み取りは、Kiro CLIの現行SQLite形式（`conversations_v2`）と従来形式に対応します。VS CodeのJSONL更新履歴は1行ずつ復元するため、保存ファイルが64MBを超えていても検索・プレビュー・引き継ぎに利用できます。本文を途中で切り捨てることはありません。

検索結果は1ページ最大50件で、「前へ」「次へ」で切り替えます。本文もページ単位で検索し、一致する会話が少ない場合は次の範囲を「次へ」で調べます。検索条件を変えると、選択中の会話と詳細表示はすぐにクリアされます。

共有の有効・無効は、設定の「共有を使う」で切り替えます。「自動で引き受ける」のチェックがなければ、選んだ依頼だけを手動で引き受けます。以前の「受けない」設定も手動として扱います。

### 自分のセッションを公開する

会話の「••• → セッションを公開」で、同じ合言葉の参加者に会話を公開できます。ターン終了後も公開でき、公開中は後続の会話も反映します。「公開を停止」で取り下げます。公開状態は再起動後も保持し、設定の「共有を使う」が無効な間は配信しません。

「共有」の一覧に公開セッションが並びます。会話、閲覧用の端末表示、「ひとこと」、フォークを同じ画面で利用できます。終了後も保存された会話を読んでコメントできます。ひとことはAIへの依頼とは別で、500文字まで・直近50件を保持します。送信に失敗した場合は入力が残るため、再送できます。新しい公開を探すときは「更新」を押してください（一覧は30秒間保持します）。

「会話を検索」は通常ローカルだけを調べます。「共有も検索」を押すと、現在の条件で参加者の公開セッションも検索します。条件を変更するとローカル検索に戻ります。結果・プレビュー・フォーク先の選択はローカルと同じで、共有元のユーザー名が付きます。元の会話のリンクから共有検索に戻れます。

検索結果は1ページ50件で、本文は選択時に取得します。公開側でも読む量を制限するため、一致がなくても「次へ」が出る場合があります。取得できない参加者がいても、ほかの結果は表示します。公開停止や更新があった場合は、会話を開き直してください。公開側のアプリが起動し、共有が有効になっている必要があります。

### タスク本文の編集と削除

プロンプト型は詳細の「プロンプトを編集」で本文を変更できます。定期実行の条件、エージェント、モデルは維持され、以後の手動実行・定期実行に新しい本文を使います。

全タスク型の詳細から「削除」を選べます。タスク登録と定期実行・フックなどの設定を削除し、ステートマシン型では同じ定義に紐づくリポジトリ設定・共通設定の予定をまとめて削除します。ステートマシン本体と実行履歴は残します。削除済みのステートマシンは `.agents/task-state.yaml` に記録し、ファイルから再表示されることを防ぎます。他のタスクや別リポジトリの設定は維持します。

この操作には `taskMutation` 対応の agent-loop が必要です。未対応の場合は更新案内を表示し、設定は変更しません。
