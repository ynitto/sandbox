# 夜間定型メニューの検収

## 1. 朝に受け箱を見る

Dagu の実行履歴で各メニューのステップの終了コードとログを確認する。手動の `submit` では標準出力に出た依頼 ID を控える。

```powershell
python copilot_app_job.py status --dir C:/work/my-folder --last 20
```

別の受け箱を使っている場合は、依頼時と同じ `--box` を渡す。`status` は各フォルダの件数と最近の ID を表示する。`pending` は未着手、`running` は着手済み、`done` は処理済みの依頼文、`results` は結果報告。Dagu 例では ID 末尾のメニュー名と実行時刻で対象を探し、同じ ID のファイルを照合する。

## 2. 結果と下書きを読む

`results/<ID>.md` の 1 行目で `status: ok` または `status: failed` を確認する。3 行目以降の報告を読み、`done/<ID>.md` にある依頼文から入力と出力先を確認する。`ok` でも成果物を開いて照合し、人が採否を決める。

| メニュー | 検収する内容 |
|---|---|
| [docs-followup](./docs-followup.md#検収観点) | 指定パスの差し替え案をコード差分と照合し、対象文書・節と根拠を確認する。 |
| [test-maintenance](./test-maintenance.md#検収観点) | 指摘・ケース ID・コードの対応と期待結果を確認する。既存テストを削除・無効化する案がないか確認する。 |
| [changelog-draft](./changelog-draft.md#検収観点) | コミット・PR の範囲、既存項目との重複、書式、破壊的変更の記載を確認する。 |
| [drift-scan](./drift-scan.md#検収観点) | 元の検査結果と照合し、指摘の網羅性、重複、影響に応じた優先度を確認する。 |

どのメニューも指定パスに実物があるか、今回の依頼の成果物か、根拠のない断定がないかを確認する。

## 3. 終了コードごとに対応する

| 終了コード | 対応 |
|---|---|
| 0 | 結果と成果物を検収する。 |
| 1 | `status: failed` の報告から原因を読み、入力と依頼文を直してから新しい依頼を出す。 |
| 3 | 未着手の依頼は取り下げ済み。アプリの起動と自動実行の設定を確認して再試行できる。Dagu 例はこのコードだけを自動再試行する。 |
| 4 | 再試行禁止。元の依頼が受け箱に残り、進行中のセッションや後続の自動実行が処理し得るため、新しい ID で出すと二重に作業される。同じ ID の状態と結果を追う。 |

`failed` では、まずパスが作業フォルダから読めるか、入力ファイルが検査結果の最新版か、出力先が書き込めるかを確認する。対象が広すぎたら対象フォルダや期間を絞る。入力や対象が曖昧なら `--param` を修正し、`generate` で再展開して依頼文を確認してから出し直す。途中の成果物が残っていたら内容を確認し、必要に応じて別の `output` を指定する。

## 4. 未回収の依頼を追う

`running` にあり結果がない場合は、アプリのセッションと成果物の途中経過を確認する。取りかかってから既定で 2 時間が経過し、同じ ID の結果がなければ、次にアプリが依頼を取りに来たときに同じ依頼が優先して出し直される。経過時間は `next --stale <秒>` で変更できる。新しい依頼は作らず、元の ID で結果を追う。

## 5. 結果を保管する

検収後、必要な成果物と対応する `done/<ID>.md`・`results/<ID>.md` をまとめて保管する。受け箱から削除する前に、依頼と結果の ID が一致し、再確認に必要なファイルが保管先で読めること、同じ ID が `running` に残っていないことを確認する。
