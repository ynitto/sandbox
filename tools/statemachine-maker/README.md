# statemachine-maker

statemachine-use スキルで動くステートマシン（`.statemachine/<識別名>/`）を、**工程列と人の操作の記録**から
組み立て・編集する Electron アプリ。agent-dashboard の定常業務作成（手順ビルダー・操作の記録）を
切り出し、単体で動くようにしたもの。

- **フォルダを登録して使う**。見に行くのは登録したフォルダの `.statemachine/` だけで、それ以外は
  読み書きしない。一覧は右に登録したフォルダ、左にそのフォルダのステートマシンを並べる。
- 画面はライトトーンの **1 列**。工程カードを縦に並べ、選んだカードだけがその場で開いて設定欄になる
  （Zapier 型）。畳んだカードは「動詞で始まる 1 文の要約」だけ（Apple Shortcuts 型）、カードの間に
  次にどこへ行くかを縦に積む（Power Automate 新デザイナー型）。記録・中身・AI・動かす・設定はダイアログ。
- **画面に出す言葉に内部の用語を入れない**。YAML の項目名・コマンドの綴り・ステートの呼び名は
  人が読む言葉に直してから出す（下の対応表）。
- 見た目は **設定（色・間隔・文字の大きさ・種類の色）** と **ユーザー CSS**（`userData/custom.css`）で
  変えられる。色・余白・幅・文字はすべて CSS 変数。

## 起動

```bash
cd tools/statemachine-maker
npm install
npm start
```

初回は「フォルダを登録」でステートマシンを置くフォルダ（リポジトリのルートなど）を登録する。
そのフォルダの `.statemachine/` にあるものが左に並ぶ。フォルダは何個でも登録でき、右で切り替える。
登録を外してもフォルダの中身は消えない。

検証・実行には Python 3 と PyYAML、statemachine-use スキル（`.github/skills/statemachine-use/scripts/`）が要る。
スキルは選んだフォルダから上へ辿って探し、見つからなければ「⚙ 設定」でフォルダを指定する。

## 使い方

| したいこと | 操作 |
|---|---|
| フォルダを増やす | 右の「フォルダ」の ＋。登録したフォルダだけを見に行く |
| 新しく作る | 「＋ 新しいステートマシン」→ 名前・目的 → 工程を種類（ブラウザ / Windows アプリ / スキル / コマンド / AI）で足す → 保存 |
| 人の操作から起こす | 「記録」。ブラウザは URL を入れて記録を開始（`playwright-cli` が見える形で開く）→ 操作 → 終了。Windows アプリは Windows 上で `winauto record` を起こす。別の端末で取った記録（`recording-stop` の出力 / JSONL）は貼り付けで受ける |
| 次にどこへ行くか | 工程の「次にどこへ行くか」に、決め方（結果の名前 / 文章の条件 / いつでも / 条件式）と行き先を並べる。上から順に見て、最初にあてはまったところへ進む |
| できたかを機械で確かめる | 工程の「できたか確かめるコマンド」を書く。うまくいったときだけ次へ進む |
| 既存を編集する | 一覧から選ぶ。手で書いた定義（文章の条件・無条件・条件式・終わり方が 3 つ以上）もそのまま画面の行になる |
| 点検・実行 | 「動かす」。点検（抜けが無いかを見るだけ）と実行を、様子を流しながら行う |
| AI に補完させる | 「AI 補完」の指示文（statemachine-use の作成モード向け）をコピーしてエージェント CLI に貼る。待機・読み取り・想定外の画面の扱いを足してもらう用途 |
| 見た目を変える | 「⚙ 設定」→ 見た目。アクセント色・密度・文字サイズ・種類の色を保存する。「ユーザー CSS を開く」で `custom.css` を編集し、「再読み込み」で反映する（`:root` の変数を何でも上書きできる） |

## 生成する定義の形

statemachine-use の作成モードの原則に沿う（`SKILL.md` ステップ 2）:

- 1 ステート 1 工程。`action_file: actions/<id>.md`。本文の末尾は単一指示。
- 出力契約は `output_validator: startswith:<ラベル…>`（既定は `OK,FAILED`）。
- 分岐は `condition_rule`（`startswith:last_output:<ラベル>`）。`check` を宣言した工程は `equals:check_ok:true` で進む。
- 画面操作は `playwright-cli` / `windows-app-automation` スキルを本文で名指しする。記録した操作は role と名前で載せる。
- 終端は `complete`（完了）と `failed`（失敗）。どこからも行かない終端は書かない。
- `maker.json` は画面が読み戻すための写しで、実行には使わない。

## 検証

```bash
cd tools/statemachine-maker
npm test          # 往復・記録・保存・結合（スキルの run_machine.py --dry-run）・実機の起動
npm run smoke     # 実機の起動だけを xvfb 越しに走らせる（表示先の無い Linux 用）
npm run lint      # eslint（devDependencies が要る）
```

- 結合テスト（スキルの `run_machine.py --dry-run`）は python3 + PyYAML があるときだけ走る。
- **実機の起動**（`test/electron-smoke.test.js`）は Electron を本当に立ち上げ、画面が描画される
  ことまで見る。electron のバイナリ・表示先・playwright が揃っているときだけ走り、CI（実行時
  依存だけを入れる）では skip される。表示先の無い Linux では `npm run smoke` を使う。

## 次にどこへ行くか

工程ごとに、行き先を上から順に並べる。決め方は 4 つ。

| 決め方 | 何を見るか | 書かれるもの |
|---|---|---|
| 結果の名前で | 出力の 1 行目がその語で始まるか | `condition_rule: startswith:last_output:<語>` |
| 文章の条件で | その文にあてはまるか（AI が見る） | `condition: <文章>` |
| いつでも | 条件なし | 条件を付けない |
| 条件式で | 読み込んだ式をそのまま | `condition_rule: <式>` |

何も足さなければ「できた → 次へ」「できなかった → 中止」になる。行き先は次の工程・完了・中止のほか、
**定義が持つ終わり方**（承認 / 差し戻し / 判別できない…）や、前の工程へ戻ることも選べる。

第 1 行の出力契約を書くのは、行き先が**すべて**結果の名前で決まるときだけ。文章の条件が混ざる工程に
契約を足すと、名前で始まらない出力が失敗扱いになり、元の定義では通っていた道が通らなくなる。

## 画面の言葉

内部の綴りをそのまま出さない。画面には次の言葉を使う。

| 内部 | 画面 |
|---|---|
| ステートの ID | 工程の記号（「詳しい設定」の中） |
| 識別名・フォルダ名 | 保存名 |
| `output_validator` の第 1 行 / 出力契約 | 結果の名前 |
| `check` / 終了コード 0 | できたか確かめるコマンド／確認できたら |
| `check_retries` | やり直す回数 |
| transitions / 遷移 | 次にどこへ行くか |
| 既定の OK / FAILED | できた／できなかった |
| `{{key}}` / 入力パラメータ | 毎回変わる値 |
| `--dry-run` | 点検する |
| `--agent` | 使う AI |
| 自然言語の条件（`condition`） | 文章の条件で |
| 無条件の遷移 | いつでも |
| `condition_rule`（読み込んだ式） | 条件式で |
| 終端ステート | 終わり方（いくつあっても行き先に選べる） |

`test/app.test.js` が、画面の言葉に内部の綴りが混ざっていないことを検査する。実機の煙試験も
描画された文字を見る。

### 画面を直すときの落とし穴

renderer で **`const api = …` のように preload が公開した名前を宣言してはいけない**。
`contextBridge` が置く `window.api` は再定義できないので、宣言するとスクリプトの実行前に
`Identifier 'api' has already been declared` で落ち、**画面が真っ白**になる（自分のログも出ない）。
ブラウザに `window.api` を代入して描く確認ではこの事故は再現しないため、
`test/preload-contract.test.js`（静的検査）と実機の起動の 2 つで押さえている。
