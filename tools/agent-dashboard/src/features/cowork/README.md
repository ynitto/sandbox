# Cowork feature

Cowork は agent-dashboard の独立した制御面です。

- 作業は `cowork.items` にフラットに並びます。`type: "loop"` は `agent-loop`、`type: "state-machine"` は `statemachine-use` で実行します。
- 各作業は `repo` で全体設定に登録済みのフォルダ（リポジトリ）を参照します。追加 UI では登録済みリポジトリから選択します。
- 実行エンジンが担当するプロジェクト配下の定常業務ループ設定 / `.statemachine/*/workflow.yaml` は自動発見します。ループ設定の探索先は `.agents/agent-loop.{yaml,yml,json}`（旧ホーム `.agent/` はそこにしか無いときのフォールバック）で、これは agent-loop 自身の探索と同じです。旧 `.agents/agent-loop.*` とフォルダ直下の `agent-loop.*` も**読むだけ**受けます（agent-loop 退役までの互換。両方あれば agent-loop 側が勝ちます）。発見結果は短時間キャッシュし、ポーリングごとに再走査しません（キャッシュの鍵は走査ルート＝エンジン担当 + `cowork.roots` なので、フォルダの登録・解除は即座に効きます）。
- **予約した定型業務は `statemachine:` の宣言として書きます。** 散文（「statemachine-use スキルで〈名前〉ステートマシンを実行して」）を `prompt` に置くと、agent-loop のデーモンからは普通の定期プロンプトに見えてハーネス固定にならず、本文だけがペインへ流れてワークフローは一度も走りません（scheduler は `statemachine:` を見て per-run のハーネスへ倒します）。自由文があるときだけ `prompt` を併記し、実行条件（`input` パラメータ）として渡します。
- **書き先は読取候補と分けます。** 画面で作った管理項目は、既にあるループ設定があればそこへ、無ければ `.agents/agent-loop.yml` を新規に作って書きます。旧 `.agents/agent-loop.*` は読めても新規の書き先にはしません——agent-loop が読まないファイルを増やすことになるためです。既存設定が `.json` のフォルダは画面から編集できません（YAML の外科的書換を JSON へ流し込むと壊れ、避けて `.yml` を作ると agent-loop の探索順で元の `.json` が無視されるため、どちらも取らずエラーにします）。
- 実行エンジンの管理外のフォルダは `cowork.roots` に登録すると走査対象になります。登録の入口は**⚙ 全体設定の「定常業務」**です。定常業務画面はプロジェクトを 1 つ選んでから開く画面なので、エンジンがまだ動いていない初期状態ではそこからは 1 件目を登録できません（全体設定はプロジェクト選択に依存しません）。
- `loopCommand` で定期実行のコマンドを切り替えます（**既定は `agent-loop`**）。設定は 1 つだけで、旧 `loopProvider`（種類）は読み取り互換のためだけに残しています。
- loop の単発実行は `<loopCommand> send <プロンプト名>` で行います（`run` サブコマンドは存在しません）。`send` はワークスペース（cwd）のループ設定から定期プロンプト名を解決し、稼働中の tmux セッションへ送信します。項目に `args` を明示した場合はそちらを優先します。
- `statemachine-use` は CLI ではなく**スキル**です。ステートマシンの実行は `<loopCommand> send "xxx ステートマシンを実行して"` でエージェントセッションへプロンプトを送ってスキルを発動します。
- ループ設定の prompts が **`statemachine:` を宣言**している場合、その loop 項目は名指しされたステートマシン項目へ**統合して表示**します。宣言があるときは推測しません。宣言が無いエントリに限り、従来どおり本文の言い回しから対を推測します（本文が `.statemachine/<name>` のフォルダ名か workflow.yaml の表示名に言及し「ステートマシン」を含む）。統合項目は schedule / enabled を対エントリから引き継ぎ、編集の書き戻しは schedule / enabled → ループ設定側・name / description → workflow.yaml 側に振り分けます。宣言先の定義が実在しなくても項目は消しません（設定を直す取っかかりを残すため。実在しないことは実行時に実体パス付きで報告されます）。
- **実行条件は宣言から引きます。** `statemachine:` を宣言したエントリの `input:`（名前のある条件のマップ）と `prompt`（名前の無い自由文 → ワークフローの `input` パラメータ 1 個ぶん）は、入力ダイアログでは**訊かず既定値として畳み**、そのままハーネスの `--param` へ渡します。つまり「今すぐ実行」はデーモンの定期実行と同じ条件で回ります。宣言していないキーだけが従来どおり入力欄に残ります。書き方の正典は `input:` のマップで、理由は [`docs/specs/agent-loop-spec.md` §2.3.1](../../../../../docs/specs/agent-loop-spec.md)。宣言の無い（推測で対にした）項目では、`prompt` は従来どおり対話 CLI へ送る指示文のままで、実行条件にはしません。
- 状態表示のために新しい状態ファイルは作りません。既存ログ（`.agent-loop/logs` / 旧 `.agent-loop/logs` / `.statemachine-use/logs` / `logs`）から動的に推定します。プロセス探査（`pgrep` / `wmic`）はポーリングでは行わず、実行直後や手動更新時だけ行います。
- UI はメインの **Cowork タブ**に統一しています。左ペインには出しません。作業（手動登録または発見）が 1 件も無いときはタブ自体を非表示にします。
- 一覧は**選択中プロジェクトの作業だけ**を表示します（WSL UNC と POSIX パスは同一視）。「すべてのプロジェクトを表示」で全件に切り替えられます。
- 各作業の「履歴」から、**この画面からの実行記録**（`~/.agent-dashboard/cowork-history.jsonl` に追記・上限超は新しい方だけ残す）と、リポジトリの**実行ログ**（`.agent-loop/logs` / 旧 `.agent-loop/logs` / `.statemachine-use/logs` / `logs`）の一覧・末尾を確認できます。ログの読み出しはその作業のログ候補に実在するパスだけを許可します。
- agent-loop は WSL 側にしか無い想定のため、Windows 上の dashboard からの実行は**リポジトリが Windows ドライブ上でも常に `wsl.exe` 経由**でプロジェクトルート（`C:\...` は `/mnt/c/...` に変換）から行います。出力は UTF-8（失敗時は Shift_JIS）でデコードします。git 操作は WSL UNC のリポジトリのみ `wsl.exe` 経由です。
- Windows では実行を**新しいコンソールウィンドウ（WSL）で開始**します（既定。`cowork.runWindow: false` で従来の非表示実行に戻せます）。ウィンドウ実行は **ループ CLI を介しません** — tmux セッションに**エージェント CLI をインタラクティブ起動**し、dashboard が解決したプロンプトを直接送信して、そのまま **`tmux attach`** で実行の様子を見続けられます（`Ctrl+b d` で離脱）。
  - **どの CLI とモデルで起動するか**: 全体設定 →「実行制御」→「機能ごとのエージェントとモデル」の**定常業務**（agent-control 契約の `workloads.routine.agent_cli` / `model`）が最優先。空欄なら `defaults` → ⚙ AIアシスタント設定（`agent.cli` / `agent.model`）→ プロジェクト設定（`agent-project.yaml` / `agent-flow.yaml`）→ 既定 `kiro` の順に委ねます。起動 argv は CLI 定義（`agents/<name>.json` の `interactive`）が正典なので、`ollama` のように**モデル名を argv に載せる CLI**（`agent-ollama --tui --think on <model>`）も指定どおりに起動します。`cowork.chatCommand` は明示上書きで、既定は空です。
  - **ステートマシンは実行形の 1 行で起こします。** 一族（ollama / aider）の共通 TUI へは `/sm <ワークフロー> [--param k=v]`（TUI がヘッドレスのハーネスへ回します）、クラウド CLI へはスキル発動文（自分でスキルを見つけて 1 セッションで通せます）。state ごとにヘッドレス起動しないのは、CLI の起動・文脈の再構築・システムプロンプトの再送が state の数だけ掛かるからです（クラウド CLI ではトークン消費が跳ねます）。綴りの正典は `agentcore.loopentry.statemachine_command` で、agent-loop のデーモンも同じ 1 行を送ります。`/sm` は先頭行でなければ効かないので、共通指示はこの 1 行には前置しません。
  - **ハーネス（`agent-loop run` / `statemachine`）は逃げ道です。** 対話面を宣言していない CLI 定義だけがそちらを通ります（`cowork.needsHeadlessHarness`）。RESULT 契約と受入条件ゲートもそちら側にあります。
  - **入力の補助**: `{{…}}` プレースホルダーやステートマシンの入力パラメータなど、ユーザー入力が必要な項目が埋まっていない場合に備え、「仮の値で進めず、先に必要な入力を質問してから実行する」補助文を自動で付け加えます。不足があればウィンドウ内のエージェント CLI が質問してくるので、そのまま対話で埋められます。
  - セッション名は `kiro-dash-<repoダイジェスト>`（リポジトリごとに再利用。`kiro` 接頭辞なので「端末」タブの一覧にも載ります）。入力受付の待ち方（`interactive.ready_pattern` / `ready_timeout_sec`）は CLI 定義から来ます。入力を受け付けたのを確認してから送信します。
  - ウィンドウは `cmd /s /c start … wsl.exe -e sh -lc ". '<一時スクリプト>'"` で開きます。GUI プロセス（Electron main）からコンソールアプリを直接 spawn しても対話可能なコンソールは割り当てられない（ウィンドウが出ない・`tmux attach` 不可）ため、`start` に新しいコンソールを作らせます。スクリプト本文は `%TEMP%\agent-dashboard\` の一時ファイルに書いて cmd の引用規則を回避します。
  - 明示 `args` を持つ手動項目は従来どおり `<loopCommand>` をウィンドウ内で実行します（レガシー経路）。
- `loopCommand` / `chatCommand` は**複数語のコマンド**（例 `python3 ~/sandbox/tools/agent-loop/agent-loop.py`）も指定できます。空白入りパスは `"…"` / `'…'` で囲みます。先頭の `~` は WSL 側の `$HOME` で展開されます（全体を 1 トークンとして引用すると `not found` になっていた問題を修正）。
- **手順ビルダー（定型手順）**: 作業タブの「手順を組み立てる」（設定変更ダイアログの手順付き作業からも移れる）で、画面操作（ブラウザ / Windows アプリ）・スキルに任せる（`redmine-use` など名前で指定）・コマンド実行・AI の処理（生成・判断）を工程として並べ、判断の分岐（「ラベル: 行き先」）・完了の確認コマンド・`{{key}}` 入力を付けて定型業務を作ります。組んだ工程列（`procedure`）は main（`main/procedure.js`）が検査して**作成モードへ渡す指示文**へ決定的に変換し、起動は自由文と同じ `cowork:generateStateMachine`（`payload.procedure`）を通します——dashboard は YAML を書かず、作成の入口も増やしません。指示文は移譲先スキル（`playwright-cli` / `windows-app-automation`）を名指しし、画面操作・コマンドの工程には `check` の宣言を促し、分岐は遷移に書かせます（ヘッドレスのハーネスはシェルを介さないので、コマンドと確認コマンドのシェル記号は投入前に断ります）。工程列は作業項目に残るので「手順を組み立て直す」から同じ画面で作り直せます。**工程の種類の正典は `main/procedure.js` の種別カタログ 1 か所**で、画面は `cowork:procedureCatalog` で受け取って入力欄を描きます（表示名・移譲先スキル・指示文の案内・道具の診断を 1 項目に持つので、種類を足すのはその配列へ 1 項目足すだけ）。画面のコードは `renderer/sections/procedure.js` に独立していて、実行・保存の経路には触れません。「道具を確認」（`cowork:procedureTools`）は `playwright-cli --version` / `winauto doctor --output json` だけを呼び、LLM もデスクトップロックも使いません。
- **操作を記録して工程にする（定型手順）**: 手順ビルダーの「操作を記録する」で、人が画面でやった操作を工程に起こせます。ブラウザは `playwright-cli` の記録（`-s=agent-dashboard-record open --headed <URL>` → `recording-start` → 人が操作 → `recording-stop` → `close`）を、Windows アプリは `winauto record --app <アプリ> --output <一時ファイル> --stop-file <停止ファイル>` を**別ウィンドウ（tmux）**で走らせて停止ファイルで止めるのを、どちらも main が呼びます（人はそのウィンドウで進行を見られ、`Ctrl+C` でも止められます）。信号で止めないのは、win32 では `wsl.exe` → ラッパー → Windows Python と挟まっていて途中で落ちるからです。一時ファイルの綴りは **main が決めて覚えます**——画面から受け取ったパスで読み書きしません。別の端末で取った記録（JSONL / `recording-stop` の出力。契約は `main/recording.js` の `WINAUTO_EVENT_KINDS`）は貼り付けでも受けます。ブラウザが見える形で開かない環境（WSL 側に画面が無い等）では、落ちた理由ごとに次の一手を添えて断ります（`browserOpenHint`）。変換（`main/recording.js`）は**決定的**で、要素は role と名前（`getByRole(...)` / `auto_id:=`）で残して ref・座標は断り、人の癖（入力前のクリック・確定後の Enter の重複）を落とし、ページ遷移・ウィンドウの切り替わり・確定の操作（ボタン / リンク / Enter）で工程を切り、`fill` / `type` の値を `{{key}}` にして記録時の値を例に残します（パスワードらしい欄は例にも残しません）。Windows は `winauto wait` の確認コマンドを置きます（測るのは**その工程がもたらした変化**なので、見るのは「次の工程が始まったときの画面」です。工程の最中に既に出ていた画面を待っても押す前から真で、何も検知しません）。工程列は版 2（工程に任意の `recorded[]`）になり、指示文には「記録した操作」と汎用化の案内（記録に無い操作を足さない・待機と読み取りを足す・例を既定値にしない・脆いロケータは言い換えてよい）が載ります——待機・確認・分岐の補完は作成モードのスキルの仕事で、画面は推測しません。IPC は `cowork:procedureRecording`（start / stop / import）の 1 チャネルだけで、作成の入口は増やしません。設計と検証: [`docs/plans/2026-09-04-agent-dashboard-routine-recording-feasibility.md`](../../../../../docs/plans/2026-09-04-agent-dashboard-routine-recording-feasibility.md)。
- **アドホック起動**（`cowork:runAdhoc`）: 作業（items）を登録しなくても、**登録済みフォルダ + 自由文**で対話 CLI を起動できます。入口は「実行の記録」タブの「アドホック起動」パネルです。起動経路は定常業務ウィンドウと同一——共通指示（agent-instructions）の前置・CLI とモデルの解決（agent-control の `workloads.routine`）・セッション開始コマンド・履歴の追記（`cowork-history.jsonl` に `type: "adhoc"`、名前はプロンプトの 1 行目）をそのまま通し、新しい状態ファイルも起動系も作りません。cwd は**登録済みフォルダ（走査ルートと同じ集合。`cowork:overview` の `roots`）からの選択のみ**で、未登録パスは拒否します。tmux セッションは `agent-chat-adhoc-<digest>`（定常業務のセッションへは合流しません）。
