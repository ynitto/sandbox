# testcase-lint

自然文で書いたテストケース（e2e・シナリオテスト・人が見るチェックリスト）を読み、
**重複・矛盾・漏れ・不備**を指摘する。LLM は使わない。同じ入力からは毎回同じ指摘が出る。

- 読めるのは **JSON / YAML**（LLM の出力によくある ```` ``` ```` の囲みも、行番号を保ったまま読む）
- 依存は **PyYAML** と **[Janome](https://github.com/mocobeta/janome)**（純 Python の日本語形態素解析器、Apache-2.0）だけ
- [webui-test](../webui-test/README.md) のケースファイルもそのまま点検できる

```text
$ testcase-lint examples/login-cases.yaml -r examples/requirements.yaml
examples/login-cases.yaml
    5  エラー C01 矛盾 TC-01, TC-04  前提と手順が同じなのに、期待結果が逆です（「ホーム画面が表示される」と「ホーム画面が表示されない」）（ほかに 41 行目）
         → どちらが正しいかを仕様で確かめる。条件が違うなら、その違いを前提に書く
   29  警告  D06 不備 TC-02  「正しく」では合否を決められません
         「エラーメッセージが正しく表示される」
         → 何が・どうなれば合格かを、見て判断できる形（表示される文言・値・件数など）で書く
   75  警告  G03 漏れ  「パスワード」の条件「最大30文字」の境界 31文字 を試すケースがありません（TC-07）
         → 境界のちょうど（30文字）と、1 つ外（31文字）の両方を試す
...
examples/requirements.yaml
    5  警告  C04 矛盾  「パスワード」の上限が食い違います: 要件 REQ-02「20文字以下」、TC-07「最大30文字」
    9  エラー G01 漏れ  要件「REQ-04」を確かめるケースがありません
```

## 入れる

```bash
pip install ./tools/testcase-lint        # testcase-lint コマンドが入る（Windows でも同じ）
# 入れずに使うなら
pip install pyyaml janome
python -m testcase_lint ...              # tools/testcase-lint で実行する
```

## 使う

```bash
testcase-lint cases.yaml                          # 1 ファイル
testcase-lint tests/cases/ more.json              # フォルダ（.json / .yaml / .yml を探す）と複数ファイル
testcase-lint cases.yaml -r requirements.yaml     # 要件一覧と突き合わせる（ケースのない要件・境界値）
testcase-lint cases.yaml -f json -o result.json   # 機械で読む形（ほかに -f markdown）
testcase-lint cases.yaml --fail-on warning        # 警告以上があれば終了コード 1（既定は error）
testcase-lint cases.yaml --min-severity warning   # 参考は出さない
testcase-lint --list-rules                        # 規則の一覧
```

終了コード: `0` 落とす重さの指摘なし / `1` あり / `2` 使い方の誤り。CI ではそのままゲートに使える。

## 読める形

項目名は、英語・日本語・Gherkin のよくある綴りを受ける。ケースの列は、ファイルの一番上の配列か、
`cases` `tests` `scenarios` `checklist` `テストケース` などのキーの下に置く。入れ子（機能ごとの
まとまり）もたどる。

| 意味 | 受ける項目名の例 |
|---|---|
| ID | `id` `case_id` `no` `テストID` `項番` |
| タイトル | `title` `name` `scenario` `テスト項目` `確認項目` |
| 前提 | `preconditions` `given` `setup` `前提条件` `事前条件` |
| 手順 | `steps` `when` `actions` `手順` `操作手順` |
| 期待結果 | `expected` `then` `assertions` `期待結果` `確認内容` |
| 要件 | `requirement` `requirements` `refs` `要件` `要件ID` |

- 手順・期待結果は、文字列・文字列の配列・複数行の文字列（`1.` などの番号付きでもよい）のどれでもよい
- 手順の要素が `{action: ..., expected: ...}` の形なら、期待結果を分けて読む。`expect:` `verify:` も期待結果として読む
- 文字列だけの配列（`checklist: [...]`）は、人が見るチェックリストとして読む（手順・期待結果を求めない）
- 上の表にない項目（テストデータ・モック・言語設定など）は、前提として比べる。同じ手順でも前提が違えば別のケースとみなす
- 付帯情報（`tags` `priority` `備考` など）は比べない

要件一覧（`-r`）は、ID の配列・`{id, text}` の配列・`ID: 本文` の対応のどれでもよい。本文に
「8文字以上20文字以下」のような数値の条件があれば、境界値の点検にも使う。

## 指摘すること

| コード | 分類 | 既定 | 内容 |
|---|---|---|---|
| D01 | 不備 | 警告 | ID がない |
| D02 | 不備 | エラー | 同じファイルの中で ID が重複している |
| D03〜D05 | 不備 | 警告・エラー | タイトル・手順・期待結果がない |
| D06 | 不備 | 警告 | 合否を決められない曖昧な表現（「正しく」「適切に」「問題なく」「など」「仕様どおり」…） |
| D07 | 不備 | エラー | 書きかけ（TBD・TODO・要確認・???・○○…） |
| D08 | 不備 | 警告 | テストデータが決まっていない（「任意の」「適当な」「有効な値」…） |
| D09 | 不備 | 警告 | ほかのケースに依存している（「同上」「前のケースと同じ手順で」…） |
| D10 | 不備 | 警告 | 期待結果に操作が書かれている（「〜をクリックする」） |
| D11 | 不備 | 参考 | 手順に確認が混ざっている（「〜が表示されること」） |
| D12 | 不備 | 参考 | 1 つの手順に操作が多い |
| D13 / D14 | 不備 | 警告 | 要件の紐づけがない（ほかのケースにはある）/ 要件一覧にない要件を指している |
| D15 | 不備 | エラー | 同じキーが 2 回書かれ、先の値が捨てられている |
| U01 | 重複 | エラー | 手順と期待結果が完全に同じ |
| U02 | 重複 | 警告 | ほぼ同じ（表記の揺れだけ） |
| U03 | 重複 | 参考 | 値だけが違うよく似たケースが 3 件以上（表にまとめられる） |
| U04 | 重複 | 参考 | タイトルが同じで中身が違う |
| C01 | 矛盾 | エラー | 前提と手順が同じなのに、期待結果が逆（表示される／されない、成功／失敗、有効／無効…） |
| C02 | 矛盾 | エラー | 1 つのケースの中で、前提どうし・期待結果どうしが食い違う |
| C03 | 矛盾 | 警告 | 前提と手順が同じなのに、期待結果が違う |
| C04 | 矛盾 | 警告 | 同じ対象の数値の条件が食い違う（要件は 20 文字以下、ケースは最大 30 文字…） |
| G01 | 漏れ | エラー | ケースのない要件（`-r` を渡したとき） |
| G02 | 漏れ | 警告 | 機能のまとまりに異常系が 1 件もない |
| G03 | 漏れ | 警告 | 数値の条件の境界（ちょうど・1 つ外）を試していない |
| G04 | 漏れ | 参考 | 対になる条件の片方しか試していない（ログイン済み／未ログイン、管理者／権限なし、入力／未入力、一覧／0 件…） |

## 設定（任意）

`-c testcase-lint.yaml` で渡す。書かなかった所は既定のまま。

```yaml
rules:                 # 規則ごとに off / error / warning / info
  D11: off
  G04: warning
similarity:
  duplicate: 0.9       # これ以上似ていれば「ほぼ同じ」（0〜1）
  same_steps: 0.92     # 前提＋手順がこれ以上似ていれば、期待結果を比べる
vague_words: [見栄えがよい]           # 曖昧な表現を足す（正規表現）
negative_words: [差し戻し]            # 異常系とみなす語を足す（正規表現）
pairs:                                # 対になる条件を足す
  - {a_label: 会員, b_label: 非会員, a: ["(?<!非)会員"], b: [非会員, ゲスト]}
fields:                               # 項目名の綴りを足す
  expected: [確認ポイント]
```

## 分かること・分からないこと

文字の並び・否定の向き・数値で判断するので、次は**分からない**。必要なら人か LLM のレビューと組み合わせる。

- 言い換えの矛盾（「ログイン画面に戻る」と「ホーム画面へ移る」は、別の文としか分からない）
- 仕様に書かれていない観点の漏れ（要件一覧と、上の対になる条件・境界値から分かる分だけ）
- 期待結果が仕様として正しいか

似ている度合いは、文字の 2〜3 文字組の重なりで測る（表記が少し揺れても拾える）。数値と「」で囲んだ
値は伏せて比べ、値が違う組は重複や矛盾にしない（境界値のケースを重複と言わないため）。
仕組みの詳細は [設計書](../../docs/designs/testcase-lint-design.md) にある。
