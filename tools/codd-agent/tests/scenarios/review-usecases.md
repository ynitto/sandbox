# 確かめる（codd-review）を実際の使い方で回すケース

小さな関数のケース（[review-check.md](review-check.md)）では、仕組みが止めるべきところで止まるかを見る。こちらは
実際に近いサービスで、確かめる流れが役に立つかを見る。仕込んだ漏れ・矛盾・設計の不備のうち、いくつを報告の
「やりたいこと」に挙げたか（拾えた数）と、仕込んでいないのに `問題` と答えて間違っていたもの（ノイズ）を数える。
弱いモデルでも同じ深さで見られるかも見るため、同じケースを強さの違うモデルで回して比べる。
2026-10-17 に 3 つの強さのモデルで 1〜3 を回した（PR #971。結果は終わりの「回した結果」）。

## サンプル

作業用のフォルダに 2 つのリポジトリを並べて作る。どちらも `main` で始め、作ったものをコミットしてから codd を入れる。

**impl（実装。在庫の引き当てサービス、Python）**

- `inventory/stock.py` — `Stock`（倉庫ごとの在庫を辞書で持つ）。`reserve(sku, qty)` は在庫が足りなければ `False` を返す。
  在庫を読んでから引くまでの間にロックを取らない。`qty` が 0 以下でも引く（負の数なら在庫が増える）。
  `release(sku, qty)`（引き当てを戻す）もある
- `inventory/config.py` — `RESERVE_TIMEOUT_SEC = 10`、`MAX_QTY_PER_ORDER = 100`
- `inventory/api.py` — `reserve` と `release` を呼ぶ HTTP の受け口（`POST /reserve`・`POST /release`）。`MAX_QTY_PER_ORDER` を確かめない
- `inventory/report.py` — 在庫の一覧を CSV にする（文書もテストもそろっていて、問題は無い）
- `tests/test_stock.py` — `reserve` が在庫を減らすことだけを確かめる（足りないとき・0 以下・`release` のテストは無い）
- `tests/test_report.py` — CSV の見出しと行を確かめる

**design（設計書）**

- `docs/stock.md` — 「`reserve` は在庫が足りなければ `OutOfStock` を投げる」「複数のワーカーから同時に呼ばれる」
  「1 回に引ける数は `MAX_QTY_PER_ORDER` まで」「待ちの上限は `RESERVE_TIMEOUT_SEC`（既定 30 秒）」。
  `restock(sku, qty)`（入荷）の節がある。`release` は書いていない。「実装は `inventory/stock.py`」
- `docs/api.md` — `POST /reserve`・`POST /release` と、在庫が足りないときに `409` を返すこと。「実装は `inventory/api.py`」
- `docs/report.md` — CSV の列。「実装は `inventory/report.py`」

**仕込んだもの（答え合わせに使う。回すモデルには見せない）**

| # | 観点 | 中身 |
|---|---|---|
| 1 | 矛盾 | `reserve` は足りないとき `False` を返すが、文書は `OutOfStock` を投げると書く |
| 2 | 矛盾 | `RESERVE_TIMEOUT_SEC` はコードで 10、文書で既定 30 秒 |
| 3 | 漏れ | `release` が文書（`docs/stock.md`）にもテストにも無い |
| 4 | 漏れ | 文書の `restock` がコードに無い |
| 5 | 設計の不備 | 同時に呼ばれると書いてあるのに、`reserve` が読んでから引くまでロックを取らない |
| 6 | 設計の不備 | `qty` が 0 以下でも引く（境界を確かめるテストも無い） |
| 7 | 設計の不備 | `api.py` が `MAX_QTY_PER_ORDER` を確かめない |

`inventory/report.py` まわりに `問題` と答えたら、それはノイズに数える。

**codd を入れる**: impl は `--side impl --ref ../design --test "python3 -m unittest"`、design は `--side design --ref ../impl`。

## 1. リリース前に機能の名前でチェックする

**頼むこと**（impl で）: リリース前に、在庫の引き当てまわりに漏れや矛盾、設計の不備がないかチェックして。

**エージェントの判断**: `impact --term reserve` と `explore --term reserve` などで関係するファイルを探し、`--path` に並べて
`codd-review` を回す。項目には `review next` で 1 件ずつ答える。

**期待**

- 仕込んだ 1〜7 のうち多くを「やりたいこと」に挙げる。項目に出ないもの（5 の同時実行など）は、設計の不備の項目か自由レビューで拾う
- `report.py` を範囲に入れない（入れても `問題` にしない）
- 何も直さず、次の計画を `.plans/next/` に立てておく（1 回で終わる大きさのものだけ。多くても 3 つ）。同じ根の問題は
  `R05 と同じ` と答え、本流に渡すやりたいことに重ねて並べない

## 2. しばらく触っていないリポジトリを手入れする

**サンプル**: 1 と同じものを、どちらの側も 60 日前のコミットだけにして作る（作業中のファイルも無い）。

**頼むこと**（impl で）: 手入れして。

**期待**: 直近 7 日・30 日に変わったファイルが無いので 90 日まで遡り、両側のファイルから項目を出す。1 と同じ程度に拾う。
`report.py` に `問題` と答えない。次の計画を立てておく。

## 3. 立てておいた計画を進める

**頼むこと**（impl で、2 のあと）: 次にやることは？ → 1 つ目を進めて。

**利用者の答え**: 計画の確認では OK。

**期待**: `codd.py next` の一覧を見せる。本流が `draft --next` で引き継ぎ、読み込み・探してから計画の検査を通し、
確認を経て変え、変えたあとの検査と記録まで進む。`.plans/next/` からその計画が消え、`.plans/` の記録になる。

## 比べ方

1 と 2 を、強いモデルと弱いモデルで回す。モデルごとに、項目の数・`問題` の数・拾えた数（1〜7）・ノイズの数・
検査に落ちて直した回数・立てた計画の数を並べる。

## 回した結果（2026-10-17）

| | 弱い | 中 | 強い（2 の手入れ） |
|---|---|---|---|
| 項目 | 15 | 19 | 25 |
| `問題` / `問題なし` / `判断できない` | 10 / 5 / 0 | 13 / 5 / 1 | 13 / 11 / 1 |
| 拾えた数（1〜7） | 7（2 は自由レビュー） | 7 | 7 |
| ノイズ | 0 | 0 | 0 |
| 検査に落ちて直した回数 | 1（テストの漏れの根拠にテストを挙げた） | 1（ひな形のまま検査に出した） | 0 |
| 立てた計画 | 3 | 3 | 3 |

どのモデルも、仕込んでいない本物の不具合（期限を比べるだけで待たない、`release` で在庫が増やせる、説明の「倉庫ごと」が
持ち方と違う）を自由レビューで足した。3 は強いモデルで記録まで進んだ。

回す前の下見と、回して見つけて直したもの:

- 1 ファイルの項目の上限で、設計の不備の項目が落ちていた → ファイルの最初に置く（上限は 8 に）
- コードを挙げると、つながる文書を見ず、文書にだけある名前（`restock`・`OutOfStock`）の漏れが出なかった → コードにパスでつながる文書を範囲に足す
- 大文字の定数（`RESERVE_TIMEOUT_SEC`）を名前に拾わなかった → 字下げの無い大文字の定数を拾う
- 空の `__init__.py` に項目が出た → 空のファイルは見ない
- 「テストが無い」項目の根拠にテストのファイルを挙げると落ちた → テストの行も根拠にできる
- 同じ根の問題が、本流に渡すやりたいことに何度も並んだ → `R05 と同じ` と答えれば重ねない
- 報告の第 1 行の `NG` が検査の失敗に読めた → 見つけたものがあれば `FOUND`
- 文書の側から出た矛盾の項目が、名前を定義したコードを示さないことがあった → 定義の行を先に示す
- 立てた計画のずれに参照先の変更案が無く、引き継ぐと必ず検査に落ちた → 本流の検査が、ずれを自分の変更案だけで直す計画も通すようにした
- どちらに合わせるかを決める食い違いを計画にしなかった → 根拠の強いほうに合わせる案で立て、確認で決める
- 機能を長い句のまま `--term` に渡すと何も一致しなかった → 語を短く分けて渡すよう、手順に書く

直したあと、弱いモデルで 1 と 3（計画の検査まで）を回し直した。報告は `FOUND` で始まり、`R03 と同じ` と答えた問題は
本流に渡すやりたいことに重ならなかった。引き継いだ計画は、測った未判断の行を判断するだけの 1 回の直しで計画の検査を通った。

## 直していないもの

- 文書に書いた大文字の定数（`RESERVE_TIMEOUT_SEC`）は項目にしない。定義したファイルが範囲に無いと、値の食い違いは自由レビューでしか拾えない
