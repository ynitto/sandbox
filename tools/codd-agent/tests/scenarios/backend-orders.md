# 注文 API（Python）と仕様書

画面の無いバックエンドで、関数の改名と項目の追加を流す。2026-10-05 に通し、見つけた不具合を直した（PR #911）。

## サンプル

作業用のフォルダに 2 つのリポジトリを並べて作る。どちらも `main` で始め、作ったものをコミットしてから codd を入れる。
実装に `.gitignore` は置かない（`init.py` が書く `.codd/` だけのもののまま。キャッシュの扱いを見るため）。

**api（実装）**

- `orders/models.py` — データクラス `Item`（`sku`・`price`・`qty`）と `Order`（`id`・`items`・`status = "new"`）
- `orders/service.py` — `TAX_RATE = 10`、`calc_total(order)`（小計に税を足す）、`cancel(order)`（発送済みは取り消せない）
- `orders/routes.py` — `GET /orders/{id}/total` が `calc_total` を、`POST /orders/{id}/cancel` が `cancel` を呼ぶ
- `users/service.py` — `get`・`update`（`status` を変える）
- `db/migrations/001_orders.sql` — orders テーブル（`id`・`status`）
- `tests/__init__.py`（空）・`tests/test_service.py`（`calc_total` が 220、`cancel`）・`tests/test_users.py`

**spec（設計書）**

- `docs/api/orders.md` — 見出しは概要・エンドポイント・状態。「`GET /orders/{id}/total` — 合計（税込み）を返す。`calc_total` で計算する」。
  概要に実装のパス（`orders/models.py`・`orders/service.py`・`orders/routes.py`）を書く
- `docs/api/users.md` — 同じ見出しで、`get`・`update`。概要に `users/service.py` を書く
- `docs/db/schema.md` — orders の列の表
- `docs/overview.md` — 全体の概要。「注文は `orders/`、利用者は `users/` に置く」とフォルダだけを書く

**codd を入れる**: api は `--side impl --ref ../spec`、`test` は `python3 -m unittest discover -s tests -t .`。spec は `--side design --ref ../api`。

シナリオはそれぞれ作り直したサンプルで流す。

## 1. 割引を足して改名する

**頼むこと**（api で）: 注文に割引（`discount`、円）を足し、合計は割引を引いてから税を掛けて。`calc_total` は `compute_total` に改めて。
マイグレーション `002_discount.sql` も書く。

**期待**

- 計画の検査が、書式の見本 `spec:docs/db/schema.md` を「未判断」に足し、新しく足す `discount` のテストが無いと止める。直せば通る
- 変えたあと、codd がテストを動かして出来た `__pycache__` の `.pyc` を「響くテスト」に数えない。何度 verify-apply しても通る。
  エージェントが手でテストを動かして出来た `.pyc` も「計画に無いファイル」に数えない
- 計画の `discount: int = 0` のようなコードの断片は、先頭の名前（`discount`）として扱う。テストの変更案に `discount` と書けば足りる
- 自分の変更案があれば、参照先の変更案があっても影響範囲を「なし」と書いてよい（測って「未判断」として書き足す）
- エージェントが手でテストを動かしたときのキャッシュも、テストが作り直すファイルとして「計画に無いファイル」に数えない

## 2. 状態を変える関数を足す

**頼むこと**（api で）: 注文の状態を変える `Order.set_status` を足し、`cancel` から使って。

**期待**: 計画の検査が「未判断」を書き足し、判断を書けば通る。参照先を変えずに最後まで通る。

## 3. 割引を途中まで変える

**頼むこと**: 1 と同じ。ただし変える段で、計画に挙げたファイルの一部（コードとテスト）を変えずに verify-apply する。

**期待**: 同じファイルを 2 つの指摘に重ねて挙げない（テストの変更案のテストは「テストをまだ変えていません」だけに、変え残した
自分の変更案のコードは「自分の変更案のファイルをまだ変えていません」だけに出る）。
advise は AUTO APPLY。残りを変えれば通る。

## 4. 仕様書を直さずに改名する

**頼むこと**（api で）: `calc_total` を `compute_total` に改めて（中身は変えない）。

**エージェントの判断**（わざとこうする）: 参照先の変更案は「なし」にして、仕様書を直さない。

**利用者の答え**: 仕様書の `calc_total` は同じ関数なので、直すことを計画に足す（PLAN）。

**期待**

- 変えたあとの検査が「消した名前を、計画で変えないファイルがまだ書いています: `calc_total` — docs/api/orders.md:9」で止める。
  変える段だけでは直せない（直すと計画に無い変更になる）ので、advise は訊かずにやり直さず利用者に訊く。勧めは計画を直す（PLAN）
- 仕様書のその行を計画の前提の根拠に挙げているので、「関係なし」と書いても済まない
- 計画に仕様書の変更を足して確認で OK すれば、仕様書を直して通る

## 5. 本流を続けて回し、確かめる流れを勧める

context-mode を入れた端末で流す（2026-10-18。PR #973）。

**頼むこと**（api で、順に）: 2 の `set_status`、割引を足す計画を立ててすぐやめる（STOP）、いない利用者の `update` で落ちないようにする、
1 の割引（改名はしない）。最後に「チェックして」。

**利用者の答え**: どれも OK（2 回目だけ STOP）。勧められたら「回す」。

**期待**

- explore の詳細に「全文検索（context-mode）」が載り、仕様書の節（`docs/api/orders.md — 注文 API > エンドポイント` など）が出る。
  参照先に置いた `.statemachine/codd/` のファイルが検索の上位を埋めて、当たりが「該当なし」にならない
- 索引は文書だけで作る。大きなリポジトリでも作り直しで長く待たせない（2,600 ファイルのリポジトリで、コードも入れると 100 秒、文書だけなら 17 秒）
- やめた回は数えない。3 回目を終えた `record` の最後に `REVIEW` の行が出て、エージェントが確かめる流れを回すか尋ねる
- 「チェックして」で `review start` を回すと数え直す。断ったときは、次の回ではなく 3 回後にまた尋ねる
- 尋ねるのはステートマシンが終わってから（done の段では `REVIEW` の行を伝えるだけで待たない。そのあと振り返りの段が続くため）
- spec（設計書）の側で回しても同じ。参照先の api は文書が無いので、explore の詳細に全文検索の節を出さない

## 6. 新しい機能をファイルごと足す

2026-10-18 に、新しく実装するときに仕様書の新規作成が漏れたことから足した。

**頼むこと**（api で）: 返金を足して。`orders/refund.py` に `refund(order)` を置き、`POST /orders/{id}/refund` から呼ぶ。

**利用者の答え**: OK。

**期待**

- 計画で新しく作る `orders/refund.py` に、作る・足す文書の項目が無ければ、計画の検査が「対応する文書の無いコード」で止め、
  見本に `spec:docs/api/orders.md`（`orders/service.py` に対応）を挙げる。`docs/overview.md` が `orders/` を書いていても、
  隣のコードがファイルごとの文書を持つので、概要の文書では済ませない
- 見本に倣って `docs/api/refund.md` を作るか `docs/api/orders.md` に節を足す項目を、参照先の変更案に `orders/refund.py` と同じ行で書けば通る
- 変えたあと、作った・足した文書の本文に `orders/refund.py` が無ければ止まる。書けば通る
- 返金をフォルダごと新しく作る（`returns/service.py`。`returns/` はまだ無い）計画も書け、同じく文書を求める
- 文書をフォルダごとに書くサンプル（`docs/api/orders.md` がパスを書かず、`orders/` だけを書く）なら、同じ依頼でも文書を求めない

## 7. 振り返りで課題メモを残す

2026-10-19 に、終わりの振り返りで課題メモ（`.plans/retro/`）を残すようにしたことから足した。

**頼むこと**（api で、同じサンプルで順に）: 4 を流す。続けて「`cancel` を `cancel_order` に改めて（中身は変えない）」。
最後に 2 の `set_status`。

**エージェントの判断**（わざとこうする）: 2 回目も参照先の変更案を「なし」にして、仕様書を直さない。

**利用者の答え**: 止まったらどちらも計画を直す（PLAN）。確認はどれも OK。

**期待**

- 1 回目の振り返りで、`.plans/retro/` に課題メモが 1 つできる。「起きたこと」に変えたあとの検査で止まったことと PLAN の答え、
  「原因」に仕様書が消した名前を書いていたこと（根拠つき）、「直す先」がある。直し方は書かない。codd はコミットしない
- 2 回目も、仕様書が関数名 `cancel` を説明の文に書いていれば、定義を消した名前として止まる。URL（`/orders/{id}/cancel`）の
  中の `cancel` は名前に数えないので、関数名を直したあとは URL が残っていても通る
- 2 回目は同じ問題なので、新しいメモを作らずに 1 回目のメモの「起きたこと」へ 1 行足す
- 2 回目の振り返りの「同じファイルを変えた過去の記録」に 1 回目の記録が載る。改名は別の判断なので、食い違いとしては書かない
- 3 回目（止まらず、指摘も無い回）は何も書かない。計画の検査が「未判断」を書き足して一度落ちるのはいつもの流れで、出来事に数えない
- 計画の検査を通す前にやめた回の記録に、前の回の変更を書かない
- 課題メモがあっても、次の回の計画の検査・変えたあとの検査が計画に無いファイルとして止めない
