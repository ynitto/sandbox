# 確かめる（codd-review）を種類の違うリポジトリで回すケース

[review-usecases.md](review-usecases.md) と同じく、確かめる流れが役に立つかを見る。こちらは言語・リポジトリの形・
大きさを変え、問題の無いリポジトリでノイズを出さないか、上限を超える大きさで見残しを伝えて続けられるか、
直したあとにもう一度確かめたときに同じものを挙げ直さないかを見る。2026-10-17 に 2 周回した（PR #971）。

## サンプル

**A. 1 つのリポジトリの JS（`node --test`）**: `src/rateLimiter.js`（`export const LIMIT_PER_MINUTE = 100`、利用者ごとの数を
`Map` に足すだけで消さない、`export function stats()`）、`src/format.js`（文書もテストもそろう）、`test/` に 2 つ、
`docs/rate-limiter.md`（「`LIMIT_PER_MINUTE`（60 回）まで」「利用者は数百万人」「`reset(key)` の節」）。
`init.py --test "node --test"` で入れる（参照先は同じリポジトリの `docs`）。

仕込んだもの: 上限の値（100 と 60）、`reset` がコードに無い、`stats` が文書とテストに無い、`Map` が増え続ける、
上限を超えたときのテストが無い。

**B. 問題の無いリポジトリ（Python と設計書）**: 長さの単位を変える `convert`。文書・コード・テストが合っていて、
失敗（知らない単位）・0・負の値もテストがある。

**C. 30 のハンドラ（Python と設計書）**: `handlers/hNN.py`（`LIMIT_NN` と `handle_NN`）・`tests/test_hNN.py`・`docs/hNN.md`。
04 と 29 だけ、文書の上限がコードと違う。最近のコミットで 30 個すべての説明を書き換える。

## 1. チェックする（A）

**頼むこと**: チェックして。

**期待**: 仕込んだ 5 件を挙げる。`buckets` のような export しない変数や、文書が書く引数の名前（`key`）は項目にしない。

## 2. 問題の無いリポジトリをレビューする（B）

**頼むこと**: 漏れや矛盾がないかレビューして。

**期待**: すべて `問題なし` で、報告は `OK` で始まる。次の計画を立てない。問題を作るよう促す手順が無い。

## 3. 大きいリポジトリを全体チェックし、見なかったところも確かめる（C）

**頼むこと**: 最近いろいろ変えたので、全体をチェックして。→ 見なかったところも確かめて。

**期待**: 1 回目は 20 ファイルまでを見て 04 を挙げ、「見なかったもの」に残りと続け方（`review start --rest`）を示す。
続きの回は前の回のやりたいことを引き継ぎ、3 回目までに 29 も挙げる。「全体」と頼まれたら `--path .` で、どの側も見る。
項目の上限で落ちたファイル（h14〜h18）は「見なかったもの」に入り、`--rest` で見る。項目の出ないファイル（`.gitignore` など）は
20 ファイルに数えない。前の回の項目の箇所に出たテストと文書は、続きの回で見直さない（項目の上限で出し切れなかったテストも、ほかの項目の箇所に出ていれば続きに回さない）。上限で見なかったファイルの項目は「出さなかった項目」に
数えず、続け方は `--rest` の 1 通りだけを示す。

## 4. 直してから、もう一度確かめる（A）

**頼むこと**: チェックして。→ 次にやることは？ → 上限の値の食い違いを直す計画を進めて（確認では「文書の 60 回に合わせて OK」）。
→ もう一度チェックして。

**期待**: 2 回目のチェックで上限の食い違いが消え、残りの計画は重ねて立てない。立てたあとにファイルが変わった計画は、
`codd.py next` の一覧に「立てたあとに N ファイル変わった」と出る。

## 回した結果（2026-10-17）

1 周目（直す前）と 2 周目（直したあと）で、弱いモデルと中くらいのモデルに回させた。

| | モデル | 結果 |
|---|---|---|
| 1 | 弱い | 仕込んだ 5 件をすべて挙げた。ほかに、分の境目で上限の約 2 倍が通る・複数プロセスで数えが分かれる を自由レビューで足した |
| 2 | 中 | 項目 4 件すべて `問題なし`。報告は `OK`、計画は 0 |
| 3 | 中（1 周目）・弱い（2 周目） | 1 周目は続け方が無く、2 回目の報告が「見なかったもの: なし」になって 29 を見落とした。2 周目は `--rest` で 3 回回し、04 と 29 を挙げた |
| 4 | 中（2 周目） | 直したあとのチェックで食い違いが消え、残った計画は重ねなかった |

回して見つけて直したもの:

- 引数の名前（`key`・`value`）や export しない変数（`buckets`）、定数のテストが項目になり、問題の無いリポジトリでも項目が倍に増えた
  → コードで定義していない名前、export するモジュールの export しない変数、大文字の定数のテストを項目にしない
- 上限で見なかったファイルの続け方が無く、次の回が前の回の見つけたものと見残しを消した → `review start --rest` で続け、
  前の回のやりたいことを引き継ぐ。報告の「見なかったもの」に続け方を出す
- 「全体」と頼まれても直近 7 日しか見なかった → `--path .` でどの側も見る
- 範囲が `7 days ago` と git の書き方のまま出た → 「直近 7 日」
- `R04 と同じ` が報告で何を指すか分からなかった → 指した項目のやりたいことを添える
- 立てたあとにコードが変わった計画に気づけなかった → `codd.py next` の一覧に、変わったファイルの数を添える

- 2026-10-23 に `step` で 1〜4 を回し直した。A を `--ref docs`（同じリポジトリのフォルダ）で入れると、`docs/` のファイルが
  「受け持ちのフォルダの外」と知らされていた → 参照先のフォルダが受け持つファイルは挙げない。4 で確かめ直した回が、もう
  立ててある計画と同じやりたいことをもう一度立てられた → `draft --ahead` が断る。2 でやりたいことが無いのに次の計画を
  立てる段の指示が出た → free の検査が `OK やりたいこと 0 件` を出し、その段を飛ばす
- 本流の計画の検査が、実装を文書に合わせる直しでも `ずれ` に参照先の変更案を求めた → ずれは、自分の変更案か参照先の変更案の
  どちらかで直していれば通す

## 2026-10-24 に回し直して直したもの

- 同じ答えから `draft --ahead` を 2 度呼ぶと、やりたいことが複数行のとき重複に気づかず 2 つ目の計画を作った → 行ごとに見比べる
- 自分の側の根拠を、参照先の前提に置いた。同じ根拠を重ねて書いた → 自分の側の根拠は前提に置かず、重ねない
