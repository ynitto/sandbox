# 頼まれて確かめる（レビュー）のケース

「チェックして」で本流ではなくレビューのステートマシン（`review.yaml`）を回し、漏れ・矛盾・設計の不備を
項目と自由レビューで挙げ、何も直さないことを見る。2026-10-17 に `codd.py review` を順に動かして確かめた（PR #971）。

## サンプル

作業用のフォルダに 2 つのリポジトリを並べて作る。どちらも `main` で始め、作ったものをコミットしてから codd を入れる。

**impl（実装）**

- `src/app.py` — `def hello(): return 2` と、`def bye(name): return name`
- `tests/test_app.py` — `hello()` が 2 を返すことを確かめる（`bye` のテストは無い）

**design（設計書）**

- `docs/api.md` — 見出し `## hello`、「`hello` は 1 を返す。`goodbye` もある。」、「実装は `src/app.py`。」

**codd を入れる**: impl は `--side impl --ref ../design --test "python3 -m unittest"`、design は `--side design --ref ../impl`。
入れたあと、impl の `src/app.py` で `hello` の戻り値を 2 に変えて、codd を通さずにコミットする。

## 1. 範囲を挙げずにチェックする

**頼むこと**（impl で）: 実装・テスト・文書に漏れや矛盾がないかチェックして。

**エージェントの判断**: 本流の計画は書かず、`review.yaml` を `target` 空で回す。項目には `review next` で 1 件ずつ答える。

**期待**

- start が `lint` を動かし、直近 30 日に変わった両側のファイル（`src/app.py`・`tests/test_app.py`・`docs/api.md`）から項目を出す
- 項目に `hello` の矛盾（コード・文書・テストの箇所を並べて示す）、`bye` の漏れ（文書とテスト）、文書だけにある `goodbye` の漏れ、
  `src/app.py` の設計の不備、テストのファイルの確かめ漏れが入る
- 示されていない項目に先に答える・項目に無いファイルの行を根拠にする・問題に「やりたいこと」を添えない、のどれでも
  items の検査で止まり、指摘の行だけを直せば通る
- 設計の項目があるのに守る決まりを読んでいなければ止まる（守る決まりが無いサンプルでは止まらない）
- free で `## 自由レビュー` が無ければ止まる。無いなら「なし: 見た範囲と理由」で通る
- report が `hello` の戻り値を合わせるやりたいことを挙げ、「codd を通らずに入った変更を確かめたい」は本流に渡さない
  （このレビューで確かめたため）。どのファイルも変わっていない

## 2. 機能の名前でチェックする

**頼むこと**（impl で）: `bye` まわりの設計に不備がないか見て。

**エージェントの判断**: `impact --term bye` と `explore --term bye` で関係するファイルを探し、`--path src/app.py` で始める。

**期待**: 項目は `src/app.py` から出るものだけになる。直してと言われたら、report の「やりたいこと」の行を依頼にして
本流（`workflow.yaml`）を始める。
