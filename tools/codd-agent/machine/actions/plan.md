この段では**どのリポジトリも変更しないでください**（`.plans/` の計画だけを書く）。
**検査の指摘で戻ってきたとき（この指示の後ろに検査の出力が付いているとき）は、0〜4 をやり直さず、**
**計画の指摘された箇所だけを直して 5 の検査を通してください。** 読み込み・探した記録は残っています。

`caveman` スキルが会話に未読なら `python3 .statemachine/codd/codd.py skill caveman` で読みます。
応答は full で短くし、待機中の実況は省きます。利用者が解除したら従います。計画書と確認に必要な内容、出力形式は保ちます。

**長いコマンドの結果待ち:** 完了通知か終了まで待つ機能を優先します。非同期の結果取得が必要なら、最初は30秒、
実行中なら次から60秒あけます（待機ツールの上限があれば従う）。変化のない待機報告や同じ途中ログの再掲は省きます。
実行中のコマンドを重ねて起動せず、終了コードを確認してから次へ進みます。`verify-plan` の実行タイムアウトは
`workflow.yaml` の `check.timeout_sec` を守ります。ハーネスが検査する場面では、同じ検査を手動で重ねません。
`ReadFile` で `*.out`・`*.log` を確認する場合も同じ間隔を守り、待機中にログ全体を読み直しません。
終了状態の確認を優先し、失敗時は必要な末尾や該当箇所だけ読みます。ログだけで成功と判断しません。

0. **この側・参照先・守る決まり・使うスキルと道具を確かめる。**

   ```bash
   python3 .statemachine/codd/codd.py show --phase plan
   python3 .statemachine/codd/codd.py rule --all
   ```

   - 決まりのファイルは `rule --all` で読み込み、このやりたいことに効く決まりを「守る決まり」に書く
     （読み込み済みで変わっていないものは出し直されない。読み込んでいないものがあると検査で落ちる）
   - 「決まりの候補」が挙がっていれば、関係しそうなものだけ読み、効くなら「守る決まり」に挙げる（設定は変えない）
   - 挙がったスキルは `python3 .statemachine/codd/codd.py skill 名前` で読み込んで従い、道具は実際に使い、
     何を得たかを「使ったスキルと道具」に書く。「リポジトリのスキル」は説明で判断し、関係するものだけ読み込む。
     「使ったスキルと道具」には使ったものだけを書く。変えるときに使うスキルもここで決めて書く
1. **参照先を探す。** やりたいことに固有の語（機能名・API や画面の名前・用語）を 3〜8 個選んで実行します。
   ありふれた語は避けます（一致が増え、扱うファイルが増えるだけ）。

   ```bash
   python3 .statemachine/codd/codd.py explore --term "語1" --term "語2"
   ```

   一致した行が `パス:行  その行` で出ます。**まずその行で関係を判断し、関係しそうなファイルだけ、その行の前後
   （見出し 1 つぶん程度）を行番号で範囲を指定して開きます。ファイル全体は読みません。**
2. **参照先を 3 つに分ける。** 前提（参照先が「すでにそうなっている」と定めていること）・制約（「こうしなければならない /
   してはならない」）・その他（決まっていないこと・任されていること・補足）。
3. **自分の現状と比べる。** 自分の該当箇所を読み、食い違うものを「ずれ」に挙げます。
4. **変更を練る。** 自分の変更案と、ずれがあれば参照先の変更案を書きます。変わる・使う名前（関数・API・用語・見出し）と、
   変わる画面の文言・URL は `…` で囲みます（e2e のケースはコードの名前ではなく文言や URL で書かれています）。ハーネスはその名前と、変えるファイルとパスで指し合うファイルから、響く範囲（呼び出し元・参照先・
   テスト・文書の書式の見本）を測ります。
5. **計画を書いて検査する。** ひな形を置き（進めている計画があれば残す）、**見出しごとに**コメントを本文に置き換えます。
   名前は、やりたいことを表す英語の短い名前（小文字・数字・ハイフン。例: `hello-returns-two`）。日時と合わせて
   `.plans/日時-名前.md` になります。
   見出しの名前と順番は変えません。1 回の書き込みで全文を書かないでください（応答の長さに上限があるエージェントでは
   途中で止まります）。練り直すときは、直す見出しだけを書き換えます。

   ```bash
   python3 .statemachine/codd/codd.py draft --name 英語の短い名前
   python3 .statemachine/codd/codd.py verify-plan
   ```

   **検査は、測ったのに計画に無いファイルを「未判断」の行として該当の見出しに書き足します。** その行を判断に
   書き換えます: 自分のファイルは直し方か `変更不要: 理由`、テストは直し方か `変更不要: 理由`、参照先のファイルは
   示した行の前後だけを読んで前提・制約・ずれの根拠に移すか `関係なし: 理由`（関係しないものは
   `- 関係なし: パス:行, パス:行 — 理由` と 1 行にまとめてよい）、書式の見本は守り方。「未判断」が残ると通りません。

   - 根拠は `パス:行`・`パス:行-行`・`パス#見出し` で読んだ箇所を指す（参照先が複数なら `名前:パス`）。
     指した行・見出しが無い、前提・制約・その他で `…` に囲んだ名前が根拠のファイルに無いと落ちる
   - 自分の変更案には変えるファイル（テストも）をすべて挙げる。ここと影響範囲に無いファイルは apply で変えられない
   - **テストもコード・仕様書と同じ成果物。** 足す・直すテストを「テストの変更案」に書く。何かを変えるのに「なし」は
     認めない（要らないなら `- 変更不要: 理由`）。「変更不要」だけ・空の理由は検査で落ちる。
     新しく足す名前（関数・API・仕様の項目）は、今あるテストに当たらないので、確かめるテストを足す。単体テストも、
     画面に出るなら e2e のケースも考え、`- tests/test_app.py — `greet` が挨拶を返すことを確かめるケースを足す` のように
     名前を添えて書く（要らないなら `` - `greet` — 変更不要: 理由 ``）。仕様書だけを変えるときも、実装の側のテストを挙げる。
     対象は行の先頭に `- tests/test_app.py — 直し方` と書く。複数ならパスをカンマで区切り、参照先は `名前:パス`。
     検索コマンドは説明部分のインラインコード・コードブロック、または `- 検索: コマンド` の補足に書く。
     コマンドの入力・出力パスは変更対象に数えない。検索の記録だけではテストの変更案や変更不要の理由の代わりにならない。
   - **文書の今の書式は決まり。** 変える文書は今の見出しの並び・表の形・言い回しを、新しい文書は同じフォルダの見本の
     書式を守る。見出しを変える・消すなら計画に `## 見出し` と書く
   - `show` に「変えたあとに実行するもの」があれば、その検査で作り直すファイルも挙げる（文書に貼った画面の画像は除く。
     ハーネスが差し替える）。テストで得たもの（`codd.py evidence`）を文書に写すときは `<!-- evidence: id -->` の印で写す
   - 当てはまるものが無い見出しは「なし」（ずれが「なし」なら参照先の変更案と影響範囲も「なし」）
   - **1 回で終わる大きさにする。** 変えるファイルが上限を超えると落ちる。絞って、残りを「今回やらないこと」に書く。
     上限より少なければ、多くても絞らなくてよい（変えるときはハーネスが段に分ける）


計画は短く書く。変更不要の判断は検査通過時に内部の検査記録へ移され、計画書・要約・結果には載らない。
関係なしは共通の理由ごとにまとめる。変更や根拠の説明を見出し間で繰り返さない。

**出力形式:** 書き終えたら第 1 行に `OK`、書けなかったら `FAILED` と理由。
