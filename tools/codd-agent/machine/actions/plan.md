## [plan: 参照先を読み、変更を練る]

**やりたいこと:** {{request}}
**前回の確認での答え（NG と指摘があれば、それを踏まえて練り直す）:** {{answer}}
**止まったときの利用者の答え（あれば、それを踏まえて練り直す）:** {{choice}}

この段では**どのリポジトリも変更しないでください**（`.plans/` の計画だけを書く。変えると計画の検査が止め、利用者に確かめます）。
**検査の指摘で戻ってきたときは、0〜4 をやり直さず、指摘された箇所だけを直してください。** 読み込み・探した記録は残っています。

0. **この側・参照先・従う手順（決まり・スキル・道具）を確かめる。**

   ```bash
   python3 .statemachine/codd/codd.py show --phase plan
   python3 .statemachine/codd/codd.py guide --all
   ```

   計画の「従う手順」には、効く決まり・使ったスキルと道具・ファイルに決められた手順を、どう従うかと一緒に書く。
   - 決まりのファイルは `guide --all` で読み込み、このやりたいことに効く決まりを書く
     （読み込み済みで変わっていないものは出し直されない。読み込んでいないものがあると検査で落ちる）
   - 最初に出る「読み書きの手順」は、この回のすべての段で従う（計画に挙げなくてよい）
   - 「決まりの候補」が挙がっていれば、関係しそうなものだけ読み、効くなら挙げる（設定は変えない）
   - 挙がったスキルは `guide 名前` で読み込んで従い、道具は実際に使い、
     何を得たかを書く。「リポジトリのスキル」「関係すれば使う手順」は説明で判断し、関係するものだけ読み込む。
     使ったものだけを書く。変えるときに使うスキルもここで決めて書く
   - 「ファイルに決められた手順」は、計画で作る・変えるファイルに当たるものを検査が「従う手順」に書き足す。
     `guide 名前かパス` で読み込み、その手順が求めるもの（付随するファイルなど）を計画に入れる（読み込まないと検査で落ちる）
1. **グラフを用意してから、参照先を探す。** まず `graph` を実行します。`PENDING` と出たら、示されたとおりに束ごとに
   文書を抜き出し（サブエージェント `codd-graph` に渡すと示されたら、自分では文書を読まない）、`graph --merge` を実行します。
   `OK` が出るまで繰り返します（`FAILED` と出た束だけをやり直す）。
   続けて、やりたいことに固有の語（機能名・API や部品の名前・用語）を 3〜8 個選んで探します。
   ありふれた語は避けます（一致が増え、扱うファイルが増えるだけ）。

   ```bash
   python3 .statemachine/codd/codd.py graph
   python3 .statemachine/codd/codd.py explore --term "語1" --term "語2"
   ```

   一致した行が `パス:行  その行` で出ます。**まずその行で関係を判断し、関係しそうなファイルだけ、その行の前後
   （見出し 1 つぶん程度）を行番号で範囲を指定して開きます。ファイル全体は読みません。**
2. **参照先を 3 つに分ける。** 前提（参照先が「すでにそうなっている」と定めていること）・制約（「こうしなければならない /
   してはならない」）・その他（決まっていないこと・任されていること・補足）。
3. **自分の現状と比べる。** 自分の該当箇所を読み、食い違うものを「ずれ」に挙げます。
4. **変更を練る。** 自分の変更案を書き、ずれを参照先のほうで直すなら参照先の変更案も書きます（自分を参照先に合わせるなら自分の変更案だけでよい）。変わる・使う名前（関数・API・用語・見出し）と、
   変わる表示の文言・URL は、コードや文書にあるとおりの綴りをバッククォートで囲みます（`createOrder` のように。`…` などで省略しない。e2e のケースはコードの名前ではなく文言や URL で書かれています）。ハーネスはその名前と、変えるファイルとパスで指し合うファイルから、響く範囲（呼び出し元・参照先・
   テスト・文書の書式の見本）を測ります。
5. **計画を書く。** ひな形を置き（進めている計画があれば残す）、**見出しごとに**コメントを本文に置き換えます。
   名前は、やりたいことを表す英語の短い名前（小文字・数字・ハイフン。例: `hello-returns-two`）。
   立てておいた計画（`.plans/next/`）を進めるよう頼まれたときは、`--name` の代わりに `draft --next ファイル名` で引き継ぎ、
   書いてある見出しを今のコードと参照先で確かめ直します（「立てたあとに変わったファイル」が出たら、そこを読み直す）。
   見出しの名前と順番は変えません。1 回の書き込みで全文を書かないでください。

   ```bash
   python3 .statemachine/codd/codd.py draft --name 英語の短い名前
   ```

   - 根拠は `パス:行`・`パス:行-行`・`パス#見出し` で読んだ箇所を指す（参照先が複数なら `名前:パス`）
   - 自分の変更案には変えるファイル（テストも）をすべて挙げる。ここと影響範囲に無いファイルは apply で変えられない
   - **テストもコード・仕様書と同じ成果物。** 「テストの変更案」は必ず書く。新しく足す名前は、確かめるテストを名前を添えて足す
     （`- tests/test_app.py — `greet` が挨拶を返すことを確かめるケースを足す`）。要らないなら `- 変更不要: 理由`
   - 見出しを変える・消すなら、計画に `## 見出し` と書く（文書の今の書式は決まり。見本と守り方は検査が「従う手順」に書く）
   - テストで得たもの（`codd.py evidence`）を文書に写すときは `<!-- evidence: id -->` の印で写す
   - 当てはまるものが無い見出しは「なし」（コメントのままでもよい）。人の承認が要るファイルも、変える必要があれば挙げてよい
   - 変えるファイルが上限を超えたら絞り、残りを「今回やらないこと」に書く

   書き終えたら出力（`OK`）を返します。**検査（`verify-plan`）は次の段が動かすので、自分では動かしません。**
   検査が落ちると、指摘が付いて戻ってきます。測ったのに計画に無いファイルは「未判断」として番号（`U3`）付きで出るので、
   計画のファイルを開かずに `codd.py judge` で答えます（自分のファイルとテストは直し方か変更不要、参照先は関係なしか、
   前提・制約・ずれの根拠に書いてから `--drop`）。同じ答えはまとめて渡します。

   ```bash
   python3 .statemachine/codd/codd.py judge U3 U5-U9 --skip "表示だけで名前を使わない"
   python3 .statemachine/codd/codd.py judge U4 --fix "`createOrder` の呼び出しを新しい引数に合わせる"
   ```


計画は短く書く。変更不要の判断は検査通過時に内部の検査記録へ移され、計画書・要約・結果には載らない。
関係なしは共通の理由ごとにまとめる。変更や根拠の説明を見出し間で繰り返さない。

**応答:** `caveman` の full で短く（利用者が解除したら従う）。待機中の実況はしない。`summary`・`record` の出力と出力形式は省かず、変えない。
**待ち方:** 長いコマンドは終わるまで待つ（非同期なら最初 30 秒、以後 60 秒おき）。重ねて起動せず、終了コードで判断する（詳しくはエージェント定義の「長いコマンドの結果待ち」）。

**出力形式:** 書き終えたら第 1 行に `OK`、書けなかったら `FAILED` と理由。

この指示に従ってタスクを実行してください。
完了後、指定された形式で出力のみを返してください。次のステップは別途指示されます。
