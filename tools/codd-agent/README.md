# codd-agent

**実装と設計書（仕様）を食い違わせずに変えていくためのステートマシン。**
やりたいことを伝えると、参照先（実装なら設計書、設計書なら実装）を探して自分の変更を練り、確認を取ってから変える。
参照先の前提・制約とずれていれば、参照先の変更案とその影響範囲も見せ、了承されれば両方を変える。

> 設計: [`docs/designs/codd-agent-design.md`](../../docs/designs/codd-agent-design.md)
>
> 名前の近い [codd-gate](../codd-gate/README.md) は、1 つのリポジトリの中で文書・コード・テストの食い違いを
> 受け入れ前に止める検査ツール。codd-agent はそれとは別のもので、変える前に参照先を読んで確かめ、
> 了承を得てから両方を変えるステートマシン。

- 同じ定義を**両方のリポジトリに置く**。実装側で動かせば参照先は設計書、設計書側で動かせば参照先は実装。
  参照先はいくつでも持てる（設計書が API と画面で分かれている、など）。
  実装と設計書が**同じリポジトリの別フォルダ**にあってもよい（[下記](#実装と設計書が同じリポジトリにあるとき)）
- モデルの申告を信じず、スクリプトが確かめる（[下記](#何を確かめるか)）。入力（影響箇所を漏れなく見つけたか）・
  過程（決まりを読み、決めたスキルと道具を使ったか）・出力（計画どおりに、最後まで変えたか）のそれぞれで止める
- **1 回の実行は 1 つの会話で終わる大きさに保つ。** 変えるファイルが上限（既定 60）を超える計画は通さず、
  残りは「今回やらないこと」に回して、終わるときに次にやることとして伝える
- **変えるファイルが多い計画は、段に分けて変える。** 1 つの段は既定 10 ファイル。
  段ごとに挙げたファイルを変え終えたかを確かめてから次の段へ進むので、変え残しをその段のうちに見つける
- 計画を練るとき・変えるときに従う手順（守る決まり・スキル・道具）を設定できる
- カスタムエージェント `codd`（kiro-cli・GitHub Copilot）にやりたいことを伝えるだけで動く。依存は python3 と git だけで、
  言語やビルドの仕組みを問わない
- 参照先を探すとき、[graphify](https://pypi.org/project/graphifyy/) があれば知識グラフを使う。
  グラフはリポジトリが変わるたびに自動で作り直す。無ければ文字列検索だけで動く

## 置き方

置き方は 2 つに分かれる。

### 1. 外部のミドルウェアを端末に入れる（端末ごとに 1 回）

graphify（任意。参照先を探すときの知識グラフ）を uv・pipx・pip のどれかで入れ、git があるかを確かめる。
続けて caveman・graphify の外部スキルを Kiro・Copilot のユーザー領域へ配置する（既定は両方。エージェントの CLI は無くてよい）。
`--upgrade` を付けると、入っているものも最新にする（caveman も配布元から取り直す）。

```bash
python3 tools/codd-agent/install.py
# 片方だけ導入する
python3 tools/codd-agent/install.py --agent kiro
python3 tools/codd-agent/install.py --agent copilot
# スキルを配置せず、graphify 本体だけ導入する
python3 tools/codd-agent/install.py --no-skills
```

この配布リポジトリのルートで実行する。`tools/codd-agent/install.py` だけで導入でき、リポジトリ直下の `install.py` は要らない
（直下の `install.py` の外部ツールのセットアップでも graphify は入る）。外部の配布元へのネットワーク接続が必要。

caveman と graphify のスキルは codd-agent に内包せず、`init.py` でもコピーしない。caveman は公式 GitHub から取得し、
graphify は本体の登録処理（`graphify install --platform kiro` など）で置く（`references/` もこの処理が置く）。そのため graphify 本体が入らなかったときは、
graphify スキルも置けない。すでに入っている caveman スキルは、`--upgrade` を付けない限りそのまま残す。
Windows では `USERPROFILE`、その他ではホームディレクトリの下に置く。

| 対象 | スキルの保存先 |
|---|---|
| Kiro IDE / CLI | `~/.kiro/skills/caveman/`、`~/.kiro/skills/graphify/` |
| VS Code Copilot / CLI | `~/.copilot/skills/caveman/`、`~/.copilot/skills/graphify/` |

### 2. codd をリポジトリに置く（リポジトリごとに 1 回）

`.statemachine/codd/` に定義を写し、`codd.json` を書く。

```bash
# 実装のリポジトリへ（参照先 = 設計書）
python3 tools/codd-agent/init.py ~/work/my-app --side impl --ref docs=../my-app-docs
# 設計書のリポジトリへ（参照先 = 実装）
python3 tools/codd-agent/init.py ~/work/my-app-docs --side design --ref app=../my-app
# 参照先が複数
python3 tools/codd-agent/init.py ~/work/my-app --side impl --ref api=../api-docs --ref ui=../ui-docs
```

`--ref` は `名前=パス` か `パス`（名前はフォルダ名になる）。初めて置くときは `--side` と `--ref` が要る。

`init.py` は次をする。

- `<リポジトリ>/.statemachine/codd/` に定義とスクリプトを写し、`codd.json` に設定を書く
- カスタムエージェント `codd` を書く（[下記](#カスタムエージェントkirogithub-copilot)）
- 作業ファイルを置く `.codd/` を `.gitignore` に足す（`--no-gitignore` で足さない）。
  このマシン自身が graphify の索引に入らないよう、`.graphifyignore` に `.statemachine/codd/` を足す
- 初めて置いたときは、自分と参照先から決まりらしいマークダウン（コーディングルールなど）を探し、
  `codd.json` の `guides` に書く（[下記](#守る決まりを見つける)。`--no-discover-rules` でやめる）

もう一度 `init.py` を実行すると、定義とスクリプトを入れ替え（前の版のファイルは消す）、`codd.json` は上書きせずに残す。
次の引数を渡したときだけ、その項目を書き換える。

| 引数 | 書き換え方 |
|---|---|
| `--side` | 入れ替える |
| `--ref` | 参照先の一覧を入れ替える。同じ名前の参照先に手で書いた `guides`・`scope`・`exclude` などは残す |
| `--scope` | 自分の `scope` を入れ替える |
| `--ref-scope 名前=フォルダ` | その参照先の `scope` にフォルダを足す |
| `--exclude` / `--ref-exclude 名前=パターン` | その呼び出しで渡したパターンに入れ替える。`--exclude ""` / `--ref-exclude 'docs='` で空にする |
| `--test` / `--check` | 入れ替える。`""` で消す |
| `--evidence` | 渡した一覧に入れ替える。`""` で結果を扱わなくする |

置き先の名前は `codd` のまま変わらないので、前の版で置いたものもそのまま入れ替えられる。
前の使い方（`install.py <リポジトリ> --side … --ref …`）で呼ぶと、そのまま `init.py` に渡す。
手で置くなら `machine/` の中身をそのフォルダへ写し、`codd.json` を直せばよい。

### カスタムエージェント（Kiro・GitHub Copilot）

`init.py` は、コードや文書を変える依頼を**必ずこのステートマシンで進める**カスタムエージェント `codd` も書く。

| 使うもの | 書くファイル | 呼び方 |
|---|---|---|
| Kiro IDE / CLI | `.kiro/agents/codd.json` | IDE のエージェント選択で `codd`、CLI は `kiro-cli chat --agent codd` |
| GitHub Copilot | `.github/agents/codd.agent.md` | チャットのエージェント選択で `codd` を選ぶ |

エージェントは、変える依頼を受けたらステートマシンを始め、外でファイルを変えない。読むだけの質問にはそのまま答える。
statemachine-use スキルが無い環境でも、エージェントの指示だけで `workflow.yaml` を回せる。kiro-cli では始めるたびに
`codd.py show` を実行して、参照先・守る決まり・使うスキルを読み込む。
置くたびに書き直す生成物なので、手で直さない。`--agent kiro` で片方だけ、`--no-agents` で書かない。
すでに置いたリポジトリでエージェントの指示を新しくするときも、`init.py` をもう一度実行する。

## 使い方

エージェント `codd` を選び、やりたいことを伝える（「`hello` の戻り値を 2 にしたい」など）。変える依頼なら、
エージェントが自分でステートマシンを始める。カスタムエージェントを使わないときは、statemachine-use スキルのある
エージェントに「codd のステートマシンを実行して」と頼んでもよい。

```
plan ─→ confirm ─┬─ OK ─→ apply ─→ done
  ↑              ├─ NG ─┐
  └──────────────┼──────┘（指摘を踏まえて練り直す）
                 └─ やめる ─→ 何も変えずに終わる

検査で止まったら（plan・apply のどちらでも）:
stuck ─┬─ 練り直す ─→ plan（変えた分は残すか戻すかを選ぶ）
       ├─ 変え直す ─→ apply
       └─ やめる   ─→ 結果を伝えて終わる
```

1. **練る（plan）** — 参照先を探し、やりたいことに関係する記述を**前提・制約・その他**に分ける。
   自分のリポジトリの現状と比べて、ずれているものを挙げ、自分の変更案を書く。
   ずれがあれば参照先の変更案を書き、それを自分のリポジトリに適用したときの**影響範囲を測る**。
   この段ではどちらのリポジトリも変えない
2. **確認する（confirm）** — 計画と測った影響範囲を見せて OK / NG / やめるを訊く。NG なら指摘を踏まえて 1 に戻る。
   変えてよいのは、検査を通ってここで OK とした計画だけ（ほかの計画で変えると、変えたあとの検査で落ちる）
3. **変える（apply）** — 自分の変更案を適用する。参照先の変更案があれば参照先も変え、
   **実際の変更から影響範囲を測り直す**。
   コミットはしないので、内容を確かめてからそれぞれのリポジトリでコミットする

| 分類 | 意味 |
|---|---|
| 前提 | 参照先が「すでにそうなっている」と定めている事実・決定・振る舞い・用語 |
| 制約 | 参照先が「こうしなければならない / してはならない」と課している条件 |
| その他 | それ以外の関係する記述（決まっていないこと・任されていること・補足） |

確認は会話の中で待つ。会話で動かすことを前提にしており、人の返事を受け取れない無人の実行ではここで止まる。

### 計画を確かめる

計画は `.plans/日時-名前.md`（名前はエージェントが付ける英語の短い名前。例: `2026-10-02-2330-hello-returns-two.md`）に
書かれる。確認では、計画の全文ではなく要約（やりたいこと・ずれ・変えるファイル・テスト・今回やらないこと）が出るので、
全文はこのファイルを開いて読む。

- 計画の最後の「今回やらないこと」は、この回では扱わないもの。終わるときに次にやることとして伝える
- 計画が「人の承認が要るファイル」（[下記](#人の承認が要るファイル)）を変えるときは、要約に別に出し、変えてよいかをはっきり訊く。
  認めないファイルは「今回やらないこと」へ回す
- 変えるファイルが `batch_files`（既定 10）より多いときは、変える段を段に分けて進める。計画と確認は 1 回のまま

終わると（done・stopped）、確認の答え・止まったときの答えと結果を計画に書き足し、同じ名前のまま判断の記録として残す
（コミットしてよい）。記録には、使わなかったスキル・関係なしとしたファイル・中身が「なし」の見出しを残さない。
終わった回の記録を書き換えると、次の回の検査で落ちる。
`.plans/` は変えたファイルや探す対象に数えない（旧 `docs/.plans/`・`docs/.plan/` も同じ。旧記録は移動せず、点検でも読まない）。

### 止まったとき

計画の検査が落ちると、エージェントはまず自分で直してやり直す（2 回まで）。
それでも通らないときや、変えたあとの検査が落ちたときに、落ちた理由が人の判断の要らないもの（テストや検査の失敗・変え残し・
計画に無い変更・影響の直し忘れ・同じ綴りの別の名前・書いたパスの誤り・記録の漏れ・計画の書き方・「未判断」の行の残り）だけなら、
訊かずにもう一度やり直す（2 回まで。前回と同じ指摘が残っていれば、回数が残っていても訊く）。
テストや検査が落ちたときは、変える前の中身でも同じコマンドを動かす（一時的な作業フォルダで。今の作業中の
ファイルには触れない）。同じところで前から落ちていたなら、この回の変更のせいではないので、直させずに訊く。
「前から落ちていたものとして続ける」を選ぶと、同じ失敗だけを通し、新しい失敗はこれまでどおり止める。
計画を変える・範囲を絞る・変えた分を戻すなど、人の判断が要るものが混じるときや、やり直しても通らないときは止まり、
次を見せてどうするかを訊く。答えるまで先へ進まない。

- 止めている理由（どのファイルの、何が足りないか）
- 確かめたいこと（例: このファイルは「変更不要」でよいか、今回どこまでやるか、設定を直してもらえるか）
- 選択肢と勧め

| 選択肢 | どうなるか |
|---|---|
| 計画を練り直す | 答えを踏まえて計画から作り直す |
| 計画はそのままで、変え直す | 答えを踏まえて変更をやり直す |
| 変えた分は残して、計画を直す | 変更はそのまま、計画にファイルを足す・「変更不要」と書くなどして確認からやり直す |
| 変えた分を戻して、計画から練り直す | 計画を確認する直前の中身に戻してから練り直す。計画より前から作業中だった変更は、その中身に戻る |
| 計画に無いファイルを足したのを認める | 変える段で理由を書いて足したファイルを認め（`accept`）、続ける |
| 前から落ちていたものとして続ける | 変える前から同じところで落ちていたテストを認め（`accept`）、続ける |
| ここでやめる | 結果を伝えて終わる。変えた分を残すか戻すかも訊く |

手で確かめるなら次のとおり。途中でコミットしていると、戻すことはできない（git で戻す）。

```bash
python3 .statemachine/codd/codd.py advise          # 止めている理由・確かめること・選択肢（.codd/advice.md にも残る）
python3 .statemachine/codd/codd.py rollback        # 変えた分を戻す
```

変えた分を残したまま計画を直すときは、何も実行しなくてよい。同じ計画で変えたファイルがあれば、計画の検査をし直しても
変える前の印を取り直さず、変え終えたファイルは「変えた」と数え続ける。

### 終わりの報告

終わるとき（done）は `codd.py report` の出力をそのまま伝える（モデルがまとめ直さない）。報告には、計画に挙げたファイルごとに
変えたかどうか、変えたあとに測って対応した影響範囲、次にやること（「今回やらないこと」）が出る。
参照先とパスでつながっていない自分の変更があれば、それも挙げる。同じ内容は `.codd/report.md` に残る。

変えたあとの検査をまだ通っていないときや、通ったあとにさらに変わっているときは、終了コード 1 でそう伝える。

### 手で使うコマンド

どれもリポジトリのルートで実行する。

```bash
python3 .statemachine/codd/codd.py show            # 参照先の一覧、守る決まり、段階ごとに使うスキルと道具
python3 .statemachine/codd/codd.py show --phase apply
python3 .statemachine/codd/codd.py rules           # 守る決まりと、設定に無い候補
python3 .statemachine/codd/codd.py explore --term 語   # 参照先を探す（--ref 名前 で絞る）
python3 .statemachine/codd/codd.py impact --term 語    # 自分のリポジトリの影響範囲を探す
python3 .statemachine/codd/codd.py graph           # グラフを用意する（文書を LLM で読むときは束を出す。下記）
python3 .statemachine/codd/codd.py evidence        # テストで得たものと、文書の印の様子
python3 .statemachine/codd/codd.py lint            # 定期的な点検（下記）
```

## 設定（codd.json）

設定は `.statemachine/codd/codd.json` に書く。

```json
{
  "side": "impl",
  "refs": [
    {"name": "api", "path": "../api-docs"},
    {"name": "ui", "path": "../ui-docs"}
  ],
  "guides": [
    {"use": "skill:domain-modeler", "when": {"phase": "plan"}},
    {"use": "skill:tdd", "when": {"phase": "apply"}}
  ],
  "graphify": "auto",
  "max_files": 60,
  "batch_files": 10,
  "subagent": false
}
```

| 項目 | 値 |
|---|---|
| `side` | このリポジトリの側。`impl`（実装）か `design`（設計書） |
| `refs` | 参照先の一覧。`name`（英数字と `_` `.` `-`。省略するとフォルダ名）と `path`（相対パスはこのリポジトリのルートから）。**置き場所が変わったらここを手で直す** |
| `guides` | 任意。従う手順（守る決まりのマークダウン・スキル・道具）を、いつ・どれだけ確かに従うかと一緒に並べる。[下記](#従う手順guides) |
| `refs[].guides` | 任意。その参照先を変えるときに足す手順。参照先が決めた手順に足すだけで、外せない |
| `skills` / `tools` / `rules` / `refs[].skills` / `refs[].rules` | 前の版の書き方。今も読み、`guides` と同じに扱う（`skills.plan` は計画を練るとき、`skills.apply` は変えるときのスキル、`tools` は同じ形の道具、`rules` はいつも守る決まり） |
| `skill_dirs` | 任意。設定しなくても使うスキルの置き場所（既定 `[".agents/skills"]`。`名前/SKILL.md` の形）。`[]` で使わない |
| `graphify` | `auto`（あれば使う）か `off`。文書の意味もグラフに入れるなら `{"semantic": "session"}` か `{"semantic": "ollama", "model": "qwen2.5-coder:7b"}` のように書く（[下記](#文書の意味もグラフに入れる)） |
| `test` | 任意。変えたあとに動かすテストのコマンド。1 つなら配列（例: `["npm", "test"]`）、単体・API・シナリオなどいくつもあるなら名前ごと（例: `{"単体": ["npm", "test"], "API": ["npm", "run", "test:api"]}`）。参照先も変えたときは、参照先の `codd.json` の `test` も動かす |
| `tests` | 任意。テストのファイルの書き方（glob の配列）。既定は `test/**`・`tests/**`・`e2e/**`・`**/*.test.*`・`**/*.spec.*`・`**/test_*.py`・`**/*.feature`・`**/*.http`・`**/scenarios/**` など。`[]` でテストを扱わない |
| `evidence` | 任意。テストで得たもの（振る舞い・時間・画面）を書いたファイル（glob の配列）。既定 `[]`（扱わない）。使う結果ファイルのパスを明示する |
| `check` | 任意。テストのあとに実行する検査コマンドの配列（例: `["webui-test", "check"]`）。参照先も変えたときは、参照先の `codd.json` の `check` も実行する |
| `scope` | 任意。このリポジトリのうち自分が受け持つフォルダの配列（例: `["src", "tests"]`）。書かなければ全体 |
| `refs[].scope` | 任意。その参照先のうち読む・変えるフォルダの配列。書かなければ全体 |
| `exclude` | 任意。自分側で対象から除くパス・glob の配列。ルートからの相対。省略・`[]` は追加の除外なし |
| `refs[].exclude` | 任意。その参照先で対象から除くパス・glob の配列。参照先のルートからの相対。参照先自身の `exclude` は継承せず、この項目で指定する |
| `protect` | 任意。人の承認なしに変えないファイル（パス・glob の配列。書き方は `exclude` と同じ）。[下記](#人の承認が要るファイル) |
| `refs[].protect` | 任意。その参照先で、人の承認なしに変えないファイルを足す。参照先自身の `codd.json` の `protect` はそのまま効き、外せない |
| `max_files` | 任意。1 回で変えるファイルの上限（既定 60）。自分の変更案・参照先の変更案・「変更不要」でない影響範囲・テストの変更案のファイルを数える |
| `batch_files` | 任意。変えるときの 1 つの段のファイルの数（既定 10）。`max_files` までの計画を、この数ずつに分けて変える |
| `subagent` | 任意。`true` なら、変える段をサブエージェント `codd-apply` に 1 段ずつ渡す（既定 `false` で、codd が自分で変える）。「サブエージェントに渡す」を参照 |

知らない項目（綴り違いなど）があると、動かす前に止まる。

### 実装と設計書が同じリポジトリにあるとき

実装と設計書が同じリポジトリ（例: `src/` と `docs/`）にあるときは、参照先の `path` を `.` にし、
自分と参照先がそれぞれ受け持つフォルダを `scope` に書く。探す・根拠を認める・変わったかを測るのは、
それぞれのフォルダの中だけになる。フォルダが重なっている・書いていないときは動かす前に止まる。
どの `scope` にも入らないファイル（CI の設定など）に、変わる名前が出てくるときは、計画の検査が「知らせ」として挙げる
（検査は止めない。環境変数や API の改名なら、一緒に直すかを確かめる）。

```bash
python3 tools/codd-agent/init.py ~/work/my-app --side impl --scope src --scope tests \
    --ref docs=. --ref-scope docs=docs
```

```json
{"side": "impl", "scope": ["src", "tests"], "refs": [{"name": "docs", "path": ".", "scope": ["docs"]}]}
```

### 設定ファイルなどを対象から除く

codd 自身の生成物以外の設定ファイルは、自動では除外しない。`scope` は対象フォルダを限定するだけなので、
その中に混在する設定を除くには、自分側の `exclude` と参照先ごとの `refs[].exclude` を指定する。
「実装・テスト・ドキュメントだけ」をファイルの種類から自動選別する機能はない。

```json
{
  "side": "impl",
  "scope": ["src", "tests"],
  "exclude": ["**/*.config.*", "src/settings.json", "tests/fixtures/config/"],
  "refs": [{
    "name": "docs",
    "path": "../my-app-docs",
    "scope": ["docs"],
    "exclude": ["docs/settings/", "**/*.config.*"]
  }]
}
```

パターンはそれぞれのリポジトリのルートからの相対で、`*`・`?`・`[...]` はフォルダをまたがず、
`**/` は 0 階層以上をまたぐ。`{ts,tsx}` はどれか 1 つに一致し、先頭の `./` は無視する。例: `*.json` はルート直下、`**/*.json` は全階層の JSON に一致する。
フォルダのパス（`docs/settings` または `docs/settings/`）は中のファイルも除く。
絶対パス・`..`・`!` による再包含は使えない。`scope` と重なれば除外を優先する。

除外したファイルは、検索（graphify の候補も）・影響範囲・パスのつながり・テストファイルの選別・点検・変更検出の
対象に数えず、計画の変更案や根拠にも使えない。graphify の索引は従来どおりリポジトリ全体で作り、検索結果を絞る。
`AGENTS.md` などのよくある決まりと、`guides` などに指定した決まりは、除外しても読み込む。
決まりの候補探しも除外の対象にしない。設定した `test` / `check` のコマンドの実行範囲は変わらない。

初期化コマンドからも指定できる（glob はシェルが展開しないよう引用符で囲む）。

```bash
python3 tools/codd-agent/init.py ~/work/my-app \
    --exclude '**/*.config.*' --exclude 'src/settings.json' \
    --ref-exclude 'docs=docs/settings/' --ref-exclude 'docs=**/*.config.*'
```

`codd.py show` に現在の除外パターンを表示する。

### 人の承認が要るファイル

要件定義・ガイドライン・互換性のために残す旧いコードのように、エージェントが人の承認なしに変えてはいけないファイルは
`protect` に書く。

```json
{
  "side": "impl",
  "protect": ["docs/requirements/", "docs/guidelines/**/*.md", "src/legacy/"],
  "refs": [{"name": "docs", "path": "../my-app-docs", "protect": ["docs/adr/"]}]
}
```

- 計画が当たるファイルを変えるときは、確認の要約に「人の承認が要るファイル」として別に出し、変えてよいかを
  はっきり訊く。認めないファイルは計画の「今回やらないこと」へ回す。何を承認したかは計画の記録に残る
- 変えたあとの検査は、確認で OK と答えた計画に挙げていない当たるファイルを変えていたら止める。変える段で「追加」と
  申告しただけでは通らず、利用者が認めた（`accept`）ものだけが通る。
  変更の影響を受けるだけのものも、エージェントに直させずに止めて訊く。どちらも訊かずにやり直すことはしない
- 参照先が自分の `codd.json` に書いた `protect` は、呼び出し元からも効く。呼び出し元は `refs[].protect` で足せるだけ
- 同じリポジトリの参照先には、自分の `protect` がそのまま効く

### テストと検査コマンド

`test` には変えたあとに動かすテストを、`check` にはそのあとに実行する検査コマンドを書く。参照先も変えたときは、
参照先に置いた `codd.json` の `test` と `check` も動かす。どのファイルがテストかは `tests` の書き方で決まり、
参照先のテストは参照先の `codd.json` の `tests` を使う。

```bash
python3 tools/codd-agent/init.py ~/work/my-app --side impl --ref docs=../my-app-docs --test "npm test"
```

`test` が無いと、変えたあとの検査はテストを動かさずに通る。そのときは `show` と終わりの報告に「動かしていない」と出る。
`init.py` は、`--test` を渡さずに置いたとき、よくある置き方（`package.json` の `test`・pytest の設定・`go.mod`・
`Cargo.toml`・`Makefile` の `test`・`tests/test_*.py`）から推したコマンドを示す（`codd.json` には書かない）。

テストはコード・仕様書と同じく整合を取る成果物として扱い、変更が響くテストを計画に挙げさせる（[下記](#テストもコード仕様書と同じに扱う)）。

### 従う手順（guides）

読んで従うもの（決まりのマークダウン・スキル・道具）は、`codd.json` の `guides` に 1 件ずつ、「何を（`use`）」「いつ（`when`）」
「どれだけ確かに（`must`）」で書く。

```json
{
  "guides": [
    {"use": "docs/coding-rules.md"},
    {"use": "skill:tdd", "when": {"phase": "apply"}},
    {"use": "tool:github", "when": {"phase": "plan"}},
    {"use": "skill:migration", "when": {"files": ["db/migrations/*.sql"], "change": ["create"]},
     "check": ["python3", "tools/check_migrations.py"]},
    {"use": "docs/api-writing.md#表の書き方", "when": {"files": ["docs/api/**/*.md"]},
     "asks": ["戻り値の表に型の列がある"]}
  ]
}
```

| 項目 | 値 |
|---|---|
| `use` | `パス.md`（`#見出し` を付けるとその節だけ。glob も書ける）・`skill:名前`・`tool:名前`（MCP サーバーやコマンド）。参照先のものは `参照先の名前:パス.md`・`skill:参照先の名前:名前` |
| `when.phase` | `plan`（計画を練るとき）か `apply`（変えるとき）。書かなければ両方 |
| `when.files` | 作る・変えるファイルの glob（書き方は `exclude` と同じ）。当たるファイルを作る・変えるときだけ効く |
| `when.change` | `create` / `update` / `delete` / `rename` の配列。そのファイルの変え方 |
| `when.tests` | `true` ならテストのファイル（`tests` の書き方）だけ、`false` ならテスト以外だけ |
| `when.terms` | 語の配列。強制せず、`show` の「関係すれば使う手順」に出すだけ |
| `must` | 既定 `true`。`false` なら強制せず、関係すれば使う（使ったものだけ計画に書く） |
| `check` | 当たるファイルを変えた回に、変えたあとの検査で動かすコマンド。手順を守ったかを終了コードで確かめる。`tool:` には付けられない |
| `asks` | 申告で確かめる項目（コマンドで確かめにくいもの）。手順の文書の `- [ ]` の行も同じに扱う |

`when` を書かなければいつも効く（前の版の `rules` と同じ）。`when.phase` だけなら前の版の `skills.plan` / `skills.apply`。
`when.files`・`change`・`tests` を書いた手順を、**ファイルに決められた手順**と呼ぶ。計画で作る・変えるファイルに当たると、
計画を練るときに読み込ませ、変えたあとに守ったかを確かめる（[下記](#ファイルに決められた手順)）。
コマンドで確かめられる手順は `check` に、確かめにくいものは `asks`（か手順の文書の `- [ ]`）に書く。両方書けば両方を求める。
文書が無い・見出しが無い・glob が何にも当たらない手順は求めず、`show` に「読めません」と出す。

**どのリポジトリの手順が効くか。** 自分のファイルには自分の `codd.json`、参照先のファイルには参照先に置いた `codd.json` の
`guides` が効く。手順を持つリポジトリに 1 回書けば、どのリポジトリの codd から変えても同じ手順に従う。呼び出し元は
`refs[].guides` で足せるが、参照先が決めた手順は外せない。`refs[].guides` の文書は、参照先にあれば参照先から、
無ければ呼び出し元から読む。`check` は手順を書いた `codd.json` のリポジトリで動く。計画や `.codd/apply.md` では、
参照先のスキルを `名前` とも `参照先の名前:名前` とも書ける。
たとえば実装を変えるときは `tdd`、設計書を変えるときは文書を書くスキル、のように側ごとに決められる。

**置くだけで効く手順。** `.agents/guides/*.md` の文書と `.agents/skills/*/SKILL.md` のスキルは、先頭に `codd:` を書くと
`codd.json` に書かなくても効く（参照先に codd を置いていなくても、参照先に置いた文書は効く）。

```markdown
---
name: migration
description: マイグレーションを足すときの手順
codd:
  files: ["db/migrations/*.sql"]
  change: [create]
  check: ["python3", "tools/check_migrations.py"]
---

# マイグレーションを足す

## 手順
1. 番号は既存の最大 + 1
2. 戻す SQL を `down/` に書く

## 確かめること
- [ ] 戻す SQL がある
- [ ] 本番のデータ量で、ロックが長くならない
```

`codd:` の下には `files`・`change`・`tests`・`phase`・`terms`・`must`・`check`・`asks` を 1 段で書く。
値は文字列・`true`/`false`・`[a, b]` の配列か、次の行から `- 値` を並べた配列で書く。
`files`・`terms`・`asks` は 1 つなら配列にしなくてよい。`files` は Copilot の `applyTo` と同じく、`"**/*.ts,**/*.tsx"` のように `,` で並べてもよい。
` #` から後ろは注釈になる。

`codd.py show` は、自分と参照先の手順を「いつも / 工程ごと / ファイルに決められた / 関係すれば使う」に分けて挙げる。
見出しで指した節が見つからない文書も `show` が知らせる。

**設定しなくても使うもの。** `CLAUDE.md`・`AGENTS.md`・`GEMINI.md`・`.github/copilot-instructions.md`・`CONTRIBUTING.md` は、
書かなくてもあれば守る決まりとして読む。リポジトリの `.agents/skills/` に置いたスキルも、設定しなくても使う。`show` が名前と説明を挙げ、
計画を練るときに関係するものを読み込んで使い、計画の「従う手順」には使ったものだけを書く。エージェントに登録されていない
スキルでも、`SKILL.md` を読んでその手順に従う。置き場所は `skill_dirs` で変えられる。
名前で指定したスキルは、`skill_dirs`・`.agents/skills`・`.kiro/skills`・`.github/skills`・`.claude/skills`・`.copilot/skills` から
探す（リポジトリ、利用者のホーム、参照先の順）。

#### 守る決まりを見つける

設計書のリポジトリにあるコーディングルールのような決まりは、`guides` に書いても、見つけさせてもよい。

- **書く:** `refs[].guides` に並べる（`{"name": "docs", "path": "../docs", "guides": [{"use": "docs/coding-rules.md"}]}`）。
  `guides` の `use` には glob も書ける（例: `docs/rules/**/*.md`）。`*` はフォルダをまたがず、`**/` はまたぐ。
  1 つのファイルにも当たらないものは、`show` と `rules` が知らせる
- **見つけさせる:** パスか最初の見出しに「ルール・規約・規則・規程・約束・作法・ガイドライン・コーディング」や
  rules・guideline・convention・coding・style-guide・standard・policy・contributing を含むマークダウンを、自分と参照先から探して候補にする。
  `CHANGELOG`・`HISTORY`・`LICENSE` で始まるファイルは候補にしない。
  自分の分は `scope` の中と、その上のフォルダ（ルートを含む）だけを探す。スキルの中のファイル（`SKILL.md` のあるフォルダの下）と、
  日付で始まるファイル（計画や記録）も候補にしない。
  `init.py` は初めて置いたときに、候補を `codd.json` の `guides`（参照先の分は `refs[].guides`）に `{"use": "パス"}` として書く。
  あとから増えた候補は `show` に「決まりの候補」として出て、計画のときに読まれる（確認では訊かない）。
  設定に書くなら次のとおり

```bash
python3 .statemachine/codd/codd.py rules                    # 守る決まりと、設定に無い候補
python3 .statemachine/codd/codd.py rules --write            # 候補をすべて codd.json の guides に書く
python3 .statemachine/codd/codd.py rules --write --only docs:docs/coding-rules.md
```

書いたあとで決まりでないとわかったものは、`codd.json` から手で消す。

### 画面のあるアプリ（webui-test と組む）

実装・テスト・設計書をそろえるには、動かして確かめる検査も要る。画面のあるアプリでは
[webui-test](../webui-test/README.md) の `webui-test check` を `check` にすると、変えるたびに次を確かめる。

- アプリをローカルで起動しての e2e テスト
- 前回と画面が変わったか（webui-test は仕様書を読まない）
- 確かめた振る舞い・ページの読み込み時間・`measure` で測った時間・画面を `results/webui-test-evidence.json` に残す

このマシンがそれを受け取り、変わった画面を貼っている文書の画像を差し替える
（[テストで得たものを文書に写す](#テストで得たものを文書に写す)）。

単体テスト・API テストなどは webui-test ではなく `test` に書く。

```bash
python3 tools/codd-agent/init.py ~/work/my-app --side impl --ref docs=../my-app-docs \
  --test "npm test" --check "webui-test check" --evidence "results/webui-test-evidence.json"
```

`check` と `evidence` は自分で設定する。ほかの道具の設定ファイルや出力先は、自動では探さない。
`--evidence` は繰り返して指定でき、パス・glob は対象リポジトリのルートからの相対。
webui-test の保存先を変えたら、使うプロジェクトで codd-agent の `evidence` も合わせる。
前の版が自動で見つけて書いた `check` も残るので、要らなければ `--check ""` で消す。

- e2e のケースファイルに `# coherence: doc=docs:docs/login.md` のように仕様書を書いておくと、仕様書を変える計画は
  ケースファイルも扱わないと通らない（[パスのつながり](#パスのつながり)。任意。webui-test はこの注記を読まない）

#### 設計書側から画像を作る

設計書側の `check` に撮影コマンドを設定すると、design 側からも画像を作れる。
次の例では、実装側が `~/work/my-app`、設計書側が `~/work/my-app-docs` にある。

```bash
webui-test init ~/work/my-app --base-url http://localhost:3000 --serve "npm start"
python3 tools/codd-agent/init.py ~/work/my-app-docs --side design --ref app=../my-app \
  --check "webui-test capture docs/screens.yaml --config ../my-app/webui-test.config.yaml --out docs/images"
```

実装側に設定がすでにあれば `webui-test init` は要らない。`webui-test init` は既存の設定を上書きしない。
設計書側の `docs/screens.yaml` に、撮影する画面への操作と画像名を書く。

```yaml
suite: 仕様書の画像
viewport: { width: 1280, height: 800 }
cases:
  - id: S-01
    title: ログイン画面
    steps:
      - goto: /login
      - screenshot: { name: login-form, target: { css: main } }
```

この例は `docs/images/login-form.png` を作る。`docs/login.md` から
`![ログイン画面](images/login-form.png)` で参照する。
初めて撮るときは、撮影の YAML・作る画像・画像を貼る文書を計画に挙げ、変える段（apply）で撮影してから文書に貼る。
撮り直す画像を計画に挙げたときも、同じ手順で進める。撮影は設計書側のルートで実行する。

```bash
webui-test capture docs/screens.yaml --config ../my-app/webui-test.config.yaml --out docs/images
```

変えたあとの検査（`verify-apply`）でも同じ `check` を実行するので、撮影に失敗すれば検査は通らない。

`test` と `check` が作り直したファイル（撮り直した画像・結果のファイル）は `.codd/generated.json` に控え、
中身がそのままなら「変えたファイル」に数えない。そのため検査を通し直しても、作り直した画像で「計画に無いファイル」として
止まることはない。エージェントが同じファイルを手で変えたら、その変更は数える。
逆に、計画で「撮り直す」と挙げた画像（`.png`・`.jpg`・`.svg` など）は、画面が変わらず中身が同じままでも、
変え残しとはみなさない。終わりの報告に「撮り直しても同じ」と出る。

参照先の実装を読むだけのときは、その参照先の `check` は実行されない。そのため撮影のコマンドは設計書側の `check` に設定する。
`capture` は画像を作るだけで、画像を比べるための結果ファイルは作らない。
結果ファイル（`evidence`）を使った画像の差し替えは、これまでどおり実装側の `webui-test check` で使える。

codd-agent は外部のコマンドを実行するだけで、撮影の YAML や webui-test のコードは読み込まない。
webui-test も、設計書や codd-agent の設定を読まない。撮影の連携は使うプロジェクトの設定で組むので、
どちらの必須の依存も増えない。別の撮影ツールも、同じように `check` に設定できる。

#### テストで得たものを文書に写す

文書には、テストで確かめた振る舞いや測った時間を手で書かず、印で写す。値は `evidence` の結果ファイルから読む。

```markdown
ログイン画面の読み込み: <!-- evidence: login/S-01/load max=1000 -->812 ms<!-- /evidence -->

確かめた振る舞い:<!-- evidence: login/* -->
- ✓ ログイン画面 正しい ID でログインできる
<!-- /evidence -->
```

- `id` はテストの結果の項目（`codd.py evidence` で一覧）。`…/*` で前方一致の一覧になる。別のリポジトリのテストは `名前:id`
- 測った値（時間）は 2 割までの揺れを同じとみなす（`tolerance=0.1` のように書くと変えられる）。`max=` は目安で、超えたら落とす
- 振る舞いは ✓（通った）・✗（落ちた）として写す

文書に画面を貼るときは、結果ファイルの画像のパス（`items[].path`）にある画像をそのまま写す（以後、画面が変われば差し替わる）。

```bash
python3 .statemachine/codd/codd.py evidence                       # テストで得たものと、文書の印の様子
python3 .statemachine/codd/codd.py evidence --write docs:docs/perf.md
```

webui-test 以外のテストも、同じ形のファイルを書けば使える（`{"version": 1, "items": [{"id", "kind": "behavior"|"metric"|"image",
"title", "status", "value", "unit", "path", "sha256", "history", "file"}]}`。`file` はそのテストのファイル、`history` は画面の
これまでの版の sha256（今の版が先頭）。パスはリポジトリのルートからの相対）。

### graphify を使う

graphify が入っていれば（`graphify` が `auto`）、参照先を探すときと影響範囲を測るときにグラフを使う。
グラフはリポジトリが変わるたびに自動で作り直すので、手で更新しなくてよい。無ければ文字列検索だけで動く。
graphify スキルは、グラフの作成・更新・調査を直接頼んだときにエージェントが読む。仕組みは[下記](#graphify-の使い方)。

#### 文書の意味もグラフに入れる

`auto` のグラフに入るのは、コードと Markdown の見出し・参照だけ。`.txt`・`.yaml`・`.html`・PDF なども意味でつなぐには、
`graphify` に `semantic` を書く。

| `semantic` | 誰が文書を読むか |
|---|---|
| `session` | 今のセッションのエージェント（Kiro・Copilot など）。`codd.py graph` が文書を束に分けて出し、エージェントが読んで決まった形の JSON を書く |
| `ollama`・`openai`・`claude`・`gemini`・`bedrock` など | codd.py が graphify の `extract` で自分で済ませる。`model` で使うモデルを選べる。セッションには何も頼まない |

```json
"graphify": {"semantic": "session", "max_files": 100}
```

- 計画を練るときに、探す前に 1 回 `codd.py graph` を動かす（plan の手順に入っている）。自分と参照先のどちらも、変わった文書だけを読み直す
- 束は、`subagent` が `true` ならサブエージェント `codd-graph` に 1 束（20 ファイルまで）ずつ渡す。`false` なら codd が自分で読む（1 束 5 ファイルまで）
- 全部読み終えたら `codd.py graph --merge` でグラフに合わせる。足りない束や壊れた束は、その束だけ出し直す
- 1 回に読む文書は `max_files`（既定 100）まで。残りは次の回に回す
- 結果は参照先の分も自分の `.codd/graph/` に置く。参照先には何も書かない
- `session` のとき、この回にまだグラフを用意していなければ、計画の検査がそう伝えて止める

## 定期的に点検する（本流とは別）

本流は、依頼が触れた範囲しか見ない。codd を通らずに入った変更や、もとからある食い違いは残る。
`lint` はリポジトリ全体を読むだけで点検し、見つけたものを本流に渡す「やりたいこと」の 1 行にする。**何も直さない。**
直すときは、その 1 行をいつもどおりエージェント `codd` に伝える。

```bash
python3 .statemachine/codd/codd.py lint                       # 見つかれば終了コード 1
python3 .statemachine/codd/codd.py lint --since "8 days ago"  # 週に 1 回なら、前の回と少し重ねる
python3 .statemachine/codd/codd.py lint --no-test             # テストを動かさない
```

| 見るもの | 見つけるもの |
|---|---|
| 壊れたパス | 文書のリンクと注記（`coherence: doc=…`）が指すのに、どこにも無いファイル |
| 文書の書式 | 同じフォルダのほかの文書（2 つ以上）がみな持つ見出しを、欠いている文書（`README`・`index` などの索引は比べない） |
| テストの結果を写した文書 | 文書の印が今のテストの結果と違う・目安（`max=`）を超えた・写した振る舞いが落ちている |
| テスト | 両側の設定の `test` が落ちる（`check` はファイルを作り直すことがあるので動かさない） |
| codd を通らなかった変更 | codd を置いたあと、期間（既定は 30 日）のうちのコミットで、計画の記録（`.plans/`）に出てこないファイル。やりたいことはコミットごとに 1 行 |

結果は `.codd/lint.md` に残る。`…` の中のパスや、コードブロックの中のリンク・印は書き方の例として見ない。

**CI で週に 1 回動かす例**（GitHub Actions。見つかったら Issue を立てる）

```yaml
on:
  schedule: [{cron: "0 0 * * 1"}]
  workflow_dispatch:
jobs:
  lint:
    runs-on: ubuntu-latest
    permissions: {contents: read, issues: write}
    steps:
      - uses: actions/checkout@v4
        with: {fetch-depth: 0}            # 「codd を通らなかった変更」は git の履歴から探す
      - run: python3 .statemachine/codd/codd.py lint --since "8 days ago" || echo found=1 >> "$GITHUB_ENV"
      - if: env.found == '1'
        run: gh issue create --title "codd の点検で食い違いが見つかりました" --body-file .codd/lint.md
        env: {GH_TOKEN: "${{ github.token }}"}
```

参照先が別のリポジトリなら、同じジョブでそれも `codd.json` の `refs` のパスへチェックアウトする。

### 意味のずれを見つける（サンプル）

`lint` は名前やパスの食い違いしか見ない。名前は合っているのに中身がずれている（コードは 2 を返すのに設計書は 1 と
書いている、順番や条件が違う）は、読んで比べないと分からない。`samples/drift/` は、それをモデルに判断させる
小さなワークフローのサンプル。これも何も直さず、ずれを本流に渡す「やりたいこと」の 1 行にする。

```
collect（比べる組を集める）─┬─ 候補あり ─→ judge（組ごとに判断する）─→ report（伝える）
                            └─ 候補なし ────────────────────────────→ report
```

1. **collect** — `lint` の「codd を通らなかった変更」から、変わった値・条件・見出しを選び、`explore`・`impact` で
   相手の側の同じことを述べている箇所を探して、`.codd/drift-candidates.md` に `パス:行 ⇔ パス:行` の組で書く（多くても 10 組）
2. **judge** — 組ごとに両方を読み、`ずれ` / `合っている` / `判断できない` を `.codd/drift.md` に書く。
   `ずれ` には本流に渡す「やりたいこと」を添える
3. **report** — まとめを伝える

候補と判断の形（指す行が実在するか、すべての組を判断したか、ずれに「やりたいこと」があるか）は、同じフォルダの
`check_drift.py` が検査する。置くときは、codd-agent を置いたリポジトリの `.statemachine/codd-drift/` へ写す。

```bash
cp -r tools/codd-agent/samples/drift <リポジトリ>/.statemachine/codd-drift
```

人の確認を待たないので、agent-app の定期実行で動かせる（入力は「いつからの変更を見るか」だけ。既定は 30 日）。
statemachine-use スキルのあるエージェントに「codd-drift を実行して」と頼んでもよい。

## 仕組み

ここから下は、検査が何をどう確かめるかの説明。使うだけなら読まなくてよい。設計の全体は
[設計書](../../docs/designs/codd-agent-design.md) にある。

### 何を確かめるか

| 段 | 確かめること | どう確かめるか |
|---|---|---|
| 入力 | 影響箇所を漏れなく見つけたか | 計画の名前（`…`）から、自分の呼び出し元（graphify `affected` と文字列検索）と、その名前に触れている参照先のファイル（文字列検索）を測り、計画が扱っていなければ落とす |
| 入力 | パスでつながったファイルを漏らしていないか | 変えるファイルとパスで指し合っている（[パスのつながり](#パスのつながり)）ほかの側のファイルを、計画が扱っていなければ落とす |
| 入力 | 参照先を読んだか | 参照先ごとに探したか（`explore`）。探して見つかったファイルを、根拠か「関係なし: 理由」として計画がすべて扱ったか |
| 入力 | 読んだものを根拠にしているか | 根拠のパス・行・見出し・名前が参照先に実在するか |
| 入力 | 響くテストを漏らしていないか | 変える名前が書かれているテスト、変えるファイルと名前が対になっているテスト、変えるファイルとパスでつながっているテストを測り、計画の「テストの変更案」が扱っていなければ落とす。新しく足す名前は、足すテストを計画させる |
| 過程 | 決まりを守ったか | 決まりのファイル（`CLAUDE.md` など）を `codd.py rule` で読み込んだか（読み込んだあとに変わっていないか）。決まりのファイルと、変える文書の今の書式（見本）を、計画の「従う手順」にすべて挙げたか |
| 過程 | 決めたスキル・道具を使ったか | `guides`（と前の版の `skills`・`tools`）に書いたものを、計画の「従う手順」と `.codd/apply.md` にすべて挙げたか。ファイルに決められた手順は、当たったファイルごとに記録し、確かめることに答え、手順の `check` が通ったか |
| 出力 | 計画どおりに、最後まで変えたか | 計画に挙げたファイル（テストも）をすべて、それだけを変えたか。実際の差分から影響範囲と響くテストを測り直す。新しく足した名前を確かめるテストがあるか。`test` のテストと `check` の検査コマンド |
| 出力 | テストで得たものを文書に返したか | 変わった画面を貼っている文書の画像を差し替える（ハーネスがする）。文書の印（`<!-- evidence: id -->`）が今のテストの結果と合うか、目安（`max=`）を満たすか、写した振る舞いが通っているか |
| 出力 | 文書の書式を守ったか | 変えた文書が、計画のときの見出しの並び（新しい文書は同じフォルダの文書の見出しの並び）を保っているか |
| 出力 | 指す先が壊れていないか | 書き足したパスが実在するか、消したファイルを指したままのところが無いか |
| 出力 | 結果を正しく伝えたか | 終わりの報告を `codd.py report` が作る（モデルがまとめ直さない） |

スキル・道具を使ったかは、使った記録（何に使い、何を得たか）を求めることで確かめる。スクリプトからはエージェントの
道具の呼び出しそのものは見えないので、実際に動かして確かめたいものは `check` の検査コマンドに入れる。

### 計画の書き方

計画は `codd.py draft --name 名前` で置いたひな形に、見出しごとに書く。同じ回の練り直しでは、このファイルを直す。
GitHub Copilot などは 1 回の応答の長さに上限があり、長い計画を一度に書いたり貼ったりすると
「the response hit the length limit」で止まるため、全文を一度に書かせず、確認でも要約（`codd.py summary`）を見せる。

参照先が複数あるときは、根拠や参照先の変更案のパスを `名前:パス`（例: `api:hello.md`）で書く。
どれか 1 つの参照先にしか無いパスなら名前を省いてよい。

当てはまるものが無い見出しは「なし」と書く。ひな形のコメントのままにした見出しも「なし」と読む
（「やりたいこと」「自分の変更案」「テストの変更案」は書き忘れと区別するため、必ず書く）。

「影響範囲」と「テストの変更案」で変えないファイルは、`変更不要: 理由` と書く。書き方は 2 つで、計画の検査も
変えたあとの検査も同じに読む。

| 書き方 | 例 |
|---|---|
| パスが先 | `- src/use.py, src/view.py — 変更不要: 表示は変わらない` |
| 変更不要が先 | `- 変更不要: src/use.py, src/view.py — 表示は変わらない` |

対象は項目の先頭に並べたパスだけで、理由の中に書いたパスは対象にしない。
新しいファイルを足すだけで響くファイルが無いときは、影響範囲を `- 変更不要: 理由` と理由だけで書く（測って見つかったファイルは、別に「未判断」として求める）。
理由の無い「変更不要」や、「直さない」「対応不要」「影響なし」などほかの言い回しは、計画の検査が書き直させる
（変えたあとの検査が変更不要と読めず、直していないファイルとして落ちるため）。

利用者が読む計画書・要約・終了時の結果には、変更不要の項目を載せない。
計画の検査（`verify-plan`）が通ると、計画書から説明のコメントと変更不要の項目を除き、検査に必要な判断だけを
`.codd/plan-check.json` に控える。検査は、控えた判断を使って、対象のパスと理由をこれまでどおり確かめる。
控えた判断も計画の検査を通った印に含めるので、承認のあとに書き換えると、変えたあとの検査で止まる。

### 計画の検査で確かめること

- 前提・制約・その他・ずれの各項目に、参照先に実在するファイルのパスが根拠として付いているか。
  `パス:行`・`パス:行-行`・`パス#見出し` で箇所まで指したときは、その行や見出しが実在するか
- 前提・制約・その他で `…` に囲んだ名前が、根拠のファイルに書かれているか（読んでいないことを書かせない）
- 決まりのファイルと、設定したスキル・道具と、計画で作る・変えるファイルに決められた手順を、すべて「従う手順」に挙げたか（ファイルに決められた手順は `codd.py guide` で読み込んだかも）
- 決まりのファイルを `codd.py rule --all` で読み込んだか（パスを挙げるだけでは通らない。読み込んだあとに中身が変わったものは読み直す。
  練り直しで呼び直しても、この回で読み込み済みで変わっていないものは出し直さない）
- 参照先をすべて `codd.py explore` で探したか。文字列の一致で見つかったファイルを、根拠か参照先の変更案、または
  その他の「関係なし: 理由」として計画がすべて扱ったか（前提・制約・その他・ずれを全部「なし」にして読まずに済ませない）。
  見つかったファイルは `explore` が出す一致した行（`パス:行  その行`）で判断し、関係するものだけ前後を読む（全文は読まない）。
  関係しないものは `- 関係なし: パス:行, パス:行 — 理由` と 1 行にまとめてよい
- 探した・読んだ記録（`.codd/explore.json`・`rules-read.json`・`skills-read.json`・`guides-read.json`）は、終わりの報告（`report`）で消える。次の回に持ち越さない
- 自分の変更案の各項目に、自分のリポジトリのパス（まだ無い新しいファイルでもよい）と、変わる名前（`…`）があるか
- 計画の名前で測った自分の影響範囲を、自分の変更案か影響範囲にすべて挙げたか
- 自分の変更で動く名前に触れている参照先のファイルを、根拠か参照先の変更案として扱ったか
- 自分の変更案のファイルとパスでつながっている参照先のファイルを、根拠か参照先の変更案として扱ったか。
  参照先の変更案のファイルとパスでつながっている自分のファイルを、自分の変更案か影響範囲に挙げたか
- ずれがあるときは参照先の変更案と影響範囲があり、影響範囲に自分のリポジトリに実在するパスがあるか
  （ずれが無くても、やりたいことが参照先も変えるなら参照先の変更案を書いてよい）
- 変える名前・変えるファイルが響くテストを、「テストの変更案」にすべて挙げたか。何かを変えるのに「なし」でないか
- 新しく足す名前（どの側にもまだ無い `…`）を確かめるテストを、名前を添えて「テストの変更案」に挙げたか
- 変える文書の今の書式（見本のパス）を「従う手順」に挙げたか
- 変えるファイルが `max_files` に収まっているか

測ったのに計画に無いファイル（影響範囲・響くテスト・探して見つかった参照先・つながっているファイル・書式の見本）は、
検査が計画の該当する見出しに「未判断」の行として書き足す（参照先のファイルには一致した行を添える）。エージェントは
測った結果のファイルを開かずに、その行を判断（直し方・`変更不要: 理由`・根拠・`関係なし: 理由`・守り方）に書き換える。
「未判断」が残っている計画は通らない。

検査は、形の指摘があっても測るところまで進め、指摘を 1 回で出し切る。出す指摘は短くし（1 行目は件数）、
全文は `.codd/problems.json` に残す。

### 段に分けて変える

計画で変えるファイルが `batch_files` より多いとき、変える段階（apply）を段に分ける。計画の検査が通ると、変えるファイルを
自分の変更案・参照先の変更案・影響範囲・テストの変更案の順に（同じ見出しの中はパスの順に）並べ、`batch_files` ずつに区切る。

ファイルに決められた手順があれば、効く手順の組が同じファイルどうしで段を作り、段ごとに出す手順を
1 組にする（混ざった段の最初に手順をまとめて出すと、後半のファイルで読み飛ばされやすい）。手順の無いファイルは空いている段に詰める。
こう分けると、ファイル数だけで分けたときより段が 3 つより多く増えるなら、ファイル数だけで分ける。
手順の無いファイルが `batch_files` の 4 分の 1 以下だけ余ったときは、新しい段を作らずに前の段へ入れる（11 ファイルを 10 と 1 に分けない）。
2 段目からは短い指示（`actions/apply-more.md`）で変えるので、段が増えても読み直す量は少ない。

1. エージェントは `codd.py batch` で今の段のファイルを確かめ、そのファイルだけを変える
2. 変えたあとの検査は、途中の段ではその段までに挙げたファイルをすべて変えたかだけを確かめる。通れば次の段へ進み、
   エージェントは次の段を変える。変え残しがあれば、その段のうちに止まる（訊かずにやり直す対象）
3. 最後の段のあと、全体を検査する（計画に無い変更・影響範囲の測り直し・響くテスト・`test` と `check`）

段はエージェントの 1 回の作業を小さくするためのもので、計画と確認は 1 回のまま。前の段で変えたファイルを、あとの段で
一緒に直してもよい。

### サブエージェントに渡す

`codd.json` の `subagent` を `true` にすると、変える段を codd が自分で変えずに、サブエージェント `codd-apply` に 1 段ずつ渡す。
段に分けないときも、変える作業をまるごと渡す。

- 段ごとに新しい文脈で変えるので、codd の会話には計画・確認・相談・報告と各段の短い結果だけが残る。大きな計画でも会話が
  長くなりにくく、後半の段で決まりから外れにくい。検査で落ちてやり直すときも、前の試行に引きずられない
- `codd-apply` は段ごとに手順の全文を読み直す（前の段で読んだものを覚えていないため）。そのぶん、読む量は増える
- 段は 1 つずつ順に渡す。同時には変えない（変えた記録を同じファイルに書くため）
- 確認・相談・検査は codd が受け持つ。`codd-apply` は利用者に訊かず、迷ったら変えずに `FAILED` を返す
- `codd-apply` を呼べない環境では、codd が自分で変える
- 文書の意味をグラフに入れる設定（`"semantic": "session"`）なら、文書を読む束もサブエージェント `codd-graph` に 1 束ずつ渡す。
  文書の全文が codd の会話に積まれない

`init.py` は `codd` と並べて `codd-apply`・`codd-graph` のカスタムエージェント（`.kiro/agents/codd-apply.json`・
`.github/agents/codd-apply.agent.md` など）を書く。モデルは書いていないので、GitHub Copilot では呼び出し元と同じモデルで動く。
kiro-cli がサブエージェントに呼び出し元のモデルを引き継ぐかは公式の説明に無いので、使う前に確かめる。

### 計画と違うことをしたとき

変える段で、計画に挙げたファイルを変えなくてよいと分かったり、挙げていないファイルも変える必要が出たりしたら、
計画は直さずに `.codd/apply.md` へ書く。計画から練り直さずに続けられる。

```markdown
## 計画との違い

- src/other.py — 変更不要: 段はもう正しかった
- src/notes.txt — 追加: 書き方を残した
- `disabled` — 関係なし: ズームのボタンの状態で、今回の印刷ボタンとは別物
```

理由付きの「変更不要」は、そのまま認める。「追加」は、計画のどこかで挙げたファイル（「変更不要」「関係なし」としたものも含む）なら
そのまま認め、挙げていないファイルだけを利用者に確かめる。認めると `codd.py accept` で控えて続ける。
変えたあとの検査が「直していない」と挙げたファイル（影響を受けるファイル・響くテスト）を直したときは、計画に無くても申告は要らない。
「関係なし」は、変えて使った名前が関係の無いファイルにも同じ綴りで出てくるときに、名前ごとかファイルごとに書く。
名前ごとに書くと、その名前だけで当たったファイル（参照先・自分・テスト）はまとめて済む。計画に書いた名前と、
パスでつながっているファイルには使えない（それは計画で判断するか、利用者に確かめる）。
関数の中の変数で、名前はそのままに中身だけ変えたもの（`disabled` など）は、はじめから影響を測る名前に数えない。
どれも報告と計画の記録に残る。

この回で消した名前（改名の元の名前・消したファイルの関数など）をほかの側がまだ書いていれば、変えたあとの検査が止める。
計画で変えるファイルなら、訊かずに直させる。計画で変えないファイルなら、変える段だけでは直せない（直すと計画に無い変更になる）
ので、同じものなら計画に足すか、別物として「関係なし」とするかを利用者に訊く。計画の根拠（前提・制約・ずれ）に挙げたファイルは
今回の名前のことを書いているので、「関係なし」では済ませない。「変更不要」としたファイルと「今回やらないこと」に挙げたファイルは、
残っていてよい。

### 変えたあとの検査で確かめること

- 計画の「自分の変更案」「参照先の変更案」に挙げたファイルを、すべて変えたか（途中で止まっていないか）
- 自分で変えたのが、計画の「自分の変更案」と「影響範囲」に挙げたファイルだけか
- 人の承認が要るファイル（`protect`）を変えたなら、確認で OK と答えた計画に挙げたものか（か、`accept` で認めたものか）
- 参照先で変えたのが、「参照先の変更案」に挙げた参照先の、挙げたファイルだけか
- 自分と参照先の実際の変更から測り直した影響範囲を、直したか「変更不要」としたか（[影響範囲を測る](#影響範囲を測る)）。
  名前を変えたときは、その名前に触れている参照先も扱ったか
- 変えたファイルとパスでつながっているほかの側のファイルを、扱ったか（自分のファイルなら直したか「変更不要」としたか）
- 変えたファイルに書き足したパスが、どこかの側に実在するか。消したファイルを、まだ指しているところが無いか
- この回で消した・改めた名前を、ほかの側がまだ書いていないか
- 変えるときのスキル・道具を設定していれば、`.codd/apply.md` に使った記録があるか
- 「テストの変更案」のテストをすべて変えたか。実際の変更から測り直した響くテストを、直したか「変更不要」としたか
- 変えた文書が、今の書式（見出しの並び）を保っているか
- `test` のテストと `check` の検査コマンド

計画より前から作業中だったファイルは、変えたものに数えない（計画の検査が通ったときの中身と比べる）。

### 影響範囲を測る

変更が自分のリポジトリのどこに響くか、自分の変更がどの参照先のファイルに触れるかは、モデルの申告ではなくスクリプトが測る。
自分も参照先も、文字列検索（識別子は語単位）と graphify のグラフで測る。グラフは自分と参照先の分を合わせ、
同じ名前の関数・クラスでつないで、設計書の見出しから実装の関数、そこからテスト、のようにリポジトリをまたいで辿る。

| いつ | 何から測るか | 通る条件 |
|---|---|---|
| 確認の前（計画の検査） | 計画の「自分の変更案」「参照先の変更案」「ずれ」で `…` に囲んだ名前 | 自分で測ったファイルがすべて自分の変更案か影響範囲に挙がっている（直さないなら「変更不要: 理由」） |
| 確認の前（計画の検査） | 「自分の変更案」で `…` に囲んだ名前 | その名前に触れている参照先のファイルを、計画が根拠か参照先の変更案として扱っている |
| 変えたあと | 自分と参照先の**実際の変更**（差分の定義・見出し・`…`）と、計画の名前 | 測ったファイルを直したか、計画で「変更不要」としたか |

グラフで拾ったものは、根拠の強さで 3 段に分ける。拾う範囲は広げ、検査で見せる量は強さで絞る。

| 段 | 何で拾ったか | 扱い |
|---|---|---|
| 明示 | 文字列の一致、コードの呼び出し・読み込み、文書に書いてあるつながり。変わる名前から 2 歩まで（参照先は 1 歩まで） | 計画が扱うまで通さない |
| 要判断 | LLM が文書から読み取ったつながりのうち、確からしさが高く（0.85 以上）、変わる名前から 1 歩のもの | 計画に変更案か「変更不要: 理由」（参照先は「関係なし: 理由」）を 1 行書く。黙って落とせない |
| 参考 | それより弱いもの、似ているだけのもの、2 歩目の推定 | 検査には出さず、測った結果のファイルにだけ残す |

- 辿るのは、計画に挙げたファイルの中で変わる名前のノードから。変えたあとの検査では、変えた文書の行に重なる見出しからも辿る。
  同じ綴りがほかのファイルにあっても、そこからは辿らない
- 推定のつながりは最後の 1 歩にだけ使う。推定から推定へは広げない
- つながりの多いノード（README・用語集・共通の関数など）は候補にするが、その先へは辿らない
- 「変更不要」「関係なし」とした要判断のファイルは、そのファイルが変わるまで次の計画では参考に下げる（`.codd/graph/dismissed.json` に控える）

変えたあとに測り直すのは、計画より広く変えた場合（関数の名前まで変えた、など）にもその影響を取りこぼさないため。
測った結果は `.codd/impact.md`・`.codd/ref-impact.md`（確認の前）と `.codd/impact-after.md`（変えたあと）に残る。

### パスのつながり

名前が一致しなくても、ファイル同士がパスで指し合っていれば、片方を変えるともう片方に響く。次の書き方を「つながり」として拾う。

- どのファイルにも書ける注記: `coherence: doc=docs/api.md`（`code=`・`test=` も同じ）。コードならコメントに書く
- 文書（`.md`・`.rst`・`.adoc`・`.txt`）の中の、`…` で囲んだパス（`src/app.py`）とリンク（`[説明](../src/app.py)`）。
  文書では、コードブロックの中と `…` の中の注記は書き方の例として拾わない（地の文か `<!-- … -->` に書く）

パスはリポジトリのルートから（リンクは文書のフォルダからも）探し、書いた側のリポジトリに無ければほかの側で探す。
参照先が複数あるときは `名前:パス` で指せる。

| いつ | 何を確かめるか |
|---|---|
| 確認の前（計画の検査） | 自分の変更案のファイルとつながっている参照先のファイルを、計画が根拠か参照先の変更案として扱っているか。参照先の変更案のファイルとつながっている自分のファイルを、自分の変更案か影響範囲に挙げたか |
| 変えたあと | 変えたファイルとつながっているほかの側のファイルを扱ったか。書き足したパスが実在するか（`…` で囲んだパスは、実在するフォルダで始まるときだけ確かめる）。消したファイルを指したままのところが無いか |
| 終わりの報告 | 自分の変えたファイルのうち、参照先とつながっていないものを知らせる（落とさない） |

結果は `.codd/trace.md`（確認の前）と `.codd/trace-after.md`（変えたあと）に残る。

### テストもコード・仕様書と同じに扱う

テストケースとテストコードは、コード・仕様書と同じく整合を取る成果物として扱う。単体テストも、コードを動かす
API テスト・シナリオテストも、画面の e2e のケースも同列で、計画の「テストの変更案」に足す・直すものを挙げる。

| いつ | 何を確かめるか |
|---|---|
| 確認の前（計画の検査） | 響くテストを自分と参照先の両方で測る（`.codd/tests.md`。拾い方は下の表）。計画に無ければ「未判断」として書き足す（参照先のテストも、根拠ではなく「テストの変更案」に入る）。何かを変えるのに「なし」は認めない（要らないなら `- 変更不要: 理由`）。変更案で新しく足す名前（どの側にもまだ無い `…`）は、今あるテストに当たらないので、足すテストを名前を添えて挙げさせる（要らないなら `` - `名前` — 変更不要: 理由 ``） |
| 変えたあと | 挙げたテストをすべて変えたか。実際の変更から響くテストを測り直し（`.codd/tests-after.md`）、直していないテストがあれば落とす。新しく足した関数・型・文書の見出しが、どのテストにも出てこず計画も扱っていなければ落とす（見出しは、その文書をパスで指すテストをこの回に変えていればよい）。`test` のテストを動かす |

響くテストの拾い方は、テストの道具の書き方に頼らない。e2e のケースのようにコードの名前が出てこないテストも、
文字列とファイル名で拾う。

| 拾い方 | 何が書かれていれば響くとみなすか |
|---|---|
| 名前 | 変える名前（計画の `…`、差分の定義や見出し） |
| 文字列 | 変えたコードの文字列（画面の文言・URL・メッセージなど、差分の引用符の中。変えたあとだけ） |
| ファイル名 | 変えるファイルと同じ語幹（`src/app.py` と `tests/test_app.py`、`src/pages/Login.tsx` と `tests/e2e/login.yaml`） |
| つながり | 変えるファイルを指すパス（`coherence: code=…`・`doc=…` の注記や、文書が挙げているテストのファイル） |

計画の段階では文字列が分からないので、画面の文言や URL を変えるときは、計画にその文字列を `…` で囲んで書く。

### テストで得たものを実装と文書に活かす

テストは合否のほかに、確かめた振る舞い・測った時間・前回と比べた画面を残す。これを `evidence` のファイル
（[webui-test](../webui-test/README.md) は `results/webui-test-evidence.json` に書く）から読み、実装と文書に返す。
テストの側は文書を知らない。文書への影響を測って直すのはこのマシンである。

**画面**: 文書のリポジトリにある画像（`.png`）を sha256 で引き、テストの画面のこれまでの版と同じ画像を見つける。
前の版と同じ画像は、変えたあとの検査で今の画面に差し替え、どの文書が貼っているかを報告する。差し替えはハーネスの変更なので、
計画に挙げなくてよく、「計画に無い変更」にも数えない。テストで撮らなくなった画面を貼っている画像は知らせる。

**振る舞い・時間**: 文書の印（[テストで得たものを文書に写す](#テストで得たものを文書に写す)）で写した値を確かめる。

| いつ | 何をするか |
|---|---|
| 計画を練るとき | 計画に関係するテストの結果と、響くテストの画面を貼っている文書の画像を `.codd/evidence.md` に出す。響くテストの結果を印で写している文書が計画に無ければ落とす |
| 変えるとき | テストを動かしてから `codd.py evidence --write 文書のパス` で印を写し直す |
| 変えたあと | 変わった画面を貼っている文書の画像を差し替える。印が今の結果と合うか、目安を満たすか、写した振る舞いが通っているかを確かめる |
| 終わりの報告 | 差し替えた画像と、それを貼っている文書。計画のときと比べて変わった時間・画面・振る舞いの合否 |

### 文書の書式を決まりとして守る

文書の今の書式は、コードで言う決まりにあたる。変える文書は今の見出しの並び・表の形・言い回しを、新しく足す文書は
同じフォルダの文書（`README` などの索引を除く）がそろって持つ見出しの並びを見本として守る。

| いつ | 何を確かめるか |
|---|---|
| 確認の前（計画の検査） | 変える文書ごとに見本と見出しの並びを測り（`.codd/formats.md`）、「従う手順」に見本のパスと守り方が無ければ落とす |
| 変えたあと | 変えた文書が、測った見出しの並びを順に保っているか。見出しを変える・消すときは、計画に `` `## 見出し` `` と書いておく |

### スキルと手順を読み込ませる

エージェントが自分でスキルを選ぶのを待たない（kiro-cli などはスキルを自動で選ばないことが多い）。スキルは
`codd.py skill 名前` で読み込ませ、読み込んだことを `.codd/skills-read.json` に控える。計画の「従う手順」や
`.codd/apply.md` に使ったと書いたスキル（「使わない」と書いたものを除く）を、その段で読み込んでいなければ検査で落ちる。

```bash
python3 .statemachine/codd/codd.py skill tdd                # SKILL.md を出して読み込む
python3 .statemachine/codd/codd.py skill docs:doc-writer    # 参照先のスキル
```

変えるときに使うスキルは、`batch` が段の最初にその手順を出して読み込ませる。参照先を変えるときは、参照先に置いた `codd.json` が
決めた変えるときのスキルに、`refs[].skills`（と `refs[].guides`）で足したものを使う。
`.codd/apply.md` には `` - `名前` — 変えたファイル: 何をしたか `` の形で書く。変えたファイルを挙げていないと、検査は
スキルの手順と実際の差分を並べた `.codd/skill-review.md` を作って止める。スキルを読み直して記録を足すだけでは、手順が変更に
反映されない。手順と差分を見比べ、合わない箇所を直してから記録を書く。

#### ファイルに決められた手順

ファイルに決められた手順（`when.files`・`change`・`tests` を書いたもの）は、次のように必ず踏ませる。

| いつ | どうなるか |
|---|---|
| 計画を練るとき | 計画で作る・変えるファイルに当たる手順を `codd.py guide 名前かパス` で読み込み、「従う手順」に（読み込んだときと同じ名前かパスで）挙げるまで計画の検査を通さない |
| 変える前 | 段（[段に分けて変える](#段に分けて変える)）を手順の組ごとに分け、`batch` がその段に効く手順と、どのファイルに効くか、確かめることを出す |
| 変えたあと | 実際に変えたファイル（計画に無く足したものも）に当たる手順ごとに、`.codd/apply.md` のその手順の行に当たったファイルがすべて挙がっているか、確かめることに 1 項目ずつ答えたか（`- [x] 項目 — 根拠` か `- 該当なし: 項目 — 理由`）、`check` が通ったかを確かめる |

`.codd/apply.md` では、手順の行の下に字下げして、ファイルと答えを 1 行ずつ書いてもよい。
`change` が `delete`・`rename` だけの手順は、変える前には当たるか決まらないので、`batch` が「消す・名前を変えるときだけ効く」と
添えて出す。変えたあとは実際の変え方で確かめる（git にまだ足していない新しいファイルへの名前の変更も見分ける）。

### エージェントの応答と待ち方

codd は始めるときに `codd.py skill caveman` を読み、caveman の full で短く応答する。利用者が解除すれば、それに従う。
短く応答しても、コード・計画書の書式と、確認に必要な情報・検査結果は保つ。
graphify スキルは、グラフの作成・更新・調査を直接頼まれたときに `codd.py skill graphify` で読む。
ふだんの `explore` や影響範囲を測るときは、codd.py の自動更新を使う。

長いコマンドを待つときは、完了の通知か終了まで待つ機能を優先して使う。非同期の結果を待つ必要があるときは、
最初は 30 秒、まだ続いていればその後は 60 秒の間隔をあけるよう、エージェントの指示と plan / apply のアクションに指定している。
待っている間は、変化の無い報告や同じ途中ログを繰り返し出さず、終了コードを受け取ってから次へ進む。実行中の検査は重ねて起動しない。
`ReadFile` で `*.out`・`*.log` を読むときも同じ間隔を守り、待っている間にログの全文を読み直さない。
これはエージェントへの指示で、IDE が内部で問い合わせる周期を変える設定ではない。

### graphify の使い方

graphify が入っていれば、探すたびに、リポジトリの今の中身（HEAD と作業中の変更）を前に控えた印と比べる。
変わっていれば `graphify update` でグラフを作り直してから引く。変わっていなければ前のグラフをそのまま使う。
変えたあとの検査は作り直さず、変える前のグラフを使う（変わる名前の呼び出し元は変える前のグラフで分かり、
足した名前は文字列検索が拾う。やり直すたびに全体を作り直して待たせない）。
グラフは自分の `.codd/graph/` に書くので、参照先には何も書かない。
更新・検索のどちらにも同じ `GRAPHIFY_OUT` を渡し、`manifest.json` などの作業ファイルも各グラフと同じフォルダに置く。

- 参照先を探すときは `graphify query` で関係するノード（見出し・関数・呼び出し元）をたどる
- 影響範囲・参照先の漏れ・響くテストは、自分と参照先のグラフを合わせて codd.py が辿る（[影響範囲を測る](#影響範囲を測る)）
- どれも文字列検索を並べて行うので、グラフに入らない文書やまだコミットしていないファイルも拾う
- 文書の意味を入れる設定なら、`update` でコードを作り直しても、LLM が読んだ文書のノードは残る。変えた文書だけを次の回に読み直す

### 作業ファイル

探した結果・検査の記録・変える前の写し・graphify のグラフは `<リポジトリ>/.codd/` に置く（`init.py` が `.gitignore` に足す）。
計画と判断の記録は `.plans/` に置く。どちらも、変えたファイルや探す対象には数えない。

## テスト

```bash
python -m unittest discover -s tools/codd-agent/tests
```

### シナリオを再生する

サンプルのリポジトリで最初から最後まで通したときの記録を、`tests/scenarios/` に自然文で置いている（サンプルの要点・頼むこと・
利用者の答え・期待）。エージェントに「`tests/scenarios/aws-orders.md` のシナリオを再生して」と頼むと、サンプルを作り直して
codd を回し、期待と違ったところを挙げる。手順やファイルの中身は固めないので、出力が少し違っても構わない。
