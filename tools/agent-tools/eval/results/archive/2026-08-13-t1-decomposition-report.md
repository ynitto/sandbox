# tier:basic の事前分解は効くか（2026-08-13・gemma4:e4b × aider）

柱3 資源効率 / C9・C10 — 仕事を足る最小のモデルへ流せるかを実測で決める。

## 問い

tier:basic の CLI（aider + ollama gemma4:e4b）でクラウド予算を節約したい。
定型タスクを**あらかじめ分解**しておけば、一発では通らない仕事が通るようになるか。

一発版 T1（実装 + テスト追加）は過去 0/9。ここが分解で上がるなら、agent-loop の
statemachine を定型業務の受け皿にする投資に意味がある。

## 測り方

`worker_eval.py` に多段セルを追加した。判定は全アーム共通の `check_t1`
（仕様 6 ケースの実挙動 + テストが存在して通ること）。

| アーム | 手順 | 分離した変数 |
|---|---|---|
| T1 | 1 回で実装 + テスト | 基準線 |
| T1seq | 実装 / テストの 2 手順。ゲートは記録のみ（`max_retries=0`） | 分解そのもの |
| T1gate | 同じ 2 手順 + 決定的ゲート + 再試行（実装 2 回・テスト 1 回まで） | 機械検証と再投入 |

比較の担保:

- 課題文は `T1_IMPL_GOAL` / `T1_TEST_GOAL` の 1 本を全アームが参照する。
- ゲートが返す不一致は課題文がすでに列挙している 6 例そのもの。仕様の機械化であって、
  一発版に無い情報を多段版へ足してはいない。
- 1 回の呼び出しの argv は `engine.headless_cmd("aider", ...)`（本番の正典ビルダー）。
  手順制御だけがハーネス側の模擬——測っているのは分解とゲートの効果であって、
  statemachine 実装の出来ではない。

## 結果

| アーム | 受入 | 呼び出し | 壁時計 中央値 |
|---|---:|---:|---:|
| T1（一発） | 1/3 | 3 | 446s |
| T1seq（分解のみ） | **0/3** | 6 | 237s |
| T1gate（分解 + ゲート） | **3/3** | 12 | 952s |

別セッションのスモーク 1 本を含めると T1gate は 4/4。過去の T1 は 0/9 なので、
一発版は通算 1/12。

**分解だけでは上がらない。下がる。** T1seq の 3 本はすべて実装ステップで、
しかも**まったく同じ**壊れ方をした:

```
BAD [(1048576, '1024.0 KiB', '1.0 MiB'), (1073741824, '1048576.0 KiB', '1.0 GiB')]
```

KiB で止まって MiB / GiB へ繰り上がらない。これは実装ステップの初回 7/7（T1seq 3 +
T1gate 3 + スモーク 1）で再現した。ばらつきではなく、このモデルの決定的な癖である。
課題文には `human_bytes(1048576)=='1.0 MiB'` と書いてあるので、**散文の仕様例は
オラクルとして機能していない**。

**ゲートを足すと直る。** 機械が測った不一致を課題文に足して同じ手順をやり直すと、
実装は 4/4 で 2 回目に通った。テストステップも初回 7/7 で落ち、再試行 4/4 で通った。

## 検査は要る。診断の中身は速度にしか効かない

「機械が測った値を見せたから直った」のか「もう一度やらせたから直った」のかを、
実装ステップだけの対照 2 本で分けた。再試行の回数は同じ 1 回で、渡す材料だけが違う。

| アーム | 再試行時に渡すもの | 受入 | 再試行の壁時計 中央値 |
|---|---|---:|---:|
| T1impl_blind | 「仕様を満たしていない。直すこと」だけ | 3/3 | 148s |
| T1impl_diag | 測った不一致（`BAD [...]`） | 3/3 | 107s |

**受入は同じ。診断を渡すと再試行が 28% 速い。** 測った値があると直行し、無いと
モデルが自分で不一致を探し直すぶん遅くなる。

初回の失敗はここでも 6/6。実装ステップの初回失敗は全実行を通算して **13/13** になった。

ここから言えること——効いているのは **(a) ハーネスが決定的に失敗を検知したこと** と
**(b) 再投入したこと** の 2 つで、診断文の中身ではない。ただし「検査を省いて常に 1 回
やり直す」には倒せない。停止条件が無くなり、既に正しい成果物にも 2 倍払い、
やり直しで壊す危険が残り、done の根拠が自己申告へ戻る。**検査は要る。返す値は
真偽で足りる。** 診断の受け渡しは速度の最適化であって前提条件ではない。

この結論は 1 課題・1 種類のバグ・各 n=3 のもの。より難しいバグでは診断の中身が
受入そのものを分ける可能性が高く、「中身は要らない」とまでは言えない。

## 費用

T1gate は中央値 952s・4 呼び出し。一発版 446s・1 呼び出しの 2.1 倍の壁時計。
ローカル GPU なのでクラウド予算は増えない。節約したいのはクレジットであって
壁時計ではないから、この交換は成立する。ただし「1 タスク 15 分」はそれ自体の
天井なので、対象は本当に繰り返す定型に絞る。

## 現行 statemachine への転用可否

**そのままでは転用できない。** ここで効いたゲートが agent-loop の statemachine に無い。

- `condition_rule` が見るのは `last_output` と `output_key` の値だけで、どちらも
  モデルが書いたテキスト（statemachine-use の `next_state.py` `_build_ctx`）。
- `output_validator` はその 1 行目の**書式**を見るだけ。「PASS」と書くのはモデル自身。
- ハーネスが決定的に見ているのは受入条件のパスについて「実在する / この実行で触れた /
  実際に変わった」の 3 点（`toolloop.py` `acceptance_evidence_errors`）。
  ファイルが在るかは見るが、**中身が仕様どおり動くかは見ていない**。

つまり現行の遷移は決定的だが、遷移の**材料**が自己申告である。今回 7/7 で壊れた実装は
ファイルとしては実在し、この実行で作られ、変更もされている——機械層は全部通す。

## 結論

採るべきは「定型タスクの事前分解」ではなく「**決定的な検査と再投入**」。
分解が要るのは、検査を差し込む場所を作るためであって、分解それ自体に効果は無い。

必要な実装は 1 つに絞れる。

**state に「ハーネスが実行する検査コマンド」を足し、その exit code を `condition_rule` の
コンテキストへ入れる。** モデルの自己申告を遷移材料から外す。落ちたら同じ state を
やり直す（既存の `max_retries` がそのまま使える）。statemachine-use のスキーマにも及ぶ。

検査の stdout を再試行の課題文へ足すのは、同じ受入を 28% 速く取るための最適化。
先に真偽だけで動かし、後から足してよい。

`tier` → workflow の決定的ルーティングは、これが動いてからでよい。定型タスクを
細かく割ること自体は目的ではない。**検査を置ける単位で割る**のが目的である。

## 未検証・限界

- 対象は humansize 1 課題のみ、各アーム n=3。他の定型で同じ形になるかは未測定。
  特に「初回が決定的に同じ壊れ方をする」性質は、この課題に固有かもしれない。
- 診断の中身が要らないのは、このバグが 1 回の指摘で直る種類だったため。
  難しいバグでは中身が受入そのものを分ける可能性が高い。
- 一発版 T1 が時々通る（1/3）のは aider の `--auto-test` が部分的なオラクルを
  供給しているため。T1seq の実装ステップにはこれが無く、その分だけ不利。
  分解アームの評価が辛めに出ている可能性はあるが、初回 13/13 の同一失敗が示すとおり
  向きは変わらない。
- 手順制御はハーネス側の模擬であって、agent-loop の statemachine 実装そのものは
  測っていない。上の実装を入れたあと、同じセルを実機経路で再測する必要がある。
