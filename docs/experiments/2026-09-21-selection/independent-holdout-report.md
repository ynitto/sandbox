# 独立適合判定: 固定 holdout 評価（2026-09-21）

候補を個別に評価する方式は、今回の6依頼では候補順を逆転しても結果が変わらなかった。一方、期待する実行先との一致は通常順・逆順とも4/6にとどまる。単純抽出の過剰なクラウド選択と、実装調査依頼で全候補が不適合になる問題が残る。これだけで選択品質が十分になったとは評価しない。

## 固定した条件

- 独立実装 `independent.py:evaluate` を使用。候補を見せず要求を判定し、1候補ずつ適合性を評価する。
- 適合確率 >= 0.6 かつ最良スコアとの差 <= 0.01 を候補に残す。同等候補は ID 昇順にしてから `audit_order` で費用等を比較する。0.01 は開発6件で選んだ仮パラメータであり、今回の holdout では変更していない。
- 未使用6依頼 × 通常順／逆順。期待先は事前の simple=local / complex=cloud。実タスクを実行して品質採点した評価ではない。
- 候補: cursor, codex, claude, ollama/gemma4:e4b。クラウドの具体モデルは未解決（空文字）、各候補の評価記録は未供給。これらを明示的に unknown として渡した。本番実装とは判断材料の構造が異なる。本番でも新しい能力実測は追加していない。
- judge の返答60件はすべて `logprobs`。`text` の確定ラベルを確率として採用する方法は使っていない。

期待先一致は8/12（通常順4/6・逆順4/6）。選択された候補IDの順序一致は5/5、判定保留も含む結果一致は6/6。保留は両順のh4、計2/12で、期待先一致の分母から除外していない。実行時エラーは再実行では0/12。要件判定 routine/demanding は12/12で事前群分けと一致した。

h3のJSON抽出は、通常順で Ollama=0.9804、Claude=0.9938。差0.0134のため同等幅0.01から外れた。この僅差が実品質差を示す根拠はなく、過剰選択の可能性がある。h4は全候補が0.6未満で、最大でもOllama=0.1984。未知モデル・実測なしの情報が不足していた可能性はあるが、原因をこの結果だけで断定できない。h5/h6でもOllamaのyes確率自体は0.9を超えており、0.6の最低閾値だけでは複雑な仕事を分離できていない。

## 残るラベル／表現依存（静的レビュー）

`judge.py:BOOLEAN_CRITERIA` は yes, no の固定順。`normalize_question` は boolean でこの順を使い、`build_prompt` は A=yes / B=no とする。FITは肯定形の「good capability match?」であり、肯定応答や先頭Aへの偏りは候補を個別評価しても残りうる。今回の逆転は候補の評価順だけで、yes/noの位置や質問の極性は逆転していない。要求判定のroutine/demandingの順も固定。したがって「候補順の影響が今回見られなかった」と「判断があらゆる表現に対して不偏」は区別する。

次の独立評価では、適合／不適合のchoice形式でラベル順を逆転した対と、肯定／否定極性の対を事前固定し、同じ候補の確率がどれだけ変わるかを見る。ブランドや既定モデル未解決の影響、実測証拠の有無も別要因として評価する。今回のholdoutを新しい閾値選びに使わない。

## 実行記録と制限

初回はサンドボックスがローカルOllama接続を拒否し12件すべて `JudgeError: Operation not permitted`。権限付きで同条件を再実行した。環境失敗の重複ログは整理時に削除し、件数と理由をこの段落に残した。失敗を隠した選別ではなく、初回は判定器まで届かなかった環境失敗である。初回も数えた総試行は24件、環境失敗12件、再実行判定12件である。

生データは `independent-holdout.jsonl`、入力は `independent-holdout-input.json`、再現スクリプトは `independent-holdout.py`。スクリプトは既存結果の上書きを拒否する。少数例・各順1回、同一judge、同一候補集合での比較であり、確率は校正された作業成功率ではない。選択先の実タスクは一切実行していない。
