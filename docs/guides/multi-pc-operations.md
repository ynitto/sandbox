# 複数 PC 分担運用ガイド（agent-project + agent-dashboard）

> 対象構成: **1 PC = 1 常駐体**（`agent-project serve`）。その常駐体が host.yaml に宣言した
> プロジェクトを子として監督する。この PC を複数台並べ、1 つのプロジェクト（backlog）を
> 分担して進める。
>
> 1 台分の導入（インストール・host.yaml・常駐化・確認）は
> [セットアップガイド](single-resident-setup.md)にある。**本書は「台数を増やしたときに
> 何が起きるか・何を決めるか」だけ**を書く。
>
> 方針: 新しい同期機構は作らない。共有点は状態専用リポジトリ 1 つで、git は輸送手段、
> 真実はファイル。

## 1. 全体像

```
[状態専用リポジトリ (Gitea/GitLab)]  ← 唯一の共有点。force push 禁止・保護ブランチ
        ▲ fetch / push（常駐体だけが行う）
        │
 ┌──────┴──────────────┬──────────────────────┬─────────────────────┐
 │ PC-A                │ PC-B                 │ PC-C（見るだけでも可）
 │ WSL : serve         │ WSL : serve          │ WSL : serve
 │   ├ 子: proj-1      │   ├ 子: proj-1       │   （プロジェクト宣言なし
 │   └ 子: proj-2      │   └ 子: proj-3       │    ＝ワーカー構成）
 │ Win : dashboard     │ Win : dashboard      │ Win : dashboard
 └─────────────────────┴──────────────────────┴─────────────────────┘
```

- **常駐体は PC に 1 本**。プロジェクトの数だけ子プロセスが起き、親が生死・計画停止・
  隔離を面倒みる。プロジェクトごとに起動コマンドを並べるのではなく、host.yaml の
  `projects[]` に足せば増える。
- **git を触るのは常駐体だけ**。dashboard は状態をファイルで読み、操作は
  ファイルドロップ（`commands/*.json`・`inbox/*.json`・`needs/<id>.md` の追記）で渡す。
  backlog の status を直接書き換える経路は存在しない（`done` は検証だけが根拠）。
  → dashboard がいつ起動・終了しても、他 PC といつ競合しても、状態遷移の整合は壊れない。
- **タスクの取り合いは git の CAS**（fast-forward push の成否）で決着する。分担は
  「早い者勝ち＋自動割当（ベストエフォート）」で、均等性は保証しない。

## 2. 設計原則（この 5 つだけ守る）

1. **状態リポジトリへ書くのは各 PC の常駐体だけ**。人と dashboard の入力は「リモート優先で
   取り込まれる入力パス」（`commands/` `inbox/` `needs/` `policy.md` `charter.md` `rules.md`）
   に限定する。
2. **PC 固有の宣言は共有 yaml に書かない**。`node_id` / clone 先 `root` / `availability` /
   ローカルクローン `repos[]` は各 PC の `~/.agents/agent-project.host.yaml` に置く。
   置き場を間違えると起動時に**キー名付きで停止する**（設定 2 層の帰属検査）ので、
   「書いたのに効かない」にはならない。
3. **状態は WSL 側 ext4 に置く**。`/mnt/c`（DrvFS）は flock が不安定で、ロックと同期の
   前提が崩れる。dashboard からは `\\wsl.localhost\<distro>\...` 越しに読める。
4. **共有ブランチへの force push は全員禁止**（サーバ側の保護ブランチで強制推奨）。
   常駐体は force push しない（push 競合は fetch → 3-way merge → 再 push）ので、
   これを人が壊さないこと。
5. **状態は専用リポジトリ方式**（[移行手順](state-repo-migration.md)）。これが唯一の方式で、
   旧 worktree 方式のキーが残っていると起動時に移行手順を示して停止する。

## 3. 設定

### 3.1 各 PC の宣言 `~/.agents/agent-project.host.yaml`

台数を増やすときに触るのはほぼここだけ。書式と全項目は
[セットアップガイド §2](single-resident-setup.md) を見る。複数 PC で意味を持つのは次:

```yaml
schema_version: 1
node_id: pc-a                 # PC ごとに一意。タスクの `- node:` 割当と端末一覧の名義になる
projects:
  - name: myproj
    state_repo: git@gitlab.example.com:team/myproj-state.git
    root: /home/me/agents/myproj-state    # この PC での clone 先（無ければ自動 clone）
repos:                        # 手元の成果物クローン（検収差分・実行の高速化に使う）
  - url: git@gitlab.example.com:team/app.git
    local: /home/me/mirrors/app
availability:                 # この PC の稼働時間帯（他の PC には影響しない）
  timezone: Asia/Tokyo
  daily_stop: "23:00"
  drain_before_sec: 1800      # 停止 30 分前から新規の取り合いをやめる
  shutdown_grace_sec: 300
```

- `node_id` は**小文字へ正規化**される。`DESKTOP-A` と書いても名義は `desktop-a`。
  タスクへ `- node:` を書くときは `agent-project status` が表示する名義をそのまま使う
  （大文字で書くと、どの PC も拾わないまま ready で固まる）。
- `node_id` を省略するとホスト名から作る。**host.yaml を複数 PC へ配って回す運用**なら
  省略が便利だが、その場合 `projects[].root` は全 PC で同一パスに揃える規約とする。
- 名義を後から変えるときは[切替ガイド](node-id-cutover.md)の手順に従う（端末状態と板の
  名義が同時に変わるため、走行中に変えると 2 名義に割れる）。

### 3.2 共有設定 `agent-project.yaml`（状態リポジトリ直下・全 PC 同一）

**複数 PC 分担のために足す設定はほとんど無い。** 状態ルートに origin があり、他の PC の
生存が観測されたときだけ、取り合いの CAS 制御が自動で有効になる（設定キーは無い）。

```yaml
workdir: work
watch: true

# 調整したいときだけ（既定のままで動く）
controller_heartbeat_sec: 30
controller_lease_sec: 120
coordination_retries: 3

state_git_interval: 300        # fetch/push の最短間隔（秒）。反映を速めたければ短く
# default_node: pc-a           # `- node:` 未指定タスクの既定の担当。空だと「どの PC も拾える」
# bus: /abs/path/to/bus        # 実行層のバスを明示（複数 PC 構成では明示を推奨・§8）
```

ポイント:

- **二重実行を防ぐ本体は git の CAS**。ローカルのロックファイルは PC を跨いだ排他には
  ならない（同期対象外）ので、複数台構成ではこれが効く。
- **計画（charter 分解・triage・inbox 取り込み・自動割当）を行うのは常に 1 台だけ**。
  リースをハートビートで維持し、切れれば他の PC が自動で引き継ぐ。引き継ぎが起きても
  **実行中のタスクは止まらない**（計画の役だけが移る）。

## 4. 分担のしかた

### 4.1 実行の分担

- **割当なし（既定）**: ready なタスクはどの PC も拾える。CAS の早い者勝ちに加えて、
  計画役の PC が未割当タスクを生存中の PC へベストエフォートで配る（ready+doing の
  少ない PC を優先）。
- **明示割当**: タスクの `- node: pc-b` で特定の PC に固定する（重い GPU ジョブ等）。
  dashboard の revise、または人が backlog を編集して指定する。
- **どの PC にも拾わせたくない時間帯**がある PC は `availability` を宣言する（§5）。

### 4.2 分担の粒度 — 既定は「タスク単位」

CAS が分散するのは **backlog のタスク**で、取った PC がそのタスクの実行
（agent-flow のタスクグラフ）を**丸ごとローカルで完走**する。グラフ内の個々のステップが
PC 間に散らないのは**仕様**で、不具合ではない: 実行層のバスは「実行はローカルのまま、
状態の鏡だけを共有する」構成になっている（鏡の反映間隔は既定 300 秒なので、他の PC が
その実行を見る頃には結果が付いている）。

ステップ単位まで散らしたい場合は、コード変更ではなく**構成の変更**で行う:

| 方式 | 仕組み | 向き・不向き |
|---|---|---|
| フォージ委譲（`executor: gitlab`） | 各ステップをイシューへ委譲。どの PC の誰（人/エージェント）でも拾える | レビュー往復を挟む長期作業向き。粒度が粗くても安定 |
| 実行層の共有バス（全 PC が同じ `--git` リモートを指す） | 取り合いを含むバス全体を git で共有し、名前空間の取り合い＋決定的タイブレーク＋リースで PC 間排他が効く | ステップ粒度の真の分散。ただしバスへの push 頻度が高い |
| 委譲板（§4.4） | 「この仕事を誰か」を板へ公示し、能力の合う PC が入札・落札する | PC ごとに能力（導入済み CLI・手元のクローン）が違うときの割り振り |

まず「タスク単位のベストエフォートで足りるか」を判断し、足りるなら既定のままでよい。

### 4.3 人の判断の分担

判断待ちは `needs/<id>.md`（proposed / review / blocked）に集まり、全 PC の dashboard に
同じワークリストが見える。

- **見る人の割り当て**: dashboard の「担当」設定は表示用のサイドカーで、エンジンの動作には
  影響しない（壊れても実害が無い）。
- **回答**: 誰かの dashboard が feedback を書くと、`needs/` はリモート優先の入力パスなので
  同期で確実に届く。二人が同時に同じ判断へ回答すると後勝ちになるが、結果は `decisions/` に
  恒久記録されるので、記録を見て再指示すれば回復できる。
- **コメント併記**: 検収コメントは 1 コメント = 1 ファイルなので、複数 PC の同時書き込みが
  自然にマージされる（衝突しない）。

### 4.4 PC をまたいだ委譲（委譲板・任意）

host.yaml に `board:` を宣言した PC は、板へ自分の能力（タグ・使える CLI・手元のクローン・
稼働時間帯・同時実行の上限）を周期的に出し、公示された仕事へ入札できる。dashboard の
板画面から手動入札・落札・中止も投函できる（投函先は PC 単位の `~/.agents/commands/`）。

**プロジェクトを 1 つも宣言していない PC は、まだ板の仕事を実行できない**（落札しても
取り込み先が無い）。dashboard はその PC でボタンを理由付きで非活性にする。フル構成の PC
（`projects:` が 1 つ以上）同士なら板は今のまま使える。

## 5. 稼働時間帯と停止

`daily_stop` を宣言した PC は 3 段で止まる。

1. `daily_stop - drain_before_sec` — 新規の取り合いをやめ、計画役を他の PC へ譲る。
   走っているタスクはそのまま完走させる。
2. `daily_stop` — 停止時間帯に入る。
3. `daily_stop + shutdown_grace_sec` — 親が子を止める（時間帯が戻れば親がそのまま再開する）。

停止を決めるのは**常に親（常駐体）**で、計画停止は死亡回数に数えない（毎晩止めても隔離には
ならない）。夜間に PC が落ちても、返却されたタスクは他の PC が翌朝拾う。返却時に取り合いの
トークンが更新されるため、遅れて届いた旧結果は棄却される。

## 6. 何が起きたらどうなるか

| 事象 | システムの挙動（実装済み） | 人の対応 |
|---|---|---|
| push 競合 | fetch → 3-way merge → 再 push を指数バックオフで 5 回。パス別に決着（人の入力はリモート優先・機械の状態はローカル優先・journal は union merge）。**止まらない** | 不要 |
| push が恒久的に詰まる | 常駐体の状態に ahead/behind と直近エラーが出る。dashboard は同じものを表示する | 表示された競合ファイルを退避。最悪 clone し直す（状態リポジトリ＝バックアップそのもの） |
| 反映が遅い気がする | 既定 300 秒間隔で fetch/push する | dashboard の「今すぐ同期」を押す（`commands/heal` の投函） |
| PC がタスク実行中にクラッシュ | 他の PC からは端末状態の鮮度で死活を判定。失踪した doing は**自動では横取りせず** blocked にして判断待ちを立てる | 判断待ちで「再割当」を承認 → 他の PC が拾う。復帰した PC の旧結果はトークン不一致で棄却される |
| 計画役の PC が落ちる | リース失効（既定 120 秒）で他の PC が自動で引き継ぐ | 不要 |
| 同じタスクを 2 台が同時に取りに行く | CAS は片方しか成功しない。負けた側はリモートの正本へ巻き戻す | 不要 |
| 常駐体が落ちる | 常駐化（systemd unit / タスクスケジューラ）が上げ直す。子の残骸（孤児プロセス・古いロック・中断した rebase）は起動時に自動回収 | 繰り返すなら `agent-project doctor` |
| 子プロジェクトが連続クラッシュ | 隔離（`agent-project status` に `!`）して親は回り続ける | 原因を直して常駐体を再起動（自動解除は無い） |
| dashboard を閉じている | 影響なし（純粋な viewer + ファイルドロップ） | 不要 |
| 指示ドロップが不正／適用失敗 | `<name>.json.err` に理由、成功は `processed/` にレシート。dashboard がカード上に「送信 → 受理／失敗」を表示 | 理由を見て再操作 |
| 常駐体の停止中に dashboard から操作 | ドロップはファイルとして残り、再開時に取り込まれる | 急ぐならその PC で `agent-project serve` を起動 |
| 時計ずれ | リースと稼働時間帯は `clock_skew_tolerance_sec` を見込む | NTP を有効に |
| 状態の破損・誤操作 | 全変更が状態リポジトリの履歴に残る | `git log` で特定 → clone し直し or revert |

## 7. やってはいけないこと

- **backlog のタスクファイルの status を手や改造で直接書き換える**。第二の書き手は
  コミット競合と `done` 不変条件の破壊の源。操作は必ず `commands/` 経由。
- **共有ブランチへの force push / 履歴書き換え**。CAS と棄却判定の前提が崩れる。
- **共有 `agent-project.yaml` に PC 固有の宣言を書く**（起動時に停止するので事故には
  ならないが、全 PC が同時に止まる）。
- **状態を `/mnt/c` に置く**。flock と rename の原子性が保証されない。
- **1 つの状態リポジトリへ複数プロジェクトの子を向ける**。「1 状態リポジトリ = 1 backlog」を守る。
- **同じ PC で常駐体を 2 本上げる**（systemd とタスクスケジューラの両方を構成する等）。
  子が二重に起きてタスクを取り合う。常駐化の方式は 1 つだけ選び、host.yaml の `residency:`
  に宣言する。

## 8. 表示のずれ（実行に影響しないもの）

複数 PC 構成で「PC-A では消えたのに PC-B に残る」ように見える表示が 2 つある。どちらも
表示だけの問題で、実行や状態遷移には影響しない。

1. **実行アーカイブは PC ごとにローカル**。dashboard は実行のスナップショットを
   プロジェクト配下の `flow-archive/` に書き、これは同期対象外（PC 固有の表示キャッシュ）。
   PC-A で消した実行は PC-B では `archived` のまま残る（上限 100 件で自然に消える）。
   邪魔なら各 PC で消す。
2. **判断待ちの再生成**。エンジンは「status が proposed/blocked/review なのに判断待ちの
   ファイルが無い」ときに status を正として作り直す自己修復を持ち、同期側にも「ローカルに
   在ってリモートで消えているなら維持」の特例がある。回答済みの判断待ちが復活して見えたら、
   その PC の状態が古いまま止まっていないか（常駐体が動いているか・ahead/behind が
   増え続けていないか）をまず見る。回答は `decisions/` に残っているので、同じ回答を
   再投入すれば収束する。

実行層のバスは、明示していないと「ローカルのバス」と「同期された鏡」のどちらかを
新しさで自動選択する。複数 PC 構成では共有 yaml の `bus:` を明示して曖昧さを無くす。

## 9. 診断と復旧

```bash
# その PC の常駐体の状態（心拍・子の生死・隔離・直近エラー）
agent-project status
agent-project status --json

# 構成の検査（host.yaml の宣言・clone・origin・常駐化・端末名義まで）
agent-project doctor

# 状態リポジトリが詰まった/壊れた疑い → 作り直しが最速（状態リポジトリ＝バックアップ）
mv ~/agents/myproj-state ~/agents/myproj-state.bak
git clone git@gitea:team/myproj-state.git ~/agents/myproj-state
# 常駐体は次の監視 tick で子を起こし直す（止めていたなら agent-project serve）

# ある PC の doing が固まった → 判断待ちに出る「再割当」を dashboard で承認するだけ
```

`agent-project status` が「見つかりません」と言う場合は、その PC で `agent-project serve` が
起動していないか、起動直後で最初の tick をまだ書いていない。
