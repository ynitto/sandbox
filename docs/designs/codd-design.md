# codd 設計 — 参照先（実装⇔設計書）を読んで自分の変更を練るステートマシン

- 実装: `tools/codd/`（配布物は `machine/`、置き先では `.statemachine/codd/`）
- 使い方: [`tools/codd/README.md`](../../tools/codd/README.md)
- [codd-gate](./codd-gate-design.md) とは別物。codd-gate は 1 リポジトリ内の doc↔code↔test のドリフトを受け入れ前に**止める**
  決定的ゲート、codd はリポジトリをまたいで変更を**練って確かめてから入れる**ステートマシン

## 1. 目的と前提

実装と設計書が別リポジトリ（別フォルダ）にあり、片方だけが直されてもう片方と食い違う。
codd は、片方を変える前に**参照先を読み、自分の現状とのずれを見せ、了承を得てから変える**。
ずれを解消するために参照先を変える必要があれば、その変更案と自分への影響範囲まで見せたうえで両方を変える。

- 同じ定義を両リポジトリに置く（対称）。違いは `codd.json` の `side` と `refs`（と `skills`）だけ。
  実装で動かせば参照先は設計書、設計書で動かせば参照先は実装。参照先はいくつでも持てる
- 参照先のパスは手で設定する（自動発見しない）
- 計画を練るとき・変えるときに使うスキルを、リポジトリごとに設定できる（§5.3）
- **できるだけ単純なハーネスにする**。ステートは 4 つで、状態ファイルも往復の管理も持たない
- 参照先と自分の探索には graphify を使えるときは使い、グラフは自動で作り直す

## 2. 流れ

```
plan ─[check: verify-plan]→ confirm ─┬─ OK ─→ apply ─[check: verify-apply]→ done
  ↑                                  └─ NG ─┐
  └─────────────────────────────────────────┘
```

| ステート | すること | 成果物 | 成否の測り方 |
|---|---|---|---|
| plan | 参照先を探し（`explore`）、前提・制約・その他に分け、自分の現状とのずれを見て、自分の変更案を練る。ずれがあれば参照先の変更案と影響範囲を書く。どちらのリポジトリも変えない | `.codd/plan.md`（`write:`） | `check: verify-plan`（影響範囲の測定を含む） |
| confirm | 計画と測った影響範囲を見せ、利用者の答えを待つ | 答え（`OK` / `NG` と指摘） | `output_validator` |
| apply | 自分の変更案を適用し、参照先の変更案があれば参照先にも適用する。コミットはしない | 両リポジトリの作業中の変更 | `check: verify-apply`（影響範囲の測り直しを含む） |
| done | 変えたファイルを伝える | — | 終端 |

NG は plan へ戻り、次の plan は `{{answer}}`（confirm の答え。NG と利用者の指摘）を踏まえて練り直す。`answer` は `context:` で空に初期化してあり、初回は空になる。
分岐は `condition_rule`（`check_ok` と confirm の第 1 行）だけで決まり、LLM の YES/NO 評価は使わない。

### 2.1 確認は会話の中で待つ

confirm は、計画を見せて利用者の答えを待つアクションである。statemachine-use を会話の中で回す
（1 ステート 1 ターン）ときは、エージェントが計画を出してターンを終え、利用者の返事を受けて出力を確定する。
実行の途中で人の入力を受け取る仕組みを持たない無人のハーネス（agent-loop の headless 実行など）では、
このステートで止まる——このマシンは会話で使うことを前提にしている。

前の版は「終端で止まり、答えを入力に入れて次の実行で再開する」形だったが、そのために意図の状態・
答え待ち・反映待ちを `state.json` に持つ必要があり、ハーネスが重くなった。会話の中で待てば状態は要らない。

## 3. 前提・制約・その他とずれ

| 分類 | 定義 |
|---|---|
| 前提 | 参照先が「すでにそうなっている」と定めている事実・決定・振る舞い・用語 |
| 制約 | 参照先が「こうしなければならない / してはならない」と課している条件 |
| その他 | それ以外の関係する記述（決まっていないこと・任されていること・補足） |

**ずれ**は、このうち自分の現状（またはやりたいことを実現した姿）と食い違うもの。ずれがあれば、
それを解消するための参照先の変更案と、その変更を自分のリポジトリに適用したときの影響範囲を計画に書く。
ずれを残したまま進めたいなら、それはずれではなく「その他」として書く（検査がずれと変更案の対応を求めるため）。

分類は向きを問わない。実装から設計書を読めば「設計書が定める前提・制約」、設計書から実装を読めば
「実装が既に持っている振る舞い（前提）と、互換性・性能・依存などの条件（制約）」になる。

## 4. 影響範囲の測定

参照先を変えるときの「自分のリポジトリへの影響範囲」は、モデルが書いた一覧をそのまま信じず、**ハーネスが測って突き合わせる**。
利用者が OK と答える材料も、NG で練り直す材料も、測った結果である。

| いつ | 測る語 | 通る条件 | 記録 |
|---|---|---|---|
| verify-plan（confirm の前） | 計画の「参照先の変更案」「ずれ」で `…` に囲んだ名前。囲んだ名前が無ければ落とす | 測ったファイル ⊆ 計画の影響範囲に挙げたファイル | `.codd/impact.md` |
| verify-apply（apply の後） | 参照先の実際の差分（`git diff HEAD` の +/- 行の定義・見出し・`…`、新しいファイルの定義・見出し）＋ 計画の名前 | 測ったファイル ⊆ 自分で変えたファイル ∪ 計画で「変更不要」としたファイル | `.codd/impact-after.md` |

- 測り方は graphify `affected`（依存している呼び出し元・参照元を深さ 2 までたどる）と `git grep --untracked`。
  識別子は語単位（`-w`）で引き、`hello` で `helloWorld` を拾わない。1 回に測るファイルは 40 まで
- 変えたあとに測り直すのは、参照先を計画より広く変えたときの影響を取りこぼさないため。計画時の語だけでは、
  計画に書かれなかった変更の影響が見えない
- 「自分で変えたファイル」は、explore のときに控えた作業中ファイルの中身のハッシュと HEAD から比べる
  （apply の前から作業中だったファイルを「変えた」と数えない）
- 「変更不要」は計画の影響範囲の項目に `変更不要: 理由` と書いたもの。利用者の確認を経た計画にしか書けない
  （apply で足すときは利用者に確かめる）

## 5. 下請けスクリプト（`codd.py`、python3 + git のみ）

| コマンド | 仕事 |
|---|---|
| `show [--phase plan\|apply]` | この側・参照先の一覧と、段階ごとに使うスキルを `` `名前` スキル `` の形で示す（§5.3） |
| `explore --term 語… [--ref 名前…]` | 参照先（既定はすべて）を graphify `query` と `git grep` で引き、`.codd/explore.md` に候補を `名前:パス` でまとめる。あわせて自分とすべての参照先の印を `.codd/before.json` に控える |
| `impact --term 語…` | 自分のリポジトリを graphify `affected` と `git grep` で引く（手で調べる用。検査は §4 の測定を自分で呼ぶ） |
| `verify-plan` | 計画の形と根拠の検査（§6）と、影響範囲の測定（§4） |
| `verify-apply` | 変えたあとの検査（§7）と、影響範囲の測り直し（§4） |

### 5.1 graphify の自動更新

リポジトリの**印**（HEAD と、`git diff HEAD`、未追跡ファイルの名前と中身から作るハッシュ）をグラフの横に控え、
`explore` / `impact` のたびに今の印と比べる。違えば `graphify update . --force` で作り直し、同じなら前のグラフを使う。
コミットだけでなく作業中の変更でも作り直すので、apply の途中や計画の練り直しで古いグラフを引くことがない。
`--force` は、削除や改名でノードが減っても作り直した方を採るため（古いノードを残さない）。

グラフは `GRAPHIFY_OUT` で自分の `.codd/graph/own/` と `.codd/graph/ref-<名前>/` に書く。参照先の中に `graphify-out/` を作らない。
`update` は AST と見出しの抽出だけで LLM を使わない。設計書の意味的な抽出（`graphify extract`）は重いので自動では回さない。

常駐の監視（`graphify watch`）や git hook は入れない。使うときに確かめて作り直す方が、仕組みが少なく、
参照先に何も仕込まずに済む。

### 5.2 文字列検索を並べる

graphify の有無にかかわらず `git grep --untracked -F -i` を並べる。グラフに入らない文書と、
まだコミットしていないファイルを拾うため。graphify が無い・`graphify: off`・作り直しに失敗したときは、
文字列検索だけで同じ形の報告を出す。

### 5.3 使うスキル

`codd.json` の `skills` に、段階ごとに使うスキルの名前を並べる。

| 設定 | 使うとき |
|---|---|
| `skills.plan` | 計画を練るとき（このリポジトリの側で読む・練るときの作法） |
| `skills.apply` | このリポジトリを変えるとき |
| `refs[].skills` | その参照先を変えるとき。書かなければ、参照先に置いた `codd.json` の `skills.apply` |

参照先を変えるときに参照先自身の設定を使うのは、「そのリポジトリをどう変えるか」はそのリポジトリの持ち物だから
（実装なら `tdd`、設計書なら文書を書くスキル、のように側ごとに決まる）。参照先に codd を置いていないときや、
この側から変えるときだけ作法を変えたいときは `refs[].skills` で上書きする。

アクションは `codd.py show --phase …` を実行し、出てきたスキルを読み込んで従う。statemachine-use の実行ハーネスは
アクション本文の `` `名前` スキル `` 表記でスキルを読み込むが、スキルは設定で変わるので本文に固定では書けない。
`show` がその表記で出力し、会話で回すエージェントがそれを読んで読み込む（confirm が会話を前提にしているので、
無人の実行で自動読み込みを効かせる必要は無い）。

### 5.4 参照先が複数あるとき

- `refs` の各項目は `name` と `path`。`name` は英数字と `_` `.` `-`（省略時はフォルダ名）で、参照先ごとに違う
- 計画の根拠と参照先の変更案のパスは `名前:パス` で書く。パスだけのときは、実在する参照先が 1 つならそれに決め、
  複数にあれば曖昧として落とす（名前を書くよう求める）。参照先が 1 つなら従来どおりパスだけでよい
- 参照先の変更案は、まだ無いファイル（親のフォルダはある）も書ける——新しい文書を足す変更案のため
- 変更案に挙げた参照先の集まりが「変えてよい参照先」。§7 はこれと実際に変わった参照先を 1 つずつ突き合わせる
- 影響範囲の測り直しは、変わった参照先すべての差分から語を集めて 1 回測る（測る先は自分のリポジトリだけ）
- 以前の `ref_path`（参照先が 1 つだった頃の書き方）も読む。インストーラーは `--ref` を渡したときに `refs` へ置き換える

## 6. 計画の契約（`verify-plan`）

`templates/plan.md` の見出し（やりたいこと / 参照先の前提 / 参照先の制約 / 参照先のその他 / ずれ /
自分の変更案 / 参照先の変更案 / 影響範囲）がこの順にそろい、中身が空でないこと。加えて:

- 前提・制約・その他・ずれは「なし」か箇条書き。各項目に**参照先に実在するパス**がある（読んでいないものを書かせない）。
  参照先が複数あって決まらないパスは `名前:パス` を求める
- 参照先の変更案の各項目が、どの参照先を変えるかを決められる（§5.4）
- ずれがある ⇔ 参照先の変更案がある
- 参照先の変更案があれば影響範囲があり、影響範囲の各項目に**自分のリポジトリに実在するパス**がある
- 参照先の変更案に `…` で囲んだ名前があり、それで測った影響範囲（§4）をすべて挙げている

## 7. 変えたあとの契約（`verify-apply`）

`explore` のときに控えた印と今の印を比べ、どのリポジトリが変わったかを測る。

- 自分の変更案があるのに自分が変わっていない → 落とす
- 参照先の変更案に挙げた参照先が変わっていない → 落とす（参照先ごと）
- 参照先の変更案に無い参照先が変わった → 落とす（了承されていない変更を参照先に入れない。参照先ごと）
- 参照先が変わったら、実際の変更から影響範囲を測り直し、測ったファイルを直したか「変更不要」としたか（§4）
- 自分の `codd.json` の `check`、変わった参照先それぞれに置いた `codd.json` の `check` を実行する

落ちたら apply を 2 回まで再投入し、尽きたら `escalate`。

## 8. やらないこと

- コミット（変更の確認とコミットは利用者がそれぞれのリポジトリで行う）
- 参照先のパスの自動発見（`codd.json` を手で直す）
- 参照先どうしの関係（参照先 A を変えたときの参照先 B への影響）。測るのは自分への影響だけ
- 状態の持ち越し（確認は会話の中で待つ。やり直しは最初から）
- 常駐・監視（graphify のグラフも使うときに確かめて作り直す）
