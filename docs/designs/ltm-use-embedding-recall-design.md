# ltm-use 埋め込み recall — 用語を忘れた検索だけを救う

> **ステータス**: 実装済み（2026-08-23。`.github/skills/ltm-use/scripts/embeddings.py`・`recall_memory.py` v5.5.0）
> **作成日**: 2026-08-11 / 実装 2026-08-23
> **前提**: ltm-use v4 の TF-IDF ハイブリッド recall（`recall_memory.search_with_index`）が稼働中
> **測定**: [`tools/agent-tools/eval/retrieval_eval.py`](../../tools/agent-tools/eval/retrieval_eval.py)

## 背景と課題

**柱3 資源効率 / C9・C10** — 生成モデルの品質の袋小路と独立に、小さいモデル（埋め込み）で
取れる利得を、客観指標で確かめてから入れる。

[品質再点検 §6 案 d](../plans/2026-08-10-agent-ollama-quality-and-role-refit-proposals.md)
が「別モデル種別（埋め込み・リランカー）は検証に値する」と立てた案の、宛先を決める書。
9B の生成モデルに何をさせるかの議論とは独立に進められるのが利点だった。

現行の recall は 4 軸のハイブリッド（keyword 0.4 + TF-IDF 0.3 + meta 0.15 + context 0.15）で、
TF-IDF は日英混合の文字バイグラム。**語が重なる限りよく効く。**

## 何を測ったか

コーパスは ltm-use の実記憶 64 件 + リポジトリの設計書・計画書 146 件（妨害文書）。
同じ 20 問を 2 通りの訊き方で引いた——記憶の用語をそのまま使う `lexical` と、
用語を思い出せず意味だけで探す `paraphrase`。正解はパスで固定してある。

| 腕 | lexical hit@1 / hit@5 / MRR | paraphrase hit@1 / hit@5 / MRR | クエリ |
|---|---|---|---|
| TF-IDF 単独（現行） | 85% / 95% / 0.900 | 30% / 35% / 0.328 | 7 ms |
| bge-m3 単独 | 80% / 100% / 0.900 | 50% / 60% / 0.576 | 170 ms |
| RRF 併用（対等） | 90% / 100% / 0.950 | 40% / 40% / 0.420 | 180 ms |
| **段構え（下記）** | **90% / 100% / 0.950** | **50% / 60% / 0.576** | **22 ms** |

読み方は 3 つ。

- **現行が弱いのは「用語を忘れたとき」だけ。** lexical では hit@5 95% で、埋め込みを足す
  理由が無い。paraphrase では 35% まで落ち、正解が 120 位・196 位まで沈んで 1 位を妨害文書に
  取られる。
- **混ぜると壊れる。** 対等な RRF 併用は paraphrase を 60% → 40% にする。順位がほぼ雑音の腕を
  等しく混ぜると単独より悪くなる。重みを 5:1 まで振ると hit@5 は戻るが hit@1 が 30% へ落ち、
  MRR は単独（0.576）に届かない。**合成は採らない。**
- **小さいコーパスでは差が出ない。** 記憶 64 件だけだと TF-IDF が hit@1 95%・hit@5 100% で
  天井に張り付く。妨害文書と言い換えクエリを入れて初めて指標が働いた。**この設計を再評価
  するときも、必ず妨害文書を入れて測ること。**

## 設計 — 合成ではなく段構え

**TF-IDF が自信を持てないときだけ埋め込みへ落とす。** 合成しない。

```
recall(query)
  ├─ 現行の 4 軸ハイブリッドで採点
  ├─ 最上位の TF-IDF コサインが しきい値以上   → そのまま返す（7 ms・現行と完全に同じ）
  └─ しきい値未満                              → 埋め込みで採点し直して返す（+170 ms）
```

しきい値は掃引して決めた。**0.11**。

| しきい値 | lexical hit@5 | paraphrase hit@5 | 埋め込みの発火率 |
|---|---|---|---|
| 0（現行） | 95% | 35% | 0% |
| 0.07 | 95% | 60% | 50% |
| 0.09 | 95% | 60% | 52% |
| **0.11** | **100%** | **60%** | **60%** |
| 0.15 | 100% | 60% | 72% |
| ∞（埋め込み単独） | 100% | 60% | 100% |

0.11 で **lexical と paraphrase の両方が単独腕の最大値に届く**。0.15 以上へ上げても精度は
変わらず発火率だけ増える。境界の実測は「外れたクエリの TF-IDF 最上位は最大 0.090、
当たったクエリの中央は 0.14〜0.18」で、0.11 はこの谷にある。

**段構えを選ぶ理由は精度ではなく費用。** 埋め込み単独でも hit@5 は同じだが、全クエリに
170 ms と索引の維持が乗る。段構えなら**強い側の経路は 1 行も変わらない**——現行の recall が
自信を持って当てているケースに、新しい故障の余地を作らない。

## 索引

- **置き場**: `<memory_dir>/.memory-embeddings.json`（TF-IDF コーパス `.memory-corpus.json` の隣。
  命名は兄弟に揃えた）。本文のハッシュを鍵に持つので、記憶を書き換えれば古い行は補修対象になる。
- **規模**: 1024 次元。実測で 210 件の索引付けに 130 秒（約 0.6 秒/件）。記憶 64 件なら 40 秒。
  ファイルは数 MB で、RAM もほぼ食わない（モデル常駐 1.2 GB）。
- **作る契機**: `save_memory` の直後に 1 件だけ追加（0.6 秒）と、`build_index.py --embeddings`
  の補修パス（新規・本文が変わった行だけ埋め込む）。**recall では作らない**——検索が数十秒待つ
  設計にはしない。索引が無い間は recall は従来どおりで、最初の 1 回だけ人が作る（opt-in）。
- **索引が無い記憶**: 段構えが発火しても素通しする（その記憶は埋め込み側の候補から外れる）。
  黙って外すと「入れたのに効かない」になるので、補修が要る件数を `build_index` が出す。

## 壊れ方

| 状況 | 振る舞い |
|---|---|
| ollama が停止 / モデル未取得 | 埋め込み段を丸ごと飛ばし、現行の結果を返す。警告は 1 セッション 1 回 |
| 索引が古い（本文ハッシュ不一致） | その記憶だけ埋め込み候補から外し、補修対象として数える |
| 索引が無い（初回） | 現行と同じ挙動。`build_index` を促す |

**recall は決して失敗しない。** 埋め込みは上積みであって前提ではない。

## やらないこと

- **5 軸目として重み付き合成する。** 実測で害（60% → 40%）。混ぜるなら訊き方で振り分ける。
- **リランカー。** ollama に rerank の口が無く、生成モデルで代用すると 1 クエリが数十秒になる。
  段構えの上に載せる話で、いまは測っていない。
- **recall 時の索引構築。** 検索の待ち時間に索引の費用を混ぜない。
- **他エージェントの記憶ディレクトリへの拡張。** まず `$HOME/.copilot/memory/home` の 1 か所で
  効果を確かめる。

## 受け入れ基準

同じハーネスで測って、次の 2 つを同時に満たすこと。**片方だけでは入れない**——現行が強い
場面を壊してまで弱い場面を救う変更にしない。

- paraphrase の hit@5 が **55% 以上**（現行 35%）
- lexical の hit@5 が **95% を下回らない**（現行 95%・段構えの実測 100%）

```bash
python3 tools/agent-tools/eval/retrieval_eval.py --model bge-m3 --k 5
```

## 実装と受け入れの実測（2026-08-23）

設計どおり段構えで入れた。`recall_memory.search_with_index` は TF-IDF の最上位コサインを
見て、しきい値未満のときだけ `embeddings.query_scores` で採点し直す（合成なし・埋め込み段では
body の語一致ブーストも足さない）。契約テストは `tests/test_embedding_cascade.py`（ollama 不要）。

| 腕 | 空間 | lexical hit@1 / hit@5 / MRR | paraphrase hit@1 / hit@5 / MRR |
|---|---|---|---|
| TF-IDF 単独 | ハーネス（261 件・妨害込み） | 85% / 100% / 0.889 | 30% / 35% / 0.325 |
| **段構え 0.11** | ハーネス（同上） | **90% / 100% / 0.950** | **50% / 60% / 0.560** |
| 現行 recall | **本番経路**（実記憶 75 件・妨害なし） | 60% / 80% / 0.665 | 15% / 25% / 0.213 |
| **段構え 0.11** | 本番経路（同上） | **85% / 95% / 0.886** | **55% / 85% / 0.682** |

受け入れ基準（paraphrase hit@5 ≥ 55% かつ lexical hit@5 ≥ 95%）は**両方の空間で満たした**。
ハーネスの腕は `retrieval_eval.py` に `cascade_ranker` として足し、`--cascade-threshold` で掃引できる。

読み方で 1 つ補う。**本番の TF-IDF はハーネスと同じ空間ではない**——本番のコーパスは
title / summary / tags だけで作る（本文は読まない）ので、ハーネス（本文全文）より最上位コサインが
低く出る。本番の実測では lexical 20 問中 6 問がしきい値未満で埋め込みへ落ちたが、その 6 問は
埋め込みでも当たり、lexical の hit@5 は 80% → 95% へ**上がった**（下がらないどころではない）。
しきい値 0.11 はこの空間でも谷にあった（lexical の最上位は 0.047〜0.426・paraphrase は 0.018〜0.233）
が、掃引し直したわけではない。記憶が数百件へ増えたら「未決」の 1 点目のとおり測り直す。

## 未決（2026-08-23 に 2 点を測った）

- **しきい値はコーパスの大きさ（と空間）に依存する。** 210 件のハーネス空間で 0.11。
  本番空間（実記憶 75 件・title/summary/tags の TF-IDF）で掃引した結果:

  | しきい値 | lexical hit@1 / hit@5 | paraphrase hit@1 / hit@5 | 発火（lexical / paraphrase） |
  |---|---|---|---|
  | 0（現行） | 60% / 80% | 15% / 25% | 0 / 0 |
  | 0.09 | 85% / 95% | 50% / 85% | 6 / 17 |
  | **0.11** | **85% / 95%** | **55% / 85%** | 6 / 18 |
  | 0.13 | 95% / 100% | 55% / 85% | 8 / 18 |
  | 0.15 | 100% / 100% | 55% / 85% | 10 / 18 |
  | ∞（埋め込み単独） | 100% / 100% | 55% / 85% | 20 / 20 |

  本番空間では埋め込みが全域で TF-IDF を上回り、0.13〜0.15 で lexical も 100% になる。
  ただし 0.11 との差は lexical **1 問**（n = 20）で、率として読める差ではない（eval README
  「n の読み方」）。**既定は 0.11 に据え置く**。記憶が数百件へ増えたら同じ手順で測り直し、
  そのとき 0.13 以上が 2 問以上の差を付けるなら動かす。
- **クエリ側の埋め込みを毎回作るか、キャッシュするか。** 未測のまま（同じ問いを繰り返す運用が
  実際にあるかは、recall の台帳を見てから）。
- **記憶の全文を埋め込むか、要約だけか。** 先頭 4000 字（全文）と title + summary + tags
  （要約だけ）を同じ 75 件・同じ問いで比べた: 要約だけは paraphrase 60% / 85% / 0.725・
  lexical（埋め込み単独）95% / 100%、全文は 55% / 85% / 0.682・100% / 100%。**差は 1 問以内**で、
  長い記憶が不利になっている証拠は無い。索引は要約だけのほうが 4 倍速い（2.9 s vs 12.8 s）が、
  75 件では差が出ない規模なので全文のまま置く。
