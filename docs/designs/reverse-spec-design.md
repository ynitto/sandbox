# reverse-spec 設計 — 既存のソースから根拠つきの仕様書を起こすステートマシン

- 実装: `tools/reverse-spec/`（配布物は `machine/`、置き先では作業場の `.rspec/`）
- 使い方: [`tools/reverse-spec/README.md`](../../tools/reverse-spec/README.md)
- 下敷き: [aws-samples/sample-reverse-spec-flow](https://github.com/aws-samples/sample-reverse-spec-flow)（以下 RSF）と、
  このリポジトリの [codd-agent](./codd-agent-design.md)

## 0. 位置づけ

| | RSF | codd-agent | reverse-spec |
|---|---|---|---|
| 目的 | ソースから仕様書を起こす | 実装と設計書を食い違わせずに変える | ソースから仕様書を起こす |
| 進め方 | 長い手順書（`pipeline.md`）をエージェントが読んで従う | `codd.py step` が 1 段ずつ指示を出し、検査と遷移を受け持つ | codd-agent と同じ `step` の形 |
| エージェント | Claude Code（検証済み）・Kiro（ホストごとの配置スクリプト） | Kiro・GitHub Copilot のカスタムエージェント | シェルを使えるものなら何でも。入口は `AGENTS.md` 1 つ |
| 1 回の大きさ | リポジトリ全体を何日もかけて | 1 つの会話で終わる大きさ | 単位ごとの段に分け、会話もプロセスもまたいで進む |
| 検査 | `gates.sh phase4` | `verify-plan` / `verify-apply` | 段ごとの検査と、最後の `gates` |

codd-agent は「1 回の実行は 1 つの会話で終える」ことを方針にしており（codd-agent 設計 §1.1）、回をまたぐ状態を持たない。
仕様書の起こし直しは、数百ファイルを読む作業なので 1 つの会話に収まらない。そこで、codd-agent の「スクリプトが段を回し、
モデルの申告を信じない」形はそのまま借り、**状態をファイルに持って会話をまたぐ**ところだけを変えた別のツールにした。

## 1. 方針

1. **段の指示と検査はスクリプトが持つ。** エージェントに長い手順書を覚えさせない。今の段で要ることだけを `step` が出す。
   RSF の `pipeline.md`（約 19 万字）を毎回読ませる形は、長い作業の途中で要約されると手順が抜け落ちる
2. **測れるものはスクリプトが測る。** 分母（数え上げ）・根拠の実在・単位のファイルの読み漏れ・検証で確かめる根拠の選び方・
   検証のあとの変更・ソースの変化。モデルに任せるのは、読んで書くことと、根拠から主張が言えるかの判定だけ
3. **エージェントに依らない。** 依存は python3 と git。エージェント固有のもの（サブエージェントの定義、入口のファイル名、
   無人実行のコマンド）は `init.py` と `rspec.json` の `agents` に寄せ、段の指示には書かない
4. **どこで切れても続きから進む。** 状態は `.rspec/state.json`、成果物は `extraction/` と `specs/` にあり、
   段が進むたびにコミットする。会話の記憶を前提にした指示を出さない
5. **1 段は 1 つの会話で読み切れる大きさにする。** 単位の大きさを入口（units の検査）で絞る（§3）
6. **ソースは読むだけ。** 作業場はソースの外に置き（`init.py` が拒む）、ソースの変化は数え上げの hash で見つける

## 2. ステート

```
scope → units → confirm → draft ⇄ verify ⇄ fix（単位ごと）→ synthesize → audit → done
                   ↑NG                                                  ↓ 不通過
                 units ←──────────────────────── stuck（RETRY / SKIP / STOP） → stopped
```

- 段の定義は `rspec.py` の `STATES`、段ごとの指示は `machine/actions/<段>.md`。指示の中の `{{…}}` は
  スクリプトが埋める（単位のファイルの一覧・行数・用紙のパス・NG の一覧など）
- 出力の第 1 語で遷移を決める（`OK` / `FAILED`、confirm は `OK` / `NG` / `STOP`、stuck は `RETRY` / `SKIP` / `STOP`）。
  決まった語でない出力は状態を変えずに断る
- 検査で落ちたら同じ段に残り、指摘を出す。`retries` 回を超えたら stuck。`FAILED` も stuck
- `on_stuck: skip` なら、単位の段（draft / verify / fix）で止まったときに訊かずにその単位を `blocked` にして次へ進む。
  最後の検査（G-BLOCKED）が止めた単位を挙げるので、黙って抜け落ちることはない
- 単位の並びは `units.txt` の順。次の段は「並び順で最初の、未着手なら draft、検証待ちなら verify」で決める（`next_unit`）。
  `requeue` と `drift --apply` もこの決め方に戻るので、途中から状態を戻しても矛盾しない

### 2.1 単位ごとに draft → verify を続ける理由

RSF はすべての単位を書いてから検証する。reverse-spec は 1 単位ごとに書いてすぐ検証する。
単位を書くたびに思い違いの癖（行のずれ・言い過ぎ）が見つかり、次の単位を書く前に直せる。
また、無人で回すときに止まった単位があっても、それまでの単位は検証済みとして確定している。

## 3. 分母と単位

- `ingest` がソースのファイルを数え上げる（git の管理下なら `git ls-files`、そうでなければフォルダをたどる）。
  `exclude` に当たるものを外し、NUL を含むものはバイナリとして分母に入れない。`inventory.tsv` に行数と sha1、
  先頭に固定した版（コミットか、管理外なら数え上げの hash）を書く
- 分母の判定にモデルの申告を使わない（RSF は分母をグラフと別の経路で突き合わせる。reverse-spec は数え上げそのものを
  スクリプトが持つので、突き合わせは要らない）
- 単位は `units.txt` に `unit <id> <種類> <題名>` と字下げしたパターンで書く。YAML や JSON にしなかったのは、
  数百行になってもエージェントが部分的に直しやすく、依存が増えないため
- 検査: すべてのテキストのファイルがどれかの単位に入る（G-DENOM）／対象外と対象の両方に入らない／
  1 単位は `max_unit_lines` 行・`max_unit_files` ファイルまで（1 ファイルだけで超えるものは、その 1 ファイルで 1 単位）
- 単位の状態には、受け持つファイルの sha1 の組み合わせ（`files_sha`）を持つ。分け直しやソースの変化で組み合わせが
  変わった単位だけを未着手に戻し、ほかは検証済みのまま残す

## 4. 単位の仕様書の検査

`check_unit_spec` が見るもの（draft・fix の検査と、最後の G-SPEC で同じものを使う）:

- 先頭の `spec-id` / `unit` がひな形のまま（ひな形はスクリプトが置く）
- 種類ごとの見出しが揃い、空でない。「なし」と書いてよい節は決まっている（`MAY_BE_EMPTY`）。
  それ以外の節には、根拠（`` `パス:行` ``）か `[[SPEC-…]]` か `UNKNOWN[…]` が要る
- 根拠のパスが分母にあり、行が範囲内。バイナリを行で指さない
- 単位のファイルが、どれも 1 回は根拠に出てくる（読み漏れの代わりに測れるもの）
- `UNKNOWN` の書き方（5 種類。`partial` は同じ行に確認した範囲と根拠）
- ひな形の「書く:」のコメントが残っていない

根拠をバッククォートで囲むことにしたのは、表やコードの中の `a:1` のような文字列と取り違えないため。
HTML コメントの中は検査の対象にしない（ひな形の説明に書き方の例があるため）。

## 5. 検証

- スクリプトが仕様書の根拠から `verify_sample` 件を選び、用紙（`extraction/verify/<単位>-<回>.md`）に
  主張（根拠を含む行）と根拠を書く。選び方は単位と回の hash で決まり、前の回で NG だった根拠を先に入れる
- 判定する側には仕様書を開かせない（用紙の主張と、根拠の行だけで判定する）。書いた側の考えに引きずられないため
- 検証の分離はエージェントによって手段が違うので、段の指示では「使えるなら `rspec-verifier` に渡す」とだけ書く。
  - Claude Code・GitHub Copilot・Kiro: `init.py` が置く検証用のサブエージェント
  - サブエージェントの無いもの: `run` で回せば、検証の段は書いた段と別のプロセスになるので、書いたときの会話を持たない
- NG があれば fix へ。fix の検査は、単位の検査に加えて「NG とされた行がそのまま残っていない」ことを見る。
  直したら次の回の用紙を作って検証し直す。`max_verify_rounds` を超えたら stuck
- 検証を通ったときの仕様書の sha256 を持ち、最後の検査（G-VERIFY）で変わっていないことを確かめる

## 6. 長い作業と無人実行

### 6.1 状態とコミット

- `.rspec/state.json`: 今の段・単位ごとの状態・段の試行回数・直前の指摘・`seq`（出力を受け付けた回数）
- `step` は `.rspec/step.lock` を取ってから読み書きする（同じ作業場で重ねて動かさない）。古いロック（持ち主の
  プロセスが無い・2 時間を超えた）は取り直す
- 状態は一時ファイルに書いてから置き換える（途中で落ちても壊れない）
- 段を受け付けるたびに作業場へコミットする（`auto_commit`）。どこまで進んだかが git の履歴に残り、戻せる
- `extraction/worklog.md` に段の移り変わりを書き足す

### 6.2 run

`run` は次を繰り返す。

1. 状態が終わり（done / stopped）なら結果を出して終わる。人の判断が要る段なら指示を出して終了コード 3
2. 使い切りの印（`.rspec/run-token.json` と環境変数 `RSPEC_RUN_TOKEN`）を作り、エージェントを新しいプロセスで起こす。
   指示は固定の短い文（`step` で読み、1 段だけ進めて終わる）
3. 終わったら `seq` が増えたかを見る。増えていれば次へ。増えていなければ待って（倍々、最大 600 秒）やり直し、
   `--retries` 回続けば終了コード 4

1 段ごとにプロセスを起こすのは、会話が長くなると要約で指示や根拠が崩れるため。1 段の中で要るものは `step` がすべて出す。

使い切りの印は、エージェントが 1 段を超えて進むのを止める。段が進んだら印を使い切り、そのプロセスからの次の出力は断る。
検査で落ちて同じ段に残ったときは使い切らない（同じプロセスが、読み込んだ中身のまま指摘だけを直せる。回数は `retries` で止まる）。

エージェントの CLI の引数は版で変わるので、既定（`AGENT_PRESETS`）は出発点にすぎず、`rspec.json` の `agents` で上書きする。

### 6.3 ソースの変化

`drift` は数え上げの sha1 と今のソースを比べ、変わった・増えた・消えたファイルと、それを受け持つ単位を挙げる。
`--apply` は数え上げ直して units の段に戻す。増えたファイルは G-DENOM が単位に入れさせ、受け持つファイルが変わった単位だけが
未着手に戻る（§3）。最後の検査の G-FRESH も同じ比べ方で、固定した版のまま終わったことを確かめる。

## 7. RSF から借りなかったもの

- **目的のプリセット（maintenance / evaluation / rebuild）と、作り直し向けの層（rebuild/）。** 仕様書の中身の厚さを
  変える仕組みで、確かめ方は変わらない。要るなら種類（`CATEGORIES`）とひな形を足す
- **スタックごとの数え方（playbooks）。** 単位の分け方の手がかりにはなるが、分母はスクリプトが数えるので、
  漏れの検出には要らない
- **コードグラフ（NODE-*）。** 単位どうしのつながりは仕様書の `[[SPEC-…]]` と `source-index.md` で追える。
  グラフを作る段を足すと、1 段で読む量がリポジトリ全体になる
- **密度の検査（G-DENSITY）。** 代わりに「どの節にも根拠か UNKNOWN」「単位のファイルをすべて根拠に挙げる」を求める

## 8. テスト

`tools/reverse-spec/tests/test_reverse_spec.py`。一時フォルダにソースと作業場を作り、エージェントの代わりに
ファイルを書いて `step` を回す（LLM は呼ばない）。

- 通し: scope から done まで、NG → fix → 検証し直し、ソースの変化で G-FRESH が落ち `drift --apply` で単位が戻る
- 検査: 分母の漏れ・単位の大きさ・根拠の範囲外と無いファイル・UNKNOWN の書き方・続けて落ちたら stuck・SKIP と requeue・
  `on_stuck: skip`・決まった語でない出力
- run: 1 段だけ進める偽のエージェントで done まで回り、段ごとに 1 プロセス・2 段目の出力を断る／
  人の判断が要る段で止まる／進まない段が続けば止まる
