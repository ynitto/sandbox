## 1. TL;DR

**何を作るか**: agent-project / agent-flow / agent-amigos / agent-loop / agent-audit が共有する
ものの**唯一の実装**を置く内部パッケージ。claim / lease、git 転送、CLI 定義のローダ、検証契約、
ノード予算、ローカル推論アダプタなど。

**主要な決定**:

1. 共有されるものは agentcore に 1 実装だけ置く。各ツールの自前実装は持たない。
2. 独立配布せず、各ツールの zipapp へ同梱する。pip 依存にしない。
3. 依存は一方向。agentcore はどのエンジンも知らず、状態も持たない。

**却下した主要案**: 各ツールが自前の小さな実装を持つ案。URL 正規化を 3 者が自前実装して吸収規則が
食い違い、「同じクローンなのに片方だけローカルと認識されない」という速度の謎になった前例がある。

**読むべき人**: agentcore へモジュールを足す人、エンジン間で同じ判定が要ると気づいた人。
**読まなくてよい人**: CLI 定義を足したいだけの人（[`agents/README.md`](../../agents/README.md) で足ります）。

## 2. 背景と課題

agent-* は 5 つのツールが別々の実行ファイルとして動く。しかし扱う対象は同じで、同じ判定が
何度も要る——「この claim の勝者は誰か」「この git URL は同じリポジトリか」「この CLI を
どう起動するか」「このノードは予算内か」。

これを各ツールが自前で書くと、**同じ仕様・別実装**が並ぶ。並ぶこと自体は動くが、片方だけが
育つと差が開く。実際に踏んだのは 3 件だ。

| 何が分かれていたか | 症状 |
|---|---|
| git URL の正規化（3 実装） | 同じクローンを symlink 経由で宣言した PC で「同じリポジトリ」と読めず、**なぜかローカルクローンが使われない**という速度の謎として出た |
| 委譲板の入札選別（2 実装） | 同じ公示が経路によって拾えたり拾えなかったりした |
| CLI の起動方法（8 か所・4 実装） | 同じ CLI でも用途によって argv が違い、CLI の作法が変わるたびに複数箇所の修正が要った |

いずれも**壊れ方が分かりにくい**のが共通している。例外も警告も出ず、「動くはずのものが動かない」
としか見えない。共有すべきものを共有していない、という一点から出た症状だ。

### 2.1 非目標

- **汎用ライブラリにすること**。agent-* 以外から使われることを想定しない。
- **独立したバージョニング・配布**。同梱するので版ずれが起きない（§3.2）。
- **エンジン固有の知識を持つこと**。設定ファイルの探索も状態ディレクトリの決定も呼び出し元の担当。
- **サードパーティ依存**。標準ライブラリだけで成立させる。

## 3. 主要な設計判断

### 3.1 共有されるものは 1 実装だけ置く

**判断**: 2 つ以上のツールが同じ判定を必要としたら、agentcore へ 1 実装を置き、各ツールはそれを
呼ぶ。ツール側に同じ仕様の別実装を持たない。

**文脈**: §2 の 3 件はどれも「最初は 1 か所だったものが、2 つ目のツールで必要になったときに
コピーされた」形で始まっている。コピーした時点では同一なので、レビューでは問題に見えない。

**選択肢と却下理由**: *各ツールが自前の小さな実装を持つ*は却下。当初はこの方針で、
「小さいのだから」と許していた。破れたのは URL 正規化で、3 者の吸収規則が食い違った結果、
症状が「速度の謎」として出た——**壊れたことにすら気づけない**のが決め手だった。
*共通ライブラリを pip で配る*も却下（§3.2）。

**トレードオフ**: agentcore が肥大する。歯止めは「2 つ以上のツールが必要とするか」の 1 点だけで、
1 ツールしか使わないものは置かない。

**確信度**: 高い。集約した 3 件はいずれも再発していない。

### 3.2 独立配布せず、各 zipapp へ同梱する

**判断**: agentcore は内部モジュールとして各ツールの zipapp へコピーして配る。PyPI へ出さず、
pip 依存にもしない。

**文脈**: agent-* は単一ファイル配布（zipapp）で、`~/.local/bin/` に置くだけで動くことが要件だ。
社内 PC には pip の使えない環境も、プロキシ越しに PyPI へ出られない環境もある。

**選択肢と却下理由**: *pip パッケージにする*は却下。インストール手順が 1 つ増え、版ずれ
（agent-flow は新しい agentcore を要求するのに古いのが入っている）という新しい壊れ方を作る。
*共有ディレクトリへ 1 部だけ置いて全ツールから読む*も却下——各ツールが別実行ファイルである以上、
それぞれが自己完結していないと**片方だけ動く状態**になる。

**トレードオフ**: 同じコードが 6 つの zipapp に入る（agent-project / agent-flow / agent-amigos /
agent-audit / agent-ollama / agent-loop）。ディスクは安いので払う。ただし
**自己更新の sparse-checkout には `tools/agent-tools` を含めなければならない**——エンジンの
subdir だけを取ると installer が agentcore を束ねられず、自己更新が永久に失敗する（実際に踏んだ罠で、
各ツールの `TOOL_SUBDIR` が 2 パスを持つのはその回避）。

**確信度**: 高い。

### 3.3 依存は一方向。agentcore はエンジンを知らない

**判断**: agentcore は状態を持たず、エンジン固有の設定ファイル・状態ディレクトリ・語彙を読まない。
必要なものはすべて呼び出し元が引数で渡す。

**文脈**: 共有実装が呼び出し元の都合を知り始めると、「agent-flow のときはこう、agent-project の
ときはこう」という分岐が中に生える。それは集約したはずの散らばりが場所を変えただけだ。

**選択肢と却下理由**: *agentcore が設定ファイルを自分で探す*は却下。探索順はツールごとに違い、
同じ関数が呼び出し元によって別の答えを返すことになる。*エンジン名を引数に取って分岐する*も却下
——CLI 名で分岐しないという CLI 契約の原則と同じ理由で、分岐の追加が止まらなくなる。

**トレードオフ**: 呼び出し側の引数が増える。代わりに agentcore の関数は**引数だけを見れば
答えが決まる**ので、テストが素直に書けて、同じ入力から同じ答えが出ることを保証できる。

**確信度**: 高い。

### 3.4 ローカル推論も同じ CLI 契約の下に置く

**判断**: ollama / aider のローカル推論を専用経路にせず、`agents/<name>.json` 契約の 1 実装として
agentcore に入れる。エンジンは `ollama` という名前で分岐しない。

**文脈**: ローカル推論はクラウド CLI と性質が違う——遅く、ツールを内蔵せず、JSON モードの制約も
違う。素直に書けば「ollama のときだけ」の分岐になる。

**選択肢と却下理由**: *ollama 専用の実行経路を作る*は却下。エンジン側に CLI 名の分岐が戻り、
2 つ目のローカル CLI（aider / opencode）で同じ分岐をもう一度書くことになる。性質の違いは
分岐ではなく**定義の申告**（`headless_autonomy` / `variants` / `relative_cost` / `readonly`）で
表現し、エンジンは申告だけを見る。

**トレードオフ**: 定義のフィールドが増える。増えた 1 ビットが何を意味するかを設計で説明する
負担は残るが、それは 1 か所で済む。

**確信度**: 高い。`aider` と `opencode` は分岐を 1 行も足さずに載った。

### 3.5 写しは禁じず、機械に突き合わせさせる

**判断**: agentcore をそのまま使えない場所（別言語・単体配布）では写しを許し、**一致をテストで
縛る**。写しを禁止する規約は置かない。

**文脈**: 2 種類ある。agent-dashboard は JS で、候補を出すたびに Python を起動すると描画が
プロセス起動待ちになる。`agent-aider` / `agent-opencode` は 1 ファイルで配るので agentcore を
import できない。どちらも技術的な必然で、規約では消せない。

**選択肢と却下理由**: *写しを禁じる*は却下。禁じても消えず、見えなくなるだけだ。
*写しを 1 本化する*も却下——判定の入力源が別プロセス・別言語なので、寄せると起動コストか
配布形態のどちらかを壊す。

**トレードオフ**: 同じ入力から違う答えが出ても誰も気付かない、という壊れ方を抱える。だから
テストが**正典を実際に読んで**突き合わせる。写しそのものが問題なので、写しを機械に突き合わせさせる。

**確信度**: 高い。この形は dashboard 側で 4 本（CLI 定義・契約バージョン・URL 正規化・
フォージ決着推定）先行しており、2026-08-22 に単体配布アダプタの環境解決へも広げた。

## 4. 何を agentcore へ置くかの線引き

この節は判断の粒度。モジュールの一覧は仕様書 §2 にある。

**置く**: 2 つ以上のツールが必要とし、**同じ答えを返さなければならない**もの。claim の勝者、
git URL の同一性、CLI の argv、検証 receipt の digest、予算の判定。ずれると症状が分かりにくい
ものほど、置く価値が高い。

**置かない**: 1 ツールしか使わないもの。エンジン固有の状態遷移。設定ファイルの探索順。
「便利だから共有したい」だけのユーティリティ——共有の理由が「同じ答えが要る」でないなら、
それは agentcore の対象ではない。

**判断に迷ったとき**は置かない側に倒す。2 つ目の利用者が現れてから移すほうが、使われない
抽象を先に作るより安い。

## 5. 未実装として残っているもの

- **`variants` の用途語彙の一致を縛るテスト**。定義が申告する 15 用途とエンジンが問い合わせる
  15 用途は現在ちょうど一致しているが、これはテストで固定していない。**あえて固定していない**
  ——定義が先に申告してエンジンが後で採用する順序も、その逆も正当なので、不一致を失敗に
  倒すと正当な作業を止める。仕様書に一覧を載せて人が見比べられる形に留めている
- **`agentcore/tests/` と `agentcore/agentcore/tests/` の統合**。テストルートが 2 つに割れており、
  片方だけ走らせると半分が素通りする。CI は両方を明示して回避しているが、根本は残っている
