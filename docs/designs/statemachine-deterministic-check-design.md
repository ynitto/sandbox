# statemachine-use 決定的検査（check）設計 — 遷移の材料を自己申告から実測へ移す

> P1。柱 3 資源効率 — ローカルモデルへ定型作業を移すための前提配線。
> **この文書は fork 先への移植を主目的に、スキル側の変更を仕様として書く。**

## 1. 解く問題

`output_validator` が見ているのは**モデルが書いた第 1 行の書式**である。「PASS」と書くのは
モデル自身なので、成果物が仕様どおり動くかは 1 バイトも見ていない。

実測（[T1 分解レポート](../../tools/agent-tools/eval/results/archive/2026-08-13-t1-decomposition-report.md)）で
この穴が形になって出た。ローカルモデルの実装ステップは初回 **13/13** が同じ壊れ方をしたのに、
機械層はすべて通した——ファイルは実在し、この実行で作られ、変更もされていたからである。

| 層 | 見ているもの | 偽 done を止められるか |
|---|---|---|
| `condition_rule` / `output_key` | モデルが書いたテキスト | ✗ |
| `output_validator` | その第 1 行の**書式** | ✗（書式だけ合っていれば通る） |
| ハーネスの受入証跡 | ファイルが実在する / 触れた / 変わった | ✗（壊れた実装も全部満たす） |

**遷移は決定的だが、遷移の材料が自己申告である。** ここを塞がない限り、作業を安いモデルへ
移すほど偽 done が増える。

同じレポートが打ち手も決めている。**分解だけでは受入が下がり（0/3）、決定的な検知と再投入を
足すと 3/3 になった。** 効いているのは (a) ハーネスが決定的に失敗を検知したことと
(b) 再投入したことの 2 つで、診断文の中身ではない（診断は受入を変えず、再試行を 28% 速くする）。

## 2. 中心となる決定

**ステートが「ハーネスが実行する検査コマンド」を宣言でき、その終了コードが遷移の材料になる。**

```yaml
states:
  implement:
    action_file: actions/implement.md
    output_validator: "startswith:OK"                # 書式（モデルが書く）— 残す
    check: "python3 -m pytest tests/test_x.py -q"    # 事実（ハーネスが測る）— 足した
    check_retries: 2
transitions:
  - from: implement
    to: review
    condition_rule: "equals:check_ok:true"           # 実際に通ったときだけ進む
```

`output_validator` は**置き換えない。併存させる**。前者は「答えの形が契約どおりか」、後者は
「成果物が実際に動くか」で、見ている対象が違う。書式が壊れていれば検査以前に再試行が要る。

設計上の要点は 1 つに尽きる——**検査の宣言も実行も結果も、モデルの手の届かない場所にある。**
コマンドは workflow.yaml（人が書く）が宣言し、ハーネスが実行し、終了コードがそのまま
コンテキストへ入る。モデルは検査を書き換えることも、結果を騙ることもできない。

## 3. スキーマ（`states.<id>` への追加）

| フィールド | 型 | 既定 | 意味 |
|---|---|---|---|
| `check` | 文字列 / 配列 / オブジェクト | — | 検査コマンド。**未宣言ならゲート無し**（従来動作） |
| `check_retries` | 整数 | `max_retries` | 検査が落ちたとき同じステートをやり直す回数 |
| `check_on_exhausted` | 文字列 | `escalate` | 使い切っても落ちるときの動作。`escalate` \| `continue` \| `error` |
| `check_feedback` | 真偽値 | `true` | 再投入時に検査の出力を課題文へ足すか |

`check_retries` の既定を `max_retries` にしてあるのは、実測ハーネス（worker_eval の多段セル）で
`max_retries` がゲートの再投入予算そのものだったためである。両者を分けたい定義だけが
明示すればよい（`max_retries: 2` + `check_retries: 0` のように書ける）。

### 3.1 `check` の 3 つの形と正規化

すべて `{command, args, timeout_sec}` へ正規化する。

```yaml
check: "python3 -m pytest tests/ -q"                                   # 文字列（shlex 分割）
check: ["python3", "-m", "pytest", "tests/"]                           # 配列（分割済み）
check: {command: "python3", args: ["-m", "pytest"], timeout_sec: 300}  # 明示
```

- `timeout_sec` の既定は **120**、下限 1。上限はスキル側では切らない（ハーネスが自分の
  上限で丸めてよい）。
- **シェルは介さない。argv を直接実行する。** したがってパイプ・リダイレクト・変数展開・
  バッククォートは動かない。
- 文字列形にシェル記号（`|` `&` `;` `>` `<` `` ` `` `$(` 改行）が含まれていたら**エラーにする**。
  リテラルの引数として黙って渡すと、書いた人の意図と違うコマンドが「成功」しうる——
  検知装置が黙って別物を測るのは、検知が無いことより悪い。合成が要るならスクリプトにまとめる。
- 引用は shlex が解く（`echo 'a b'` → `args: ["a b"]`）。

### 3.2 検査結果のコンテキスト変数（**移植で最重要の契約**）

検査を宣言したステートでは、次の 3 キーが `condition_rule` とテンプレート展開から使える。
**ハーネスが測った事実**であって、モデルが書いたテキストではない。

| キー | 値 | 備考 |
|---|---|---|
| `check_status` | `"0"` / `"1"` / … / `"error"` | 終了コードの**文字列**。実行できなかった場合（タイムアウト・コマンド不在）は `"error"` |
| `check_ok` | `"true"` / `"false"` | 終了コード 0 **かつ**実行できた場合のみ `"true"` |
| `check_output` | 文字列 | 診断の先頭行。**stderr を優先**し、無ければ stdout |

3 点が意図的な設計である。

1. **すべて文字列。** `condition_rule` の評価器は値を `str()` してから比較するので、
   真偽値や整数で入れると `equals:check_ok:True` のような書き方の揺れを生む。
2. **測れなかったときは `"error"`。** 0 でないので必ず「落ちた」側へ倒れる。
   コマンド名を間違えた定義が「検査を通った」ことにならない。
3. **`check_output` は 1 行だけ。** 遷移条件に入れるのは診断であって全文ではない。
   全文はハーネスのログと再投入の課題文へ回す（§4.2）。

## 4. 実行の意味論

```
action 実行 → 検査実行 ─ 通った ─→ 検査結果をコンテキストへ → 遷移評価
                  │
                  └ 落ちた ─ 再投入予算あり ─→ 診断を課題文へ足して同じ state をやり直す
                              │
                              └ 使い切った ─→ check_on_exhausted が決める
```

### 4.1 通ったとき — 成功側に課金しない

呼び出し回数は増えない。実測でも `T4gate` / `T2gate` は 1 call のまま通過し、壁時計への
上乗せは検査の実行時間だけだった。**「検査を常設して落ちた課題だけ再投入」は成功側に
課金しない**——「既に正しい成果物にも 2 倍払う」懸念は、検査を省いて無条件にやり直す
方式にだけ当てはまる。

### 4.2 落ちたとき — 同じステートをやり直す

`check_feedback: true`（既定）なら、次の試行の課題文の末尾へこう足す。

```
Retry 1/2: the declared check failed (exit status 1).
Check command: python3 -m pytest tests/test_x.py -q
Check output:
<stderr / stdout の末尾 2000 文字>
Fix the work so this exact command succeeds. Do not modify the check itself.
```

- **末尾を 2000 文字で切る。** ローカルモデルの文脈は超過時に黙って古い側から捨てられる。
  長い pytest 出力を丸ごと積むと、system prompt が落ちた状態の答えが返る。
- **「検査自体を書き換えるな」を明記する。** 検査を通すいちばん安い方法は検査を壊すこと
  なので、指示で塞ぎ、レビューで確かめる（`check` の宣言は workflow.yaml 側にあるので、
  モデルが書き換えるにはリポジトリのファイルを触る必要がある——検知は可能）。
- `check_feedback: false` なら真偽だけを渡す。診断は受入を変えず速度だけを変えるので、
  まず真偽で動かして後から足す運用ができる（実測の結論をそのまま選択肢にしてある）。

### 4.3 使い切ったとき — `escalate` を既定にする理由

| 値 | 動作 | 使いどころ |
|---|---|---|
| `escalate`（既定） | 実行を止め、結果へ `escalate: true` を立てる | **この実行レベルでは解けない**の宣告。上位の段（クラウド）へ回すシグナル |
| `continue` | 検査結果をコンテキストへ入れたまま遷移評価へ進む | 失敗経路を自分でグラフに書く場合（修復ステートへ分岐する等） |
| `error` | 通常の実行エラーとして落とす | 落ちたら止まってほしいだけの場合 |

既定を `escalate` にしたのは実測による。**再投入で直るのは「仕様の読み違い」族だけで、
「作業の丸ごと欠落」族は同じ診断を突きつけても 9/9 が同形で失敗する。** 決定的に同じ壊れ方を
する以上、引き直しでは埋まらない——だから上限は 1〜2 で足り、到達したら段を上げるのが
正しい打ち手になる。**失敗一般と区別して名前を付ける**のがこの設計の要点で、区別が無いと
呼び出し側は「定義が悪いのか、モデルが足りないのか」を毎回人が読んで判断することになる。

## 5. 検証（投入前に落とすもの）

`validate_workflow` へ 4 つ足した。**検知の欠落は最も気付けない事故**なので、
実行時に黙って素通りさせず定義の投入前に落とす。

| # | 落とすもの | 理由 |
|---|---|---|
| V1 | `check` の宣言が壊れている（シェル記号・`command` 欠落・`timeout_sec` が非数値） | ゲートを置いたつもりで置けていない実行を作らない |
| V2 | 終端ステートの `check` | アクションが無いので検査する対象が無い |
| V3 | `check_on_exhausted` が語彙外 / `check_retries` が負 | 綴り間違いを既定へ丸めない |
| V4 | **検査を宣言していないステートから `check_*` で分岐している** | 下記 |

**V4 が本命である。** `evaluate_condition_rule` は**キーがコンテキストに無ければ `None` を
返して LLM 評価へフォールバックする**——これは既存の仕様で、変えるべきではない（未定義の
変数を偽と決めつけると別の事故になる）。しかしその結果、`check` を書き忘れたステートで
`equals:check_ok:true` と書くと、**決定的に見ているつもりの遷移が黙って LLM 評価へ落ちる**。
つまり P1 以前の「自己申告で決まる」状態へ静かに戻る。書いた人はゲートを置いたと思っている
ので、これはテストでも運用でも気付けない。定義の検証で塞ぐしかない。

ワイルドカード（`from: "*"`）の場合は、非終端ステート全部を検査対象にする。

## 6. 外部ハーネス向けの照会口 `--state-check`

fork 先を含め、**スキルのスクリプトを subprocess として呼ぶハーネス**が YAML を自前で
読み直さずに済ませるための口。

```console
$ python3 scripts/next_state.py <workflow> --state implement --state-check
{
  "state": "implement",
  "check": {"command": "python3", "args": ["-m", "pytest", "tests/test_x.py", "-q"],
            "timeout_sec": 120},
  "check_retries": 2,
  "check_on_exhausted": "escalate",
  "check_feedback": true
}
```

- 宣言が無ければ `"check": null`（ゲート無し）。
- 宣言が壊れていれば **exit 1 + stderr に理由**（V1〜V3 のうちそのステートに関わるもの）。
- 終端判定より前に処理する。これは遷移の問い合わせではなく**宣言の照会**だから。

**なぜ口を足したか。** 正規化（文字列の分割・既定値の解決・不正宣言の拒否）を
ハーネス側にも実装すると 2 実装になり、定義側が形を足した日に静かにずれる。同じ形の事故は
このリポジトリで既に起きている（eval ハーネスが argv を写していて、定義側が予算を 30 → 12 へ
絞った当日にずれた）。**写しは人の注意力に頼る不変条件で、ずれても静かに測定が別物になる
だけ**なので、照会で解く。

## 7. fork へ移植する — 2 段階

fork 先のハーネスは旧引数（`--list-conditions` / `--evals` / `--output KEY=VALUE`）で
呼んでいる。**この設計は旧引数のままでも成立する**（下記 §7.2 で実測確認済み）。

### 7.1 段階 A — スキルだけ移す（ハーネス無改造）

スキルの 2 ファイルを移すだけで、次が手に入る。

| 手に入るもの | 効果 |
|---|---|
| スキーマと検証（V1〜V4） | 壊れた宣言・検査無しの分岐を**投入前に落とす** |
| `--state-check` | ハーネス改修の準備ができる |
| 非同期エンジン（`run_machine.py` 経路）のゲート | この経路で走らせるワークフローは**すぐにゲートが効く** |

移すもの:

- `scripts/engine.py` — `normalize_check` / `check_context` / `check_feedback_note` /
  `run_check`、`StateConfig` の 4 フィールド、`load_workflow` の解決、`validate_workflow` の
  V1〜V4、`StateMachineEngine._execute_gated`、`ExecutionResult.escalate`
- `scripts/next_state.py` — `--state-check`

**この段階では、fork の subprocess ハーネスで走らせるワークフローに検査は掛からない。**
掛かっていないことが定義から読めない状態は危険なので、段階 A で止めるなら
「ハーネス側は未対応」を fork の README に明記すること。

### 7.2 段階 B — ハーネスを対応させる

ハーネス側に要る変更は 4 つだけである。

1. **ステート実行の前に宣言を引く。** `next_state.py --state <id> --state-check` を呼び、
   `check` が `null` なら以降は従来どおり。
2. **アクションの後に検査を実行する。** argv を直接実行する（シェルを通さない）。
   終了コードから §3.2 の 3 キーを作る。
3. **落ちたら同じステートをやり直す。** `check_retries` 回まで。`check_feedback` が真なら
   §4.2 の文を課題文の末尾へ足す（末尾 2000 文字で切る）。
4. **遷移の問い合わせに 3 キーを載せる。** 呼び方は 2 通りあり、**どちらでも動く**。

```bash
# 現行契約
next_state.py <wf> --state implement --auto-eval \
  --context '{"last_output":"OK","check_ok":"true","check_status":"0","check_output":""}'

# 旧ハーネス互換（fork の現状。--context が無いキーの補完として効く）
next_state.py <wf> --state implement --list-conditions \
  --output check_ok=true --output check_status=0
```

移植の判断に効く性質を 1 つ実測で確かめてある。**旧引数の `--evals` は検査結果を上書き
できない**——`condition_rule` が決定的に評価できる条件は LLM 評価より優先されるので、
`--evals '{"0": true}'` を渡しても `check_ok=false` なら遷移は成立しない。つまり
**ハーネスが検査結果を渡しさえすれば、LLM 側から偽 done を通す経路は残らない**。

`check_on_exhausted` の受けはハーネスの結果契約に依存するので、fork の形に合わせて決める。
参考実装（agent-loop）は次のようにした。

| 値 | 参考実装の振る舞い |
|---|---|
| `escalate` | 結果 JSON へ `escalate: true` と `check`（`state` / `attempts` / `argv` / `check_status` / `check_output`）を加え、**終了コード 3** で終わる |
| `continue` | 検査結果をコンテキストへ載せたまま遷移評価へ進む |
| `error` | 通常の実行エラー（終了コード 1） |

終了コード 3 を選んだのは、呼び出し側が結果 JSON を読まずに昇格へ振り分けられるようにする
ため。非 0 を一律に失敗として扱う既存の呼び出し側とは互換のままである。

### 7.3 移植したら確かめる 2 点

チェッカーそのものを検証してから使うのが、このリポジトリの測定衛生である。移植後に
最低限これだけは確かめる（両方ともテストにしてある）。

- **モデルが「OK」と書いても、検査が落ちれば進まない。** これが通らなければ移植は
  失敗している（配線はあるが材料が繋がっていない状態）。
- **検査の無いステートで `check_ok` に分岐する定義が、投入前に落ちる。** これが通らないと、
  ゲートを置いたつもりの遷移が黙って LLM 評価へ戻る経路が残る。

## 8. 後方互換

| 対象 | 影響 |
|---|---|
| `check` を宣言しない既存ワークフロー | **無し。** 検査は走らず、コンテキストのキーも増えない |
| 既存の `output_validator` / `max_retries` | 意味を変えていない（併存する） |
| 旧引数（`--list-conditions` / `--evals` / `--output`） | 変更なし。検査結果も旧引数で渡せる（§7.2） |
| 結果契約 | `escalate` / `check` は**加算的**。`RESULT` を読むだけの呼び出し側は壊れない |
| 終了コード | 0 / 1 は従来どおり。3 が加わる（非 0 として扱う側は影響なし） |

参考実装では既存 967 件のテストが無変更で通っている。

## 9. 限界と、この設計が解かないこと

- **検査を書けない仕事には効かない。** 「読みやすさ」「方針として妥当か」は終了コードに
  ならない。ゲートを置けるのは決定的に測れる成果だけで、そこが**ステートの割り方を決める
  制約**になる（分解の目的は検査を差し込む場所を作ることであって、細かく割ること自体では
  ない——実測では検知を伴わない分解は受入を下げた）。
- **「作業の丸ごと欠落」族は直せない。検知できるだけである。** ゲートの価値は族で変わり、
  片方には修復装置として、もう片方には検知装置として効く。後者に対する打ち手は
  `escalate` であって再投入ではない。
- **検査コマンド自体の正しさは見ていない。** 常に 0 を返す検査を書けばゲートは素通りする。
  ここは定義のレビューに残る（`check` は workflow.yaml 側にあるのでレビュー対象にできる、
  というのがせめてもの担保）。
- **検査の実行コストは払う。** 通る課題では呼び出し回数は増えないが、検査の実行時間は
  毎ステート乗る。重い検査（フルテスト）をすべてのステートに置くと、そこが律速になる。
- **並行実行は考えていない。** 検査は同じ作業ディレクトリで直列に走る前提で、
  同時に複数ステートを進めるハーネスへは別途設計が要る。

| 採用案 | ステートが宣言する検査コマンドをハーネスが実行し、終了コードを `condition_rule` のコンテキストへ入れる。落ちたら同じステートを再投入し、上限到達は `escalate`（段の昇格シグナル）として失敗一般と区別する。正規化はスキルの 1 実装に閉じ、外部ハーネスは `--state-check` で照会する |
| 却下案 | `output_validator` の拡張（見ている対象が書式なので、動作の検証を混ぜると 1 フィールドが 2 つの意味を持つ）、ハーネス側での YAML 再解釈（2 実装になり定義側の変更に静かに置いていかれる。argv の写しで前科あり）、シェル経由の検査コマンド（メタ文字入りの宣言が意図と違うコマンドを「成功」させうる）、検査失敗を通常の失敗として扱う（定義の不備とモデルの能力不足を人が毎回読み分けることになる） |
| 主な理由 | 実測で、決定的な検知と再投入だけで受入が 0/9 → 3/3 になり、検知を伴わない分解は逆に下がった。効いているのは検知と再投入であって診断の中身ではないので、真偽を返す最小の口で足りる |
| トレードオフ | 検査を書けない仕事には効かない（ステートの割り方に制約が生まれる）。検査の実行時間が毎ステート乗る。検査コマンド自体の正しさは定義レビューに残る |
| 再評価条件 | 実機経路の再測で受入が 3/3 帯を割る場合、`escalate` の発生率が高く昇格コストが節約を上回る場合、または並行実行するハーネスが必要になった場合 |
