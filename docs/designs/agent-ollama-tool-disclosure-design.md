## 0. 先に用語を 3 つだけ決める

本書は「なぜツールが既定で無効なのか」という問いから始まっているので、
その答えに必要な語を最初に置く。専門用語はこの 3 つしか使わない。

| 語 | 意味 |
|---|---|
| **読み込み時間**（prefill） | モデルが「渡された文章を読む」のにかかる時間。答えを書き始める前に必ず全部読む。CPU では**読む方が書くより遅い**ことが多く、これが本件の全ての出発点。 |
| **先頭キャッシュ**（接頭辞キャッシュ） | 前回と**先頭が一字一句同じ**なら、その部分を読み直さない仕組み。ollama は `OLLAMA_NUM_PARALLEL=1` で有効になる（親文書 §案C-2）。先頭を書き換えると**全部読み直しになる**。 |
| **ツール** | モデルが外の世界へ触るための道具。agent-ollama では今のところシェル（bash）1 つだけ。 |

この 3 つの関係が本書の背骨になる:

> ツールの説明文は毎回モデルに読ませる固定費である。
> だから**説明文は小さいほどよい**し、**一度決めたら先頭を書き換えてはいけない**。

## 1. 何を解こうとしているか

現行実装には、運用上こう見える点が 2 つある。

**(1) ツールが既定で無効になっている。** `agent-ollama <model>` はファイルを読むことすら
できない。理由は §2.2 のとおり正当だが、なぜそうなのかがコードを読まないとわからない。

**(2) 「ツールが 1 つも無い」と「無制限のシェルが 1 つある」の間に段が無い。** 書き込み
モードで渡すのは `bash -lc` の素通しで、許可リストも承認もない。一方で「作業ディレクトリ
の外を変更しない」という制約は**システムプロンプトの一文でしかなく、強制力がゼロ**である
（§2.3）。**緩すぎる所と厳しすぎる所が入れ替わっている**のが実態で、本書の主目的は
ここを直すことにある。

## 2. 現状の記録（実装済みの事実）

### 2.1 2 つのモード

| 起動 | 何ができるか | 契約上の位置 |
|---|---|---|
| `agent-ollama <model>` | 単発の文章→文章。**ファイルもコマンドも触れない** | 既定・`readonly: enforced` |
| `agent-ollama --tools <model>` | シェル 1 つを道具にした実行ループ | `write_args` |

`agents/ollama.json` がこれを宣言している:

```jsonc
{
  "command": ["agent-ollama", "--think", "off", "{model}"],
  "write_args": ["--tools"],   // 書き込みモードのときだけ道具が生える
  "readonly_args": [],
  "readonly": "enforced"       // 読み取り専用は道具ゼロ＝宣言が嘘にならない
}
```

### 2.2 なぜ既定で無効なのか — 2 つの別々の理由

**理由 A（契約）**: `readonly: "enforced"` は「読み取り専用を**強制保証**する」という
宣言である。ツールが既定で生えていると、この宣言が嘘になる。親文書 §F-2 はこれを
設計の要点として明記している——「ループとツールは `--tools` でだけ生え、既定・readonly は
純 text→text のまま。`enforced` 宣言に嘘が入らない」。

**理由 B（読み込み時間）**: ツールの説明文は毎回読ませる固定費である。opencode が
1〜2 万トークンを注入して CPU で数分焼いていた主犯がこれだった。`ollama_loop.py:16-21`:

> ツール定義（JSON スキーマ）は毎リクエストの prefill に載る固定費である。（略）
> ツールを bash 1 つに絞り、呼び出しもスキーマではなくテキスト規約にすると、
> 固定費はシステムプロンプトの**数百トークンだけ**になる。

この 2 つは独立していて、**片方を緩めてももう片方は残る**。混同すると設計を誤る。

### 2.3 書き込みモードの実体

「書き込み」は契約上の**権限の段**を指す語であり、ファイル書き込みに限らない。実体は
`ollama_loop.py:402-419`:

```python
subprocess.run(["bash", "-lc", command], cwd=cwd, capture_output=True, timeout=timeout)
```

コマンド文字列はモデル出力からコードブロックを正規表現で抜いたものをそのまま渡す
（`extract_command`）。**許可リストも拒否リストも承認もない。** したがって可能なのは
「その CLI を起動したユーザーの権限でできること全部」——ファイル編集はその一例にすぎず、
`git push`・パッケージ導入・ネットワークアクセスも含む。`-l` はログインシェルなので
`~/.profile` が読まれ、利用者の PATH と認証情報がそのまま効く。

制約は 2 つあるが、性質が違う:

| 制約 | 効き方 |
|---|---|
| `--command-timeout`（既定 300 秒）・`--max-rounds`（既定 12） | **強制**。プロセスレベルで有界 |
| 「作業ディレクトリの範囲外を変更しない」（`system_prompt()` の一文） | **お願いのみ**。`cd` も絶対パスも素通り |

### 2.4 制約の出所は 3 系統ある

「制約が厳しい」と感じるとき、対象がどれかで緩め方が変わる。

| 制約 | 出所 | 硬さ |
|---|---|---|
| ツールがシェル 1 つだけ・スキーマでなくテキスト規約 | **ハードウェア**（親文書 L8「ハードウェアは変えられない」） | 前提が変われば消える |
| `--think off` / `max_output_chars 4000` / `max_rounds 12` | 同上（ラウンド毎に読み直しが乗るため） | **ただの既定値** |
| 既定でツール無効・`readonly: enforced` | **R1「止めない」**＝ agent-tools 契約への完全適合（親文書 §0.1） | 契約に食い込む |
| `stall-timeout 180` / `first-token-timeout 0`（無制限） | **R2「逐次監視できる」**（同 §0.1） | むしろ緩い方向 |
| 作業ディレクトリの範囲 | どこでもない（プロンプトの一文） | **実効性なし** |

根っこはほぼ全部ハードウェアである。親文書は「ツール実行つきループは別 PC の GPU 機が
使える構成に限定する」（L116-117）としているので、**GPU 機が入るかクラウド CLI が使える
状況なら、agent-ollama を太らせるより役割の割り当てを戻す方が設計の意図に沿う。**

## 3. 検討して却下した案

### 3.1 既定（`command`）に `--tools` を焼き込む — 却下

`readonly: "enforced"` が嘘になる。CLI に `--no-tools` のような打ち消しフラグが無いため
`readonly_args` で戻せず、契約検証（親文書 L440-443「readonly にツールが混ざらないこと」）
に反する。実害の側も大きく、agent-flow の planner / evaluator など**読み取り目的の高頻度
経路**にまで無条件のシェルが付く。

### 3.2 会話の途中でツールを開示する（素朴版） — 却下

「モデルが要求したら、その時点でシステムプロンプトへツールを足す」形。**先頭キャッシュを
壊すため、削ろうとしたコストが逆に増える。**

現状はラウンド 2 以降、差分だけを読み直せば済んでいる（親文書 L291 の実行例
「in=+412tk（接頭辞キャッシュ命中）」）。システムプロンプトを書き換えると先頭が変わり、
**そのラウンドで会話全体を読み直す**。CPU では数分の追加になる。つまり「初回 1 回だけ
払う固定費」を「開示のたびに全額払い直す変動費」に変換してしまう。

**ただしこれは実装形態の問題であって、発想の否定ではない。** 会話の**末尾に追記**する形
なら先頭は保たれる。この区別が §4.4 の不変条件になる。

### 3.3 ツール選択を LLM に判断させる（planner を置く） — 却下

二重に破綻する。(a) 選ばせるには候補一覧を見せる必要があり、それが削ろうとしていた
読み込み時間そのもの。`ollama_skills.py:5-6` が却下した形と同一である。(b) CPU では
追加の問い合わせ 1 回が数分かかる。

## 4. 採用する設計

### 4.1 全体像 — 部品は 2 つ、どちらも既存の継ぎ目に挿す

```
プロンプト前処理（ラウンド開始前・1 回だけ）
  ├ スキル展開        ollama_skills.expand()      ← 既存
  └ 初期ツールセット注入  ★部品1                    ← 新規
        ↓  ここまでで固定プレフィックスが確定する
ループ核 run_loop（ラウンドを回す）
  ├ ContextTracker    文脈の配分を決める            ← 既存
  └ ToolPolicy        権限の昇格を決める  ★部品2    ← 新規
```

**新しい層は作らない。** 部品 1 はスキル展開と同じ場所、部品 2 は `ContextTracker` と
同じ継ぎ目に座る。

### 4.2 部品 1 — 初期ツールセットの注入（前処理）

#### なぜスキルと同じタイミングなのか

スキル展開は `ollama_adapter.py:313` の `expand()` で、ループ分岐（同 `:328`）より前・
LLM 呼び出し前に 1 回だけ走る純粋な前処理である。同じ位置にツール定義を差すと
**ラウンド 1 が始まる前に固定プレフィックスが確定する**ので、以降のラウンドは全部同じ
先頭を見る。§3.2 の問題が構造的に起きない。

同時にスキル方式の 3 性質をそのまま継承する:

- **未使用時のコストが正確にゼロ**（親文書 補遺2 L376 と同じ性質）
- **決定的** — モデルに選ばせない
- **契約に載る** — `write_args` は argv 配列なので定義ファイルだけで役割別に変えられる

#### ツールの表現はテキスト規約のままにする

親文書 L242-243 は「`/api/chat` の tools で read_file / apply_edit / run_command の 3 つ
（スキーマ約 800 トークン）」も挙げているが、**採らない**。

1. 800 トークンは毎ラウンドの固定費。規約方式なら 1 ツールあたり数行で済み、桁が違う
2. 小型モデルの構造化ツール呼び出しは不安定。`--think off` を焼き込んだ理由が
   「qwen3 系の JSON 出力契約の安定化」（親文書 L340）だったのと**同根の問題を呼び込む**

結果、「ツールセット」の実体は **許可コマンドの語彙 + 規約数行** になる。既存の
`extract_command`（コードブロック抽出）がそのまま使える。

#### 指定方法

`--tools` を真偽値から**セット名**を取る形へ拡張する（引数なしは後方互換で `bash`）。

| セット | 許可する操作 | 想定 | 状態 |
|---|---|---|---|
| `read` | 読み取り系コマンドのみ（`cat` `ls` `grep` `find` `git log` 等） | 探索つき調査・レビュー | 実装済み |
| `edit` | `read` + 作業ディレクトリ内のファイル書き換え | 対象が特定済みの修正 | 未実装（名前だけ受けて明示的に断る） |
| `bash` | 制限なし（現行の挙動） | 従来どおり | 既定 |

**強制は実行ゲートで行う。** モデルの自己申告ではなく、`run_command` の手前で語彙を判定
して弾く。これによりプロンプト頼みだった境界が**初めて実際の境界になる**（§1(2) の解）。

### 4.3 部品 2 — ToolPolicy（走行中の昇格）

#### 座席は既にある

`run_loop` は `tracker` を外から受け取り、毎ラウンド観測して実行そのものを変えている
（`ollama_loop.py:484-494`）:

```python
allowed = max_output_chars
if tracker is not None:
    room = tracker.remaining_chars()
    if room < _MIN_TOOL_OUTPUT_CHARS:
        emit("context_exhausted", ...); break     # 走行を止める判断まで持つ
    allowed = min(allowed, room)
```

ループ核は戦略を知らず、判断は注入されたオブジェクトが持つ。親文書 L251-257 の
「ループ核は描画を知らない・イベントを出すだけ」と同じ分離である。ToolPolicy は
**この継ぎ目にそのまま座る**:

```python
def run_loop(model, task, *, tracker=None, policy=None, ...)
```

呼び出し側も `make_tracker(model, opts)` の隣に `make_policy(opts)` を置くだけで済む。

#### 責務と非責務

| これは | これではない |
|---|---|
| 決定的な**昇格ゲート**。単調に増える権限集合を持つ状態機械 | planner（§3.3 で却下） |
| 判断材料は観測イベントのみ。LLM 呼び出しゼロ | モデルへの問い合わせ |
| 標準ライブラリのみ・100 行前後 | 新しい依存 |

#### 遷移のきっかけは 2 つだけ（どちらも決定的に検出できるもの）

1. **語彙外コマンドが実行ゲートで弾かれた** — モデルが現在の権限の外を要求した証拠
2. **モデルが明示マーカーを出した**（例 `NEED_WRITE`）— `_DONE_MARKER` /
   `TASK_COMPLETE` と同じ検出方式。正規表現 1 本

自然文からの推測はしない。スキルの発動条件（親文書 補遺2 L378「どちらも決定的に検出
できるもの。自然文からの推測はしない」）と同じ厳しさで書く。

#### 付与のみ・剥奪なし（単調増加）

剥奪は既出テキストの書き換え（＝全部読み直し）か否定文の追記（＝小型モデルが混乱）に
なるため、**走行中に権限を戻さない**。走行は `max_rounds` で有界なので実害はない。
副産物として権限が振動せず、監査もしやすくなる。

#### 昇格試行に予算を切る

現状、規約外の応答には `_MAX_NUDGES = 2` の上限がある。ゲート拒否を無料にすると、
モデルが 12 ラウンドを権限の探りだけで焼き切れてしまう。**同じ形の上限**を持たせる。

#### 昇格をイベントに出す

R2（親文書 §0.1）は「証拠を常時出せること」が要件で、実体は JSONL ログである。
`tool_grant`（付与した語彙・きっかけ・ラウンド番号）を emit しないと、**台帳から
「なぜこの走行が書き込み権を得たか」を復元できない。** ローカル産の成果はクラウド復帰後の
再実行判定に使う前提（同 L43-46）なので、ここが空白だと判定材料が欠ける。
`session_log` を agent-audit collect に載せる話（同 L346-347）とも直結する。

### 4.4 不変条件 — 追記のみ（最重要）

**開示は必ず会話の末尾に新しいメッセージとして足し、既出部分は 1 バイトも書き換えない。**

これは様式の好みではなく、性能そのものである。追記は通常ラウンドがツール結果でやって
いることと全く同じなので、**昇格 1 回のコストはツール出力 1 回とほぼ同じ**（差分読み込み
だけ）。逆に先頭を触った瞬間に全再読み込みが発生する（§3.2）。

親文書の promptcompose「安定プレフィックス化」（L151-153）と同じ思想であり、
**ラウンド毎の開示が実質タダになるのはこの条件下でだけ**である。

## 5. データ契約への載せ方

`write_args` は argv へそのまま連結される文字列配列なので、**エンジン改修ゼロ**で
役割別のツールセットを宣言できる。

```jsonc
// agents/ollama.json（調査用に読み取り探索だけ許す例）
{
  "write_args": ["--tools", "read"],
  "readonly_args": [],          // 空のまま＝ readonly は道具ゼロ
  "readonly": "enforced"        // 宣言の真実性は保たれる
}
```

同じ理屈で `--max-rounds` や `--command-timeout` も定義ファイルから足せる
（どちらも環境変数を持たないフラグなので、**ここが一番安く効くレバー**）:

```jsonc
"write_args": ["--tools", "bash", "--max-rounds", "30", "--command-timeout", "900"]
```

`interactive` 側は `write_args` を**継承しない**設計になっている（`agentcli.py:215-217`
「トップレベルの write_args はヘッドレス専用の危険フラグを含むので継承しない」）。
TUI を最初からツール有効で開きたい場合は `interactive.write_args` に明示する。

## 6. 他の部品との相互作用

### 6.1 スキルとツールセットは暗黙に結合する（要対処）

`ollama_skills.py:107-115` の `_render()` は `{skill_dir}` を実パスへ置換する。目的は
SKILL.md が同梱 `scripts/` を叩けるようにすることで、コメントにも「`--tools` では、
この実パスを使って scripts/ をそのまま叩ける」とある。

したがって **汎用シェルを含まないセット（`read` / `edit`）を選ぶと、スクリプト同梱型の
スキルが黙って動かなくなる。** 両者は同じタイミングで注入されるので整合は展開時に判定
できる。`--skill` の解決失敗と同じく **env 分類で即失敗**させる（黙って無視しない。
`ollama_skills.py:121-122` の方針と揃える）。

### 6.2 ラウンド予算

昇格が 1 ラウンドを消費すると、そのぶん本来の作業に使えるラウンドが減る。§4.3 の
「昇格試行の上限」と `max_rounds` は同じ予算を奪い合う関係にあるので、セットを
`read` 起点にする運用では `--max-rounds` を併せて引き上げるのが現実的。

### 6.3 作業ディレクトリの実効化

`--cwd` で使い捨てワークツリーを指すと、プロンプト頼みだった範囲制約が**プロセスの
起点で実際の境界になる**。実行ゲート（§4.2）と併せると、**上限値を大胆に緩めても
実害の範囲は狭まる**——これが §2.4 の「厳しさが入れ替わっている」問題に対する
交換条件になる。

## 7. 段階的な導入

各段は独立して価値があり、前段だけで止めてもよい。

| 段 | 内容 | 規模 | 得られるもの | 状態 |
|---|---|---|---|---|
| 1 | `write_args` に `--max-rounds` 等を足す | 定義ファイルのみ | 既定値の窮屈さが即座に解消。契約は無変更 | 実装済み（30 / 900） |
| 2 | `--tools <セット>` と実行ゲート（部品 1） | ゲート判定 + 規約数行 | 中間の権限段。cwd 制約の実効化 | 実装済み（`read`） |
| 3 | ToolPolicy（部品 2） | 約 100 行 + イベント 1 種 | 走行中の昇格。台帳に根拠が残る | 未着手 |

段 2 の実装では昇格が無いぶん、ゲート拒否は「実行せず理由を末尾追記で返す」で完結する
（`tool_denied` イベント + `_MAX_DENIALS` の予算 + 走行停止）。段 3 を入れるときは、
この拒否の検出点がそのまま遷移のきっかけ 1（§4.3）になる。

**既定は常に現行の挙動**（`policy=None`・`--tools` 引数なしは `bash`）とする。
R1 の契約適合を動かさないための条件。

## 8. 非目標・決めていないこと

- **速いローカル推論を作ることは目標ではない**（親文書 §0.1）。本書の変更はどれも
  読み込み時間をほぼ増やさないが、減らしもしない。
- **ツールセットの語彙の具体的な中身**（どのコマンドを `read` に入れるか）は本書では
  確定させない。実行ゲートの判定方式（コマンド名の前方一致か、パーサを持つか）と
  併せて実装時に決める。パイプやリダイレクトを含む文字列の安全な判定は自明ではなく、
  ここを甘く作ると `read` セットの保証が形だけになる——**§7 の段 2 で最も注意を要する箇所**。
- **クラウド CLI への自動フォールバック**は範囲外（親文書 §0.1 のとおり切替は手動）。
