# エージェント CLI プラグインと失敗トリアージ — 設計書

> **対象系統**: `agent-project` / `agent-flow` / `agent-amigos` / `agent-loop` /
> `agent-dashboard` / `agent-audit`（CLI チャット・Doctor・cowork の tmux 実行を含む）。

> 契約（探索順・全フィールド・ローダ API・エラークラス・同梱定義）は
> [`docs/specs/agent-cli-spec.md`](../specs/agent-cli-spec.md)、スキーマの正典は
> [`schemas/agent-cli.schema.json`](../../schemas/agent-cli.schema.json)、追加手順は
> [`agents/README.md`](../../agents/README.md)。本書は**なぜそう決めたか**だけを書く。

---

## 1. TL;DR

エージェント CLI の呼び出しを**リポジトリ内で共通化したデータ契約**で差し替え可能にし、
あわせて失敗を**決定的にトリアージ**（誰が直すか分類）する仕組み。契約が覆う軸は
「CLI × モード（ヘッドレス / 対話）× 権限（書き込み可 / 読み取り専用）」の 3 つ。

**受入条件は 1 つだけ——CLI の挙動・作法が変わったとき、修正が `agents/<name>.json`
1 ファイルで完結すること。**以下の設計判断はすべてこの 1 点から導いている。

| 判断 | 要約 |
|---|---|
| §3.1 | 起動知識を JSON のデータ契約へ畳む。コード側にフォールバックテーブルを持たない |
| §3.2 | 組み込み名を予約しない。上位ディレクトリの同名定義が同梱定義に勝つ |
| §3.3 | ローダは言語ごとに 1 実装。JS の第二実装はゴールデンテストで縛る |
| §3.4 | 用途別の振り替えは知識を 2 つに割る。定義が変種を申告し、エンジンが対象用途を宣言する |
| §3.5 | 失敗トリアージは正規表現だけ。LLM を使わない |

---

## 2. 背景と課題

**起動知識が 8 か所・4 実装に散っていた。** `agent_cli` は kiro / claude / copilot / codex の
ハードコード 4 択で、cursor / ollama を足すには各ツールのコードを触る必要があった。しかも
未知の値は**黙って kiro-cli に落ちる**——設定ミスに気づけない。散らばりは agent-project /
agent-flow / agent-amigos の Python 3 実装 + dashboard の JS に及び、**同じ CLI でも用途によって
argv が違う**（書き込みありの act と、助言のみの Doctor で権限フラグが別）。旧契約は
ヘッドレス片道・書き込み可の 1 マスしか表現できず、対話起動・読み取り専用フラグ・入力受付検出は
各所のコード分岐に残っていた。

**失敗の扱いが「なんでもリトライ・なんでも人へ」だった。** 認証切れ・利用上限のような環境要因は、
どのタスクをリトライしても同じ理由で落ちる。実際 codex の利用上限で 26 ノードがリトライを
焼き尽くし「理由不明の全滅」になった。逆に一時的エラーまで人へ回すと判断待ちが濫造される。

### 2.1 非目標

- **実行の隔離**。このレイヤは argv を組み立てるだけで、読み取り専用フラグを無視する CLI への
  防御は持たない。責務が「argv の組み立て」から「実行の隔離」へ膨らむと、いま畳んだ散らばりが
  別の場所に再発する。保証できないことは宣言して人に見せる（`readonly: best-effort`）。
- **依存の追加**。プラグインは stdlib（json / re）だけで読める。dashboard も同じ理由で
  JSON 定義のみを読む。

## 3. 主要な設計判断

### 3.1 起動知識は JSON のデータ契約へ畳み、コード側に控えを持たない

**判断**: 1 CLI = 1 ファイル `agents/<name>.json`。**組み込み 4 択も定義ファイルにし、
コード側のフォールバックテーブルを持たない。**未知の `agent_cli` で定義も無ければ明示エラーにする
（黙って落ちるフォールバックは廃止）。

**文脈**: 「JSON も読むが、既知の CLI はコードの表を優先する」という折衷案が最初に出た。
移行が段階的にできて安全に見える。

**却下した選択肢**:
- *コード側にフォールバックテーブルを残す* — 「JSON を直したのに古い挙動のまま」という
  二重管理が別の形で戻る。受入条件（1 ファイルで完結）が最初から成り立たない。定義が
  見つからなければインストールの破損として明示エラーにし、`install.sh` 再実行へ誘導する。
- *未知の値を既定 CLI へ落とす* — これが元の罠。設定ミスが「なぜか kiro で動いている」という
  分かりにくい症状で出る。

**トレードオフ**: 唯一の例外は cowork の定常業務 tmux 実行（`cowork.js:coworkChatLaunch`）で、
定義解決に失敗しても既定コマンドへ落として定常業務を止めない。**ただし黙ってはいない**——
`console.warn` で元エラーのメッセージを残す。人の日常業務を止める副作用のほうが、この 1 か所では
沈黙のコストを上回ると判断した。

**確信度**: 高。同梱定義は 4 → 13 に増えたが、消費側のコードは増えていない。

### 3.2 組み込み名を予約しない

**判断**: 探索順は `$KIRO_AGENTS_DIR` → `<プロジェクトルート>/agents/` → `~/.agents/agents/` →
`~/.kiro/agents/` → 同梱定義（最後の候補）。同名は**先勝ち**で、上位に `claude.json` を置けば
同梱定義を上書きできる。

**文脈**: 当初は「組み込み名は予約し、ユーザー定義は別名でのみ足せる」案だった。同梱定義の
整合性を守れるので安全に見える。

**却下した理由**: それだと「claude の作法が変わったので手元で直したい」が
`claude-fixed.json` を作って全設定の `agent_cli` を書き換える作業になる。受入条件
（JSON 1 ファイルで完結）が壊れる。同梱定義は**最後の候補**であって特権ではない。

**トレードオフ**: 手元の上書きが同梱定義の更新を隠しうる。**現状これを見せる口は無い**——
探索順が表示されるのは「定義が見つからなかった」エラーのときだけで、解決に成功したとき
どのパスが勝ったかは出ない（§7 の未実装）。探索順を伸ばさないことで被害を抑えている:
ユーザー共通の定義は `~/.agents/agents/` だけを読み、旧 `~/.agent` ホームへはフォールバック
しない（探索順が長いほど「どれが効いたか」が読めなくなる）。

**確信度**: 高。

### 3.3 ローダは言語ごとに 1 実装。第二実装はゴールデンテストで縛る

**判断**: Python 側は `agentcore.agentcli`（load / headless_cmd / interactive_cmd / classify_error）に
集約し、agent-project / agent-flow / agent-amigos / agent-loop がこれを使う。dashboard（JS）だけは
自前ローダのままとし、**同一定義に対して Python と同じ argv を返すことをゴールデンテストで固定する。**

**文脈**: 当初の方針は「各ツールが自前の小さなローダを持つ」だった。依存が増えないので軽い。
これを Python 側について取り下げた——git URL 正規化を 3 者が自前実装して吸収規則が食い違った
前例と同型で、`{model}` 省略規則や空応答の扱いが実装ごとにずれると、**同じ定義ファイルが
ツールによって別の argv になる**。

**却下した選択肢**:
- *JS 側も agentcore を呼ぶ（Python を subprocess 起動）* — dashboard の UI 応答性が
  subprocess 起動 1 回分に縛られる。CLI チャットの起動は人が見ている前で走る。
- *JS を正典にして Python が従う* — 消費側 4 実装が Python で、1 実装が JS。多数側を正典にする。

**トレードオフ**: JS の第二実装は書き続ける必要がある。代わりにゴールデンテストが**機械で**
一致を強制する（同じ判断の一般形は [`agentcore-design.md`](./agentcore-design.md) §3.5）。
agent-loop も第二のローダを書かず、`install.sh` が zipapp へ agentcore を同梱する。
agentcore を解決できない環境では `agent_cli` 指定だけが使えず明示エラーになる。

**確信度**: 高。

### 3.4 用途別の振り替えは、定義とエンジンで知識を 2 つに割る

**判断**: 定義は `variants`（用途名 → 代わりに使う定義名）を申告する。エンジンは自分が扱う用途の
集合（agent-flow の `VARIANT_ELIGIBLE_ROLES`、agent-project の `JSON_CONTRACT_PURPOSES`）だけを
このマップへ問い合わせる。**どちらも自分が知っていることしか言わない。**

**文脈**: ツールループ前提の定義（`ollama`）を JSON 契約の役割にそのまま使うと、本文の代わりに
制御語だけが返って空応答で落ちる。この組み合わせを人の設定作業に頼らず塞ぎたかった。

**却下した選択肢**:
- *エンジンが CLI 名で分岐する* — `if agent_cli == "ollama"` を消すために契約を作ったのに、
  それを消費側 5 つへ書き戻すことになる。
- *エンジンが `variants` の全キーを無条件に使う* — キーが存在するからといって、どの呼び出し元でも
  振り替えてよいわけではない。agent-project 独自の `verify` purpose は寛容パーサ + 証跡の本文を
  伴うため対象外のままにしてある。エンジンが宣言する側にいないと、この線が引けない。
- *振り替えを連鎖させる* — 1 段だけにした。連鎖を許すと設定ミスがループになる。指す先が
  存在しない・自分自身を指す申告は無視して元の定義で走る（設定ミスで実行を殺さない）。

**トレードオフ**: 定義側の語彙とエンジン側の語彙が独立に育つので、片方にしか無い用途名が
生じうる。**これは意図的に許している**——新しい用途を扱うエンジンが先に出ることも、定義が
先に用途を備えることもある。無視して元の定義で走る挙動があるので、ずれても壊れない。

振り替え後のモデルは、呼び出し元が明示指定していなければ**変種自身の `default_model`** を使う。
用途専用のチューニングを base のモデル指定で上書きさせないため（例: `verify` → `ollama-verify`・
`gemma4:12b`）。

**確信度**: 高。

### 3.5 失敗トリアージは決定的。LLM を使わない

**判断**: エラー本文（プラグインの `errors` → 汎用パターンの順）から「誰が直すか」を分類し、
メッセージ先頭の機械可読タグ **`[agent-error:<class>]`** で全層に運ぶ。判定は正規表現だけ。

**文脈**: 「失敗の原因を LLM に読ませて分類する」案があった。表現の揺れに強く、規則を書かずに済む。

**却下した理由**: **分類したい失敗の大半は、LLM が使えない理由で起きている。**認証切れ・利用上限は
まさにその CLI が呼べない状態で、分類のために同じ CLI を呼べば同じ理由で落ちる。分類器が
壊れているときにこそ分類が要る。

**トレードオフ**: 正規表現は表現の揺れを取りこぼす。**迷うものはタグ無し＝「内容の問題」に倒し**、
従来のタスク単位フロー（retry → 裁定 → 人）に委ねる。取りこぼしは「従来どおり」になるだけで、
誤分類は「環境要因でないものを環境要因として全 run を止める」——非対称なので安全側が決まる。

ヒントは**実際に一致した規則から**採る。クラス一致で引くと、ある CLI に足した規則の案内文が
別 CLI の失敗に付く（実際に踏んで直した潜在バグ）。

**確信度**: 高。実運用で 26 ノード全滅の再発は無い。

## 4. トリアージが 3 層でどう効くか

`control` / `quota` / `auth` / `env` の 4 クラス（クラス定義は
[仕様書 §6](../specs/agent-cli-spec.md)）は、表示上は「実行制御による停止」と「環境要因の失敗」に
分かれるが、打ち切り・needs 化の仕組みは共通で、3 層が同じタグを読む。

1. **agent-flow**（`_continue` → `_env_failure_reason`）: 環境要因の失敗ノードが 1 つでもあれば
   **再計画せず run を即 failed で終端**する（`meta.failure_reason` にタグ付き理由）。全ノードで
   リトライを焼き尽くす無駄を止める。done ノードは温存＝再開で続きから。
2. **agent-project**（`_settle_failure`）: vmsg と `last_run` の meta / final からタグを読み、
   **リトライを消費せず・裁定（これも LLM＝同じ理由で失敗する）も呼ばず**、原因と直し方を
   明記して needs へ。環境を直して approve すれば同じ run の続きから再開する。
3. **dashboard**（`runAdvice`）: `failureReason` のタグを読み、タスク状態より先に
   「🔑 認証切れ — 再ログイン後、要対応タブで承認すると続きから再開」と言い切る。

`quota` は、当面戻らない `exhausted` と復帰時刻を持つ `rate_limit` に細分する。後者は本文から
`reset_at` を決定的に抽出し、node-budget の観測行へ載せて復帰後の候補復帰に使う。

## 5. 契約の形に残った小さな判断

痕跡だけが残っていて、読み返すと理由が分からなくなるものを書き残す。

**権限フラグを `write_args` / `readonly_args` の対にした**のは、「`readonly_args` を足すだけ」で
済まなかったからだ。kiro の `--trust-all-tools`（書き込み可）と `--trust-tools=`（読み取り専用）は
追加ではなく**排他**で、両方並べると「後勝ち」に賭けることになる。`readonly_args` /
`no_session_args` をトップレベルに置いたのは、読み取り専用がヘッドレスの Doctor や構造化 Assist でも
要るから。逆に `interactive.write_args` は継承しない——ヘッドレス用の強い権限フラグ
（claude の `--dangerously-skip-permissions` 等）を対話へ黙って持ち込まないためで、対話で要るものは
明示させる。

**`busy_pattern` を `ready_pattern` の拡張でなく別フィールドにした。**「ready にマッチしない ＝
処理中」という推論は、入力欄を常時表示する TUI（claude の `(esc to interrupt)` 等）では成立しない
——ready は処理中もマッチし続ける。否定を 1 本の正規表現に押し込むより、「処理中の正の検出」を
独立に宣言させて優先順位（busy ＞ ready ＞ 静穏 ＞ 既定 busy）をコード側で固定するほうが、
定義の読み書きも判定の説明もまっすぐになる。どちらのパターンも持てない CLI は
`idle_quiet_sec`（画面が N 秒変化しなければ待機）で判定する。

**`headless_autonomy` は定義に申告させ、他フィールドから推測しない。**`interactive` の有無・
`file_flag` の有無・`write_args` にツール系フラグがあるか、どれも相関はあるが根拠にはならない。
推測で決めると、定義を足した人が意図と違う経路へ振り分けられ、しかもそれが実行時の
「着手しない」という分かりにくい症状で出る。**未宣言は安全側の `single-shot`**——ツールループを
余計に供給しても仕事は進むが、必要な供給を落とすと何も起きないまま静かに空振りする。

**`interactive` の有無を「使えるかどうか」の判定に使わない。**かつて agent-loop は `interactive` 節の
無い定義を起動時 fail fast にしていたが、対話セッションは**会話を人に見せるための可視化**であって
実行の必須要件ではない。判定に使うべきなのは「対話 argv を組めるか」（＝経路の選択）であって、
「この CLI が使えるか」ではない。

**`prompt_inject` は当初 `interactive.prompt_via` という名前だった。**トップレベルに既にある
`prompt_via: stdin|argv` と同名で enum だけ違う入れ子になり、誤設定が静かに効かないだけで
気づけないので改名した。`file` 方式は当時どこにも実装が無かったが、対話診断がスナップショットを
渡す経路として必須になるのが分かっていたので、後追いにせず先に契約へ入れた。

**対話セッションの副作用は許容する。**対話は人が画面を見ながら操作するもので、副作用は人の
責任範囲。制限すると CLI チャットや定常業務の現行用途が壊れる。例外は診断だけで、
`readonly_args` + `no_session_args` で開き、tmux セッション名も `agent-doctor-` 接頭辞の別系統に
分ける——読み取り専用のつもりの窓が作業セッションへ合流すると、そこから書き込みができてしまう。

**退避（spill）は 2 つあり、寄せない。**定義の `spill` は退避時に権限フラグを**置き換える**もので、
kiro-cli の「positional プロンプトを渡すと stdin を読まない」癖のデータ化。もう 1 つは argv 長制限
（OS の `ARG_MAX`）の退避で、`agentcore.agentcli.spill_prompt` が担い**権限フラグには触らない**。
前者をヘッドレス実行（検証・分解・裁定）に掛けると、退避したときだけコマンドを 1 つも実行できず
検証が全基準「検証不能」に倒れる。見ているものが CLI の癖か OS の上限かで、層が違う。
**寄せる案は採らない**（P2-5 の決着）——`spill.instruction` は権限置換とセットの機構だから。
代わりに `spill_prompt` 側の指示文は `agentcore.agentcli.spill_instruction` が枠だけを持ち、
呼び出し側は「何の全文か」だけを渡す（3 者が全文を自前で持つと、言い回しの改善が 1 か所にしか
入らず、入っていない方は誰も気付かない）。

## 6. 不変条件

- 分類は**決定的**（正規表現のみ・LLM 不使用）。迷うものはタグ無し＝「内容の問題」に倒す。
- トリアージは「止める・人へ知らせる」方向にのみ働く。done を作らない・予算を破らない
  （agent-project 設計書 §1 の不変条件に従属）。
- プラグインは stdlib（json / re）だけで読める。
- CLI の挙動・作法の変更は `agents/<name>.json` 1 ファイルの修正で完結する（受入条件）。
- 読み取り専用の**防御**はこの層に持たない。保証できないことは宣言して人に見せる。

## 7. 未実装として残っているもの

- **解決元パスの可視化**。定義が複数階層で見つかりうる（§3.2）のに、解決に成功したとき
  どのパスが勝ったかを人が確かめる口が無い。探索順が出るのは失敗時のエラーだけ。
  手元の `~/.agents/agents/claude.json` が同梱定義の更新を隠していても気付けない。
  被害が出るのは「同梱定義を更新したのに反映されない」場面に限られるので、
  実際に踏むまで着手していない。
- **`headless_autonomy` の宣言と実態の突き合わせ**。`single-shot` と申告した定義が実は
  ツールループを持っていても、誰も検知しない。宣言を信じる設計（§5）を選んだ以上、
  嘘の申告は静かに「余計なツールループを供給する」形で出る——仕事は進むので害は小さい。

## 付録. viewer の executor 連動

run の `meta.executor` を orchestrator が記録（`note_executor`）し、viewer は
`run.gitlabish`（executor === 'gitlab'、旧 run は証跡から推定）で外部フォージ連携 UI の表示を
切り替える。既定の executor を使っている run に、使っていない機能のボタンを並べないための
表示制御であって、CLI 契約の一部ではない。
