# codd-agent 設計 — 実装と設計書の一貫性を保って変えるステートマシン

- 実装: `tools/codd-agent/`（配布物は `machine/`、置き先では `.statemachine/codd/`）
- 使い方: [`tools/codd-agent/README.md`](../../tools/codd-agent/README.md)
- [codd-gate](./codd-gate-design.md) とは別物。codd-gate は 1 リポジトリ内の doc↔code↔test のドリフトを受け入れ前に**止める**
  決定的ゲート、codd-agent は実装と設計書をまたいで変更を**練って確かめてから入れる**ステートマシン。
  codd-gate のうち、1 回の変更の中で決まるもの（パスのつながりと、その壊れ）だけを取り込んだ（§4.1・§8.1）
- 名前: ツールとしては codd-agent。置き先の名前（`.statemachine/codd/`・`codd.json`・`.codd/`・`codd.py`）は
  `codd` のまま据え置く。すでに置いたリポジトリの設定と、エージェント名 `codd` を壊さないため

## 1. 目的と前提

実装と設計書が別リポジトリ（別フォルダ）にあり、片方だけが直されてもう片方と食い違う。
codd-agent は、片方を変える前に**参照先を読み、自分の現状とのずれを見せ、了承を得てから変える**。
ずれを解消するために参照先を変える必要があれば、その変更案と自分への影響範囲まで見せたうえで両方を変える。

- 同じ定義を両リポジトリに置く（対称）。違いは `codd.json` の `side` と `refs`（と `skills`）だけ。
  実装で動かせば参照先は設計書、設計書で動かせば参照先は実装。参照先はいくつでも持てる。
  同じリポジトリの別フォルダを参照先にしてもよい（§5.5）
- 参照先のパスは手で設定する（自動発見しない）
- 計画を練るとき・変えるときに使うスキルを、リポジトリごとに設定できる（§5.3）
- **できるだけ単純なハーネスにする**。主の流れは plan → confirm → apply → done の 4 つで、止まったときの stuck と
  やめたときの stopped を足した 6 ステート。回をまたぐ状態は持たない（作業ファイルは `.codd/`、残すのは計画の記録だけ）
- **1 回の実行は 1 つの会話で終わる**（§1.1）
- **プロジェクトを選ばない**。依存は python3 と git だけで、言語・ビルド・フォルダの切り方を前提にしない。
  プロジェクトごとの違い（検査コマンド・使うスキル・受け持つフォルダ・1 回の上限）は `codd.json` に寄せる
- **モデルの申告を信じない**。一貫性に効くこと（根拠が実在するか・計画どおりのファイルだけを変えたか・
  影響範囲）はスクリプトが測り、測れない判断（分類・変更案）だけをモデルに任せる。
  出力だけでなく、入力（影響箇所の見つけ漏れ）と過程（決まり・スキル・道具を使ったか、最後までやったか）も止める（§1.2）
- 参照先と自分の探索には graphify を使えるときは使い、グラフは自動で作り直す

### 1.1 1 回の実行で終わる

コードや文書についてやりたいことを 1 つ受け取り、計画・確認・変更・結果の報告までを 1 つの会話の中で終える。
途中の状態を次の会話へ持ち越さない（§8）。そのために、計画の大きさを入口で絞る。

- 計画が変えるファイル（自分の変更案・参照先の変更案・「変更不要」でない影響範囲・テストの変更案）の数が `max_files`
  （既定 60）を超えたら verify-plan が落とす。モデルはやりたいことを絞り、残りを計画の「今回やらないこと」に書く
- 変える段階（apply）は `batch_files`（既定 10）ずつの段に分ける（下記）
- done は「今回やらないこと」を、次の回にそのまま渡せる形で利用者に伝える。続きは新しい実行として始める

上限はファイル数で測る。行数やトークンはモデルと言語で意味が変わるが、ファイル数は計画から決定的に数えられ、
変更・確認・検査の手間とおおむね比例する。

上限を 20 から 60 に上げ、apply を段に分けた理由: 計画は影響範囲とテスト（§4・§4.2）まで漏れなく挙げさせるので、
小さな依頼でもすぐ 20 に届いた。絞ろうとして「今回やらないこと」に回しても、測った影響範囲が計画に戻ってきて
検査が通らず、練り直しの輪から抜けられなかった。一方で、多くのファイルを 1 回の apply で変えさせると、モデルは
途中で変え残す。そこで計画（どこまで変えるか）と apply（1 回にどれだけ変えるか）の大きさを分けた。

- verify-plan が通ると、変えるファイルを変える順（自分の変更案・参照先の変更案・影響範囲・テストの変更案。同じ見出しの
  中はパスの順で、同じフォルダが続く）に並べて `batch_files` ずつに区切り、`.codd/batches.json` に控える
- apply は `codd.py batch` で今の段のファイルを読み、それだけを変える
- verify-apply は、途中の段ではその段までのファイルをすべて変えたかだけを見て、通れば段を進めて第 1 行 `MORE` で終わる。
  ステートマシンは `equals:check_ok:true;startswith:check_output:MORE` で apply へ戻る。変え残しはその段で止め、
  stuck が訊かずにやり直す（変え残しは人の判断が要らない）。最後の段では今までどおり全体を検査し、テストと検査コマンドを動かす
- テストと検査コマンドを途中の段で動かさないのは、段の途中では実装と仕様・テストがそろっておらず、落ちて当然だから

### 1.2 入力・過程・出力を確かめる

| 段 | 失敗の形 | 止め方 | 節 |
|---|---|---|---|
| 入力 | 影響箇所を見つけ損ねる（呼び出し元・同じ名前に触れる設計書） | 計画の名前から自分と参照先の両方を測り、計画が扱っていなければ落とす | §4 |
| 入力 | 名前は一致しないが、パスで指し合っているファイルを見落とす | 変えるファイルとつながったほかの側のファイルを、計画が扱っていなければ落とす | §4.1 |
| 入力 | 参照先を読まずに「なし」で済ませる | 参照先ごとに `explore` を求め、文字列の一致で見つかったファイルを計画がすべて扱うまで落とす | §6 |
| 入力 | 読んでいないものを根拠にする | 根拠のパス・行・見出し・名前の実在 | §6 |
| 過程 | プロジェクトの決まりを読まない | 決まりのファイルを自動で挙げ、`codd.py rule` で読み込ませ（中身のハッシュを控える）、計画にすべて挙げさせる | §5.7 |
| 過程 | 決めたスキル・道具を使わない | 設定したものを、計画と `.codd/apply.md` にすべて挙げさせる | §5.7 |
| 過程 | 途中で止まる | 計画のファイルをすべて変えたか。終わりの報告はスクリプトが作る | §7・§5.8 |
| 出力 | 計画に無い変更・影響の直し忘れ | 計画外のファイルを落とす。実際の差分から影響を測り直す | §4・§7 |
| 出力 | 書いたパスが無い・消したファイルを指したまま | 変えたファイルの足した行のパスと、消したファイルを指すところを調べる | §4.1 |

スキル・道具を使ったかは、使った記録を求めることでしか確かめられない（スクリプトからエージェントの道具の呼び出しは
見えない）。記録は名前だけでなく「何に使い、何を得たか」を求め、確認（confirm）で利用者が読む。実行結果そのものを
確かめたいものは `check` に入れ、ハーネスに実行させる。

## 2. 流れ

```
plan ─[check: verify-plan]→ confirm ─┬─ OK ─→ apply ─[check: verify-apply]→ done
  ↑  │                               ├─ NG ─┐         │
  └──┼───────────────────────────────┼──────┘         │
     │                               └─ STOP → stopped（何も変えずにやめる）
     │ 検査がやり直しを使い切っても落ちる                  │
     └──────────────→ stuck ←─────────────────────────┘
                        ├─ PLAN  → plan（練り直す。変えた分は残すか rollback で戻す）
                        ├─ APPLY → apply（計画はそのままで変え直す）
                        └─ STOP  → stopped（やめる。結果を伝える）
```

| ステート | すること | 成果物 | 成否の測り方 |
|---|---|---|---|
| plan | 参照先を探し（`explore`）、前提・制約・その他に分け、自分の現状とのずれを見て、自分の変更案を練る。ずれがあれば参照先の変更案と影響範囲を書く。どちらのリポジトリも変えない | `.plans/日時-名前.md` | `check: verify-plan`（影響範囲の測定を含む） |
| confirm | 計画の要約（`summary`）と測った影響範囲を見せ、利用者の答えを待つ。全文は貼らずパスを示す | 答え（`OK` / `NG` と指摘 / `STOP`） | `output_validator` |
| apply | 自分の変更案を適用し、参照先の変更案があれば参照先にも適用する。コミットはしない | 両リポジトリの作業中の変更 | `check: verify-apply`（影響範囲の測り直しを含む） |
| done | 変えたファイルを伝え（`report`）、計画を判断の記録として残す（`record`） | `.plans/日時-名前.md` | 終端 |
| stuck | `advise` が示す止めた理由・確かめること・選択肢を見せ、利用者の答えを待つ（人の判断が要らない理由だけなら訊かずに戻る）。戻すと選ばれたら `rollback` を実行する | 答え（`PLAN` / `APPLY` / `STOP` と指示） | `output_validator` |
| stopped | やめたときの結果（`report`）と、残したか戻したかを伝え、計画を記録として残す（`record`） | `.plans/日時-名前.md` | 終端 |

NG は plan へ戻り、次の plan は `{{answer}}`（confirm の答え。NG と利用者の指摘）を踏まえて練り直す。`answer` は `context:` で空に初期化してあり、初回は空になる。
分岐は `condition_rule`（`check_ok` と confirm の第 1 行）だけで決まり、LLM の YES/NO 評価は使わない。
利用者に訊く段（confirm と stuck）は、どちらからでも stopped へ進める。確認でやめたいのに NG しか無いと、
要らない練り直しが始まるため。

変えてよいのは「verify-plan を通り、confirm で退けられていない計画」だけにする。verify-plan が通ると計画の
ハッシュを `.codd/passed-plan` に控え、verify-plan が落ちる・`decide NG` / `decide STOP` で消す。verify-apply は
今の計画がこれと一致することを確かめる。ステートマシンの遷移だけでは、計画の検査で止まった stuck から `APPLY` を
選ぶ道や、apply が計画を書き換えて「変更不要」を足す道を塞げないため（一貫性の判断を利用者が確かめた計画に限る）。
apply の途中で計画を直すときは、plan → verify-plan → confirm を通る（変えた分は残る。2.1 の「やり直しの仕組み」）。

### 2.1 止まったら、次の手を提案して確かめる

計画の検査は、まず同じステートのやり直し（2 回）で直させる。モデルの読み違いはここで直る。変えたあとの検査は
同じステートで再投入しない。テストを含む検査は重く、人の判断が要る失敗（計画に無い変更など）まで再投入すると 1 回ぶん
丸ごと無駄になるので、落ちたらすぐ stuck へ進み、人の判断が要らない理由だけなら stuck が訊かずに apply へ戻す。
使い切っても落ちるものは、多くが**利用者にしか決められない**こと（計画に無いファイルを変えてよいか、測った影響を
「変更不要」としてよいか、今回どこまでやるか）か、利用者にしか直せないこと（設定・環境）である。
前の版はここで `escalate` して実行ごと止めていたので、利用者は何が起きたか・どうすればよいかを自分で探す必要があり、
やり直すには最初から始めるしかなかった。いまは `check_on_exhausted: continue` で stuck へ進み、会話の中で次の手を決める。

- 止めた理由は、検査が落ちるたびに `.codd/problems.json` へ段（plan / apply）と一緒に控える（通れば消す）。
  設定の誤り（終了コード 2）も控える
- `advise` が理由を種類に分け（確かめていない計画で変えた・計画に無い変更・変え残し・影響の直し忘れ・参照先の扱い漏れ・壊れたパス・
  スキルと道具・検査コマンド・大きすぎ・根拠と形・設定）、種類ごとに**利用者に確かめること**と**選択肢**を決定的に出す。
  最初に挙がった理由の勧めを全体の勧めにする。モデルが勧めを作らないので、同じ止まり方には同じ提案が出る
- 理由が人の判断の要らない種類だけ（plan: 未判断・決まり・形、apply: 検査コマンド・変え残し・計画に無い変更・影響の直し忘れ・
  壊れたパス・スキルと道具・形）なら、
  `advise` は選択肢の代わりに `AUTO PLAN` / `AUTO APPLY` を出して答えを控え、stuck は訊かずに同じ段へ戻る。
  段ごとに 2 回まで（`.codd/auto.json`。検査が通れば数え直す）。テストが落ちただけで利用者を待たせないため
- 計画との違いは申告で済ませる: 変える段で計画と違うことをしたら、`.codd/apply.md` の「## 計画との違い」に
  `- パス — 変更不要: 理由` か `- パス — 追加: 理由` と書かせる。計画は書き直さない（書き直すと計画の検査と確認からやり直しになり、
  探す・グラフを作り直す・確かめるが丸ごと走る）。理由付きの「変更不要」は、計画のファイル・響くファイル・響くテストの
  変え残しとして数えない。「追加」は、計画のどこかで挙げたファイル（「変更不要」「関係なし」としたもの・利用者向けに省いたものも
  含む。確認で見せた範囲）なら訊かずに認める。挙げていないファイルだけを `outside` として利用者に 1 問で確かめ、認めれば
  `accept` が `.codd/accepted.json` に控えて apply へ戻る。申告は報告と計画の記録に「変える段で判断」「変える段で足した」
  「利用者が認めた」として残る。変え残し・計画に無い変更・影響の直し忘れは、申告すれば直せるので人の判断が要らない種類に入れた
- 選択肢は 6 つで、段ごとに出せるものが違う（計画が通っていなければ「変え直す」は出さない）

| 選択肢 | 先に実行 | 次 |
|---|---|---|
| 計画を練り直す | — | plan |
| 計画はそのままで、変え直す | — | apply |
| 変えた分は残して、計画を直す | — | plan |
| 変えた分を戻して、計画から練り直す | `rollback`（verify-plan が通ったときの中身へ戻す） | plan |
| 足したファイルを認めて続ける | `accept`（計画で挙げていない追加を認めたと控える） | apply |
| ここでやめる（残すか戻すかも訊く） | 戻すなら `rollback` | stopped |

**やり直しの仕組み。** verify-plan は変える前の印（HEAD と作業中ファイルのハッシュ）に加え、作業中だったファイルの
中身を `.codd/before/` に写す。`rollback` は印から変わったファイルだけを、写しか印の HEAD の中身へ戻し、
印のあとに足したファイルは消す。計画より前から作業中だった変更は、作業中の中身へ戻るので失われない。
途中でコミットされていたら（HEAD が動いていたら）戻さずに知らせる（git の履歴は触らない）。
verify-plan は、同じ計画の印があり、そのあとに変わったファイルがあれば印を取り直さない（印に計画のパスを控える）。
取り直すと、変え終えたファイルが変える前の状態に含まれてしまい、変え残しとして落ちる。前の版は `keep-changes` を
選んだときだけ残していたので、それを選ばずに練り直したときや、練り直しのあとの確認で NG になってもう一度検査したときに
印が今の中身へ取り直されていた。回を終えると（`record`）計画に結果の見出しが付き、次の回は別の計画になるので、
印は取り直される。変えた分を捨てて練り直すときは、先に `rollback` で戻す（戻せば変わったファイルが無いので取り直される）。

### 2.2 確認は会話の中で待つ

confirm は、計画を見せて利用者の答えを待つアクションである。statemachine-use を会話の中で回す
（1 ステート 1 ターン）ときは、エージェントが計画を出してターンを終え、利用者の返事を受けて出力を確定する。
実行の途中で人の入力を受け取る仕組みを持たない無人のハーネス（agent-loop の headless 実行など）では、
このステートで止まる——このマシンは会話で使うことを前提にしている。

前の版は「終端で止まり、答えを入力に入れて次の実行で再開する」形だったが、そのために意図の状態・
答え待ち・反映待ちを `state.json` に持つ必要があり、ハーネスが重くなった。会話の中で待てば状態は要らない。

## 3. 前提・制約・その他とずれ

| 分類 | 定義 |
|---|---|
| 前提 | 参照先が「すでにそうなっている」と定めている事実・決定・振る舞い・用語 |
| 制約 | 参照先が「こうしなければならない / してはならない」と課している条件 |
| その他 | それ以外の関係する記述（決まっていないこと・任されていること・補足） |

**ずれ**は、このうち自分の現状（またはやりたいことを実現した姿）と食い違うもの。ずれがあれば、
それを解消するための参照先の変更案と、その変更を自分のリポジトリに適用したときの影響範囲を計画に書く。
ずれを残したまま進めたいなら、それはずれではなく「その他」として書く（検査がずれと変更案の対応を求めるため）。

分類は向きを問わない。実装から設計書を読めば「設計書が定める前提・制約」、設計書から実装を読めば
「実装が既に持っている振る舞い（前提）と、互換性・性能・依存などの条件（制約）」になる。

## 4. 影響範囲の測定

参照先を変えるときの「自分のリポジトリへの影響範囲」は、モデルが書いた一覧をそのまま信じず、**ハーネスが測って突き合わせる**。
利用者が OK と答える材料も、NG で練り直す材料も、測った結果である。

| いつ | 測る語 | 通る条件 | 記録 |
|---|---|---|---|
| verify-plan（confirm の前） | 計画の「自分の変更案」「参照先の変更案」「ずれ」で `…` に囲んだ名前。自分の変更案・参照先の変更案に囲んだ名前が無ければ落とす | 自分で測ったファイル ⊆ 自分の変更案 ∪ 影響範囲に挙げたファイル | `.codd/impact.md` |
| verify-plan（逆向き） | 「自分の変更案」の名前で**参照先**を測る（文字列検索だけ） | 測った参照先のファイル ⊆ 計画が根拠か参照先の変更案として挙げたファイル | `.codd/ref-impact.md` |
| verify-apply（apply の後） | 自分と参照先の実際の差分（`git diff HEAD` の +/- 行の定義・見出し・`…`、新しいファイルの定義・見出し）＋ 計画の名前 | 測ったファイル ⊆ 自分で変えたファイル ∪ 計画で「変更不要」としたファイル | `.codd/impact-after.md` |
| verify-apply（逆向き） | 自分の差分の名前のうち計画に無かったもの | 測った参照先のファイル ⊆ 計画が扱ったファイル ∪ 変えた参照先のファイル | `.codd/ref-impact-after.md` |

- 自分の変更の影響も測る。参照先を変えない計画でも、関数の呼び出し元や同じ名前に触れる設計書を見落とさないため
- 逆向き（参照先）は `git grep` だけで測る。graphify の `query` は関係の近いものまで広く拾うので、
  「扱ったか」を問う検査には決定的な文字列の一致を使う。関係の無いファイルは「その他」に「関係なし: 理由」と根拠付きで書く
- 測り方は graphify `affected`（依存している呼び出し元・参照元を深さ 2 までたどる）と `git grep --untracked`。
  識別子は語単位（`-w`）で引き、`hello` で `helloWorld` を拾わない。1 回に測るファイルは 40 まで
- 変えたあとに測り直すのは、参照先を計画より広く変えたときの影響を取りこぼさないため。計画時の語だけでは、
  計画に書かれなかった変更の影響が見えない
- 「自分で変えたファイル」は、verify-plan が通ったときに控えた作業中ファイルの中身のハッシュと HEAD から比べる
  （apply の前から作業中だったファイルを「変えた」と数えない。§7）
- 「変更不要」は計画の影響範囲の項目に `変更不要: 理由` と書いたもの。利用者の確認を経た計画にしか書けない
- 影響範囲とテストの変更案の項目は、verify-plan・verify-apply・要約・記録のどれも同じ読み方（`judgment`）で読む。
  書き方は `- パス, パス — 変更不要: 理由` と `- 変更不要: パス, パス — 理由` の 2 つ。対象は先頭に並べたパスだけで、
  理由の中のパスは対象にしない。以前は読む場所ごとに書き方の受け取り方が違い、計画の検査が通った書き方
  （「直さない」と書いた影響範囲、`変更不要: パス — 理由` と書いたテスト）が変えたあとの検査で変更不要と読まれず、
  直していないファイルとして落ちた。そこで、理由の無い変更不要と、ほかの言い回し（「直さない」「対応不要」「影響なし」
  など）を verify-plan で書き直させる
  （apply で足すときは利用者に確かめる）

### 4.1 パスのつながり（codd-gate から取り込んだもの）

名前の一致（§4）は、ファイル同士が**パスで**指し合う関係を拾えない（設計書の対応表が `src/app.py` を挙げている、
コードのコメントが設計書を指している、など）。codd-gate の「主張の抽出」をそのまま使い、これを両向きに測る。

- 拾う書き方: どのファイルでも注記 `coherence: doc|code|test=パス`。文書（`.md`・`.markdown`・`.rst`・`.adoc`・`.txt`）では
  `` `…` `` に囲んだパスらしいもの（`/` を含むか、既知の拡張子で終わる）とマークダウンのリンク。文書のフェンスと `` `…` `` の中の注記は
  書き方の例とみなして拾わない（codd-gate はフェンスの中の注記も拾うが、ここでは足した行を検査するので例を落とさないことを優先する）
- 解決: `名前:パス` なら参照先 `名前` で。それ以外はリポジトリのルートから、リンクは文書のフォルダからも試す。
  書いた側のリポジトリに実在すればそちらを採り（同じリポジトリの別フォルダは scope で側を決める）、無ければほかの側を探す。
  リポジトリの外（`../` で出る）は扱わない
- 「つながり」: ファイル A が B を指すか、B が A を指す。逆向き（ほかの側のどのファイルが A を指すか）は、A のファイル名で
  `git grep -l` して候補を絞ってから、候補の主張を解決する（全ファイルを読まない。1 側 200 ファイルまで）

| いつ | 対象 | 通る条件 | 記録 |
|---|---|---|---|
| verify-plan | 自分の変更案のファイル ↔ 参照先 | つながった参照先のファイル ⊆ 計画が根拠か参照先の変更案として挙げたもの | `.codd/trace.md` |
| verify-plan | 参照先の変更案のファイル ↔ 自分 | つながった自分のファイル ⊆ 自分の変更案 ∪ 影響範囲 | 同上 |
| verify-apply | 自分の変えたファイル ↔ 参照先 | ⊆ 計画が扱ったもの ∪ 変えた参照先のファイル | `.codd/trace-after.md` |
| verify-apply | 参照先の変えたファイル ↔ 自分 | ⊆ 自分で変えたファイル ∪ 「変更不要」 | 同上 |
| verify-apply | 変えたファイルの**足した行**（`git diff HEAD -U0`。未追跡は全行）の主張 | どれかの側に実在する（壊れたパス）。`` `…` `` のパスは、先頭のフォルダがどれかの側に実在するときだけ調べる（`path/to/x.md` のような例を落とさない） | 同上 |
| verify-apply | 消したファイル | それを指したままの主張が、どの側にも無い（宙に浮いた参照） | 同上 |
| report | 自分の変えたファイル | 参照先とつながっていないものを知らせる（落とさない） | `.codd/report.md` |

足した行だけを調べるのは、1 回の変更が持ち込んだ誤りだけを止め、前からある壊れたパス（リポジトリ全体の負債）を
この回の仕事にしないため（§1.1）。

### 4.2 テストもコード・仕様書と同じ成果物として測る

テストケースとテストコードは、コード・仕様書と同じく整合を取る成果物である。モデルは「テストは最後に動かすもの」と
扱いがちで、名前や仕様を変えたときに響くテストを直し忘れる。そこで、響くテストもハーネスが測って計画に挙げさせる。
単体テスト・API テスト・シナリオテスト・e2e のケースは区別しない（どれも「変更が響けば直す」もの）。

- どのファイルがテストか: `codd.json` の `tests`（glob）。既定は `test/**`・`tests/**`・`e2e/**`・`**/__tests__/**`・
  `**/*.test.*`・`**/*.spec.*`・`**/test_*.py`・`**/*_test.py`・`**/*_test.go`・`**/*Test.java`・`**/*Tests.cs`・
  `**/*.feature`・`**/*.robot`・`**/*.http`・`**/*.postman_collection.json`・`**/scenarios/**`・`cypress/**`・`playwright/**`。
  `spec/**` は仕様書のフォルダと重なるので入れない。参照先のテストは参照先に置いた `codd.json` の `tests` で決める
- 響くテスト = (a) 変える名前（§4 と同じ語）が書かれているテスト（`git grep`）、(b) 変えるファイルをパスで指しているテスト、
  (c) 変えるファイルが指しているテスト（§4.1 の主張の解決）、(d) 変えるファイルと語幹が同じテスト（`app.py` と `test_app.py`、
  `Login.tsx` と `login.yaml`。`test_`・`_test`・`.spec`・`Test` などの印を外して比べる。`index`・`main` などは除く）、
  (e) verify-apply だけ、変えたコードの差分の引用符の中の文字列（画面の文言・URL）が書かれているテスト。
  §4.1 と違い、**同じ側**のテストも数える（実装の変更が同じリポジトリの単体テストに響くのが最もよくあるため）。1 側 2000 ファイルまで
- (d)・(e) は e2e のケースのため。e2e のケースは画面の文言や URL で書かれ、コードの名前が出てこないので (a) では拾えない。
  ケースの書き方（webui-test の YAML など）を読めば拾えるが、それはテストの道具とこのマシンを結び付ける（§5.9 の独立性）。
  ファイル名と文字列はどの道具のケースにも共通する手がかりなので、これで拾う。計画の段階では差分が無いので、変わる文言・URL は
  計画に `…` で書かせ (a) で拾う
- 参照先のテストは、探して見つかった（§4.1）ときも根拠の見出しではなく「テストの変更案」に「未判断」として書き足す。
  根拠として「関係なし」で片付けさせず、足す・直す・変更不要のどれかで判断させる
- 新しく足す名前は、今あるテストに書かれていないので (a)〜(e) では響くテストにならない。そこで別に確かめる:
  verify-plan は、変更案の `…` のうちどの側にもまだ無い名前が「テストの変更案」に出てくること（足すテストに名前を添えるか、
  `` - `名前` — 変更不要: 理由 ``）、verify-apply は、差分で新しく足した定義（関数・クラス・型・export した値。`_` で始まるものは除く）と
  文書の見出しのうち HEAD に無かったものが、どこかのテストか「テストの変更案」に出てくること。文書の見出しは、その文書をパスで
  指すテストをこの回に変えていてもよい（e2e のケースの `coherence: doc=…`）
- 計画の見出し「テストの変更案」に、足す・直すテストと「変更不要: 理由」を書く。何かを変えるのに「なし」は認めない
  （響くテストが無く足すテストも要らないときは、パスの無い `- 変更不要: 理由` を書く。黙って飛ばさせない）

| いつ | 通る条件 | 記録 |
|---|---|---|
| verify-plan | 響くテスト ⊆ テストの変更案 ∪ 自分の変更案・影響範囲 ∪ 参照先の変更案。変更案で新しく足す名前 ⊆ テストの変更案に出てくる名前 | `.codd/tests.md` |
| verify-apply | テストの変更案（変更不要を除く）をすべて変えた。実際の変更から測り直した響くテスト ⊆ 変えたファイル ∪ 変更不要。新しく足した名前がテストか計画に出てくる | `.codd/tests-after.md` |
| verify-apply | `codd.json` の `test` のテストが通る（名前ごとに書けば、単体・API・シナリオを別々に動かして結果を分けて出す） | 出力 |

テストを動かすのはこのマシンの責務である（§5.9 の webui-test は e2e と仕様書の画像だけを受け持ち、単体テストを持たない）。

### 4.3 テストで得たもの（evidence）を実装と文書に返す

テストは合否のほかに、確かめた振る舞い・測った時間・画面を生む。これが文書に手で写されると、次の変更で黙って古くなる。
そこで、テストの結果を共通の形のファイル（evidence）に出させ、文書への影響はこのマシンが測って直す。
**テストの側は文書を知らない**（webui-test は仕様書を読まず、前回と画面が変わったかだけを出す。§5.9）。
文書との対応を持つのは、実装と文書の両方を見ているこのマシンだけにする。

- 形: `{"version": 1, "source", "root", "items": [{"id", "kind": "behavior"|"metric"|"image", "title", "status", "value", "unit",
  "max", "path", "sha256", "history", "file"}]}`。`file` はその項目を生んだテストのファイル（§4.2 の響くテストと結ぶ鍵）。
  画面の `status` は前回と比べた same / changed / new / removed、`history` はこれまでの版の sha256（今の版が先頭）。
  `root` は項目の `path` の起点で、この evidence.json のフォルダからの相対（無ければその側のルート）。読む側はテストの道具の
  置き場を知らなくてよい。ほかのテストも同じ形で書けば読む（`codd.json` の `evidence` に glob を書く）

**画面 → 文書の画像（差し替え）**

- 文書のリポジトリの画像（git が無視していない `.png`、各側 5000 まで）を sha256 で引く。画面の `history` のどれかと同じ画像が、
  その画面を貼っている画像である。文書側に印や対応表を書かせない（書き忘れ・書き間違いが起きない。
  文書に貼るときに `webui-test-results/screens/` の画像を写せば、それだけで対応が付く）
- 前の版と同じ画像は、verify-apply（`check` のあと）でハーネスが今の画面に差し替える。差し替えた画像は `.codd/replaced.json` に控え、
  「変えたファイル」から外す（モデルの変更ではないので、計画との突き合わせに入れない）。どのマークダウンが貼っているかも引いて報告する
- 撮らなくなった画面（removed）を貼っている画像は差し替えられないので、知らせるだけにする
- `test`・`check` が作り直したファイル（撮り直した画像・結果のファイル）も、モデルの変更ではない。verify-apply は
  `test`・`check` の前後で作業中の変更を比べ、変わったファイルとその中身のハッシュを `.codd/generated.json` に控える。
  次の verify-apply は、中身が控えと同じファイルを「変えたファイル」から外す。控えるのは、検査の前の中身が
  変える前の印か前の控えと同じファイルだけ（モデルが変えたファイルを検査が上書きしても、モデルの変更として数える）。
  以前は、1 回目の verify-apply が作り直した画像を 2 回目以降が「計画に無いファイル」として数え、検査を通し直すたびに止まった
- 逆に、計画に挙げた画像（`.png`・`.jpg`・`.jpeg`・`.gif`・`.webp`・`.svg`）は、変わっていなくても変え残しとみなさない。
  撮り直しても画面が同じなら同じバイト列が残る（撮影の道具は同じとみなした画像を書き換えない）ので、変わらないことは
  失敗ではない。report は「撮り直しても同じ」と出す
- 比べるのはバイト列の sha256 だけで軽い。描画の揺れは webui-test が吸収する（画素で同じとみなせば前回のファイルを残すので、
  同じ画面の sha256 は変わらない）

**振る舞い・時間 → 文書の印**

- 印: `<!-- evidence: id 任意の max=… tolerance=… -->写した値<!-- /evidence -->`。`id` が `*` で終われば前方一致の一覧。
  `名前:id` で参照先の evidence を指す（無ければ文書の側・自分・参照先の順に探す）。値は機械が描く
  （時間は `812 ms`、振る舞いは `✓ 題名`）ので、写し方の揺れは起きない。画面は印で写さない（上の差し替えで扱う）
- 時間は毎回揺れるので、数は 2 割（`tolerance`）までの違いを同じとみなす。揺れの中なら `--write` も書き換えない（差分を作らない）
- 目安（`max`）は実装への返し口である。超えたら verify-apply が落とし、モデルは実装を直す。目安を変えるのは文書の変更なので
  計画と確認を経る

| いつ | すること | 記録 |
|---|---|---|
| verify-plan | 計画で変えるファイルと響くテストに関係する項目、響くテストの画面を貼っている文書の画像を出す。響くテスト（§4.2）の結果を印で写している文書が計画に無ければ落とす。今の evidence を控える | `.codd/evidence.md`・`.codd/evidence-before.json` |
| apply | テストを動かしてから `codd.py evidence --write 文書` で印を写し直す（計画に挙げた文書だけ）。画像には触れない | — |
| verify-apply（`test`・`check` のあと） | 変わった画面の画像を差し替える。印が今と合う・目安を満たす・写した振る舞いが通っている | `.codd/replaced.json`・出力 |
| report | 差し替えた画像と貼っている文書、撮らなくなった画面。控えと比べて変わった時間・画面・合否 | `.codd/report.md` |

verify-apply が確かめる印は、変えた・変える文書のものと、変更が響くテストの結果を写したものだけ。計画に無い文書の印は
写し直すと「計画に無い変更」になってどうやっても通らないので、ここでは見ず、`lint` が拾う。

### 4.4 文書の書式を決まりとして守らせる

文書の今の書式は、コードで言うコーディングルールにあたる。モデルは文書を書き足すとき、見出しを自分の好みで並べ替えたり、
同じフォルダの他の文書と違う形で書いたりしがちである。そこで、変える文書の書式を測って「守る決まり」に挙げさせ、
変えたあとに機械で確かめる。

- 書式 = 見出し（`##` 以下）の並び。題名の `#` は文書ごとに違うので見ない。コードブロックの中は見ない。
  表の形や言い回しは機械で確かめず、見本を「守る決まり」に挙げさせてアクションで守らせる
- 見本: 今ある文書はそれ自身。新しい文書は同じフォルダのマークダウン（`README`・`index`・`CHANGELOG` などの索引を除く）が
  2 つ以上あるとき、そのすべてが持つ見出しを最初の文書の順に並べたもの。共通の見出しが無ければ決まりは無い
- verify-plan: 変える文書（自分の変更案・「変更不要」でない影響範囲・参照先の変更案のマークダウン。テストを除く）ごとに見本と
  見出しの並びを `.codd/formats.json`（機械用）と `.codd/formats.md`（人とモデル用）に控え、「守る決まり」に見本のパスが
  無ければ落とす
- verify-apply: 控えた見出しが、変えたあとの文書に順に残っているか。計画に `` `## 見出し` `` と書いた見出しは除く
  （見出しを変える・消すのは、確認を経た計画に書いたときだけ）。消した文書は見ない

| `summary` | 計画の要約（やりたいこと・根拠の件数・ずれ・変えるファイル・テスト・今回やらないこと。見出しごとに 12 項目・1 行 120 字まで） |
| `report` | 終わりの報告（§5.8） |
| `decide 答え [--note 文]` | 確認（`OK` / `NG`）と止まったとき（`PLAN` / `APPLY` / `STOP`）の利用者の答えを `.codd/decisions.json` に控える。計画の本文は練り直しで書き換わるので、答えは別に持つ |
| `record` | 1 回の終わりに、計画へ「確認と判断」（控えた答え）と「結果」（`report` の出力）を書き足し、同じ名前のまま残す。使わなかったスキル・関係なしとしたファイル・中身が「なし」の見出し・残ったひな形の説明は記録から除く（判断の記録として読むのに要らない）。`.plans/` は判断の記録として利用者のリポジトリに残す。マシンの持ち物と同じく、変えたファイル・探す対象に数えない。コミット済みの記録を書き換えていれば、計画と変えたあとの検査で落とす |

### 5.1 graphify の自動更新

リポジトリの**印**（HEAD と、`git diff HEAD`、未追跡ファイルの名前と中身から作るハッシュ）をグラフの横に控え、
`explore` / `impact` のたびに今の印と比べる。違えば `graphify update . --force` で作り直し、同じなら前のグラフを使う。
コミットだけでなく作業中の変更でも作り直すので、apply の途中や計画の練り直しで古いグラフを引くことがない。
`--force` は、削除や改名でノードが減っても作り直した方を採るため（古いノードを残さない）。

グラフは `GRAPHIFY_OUT` で自分の `.codd/graph/own/` と `.codd/graph/ref-<名前>/` に書く。参照先の中に `graphify-out/` を作らない。
`update` は AST と見出しの抽出だけで LLM を使わない。設計書の意味的な抽出（`graphify extract`）は重いので自動では回さない。

常駐の監視（`graphify watch`）や git hook は入れない。使うときに確かめて作り直す方が、仕組みが少なく、
参照先に何も仕込まずに済む。

### 5.2 文字列検索を並べる

graphify の有無にかかわらず `git grep --untracked -F -i` を並べる。グラフに入らない文書と、
まだコミットしていないファイルを拾うため。graphify が無い・`graphify: off`・作り直しに失敗したときは、
文字列検索だけで同じ形の報告を出す。

### 5.3 使うスキル

`codd.json` の `skills` に、段階ごとに使うスキルの名前を並べる。

| 設定 | 使うとき |
|---|---|
| `skills.plan` | 計画を練るとき（このリポジトリの側で読む・練るときの作法） |
| `skills.apply` | このリポジトリを変えるとき |
| `refs[].skills` | その参照先を変えるとき。書かなければ、参照先に置いた `codd.json` の `skills.apply` |

参照先を変えるときに参照先自身の設定を使うのは、「そのリポジトリをどう変えるか」はそのリポジトリの持ち物だから
（実装なら `tdd`、設計書なら文書を書くスキル、のように側ごとに決まる）。参照先に codd を置いていないときや、
この側から変えるときだけ作法を変えたいときは `refs[].skills` で上書きする。

アクションは `codd.py show --phase …` を実行し、出てきたスキルを読み込んで従う。statemachine-use の実行ハーネスは
アクション本文の `` `名前` スキル `` 表記でスキルを読み込むが、スキルは設定で変わるので本文に固定では書けない。
`show` がその表記で出力し、会話で回すエージェントがそれを読んで読み込む（confirm が会話を前提にしているので、
無人の実行で自動読み込みを効かせる必要は無い）。

### 5.4 参照先が複数あるとき

- `refs` の各項目は `name` と `path`。`name` は英数字と `_` `.` `-`（省略時はフォルダ名）で、参照先ごとに違う
- 計画の根拠と参照先の変更案のパスは `名前:パス` で書く。パスだけのときは、実在する参照先が 1 つならそれに決め、
  複数にあれば曖昧として落とす（名前を書くよう求める）。参照先が 1 つなら従来どおりパスだけでよい
- 参照先の変更案は、まだ無いファイル（親のフォルダはある）も書ける——新しい文書を足す変更案のため
- 変更案に挙げた参照先の集まりが「変えてよい参照先」。§7 はこれと実際に変わった参照先を 1 つずつ突き合わせる
- 影響範囲の測り直しは、変わった参照先すべての差分から語を集めて 1 回測る（測る先は自分のリポジトリだけ）
- 以前の `ref_path`（参照先が 1 つだった頃の書き方）も読む。インストーラーは `--ref` を渡したときに `refs` へ置き換える

### 5.5 同じリポジトリの別フォルダ

実装と設計書が同じリポジトリにあるプロジェクトも多い。`refs[].path` を `.` にし、自分の `scope` と参照先の
`refs[].scope` にそれぞれが受け持つフォルダを書く。

- 探す（`git grep` のパス指定、graphify の結果の絞り込み）・根拠を認める・変わったかを測る・差分から語を拾うのは、
  それぞれの scope の中だけ。グラフはリポジトリ全体で 1 つ作って共有する
- 同じリポジトリを使う側どうしは、どれも scope を持ち、互いに重ならないこと。そうでなければ動かす前に止める
  （重なると、どちらを変えたのかが決まらない）
- 参照先に置いた `codd.json` は読まない（自分の設定そのものなので）。参照先の呼び名は自分の反対側になる
- scope は別のリポジトリでも使える（参照先のリポジトリのうち `docs/` だけを読む、など）
- 自分の `exclude` と `refs[].exclude` で、それぞれのルートからの相対パス・glob を除外する。
  省略・`[]` は追加の除外なし。参照先自身の `exclude` は継承しない。`scope` の中でも除外を優先する。
  `*`・`?`・`[...]` はフォルダをまたがず、`**/` は 0 階層以上をまたぐ。フォルダのパスは配下も除く。
  検索候補（graphify も）・影響測定・パスのつながり・テストの選別・点検・変更検出を同じ対象判定で絞り、
  除外されたパスは計画の根拠や変更案としても認めない。索引はリポジトリ全体で共有し、結果を絞る。
  守る決まりの読み込みと候補探しは別で、除外に関係なく行う。`test` / `check` のコマンド自体は絞らない。
  codd 自身の生成物以外の設定ファイルは、自動では除外しない。
  `init.py --exclude` / `--ref-exclude 名前=パターン` は指定した側の一覧を入れ替え、省略した側は維持する。


### 5.6 設定の誤りは動かす前に止める

`codd.json` と `refs[]` の知らない項目（綴り違い）、`scope` / `exclude` の外向きのパス、`exclude` の不正な型、`max_files` の不正な値は、
どのコマンドでも最初に `ERROR`（終了コード 2）で止める。黙って既定値で動くと、利用者は設定が効いていないことに気付けない。

### 5.7 守る決まり・使うスキルと道具

- 決まりのファイル: 自分と（別のリポジトリの）参照先にある `CLAUDE.md`・`AGENTS.md`・`GEMINI.md`・
  `.github/copilot-instructions.md`・`CONTRIBUTING.md` と、`codd.json` の `rules`・`refs[].rules`（と参照先に置いた
  `codd.json` の `rules`）。`rules` は glob も書ける（git の `:(glob)` と同じ意味で、追跡中と未追跡のファイルから引く）。
  当たらないものは `show` が知らせる（綴り違いやファイルの移動で、決まりが黙って外れないように）。`show` が挙げ、計画の「守る決まり」に
  すべて（参照先のものは `名前:パス`）挙がっていなければ verify-plan が落とす。名前をそろえたのは、多くのプロジェクトで
  エージェント向けの約束がこの名前で置かれているため（プロジェクトごとの設定なしに効く）
- 決まりの読み込み: パスを挙げただけでは読んだことにならないので、`codd.py rule --all` で中身を出して文脈へ入れ、
  ファイルごとの中身のハッシュを `.codd/rules-read.json` に控える。控えに無い、またはハッシュが今と違う（読んだあとに
  決まりが変わった）ファイルがあれば verify-plan が落とす
- 参照先の探索: `explore` は文字列の一致（`git grep`。graphify の `query` は広く拾うので使わない）で見つかったファイルを
  参照先ごとに `.codd/explore.json` へ足していく。verify-plan は、探していない参照先があるか、控えたファイルが計画の
  根拠・参照先の変更案（「関係なし: 理由」を含む）に無ければ落とす。前提・制約・その他・ずれを全部「なし」と書いて
  参照先を読まずに通す道を、これで塞ぐ。探す語はモデルが選ぶが、自分の変更案の名前は別に `measure_refs` が必ず引く（§4）
- 応答の長さ: GitHub Copilot などは 1 回の応答の長さに上限があり、超えると「the response hit the length limit」で止まる。
  計画は日本語で長くなりやすいので、全文を一度に書かせない（`draft` でひな形を置き、見出しごとに書かせる）・
  確認で全文を貼らせない（`summary` の要約とパスを見せる）。練り直しでは直す見出しだけを書き換えさせる
- 記録の寿命: 探した・読んだ記録（explore・rules-read・skills-read）は `report` で消す。1 回の実行の中だけで有効にし、
  前の回の記録で読んだことにさせない
- 決まりの発見: パスか最初の見出しに決まりらしい語（ルール・規約・コーディング・rules・guideline・convention など）を
  含むマークダウンを候補にする（`rules`）。候補は設定に書くまで検査の対象にしない——語の一致だけでは決まりとは限らず、
  誤って挙げると毎回その読み込みを強いるため。書くのは利用者の同意があるとき: `init.py` で初めて置くとき（置くこと自体が同意。
  `--no-discover-rules` でやめる。既にある `codd.json` は利用者の設定なので、置き直しでは探し直さない）と、利用者が `rules --write` を実行するとき。確認（confirm）では訊かない——断っても記録が無いので、候補を使うたびに同じことを訊くことになる。
  あとから増えた候補は `show` に出るので、計画のときに読まれる。
  拾いすぎると計画の段で毎回その全文を読み込ませ、文脈を圧迫する。そのため自分の分は `scope` の中とその上のフォルダ
  （ルートを含む）だけを探し（同じリポジトリのほかの道具の決まりを拾わない）、スキルの中（`SKILL.md` のあるフォルダの下。
  そのスキルを使うときに読むもの）と、日付で始まるファイル（計画や記録）は候補にしない
- 読む量: `rule --all` は、この回で読み込み済みで中身も変わっていないものを出し直さない（練り直しのたびに全文を
  読み込ませない。`--again` で出す）。探して見つかったファイルは `explore.md` の一致した行で判断させ、関係するものだけ
  前後を読ませる（全文は読ませない）。関係しないものは「関係なし」を 1 行にまとめてよい。計画のひな形のコメントは
  1 行ずつにし、詳しい書き方はアクションの側にだけ書く（同じ説明を 2 度読ませない）
- スキルと道具: `skills.plan`・`tools.plan` は計画の「使ったスキルと道具」に、`skills.apply`・`tools.apply`
  （と変えた参照先の分）は `.codd/apply.md` にすべて挙がっていなければ落とす。`.codd/apply.md` は変える前の印より新しいこと
  （前の回の記録を使い回させない）
- リポジトリのスキル: `skill_dirs`（既定 `.agents/skills`）の `名前/SKILL.md` を、設定しなくても `show` が挙げる
  （名前と説明は SKILL.md の先頭の `name` / `description`。30 まで）。計画の「使ったスキルと道具」には使ったものだけを書く。
  使うことを強制しないのは、説明だけでは関係するかを決定的に決められないため。前の版は使わないものにも「使わない: 理由」を
  1 つずつ求めていたが、記録に要らない行が増えるだけだったのでやめた
- スキルの読み込み: エージェントのスキル選択（kiro-cli などは自動で選ばないことが多い）に頼らず、`codd.py skill 名前` で
  `SKILL.md` を出して文脈へ入れる。出したときに名前と時刻を `.codd/skills-read.json` に控え、計画の「使ったスキルと道具」・
  `.codd/apply.md` で使ったと書いた（「使わない」の行を除く）スキルが控えに無ければ落とす。apply は変える前の印より新しい
  読み込みだけを認める（計画のときに読んだだけで済ませない）。これで「使った」と書くことと「読んだ」ことを、スクリプトから
  見える事実で結び付ける。見つからないスキル（エージェントの組み込みなど）は読み込みを求めない
- 変える前に手順を渡す: `skills.apply`（と変える参照先の分）は、`batch` が段の最初に `SKILL.md` を出して控える
  （この回で読み込み済みなら名前だけ）。使った記録を確かめられるのは変え終えたあとなので、そこで落ちてから読み直しても
  記録を足すだけになり、手順が変更に効かない。手順を変える前に必ず目に入れる
- 見直させる: `.codd/apply.md` のスキルの行に、その側で変えたファイルが 1 つも無ければ落とし、スキルの手順と変えたファイルの
  差分（`git diff HEAD`。長ければ切る。新しく足したファイルは名前だけ）を並べた `.codd/skill-review.md` を作る。
  指摘は人の判断が要らない種類に入れ、stuck は訊かずに apply へ戻して見直させる。資料に手順を載せたので、そのスキルは
  読み込んだと控える
- 導入の 2 つ: `install.py` は codd が使う外部のミドルウェアを端末に入れる（graphify を uv・pipx・pip で。
  git は有無を確かめるだけ）。codd そのものは端末に入れず、`init.py` がリポジトリの `.statemachine/codd/` に
  写して `codd.json`・カスタムエージェント・`.gitignore` を書く（リポジトリだけで動き、版もリポジトリごとに決まる）
- カスタムエージェント: `init.py` が kiro-cli（`.kiro/agents/codd.json`）と GitHub Copilot（`.github/agents/codd.agent.md`）
  向けに、変える依頼は必ずこのマシンで進めるエージェントを書く。指示は `agents/codd-agent.md` 1 つから両方へ写す。
  statemachine-use が無い環境でも回せるよう、`workflow.yaml` の読み方（action・check と再投入・condition_rule・答えを待つ
  ステート）を指示に含める。kiro-cli では `agentSpawn` の hook で `codd.py show` を読み込ませる。エージェントのファイルは
  マシンの一部として、探す・変わったかを測る対象から外す

### 5.8 終わりの報告（`report`）

done は `codd.py report` の出力をそのまま伝える。計画のファイルごとの「変えた / まだ」、変えたあとに測った影響範囲の
「直した / 未対応」（変更不要の項目は載せない）、「今回やらないこと」を、計画・変える前の印・今の中身から作る。verify-apply が通ったときの
中身を `.codd/applied.json` に控え、今と違えば「通ったあとに、さらに変わっている」として終了コード 1 を返す。
報告をモデルの記憶でまとめさせると、変え残しや直していない影響を「終わった」と伝えてしまうため。

### 5.10 点検（`lint`。本流とは別）

本流は依頼が触れた範囲だけを測る。codd を通らずに入った変更や、もとからある食い違いは、別の依頼がそこに触れるまで
見つからない。`lint` は本流の部品（`claims_in`・`resolve`・`doc_headings`・`check_marks`・`run_check`）をリポジトリ
全体に当て、見つけたものを本流に渡す「やりたいこと」の 1 行にして `.codd/lint.md` に書く。

- **直さない。** 変える道を本流の 1 本に保つ（確認・検査・記録を通さない変更を作らない）。書くのは `.codd/` だけ
- **決定的にする。** LLM を使わないので CI の定期実行で回せる。見つかれば終了コード 1
- **誤検出を抑える。** 全体を見ると、`…` のパス（別のリポジトリのファイルや例が多い）は壊れたパスに数えない。リンクと
  注記だけを見る。`…` とコードブロックの中のリンク・evidence の印は書き方の例として外す（本流の `claims_in`・`marks_in` も同じ）
- **codd を通らなかった変更**は、codd を置いたコミットより後、`--since`（既定 30 日）のうちのコミットで変わったファイルの
  うち、どの側のリポジトリの `.plans/`の記録にもパスが出てこないもの。状態を持たない（前回の点検の位置を控えない）ので、
  定期実行は前の回と少し重なる期間を渡す
- `check` は「変えたあとに作り直す」コマンドで、ファイルを書き換えることがあるので動かさない。`test` を動かして作業中の
  ファイルが変わったら、それも知らせる

**意味のずれ（サンプル `samples/drift/`）。** `lint` は決定的に見られるもの（名前・パス・見出し・写した値）だけを見る。
名前は合っていて中身がずれているものは、読んで判断するしかないので、モデルに判断させる別のワークフローにした。
本流にも `lint` にも入れないのは、判断がモデルに依るので終了コードで CI を止める材料にできないため、と
人の確認を待たずに定期実行で回したいため。モデルが書く候補と判断の形（指す行の実在・組の網羅・ずれに添える
「やりたいこと」）は `check_drift.py` が `check` で確かめる。比べる組は codd を通らなかった変更から集め、10 組までに絞る
（全体を比べると読む量が際限なく増える）。

### 5.9 画面のあるアプリ: webui-test と組む

実装・テスト・設計書の 3 つをそろえるには、設計書との突き合わせ（このマシン）に加えて、動かして確かめる検査が要る。
このマシンは言語やビルドを問わないので、その検査は `check` の 1 コマンドに任せ、画面のあるアプリでは
`tools/webui-test` の `webui-test check` をそのコマンドにする。

- 責務を分ける。webui-test は**仕様書に依存しない**: アプリをローカルで起動して（`serve`）e2e のケースを動かし、`screenshot`
  ステップの画面を前回の `check` と比べ（まずバイト列、違えば画素）、結果を `results/webui-test-evidence.json` に書くだけ。
  画面が変わってもケースは落とさない（変わったかどうかは情報で、良し悪しは文書と突き合わせる側が決める）。
  文書への影響を測って画像を差し替えるのはこのマシン（§4.3）
- `run_check` は出力の末尾 20 行しか見せないので、webui-test は結果を最後にまとめて出す
- 結果の置き場は git に無視させているので、evidence や前回の画面を書いても変更に数えない
- 単体テストは webui-test に持たせない。テストを動かすのはこのマシンの `test`（§4.2）
- e2e のケースファイルに `# coherence: doc=…` を書けば §4.1 のつながりとしてたどる（任意。webui-test はこの注記を読まない）
- codd-agent の既定 evidence は `[]`。`init.py --check` と `--evidence` で利用者がコマンドと結果ファイルを指定する。
  webui-test の設定・出力先は自動検出せず、インストーラも webui-test の有無を確認しない。
  既にある `codd.json` は渡された項目しか書き換えない（利用者が手で整えた設定を置き直しで崩さない）。
  任意のコマンドは `--check` で書ける
- Windows では `webui-test`・`npm` が `.cmd` なので、`run` は実行ファイルを PATHEXT で探してから起動する

前回との画素の比べ方は Playwright の `toHaveScreenshot` と同じ（色の近さの許容 0.2）で、既定では 1 画素でも違えば変わったとみなす
（文言 1 つの変更が全体の 1% に満たないことがあるため）。PC ごとの描画の差で揺れるときは `check.maxDiffRatio` で緩める。

## 6. 計画の契約（`verify-plan`）

`templates/plan.md` の見出し（やりたいこと / 守る決まり / 使ったスキルと道具 / 参照先の前提 / 参照先の制約 / 参照先のその他 / ずれ /
自分の変更案 / 参照先の変更案 / 影響範囲 / テストの変更案 / 今回やらないこと）がこの順にそろい、中身が空でないこと。加えて:

- 前提・制約・その他・ずれは「なし」か箇条書き。各項目に**参照先に実在するパス**がある（読んでいないものを書かせない）。
  参照先が複数あって決まらないパスは `名前:パス` を求める
- 根拠を `パス:行`・`パス:行-行`・`パス#見出し` で書いたときは、その行がファイルの中にあり、その見出しが
  （GitHub のアンカーと同じ正規化で）実在すること。ファイルだけでなく箇所まで偽れないようにする
- 前提・制約・その他で `` `…` `` に囲んだ名前（パスを除く）は、その項目の根拠のファイルのどれかに書かれていること
  （大文字小文字は問わず、末尾の `()` は落として探す）。ずれは自分の側の名前も書くので対象にしない
- 自分の変更案の各項目に自分のリポジトリのパスがある（まだ無いファイルは、親のフォルダがあり拡張子があれば認める）
- 参照先の変更案の各項目が、どの参照先を変えるかを決められる（§5.4）
- ずれがある ⇔ 参照先の変更案がある
- 参照先の変更案があれば影響範囲があり、影響範囲の各項目に**自分のリポジトリに実在するパス**がある
- 参照先の変更案に `…` で囲んだ名前があり、それで測った影響範囲（§4）をすべて挙げている
- 変えるファイルの数が `max_files` 以下（§1.1）。通ったら段に分ける
- 自分の変更案・参照先の変更案のファイルとパスでつながったほかの側のファイルを扱っている（§4.1）
- 響くテストをテストの変更案にすべて挙げている。何かを変えるのにテストの変更案が「なし」でない（§4.2）
- 響くテストの結果を写している文書を扱っている（§4.3）
- 変える文書の見本を守る決まりに挙げている（§4.4）

測ったのに計画に無いファイル（影響範囲・響くテスト・探して見つかった参照先・つながっているファイル・書式の見本）は、
落とす代わりに検査が計画の該当する見出しへ「未判断」の行として書き足す（参照先のファイルには一致した行を添える）。
モデルは測った結果のファイルを開かずに、その行を判断に書き換える。「未判断」が残る計画は通さない。
形の指摘があっても測るところまで進め、指摘を 1 回で出し切る（やり直しの回数を減らす）。

## 7. 変えたあとの契約（`verify-apply`）

verify-plan が通ったときに控えた印と今を比べ、scope の中で中身が変わったファイルを側ごとに求める。
印を explore ではなく verify-plan で取るのは、explore はモデルが呼ぶかどうかを選べるが、verify-plan は
ハーネスが必ず confirm の直前に実行するため（練り直しのたびに取り直すので、古い印が残らない）。

- 自分の変更案があるのに自分が変わっていない → 落とす
- 自分の変更案・参照先の変更案に挙げたファイル（フォルダならその中のどれか）を変えていない → 落とす（途中で止まらせない）
- 設定したスキル・道具の記録が `.codd/apply.md` に無い → 落とす（§5.7）
- 自分で変えたファイルが、自分の変更案と影響範囲に挙げたパス（フォルダを挙げたらその中）の外にある → 落とす
- 参照先で変えたファイルが、その参照先について参照先の変更案に挙げたパスの外にある → 落とす
- 参照先の変更案に挙げた参照先が変わっていない → 落とす（参照先ごと）
- 参照先の変更案に無い参照先が変わった → 落とす（了承されていない変更を参照先に入れない。参照先ごと）
- 参照先が変わったら、実際の変更から影響範囲を測り直し、測ったファイルを直したか「変更不要」としたか（§4）
- 変えたファイルとパスでつながったほかの側のファイルを扱ったか、足したパスが実在するか、消したファイルを指したままのところが無いか（§4.1）
- テストの変更案のテストをすべて変え、測り直した響くテストを直したか「変更不要」としたか（§4.2）
- 変えた文書が控えた見出しの並びを保っているか（§4.4）
- 自分の `codd.json` の `test` と `check`、変わった参照先それぞれに置いた `codd.json` の `test` と `check` を実行する
- そのあと、文書の evidence の印が今の結果と合い、目安を満たすか（§4.3）

落ちたら stuck へ。人の判断が要らない理由だけなら訊かずに apply へ戻し（2 回まで）、
そうでなければ次の手を利用者に訊く（§2.1）。

## 8. やらないこと

- コミット（変更の確認とコミットは利用者がそれぞれのリポジトリで行う）
- 参照先のパスの自動発見（`codd.json` を手で直す）
- 参照先どうしの関係（参照先 A を変えたときの参照先 B への影響）。測るのは自分への影響だけ
- 状態の持ち越し（確認は会話の中で待つ。やり直しは同じ会話の中で stuck から（§2.1）。収まらないぶんは「今回やらないこと」として伝えるだけで、
  次の回の入力にはしない）
- 常駐・監視（graphify のグラフも使うときに確かめて作り直す。定期的な点検は `lint` を CI などの定期実行から呼ぶ）

### 8.1 codd-gate から取り込まなかったもの

codd-gate の機能のうち、「1 回の変更を、その会話の中で、実装と設計書の両方にわたって一貫させる」に合うものだけを採った（§4.1）。

| codd-gate の機能 | 取り込まない理由 |
|---|---|
| `scan` の地図の保存と、負債の件数を増やさないラチェット（`--update-baseline`・`tasks --debt`） | リポジトリ全体の積み残しを扱う仕組みで、1 回で終わる（§1.1）と合わない。前からある壊れは足した行だけを見ることで対象外にした |
| `tasks` の JSON と、別のツールへの受け渡し | 次の回へ状態を持ち越さない（§8）。収まらないぶんは「今回やらないこと」で伝える |
| `check --fresh`（更新日時で古さを見る） | 更新日時は clone や checkout で変わり、決定的でない。変わったかは中身のハッシュで測る（§7） |
| テストの import によるつながり | テストは仕様そのものではなく、確かめ方は `check` に任せる。言語ごとの規則を持ち込むと、プロジェクトを選ばない前提に反する（名前・語幹・文字列の一致は言語を問わないので §4.2 で使う） |
| Green / Amber / Gray の分類と `--strict` のような厳しさの切り替え | verify-plan・verify-apply が通るか落ちるかで決まり、落ちたら直してやり直す。段階を足すと抜け道になる |
| 複数リポジトリの登録簿・`--sync` による取り寄せ・`.kiro` の設定 | 参照先は `refs` に手元のパスで書く（§5.4）。取り寄せは通信と認証に頼り、可搬性を下げる |


計画はルートの `.plans/` に作る。点検で読む記録は `.plans/` だけとし、旧 `docs/.plans/`・`docs/.plan/` は読まない。
計画の検査が通ったあと、確認前に説明コメントと変更不要の項目を除く。
判断を含む検査用の本文は `.codd/plan-check.json` に、利用者向けの計画のパス・ハッシュと合わせて控える。
再検査・変更後の検査では同じ計画の判断だけを復元し、計画と内部の判断の両方を承認後の変更検出に含める。
終了時の結果にも変更不要を載せない。
