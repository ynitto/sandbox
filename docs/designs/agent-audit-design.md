## 1. TL;DR

**何を作るか**: agent-project / agent-flow / agent-amigos / agent-loop の実行証跡と、
エージェント CLI 自身のセッションログを**読み取り専用で**収集・正規化し、(a) トークン使用量の
実測集計と (b) 知見・スキル改善点の蒸留を行う独立 CLI。

**主要な決定**:

1. 読み手に徹する。4 ツールは無改造で、結合はファイルの読み取りとデータ契約だけ。
2. 決定的にできる処理に LLM を使わない。LLM は map（extract）と reduce（distill）の 2 段だけ。
3. CLI の作法（ログの所在と形式）は `agents/<name>.json` の宣言で吸収し、本体に分岐を書かない。

**却下した主要案**: エンジンを改造してセッション ID と `@agent-usage` を出させる案。
実測は既に CLI 自身のログにあり、4 ツールを触らずに読めるので、改造の対価に見合わない。

**読むべき人**: 実測トークンや実行品質を見たい人、新しい CLI のログを収集させたい人、
洞察を学習ループへ流す実装者。
**読まなくてよい人**: 可視化 UI が欲しい人（それは agent-dashboard の領分。audit は JSON を出すまで）。

## 2. 背景と課題

2026-08-03 の実装横断調査で 4 点が確定した。

**トークン計測の配管は完成しているが、実測が流れていない。** `parse_usage`（stderr の
`@agent-usage`）→ node-budget 台帳の経路は 3 ツールに実装済みなのに、同梱の CLI 定義は
どれも `@agent-usage` を出さない。台帳の実態は「実測秒 + rates による読み出し時推定」だ。
**一方で CLI 自身のセッションログには実測トークンが残っている**のに、読むツールが無い。

**どのツールも transcript を保存していない。** flow は stdout を残すが、amigos は JSON パース後に
生テキストを破棄、project は抜粋だけ、loop は tmux ペインに打鍵するため stdout 自体を見ない。
セッション ID もどのツールも記録していない。

**決定的に読める実行証跡は既に豊富。** flow バスの events / meta、project の run-log と journal、
amigos の events と delivery、失敗トリアージの `[agent-error:*]` タグ、verify receipt。
これらの集計に LLM は要らない。

**知見はノードに死蔵される。** 学習ループの「捕捉→共有→蒸留→強制→評価」のうち、タスク経由の
decisions / learn は agent-project が担うが、**セッションそのもの**（失敗の経緯、リトライの内訳、
プロンプトの癖、スキルが選ばれなかった事実）を横断的に観測する道具が無い。

agent-audit はこの 4 点を「読むだけの独立 CLI + 限定された LLM 蒸留」で埋める。

### 2.1 非目標

- **リアルタイム監視・可視化 UI**。agent-dashboard の領分で、audit は JSON を出すまで。
- **done 判定・品質ゲート**。agent-project / codd-gate の領分で、audit は洞察とタスク候補まで。
- **rules.md / skills への自動昇格**。強制・評価は agent-project の学習ループの担当。
- **エンジン改造**。セッション ID 記録や `@agent-usage` 出力の追加は別提案。本設計は無改造で
  成立する範囲に閉じる。
- **中央収集サーバ・ノード横断の生ログ集約**。ノード間で交換してよいのは蒸留済みの洞察・
  タスク・集計だけで、その転送は既存の state repo / 板の仕組みに委ねる。

## 3. 主要な設計判断

### 3.1 読み手に徹する（エンジン改造を却下）

**判断**: 4 ツールのどれにも依存せず、結合は**ファイルの読み取りとデータ契約のみ**にする。
書くのは audit ディレクトリと、明示フラグを付けたときの型付き許可パスだけ。

**文脈**: 実測トークンが欲しいだけなら、各エンジンに `@agent-usage` を出させ、セッション ID を
記録させるのが素直に見える。だが 4 ツール × 各 CLI 定義に手を入れることになり、audit を使わない
人にも変更が乗る。しかも欲しい実測は**既に CLI 自身のログにある**。

**選択肢と却下理由**:

- *エンジンを改造してセッション ID と usage を出させる*: 却下。改造の範囲が 4 ツールへ広がり、
  audit の価値が出る前に他ツールの回帰リスクを負う。読めば済むものを書かせない。
- *中央の収集サーバを立てる*: 却下。生ログがノードを出ることになり、秘密の扱いが一段難しくなる。
  ノード間で交換してよいのは蒸留済みの層だけだ。
- *他ツールの台帳へ直接書き足す*: 却下。台帳の書き手が増えると、どちらが正かが決まらなくなる。

**トレードオフ**: 各 CLI のログ形式を audit 側で読む責務を負う。エンジン側の情報（セッション ID）が
無いぶん、相関は時刻と cwd の突き合わせになり、一意に決まらない組は結合しない。

**確信度**: 高い。エンジン無改造・CLI 単独利用の両方で価値が出ることが M1 の時点で確認できている。

**例外は 2 つだけ**で、どちらも明示フラグが要る。`calibrate --write` は budget の `rates` を、
`tune --apply` は agent-tuning / agent-profiles / rates の**型付き許可パス**を書く。どちらも
「実測から機械的に決められる宣言」に限っている——ここを広げると agent-audit が他ツールの設定の
第 2 の書き手になり、どちらが正かが決まらなくなる。

### 3.2 決定的にできる処理に LLM を使わない

**判断**: 収集・正規化・クリーニング・相関・集計・クラスタリング・レポート描画は stdlib のみで
再現可能にする。LLM は extract（map）/ distill（reduce）/ review の 3 purpose に閉じる。

**文脈**: 「ログを LLM に読ませて要約する」は書くのが速いが、同じ入力から同じ答えが出ない。
効果測定（P4）は前後比較なので、集計そのものが揺れると測れない。

**選択肢と却下理由**: *集計まで LLM に任せる案*は却下。再現しない数字は改善の根拠にならない。
*逆に全部を決定的にする案*も却下——「失敗の経緯から何を学ぶか」は決定的に書けない。
分けどころは**事実の集計**（決定的）と**意味の抽出**（LLM）だ。

**トレードオフ**: 観測の質が extract に使うモデルに依存する。だから観測レコードには
`extract_agent` / `extract_model` を残し、どのモデルが抽出したかを後から評価できるようにした。

**確信度**: 高い。

### 3.3 LLM は map と reduce の 2 段に分け、段ごとにモデルを選ぶ

**判断**: レコード → 観測（extract・1 レコード 1 回の map）と、観測クラスタ → 洞察
（distill・クラスタ 1 つ 1 回の reduce）を分け、purpose ごとに CLI とモデルを選べるようにする。

**文脈**: 1 段で強いモデルに全部読ませると、レコード数に比例してコストが線形に増える。しかし
extract がやるのは「この 1 本のログで何が起きたか」の抽出で、弱いモデルでも足りる。

**選択肢と却下理由**: *1 段で強モデルに通す案*は却下。コストが源泉の量に直結し、収集を増やすほど
使えなくなる。*extract も決定的ルールで済ませる案*も却下——正規表現で拾えるのは既知の失敗型だけで、
「知らない失敗」を見つけるのが目的だった。

**トレードオフ**: 段が増えるぶん、どこで止まったかの管理が要る。処理済みカーソル・段別の
呼び出し上限・間隔と蓄積のゲートで有界にした。`--force` が外せるのはゲートだけで、上限と
node-budget は外せない。

**確信度**: 高い。

### 3.4 CLI の作法は定義ファイルの宣言で吸収する（`session_log` 契約）

**判断**: 「どこに・どの形式でセッションログがあるか」を `agents/<name>.json` に additive な
`session_log` ブロックとして宣言させ、パーサは format ごとに 1 実装だけ持つ。

**文脈**: CLI ごとにログの置き場も形式も違う。これを audit 側の分岐で吸収すると、CLI が増える
たびに本体を触ることになる。エージェント CLI プラグイン契約は既に「CLI の作法の変更は JSON 1
ファイルで完結」という受入条件を持っており、ログの所在にも同じ条件を適用できる。

**選択肢と却下理由**: *CLI 名で分岐する案*は却下。プラグイン契約を作った理由そのものを崩す。
*ログ形式を 1 つに正規化させる案*も却下——CLI 側に変更を要求することになり、§3.1 と矛盾する。

**トレードオフ**: format は閉じた enum なので、既存 format に当てはまらない CLI はパーサの追加が
要る。ただし**既存 format なら JSON への追記だけ**で収集できる。未知の format と未宣言の CLI は
「未収集」と明示し、黙ってスキップしない。

**確信度**: 高い。実際 opencode は kiro 形では読めず `opencode-sqlite` を足したが、agent-ollama は
既存の進捗ログに会話本文を載せる形で `jsonl-dir` に相乗りでき、宣言だけで収集できた。

### 3.5 環境変数を導入しない・見ない

**判断**: 書き先も源泉の場所も、**引数 > 設定ファイル > 組み込み既定**の 3 段だけで解決する。
agent-audit 固有の環境変数を作らず、他ツールの `$AGENT_*_DIR` も見ない。

**文脈**: agent-audit は cron・agent-loop の定期プロンプト・手元の手動と、実行環境が変わりやすい。
環境変数依存があると「同じ設定ファイルなのに置き場所が違う」事故を作る。

**選択肢と却下理由**: *読む相手の契約が持つ env 上書きを尊重する案*は却下。他ツールの env 契約は
その契約の所有者のもので、audit が乗ると「どちらの env が効くか」が実行経路で変わる。読む場所も
設定ファイルへ明示させる。

**トレードオフ**: 他ツールが env で置き場所を変えている環境では、audit 側にも同じ場所を書く手間が
残る。**書いたことが効く**ほうを取った。

**確信度**: 高い。この不変条件はテストで固定してある。

## 4. 全体像

この節は概要の粒度。源泉の表・レコード契約・設定キー・上限は仕様書にある。

```
                （読み取りのみ・無改造）                        audit ディレクトリ（唯一の書き先）
  ┌─ 源泉 ──────────────────────────────┐   collect    ┌──────────────────────────────┐
  │ node-budget 台帳 ledger/*.jsonl     │ ──────────▶ │ records/<YYYYMMDD>.jsonl      │
  │ agent-flow バス runs/<id>/…         │  決定的      │ transcripts/…（任意・ローカル）│
  │ agent-project run-log.jsonl         │  増分        │ state.json（収集カーソル）     │
  │ agent-amigos missions/<mid>/…       │  冪等        └──────────────┬───────────────┘
  │ agent-loop の宣言済みログ            │                            │
  │ CLI ネイティブストア・CLI 残枠        │        ┌───────────────────┼───────────────────┐
  │ 記憶 3 層 + moltbook のメタデータ     │        │ 決定的（LLM 不使用）│ LLM（段別にモデル選択）
  └─────────────────────────────────────┘        ▼                   ▼
                                      usage / stats / ratings  extract（map・弱モデル可）
                                      trials / report / calibrate    │ observations/*.jsonl
                                                 ▲                   ▼
                                                 │             cluster（決定的・distill の内部段）
                                                 │                   ▼
                                                 │             distill（reduce・中〜強モデル）
                                                 └────────┬──────────┘ insights/<id>.json
                                                          ▼
                                            report・tasks（task.schema.json）・tune
```

### 4.1 measured と estimated を混ぜない

台帳には**実測できた行だけ**トークンを書き、未報告行は読み出し側が `rates` で推定する。
集計は measured と estimated を別掲する。混ぜると「実測が増えた」のか「推定係数が変わった」のかが
区別できなくなり、較正の効果そのものが測れない。

相関（セッションと実行の突き合わせ）は時刻と cwd で行い、**一意に決まらなければ結合しない**。
推測で繋いだ組は、後から見ると実測と見分けがつかないからだ。

### 4.2 洞察から宣言への還流

`tune` は洞察を型付きの調整候補に変え、`--apply` で許可パスだけ宣言へ昇格させる。昇格した調整は
`tune_evaluation_runs` 回の評価を受け、品質が `tune_quality_floor` を割るか `tune_max_quality_drop`
を超えて落ちたら**退役**する。総量は 1 回あたりと累計の両方で規制する。

自動昇格を持ちつつ暴走させないための線がここだ。書き込みは型付きの許可パスだけ、評価は決定的な
集計、悪化したら自動で戻す。任意パス・任意コマンドの書き込み口は持たない。
