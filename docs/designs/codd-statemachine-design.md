# codd-statemachine 設計 — 実装と設計書の一貫性を保って変えるステートマシン

- 実装: `tools/codd-statemachine/`（配布物は `machine/`、置き先では `.statemachine/codd/`）
- 使い方: [`tools/codd-statemachine/README.md`](../../tools/codd-statemachine/README.md)
- [codd-gate](./codd-gate-design.md) とは別物。codd-gate は 1 リポジトリ内の doc↔code↔test のドリフトを受け入れ前に**止める**
  決定的ゲート、codd-statemachine は実装と設計書をまたいで変更を**練って確かめてから入れる**ステートマシン。
  codd-gate のうち、1 回の変更の中で決まるもの（パスのつながりと、その壊れ）だけを取り込んだ（§4.1・§8.1）
- 名前: ツールとしては codd-statemachine。置き先の名前（`.statemachine/codd/`・`codd.json`・`.codd/`・`codd.py`）は
  `codd` のまま据え置く。すでに置いたリポジトリの設定と呼び方（「codd のステートマシンを実行して」）を壊さないため

## 1. 目的と前提

実装と設計書が別リポジトリ（別フォルダ）にあり、片方だけが直されてもう片方と食い違う。
codd-statemachine は、片方を変える前に**参照先を読み、自分の現状とのずれを見せ、了承を得てから変える**。
ずれを解消するために参照先を変える必要があれば、その変更案と自分への影響範囲まで見せたうえで両方を変える。

- 同じ定義を両リポジトリに置く（対称）。違いは `codd.json` の `side` と `refs`（と `skills`）だけ。
  実装で動かせば参照先は設計書、設計書で動かせば参照先は実装。参照先はいくつでも持てる。
  同じリポジトリの別フォルダを参照先にしてもよい（§5.5）
- 参照先のパスは手で設定する（自動発見しない）
- 計画を練るとき・変えるときに使うスキルを、リポジトリごとに設定できる（§5.3）
- **できるだけ単純なハーネスにする**。ステートは 4 つで、状態ファイルも往復の管理も持たない
- **1 回の実行は 1 つの会話で終わる**（§1.1）
- **プロジェクトを選ばない**。依存は python3 と git だけで、言語・ビルド・フォルダの切り方を前提にしない。
  プロジェクトごとの違い（検査コマンド・使うスキル・受け持つフォルダ・1 回の上限）は `codd.json` に寄せる
- **モデルの申告を信じない**。一貫性に効くこと（根拠が実在するか・計画どおりのファイルだけを変えたか・
  影響範囲）はスクリプトが測り、測れない判断（分類・変更案）だけをモデルに任せる。
  出力だけでなく、入力（影響箇所の見つけ漏れ）と過程（決まり・スキル・道具を使ったか、最後までやったか）も止める（§1.2）
- 参照先と自分の探索には graphify を使えるときは使い、グラフは自動で作り直す

### 1.1 1 回の実行で終わる

コードや文書についてやりたいことを 1 つ受け取り、計画・確認・変更・結果の報告までを 1 つの会話の中で終える。
途中の状態を次の会話へ持ち越さない（§8）。そのために、計画の大きさを入口で絞る。

- 計画が変えるファイル（自分の変更案・参照先の変更案・「変更不要」でない影響範囲）の数が `max_files`（既定 20）を
  超えたら verify-plan が落とす。モデルはやりたいことを絞り、残りを計画の「今回やらないこと」に書く
- done は「今回やらないこと」を、次の回にそのまま渡せる形で利用者に伝える。続きは新しい実行として始める

上限はファイル数で測る。行数やトークンはモデルと言語で意味が変わるが、ファイル数は計画から決定的に数えられ、
変更・確認・検査の手間とおおむね比例する。

### 1.2 入力・過程・出力を確かめる

| 段 | 失敗の形 | 止め方 | 節 |
|---|---|---|---|
| 入力 | 影響箇所を見つけ損ねる（呼び出し元・同じ名前に触れる設計書） | 計画の名前から自分と参照先の両方を測り、計画が扱っていなければ落とす | §4 |
| 入力 | 名前は一致しないが、パスで指し合っているファイルを見落とす | 変えるファイルとつながったほかの側のファイルを、計画が扱っていなければ落とす | §4.1 |
| 入力 | 読んでいないものを根拠にする | 根拠のパス・行・見出し・名前の実在 | §6 |
| 過程 | プロジェクトの決まりを読まない | 決まりのファイルを自動で挙げ、計画にすべて挙げさせる | §5.7 |
| 過程 | 決めたスキル・道具を使わない | 設定したものを、計画と `.codd/apply.md` にすべて挙げさせる | §5.7 |
| 過程 | 途中で止まる | 計画のファイルをすべて変えたか。終わりの報告はスクリプトが作る | §7・§5.8 |
| 出力 | 計画に無い変更・影響の直し忘れ | 計画外のファイルを落とす。実際の差分から影響を測り直す | §4・§7 |
| 出力 | 書いたパスが無い・消したファイルを指したまま | 変えたファイルの足した行のパスと、消したファイルを指すところを調べる | §4.1 |

スキル・道具を使ったかは、使った記録を求めることでしか確かめられない（スクリプトからエージェントの道具の呼び出しは
見えない）。記録は名前だけでなく「何に使い、何を得たか」を求め、確認（confirm）で利用者が読む。実行結果そのものを
確かめたいものは `check` に入れ、ハーネスに実行させる。

## 2. 流れ

```
plan ─[check: verify-plan]→ confirm ─┬─ OK ─→ apply ─[check: verify-apply]→ done
  ↑  │                               └─ NG ─┐         │
  └──┼──────────────────────────────────────┘         │
     │ 検査がやり直しを使い切っても落ちる                  │
     └──────────────→ stuck ←─────────────────────────┘
                        ├─ PLAN  → plan（練り直す。変えた分は keep-changes で残すか rollback で戻す）
                        ├─ APPLY → apply（計画はそのままで変え直す）
                        └─ STOP  → stopped（やめる。結果を伝える）
```

| ステート | すること | 成果物 | 成否の測り方 |
|---|---|---|---|
| plan | 参照先を探し（`explore`）、前提・制約・その他に分け、自分の現状とのずれを見て、自分の変更案を練る。ずれがあれば参照先の変更案と影響範囲を書く。どちらのリポジトリも変えない | `.codd/plan.md`（`write:`） | `check: verify-plan`（影響範囲の測定を含む） |
| confirm | 計画と測った影響範囲を見せ、利用者の答えを待つ | 答え（`OK` / `NG` と指摘） | `output_validator` |
| apply | 自分の変更案を適用し、参照先の変更案があれば参照先にも適用する。コミットはしない | 両リポジトリの作業中の変更 | `check: verify-apply`（影響範囲の測り直しを含む） |
| done | 変えたファイルを伝える | — | 終端 |
| stuck | `advise` が示す止めた理由・確かめること・選択肢を見せ、利用者の答えを待つ。選ばれたら `rollback` / `keep-changes` を実行する | 答え（`PLAN` / `APPLY` / `STOP` と指示） | `output_validator` |
| stopped | やめたときの結果（`report`）と、残したか戻したかを伝える | — | 終端 |

NG は plan へ戻り、次の plan は `{{answer}}`（confirm の答え。NG と利用者の指摘）を踏まえて練り直す。`answer` は `context:` で空に初期化してあり、初回は空になる。
分岐は `condition_rule`（`check_ok` と confirm の第 1 行）だけで決まり、LLM の YES/NO 評価は使わない。

### 2.1 止まったら、次の手を提案して確かめる

検査は、まず同じステートのやり直し（plan は 2 回、apply は 1 回）で直させる。モデルの読み違いはここで直る。
使い切っても落ちるものは、多くが**利用者にしか決められない**こと（計画に無いファイルを変えてよいか、測った影響を
「変更不要」としてよいか、今回どこまでやるか）か、利用者にしか直せないこと（設定・環境）である。
前の版はここで `escalate` して実行ごと止めていたので、利用者は何が起きたか・どうすればよいかを自分で探す必要があり、
やり直すには最初から始めるしかなかった。いまは `check_on_exhausted: continue` で stuck へ進み、会話の中で次の手を決める。

- 止めた理由は、検査が落ちるたびに `.codd/problems.json` へ段（plan / apply）と一緒に控える（通れば消す）。
  設定の誤り（終了コード 2）も控える
- `advise` が理由を種類に分け（計画に無い変更・変え残し・影響の直し忘れ・参照先の扱い漏れ・壊れたパス・
  スキルと道具・検査コマンド・大きすぎ・根拠と形・設定）、種類ごとに**利用者に確かめること**と**選択肢**を決定的に出す。
  最初に挙がった理由の勧めを全体の勧めにする。モデルが勧めを作らないので、同じ止まり方には同じ提案が出る
- 選択肢は 5 つで、段ごとに出せるものが違う（計画が通っていなければ「変え直す」は出さない）

| 選択肢 | 先に実行 | 次 |
|---|---|---|
| 計画を練り直す | — | plan |
| 計画はそのままで、変え直す | — | apply |
| 変えた分は残して、計画を直す | `keep-changes`（次の verify-plan が変える前の印を取り直さない） | plan |
| 変えた分を戻して、計画から練り直す | `rollback`（verify-plan が通ったときの中身へ戻す） | plan |
| ここでやめる（残すか戻すかも訊く） | 戻すなら `rollback` | stopped |

**やり直しの仕組み。** verify-plan は変える前の印（HEAD と作業中ファイルのハッシュ）に加え、作業中だったファイルの
中身を `.codd/before/` に写す。`rollback` は印から変わったファイルだけを、写しか印の HEAD の中身へ戻し、
印のあとに足したファイルは消す。計画より前から作業中だった変更は、作業中の中身へ戻るので失われない。
途中でコミットされていたら（HEAD が動いていたら）戻さずに知らせる（git の履歴は触らない）。
`keep-changes` は、残した変更を次の verify-apply が「変えた」と数え続けるためにある。印を取り直すと、
残した変更が変える前の状態に含まれてしまい、変え残しとして落ちる。

### 2.2 確認は会話の中で待つ

confirm は、計画を見せて利用者の答えを待つアクションである。statemachine-use を会話の中で回す
（1 ステート 1 ターン）ときは、エージェントが計画を出してターンを終え、利用者の返事を受けて出力を確定する。
実行の途中で人の入力を受け取る仕組みを持たない無人のハーネス（agent-loop の headless 実行など）では、
このステートで止まる——このマシンは会話で使うことを前提にしている。

前の版は「終端で止まり、答えを入力に入れて次の実行で再開する」形だったが、そのために意図の状態・
答え待ち・反映待ちを `state.json` に持つ必要があり、ハーネスが重くなった。会話の中で待てば状態は要らない。

## 3. 前提・制約・その他とずれ

| 分類 | 定義 |
|---|---|
| 前提 | 参照先が「すでにそうなっている」と定めている事実・決定・振る舞い・用語 |
| 制約 | 参照先が「こうしなければならない / してはならない」と課している条件 |
| その他 | それ以外の関係する記述（決まっていないこと・任されていること・補足） |

**ずれ**は、このうち自分の現状（またはやりたいことを実現した姿）と食い違うもの。ずれがあれば、
それを解消するための参照先の変更案と、その変更を自分のリポジトリに適用したときの影響範囲を計画に書く。
ずれを残したまま進めたいなら、それはずれではなく「その他」として書く（検査がずれと変更案の対応を求めるため）。

分類は向きを問わない。実装から設計書を読めば「設計書が定める前提・制約」、設計書から実装を読めば
「実装が既に持っている振る舞い（前提）と、互換性・性能・依存などの条件（制約）」になる。

## 4. 影響範囲の測定

参照先を変えるときの「自分のリポジトリへの影響範囲」は、モデルが書いた一覧をそのまま信じず、**ハーネスが測って突き合わせる**。
利用者が OK と答える材料も、NG で練り直す材料も、測った結果である。

| いつ | 測る語 | 通る条件 | 記録 |
|---|---|---|---|
| verify-plan（confirm の前） | 計画の「自分の変更案」「参照先の変更案」「ずれ」で `…` に囲んだ名前。自分の変更案・参照先の変更案に囲んだ名前が無ければ落とす | 自分で測ったファイル ⊆ 自分の変更案 ∪ 影響範囲に挙げたファイル | `.codd/impact.md` |
| verify-plan（逆向き） | 「自分の変更案」の名前で**参照先**を測る（文字列検索だけ） | 測った参照先のファイル ⊆ 計画が根拠か参照先の変更案として挙げたファイル | `.codd/ref-impact.md` |
| verify-apply（apply の後） | 自分と参照先の実際の差分（`git diff HEAD` の +/- 行の定義・見出し・`…`、新しいファイルの定義・見出し）＋ 計画の名前 | 測ったファイル ⊆ 自分で変えたファイル ∪ 計画で「変更不要」としたファイル | `.codd/impact-after.md` |
| verify-apply（逆向き） | 自分の差分の名前のうち計画に無かったもの | 測った参照先のファイル ⊆ 計画が扱ったファイル ∪ 変えた参照先のファイル | `.codd/ref-impact-after.md` |

- 自分の変更の影響も測る。参照先を変えない計画でも、関数の呼び出し元や同じ名前に触れる設計書を見落とさないため
- 逆向き（参照先）は `git grep` だけで測る。graphify の `query` は関係の近いものまで広く拾うので、
  「扱ったか」を問う検査には決定的な文字列の一致を使う。関係の無いファイルは「その他」に「関係なし: 理由」と根拠付きで書く
- 測り方は graphify `affected`（依存している呼び出し元・参照元を深さ 2 までたどる）と `git grep --untracked`。
  識別子は語単位（`-w`）で引き、`hello` で `helloWorld` を拾わない。1 回に測るファイルは 40 まで
- 変えたあとに測り直すのは、参照先を計画より広く変えたときの影響を取りこぼさないため。計画時の語だけでは、
  計画に書かれなかった変更の影響が見えない
- 「自分で変えたファイル」は、verify-plan が通ったときに控えた作業中ファイルの中身のハッシュと HEAD から比べる
  （apply の前から作業中だったファイルを「変えた」と数えない。§7）
- 「変更不要」は計画の影響範囲の項目に `変更不要: 理由` と書いたもの。利用者の確認を経た計画にしか書けない
  （apply で足すときは利用者に確かめる）

### 4.1 パスのつながり（codd-gate から取り込んだもの）

名前の一致（§4）は、ファイル同士が**パスで**指し合う関係を拾えない（設計書の対応表が `src/app.py` を挙げている、
コードのコメントが設計書を指している、など）。codd-gate の「主張の抽出」をそのまま使い、これを両向きに測る。

- 拾う書き方: どのファイルでも注記 `coherence: doc|code|test=パス`。文書（`.md`・`.markdown`・`.rst`・`.adoc`・`.txt`）では
  `` `…` `` に囲んだパスらしいもの（`/` を含むか、既知の拡張子で終わる）とマークダウンのリンク。文書のフェンスと `` `…` `` の中の注記は
  書き方の例とみなして拾わない（codd-gate はフェンスの中の注記も拾うが、ここでは足した行を検査するので例を落とさないことを優先する）
- 解決: `名前:パス` なら参照先 `名前` で。それ以外はリポジトリのルートから、リンクは文書のフォルダからも試す。
  書いた側のリポジトリに実在すればそちらを採り（同じリポジトリの別フォルダは scope で側を決める）、無ければほかの側を探す。
  リポジトリの外（`../` で出る）は扱わない
- 「つながり」: ファイル A が B を指すか、B が A を指す。逆向き（ほかの側のどのファイルが A を指すか）は、A のファイル名で
  `git grep -l` して候補を絞ってから、候補の主張を解決する（全ファイルを読まない。1 側 200 ファイルまで）

| いつ | 対象 | 通る条件 | 記録 |
|---|---|---|---|
| verify-plan | 自分の変更案のファイル ↔ 参照先 | つながった参照先のファイル ⊆ 計画が根拠か参照先の変更案として挙げたもの | `.codd/trace.md` |
| verify-plan | 参照先の変更案のファイル ↔ 自分 | つながった自分のファイル ⊆ 自分の変更案 ∪ 影響範囲 | 同上 |
| verify-apply | 自分の変えたファイル ↔ 参照先 | ⊆ 計画が扱ったもの ∪ 変えた参照先のファイル | `.codd/trace-after.md` |
| verify-apply | 参照先の変えたファイル ↔ 自分 | ⊆ 自分で変えたファイル ∪ 「変更不要」 | 同上 |
| verify-apply | 変えたファイルの**足した行**（`git diff HEAD -U0`。未追跡は全行）の主張 | どれかの側に実在する（壊れたパス）。`` `…` `` のパスは、先頭のフォルダがどれかの側に実在するときだけ調べる（`path/to/x.md` のような例を落とさない） | 同上 |
| verify-apply | 消したファイル | それを指したままの主張が、どの側にも無い（宙に浮いた参照） | 同上 |
| report | 自分の変えたファイル | 参照先とつながっていないものを知らせる（落とさない） | `.codd/report.md` |

足した行だけを調べるのは、1 回の変更が持ち込んだ誤りだけを止め、前からある壊れたパス（リポジトリ全体の負債）を
この回の仕事にしないため（§1.1）。

## 5. 下請けスクリプト（`codd.py`、python3 + git のみ）

| コマンド | 仕事 |
|---|---|
| `show [--phase plan\|apply]` | この側・参照先の一覧と、段階ごとに使うスキルを `` `名前` スキル `` の形で示す（§5.3） |
| `explore --term 語… [--ref 名前…]` | 参照先（既定はすべて）を graphify `query` と `git grep` で引き、`.codd/explore.md` に候補を `名前:パス` でまとめる |
| `impact --term 語…` | 自分のリポジトリを graphify `affected` と `git grep` で引く（手で調べる用。検査は §4 の測定を自分で呼ぶ） |
| `verify-plan` | 計画の形と根拠の検査（§6）と、影響範囲の測定（§4）。通ったら、自分とすべての参照先の変える前の印（HEAD と作業中ファイルの中身のハッシュ）を `.codd/before.json` に控える |
| `verify-apply` | 変えたあとの検査（§7）と、影響範囲の測り直し（§4） |
| `report` | 終わりの報告（§5.8） |

### 5.1 graphify の自動更新

リポジトリの**印**（HEAD と、`git diff HEAD`、未追跡ファイルの名前と中身から作るハッシュ）をグラフの横に控え、
`explore` / `impact` のたびに今の印と比べる。違えば `graphify update . --force` で作り直し、同じなら前のグラフを使う。
コミットだけでなく作業中の変更でも作り直すので、apply の途中や計画の練り直しで古いグラフを引くことがない。
`--force` は、削除や改名でノードが減っても作り直した方を採るため（古いノードを残さない）。

グラフは `GRAPHIFY_OUT` で自分の `.codd/graph/own/` と `.codd/graph/ref-<名前>/` に書く。参照先の中に `graphify-out/` を作らない。
`update` は AST と見出しの抽出だけで LLM を使わない。設計書の意味的な抽出（`graphify extract`）は重いので自動では回さない。

常駐の監視（`graphify watch`）や git hook は入れない。使うときに確かめて作り直す方が、仕組みが少なく、
参照先に何も仕込まずに済む。

### 5.2 文字列検索を並べる

graphify の有無にかかわらず `git grep --untracked -F -i` を並べる。グラフに入らない文書と、
まだコミットしていないファイルを拾うため。graphify が無い・`graphify: off`・作り直しに失敗したときは、
文字列検索だけで同じ形の報告を出す。

### 5.3 使うスキル

`codd.json` の `skills` に、段階ごとに使うスキルの名前を並べる。

| 設定 | 使うとき |
|---|---|
| `skills.plan` | 計画を練るとき（このリポジトリの側で読む・練るときの作法） |
| `skills.apply` | このリポジトリを変えるとき |
| `refs[].skills` | その参照先を変えるとき。書かなければ、参照先に置いた `codd.json` の `skills.apply` |

参照先を変えるときに参照先自身の設定を使うのは、「そのリポジトリをどう変えるか」はそのリポジトリの持ち物だから
（実装なら `tdd`、設計書なら文書を書くスキル、のように側ごとに決まる）。参照先に codd を置いていないときや、
この側から変えるときだけ作法を変えたいときは `refs[].skills` で上書きする。

アクションは `codd.py show --phase …` を実行し、出てきたスキルを読み込んで従う。statemachine-use の実行ハーネスは
アクション本文の `` `名前` スキル `` 表記でスキルを読み込むが、スキルは設定で変わるので本文に固定では書けない。
`show` がその表記で出力し、会話で回すエージェントがそれを読んで読み込む（confirm が会話を前提にしているので、
無人の実行で自動読み込みを効かせる必要は無い）。

### 5.4 参照先が複数あるとき

- `refs` の各項目は `name` と `path`。`name` は英数字と `_` `.` `-`（省略時はフォルダ名）で、参照先ごとに違う
- 計画の根拠と参照先の変更案のパスは `名前:パス` で書く。パスだけのときは、実在する参照先が 1 つならそれに決め、
  複数にあれば曖昧として落とす（名前を書くよう求める）。参照先が 1 つなら従来どおりパスだけでよい
- 参照先の変更案は、まだ無いファイル（親のフォルダはある）も書ける——新しい文書を足す変更案のため
- 変更案に挙げた参照先の集まりが「変えてよい参照先」。§7 はこれと実際に変わった参照先を 1 つずつ突き合わせる
- 影響範囲の測り直しは、変わった参照先すべての差分から語を集めて 1 回測る（測る先は自分のリポジトリだけ）
- 以前の `ref_path`（参照先が 1 つだった頃の書き方）も読む。インストーラーは `--ref` を渡したときに `refs` へ置き換える

### 5.5 同じリポジトリの別フォルダ

実装と設計書が同じリポジトリにあるプロジェクトも多い。`refs[].path` を `.` にし、自分の `scope` と参照先の
`refs[].scope` にそれぞれが受け持つフォルダを書く。

- 探す（`git grep` のパス指定、graphify の結果の絞り込み）・根拠を認める・変わったかを測る・差分から語を拾うのは、
  それぞれの scope の中だけ。グラフはリポジトリ全体で 1 つ作って共有する
- 同じリポジトリを使う側どうしは、どれも scope を持ち、互いに重ならないこと。そうでなければ動かす前に止める
  （重なると、どちらを変えたのかが決まらない）
- 参照先に置いた `codd.json` は読まない（自分の設定そのものなので）。参照先の呼び名は自分の反対側になる
- scope は別のリポジトリでも使える（参照先のリポジトリのうち `docs/` だけを読む、など）

### 5.6 設定の誤りは動かす前に止める

`codd.json` と `refs[]` の知らない項目（綴り違い）、`scope` の外向きのパス、`max_files` の不正な値は、
どのコマンドでも最初に `ERROR`（終了コード 2）で止める。黙って既定値で動くと、利用者は設定が効いていないことに気付けない。

### 5.7 守る決まり・使うスキルと道具

- 決まりのファイル: 自分と（別のリポジトリの）参照先にある `CLAUDE.md`・`AGENTS.md`・`GEMINI.md`・
  `.github/copilot-instructions.md`・`CONTRIBUTING.md` と、`codd.json` の `rules`・`refs[].rules`（と参照先に置いた
  `codd.json` の `rules`）。`rules` は glob も書ける（git の `:(glob)` と同じ意味で、追跡中と未追跡のファイルから引く）。
  当たらないものは `show` が知らせる（綴り違いやファイルの移動で、決まりが黙って外れないように）。`show` が挙げ、計画の「守る決まり」に
  すべて（参照先のものは `名前:パス`）挙がっていなければ verify-plan が落とす。名前をそろえたのは、多くのプロジェクトで
  エージェント向けの約束がこの名前で置かれているため（プロジェクトごとの設定なしに効く）
- 決まりの発見: パスか最初の見出しに決まりらしい語（ルール・規約・コーディング・rules・guideline・convention など）を
  含むマークダウンを候補にする（`rules`）。候補は設定に書くまで検査の対象にしない——語の一致だけでは決まりとは限らず、
  誤って挙げると毎回その読み込みを強いるため。書くのは利用者の同意があるとき: `install.py`（置くこと自体が同意。
  `--no-discover-rules` でやめる）と、確認（confirm）で訊いて `rules --write --only` するとき。
  あとから増えた候補は `show` に出るので、計画のときに読まれる
- スキルと道具: `skills.plan`・`tools.plan` は計画の「使ったスキルと道具」に、`skills.apply`・`tools.apply`
  （と変えた参照先の分）は `.codd/apply.md` にすべて挙がっていなければ落とす。`.codd/apply.md` は変える前の印より新しいこと
  （前の回の記録を使い回させない）
- リポジトリのスキル: `skill_dirs`（既定 `.agents/skills`）の `名前/SKILL.md` を、設定しなくても `show` が挙げる
  （名前と説明は SKILL.md の先頭の `name` / `description`。30 まで）。計画の「使ったスキルと道具」に、使った結果か
  「使わない: 理由」が無ければ verify-plan が落とす。関係するかの判断はモデルに任せるが、**全部に目を通したこと**は
  測れるようにする。使うことを強制しないのは、説明だけでは関係するかを決定的に決められないため
- カスタムエージェント: `install.py` が kiro-cli（`.kiro/agents/codd.json`）と GitHub Copilot（`.github/agents/codd.agent.md`）
  向けに、変える依頼は必ずこのマシンで進めるエージェントを書く。指示は `agents/codd-agent.md` 1 つから両方へ写す。
  statemachine-use が無い環境でも回せるよう、`workflow.yaml` の読み方（action・check と再投入・condition_rule・答えを待つ
  ステート）を指示に含める。kiro-cli では `agentSpawn` の hook で `codd.py show` を読み込ませる。エージェントのファイルは
  マシンの一部として、探す・変わったかを測る対象から外す

### 5.8 終わりの報告（`report`）

done は `codd.py report` の出力をそのまま伝える。計画のファイルごとの「変えた / まだ」、変えたあとに測った影響範囲の
「直した / 変更不要 / 未対応」、「今回やらないこと」を、計画・変える前の印・今の中身から作る。verify-apply が通ったときの
中身を `.codd/applied.json` に控え、今と違えば「通ったあとに、さらに変わっている」として終了コード 1 を返す。
報告をモデルの記憶でまとめさせると、変え残しや直していない影響を「終わった」と伝えてしまうため。

## 6. 計画の契約（`verify-plan`）

`templates/plan.md` の見出し（やりたいこと / 守る決まり / 使ったスキルと道具 / 参照先の前提 / 参照先の制約 / 参照先のその他 / ずれ /
自分の変更案 / 参照先の変更案 / 影響範囲 / 今回やらないこと）がこの順にそろい、中身が空でないこと。加えて:

- 前提・制約・その他・ずれは「なし」か箇条書き。各項目に**参照先に実在するパス**がある（読んでいないものを書かせない）。
  参照先が複数あって決まらないパスは `名前:パス` を求める
- 根拠を `パス:行`・`パス:行-行`・`パス#見出し` で書いたときは、その行がファイルの中にあり、その見出しが
  （GitHub のアンカーと同じ正規化で）実在すること。ファイルだけでなく箇所まで偽れないようにする
- 前提・制約・その他で `` `…` `` に囲んだ名前（パスを除く）は、その項目の根拠のファイルのどれかに書かれていること
  （大文字小文字は問わず、末尾の `()` は落として探す）。ずれは自分の側の名前も書くので対象にしない
- 自分の変更案の各項目に自分のリポジトリのパスがある（まだ無いファイルは、親のフォルダがあり拡張子があれば認める）
- 参照先の変更案の各項目が、どの参照先を変えるかを決められる（§5.4）
- ずれがある ⇔ 参照先の変更案がある
- 参照先の変更案があれば影響範囲があり、影響範囲の各項目に**自分のリポジトリに実在するパス**がある
- 参照先の変更案に `…` で囲んだ名前があり、それで測った影響範囲（§4）をすべて挙げている
- 変えるファイルの数が `max_files` 以下（§1.1）
- 自分の変更案・参照先の変更案のファイルとパスでつながったほかの側のファイルを扱っている（§4.1）

## 7. 変えたあとの契約（`verify-apply`）

verify-plan が通ったときに控えた印と今を比べ、scope の中で中身が変わったファイルを側ごとに求める。
印を explore ではなく verify-plan で取るのは、explore はモデルが呼ぶかどうかを選べるが、verify-plan は
ハーネスが必ず confirm の直前に実行するため（練り直しのたびに取り直すので、古い印が残らない）。

- 自分の変更案があるのに自分が変わっていない → 落とす
- 自分の変更案・参照先の変更案に挙げたファイル（フォルダならその中のどれか）を変えていない → 落とす（途中で止まらせない）
- 設定したスキル・道具の記録が `.codd/apply.md` に無い → 落とす（§5.7）
- 自分で変えたファイルが、自分の変更案と影響範囲に挙げたパス（フォルダを挙げたらその中）の外にある → 落とす
- 参照先で変えたファイルが、その参照先について参照先の変更案に挙げたパスの外にある → 落とす
- 参照先の変更案に挙げた参照先が変わっていない → 落とす（参照先ごと）
- 参照先の変更案に無い参照先が変わった → 落とす（了承されていない変更を参照先に入れない。参照先ごと）
- 参照先が変わったら、実際の変更から影響範囲を測り直し、測ったファイルを直したか「変更不要」としたか（§4）
- 変えたファイルとパスでつながったほかの側のファイルを扱ったか、足したパスが実在するか、消したファイルを指したままのところが無いか（§4.1）
- 自分の `codd.json` の `check`、変わった参照先それぞれに置いた `codd.json` の `check` を実行する

落ちたら apply を 1 回まで再投入し、尽きたら stuck で次の手を利用者に訊く（§2.1）。

## 8. やらないこと

- コミット（変更の確認とコミットは利用者がそれぞれのリポジトリで行う）
- 参照先のパスの自動発見（`codd.json` を手で直す）
- 参照先どうしの関係（参照先 A を変えたときの参照先 B への影響）。測るのは自分への影響だけ
- 状態の持ち越し（確認は会話の中で待つ。やり直しは同じ会話の中で stuck から（§2.1）。収まらないぶんは「今回やらないこと」として伝えるだけで、
  次の回の入力にはしない）
- 常駐・監視（graphify のグラフも使うときに確かめて作り直す）

### 8.1 codd-gate から取り込まなかったもの

codd-gate の機能のうち、「1 回の変更を、その会話の中で、実装と設計書の両方にわたって一貫させる」に合うものだけを採った（§4.1）。

| codd-gate の機能 | 取り込まない理由 |
|---|---|
| `scan` の地図の保存と、負債の件数を増やさないラチェット（`--update-baseline`・`tasks --debt`） | リポジトリ全体の積み残しを扱う仕組みで、1 回で終わる（§1.1）と合わない。前からある壊れは足した行だけを見ることで対象外にした |
| `tasks` の JSON と、別のツールへの受け渡し | 次の回へ状態を持ち越さない（§8）。収まらないぶんは「今回やらないこと」で伝える |
| `check --fresh`（更新日時で古さを見る） | 更新日時は clone や checkout で変わり、決定的でない。変わったかは中身のハッシュで測る（§7） |
| テストの import・名前によるつながり | テストは仕様そのものではなく、確かめ方は `check` に任せる。言語ごとの規則を持ち込むと、プロジェクトを選ばない前提に反する |
| Green / Amber / Gray の分類と `--strict` のような厳しさの切り替え | verify-plan・verify-apply が通るか落ちるかで決まり、落ちたら直してやり直す。段階を足すと抜け道になる |
| 複数リポジトリの登録簿・`--sync` による取り寄せ・`.kiro` の設定 | 参照先は `refs` に手元のパスで書く（§5.4）。取り寄せは通信と認証に頼り、可搬性を下げる |
