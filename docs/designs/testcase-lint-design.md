# testcase-lint 設計

自然文のテストケースを LLM なしで点検する道具。利用者向けの説明は
[tools/testcase-lint/README.md](../../tools/testcase-lint/README.md)。ここには判断の根拠を書く。

## 方針

- **決定的であること。** 同じ入力なら同じ指摘を出す。CI のゲートに置けて、指摘の理由を規則と語の表まで
  たどれる。LLM の判断は入れない（揺れる・費用がかかる・オフラインで動かない）。
- **取りこぼしより誤検知を嫌う規則と、その逆の規則を、重さで分ける。** 構造の欠け・書きかけ・明白な逆の
  期待結果はエラー。語の表に頼る規則（対になる条件など）は参考にとどめ、設定で止められる。
- **入力の形を決めつけない。** LLM が出す JSON / YAML は項目名も入れ子も揺れる。項目名の別名表と、
  「ケースの列を置くキー」を手がかりに木をたどって Case にそろえ、規則は Case だけを見る。

## 構成

| モジュール | 役割 |
|---|---|
| `loader.py` | JSON / YAML を YAML の読み手で読む（行番号・重複キーを取るため）。``` の囲みは外側を空行にして行番号を保つ。別名表で Case にそろえる |
| `text.py` | 正規化（NFKC・小文字）、n-gram の余弦、肯定・否定の判定、数値の条件の抽出 |
| `checks.py` | 規則の本体と語の表 |
| `model.py` | Case・Finding と規則の一覧（コード・分類・既定の重さ） |
| `report.py` / `cli.py` | 出力（text / json / markdown）と入口 |

## 判断の要点

### 似ている度合い

文字の 2〜3 文字組の出現回数（対数）を L2 正規化し、余弦で比べる。分かち書きに頼らないので、
「ログイン画面」「ログインの画面」のような揺れに強い。

- **IDF で重みを付けない。** LLM が出すケースは同じ言い回しの繰り返しが多い。IDF を掛けると共通部分が
  軽くなり、1 文字違いの重複が 0.9 を割った（3000 件の検証で、手で入れた重複 5 組をすべて落とした）。
- 代わりに、長い共通の手順だけで「似ている」と判断しないよう、**期待結果どうしも似ていること**を重複の条件にする。
- 数値と「」で囲んだ値は伏せて比べ、値の集合が違う組は重複にも矛盾にもしない。境界値のケース
  （7 文字と 8 文字）を重複と言わないため。値だけが違う 3 件以上のまとまりは「表にまとめられる」と参考で出す。
- 全組の比較は件数の 2 乗になるので、**All-Pairs の前置フィルタ**で候補を絞る。ベクトルは長さ 1 なので、
  よく出る特徴から並べた前半のノルムが閾値未満なら、前半だけで閾値に届くことはない（コーシー＝シュワルツ）。
  後半だけを索引に入れ、部分和＋前半のノルムが閾値に届かない組を捨てる。**取りこぼしはない**（総当たりと
  一致することをテストで確かめている）。よく出る特徴を単に捨てる近似は、定型文の多い入力で再現率が落ちたので採らない。
  3000 件で 10 秒ほど。

### 矛盾（肯定と否定）

Janome で形態素に分け、節ごとに「中身の語の集合」と「否定の偶奇」を持つ。

- 否定として数えるもの: 助動詞「ない・ぬ・ん」、形容詞「ない」、接頭詞「未・不・非・無」、反対語の表
  （無効／有効、失敗／成功、非表示／表示、なし／あり、hidden／visible など）。
- 偶奇で持つので「未入力ならエラーが表示される」と「入力したらエラーが表示されない」は食い違いにならない。
- 前提＋手順の似ている度合いが `same_steps`（既定 0.92）以上で、値も同じ組だけを比べる。
- 1 つのケースの中では、別々の手順に付いた確認（webui-test の `expect:`）は時間の順なので比べない。
  再試行の前後で「表示される」「表示されない」が並ぶのは正しい。

### 数値の条件と境界値

「N 単位 以上・以下・未満・超・まで・以内」「最大・上限・最小・下限 N」を拾い、直前の名詞のまとまりを対象とする。
境界を含む整数に直し、上限 M なら {M, M+1}、下限 m なら {m−1, m} を境界とする。

- 試した値は、タイトル・前提・手順の「N 単位」（条件として書いた所は除く）と、文字数・桁の条件なら
  入力に使った「」の値の長さから拾う。期待結果は数えない（エラー文言の長さを入力と取り違えたため）。
- 対象の名詞を含むケースだけを見る（ユーザー名とパスワードの 20 文字を混ぜない）。
- 同じ対象・単位・向きで値が違えば C04。要件一覧の本文も条件の出どころにする。

### 異常系と対になる条件

- 異常系は語の表（エラー・失敗・無効・未入力・上限・タイムアウト・権限なし…）か、タイトル・前提・手順に
  否定の節があるかで判定する。**要件ごとではなく機能のまとまり（ファイルと suite / feature）ごと**に見る。
  要件ごとにすると「正しく入れたら通る」だけの要件まで毎回指摘した。
- 対になる条件は、片側の語があって反対側がない組を出す。「あるなら反対も欲しい」だけの組（一覧→0 件、
  送信→通信の失敗、作成→削除）は片方向で見る。語の表に頼るので参考にとどめる。

## やらないこと

- 言い換えの矛盾・意味の重複（埋め込みや LLM が要る）。必要なら、この道具の JSON 出力を前段の篩にして、
  残りだけを LLM に見せる使い方を想定する。
- Gherkin（.feature）・Excel の直接読み込み。LLM に JSON / YAML で出させる前提に絞った。
