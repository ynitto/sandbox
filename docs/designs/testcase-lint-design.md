# testcase-lint 設計

自然文のテストケースを、テストケースとしての妥当性で点検し、ケースと実際のテストの対応と実行結果をつなぐ道具。利用者向けの説明は
[tools/testcase-lint/README.md](../../tools/testcase-lint/README.md)。ここには判断の根拠を書く。

## 方針

- **決定的であること。** 同じ入力なら同じ指摘を出す。CI のゲートに置けて、指摘の理由を規則と語の表まで
  たどれる。期限の点検ではUTCの当日も入力とする。LLM の判断は入れない（揺れる・費用がかかる・オフラインで動かない）。
- **書き方より、不具合を見つけられるかを見る。** 文書としての読みやすさではなく、「このケースで合否を決められるか」
  「実行できるか」「試すべき組を試しているか」「仕様・実装と合っているか」を規則にする。
- **独立して動く。** ほかの道具（ケースを作って動かす道具・文書の整合を取る道具）の名前・設定・作業ファイルに
  触れない（`test/independence.test.js` が検査する）。ケースは JSON / YAML の一般的な形と Gherkin として読み、結果は
  version 1 の items 形式のファイルで渡す。組み合わせ方は README にだけ書く。
- **オプション無しで動かす。** ふだんの使い方は `testcase-lint` だけにする。何を点検するか（ケース・仕様・実装の
  フォルダ、結果ファイル、落とす重さ）は設定ファイルに書き、今のフォルダから親へさかのぼって探す。設定ファイルが
  無ければ、よくあるフォルダ（`tests/cases`・`docs/specs`・`src` など）を探す。ほかの道具の検査コマンドにも
  `testcase-lint` とだけ書けば済み、呼ぶ側に点検の中身を持たせない。出力の 1 行目に、何を点検したかを出す。
- **点検は何も実行しない。** テスト・アプリ・import 先のコードを読むだけにする。テストを動かすのは `run` だけで、
  動かすのは設定に書いたコマンドに限る。
- **取りこぼしより誤検知を嫌う規則と、その逆の規則を、重さで分ける。** 構造の欠け・書きかけ・明白な逆の
  期待結果・仕様の要件の漏れはエラー。語の表に頼る規則は参考にとどめ、設定で止められる。

## 構成

| モジュール | 役割 |
|---|---|
| `load.js` | JSON / YAML を YAML の構文木で読み、行番号付きの小さな木にする（重複キーもここで拾う）。``` の囲みは外側を空行にして行番号を保つ。別名表で Case にそろえる |
| `gherkin.js` | `.feature` を公式パーサーで展開し、load.js が読む形のケースと元の行にする |
| `bindings.js` / `run.js` | ケースと個別テストの対応表の点検（B）/ 設定したテストの実行と JUnit の突き合わせ（`run`） |
| `text.js` | 正規化（NFKC・小文字）、n-gram の余弦と All-Pairs、肯定・否定の判定（kuromoji.js）、数値の条件の抽出、編集距離 |
| `ambiguity.js` | テストとして曖昧な点（A） |
| `lint.js` | 書き方・重複・矛盾・漏れ（D / U / C / G） |
| `validity.js` | 判定の強さ（O）・実行できるか（X）・条件の組み合わせ（M・C05・U05） |
| `spec.js` / `specCheck.js` | 仕様のフォルダを仕様のモデルにする / ケースと突き合わせる（S） |
| `source.js` | 実装のフォルダの文字列と突き合わせる（I） |
| `config.js` | 設定ファイルの探し方（親へさかのぼる）・よくあるフォルダの自動検出 |
| `audit.js` | 読み込み・書式（JSON Schema）の検査・規則の実行・重さの適用・参考の指摘のまとめ |
| `report.js` / `evidence.js` / `cli.js` | 出力（text / json / markdown）・結果ファイル・入口 |

最初に作った Python 版の規則は、そのまま `lint.js`・`ambiguity.js` に移した。形態素解析は Janome から、同じ IPA 辞書の
kuromoji.js に替えた（品詞・原形の取り方が同じなので、否定の判定は同じ結果になる）。

## 判断の要点

### テストコードの静的な重複・統合候補

`code` サブコマンドは自然文モードと入力を分け、JavaScript/TypeScript と Python の AST を比較する。
JavaScript は Babel の parser と scope binding、Python は隔離モードの標準 `ast` を使う。
プロジェクトの設定・テスト・import 先のコードは読み込んで実行しない。Python は該当ファイルを選んだ場合だけ必要。

比較層 `src/code/analyze.js` は、パーサーから独立したテストの位置・本文・構造・実行条件のキーを読む。
他言語のアダプターも `schema/test-code.schema.json` と `--ir` で接続できる。
本文はローカル変数の束縛を正規化して値を残し、構造は同じ AST のリテラル値を型で置き換える。
関数・クラス・プロパティ・外部の束縛の識別は維持する。
hook・mock・fixture・callback 引数・修飾子・宣言間の初期化・モジュールの記述は実行条件に含める。

K01 は同一ファイルの本文と条件の一致、K02 は値の違う構造の一致、K03 は完全名の重複、K04 は別ファイルの一致、
K05 は静的な表の重複行を出す。値違いは「各ケースを残す統合」、別ファイルは「検証層の確認」として示し、
どの指摘もソースの自動削除には使わない。意図的なケースは規則と理由を持つ抑制コメントで除ける。
グループ単位で報告することで、N件の重複からN²件の指摘を作らない。

動的・未対応の部分は K00 と diagnostics に残し、通常は終了コード 2 にする。
ルールを非表示にしても不完全さは残る。部分的な解析を許す場合は明示的に `--allow-incomplete` を使う。
`complete` は対応する構文についての静的な解析状態であり、ランナーが収集する全テストとの一致や実行時の等価性を保証しない。
JSON の `tests` は自然文の `cases` と分け、evidence も `purpose: check` のまま実行証拠とは区別する。

参考: [vitest-dedup の規則](https://github.com/figueiredoluiz/vitest-dedup/blob/main/docs/rules.md) と
[パーサーから独立したモデル](https://github.com/figueiredoluiz/vitest-dedup/blob/main/src/model.rs)（2026-10-25確認）。
本文・構造・実行条件と整理方法を分ける考え方を採り入れ、JS/Python 用のアダプターと既存の指摘形式へ実装した。
外部の解析ツール本体を必須にはしない。

### ケース一覧と点検結果

JSON 出力には指摘と要約に加えて正規化した `cases` を出す。元ファイル・ID・入力の SHA-256 により、
読み手が個別テストとの対応やケースの追加漏れを確認できる。本体はその読み手を知らない。
evidence には `purpose: check` を付け、ケースの点検結果と振る舞いを実行した証拠を区別する。既存の ID と件数は維持する。

### Gherkin を直接読む（2026-10-26 に統合）

`.feature` は公式パーサー（`@cucumber/gherkin`）とその展開処理で読み、`gherkin.js` が JSON / YAML と同じ形のケースに
する。Feature / Rule はグループ、Background は各ケースの前提・手順、Outline は例の行ごとのケース、
Given / When / Then は前提 / 手順 / 期待結果、And / But は直前の役割を継ぐ。DataTable・DocString はステップの値に含める。
ID は `@case:ID` か Examples の `case_id` 列。無ければ名前・グループ・例の値から仮の ID を作り D01 にする
（行の並べ替えでは変わらないが、名前・値を変えると変わる）。構文・展開の誤りは D00 で元の行を示す。

展開したケースは JSON に直して load.js の同じ読み取り（別名表・条件の組・タグ）に通し、行番号だけを `.feature` の
シナリオ・例・各ステップの行に置き換える。読み取りを 2 つ持たないためである。

10-25 の版では、変換を独立した道具に置き、生成した JSON の `origin`（入力元の位置と SHA-256）で指摘を元へ返していた。
利用者が生成物を作り直す手間と、生成物が古いときの D00 が増えるだけだったので、変換を本体に入れて生成物と
`origin` の公開の形をやめた。

### ケースと個別テストの対応・実行（2026-10-26 に統合）

対応表（`bindings`）は、ケース（ファイル・ID、別リポジトリなら `side`）と個別テスト（suite・ファイル・selector）を結ぶ
JSON（`schema/bindings.schema.json`）。点検では B01（対応表のケースが無い）・B02（対応先のテストのファイルが無い・
書き方の誤り・run に無い suite）・B03（どのテストにも対応していないケース）を出す。テストは実行せず、ファイルの有無と
ケースの ID だけを見る。selector の中身はランナーごとに違うので解釈しない。

`run` だけがテストを実行する。設定の `run.<suite>.command` を引数の配列のまま（シェルを通さず）実行し、JUnit XML を
対応表と突き合わせて `purpose: execution` の結果（`schema/execution.schema.json`）を書く。成功を取り違えないため:

- 実行前にケースとテストの SHA-256 を控え、終了後に変わっていれば結果を書かない。
- ファイルに書く JUnit と以前の結果は実行前に消す。ランナーが何も書かなければ古い成功を使わない。
- ランナーの失敗・対応先の欠落・skip・未知の status は終了コード 0 にしない。JUnit に `file` が無く同名テストが
  複数の対応にあれば、取り違えないよう止める。
- 実行の識別は環境変数 `TEST_EVIDENCE_RUN_ID` / `TEST_EVIDENCE_INPUTS_DIGEST` で受け取り、無ければ自分で作る。
  呼ぶ側の道具の名前は知らない。

JUnit の読み取りは依存を増やさないよう `run.js` の小さな読み手で行う。`testcase` と、その直下の
`failure` / `error` / `skipped` と属性だけを見て、DTD / ENTITY と崩れた XML は受けない。

10-25 の版では、この実行を Python 標準ライブラリだけの独立した道具に置いていた。点検と実行で同じ対応表・ケースを
読むのに設定と引数が二重になり、suite ごとに長いコマンドを並べる必要があったため、`run` に統合して設定ファイルに
寄せた。結果の形式・環境変数・判定の約束は変えていないので、結果を読む側は変更不要である。

### 曖昧さ

「読む人によって、使う値・操作・合否が変わる」書き方を、当てる場所ごとに語の表で拾う。

| 規則 | 当てる場所 | 拾うもの | 言わないとき |
|---|---|---|---|
| A01 合否の基準 | 期待結果・チェック項目 | 正しく・適切・問題なく・仕様どおり・崩れていない・など | — |
| A02 使う値 | 前提・手順 | 任意の・適当な・正しい／誤った〇〇・有効な値 | その後ろに「」の値がある |
| A03 量・回数・時間 | すべて | 複数・いくつか・しばらく・数秒・長い文字列・大きなファイル | すぐ後ろに数値がある（「複数（3 件）」） |
| A04 指すもの | すべて | 該当の・当該・所定の・最新の・必要な項目、最初の文の指示語 | — |
| A05 選択肢 | 期待結果 | または・いずれか・どちらか | — |
| A06 言い切らない | 期待結果 | ことがある・場合がある・はず・基本的に・ほぼ・二重否定 | — |
| A07 比べる基準 | 期待結果 | 前より速く・改善される・向上する | 数値がある |
| A08 操作の対象 | 手順 | 「ボタンを押す」で始まる・各項目／必要事項を入力 | 値がある |
| A09 閉じない列挙 | 前提・手順 | など・その他・… | — |

- 「」・"" で囲んだ値（画面の文言・入力する値）は伏せてから当てる。文言「いずれかを選んでください」の
  「いずれか」を、期待結果の選択肢と取り違えないため。
- 書きかけ（D07）・他ケースへの依存（D09）は、曖昧というより書き切っていないものなので「不備」に残した。
- 「数値があれば言わない」のは、量や比較を数値で決めていれば、人によって変わらないため。

### 似ている度合い（重複・同じ手順）

文字の 2〜3 文字組の出現回数（対数）を L2 正規化し、余弦で比べる。分かち書きに頼らないので表記の揺れに強い。

- **IDF で重みを付けない。** LLM が出すケースは同じ言い回しの繰り返しが多い。IDF を掛けると共通部分が軽くなり、
  1 文字違いの重複が 0.9 を割った（3000 件の検証で、手で入れた重複 5 組をすべて落とした）。代わりに、長い共通の
  手順だけで「似ている」と判断しないよう、**期待結果どうしも似ていること**を重複の条件にする。
- 数値と「」で囲んだ値は伏せて比べ、値の集合が違う組は重複にも矛盾にもしない（境界値のケースを重複と言わない）。
- 全組の比較は件数の 2 乗になるので、**All-Pairs の前置フィルタ**で候補を絞る。ベクトルは長さ 1 なので、よく出る
  特徴から並べた前半のノルムが閾値未満なら、前半だけで閾値に届くことはない（コーシー＝シュワルツ）。後半だけを
  索引に入れ、部分和＋前半のノルムが閾値に届かない組を捨てる。取りこぼしはない。よく出る特徴を単に捨てる近似は、
  定型文の多い入力で再現率が落ちたので採らない。3000 件で 5 秒ほど。

### 矛盾（肯定と否定）

節ごとに「中身の語の集合」と「否定の偶奇」を持つ。否定として数えるのは、助動詞「ない・ぬ・ん」、形容詞「ない」、
接頭詞「未・不・非・無」、反対語の表（無効／有効、失敗／成功、非表示／表示…）。偶奇なので「未入力ならエラーが
表示される」と「入力したらエラーが表示されない」は食い違いにならない。1 つのケースの中では、別々の手順に付いた確認は
時間の順なので比べない（再試行の前後で「表示される」「表示されない」が並ぶのは正しい）。

### 文言の揺れ（C06・C07）

ケースどうしで、同じ文言を少しだけ違えて書いたもの（「保存しました。」と「保存しました」）を出す。仕様も実装も
渡さないとき、文言の誤りを拾う手がかりはこれしかない。

- 数値は伏せてから比べる。「3件です」と「5件です」は別の値を確かめているだけで、揺れではない。
- 1 つのケースで両方を確かめている組は出さない。「姓を入力してください」と「名を入力してください」のように、
  書き分けている文言だからだ。
- 仕様か実装に片方でもあれば出さない。両方あれば別々の文言で、片方だけなら S06・I01 がもう片方を指摘する。
  同じ誤りを 2 度言わない。
- 句読点・空白だけの違いは誤りとみてよいので警告（C06）。1〜2 文字の違い（編集の近さ 0.85 以上、8 文字以上）は
  参考（C07）にとどめる。ケースが違えば「姓」「名」のような別の文言でも当たるからだ。
- 全角と半角の違いは見ない。ほかの規則と同じく NFKC でそろえてから比べている。
- 全組を編集距離で比べると件数の 2 乗になる。重複と同じ All-Pairs で余弦 0.6 以上に絞り、残りだけを編集距離で
  確かめる。3000 件のケースで、かかる時間は変わらなかった。

### テストデータの安全（D18・D19）

ケースは CI のログ・不具合票・結果ファイルに写る。本物の個人情報や鍵がそこに残らないようにする。

- **パスワードは見ない。** 「パスワードに「Passw0rd」を入力する」はテストの値として要る。見ると、ログインの
  ケースがすべて誤検知になる。
- **メールアドレス（D18、警告）。** 予約済みのドメイン（RFC 2606・6761 の example.com/net/org・.example・.test・
  .invalid・localhost）以外は、実在しうるものとして出す。手順どおりに動かすと、本物の宛先にメールが届くおそれがある。
  自社のテスト用ドメインは設定の `test_data.domains` に書く。
- **カード番号（D19、エラー）。** 13〜19 桁で、国際ブランドの先頭番号と桁数が合い、Luhn も通るものだけを見る。
  形を絞らないと、13 桁のタイムスタンプや JAN コードの 1 割が Luhn を通ってしまう。決済会社が公開しているテスト用の
  番号と、同じ数字が 6 つ続く番号（4000 0000 0000 0077 など）はテスト用とみなす。後者は本物でもまれに当たるが、
  テスト用の番号の多くはこの形をしている。
- **鍵（D19、エラー）。** 形の決まったもの（AWS・GitHub・Stripe の本番キー・Slack・Google・JWT・秘密鍵）だけを拾う。
  `sk-xxxx…` のような伏せ字は、使っている文字の種類が少ないので鍵とみなさない。エントロピーだけで拾う方法は、
  ID やハッシュ値を拾いすぎるので採らなかった。
- 指摘には、鍵は先頭 4 文字、カード番号は末尾 4 桁しか出さない。指摘そのものが CI のログに残るためだ。

### 判定の強さ

- **見て確かめられるか（O01）。** 「保存される」「DB に登録される」のような中で起きることだけで、画面・応答・件数など
  見えるものが期待結果のどこにも無いもの。
- **何が出ても通るか（O02）。** 期待結果がすべて「〇〇画面が表示される」「エラーにならない」の形で、引用も数値も無いもの。
  画面の中身が壊れていても合格になる。
- **異常系の判定（O03・O04）。** 異常系（語の表か否定の節で判定）で、保存・送信などの副作用のある操作をしたのに
  「変わらない」ことを見ていないもの。期待結果が「エラーになる」だけで、文言もコードも無いもの（別の理由の失敗でも通る）。

### 実行できるか

- **データ（X01）。** 「〜を編集・削除・取り消す」の対象を取り出す。ID（`O-100`・「…」）があれば ID が、無ければ名詞が、
  前提・条件・前の手順に出ているかを見る。ボタン・画面・欄などの UI の名詞は対象にしない。
- **ログイン（X02）。** ケースの集まりのどこかにログインが出てくるときだけ、マイページ・ログアウトなどログイン後の画面を
  使うのに、ログインする前提も手順も無いものを出す。ログインしていない状態を前提に書いたケースは除く。
- **始める画面（X03）。** 最初の手順が「開く・アクセス・起動」でなく、前提にも画面・状態が無いもの。

### 条件の組み合わせ

ケースから `{条件: 値}` を取り出す。`conditions` に書いたものと、手順の「〇〇に「値」を入力する」「〇〇で「値」を選ぶ」
（構造で書いた `fill label="…" value="…"` も）から推したもの。

- **C05 / U05。** 条件の組が同じで手順も似ている（0.6 以上）組の期待結果を比べ、逆なら矛盾、同じなら重なりとする。
- **M02。** 同じ条件名が 2 件以上で使われ、どれも異常系でないもの（同値分割の無効クラスが無い）。
- **M01。** `conditions` に書いた条件だけで、2 つずつの組み合わせの網羅を測る（手順から推した値は揺れるので使わない）。
  条件が 3 つ以上あるときだけ。埋める行を貪欲法で提案する。

### 暫定実装に依存するテストの引退

暫定実装が正式実装に置き換わっても、古い固定値のケースがたまたま成功することがある。
実行成功は、そのケースを現在の仕様として残す理由にはならない。
自然文ケースとコードの中間表現に、共通の任意メタデータ `temporary` を持たせる。
コード側はAST・tokenizeで抽出した本物のコメントから宣言へ結び付け、文字列を指示として読まない。
理由と終了条件（UTCの期限、実装の固有マーカーまたはSHA-256）を記録し、
期限切れ・実装削除・マーカー消失をT02、内容変更をT03として報告する。
マーカー照合はファイル内の文字列の存在確認であり、実装の意味の証明とはしない。
ファイルの読み込みは1回の検査内で共有し、プロジェクトのコードを実行しない。

暫定らしいタイトル・コメント・ケースの本文・タグだけがある場合は、未管理の候補T01にする。
一般的なmock・fallback・temporary directoryという語だけでは候補にしない。
理由と `status: permanent` を記録すれば、正式仕様として必要な回帰テストを区別できる。
不正な期限や壊れた管理情報はT04で報告し、有効な終了条件として扱わない。
Gherkin では `@temporary` などのタグも T01 の候補にする（タグには終了条件を書けないため T01 にとどまる）。
自動削除・自動的な期限延長・ハッシュ更新は行わない。

### 仕様との突き合わせ

仕様のフォルダを読み、要件・項目の制約・状態遷移・権限・API・文言のモデルにする。表は見出しの語で見分ける
（「現在の状態・イベント・次の状態」なら状態遷移、2 列以上が ○× なら権限、「項目名」と制約の列があれば項目定義）。

- **対象を絞る。** 仕様は広く、ケースは一部の機能だけを扱うことが多い。表・図・API ごとに、ケースが 1 つでも触れて
  いるもの（項目名・状態名・役割・パスがケースに出る）だけを突き合わせる。要件はそのファイルが対象のときだけ数える。
  対象外のファイルは結果に並べる（黙って外さない）。
- **覆ったかの数え方。** 状態遷移は「遷移元が前提か手順に、操作が手順に、遷移先が期待結果に」あること。権限は
  「役割が前提・条件に、操作が手順に」あること。前提の「発送済みの注文」を、操作「発送済みにする」と取り違えないため。
- **境界値。** 項目の範囲から境界（ちょうど・1 つ外）を作り、項目名を含むケースのタイトル・前提・手順の「N 文字」と、
  入力に使った「」の値の長さで試したかを見る。期待結果は数えない（エラー文言の長さを入力と取り違えたため）。
  ケースの文から拾った条件の境界（G03）とは重ねて出さない。
- **文言（S06）。** 期待結果の「」の文言が仕様の本文に無く、**仕様の文言に近いもの（編集距離で 0.6 以上）があるとき
  だけ**出す。仕様がすべての文言を載せているとは限らないため。セレクタ・役割・URL などの値は文言に数えない。

### 実装との突き合わせ

実装のフォルダの文字をすべて読み、期待結果の文言がどこかに含まれるかを見る。`{0}` `%s` `${n}` `{{name}}` などの
差し込みのある文字列は、その部分を任意の値とする正規表現にして照らす。見つからなければ、文字列の中から近いものを示す。
アプリは動かさない（動かして確かめるのは、ケースを実行する道具の役目）。

エラーコード（I02）も同じように照らす。I01 が見るのは日本語を含む引用だけで、`E1001`・`ORDER_NOT_FOUND` のような
識別子は素通りしていた。コードの形（英大文字＋3〜5 桁の数字、大文字のスネークケース）で拾う。注文番号 `O-100` の
ようなデータの ID と区別するため、「エラー」「コード」「例外」などの語がある期待結果だけを見る。日本語を含む引用の
中のコードは、I01 が文言として見るので重ねない。

### 検討して入れなかったもの

- **前提の日付が実行日より過去（期限切れ）。** 実行した日によって指摘が変わり、「同じ入力なら同じ指摘」を破る。
- **電話番号。** 日本には架空の番号として予約された範囲が無く、誤検知を抑えられない。
- **仕様・実装の変更に追いついていないケース（git の差分）。** 比べる版が入力に入り、オプション無しで動かす方針と
  合わない。文書・コード・テストの整合を取る道具の役目とした。

## やらないこと

- 言い換えの矛盾・意味の重複（埋め込みや LLM が要る）。必要なら、この道具の JSON 出力を前段の篩にして、残りだけを
  LLM に見せる使い方を想定する。
- Excel の直接読み込み。LLM に JSON / YAML で出させる前提に絞った（Gherkin は 2026-10-26 に読むようにした）。仕様は Markdown・YAML・
  JSON・CSV を読む（Excel の仕様は CSV に書き出して渡す）。
