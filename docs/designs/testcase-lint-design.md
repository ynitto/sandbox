# testcase-lint 設計

自然文のテストケースを、テストケースとしての妥当性で点検する道具。利用者向けの説明は
[tools/testcase-lint/README.md](../../tools/testcase-lint/README.md)。ここには判断の根拠を書く。

## 方針

- **決定的であること。** 同じ入力なら同じ指摘を出す。CI のゲートに置けて、指摘の理由を規則と語の表まで
  たどれる。LLM の判断は入れない（揺れる・費用がかかる・オフラインで動かない）。
- **書き方より、不具合を見つけられるかを見る。** 文書としての読みやすさではなく、「このケースで合否を決められるか」
  「実行できるか」「試すべき組を試しているか」「仕様・実装と合っているか」を規則にする。
- **独立して動く。** ほかの道具（ケースを作って動かす道具・文書の整合を取る道具）の名前・設定・作業ファイルに
  触れない（`test/independence.test.js` が検査する）。ケースは JSON / YAML の一般的な形として読み、結果は
  version 1 の items 形式のファイルで渡す。組み合わせ方は README にだけ書く。
- **オプション無しで動かす。** ふだんの使い方は `testcase-lint` だけにする。何を点検するか（ケース・仕様・実装の
  フォルダ、結果ファイル、落とす重さ）は設定ファイルに書き、今のフォルダから親へさかのぼって探す。設定ファイルが
  無ければ、よくあるフォルダ（`tests/cases`・`docs/specs`・`src` など）を探す。ほかの道具の検査コマンドにも
  `testcase-lint` とだけ書けば済み、呼ぶ側に点検の中身を持たせない。出力の 1 行目に、何を点検したかを出す。
- **取りこぼしより誤検知を嫌う規則と、その逆の規則を、重さで分ける。** 構造の欠け・書きかけ・明白な逆の
  期待結果・仕様の要件の漏れはエラー。語の表に頼る規則は参考にとどめ、設定で止められる。

## 構成

| モジュール | 役割 |
|---|---|
| `load.js` | JSON / YAML を YAML の構文木で読み、行番号付きの小さな木にする（重複キーもここで拾う）。``` の囲みは外側を空行にして行番号を保つ。別名表で Case にそろえる |
| `text.js` | 正規化（NFKC・小文字）、n-gram の余弦と All-Pairs、肯定・否定の判定（kuromoji.js）、数値の条件の抽出、編集距離 |
| `ambiguity.js` | テストとして曖昧な点（A） |
| `lint.js` | 書き方・重複・矛盾・漏れ（D / U / C / G） |
| `validity.js` | 判定の強さ（O）・実行できるか（X）・条件の組み合わせ（M・C05・U05） |
| `spec.js` / `specCheck.js` | 仕様のフォルダを仕様のモデルにする / ケースと突き合わせる（S） |
| `source.js` | 実装のフォルダの文字列と突き合わせる（I） |
| `config.js` | 設定ファイルの探し方（親へさかのぼる）・よくあるフォルダの自動検出 |
| `audit.js` | 読み込み・書式（JSON Schema）の検査・規則の実行・重さの適用・参考の指摘のまとめ |
| `report.js` / `evidence.js` / `cli.js` | 出力（text / json / markdown）・結果ファイル・入口 |

最初に作った Python 版の規則は、そのまま `lint.js`・`ambiguity.js` に移した。形態素解析は Janome から、同じ IPA 辞書の
kuromoji.js に替えた（品詞・原形の取り方が同じなので、否定の判定は同じ結果になる）。

## 判断の要点

### 曖昧さ

「読む人によって、使う値・操作・合否が変わる」書き方を、当てる場所ごとに語の表で拾う。

| 規則 | 当てる場所 | 拾うもの | 言わないとき |
|---|---|---|---|
| A01 合否の基準 | 期待結果・チェック項目 | 正しく・適切・問題なく・仕様どおり・崩れていない・など | — |
| A02 使う値 | 前提・手順 | 任意の・適当な・正しい／誤った〇〇・有効な値 | その後ろに「」の値がある |
| A03 量・回数・時間 | すべて | 複数・いくつか・しばらく・数秒・長い文字列・大きなファイル | すぐ後ろに数値がある（「複数（3 件）」） |
| A04 指すもの | すべて | 該当の・当該・所定の・最新の・必要な項目、最初の文の指示語 | — |
| A05 選択肢 | 期待結果 | または・いずれか・どちらか | — |
| A06 言い切らない | 期待結果 | ことがある・場合がある・はず・基本的に・ほぼ・二重否定 | — |
| A07 比べる基準 | 期待結果 | 前より速く・改善される・向上する | 数値がある |
| A08 操作の対象 | 手順 | 「ボタンを押す」で始まる・各項目／必要事項を入力 | 値がある |
| A09 閉じない列挙 | 前提・手順 | など・その他・… | — |

- 「」・"" で囲んだ値（画面の文言・入力する値）は伏せてから当てる。文言「いずれかを選んでください」の
  「いずれか」を、期待結果の選択肢と取り違えないため。
- 書きかけ（D07）・他ケースへの依存（D09）は、曖昧というより書き切っていないものなので「不備」に残した。
- 「数値があれば言わない」のは、量や比較を数値で決めていれば、人によって変わらないため。

### 似ている度合い（重複・同じ手順）

文字の 2〜3 文字組の出現回数（対数）を L2 正規化し、余弦で比べる。分かち書きに頼らないので表記の揺れに強い。

- **IDF で重みを付けない。** LLM が出すケースは同じ言い回しの繰り返しが多い。IDF を掛けると共通部分が軽くなり、
  1 文字違いの重複が 0.9 を割った（3000 件の検証で、手で入れた重複 5 組をすべて落とした）。代わりに、長い共通の
  手順だけで「似ている」と判断しないよう、**期待結果どうしも似ていること**を重複の条件にする。
- 数値と「」で囲んだ値は伏せて比べ、値の集合が違う組は重複にも矛盾にもしない（境界値のケースを重複と言わない）。
- 全組の比較は件数の 2 乗になるので、**All-Pairs の前置フィルタ**で候補を絞る。ベクトルは長さ 1 なので、よく出る
  特徴から並べた前半のノルムが閾値未満なら、前半だけで閾値に届くことはない（コーシー＝シュワルツ）。後半だけを
  索引に入れ、部分和＋前半のノルムが閾値に届かない組を捨てる。取りこぼしはない。よく出る特徴を単に捨てる近似は、
  定型文の多い入力で再現率が落ちたので採らない。3000 件で 5 秒ほど。

### 矛盾（肯定と否定）

節ごとに「中身の語の集合」と「否定の偶奇」を持つ。否定として数えるのは、助動詞「ない・ぬ・ん」、形容詞「ない」、
接頭詞「未・不・非・無」、反対語の表（無効／有効、失敗／成功、非表示／表示…）。偶奇なので「未入力ならエラーが
表示される」と「入力したらエラーが表示されない」は食い違いにならない。1 つのケースの中では、別々の手順に付いた確認は
時間の順なので比べない（再試行の前後で「表示される」「表示されない」が並ぶのは正しい）。

### 判定の強さ

- **見て確かめられるか（O01）。** 「保存される」「DB に登録される」のような中で起きることだけで、画面・応答・件数など
  見えるものが期待結果のどこにも無いもの。
- **何が出ても通るか（O02）。** 期待結果がすべて「〇〇画面が表示される」「エラーにならない」の形で、引用も数値も無いもの。
  画面の中身が壊れていても合格になる。
- **異常系の判定（O03・O04）。** 異常系（語の表か否定の節で判定）で、保存・送信などの副作用のある操作をしたのに
  「変わらない」ことを見ていないもの。期待結果が「エラーになる」だけで、文言もコードも無いもの（別の理由の失敗でも通る）。

### 実行できるか

- **データ（X01）。** 「〜を編集・削除・取り消す」の対象を取り出す。ID（`O-100`・「…」）があれば ID が、無ければ名詞が、
  前提・条件・前の手順に出ているかを見る。ボタン・画面・欄などの UI の名詞は対象にしない。
- **ログイン（X02）。** ケースの集まりのどこかにログインが出てくるときだけ、マイページ・ログアウトなどログイン後の画面を
  使うのに、ログインする前提も手順も無いものを出す。ログインしていない状態を前提に書いたケースは除く。
- **始める画面（X03）。** 最初の手順が「開く・アクセス・起動」でなく、前提にも画面・状態が無いもの。

### 条件の組み合わせ

ケースから `{条件: 値}` を取り出す。`conditions` に書いたものと、手順の「〇〇に「値」を入力する」「〇〇で「値」を選ぶ」
（構造で書いた `fill label="…" value="…"` も）から推したもの。

- **C05 / U05。** 条件の組が同じで手順も似ている（0.6 以上）組の期待結果を比べ、逆なら矛盾、同じなら重なりとする。
- **M02。** 同じ条件名が 2 件以上で使われ、どれも異常系でないもの（同値分割の無効クラスが無い）。
- **M01。** `conditions` に書いた条件だけで、2 つずつの組み合わせの網羅を測る（手順から推した値は揺れるので使わない）。
  条件が 3 つ以上あるときだけ。埋める行を貪欲法で提案する。

### 仕様との突き合わせ

仕様のフォルダを読み、要件・項目の制約・状態遷移・権限・API・文言のモデルにする。表は見出しの語で見分ける
（「現在の状態・イベント・次の状態」なら状態遷移、2 列以上が ○× なら権限、「項目名」と制約の列があれば項目定義）。

- **対象を絞る。** 仕様は広く、ケースは一部の機能だけを扱うことが多い。表・図・API ごとに、ケースが 1 つでも触れて
  いるもの（項目名・状態名・役割・パスがケースに出る）だけを突き合わせる。要件はそのファイルが対象のときだけ数える。
  対象外のファイルは結果に並べる（黙って外さない）。
- **覆ったかの数え方。** 状態遷移は「遷移元が前提か手順に、操作が手順に、遷移先が期待結果に」あること。権限は
  「役割が前提・条件に、操作が手順に」あること。前提の「発送済みの注文」を、操作「発送済みにする」と取り違えないため。
- **境界値。** 項目の範囲から境界（ちょうど・1 つ外）を作り、項目名を含むケースのタイトル・前提・手順の「N 文字」と、
  入力に使った「」の値の長さで試したかを見る。期待結果は数えない（エラー文言の長さを入力と取り違えたため）。
  ケースの文から拾った条件の境界（G03）とは重ねて出さない。
- **文言（S06）。** 期待結果の「」の文言が仕様の本文に無く、**仕様の文言に近いもの（編集距離で 0.6 以上）があるとき
  だけ**出す。仕様がすべての文言を載せているとは限らないため。セレクタ・役割・URL などの値は文言に数えない。

### 実装との突き合わせ

実装のフォルダの文字をすべて読み、期待結果の文言がどこかに含まれるかを見る。`{0}` `%s` `${n}` `{{name}}` などの
差し込みのある文字列は、その部分を任意の値とする正規表現にして照らす。見つからなければ、文字列の中から近いものを示す。
アプリは動かさない（動かして確かめるのは、ケースを実行する道具の役目）。

## やらないこと

- 言い換えの矛盾・意味の重複（埋め込みや LLM が要る）。必要なら、この道具の JSON 出力を前段の篩にして、残りだけを
  LLM に見せる使い方を想定する。
- Gherkin（.feature）・Excel の直接読み込み。LLM に JSON / YAML で出させる前提に絞った。仕様は Markdown・YAML・
  JSON・CSV を読む（Excel の仕様は CSV に書き出して渡す）。
