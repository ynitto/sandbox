## 1. TL;DR

**何を作るか**: 別ホスト（WSL・他 PC）で動く agent-project / agent-flow / agent-amigos /
定常業務を 1 つの Windows GUI から見渡し、人の判断だけをその場で返せるようにする操作面。

**主要な決定**:

1. dashboard は状態の**書き手にならない**。読むのはファイル、書くのは公式契約の投函だけ。
2. 制御面はソースツリーで分け、`features/index.js` の配列 1 本で合成する。動的プラグインにしない。
3. プロジェクトの発見は実行側が書く `engine/status.json` 1 枚だけを根拠にする。
4. 画面はビルド工程を持たない。読み込み順を契約にする。
5. YAML は読みと書きでパーサを分ける。

**却下した主要案**: dashboard 自身が状態共有リポジトリを pull / push する案。一度実装したが、
viewer の push が本体の状態ファイルへコンフリクトマーカーを書き込んで状態を失わせたので撤去した。

**読むべき人**: dashboard に制御面を足す人、契約ファイルを介して dashboard と繋ぐツールの実装者。
**読まなくてよい人**: 使い方だけ知りたい人（README を読めばよい）。

## 2. 背景と課題

エージェントを回す本体は WSL や別の PC にいる。状態はファイルで、正しく読めば全部見える。
問題は**人の側**だ。needs（人の判断待ち）が出たことに気づくには誰かが端末を覗く必要があり、
承認を返すにはコマンドを打つ必要がある。ツールが増えるほど覗く場所も増える。

しかも「人が触れる GUI」を素朴に作ると壊れる。実際に壊した。viewer から状態共有リポジトリへ
push した結果、本体の状態ファイルにコンフリクトマーカーが書き込まれ、状態共有が復旧不能になった。
GUI は状態の書き手として最悪の性質を持つ。人の操作タイミングは予測できず、本体の同期規律を知らない。

そこで dashboard は**見る面**と**判断を返す面**に徹する。状態を動かすのは常駐体
（`agent-project serve`）だけ、という一本化を GUI 側からも守る。

### 2.1 目標と非目標

**やらないこと**を先に決める。

- **状態の書き込み**。`backlog/*.md` の status、`project.json`、agent-flow の run 状態を画面から
  書き換えない。done の根拠は検証 receipt だけ、という本体の不変条件を GUI から壊さない。
- **フォージへの書き込み**。GitLab / GitHub は読み取りだけで、レビュー操作は引き継ぎ先に任せる。
- **完全自動運転**。判断を減らす仕組みは作るが、人がゼロになる状態は目標にしない。
- **動的プラグイン**（実行時ロード・サンドボックス・版管理）と npm ワークスペース分割。
- **実行エンジンを起動・再起動する経路**。常駐体の起動は OS の起動系が担う。

**やること**は 4 つ。複数プロジェクト・複数ワークロードの状態を 1 画面で見渡す。人の判断を
公式契約で返す。判断が必要になったことに、画面を見ていなくても気づける。判断そのものを AI が
下ごしらえして、人の 1 回の介入の質を上げる。

例外が 2 つある。進まないタスクの**強制完了**は「verify を通さない done」を必要とするが、これも
画面が状態を書くわけではない——`commands/force-complete` を投函し、本体が未検証（`FORCED`）と
分かる形で確定する。もう 1 つは「この端末で募集中の仕事を引き受ける」参加操作で、人が明示的に
押したときだけ agent-flow のワーカーを 1 つ立てる。例外を持つのは本体、という線は動かさない。

## 3. 主要な設計判断

### 3.1 dashboard は状態の書き手にならない（viewer からの git 書き込みを撤去）

**判断**: dashboard が触れるのは、状態ファイルの**読み取り**と、公式契約ファイルの**投函**の
2 つだけ。状態共有リポジトリへの pull / push / commit も、本体の状態ファイルの書き換えも持たない。

**文脈**: 本体は状態をファイルで持ち、git で共有する。同期には規律（間隔律速・pathspec 限定
コミット・rebase リトライ・force push 禁止）がある。GUI はその規律の外側から、人の気まぐれな
タイミングで書き込もうとする。

**選択肢と却下理由**:

- *viewer 自身が pull / push する*: リモートで動く本体へ操作を即座に届けられる。**一度実装した**
  （⇣ ボタン・自動 pull 間隔・操作を都度コミットしてプッシュ）。却下。viewer の push が本体の
  状態ファイルへコンフリクトマーカーを書き込み、状態共有が復旧不能になった。多重コミッタ対策
  （pathspec 限定・autostash・バックオフ）を積んでも、書き手が 2 人いる構図そのものが残る。
- *操作を CLI で直接実行する（本体を起こす）*: 反映が速い。却下。CLI パスの誤りが「押しても何も
  起きない」原因不明の不具合になり、同一ホストでしか効かない。

**トレードオフ**: 操作の反映が常駐体の同期間隔ぶん遅れる。即時性は諦めた。

**確信度**: 高い。実障害が根拠。

この判断は 3 か所へ同じ形で効いている。**画面の AI** はテキストを返すだけで、ファイルを書かない
——charter の下書きも、承認の推薦も、差し戻し文面も、人が確定ボタンを押して初めてファイルになる。
AI に確定権を渡すと、ここで消したはずの「規律を知らない書き手」が別の顔で戻ってくる。
**委譲板への中止・落札・手動入札**も板へ直接書かず、ノード宛て指示として投函する——`git+` 板では
アダプタが作業ディレクトリへ置くだけで push しないので、直接書き込みは誰にも届かない「押しても
効かないボタン」だった。**共有カタログ**（`.agents/workflows/` と `.agents/methods/`）も読み取り
専用で探索し、書けるのはユーザー共通の `~/.agents/workflows/` だけにする——共有版の作成・配布は
通常の Git、PR/MR、clone 更新の責務で、dashboard に git 資格情報を持たせない。

護りはレビューではなくテストで固定した（`test/no-git-writes.test.js`）。コードを足せば簡単に
戻せてしまう類の護りだからだ。同じテストが**掛かっている範囲そのもの**も検査する——護りの中身
より先に範囲が縮むほうが起きやすく、しかもテストが緑のままなので気づきにくい。

### 3.2 制御面はソースツリー分離と列挙合成（フルプラグインを却下）

**判断**: Electron シェル等の共通部を `src/base/` に、各制御面を `src/features/<id>/` に置き、
`src/features/index.js` の配列に並べるだけで IPC・preload・設定既定へ反映する。

**文脈**: 上流のダッシュボード更新を取り込みつつ、別グループが自分の制御面を足せる形が要る。
一方で、この規模のアプリに動的ロードの仕組みを持ち込むのは明らかに過剰だ。

**選択肢と却下理由**: *フルプラグイン（動的ロード・隔離・版管理）*と *npm ワークスペース化*は却下。
分離したいのは**ソースの所有**であって実行時の境界ではない。列挙合成なら、上流とのマージで
衝突するのは `features/index.js` の 1 行だけになる。

**トレードオフ**: 制御面は同一プロセス・同一権限で動く。信頼できないコードは載せられない。

**確信度**: 高い。当初 2 つだった制御面が 9 つに増えても、合成点は 1 ファイルのままだ。

### 3.3 プロジェクトの発見は実行側の状況ファイル 1 枚

**判断**: **agent-project のプロジェクト**がどれかは `<agents home>/engine/status.json` の
`children[].root` だけから導く。画面からの登録・登録解除は持たない。

**文脈**: 何を回すかを決めるのは実行側の `agent-project.host.yaml` で、dashboard はそれを映す面だ。
両側に登録簿があると、どちらが正かが曖昧になる。

**選択肢と却下理由**: *画面の設定で列挙する*、*親フォルダをスキャンして自動追加する*、
*ロックファイルを直接覗いて稼働を判定する*はいずれも却下（実装していたものを撤去した）。
`engine/status.json` は常駐体だけが書く 1 枚で、発見・稼働・共有の健全性・子の隔離・板の可否の
すべての根拠になる。

**適用範囲**: この判断が縛るのは **agent-project が回すプロジェクト**だけだ。agent-loop 設定や
`.statemachine/` を持つだけの**定常業務専用フォルダ**は設定 `cowork.roots` に列挙する。判断の
根拠は「両側に登録簿を持たない」ことであって「dashboard が何も宣言しない」ことではない
——定常業務のエンジンは常駐体・状態リポジトリと無関係に動き、起動・tmux 管理・履歴記録を
すべて cowork が担うので、**実行側が dashboard 自身**であり登録簿は 1 つのままだ。逆に
host.yaml へ載せると、常駐体が管理しないものを常駐体の宣言ファイルに書くねじれになる。

**トレードオフ**: 常駐体が動いていないホストでは一覧が空になる。契約版が食い違うノードは
「更新漏れ」として表示し、黙って情報を欠いたまま正常に見せない。

**確信度**: 高い。`test/discover-engine.test.js` が入口の一本化を固定している。

### 3.4 画面はビルド工程を持たない（読み込み順を契約にする）

**判断**: 機能ごとにファイルを分け、`index.html` の `<script>` 読み込み順でグローバルスコープを
共有する。バンドラも UI フレームワークも入れない。

**文脈**: 当初は 1 本の巨大 `renderer.js` だった。保守のために分けたいが、テストがソースを
**文字列走査**しているため、モジュール境界を入れると検査が全部壊れる。

**選択肢と却下理由**: *バンドラ（webpack / vite）や UI フレームワークの導入*は却下。ランタイム
依存は「自前で書くと壊れ続けるもの」に絞る方針で、画面の組み立てはそれに当たらない。当たると
判断して入れたのは差分表示と YAML の読みだけだ。

代わりに読み込み順を契約にした（core → sections → features → bootstrap）。core は差し込まれる
中身を知らず、登録簿 3 つ（タブ・ポータルカード・全体設定の面）で受ける。差し込み口をタブだけに
しなかったのは、制御面が持ち込む面が**プロジェクトごとでない**ときにタブへ入れると、選択中
プロジェクトと無関係なものがプロジェクトのタブ列へ並ぶからだ——この端末の利用量や外部連携が
それで、置き場所は全体設定になる。設定の置き場所も効く範囲で分ける。全体設定は端末のすべての
ワークロードに効くものとこのアプリ自身の設定だけを持ち、特定の agent-* にだけ効く設定はその
道具の領域へ置く。

**トレードオフ**: グローバル汚染と、順序契約を破ったときの壊れ方が分かりにくいこと。名前衝突は
人が気をつけるしかない。

**確信度**: 中。renderer が今より倍になったら、この判断は見直す引き金になる。

### 3.5 YAML は読みと書きでパーサを分ける

**判断**: YAML の**読み**は `src/base/main/yaml.js`（`yaml` パッケージ）に一本化する。
**書き戻し**（cowork の agent-loop / workflow.yaml 編集）はパーサを通さず、物理行を直接
差し替える外科的書換のままにする。

**文脈**: 当初は「ランタイム依存を増やさない」方針から、機能ごとに小さな行指向パーサを置いていた。
その前提は破れた——`repos:  # このPCのクローン` のインラインコメント 1 つで `repos:` ブロックの
照合が外れ、宣言が丸ごと無いことにされる。列 0 のコメント行で `prompts:` リストが打ち切られ、
2 件目以降の定常業務が発見から消える。どちらも壊れ方が**「設定が無いことにされる」＝黙って機能が
消える**形で、人は「書いたのに効かない」としか分からない。

**選択肢と却下理由**: *行指向パーサを直し続ける*は却下（同じ表層構文を 3 か所で追いかけ、次の
コメント記法でまた落ちる）。*書き戻しもライブラリでラウンドトリップする*も却下——再シリアライズは
人が書いたコメント・順序・整形を壊す。書き戻しの関心は値ではなく**どの物理行に書くか**なので、
値パーサでは代われない。

**トレードオフ**: agent-loop の `prompts[]` について値パーサと行アンカーの 2 系統が並ぶ。
**両者は並びが一致していなければならない**ので、その一致自体をテストで固定する。壊れた YAML は
復旧値を採らず「読めなかった」に倒す——半分だけ効いている設定を静かに作らないためだ。

**確信度**: 高い。読みの正しさは実物の設定ファイルで検証済み。

## 4. 制御面の地図

この節は概要の粒度。各制御面の IPC・設定キー・読み書きするファイルは仕様書 §2 と §4〜5 にある。

| 制御面 | 見せるもの | 書くもの |
|---|---|---|
| `agent-project` | charter / 達成状況 / バックログ / 要対応 / 実行グラフ / 検収 / 履歴 | `needs/` 記入・`inbox/` 投入・`commands/` ドロップ・上位入力ファイルの編集 |
| `adhoc-flow` | 実装フローと設計フローのカタログ、作業準備項目、設計セッション、run の履歴 | ユーザー共通フロー、dashboard ローカルの準備・セッション、公式 `inbox/` 投函 |
| `cowork` | 定期実行ジョブと定型業務の一覧・設定同期・実行 | 人の成果物リポジトリ ＋ 自分の設定 |
| `routines` | 稼働中ループの構造化状態・会話画面・復旧送信 | 何も書かない（`agent-loop send` への依頼だけ） |
| `amigos` | ミッションの進行・担当・やりとり・納品棚 | ホームの `commands/` ドロップのみ |
| `orchestration` | ノード予算・エージェント制御・CLI ドロップインの棚卸し | `~/.agents/` 配下の契約ファイル |
| `delegation` | 独立画面なし（タスク・参加・全体設定へ溶かす） | 委譲封筒の変換投函と、板へのノード宛て指示 |
| `participation` | 募集中の仕事とこの端末の参加操作 | 人が押したときだけ agent-flow ワーカーを 1 つ起動 |
| `agent-audit` | 実測トークン利用量・実行品質・収集状態 | LLM を使わない段への依頼だけ |

agent-flow は run-id の相互リンクや cancel / resubmit で agent-project と結合が強いため、別の
制御面にせず `agent-project` に含めた。ディレクトリ名は制御面の主対象に合わせてある。

`src/features/preparation/` はディレクトリの位置に反して**制御面ではない**。feature 記述子を
持たず、`features/index.js` の列挙にも入らない共有モジュールで、adhoc-flow と renderer が呼ぶ。

### 4.1 委譲板を独立タブにしなかった理由

「委譲」は内部概念で、利用者の語彙ではない。独立タブを作らず、人が実際に持つ問いの場所へ割った。
「出したこの仕事、誰か拾った？」はタスク画面、「この端末で引き受けられる仕事は？」は参加タブ、
「この端末は板に参加できてる？」は全体設定の同期だ。板専用のセクションを全体設定に置く案は捨てた
——設定画面は端末の構成を決める場所で、刻々と動く公示の一覧を混ぜると、どちらの目的でも探しにくい。

中止だけは所有権の割り切りがある。板の契約上 `cancelled.json` は依頼者が書くパスだが、dashboard を
動かしている PC が依頼者とは限らない。パス単位の書き込み所有権は git でコンフリクトさせないための
規約であって認可ではないので、誰が書いても板は終端として扱う。止める判断は人にあり、どの PC の前に
座っているかで可否が変わるのは筋が悪い。誰が止めたかは `cancelled_by` に残す。

## 5. 設計 run と実装 run を分ける

設計を必要とする仕事と、設計済み・設計不要の仕事を同じ実装 run に押し込めない。フロー定義に
`purpose` と `libraryVisibility` を持たせ、保存場所だけで用途を推測しないことにした。設計 run は
読み取り専用の短命 run で、成果は dashboard ローカルの作業準備項目を介して実装 run へ渡る。

用途を属性にしたのは、保存場所での推測が破れるからだ。同じ `~/.agents/workflows/` に設計用と
実装用が並ぶし、リポジトリ共有版と同梱版も混ざる。参照キーを `id + scope + repository` にして
`id` だけで別の定義を選ばないのも同じ理由で、同名の別 scope を黙って取り違えると「共有版を直した
のに反映されない」という追いにくい症状になる。

選択時に定義を **snapshot** 化するのは、元定義やカタログの後変更で保存済みの準備項目・設計 run・
実装 handoff が暗黙に変質しないためだ。手法（`.agents/methods/`）も参照のまま保存せず、選択時の
本文と source hash をノードへ複製する。

設計 run に読み取り専用契約を課したのは、設計が成果物リポジトリを触る理由が無いからだ。ファイル
変更・commit・push・ブランチ作成をしないので `af/<run-id>` branch を作らず、agent-flow の
run / plan / workspace 契約も変更しない。実装へ渡せる成果の必須 4 節（目的・変更対象・受入基準・
検証方法）は、実装側が既存の verify 契約でそのまま使える形に合わせてある。契約の詳細は仕様書 §6。

## 6. 人のアクションと護るべき不変条件

この節は契約の粒度。返せる判断の一覧と画面ごとの表示規則は仕様書と README にある。ここには
**破ってはいけない線**だけを置く。

- **done は検証 receipt の PASS だけが根拠**。状態遷移を画面から直接書き換えない。revise も状態を
  書かず、本体側の同一ロジックが遷移を決める。
- **公式の入力契約だけを使う**。`needs/` 記入・`inbox/` 投入・`commands/` ドロップの 3 つ。
- **AI はファイルを書かない**（§3.1）。
- **フォージは読み取り専用**。
- **タスク状態ファイルは書き換えない**（`backlog/*.md` の status、`archive/`、`project.json`）。

この線を守るために、画面側で我慢していることが 3 つある。

**新しい迂回路を作らない。** integration failure は通常の工程失敗と区別して見せるが、操作は既存の
`revise` に「最新 target を統合して全検証をやり直す」という feedback を渡すだけで、失敗工程だけを
温存する `resume-run` は出さない。検証が決着しないときも `retry` / `amend` / `park` /
`accept-unverified` の 4 択に限り、前 3 つは既存の revise / hold へ、最後は既存の force-complete へ
写す。viewer 固有の状態遷移や新しい command は増やさない。

**確認方法を人に書かせない。** 通常画面で求めるのは自然文の達成条件・受入基準で、固定検証コマンドと
`verify_template` は「高度な設定」に置く。AI がシェルコマンドを作って欄を埋める機能は持たない
——AI が書いた基準を AI が満たす閉ループになるからだ。受入基準の補完だけは例外的に AI に下書き
させるが、人が承認してから確定する。

**削除は本体の整合に任せる。** タスク / run の削除は viewer が持ち主のもの（要対応カードと
レビューコメント）を一緒に掃除し、実行中は拒否する。削除 id を先行に持つ後続タスクの再審査や、
検証記録・実行権ロックの孤児掃除は本体の毎パスの整合点が引き受けるので、viewer は代行しない。

## 7. 気づく・下ごしらえする

ポーリングは純プル型なので、画面を見ていない間に出た要対応には気づけない。ここは 2 段で埋める。

**気づく**: 新しい要対応が現れたら OS 通知・タスクバーバッジ・ウィンドウのフラッシュで知らせる。
増分検知は `discover()` の `needsCount` の前後比較で、**観測済みプロジェクトで数が増えたときだけ**
通知する（起動直後の既存分・減少・新規発見では通知しない）。

**停滞を見せる**: 各要対応カードに待ち時間を出し、未対応は停滞の長い順に並べる。手戻りではなく
**停滞**の可視化で、長時間放置＝下流が止まっている、を一目で分かるようにする。

**下ごしらえする**: Viewer アシスタントは読み取り専用の 4 モードを持つ。全体を説明する
`consultation`（Doctor）、失敗ノードの `failure-diagnosis`、計画レビューの `plan-critique`、
検収の `delivery-rationale`。いずれも推薦と差し戻し文面案までを返し、確定は人が押す。

失敗診断だけは 1 往復で終わらないので、既定を**対話診断**にした。ここで判明したのは、画面が持つ
120KB 級のスナップショットは対話へ持ち込めないということだ——tmux への注入は改行を含められない
1 行で、「全文をファイルで読ませる」前提は読み取り専用モードでファイル読み取りごと落とす CLI に
破られる。送るのは**ブリーフ 1 行 + 全文ファイルのパス**で、全文は「読めるなら読め」の追加資料に
留める。残る 3 モードは、回答から構造化見出しを抽出して回答欄へ流し込む仕組みに依存するため
対話化しない——対話にすると抽出点が消える。

**上流で潰す**: タスク投入フォームは、受入基準が無い、または「ちゃんと」「正しく」のように
観測点が分からない基準を投入前に警告する。警告は非ブロックで、基準を具体化する責任は人に残す。

## 付録 B. 画面ごとの設計判断の要点

個別に検討した各画面の設計から、**却下した案を伴う判断**だけを残す。経緯は `docs/plans/` にある。

- **概要ハブ + 詳細タブ**: 「かんたん / メンテナンス」の表示モード切替を廃し、常に概要を入口にする。
  全折りたたみ案（情報量が残る）とウィザード案（横断閲覧を妨げる）は却下。
- **要対応の判断面**: 一覧・詳細・操作欄は同じ判断モデルを使い、「現在の状態と停止理由 → 次にする
  こと → 判断材料」の順に読む。過去の操作失敗は現在の停止理由を上書きせず、「過去の操作」に畳む。
- **再計画を含む工程表示**: 「計画の変遷」と「タスクの流れ」を分ける。計画更新の帯は時系列の境界で
  あって依存線ではないので、群をまたぐ依存は文字で明示し、推測した線を足さない。
- **Doctor**: 要約 200 文字への圧縮をやめ、押したときだけ関連 run の全工程出力を取得する。AI 相談は
  専用タブではなく画面単位の共通操作としてサイドバーに置く。
- **失敗診断**: 専用画面も専用 IPC も新設せず、Doctor の `mode: failure-diagnosis` として実装。
- **利用者中心の二層化**: run ID・heartbeat・lease・bus のような実装概念は日常画面から外し、開発者
  ツールへ段階的開示で移す（削除はしない）。
- **ミッション詳細**: バスのメッセージを生で見せず表示専用モデルへ変換し、内部語彙（owner / role /
  round）を「担当者を募集中」「確認待ち」のような次の展開が読める日本語へ翻訳する。
- **ノード予算とエージェント制御**: 予算の一次単位を実行時間からトークンへ移す。台帳には常に計測
  できる秒と実測トークンだけを書き、未報告 CLI 分は読み出し時にレート換算で推定する（実測のみに
  絞る案・USD を一次にする案・時間のままの案は却下）。配分はエンジンに分散協調させず、管理面が
  実効上限を再計算して書く。
- **セッション開始コマンド**: 前準備コマンドは agent-instructions に相乗りさせず独立契約にした。
  instructions は agent-flow の meta.json で他ノードへ伝播するので、相乗りすると任意シェルコマンドが
  リモートへ配られてしまう。この契約だけは非伝播とする。
- **参加 UI**: UI から工程を直接予約せず、run 限定ワーカーを 1 つ起動して既存の決定的 claim に任せる。
  予約だけ作ると、実行主体のない claim が工程を止める。
- **検収**: 正はフォージの MR/PR とし、MR は自動作成せず未作成のカードにだけ冪等な「MRを作る」操作を
  出す。worker の一時 worktree パスを前提にした旧 diff 経路は撤去した——dashboard が本体と別マシン
  なら worker の作業ツリーは `/tmp` で消えるので、そもそも動いていなかった。
- **本番化**: バグを修正で塗り重ねず、住処ごと撤去する。状態は専用状態リポジトリの通常 clone へ
  分離、操作は `commands/` の file-drop 一本へ統一、複数 PC 分散は静的割当 + git push 調停で自動
  奪取を持たない。
