# dagu-workflow-builder 設計

スキル: `.github/skills/dagu-workflow-builder/`

## 1. 目的

各環境（PC・エージェント）に入っているスキルのスクリプトを組み合わせて、Dagu の DAG を作る。
つなぎ方の決定に LLM を使わない。同じスキル構成・同じ指定なら、どの環境でも同じ DAG ができる。
スクリプトで埋まらない変換だけは、エージェント CLI を呼ぶステップとして宣言して入れられる（§2.5）。

LLM が DAG を手書きすると、(a) 引数の形をスクリプトのソースから推測して外す、(b) 環境ごとに
違う DAG ができる、(c) 毎回トークンを使う。スクリプトのつなぎ方は入出力の形だけで決まる
探索問題なので、宣言 + 探索で解く。

## 2. 判断

### 2.1 入出力はスキル側の宣言（`chain.json`）で持つ

- argparse の `--help` を読む案は捨てた。引数の名前は分かっても、どれが入力ファイルでどれが
  出力か、出力の中身が何の形かは分からない。そこを推測させると LLM が要る。
- SKILL.md の frontmatter に入れる案も捨てた。frontmatter の YAML をこのリポジトリは
  素朴なパーサで読んでおり（`generate_skill_catalog.py`）、入れ子の配列を足すとそちらが壊れる。
  スキル直下の JSON なら標準ライブラリで読め、frontmatter の未知キー検査
  （`skill-evaluator/scripts/quality_check.py`）にも触れない。
- 宣言はスキルと一緒に配られる（`install.py` はスキルのディレクトリを丸ごとコピーする）。
  宣言を持たないスキルは無視するだけで、既存のスキルに影響しない。

### 2.2 型は名前だけで照合する

型は `openapi`・`openapi-report` のような文字列で、完全一致だけでつなぐ。継承やワイルドカードは
持たない。「拡張子は同じだが中身の約束が違う」ものを取り違えるほうが、つながらないより害が大きい。
変換が要るなら、変換するアクションを宣言する。

### 2.3 探索は有向超グラフの最小コスト（決定的）

アクションは「入力の型の集合 → 出力の型の集合」の超辺。手元の型のコストを 0 とし、
全入力のコストが決まったアクションの出力を `1 + 入力のコストの和` で緩和し、変化が無くなるまで回す
（Knuth の超グラフ版 Dijkstra を素朴に反復したもの）。

- 緩和は厳密に小さいときだけ行い、アクションは (スキル名, id) の順になめる。同点は名前順で前が勝つ。
  これで同じ入力から常に同じ経路が出る。
- 後ろ向きのポインタは常にコストが厳密に下がる向きなので、取り出した経路に閉路はできない。
  同じ型を受け取って同じ型を出すアクションは宣言の検査で落とす。
- 共有される上流（1 つのアクションが 2 つの型を出し、下流がその両方を使う）は 1 ステップにまとめる。
  コストは延べ数なので共有を過大に数えるが、経路の選択が少し保守的になるだけで正しさには響かない。
- 利用者が経路を変えたいときは `--avoid` でアクションを外す。重み付けの設定は持たない。

### 2.4 Dagu v2.25 の書式に合わせる

v2.25.2 のスキーマ（`internal/cmn/schema/dag.schema.json`）と仕様書（`specs/`）に合わせた。

| 選んだもの | 理由 |
|---|---|
| `action: exec` + `with.args` | `command` は非推奨。argv で渡すのでシェルの引用規則に依らず、Windows の空白入りパスでも壊れない |
| 成果物は相対パス | ステップの作業フォルダは既定で実行ごとの `DAG_RUN_WORK_DIR`。`stdout:` の相対パスも同じ場所に解決される。実行どうしで成果物が混ざらず、作業フォルダを作る前処理が要らない |
| 入力は絶対パスの `params` | 作業フォルダが実行ごとに変わるので、入力は絶対パスにする（`build` の時点で絶対化する） |
| `${params.NAME}` で参照 | v2 の名前つき引数の参照形 |
| 入口の文書に `name` を書かない | v2 では入口の文書の `name` は不可（ファイル名が DAG 名） |
| `type: graph` + `depends` | 依存の無いステップは Dagu が並列に流す |
| `continue_on.exit_code` + `mark_success` | 「指摘があると 1 で終わる」検査系を、成果物ができた成功として扱う |

インタプリタは `build` を走らせた Python（`sys.executable`）の絶対パスにする。DAG はその環境の
スキル置き場の絶対パスを含むので、もともと環境ごとに作る前提であり、別の Python に揺れないほうがよい。

### 2.5 エージェント CLI を呼ぶステップも宣言のアクションにする

スクリプトが無い変換（監査結果を読んで優先順位をまとめる、など）は LLM に任せるしかない。これを
DAG に手で足すと 2.1 の利点（どの環境でも同じ DAG）が崩れるので、`run` の代わりに `agent`
（プロンプト）を持つアクションとして宣言し、同じ探索に載せる。

- **起動方法は `agents/<name>.json` から組む。** CLI ごとの argv の知識はこのリポジトリでは定義ファイルが
  持つ（[エージェント CLI 仕様](../specs/agent-cli-spec.md)）。探索順と argv の並び
  （command + 権限フラグ + モデル + suffix + プロンプト）は `agentcore.agentcli` に合わせた。スキルは単独で
  配られ agentcore を import できるとは限らないので、必要な部分だけを持つ。
- **最初は kiro-cli だけを確かめた形に絞る。** DAG のステップは argv を 1 回組むだけなので、プロンプトを
  引数で受け取り応答を標準出力に出す CLI（`prompt_via: argv`・`output: stdout`）だけを受け付け、
  それ以外は理由を名指しして止める。標準入力で受け取る CLI は、プロンプトを作業フォルダのファイルに
  書いて Dagu の `stdin` で渡す形で足せる。
- **コストはスクリプトの 100 倍。** スクリプトだけでつながる経路が常に勝ち、エージェントは穴を埋める
  ところにだけ入る。`--no-agent` で探索から外せる。
- **権限は出力の形から決める。** ファイルを書かせるとき（プロンプトに `{out:…}`）だけ書き込み可
  （kiro なら `--trust-all-tools`）、そうでなければ読み取りだけ（`--trust-tools=fs_read`）。
- 定義の `empty_output_is_error` は DAG にまだ反映していない（Dagu の exec は終了コードしか見ない）。
  CLI が 0 で終われば、応答が空でもステップは成功になる（既知の制限）。
- スキルにしない手元の宣言は `--actions <ファイル>` で足す。名前はファイル名から取り、スキル名と重なれば止める。

## 3. 範囲外

- 型の中身の検査（JSON スキーマとの照合など）。宣言を信じる。
- 条件分岐・繰り返し。Dagu には `preconditions` や `repeat_policy` があるが、宣言から決定的に
  決められないので出さない。要るなら生成物の外で書く。
- 定期実行の設定。生成した YAML に利用者が `schedule:` を足す。

## 4. 検証

- `tests/test_chain.py`: 宣言の検査、走査の優先順位、探索（最短・同点・`--avoid`・共有・組めない理由・
  スクリプトの経路がエージェントに勝つこと・`--no-agent`）、エージェントのステップの argv（読み取り / 書き込み・
  モデル・env・制限時間・CLI の指定）、使えない定義の止め方、`--actions`、同梱の `agents/kiro.json` が読めること、
  書き出しの形、生成した DAG を Dagu の代わりに順に流して成果物ができること、同梱の宣言が検査を通ること。
- 生成した YAML を Dagu v2.25.2 の `dag.schema.json` で検証し、エラー 0 件を確認した（2026-11-03、手元）。
  Dagu 本体での実行（`dagu validate` / `dagu start`）はまだ確かめていない。
