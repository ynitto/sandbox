# Agent Dashboard: ローカル文書からのバックログ候補生成設計

> 作成: 2026-08-02  
> 対象: `tools/agent-dashboard`  
> 状態: 承認済み

## 1. 背景

現在のメモタスク化は、選択したメモブロックだけを AI に渡してタスク候補を作る。計画書、設計書、
要件定義書などを別ファイルで持っている場合、メモにファイルパスだけを書いても AI には本文が渡らず、
十分な根拠を持ってバックログへ分解できない。

ローカル文書を一度だけ選び、その本文からバックログ候補を生成できる直接導線を追加する。文書やパスを
プロジェクトへ保存せず、既存の「AI が候補を作り、人が確認してから追加する」境界を維持する。
メモの短い要望と文書本文は、入力種別だけを持つ同じ候補生成経路へ合流させる。

## 2. 目的と非目標

### 目的

- 同じ PC 上の `.md` / `.txt` を選び、内容をバックログ候補へ分解できる。
- メモの短い利用者コメントも、同じ AI 補助で実行可能な候補へ分解できる。
- AI が文書の種類と内容を判断し、実行可能で完了判定できる粒度の候補を作る。
- 候補を確認・修正してから、既存のタスク追加経路へ送る。
- 絶対パスと本文を永続化せず、選択した一回の候補生成だけに使う。

### 非目標

- PDF、Word、画像、URL、クラウド文書への対応。
- 選択文書のプロジェクトへの添付、同期、更新監視、履歴管理。
- 文書からの自動タスク追加や自動実行。
- 文書の完全な構造を保つ専用パーサー。

## 3. UI

バックログ画面の既存「メモ」操作の隣に「文書から作る」を置く。メモと同じ固定サイズの
`dialog-shell` を使い、操作中に外枠を伸縮させない。

ダイアログは次の順で表示する。

1. 見出し「文書からタスク候補を作る」と短い説明。
2. 「文書を選択」ボタン。OS 標準のファイル選択を開き、`.md` / `.txt` だけを選べる。
3. 選択後はファイル名と本文プレビューを読み取り専用のスクロール領域に表示する。
4. メモ画面と同じ計画バージョン選択と、その版の目標説明を表示する。
5. 右下に「候補を作る」、その隣に「閉じる」を置く。

別の文書を選び直せるが、同時に保持するのは一件だけとする。ダイアログを閉じた時点で本文を破棄する。
絶対パスは表示せず、ファイル名だけを表示する。

候補生成後は既存の候補確認 UI を再利用し、候補ごとの採否、タイトル、作業内容、受入基準を編集できる。
確定時は既存の inbox 追加経路を候補ごとに呼ぶ。メモ由来ではないため `.task-links.json` は更新しない。

## 4. データフロー

```text
バックログ画面
  → OS 標準ファイル選択
  → main process で検査・一時読込
  → renderer へ { name, content }
  → 共通の読み取り専用 AI 補助（source-task-candidates）
  → { rationale, tasks[] }
  → 既存候補確認 UI
  → 人が確定
  → 既存 enqueueTask
```

ファイル選択と読み込みは main process に限定し、renderer に任意パスの読み取り API は公開しない。
IPC は利用者が選択した一件の内容だけを返す専用操作にする。

AI へ渡すコンテキストは次の情報に限定する。

- ファイル名
- 文書本文
- 選択中の計画バージョンの goal / acceptance
- 既存 backlog / archive の要約

絶対パスは AI へ渡さない。文書本文は命令ではなく分析対象のデータとして区切り、本文中のコマンド、
ファイル操作指示、プロンプト変更指示には従わないよう明記する。AI 補助は現在と同じ読み取り専用・
セッション非保持で起動する。

## 5. AI 応答契約

既存のタスク候補フィールドを再利用する。

```json
{
  "rationale": "分解方針または候補なしの理由",
  "tasks": [
    {
      "title": "タスク名",
      "desc": "変更してほしいこと",
      "acceptance": ["完了条件"],
      "priority": 0,
      "after": [],
      "why": "必要な理由"
    }
  ]
}
```

- `tasks` は 0〜8 件とする。
- 文書に実行可能な作業がなければ空配列を正常結果として許し、`rationale` を画面に表示する。
- 文書全体を漏れなく細分化するより、独立して完了判定できるまとまりを優先する。
- 根拠のない作業、選択文書にない要件、未知の既存タスク ID を作らない。
- JSON 全体を 6000 文字以内に収める。

候補生成処理と応答正規化はメモ・文書で共通にする。空配列の意味だけが異なり、メモは選択文から
最低一候補へ補完するが、文書入力では
「実行項目なし」という AI の判断を保持し、ローカル候補へ補完しない。

## 6. 入力検査とエラー表示

- 許可する拡張子は大文字小文字を区別せず `.md` / `.txt` のみ。
- 最大サイズは 64 KiB。超過時は黙って切らず、ファイルを小さく分けるよう案内する。
- 空ファイル、読み込み失敗、バイナリ相当の内容は候補生成前に拒否する。
- ファイル選択のキャンセルはエラーにしない。
- AI 応答が JSON として壊れている場合は選択文書とバージョン選択を保持し、再試行できる。
- `tasks: []` はエラーにせず、`rationale` または「実行可能な候補は見つかりませんでした」を表示する。
- 一部のタスク追加だけが失敗した場合は、既存候補 UI と同じく失敗分だけ再試行できる。

## 7. 既存機能の再利用

- Electron の既存 `dialog.showOpenDialog` の方式を再利用する。
- `agentTaskAssist` にメモ・文書共通の `source-task-candidates` モードを追加する。
- 候補の正規化、候補確認ダイアログ、`enqueueTask` を再利用する。
- 計画バージョン選択と説明表示はメモ UI と同じ helper を使う。
- 新しい文書ストア、添付ファイル管理、パーサー依存は追加しない。

## 8. テスト

最小構成として次を確認する。

1. ファイル選択 IPC が `.md` / `.txt` の一件だけを読み、名前と本文を返す。
2. キャンセル、拡張子違反、空ファイル、64 KiB 超過、読み込み失敗を区別する。
3. プロンプトに文書本文、charter、既存 backlog が載り、文書を命令として扱わない指示がある。
4. 文書用モードは `tasks: []` と `rationale` を正常結果として通す。
5. 候補確認まで `enqueueTask` を呼ばず、確定した候補だけを追加する。
6. 文書由来の追加ではメモリンクを更新しない。
7. ダイアログを閉じると本文が破棄され、再度開いたときに残らない。
8. キーボード操作、フォーカス表示、375 px / 768 px / 1024 px / 1440 px の表示を確認する。

## 9. 実装順

1. main / preload / IPC に一回限りの文書選択 API と入力検査を追加する。
2. メモ・文書共通の `source-task-candidates` モードと応答契約テストを追加する。
3. バックログの「メモ」隣に導線と固定ダイアログを追加する。
4. 既存候補確認 UI を文書入力でも使えるよう、メモリンク処理だけ分岐する。
5. エラー復旧、空候補、主要画面幅の統合テストを追加する。
