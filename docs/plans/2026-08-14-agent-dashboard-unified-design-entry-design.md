# Agent Dashboard 共通設計フェーズ・3つの開始方法 設計

## 背景

ワークフロー画面には、短い要望から設計を詰める設計セッションと、外部の設計 Markdown を依頼欄へ
読み込む機能がある。しかし、入口が「設計を練る」「対話型／全自動」「設計書を読み込む」に分散し、
ユーザーが今持っている材料に応じて何を選ぶべきか分かりにくい。

プロジェクト作成画面にも自由入力と AI 下書きはあるが、設計途中の Markdown を引き継ぐ経路や、
完成した設計書をプロジェクトの charter へ変換する経路がない。ワークフローとプロジェクトで
設計フェーズの概念と操作が異なり、同じ作業を別の用語で学ぶ必要がある。

本設計では、両領域の設計入口を次の3択へ統一する。

1. 一から設計する
2. 続きから設計する
3. 設計書をそのまま使う

設計セッションと Markdown の作業コピーは共通化し、完成後の受け渡しだけをワークフローと
プロジェクトで分ける。プロジェクトでは単一の charter だけを成果とせず、マスター憲章、複数の
計画バージョン、メモ、ドキュメントを型付き入力として束ね、複数のバックログ候補群へ結線する。

## 置き換える既存判断

[2026-08-13 の設計](./2026-08-13-agent-dashboard-design-session-design.md)では、入口を
「外部設計書の取り込み」と「短文からの設計セッション」の2経路とし、設計セッション内部で
対話型／全自動型を選ぶ構成を採用した。

この判断を次の理由で更新する。

- ユーザーが判断したいのはエージェントの実行方式ではなく、現在の設計材料が「ない／途中／完成」の
  どれかである。
- 全自動型と完成済み設計書の直接利用は、質問を挟まず実行へ進むという画面上の目的が重複する。
- プロジェクトへ同じ設計フェーズを導入するには、ワークフロー依頼欄を合流点にする既存構造では
  共通化できない。

既存の「1ラウンド = 1本の短命な設計 run」「原本を直接更新しない」「設計 run と実装 run を分離する」
判断は維持する。

## 採用方針

| アプローチ | 実装コスト | リスク | 保守性 | 拡張性 | 学習コスト | UX統一 | 推奨度 |
|---|---|---|---|---|---|---|---|
| A. 共通設計セッション＋対象別変換 | 中 | 中 | 高 | 高 | 低 | 高 | ★★★ |
| B. UIだけ共通化し内部処理を別実装 | 低 | 中 | 低 | 中 | 中 | 中 | ★★☆ |
| C. プロジェクトとワークフローで完全に別実装 | 高 | 高 | 低 | 低 | 高 | 低 | ★☆☆ |

案 A を採用する。設計の入力、作業コピー、質問、ラウンド、保存は共通サービスが管理し、完成した
設計モデルを実行対象へ変換する処理だけを対象別アダプターにする。ワークフローは単一の実行依頼、
プロジェクトは型付き入力から複数の計画・バックログ候補群を生成する。

## UI構成

### 共通の開始画面

ワークフローの作成画面とプロジェクト作成画面の設計フェーズ先頭に、同じ順序・名称・説明を持つ
3つの選択カードを表示する。

| 選択肢 | 説明 | 選択後に表示する入力 |
|---|---|---|
| 一から設計する | 要望からエージェントと対話して設計を作る | やりたいこと、対象フォルダ |
| 続きから設計する | 設計途中の Markdown を解析して対話を続ける | `.md` ファイル、対象フォルダ |
| 設計書をそのまま使う | 完成済み Markdown を実行用へ変換する | `.md` ファイル、対象フォルダ |

カード選択前に3方式の入力フォームを同時表示しない。選択後は必要な入力だけを段階表示し、方式を
変更した場合も、未実行の入力をただちに破棄しない。

- カード全体を選択可能にし、44px以上の操作領域と可視フォーカスを持たせる。
- 選択状態は枠、背景、ラジオ状態、文字のすべてで示す。
- ファイル名、サイズ、読み込み結果をカード直下に表示する。
- ファイル選択後に拡張子、空ファイル、読み込み可否、サイズをインライン検証する。
- 処理中は開始ボタンを無効化し、処理名と進行状態を表示する。

### 一から設計する

短い「やりたいこと」を入力して、対話型の設計セッションを開始する。エージェントは各ラウンドで
完全な設計書と次の質問を返す。ユーザーは回答して次のラウンドへ進むか、現在の設計を保存・実行する。

既存の全自動型は開始方法から外す。質問を挟まない利用は「設計書をそのまま使う」へ集約し、短文を
自動で膨らませて即実行する曖昧な入口を初版には置かない。

### 続きから設計する

選択した Markdown を読み込み時点のスナップショットとして保存し、セッションの `document` へ
作業コピーを作る。原本は読み取り専用とし、自動上書きしない。

最初の設計 run は、文書から次を整理する。

- 既に決まっている事項
- 未確定事項
- 矛盾または不足
- 次に人へ確認すべき質問

解析結果も完全な設計書＋質問の既存 Markdown 規約で返し、その後は「一から設計する」と同じ
ラウンド制御を使う。完成時は保存先を選び、Markdownを書き出す。読み込み元と同じパスを選んだ場合は
明示的に上書き確認を行う。

### 設計書をそのまま使う

選択した Markdown を対話的に再設計せず、対象の実行契約へ変換する。「そのまま」は内容上の決定を
追加・削除しないことを意味し、見出しの正規化や対象契約への構造変換は行う。

変換後は、原文、変換結果、警告を区別してプレビューする。ユーザーが確認して実行を選ぶまで、
agent-flowへの投入やプロジェクトファイルの作成は行わない。

変換で確定できない値を推測して埋めない。不足事項は警告と実行前入力として表示する。

## 共通セッション契約

設計セッションはワークフロー機能の内部状態から共通機能へ移し、次の加算的な契約を持つ。

```json
{
  "version": 2,
  "id": "ds-...",
  "target": "workflow",
  "sourceMode": "continue",
  "sourcePath": "/path/to/design.md",
  "sourceSnapshot": "# ...",
  "sources": [],
  "goal": "",
  "document": "# ...",
  "questions": [],
  "rounds": [],
  "proposal": null,
  "application": null,
  "outputPath": "",
  "createdAt": "...",
  "updatedAt": "..."
}
```

- `target`: `workflow` または `project`
- `sourceMode`: `new`、`continue`、`use-as-is`
- `sourcePath`: 読み込み元。原本の追跡用であり、再読込を暗黙には行わない
- `sourceSnapshot`: 読み込み時の原文。後から原文と作業結果を比較できる
- `sources`: マスター憲章、計画バージョン、メモ、ドキュメントなど型付き入力のスナップショット
- `document`: 現在の作業コピー
- `rounds`: 質問、回答、設計 run ID、結果の履歴
- `proposal`: 対象別に変換したプレビュー、警告、各候補の出典
- `application`: 反映IDと項目別の成功・未反映状態。再試行時の二重投入を防ぐ
- `outputPath`: ユーザーが保存を確定した場合だけ設定

既存version 1の設計セッションは、`target=workflow`、`sourceMode=new` として読み取る。移行のために
既存ファイルを一括書き換えない。

## 設計run

設計runは引き続き、1ラウンドごとの短命な agent-flow run とする。humanノードで長時間parkさせず、
Dashboardが質問と回答のラウンドを決定的に制御する。

共通のrun種別は次の3つとする。

| run種別 | 用途 | 対話 |
|---|---|---|
| `design-create` | 短い要望から完全な設計書と質問を作る | あり |
| `design-continue` | 途中文書を解析し、更新版と質問を作る | あり |
| `design-convert` | 完成文書を対象契約へ変換する | なし |

`design-create` と `design-continue` は同じラウンド成果規約を使う。sink出力末尾の `## 質問` を分離し、
質問がなければ収束とみなす。`design-convert` は変換結果と警告を返し、実行前プレビューへ渡す。

## 対象別アダプター

### ワークフロー

完成した設計書を、agent-flowへ渡す依頼Markdownへ変換する。

- 目的
- 変更対象またはスコープ
- 受入基準
- 検証方法
- 制約・前提・非目標（存在する場合）

変換結果の全文をinboxの依頼として固定する。元ファイルのパスだけを渡さない。実行フロー、作業ルール、
実行方針は設計書とは別の既存実行フォームで選ぶ。

### プロジェクト入力バンドル

プロジェクト対象では、単一の設計Markdownだけを入力にせず、次の既存入力を型付きソースとして
共通設計セッションへ渡す。

| 入力 | 件数 | 意味 | 自動選択 |
|---|---:|---|---|
| マスター憲章 | 0〜1 | 全計画へ効く共通目的、制約、前提 | 既存プロジェクトでは選択済み |
| 計画バージョン | 0〜複数 | 達成単位ごとの目標、成果物、達成条件 | ユーザーが対象を選ぶ |
| メモ | 0〜複数 | 未確定の観点。確定要件ではない | ユーザーがファイルまたはブロックを選ぶ |
| ドキュメント | 0〜複数 | 仕様、調査、根拠、外部設計書 | ユーザーが選ぶ |
| 開始時Markdown | 0〜1 | `continue` / `use-as-is` で指定した主文書 | 指定時に選択済み |

各ソースは種別、名前、パス、読み込み時ハッシュ、本文スナップショットを持つ。単一Markdownへ
無差別に連結せず、エージェントへ種別と意味を明示して渡す。

入力の優先順は、マスター憲章の共通制約・前提、対象計画バージョンの目標・達成条件、設計セッションで
人が回答した内容、ドキュメントの根拠、メモの未確定事項とする。下位入力が上位入力と矛盾する場合は
自動上書きせず質問または警告へ回す。メモや参考文書だけを根拠にマスター憲章を書き換えない。

### プロジェクト提案パッケージ

プロジェクトアダプターは単一のcharter候補ではなく、次の提案パッケージを返す。

```json
{
  "master": { "operation": "keep", "content": "", "sourceRefs": [] },
  "versions": [
    { "proposalId": "version-v1", "operation": "create", "name": "v1",
      "content": "", "sourceRefs": [] }
  ],
  "backlogGroups": [
    { "proposalId": "backlog-v1", "charter": "v1", "tasks": [] }
  ],
  "notes": [],
  "documents": [],
  "warnings": []
}
```

- `master`: マスター憲章の維持、作成、変更提案。既存マスターは暗黙に更新しない
- `versions`: 0件以上の計画バージョン作成・変更提案
- `backlogGroups`: 計画バージョンごとのバックログ候補群
- `notes`: 計画へ確定できずメモとして残す提案
- `documents`: 根拠として保持・参照する文書情報。原本は変更しない
- `sourceRefs`: 各提案の根拠となった入力ソースと該当箇所

バックログ候補はタイトル、理由、作業概要、対象範囲、対象リポジトリ／パス、受入基準、規模、依存、
所属計画バージョン、出典を持つ。候補生成時点で既存backlog、archive、墓標と照合し、重複・類似・
却下方針をプレビューへ表示する。

agent-project内部の物理保存先は既存どおり共通 `backlog/` とする。画面上の複数バックログ候補群は、
各タスクへ `charter` タグを付けることで計画バージョンへ帰属させる。計画ごとに別の物理backlogを
新設しない。

### 新規プロジェクト

新規プロジェクトでは、提案パッケージから次を作る。

- マスター `charter.md`: プロジェクトの目的、共通制約、前提
- 0件以上の `charters/<name>.md`: 計画ごとの目標、成果物、達成条件
- 採用された `notes/*.md`: まだ確定しない観点
- 採用されたバックログ候補: 計画バージョンごとの `charter` タグ付きタスク
- 対象リポジトリ候補: URLや担当範囲が入力で明示される場合だけ候補化

プロジェクト名、作成先、計画バージョン名、確定できないリポジトリ情報はプレビュー画面で人が入力する。

### 既存プロジェクト

既存プロジェクトでは、選択した既存入力を設計材料にし、マスターの差分、0件以上の新規または変更
計画バージョン、メモ、複数バックログ候補群を提案する。既存マスターと計画バージョンは、提案ごとに
人が変更を採用した場合だけ更新する。マスターの制約・前提との矛盾は警告として表示する。

### プロジェクト提案のレビュー

プロジェクト対象の確認画面を次の4段階にする。

1. **設計材料** — マスター、計画バージョン、メモ、ドキュメントを選ぶ
2. **設計** — 対話または完成文書の変換を行う
3. **配分確認** — 共通事項、各計画バージョン、未確定メモへの配分を確認する
4. **バックログ確認** — 計画バージョン別に候補を確認する

ユーザーはマスター変更、計画バージョン、バックログ候補、メモを個別に採用・編集・除外できる。
バックログ候補の所属バージョンも変更できる。選択カード、グループ見出し、項目のチェック操作は
44px以上の操作領域を持ち、現在のステップと未確認件数を文字で表示する。

### 反映経路

「反映」を押すまではプロジェクトへ書き込まない。反映前に名前、依存、リポジトリ参照、受入基準、
既存ファイル競合を全件検証する。

1. マスター憲章を作成、または明示承認された差分だけ更新する
2. 採用された計画バージョンを作成・更新する
3. 採用された未確定事項を `notes/*.md` へ保存する
4. 採用されたバックログ候補を既存の整合入口へ投入する
5. `charter` タグ、依存関係、出典、反映IDを付与する
6. セッションの `application` へ項目別の成功・失敗を記録する

バックログファイルを直接生成せず、既存の重複照合、墓標照合、計画レビュー経路を通す。提案段階で
既にタスク候補を生成しているため、charter保存後に無条件のreplanを追加して二重生成しない。
途中失敗時は未反映項目だけを再試行し、成功済みの `proposalId` と反映IDを再投入しない。

メモは選択しただけではバックログ化しない。提案された候補のうち人が採用した項目だけを投入し、
未確定のまま残す内容はメモとして保存する。ドキュメントは出典スナップショットとして参照し、原本を
変更しない。

## セッション一覧と再開

設計セッション一覧はrun履歴と分けて表示し、対象、開始方法、元文書名、更新時刻、質問数、状態を示す。
「一から設計する」で途中保存したものを含め、すべて同じ一覧から再開・破棄できる。

ワークフロー領域ではワークフロー対象、プロジェクト領域では選択プロジェクトまたは新規プロジェクト対象を
既定で絞り込む。他方の領域のセッションを勝手に変換して表示しない。

## 保存と原本保護

- 読み込んだMarkdownは常に `sourceSnapshot` として保持する。
- 設計runはセッション内の `document` だけを更新する。
- 自動保存先はセッションJSONであり、読み込み元Markdownではない。
- Markdownへの書き出しは、保存先をユーザーが選んだ場合だけ行う。
- 既存ファイルへの保存は上書き確認を必須とする。
- 保存処理は一時ファイル＋renameで行い、途中失敗で対象ファイルを壊さない。

## エラー処理

- `.md` 以外、空ファイル、読み込み不能は開始前にファイル欄で拒否する。
- 100KB超は警告する。実行基盤の実測上限を超える場合だけ開始を止める。
- 文字コードをUTF-8として読めない場合は、自動変換せずエラーにする。
- 設計runの失敗・中止後も原文、作業コピー、回答を保持し、再試行できるようにする。
- 原本が読み込み後に変わっても自動マージしない。保存時にmtimeまたはハッシュが変わっていれば警告する。
- 変換で必須項目が不足する場合は、原文を勝手に補完せず警告または実行前入力にする。
- プロジェクト作成やagent-flow投入に失敗しても、変換結果とセッションを保持する。

## アクセシビリティとレスポンシブ

- 3択はradiogroup相当のキーボード操作と選択状態を持つ。
- カード、ファイル選択、主要ボタンは44px以上の操作領域を持つ。
- ラベルをplaceholderだけで表現しない。
- 検証エラーは入力の近くへ表示し、`role=alert`または`aria-live`で通知する。
- 処理中はボタン文言と状態表示を更新し、色だけで進行を表さない。
- 狭幅ではカードを1列にし、原文／変換結果の比較は上下配置へ切り替える。

## テスト

1. ワークフローとプロジェクトで同じ3択、順序、説明が表示される。
2. 選択した方式に必要な入力だけが表示され、キーボードで選択できる。
3. `new` は短文から対話セッションを作り、質問回答で次ラウンドへ進める。
4. `continue` は原本を変更せず作業コピーを作り、途中文書から質問を生成する。
5. `use-as-is` は質問を作らず、対象別変換とプレビューへ進む。
6. workflow変換は実行依頼Markdownを生成し、確認後にだけinboxへ投入する。
7. project変換はマスター、複数計画バージョン、メモ、ドキュメントを型付き入力として区別する。
8. 1セッションから複数計画バージョンと、各バージョンに属する複数バックログ候補を生成できる。
9. 候補を計画単位・項目単位で採用、編集、除外し、所属計画を変更できる。
10. 採用タスクは共通 `backlog/` へ既存整合入口経由で入り、正しい `charter` タグを持つ。
11. メモは選択しただけで自動タスク化されず、ドキュメント原本は変更されない。
12. 既存プロジェクトでは明示承認のないマスター・計画バージョンを上書きしない。
13. 部分失敗後の再試行で、成功済みproposalIdのファイル・タスクを二重生成しない。
14. version 1の既存設計セッションをworkflow/newとして再開できる。
15. 空ファイル、不正拡張子、UTF-8不正、変換失敗、競合上書きを安全に扱う。
16. 375px、768px、1024px、1440pxで不要な横スクロールがない。
17. 既存の設計run、プロジェクト作成、ワークフロー投入が回帰しない。

## 非目標

- 読み込み元Markdownの自動上書き・自動マージ
- 複数Markdownの同時統合
- 設計runと実装runを1本の長時間runへ統合すること
- 完成済み設計書の内容を対話なしで創作・拡張すること
- agent-flowまたはagent-projectの実行エンジン刷新

## 実装計画

1. 既存design-session契約をversion 2へ拡張し、共通機能へ移す。
2. Markdown読込、スナップショット、作業コピー、競合検知、原子的保存を追加する。
3. `design-create`、`design-continue`、`design-convert` のrun入力と成果契約を追加する。
4. workflow用の依頼Markdown変換アダプターとプレビューを実装する。
5. project用の型付き入力バンドルとProjectDesignProposal変換アダプターを実装する。
6. 計画バージョン別バックログ候補、出典、既存タスク・墓標照合を提案へ接続する。
7. マスター／計画／メモ／タスクの項目別承認と、冪等な反映記録を実装する。
8. ワークフロー作成画面へ共通3択UIを組み込み、既存の分散した取込・モード選択を置き換える。
9. 新規／既存プロジェクトの設計入口へ、材料選択・配分確認・バックログ確認を含む同じ3択UIを組み込む。
10. セッション一覧、再開、保存、破棄を対象別に接続する。
11. 契約、変換、原本保護、部分反映、UI、レスポンシブのテストを追加し、既存テストとESLintを実行する。

## 既存スキルとの関係

- `ui-designer`: 3択カード、段階表示、44px操作領域、インライン検証、処理フィードバックへ反映した。
- `contract-driven-development`: 共通セッションversion 2と対象別変換契約の実装時に利用できる。
- `failure-driven-development`: 原本競合、変換失敗、部分的なプロジェクト作成失敗の境界設計に利用できる。
- `webapp-testing`: 両領域の3経路、プレビュー、狭幅表示の実画面検証に利用できる。
