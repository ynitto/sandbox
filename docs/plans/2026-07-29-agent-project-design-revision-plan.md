## この計画の考え方

レビューは 24 件あるが、24 通りの機構を足すと設計書が壊れる。指摘の大半は
「不変条件が層をまたぐと曖昧になる」「時刻と状態のどちらが正か書いていない」「単位が書いていない」
「投影が片方向で止まっている」の 4 つに帰着する。そこで**梁を 4 本立てて大半をそこで受け**、
残りは 1 行の契約で閉じる。

**先に決める「増やさないもの」**（この制約が計画全体の単純さを担保する）:

- 新しい常駐プロセス・新しいバス・新しいイベント台帳を作らない
- 新しい状態ファイル形式を増やさない（既存の `backlog/` `needs/` `verifications/` `project.json` で足りる範囲に収める）
- 新しい語彙を増やさない（「検証の強さ」「信頼レベル」のような等級を導入しない）
- 判定の 2 実装を作らない。既存の 1 実装へ経路を寄せる方向にだけ直す

## 梁 1 — done の根拠は 2 表現だけ。それを層をまたいで同一にする

**契約**: done を確定できる根拠は 2 表現に限る。**(a) 決定的コマンドの終了コード 0**、
**(b) 受入基準 × 証跡の全 pass**。この 2 表現が、タスク層・charter の `## acceptance`・
他ノードへの検証委譲の**3 経路すべてで同一**であり、経路によって強さが変わらない。
人のプロジェクト done は「この方向でよいか」の価値判断であって品質保証ではない（C5）——
人が細部を見落としても done の意味は壊れない、という関係を設計書に明示する。

| # | 直すこと | 閉じる指摘 |
|---|---|---|
| 1-1 | 3 層の関係を明文化する。タスク verify ／ charter acceptance ／ 人のプロジェクト done を「同じ 2 表現＋価値判断」として並べ、人の検収が機械検証の代替でないことを書く | #1 |
| 1-2 | `## acceptance` を二表現へ。各行を「決定的コマンド行」と「自然文基準行」に分け、自然文行は verifier が証跡付きで判定する。**自然文→コマンドの一発合成は廃止**（既存の残課題を、別設計に回さずここで閉じる） | #1 #3 #24 |
| 1-3 | **証跡チェックを 1 実装にして全経路へ課す。** 決定的チェックは 3 つだけ: ① 参照ファイルが検証対象の成果コミットに実在する ② 各 pass に「実行したコマンドとその終了コード」が対応づく（記録の無い出力は証跡と認めない） ③ 差分基準を満たす。内蔵 verifier・`verifier_skill`・他ノードの `external.json` の**すべて**がこの同じチェックを通り、通らない pass は機械的に fail | #2 #3 #4 #15 |
| 1-4 | 外部検証の受理は「**誰が**確かめたか」では分岐させない（現行判断を維持）。代わりに「**何を出したか**」で分岐する＝ 1-3 のチェックを外部判定にも同じだけ課す。板のノード契約版が合わない判定は fail | #4 |
| 1-5 | `verify_side_effects` の禁止は**強制しないと明記**する（非目標）。担保は事後検知——実行コマンドの記録（1-3 ②）が必須なので、逸脱は検証レポートを読めば追える。サンドボックスも許可コマンド列挙も持たない | #15 |
| 1-6 | 差分基準の逃げ道を、基準を消さずに作る。タスクに `- no_diff: <理由>` があると `DIFF_CRITERION` は**「宣言した成果物ファイルの実在と、その内容の参照」へ差し替わる**（消えない）。調査・方針・ドキュメント・「変更しないこと」系はここに載る | #16 |

**なぜこれで足りるか**: レビューの「証跡の真正性」は、LLM に真正性を証明させる方向では閉じない。
閉じるのは「**記録の無いものを証跡と認めない**」というフェイルクローズだけで、これは既存の
「証跡の無い pass は fail」の延長線上にある。証跡の再実行検算は行わない（下記 非目標）。

## 梁 2 — 正は状態。時刻は締切のヒントにすぎない

**契約**: リースの時刻は「そろそろ諦めてよい」という**ヒント**で、実行権の正本は remote の
`owner/token/generation` を CAS で確認できたときだけ与えられる。時計がずれても、奪取側は
CAS を通るまで実行権を持たない。復旧手順も新設しない——正は常に `remote の backlog + archive`
であり、その他は投影として毎パスの整合点が作り直す（判断 5-b の形をそのまま広げる）。

| # | 直すこと | 閉じる指摘 |
|---|---|---|
| 2-1 | リース失効の解釈を明文化。「失効＝奪取可」ではなく「失効＝奪取を**試みてよい**」。奪取は CAS 経由でしか成立しないので、skew は二重実行にならず、早期奪取は push 失敗として現れる | #6 |
| 2-2 | **settle は 1 コミット 1 原子**にする。archive・納品書・needs・verifications・claim 解放は 1 コミットにまとめ、push が通った時点で確定。途中死は「未 push のコミットがローカルに 1 つある」状態に落ち、次パスは remote を正として再突合する | #8 |
| 2-3 | クラッシュ復旧の契約を「投影の再計算」と明記する。専用のリカバリ手順・ジャーナル巻き戻しは持たない | #8 #11 |
| 2-4 | 実行経路は二系統ではないことを明文化。`board` 委譲は **claim を握ったまま実行先が board になるだけ**（`offloaded`）で、fencing は local と同一。**検証だけの委譲は成果を動かさないので claim を取らない**（受理点は `external.json`）——この非対称が「同一タスクが両方の意味で実行中」に見える窓の正体 | #10 #11 |
| 2-5 | `claims/` は同期しないホスト局所キャッシュで、正本ではないと明記。孤児 claim は投影の掃除対象（既存の孤児掃除に載る） | #11 |
| 2-6 | `unknown` 隔離を「必ず止まる」（不変条件 2）に載せる。隔離件数に上限を持ち、超えたそのノードは **report へ降格**して新規 claim を止める（既存 throttle と同じ出口）。自動再試行は次パスの fencing 再確認 1 回だけで、それ以上は人待ち | #7 |

## 梁 3 — 予算はノード別、進行はプロジェクト共有

**契約**: 財布に紐づく上限（トークン・コスト・実時間）は**ノード別**で、host.yaml の `budget` が正。
合算しない（C1: クレジットは個人のもの）。進行に紐づく上限（改善サイクル数・停滞の連続回数・
acceptance の PASS 数）は**プロジェクト共有**で、`project.json` が正。

| # | 直すこと | 閉じる指摘 |
|---|---|---|
| 3-1 | 上記の単位を設計書に書く。二重計上は「別の財布を別に数えている」ので正しい挙動 | #9 |
| 3-2 | throttle はノード局所の降格であり、他ノードは走り続ける——これを意図した挙動として明記する | #9 |
| 3-3 | **目標駆動モードでは人が律速であることを非目標へ書く。** 無人で回るのは backlog 消化（正準ループ）で、分解・未達 acceptance の扱い・プロジェクト done は人。目標節の「backlog が空か予算まで無人運転」はタスク層の目標だと限定する | #12 |

## #19 再整理 — 日本語タイトルの「一致性」は機械に判定させない

レビュー #19 は「投入側 Jaccard が日本語で実質無効 → 言い換え防衛がプランナー任せ → カスタム
`planner_skill` と組むと鉄則級の護りが無い」という指摘。初稿の計画はここを**文字 bigram Jaccard**
で閉じようとしたが、それは「空白の無い日本語が 1 トークンになる」という**トークン化のバグ**への
応急処置であって、指摘の本体（**意図が同じかの判定**）には届かない。

タイトルの一致性——「ログイン機能を追加」と「ユーザー認証を実装」、「dashboard の board UI を
作る」と「dashboard の board 観測 UI を作る」——は表面類似では測れない。閾値を下げれば無関係な
題を潰し、上げれば言い換えを通す。**機械的な判定は難しい**、がこの計画の前提になる。

S6 で既に採った一次防衛——**現バージョンのバックログをプランナーへ渡し、重複を出させない**——を
改めて正とする。実装は `_backlog_existing_summary` / `build_planner_input` の `existing[]` と
スキル契約「意図が似ているものは出さない」がそれに当たる。#19 でやるのは bigram 実装ではなく、
この戦略を設計書に一本化し、機械側の役割を狭く再定義すること。

### 戦略の比較（pros / cons）

| 案 | 内容 | pros | cons |
|---|---|---|---|
| **A. 文字 bigram Jaccard**（初稿） | 投入側のトークン化を bigram にし、日本語でも部分一致スコアが出るようにする | 決定的・安価・スキル差し替えでも迂回不可。トークン化バグ自体は直る | **意図の同一性は測れない**（語彙が違う言い換えはスコア 0 のまま）。閾値次第で偽陽性＝取り返しのつかない抑止、偽陰性＝すり抜け。#19 の本体を閉じた気になるだけで残る |
| **B. 既存バックログ全件を LLM へ**（採用・再確認） | 現役（blocked/doing/offloaded/review）＋却下済み（理由付き・有界）を `existing[]` に載せ、「同じ意図は出さない」をスキル責務にする | 言い換え・粒度変更を捉えられる。S6 で一次防衛として既に実装済み。抑止ではなく生成時に出させないので、黙って落とす無駄トークンも減る。設計の「提示は取り返しがつく／抑止は取り返しがつかない」と整合 | スキル差し替えで契約を無視されうる（鉄則にはならない）。**コンテキスト肥大**（却下は直近 30 件で有界だが、現役は件数上限なし・件あたり summary 160 字）。LLM が約束を破れば重複は出る。品質がプロンプト／モデル依存 |
| **C. 生成後の別 LLM 重複裁定** | enqueue 前にもう 1 回 LLM を呼び、候補×既存を突き合わせる | 組み込みにすればスキル差し替えを迂回できる。意味的判定ができる | **判定の 2 実装**（プランナー＋裁定）になり「増やさないもの」に抵触。コスト二重。硬抑止にすると偽陽性が取り返し不能、軟判定だと needs 注記が増えるだけ。新しいゲートを足す |
| **D. embedding / 形態素解析** | 外部モデルや辞書で類似度を取る | 決定的に見え、言い換えにも部分的に効く | 標準ライブラリ前提から外れる。モデル／辞書の運用が増える。閾値問題は A と同じ。本計画の非目標（依存を増やさない）と逆向き |

### コンテキスト肥大と段階的開示

B の cons であるコンテキストは、現状でも既に有界化の芽がある（却下 30 件・summary 160 字・プロンプト表示は現役 200 / 墓標 100）。それでも現役が数百件に育つと「全件＋要約」は重い。**段階的開示はできる**——ただし「何を削ると防衛が壊れるか」で形が分かれる。

| 形 | 内容 | pros | cons | 採否 |
|---|---|---|---|---|
| **B1. 密度の段階（1 ショット）** | **索引は全件**（title + status + `edited` だけ）。要約は高リスクだけ（`doing` / `offloaded` / `review` / `edited: human` / 直近却下）。其余の ready/blocked は題のみ | 呼び出しは 1 回のまま。見落としやすいのは「題が違うが意図が同じ」で、意図の手がかりが要るのは仕掛かり・人確定・却下理由側。トークンは件数に対し線形だが係数が小さい | ready/blocked の言い換え再提案は題同士の判断に寄る。索引から落ちる件が無いこと（**件数の全件性**）が防衛の前提——要約を削っても題は落とさない | **採る方向**（B の実装細化。実害＝コンテキスト圧が出てから P1） |
| **B2. 安価な想起で厚くする（1 ショット）** | 全件索引に加え、charter 文・owns・notes との表層オーバーラップ等の**決定的な安価シグナル**で top-K だけ summary を載せる | B1 より「今の分解テーマに近い既存」へ要約予算を寄せられる | 安価シグナルは意図判定ではない（A と同じ天井）。K とシグナルのチューニングが要る。新しい「類似度」語彙を増やすと設計が太る | B1 で足りないときだけ。シグナルは既存の正規化タイトル／単純部分文字列に留め、新語彙を増やさない |
| **B3. 多ターン開示** | 1 通目は題索引だけで草案 → 衝突しそうな id をモデルが指名 → 2 通目で要約を渡して出し直し | 1 通目を最小化できる | **LLM 呼び出しが 2 回**。スキル契約に「id 指名→再要求」プロトコルが増える。判定の経路が太る（C に近い）。分解は人の明示操作なのでレイテンシ増は許容範囲だが、計画の「増やさない」に逆行 | **採らない**（必要性が B1/B2 を超えたら別計画） |
| **B4. チャンク分割して複数回分解** | バックログを分割し、チャンクごとに「これに対して重複しない分解」を走らせてマージ | 1 回あたりの文脈は小さい | マージで重複・抜けが再発する。分解の正が複数回になり、人が見る提案の一貫性が壊れる | **採らない** |

**契約として残す線**:
1. **件数の全件性は守る** — 現役の title/status 索引から落とさない（ここを落とすと「見えていない既存」への言い換えが通る）。要約の有無は密度の問題であって、一覧からの脱落ではない
2. **却下は現行どおり有界**（直近 N・理由付き）— archive は際限なく育つので、全件性の対象外（既に `_PLANNER_REJECTED_LIMIT = 30`）
3. **多ターン開示・チャンク分割は非目標** — 呼び出し回数とマージ複雑性を増やさない
4. **いつ B1 を実装するか** — 既定の粒度（coarse で 3〜10 件規模）では現役が数十件に収まる想定が先。コンテキスト圧の申告または現役件数の閾値を超えたら P1 で密度段階を入れる。それまでは現行（全件＋ summary 160 字）でよい

### 採る形（B を正、機械は完全一致だけ。肥大は B1 で受ける）

1. **意図の重複防衛の正は B**（必要なら密度だけ B1）。設計書に次を明記する:
   - 同一バージョンのバックログ（保留・実行中・レビュー中・却下済み＋却下理由）をプランナー入力へ載せる
   - 「タイトルが違っても意図が同じ再提案を出さない」はプランナー（スキル）の責務
   - 投入側の類似照合（Jaccard）は**鉄則級の護りではない**——既知の天井として書く（カスタムスキル前提では迂回可能、日本語の表面類似も弱い）
   - コンテキストが重いときは **title/status の全件索引は維持**し、summary だけを高リスクへ寄せる（B1）。多ターン開示はしない
2. **機械側の硬抑止は正規化タイトルの完全一致のみ**（墓標・既存タイトルの完全一致）。類似どまりは抑止せず、プランナー入力への提示と needs 注記に留める——現行判断を維持
3. **A（bigram）は本計画の完了条件から外す**。トークン化バグの修正自体は有用だが、#19 の閉じ方ではない。重複が実際にすり抜けたときの P3 / 契機待ち（`open-items` P3-g・post-canary P3-g と同列）へ戻す
4. **C / D / B3 / B4 は採らない**。C・B3 は呼び出し・経路増、D は依存増、B4 はマージで防衛が壊れる

### カスタムスキルの穴をどう書くか

#19 の「鉄則級ではない」は事実として残る。埋めない理由: 意図の同一性を決定的に強制できる述語が無い以上、投入側に偽の鉄則（bigram 閾値）を置いても護りにならない。護れるのは「完全一致の再投入」だけで、それは既に墓標と `_is_duplicate` の完全一致側が担っている。設計書には**天井を隠さず書く**——差し替え可能スキルを許す以上、言い換え防衛の品質はスキル契約の品質であり、コアの不変条件には載せない。

## 変更する既存の設計判断（明示）

この計画で**撤回・改訂する**のは次の 2 点だけ。他はすべて既存判断の明文化か、その延長。

1. **判断 5-c の一部撤回** — 「削除は後続を再審査（proposed）へ戻さない」を撤回し、戻す（4-1）。
   削除が記録を残さない性格・墓標を積まない性格は維持。
2. **判断 1 末尾とプロジェクト層の改訂** — charter acceptance の「自然文からのコマンド一発合成」を廃止し、
   タスク層と同じ二表現へ寄せる（1-2）。「別設計の課題として残す」という現行の逃げを閉じる。

明文化にとどまる（判断は変えない）もの: 予算の単位（梁 3）、目標駆動モードの非目標（3-3）、
リース時刻の解釈（2-1）、実行経路の非対称（2-4）、外部検証の受理規則（1-4）、副作用の非強制（1-5）、
重複防衛の一次＝既存バックログ→プランナー／機械の硬抑止＝完全一致のみ（#19・S6 判断の再確認）。

## 非目標（この計画でやらないこと）

やらない理由まで書く。後から「なぜ足さなかったか」を再議論しないため。

- **証跡の再実行検算** — done のたびに verifier のコマンドを再実行して突き合わせる案。コストが二重で、
  環境差で再実行が落ちると偽陰性になる。記録の無い証跡を認めないフェイルクローズで足りる。
- **外部検証ノードの allowlist** — 「誰が確かめたか」で done を分岐させると、ワーカーノードを増やすほど
  名義管理が運用の重荷になる（C6 とも逆向き）。
- **verifier のサンドボックス／許可コマンド列挙** — 標準ライブラリだけで動く（不変条件 4）と
  Windows / WSL 混在フリートという前提から外れる。事後検知で担保する。
- **断片合成のパッケージ化** — 33 断片の再構成は本計画の 10 倍の規模で、レビューの他 23 件を止める。
  観測可能性の穴は構造テストで塞ぐ。
- **GitLab 以外のフォージ実装**、**イベント台帳（backlog-ledger 相当）の再導入**、
  **予算のノード横断合算**、**分解の自動起動** — いずれも既存判断で却下済み。本計画で復活させない。
- **意図の同一性を機械スコアで閉じる**（#19 の bigram / embedding / 生成後 LLM 裁定）—
  タイトル一致性の機械判定は偽陽性と偽陰性を避けられない。正は既存バックログをプランナーへ
  渡す一次防衛（上記「#19 再整理」）。bigram はトークン化の衛生として契機待ちに残すだけ。
- **既存バックログの多ターン開示・チャンク分割分解**（#19 の B3/B4）—
  呼び出し回数とマージ複雑性を増やす。コンテキスト圧は 1 ショットの密度段階（B1: 全件索引＋
  高リスクのみ summary）で受ける。
