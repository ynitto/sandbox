# agent-project 設計修正計画 — レビュー 24 件への対応

> 日付: 2026-07-29
> 入力: [`agent-project-design-review.md`](../designs/agent-project-design-review.md)（指摘 24 件＋小項目 6 件）
> 対象: [`agent-project-design.md`](../designs/agent-project-design.md)
> 位置づけ: 本書は**修正計画**。確定した内容は agent-project 設計書へ反映し、本書は「なぜそう直したか」の
> 履歴として残す。設計判断の正典は常に設計書側。
> 効く柱・原則: **柱 2 / C5・C3・C7** — done の意味を層をまたいで一本化し（C5）、人へ送る条件と止まる条件を
> 明示し（C3）、判断根拠と書き手を増やさずに閉じる（C7）。

## この計画の考え方

レビューは 24 件あるが、24 通りの機構を足すと設計書が壊れる。指摘の大半は
「不変条件が層をまたぐと曖昧になる」「時刻と状態のどちらが正か書いていない」「単位が書いていない」
「投影が片方向で止まっている」の 4 つに帰着する。そこで**梁を 4 本立てて大半をそこで受け**、
残りは 1 行の契約で閉じる。

**先に決める「増やさないもの」**（この制約が計画全体の単純さを担保する）:

- 新しい常駐プロセス・新しいバス・新しいイベント台帳を作らない
- 新しい状態ファイル形式を増やさない（既存の `backlog/` `needs/` `verifications/` `project.json` で足りる範囲に収める）
- 新しい語彙を増やさない（「検証の強さ」「信頼レベル」のような等級を導入しない）
- 判定の 2 実装を作らない。既存の 1 実装へ経路を寄せる方向にだけ直す

---

## 梁 1 — done の根拠は 2 表現だけ。それを層をまたいで同一にする

**契約**: done を確定できる根拠は 2 表現に限る。**(a) 決定的コマンドの終了コード 0**、
**(b) 受入基準 × 証跡の全 pass**。この 2 表現が、タスク層・charter の `## acceptance`・
他ノードへの検証委譲の**3 経路すべてで同一**であり、経路によって強さが変わらない。
人のプロジェクト done は「この方向でよいか」の価値判断であって品質保証ではない（C5）——
人が細部を見落としても done の意味は壊れない、という関係を設計書に明示する。

| # | 直すこと | 閉じる指摘 |
|---|---|---|
| 1-1 | 3 層の関係を明文化する。タスク verify ／ charter acceptance ／ 人のプロジェクト done を「同じ 2 表現＋価値判断」として並べ、人の検収が機械検証の代替でないことを書く | #1 |
| 1-2 | `## acceptance` を二表現へ。各行を「決定的コマンド行」と「自然文基準行」に分け、自然文行は verifier が証跡付きで判定する。**自然文→コマンドの一発合成は廃止**（既存の残課題を、別設計に回さずここで閉じる） | #1 #3 #24 |
| 1-3 | **証跡チェックを 1 実装にして全経路へ課す。** 決定的チェックは 3 つだけ: ① 参照ファイルが検証対象の成果コミットに実在する ② 各 pass に「実行したコマンドとその終了コード」が対応づく（記録の無い出力は証跡と認めない） ③ 差分基準を満たす。内蔵 verifier・`verifier_skill`・他ノードの `external.json` の**すべて**がこの同じチェックを通り、通らない pass は機械的に fail | #2 #3 #4 #15 |
| 1-4 | 外部検証の受理は「**誰が**確かめたか」では分岐させない（現行判断を維持）。代わりに「**何を出したか**」で分岐する＝ 1-3 のチェックを外部判定にも同じだけ課す。板のノード契約版が合わない判定は fail | #4 |
| 1-5 | `verify_side_effects` の禁止は**強制しないと明記**する（非目標）。担保は事後検知——実行コマンドの記録（1-3 ②）が必須なので、逸脱は検証レポートを読めば追える。サンドボックスも許可コマンド列挙も持たない | #15 |
| 1-6 | 差分基準の逃げ道を、基準を消さずに作る。タスクに `- no_diff: <理由>` があると `DIFF_CRITERION` は**「宣言した成果物ファイルの実在と、その内容の参照」へ差し替わる**（消えない）。調査・方針・ドキュメント・「変更しないこと」系はここに載る | #16 |

**なぜこれで足りるか**: レビューの「証跡の真正性」は、LLM に真正性を証明させる方向では閉じない。
閉じるのは「**記録の無いものを証跡と認めない**」というフェイルクローズだけで、これは既存の
「証跡の無い pass は fail」の延長線上にある。証跡の再実行検算は行わない（下記 非目標）。

## 梁 2 — 正は状態。時刻は締切のヒントにすぎない

**契約**: リースの時刻は「そろそろ諦めてよい」という**ヒント**で、実行権の正本は remote の
`owner/token/generation` を CAS で確認できたときだけ与えられる。時計がずれても、奪取側は
CAS を通るまで実行権を持たない。復旧手順も新設しない——正は常に `remote の backlog + archive`
であり、その他は投影として毎パスの整合点が作り直す（判断 5-b の形をそのまま広げる）。

| # | 直すこと | 閉じる指摘 |
|---|---|---|
| 2-1 | リース失効の解釈を明文化。「失効＝奪取可」ではなく「失効＝奪取を**試みてよい**」。奪取は CAS 経由でしか成立しないので、skew は二重実行にならず、早期奪取は push 失敗として現れる | #6 |
| 2-2 | **settle は 1 コミット 1 原子**にする。archive・納品書・needs・verifications・claim 解放は 1 コミットにまとめ、push が通った時点で確定。途中死は「未 push のコミットがローカルに 1 つある」状態に落ち、次パスは remote を正として再突合する | #8 |
| 2-3 | クラッシュ復旧の契約を「投影の再計算」と明記する。専用のリカバリ手順・ジャーナル巻き戻しは持たない | #8 #11 |
| 2-4 | 実行経路は二系統ではないことを明文化。`board` 委譲は **claim を握ったまま実行先が board になるだけ**（`offloaded`）で、fencing は local と同一。**検証だけの委譲は成果を動かさないので claim を取らない**（受理点は `external.json`）——この非対称が「同一タスクが両方の意味で実行中」に見える窓の正体 | #10 #11 |
| 2-5 | `claims/` は同期しないホスト局所キャッシュで、正本ではないと明記。孤児 claim は投影の掃除対象（既存の孤児掃除に載る） | #11 |
| 2-6 | `unknown` 隔離を「必ず止まる」（不変条件 2）に載せる。隔離件数に上限を持ち、超えたそのノードは **report へ降格**して新規 claim を止める（既存 throttle と同じ出口）。自動再試行は次パスの fencing 再確認 1 回だけで、それ以上は人待ち | #7 |

## 梁 3 — 予算はノード別、進行はプロジェクト共有

**契約**: 財布に紐づく上限（トークン・コスト・実時間）は**ノード別**で、host.yaml の `budget` が正。
合算しない（C1: クレジットは個人のもの）。進行に紐づく上限（改善サイクル数・停滞の連続回数・
acceptance の PASS 数）は**プロジェクト共有**で、`project.json` が正。

| # | 直すこと | 閉じる指摘 |
|---|---|---|
| 3-1 | 上記の単位を設計書に書く。二重計上は「別の財布を別に数えている」ので正しい挙動 | #9 |
| 3-2 | throttle はノード局所の降格であり、他ノードは走り続ける——これを意図した挙動として明記する | #9 |
| 3-3 | **目標駆動モードでは人が律速であることを非目標へ書く。** 無人で回るのは backlog 消化（正準ループ）で、分解・未達 acceptance の扱い・プロジェクト done は人。目標節の「backlog が空か予算まで無人運転」はタスク層の目標だと限定する | #12 |

## 梁 4 — 投影を一段広げる（削除・learn・保持）

| # | 直すこと | 閉じる指摘 |
|---|---|---|
| 4-1 | **削除も後続を再審査へ戻す。** 物理削除時、`after` に削除 id を持つ後続は `proposed`（人が見る状態）へ落とす。墓標も決定記録も増やさない（削除の「記録を残さない」性格は維持）。`unmet_deps` の読み方（無い id ＝満たし）は変えない——前提を失った後続は実行可能なまま放置されず、必ず人の目を通る。判断 5-c の「後続を再審査へ戻さない」だけを撤回する | #5 ／ 小項目「物理削除の窓」 |
| 4-2 | learn の再適用に**スコープと失効**を持たせる。`- learn:` にスコープ（repo / charter / 全体）を付け、連続不発が閾値に達した learn と人が無効化した learn は適用しない。無効化は決定記録で行う（新しいファイルを作らない）。learn の適用は決定的側に留め、LLM の裁定ゲートは「人が要るか」だけを判断する現行の役割分担を維持 | #14 |
| 4-3 | 状態リポジトリの**保持契約**を書く。`verifications/` は最新 rev ＋直近 N、`journal.md` と `run-log.jsonl` は期間ローテーション、`verify-recipes/` は最終使用日で失効、`archive/` は保持（納品の記録なので消さない）。`gc` は保持契約の実行者であり、契約は設計書側に置く | #22 |

## 変更する既存の設計判断（明示）

この計画で**撤回・改訂する**のは次の 2 点だけ。他はすべて既存判断の明文化か、その延長。

1. **判断 5-c の一部撤回** — 「削除は後続を再審査（proposed）へ戻さない」を撤回し、戻す（4-1）。
   削除が記録を残さない性格・墓標を積まない性格は維持。
2. **判断 1 末尾とプロジェクト層の改訂** — charter acceptance の「自然文からのコマンド一発合成」を廃止し、
   タスク層と同じ二表現へ寄せる（1-2）。「別設計の課題として残す」という現行の逃げを閉じる。

明文化にとどまる（判断は変えない）もの: 予算の単位（梁 3）、目標駆動モードの非目標（3-3）、
リース時刻の解釈（2-1）、実行経路の非対称（2-4）、外部検証の受理規則（1-4）、副作用の非強制（1-5）。

## 非目標（この計画でやらないこと）

やらない理由まで書く。後から「なぜ足さなかったか」を再議論しないため。

- **証跡の再実行検算** — done のたびに verifier のコマンドを再実行して突き合わせる案。コストが二重で、
  環境差で再実行が落ちると偽陰性になる。記録の無い証跡を認めないフェイルクローズで足りる。
- **外部検証ノードの allowlist** — 「誰が確かめたか」で done を分岐させると、ワーカーノードを増やすほど
  名義管理が運用の重荷になる（C6 とも逆向き）。
- **verifier のサンドボックス／許可コマンド列挙** — 標準ライブラリだけで動く（不変条件 4）と
  Windows / WSL 混在フリートという前提から外れる。事後検知で担保する。
- **断片合成のパッケージ化** — 33 断片の再構成は本計画の 10 倍の規模で、レビューの他 23 件を止める。
  観測可能性の穴は構造テストで塞ぐ。
- **GitLab 以外のフォージ実装**、**イベント台帳（backlog-ledger 相当）の再導入**、
  **予算のノード横断合算**、**分解の自動起動** — いずれも既存判断で却下済み。本計画で復活させない。
