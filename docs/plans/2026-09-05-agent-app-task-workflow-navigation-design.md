# agent-app タスク・ワークフローナビゲーション再設計

> 作成: 2026-09-05  
> 対象: `tools/agent-app`  
> 更新対象の設計: `2026-09-05-agent-app-simple-navigation-ux-design.md`、`2026-09-05-agent-app-statemachine-integration-design.md`

## 背景

agent-app の現在の主要メニューは `会話 / 自動化` だが、自動化画面の内部にもう一つのヘッダー、
フォルダ一覧、`実行 / ワークフロー / AIワークフロー` タブがある。そのため、次の問題が生じている。

- `新しい会話` が主要メニューより上に単独で置かれ、どの情報階層に属する操作か分かりにくい。
- agent-app のリポジトリ一覧と自動化画面のフォルダ一覧が重複している。
- `自動化` が、タスク定義、手動実行、定期実行、複数 AI のワークフローを一括りにしている。
- `ワークフロー` と `AIワークフロー` が同じ階層にあり、違いを名前だけでは判断できない。
- iframe 内に独立アプリ相当のナビゲーションがあり、アプリ全体の現在地が二重になる。

今回、ステートマシンとして実装されている現在の `実行 / ワークフロー` は「タスク」と定義する。
現在の `AIワークフロー` は、主要領域の「ワークフロー」へ昇格する。定期実行は独立した主要領域にはせず、
タスク詳細の属性として扱う。

## 一般的なエージェントアプリから得た原則

- GitHub Copilot app は My work、Automations、Sessions、Chats などをサイドバーの主要領域として分け、
  Sessions の作成操作を一覧見出しの近くに置き、セッションをプロジェクト単位で整理する。
  - https://docs.github.com/en/copilot/get-started/quickstart-copilot-app
- Codex app はスレッドをプロジェクト配下に整理し、会話、進捗、差分レビューを選択中タスクへ集約する。
  Automations の結果も、独立した編集アプリではなく確認可能な仕事として戻す。
  - https://openai.com/index/introducing-the-codex-app/
- Cursor は Background Agents を専用サイドバーの一覧と選択中エージェントの詳細に分け、状態確認、追加指示、
  引き継ぎを一つの詳細画面で行う。
  - https://docs.cursor.com/background-agent
- Claude Cowork は会話とタスクを同じ入力地点から開始し、Scheduled tasks は左サイドバーから管理する。
  - https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-claude-cowork

共通する原則は、主要ナビゲーションを仕事の種類で分け、対象の作成操作を対象一覧の近くへ置き、
選択中の仕事に関する進捗・成果・履歴を中央へ集約することである。agent-app では機能数がまだ少ないため、
定期実行を独立領域にせず、タスクの詳細へ収める。

## 目的

- 主要領域を `会話 / タスク / ワークフロー` の三つだけにする。
- 利用者が名前だけで各領域の対象と違いを推測できるようにする。
- リポジトリ選択と対象作成の位置を、すべての領域で統一する。
- アプリ内に別アプリが埋め込まれたような二重ナビゲーションを解消する。
- 定期実行を必要な利用者だけがタスク詳細で設定できるようにする。
- 既存の定義、実行履歴、スケジュール、IPC 契約を失わず、情報構造と表示だけを再編する。

## 用語と領域の境界

| 領域 | 対象 | 主な用途 | 現在の実装 |
|---|---|---|---|
| 会話 | 対話セッション | その場の依頼、追加指示、ファイル・差分確認 | agent-app の `work` 領域 |
| タスク | 保存されたステートマシン | 定型処理の手動実行、手順編集、定期実行、履歴確認 | statemachine-maker の `実行 / ワークフロー` |
| ワークフロー | 複数 AI の工程と依存関係 | 分担、並列実行、人の確認、成果追跡 | statemachine-maker の `AIワークフロー` |

ユーザー向けには `自動化` と `AIワークフロー` を主要領域名として使わない。`自動化` は機能をまとめる
抽象語であり、対象物を示さないためである。定期実行には具体的な `定期実行` という名前を使う。

タスク内部では、主要領域の「ワークフロー」との衝突を避けるため、現在の `ワークフロー` を `手順` と呼ぶ。

| 現在の表示 | 新しい表示 |
|---|---|
| 作業 | 会話 |
| 自動化 | 廃止 |
| 実行 | タスクの概要 |
| ワークフロー | タスクの手順 |
| AIワークフロー | ワークフロー |
| フォルダ | リポジトリ |

## 採用する情報構造

### アプリケーションシェル

左側を幅 264px 前後の単一サイドバーとし、上から次の順に配置する。

1. アプリ名
2. 主要メニュー `会話 / タスク / ワークフロー`
3. 共通のリポジトリ選択
4. 選択中領域の一覧見出しと作成操作
5. 選択中領域の対象一覧
6. 設定

```text
┌────────────────────┬──────────────────────────────────────────┐
│ Agent App          │ 選択中の対象                             │
│                    │                                          │
│  会話              │                                          │
│  タスク            │             詳細                         │
│  ワークフロー      │                                          │
│ ────────────────── │                                          │
│ sandbox         ▾  │                                          │
│                    │                                          │
│ タスク          ＋ │                                          │
│  リリース確認      │                                          │
│  コードレビュー    │                                          │
│                    │                                          │
│ 設定               │                                          │
└────────────────────┴──────────────────────────────────────────┘
```

主要メニューは文字付きの縦メニューとする。アイコンは識別補助にだけ使い、文字ラベルを省略しない。
選択中の項目は背景、文字色、`aria-current="page"` で示す。

### 共通リポジトリ選択

リポジトリは三領域の共通文脈として、主要メニューの直下に一つだけ置く。ドロップダウンには登録済み
リポジトリを表示し、隣の補助メニューから追加・管理を行う。

- 領域を切り替えても選択中リポジトリは変えない。
- リポジトリを切り替えたら、領域ごとに最後に選択した対象を復元する。
- 対象が存在しなければ、その領域の空状態を表示する。
- statemachine-maker 由来の独立したフォルダペインは表示しない。
- UI 表示は `フォルダ` ではなく `リポジトリ` に統一する。

### 文脈に応じた作成操作

現在の大きな `新しい会話` ボタンは削除する。作成操作は、選択中領域の一覧見出しの右側へ同じ形式で置く。

```text
会話              ＋
タスク            ＋
ワークフロー      ＋
```

ボタンには `aria-label="新しい会話"` など完全な名前を持たせ、ツールチップでも同じ意味を表示する。
会話が一件もない場合は中央の入力欄へ依頼を書いて送信するだけで、新しい会話を作成できる。

## 会話領域

既存の会話体験を維持し、サイドバーの配置だけを揃える。

- 一覧: 選択中リポジトリの最近の会話。実行中、確認待ち、失敗を文言またはアイコンと補助テキストで示す。
- 中央: 会話名、状態、`会話 / ファイル`、変更確認、その他操作、メッセージ、入力欄。
- 作成: 一覧見出しの `＋`、または空状態の入力欄から直接開始。
- 実行条件: 引き続き入力欄付近の段階表示とする。
- 変更と端末: 選択中会話の詳細操作であり、主要メニューへ昇格させない。

## タスク領域

タスク一覧には、ステートマシン定義を一件ずつ表示する。行には名前、短い状態、次回予定を表示する。

```text
タスク                         ＋
  リリース確認       月曜 09:00
  コードレビュー     未設定
  月次レポート       9/30 18:00
```

タスクを選ぶと中央に次を表示する。

```text
リリース確認                              [実行] [その他]
sandbox

  概要    手順    履歴

状態              実行可能
次回の実行        月曜 09:00
前回の結果        完了

実行時の入力
[ 対象ブランチ                                      ]

定期実行                                      [変更]
毎週月曜日 09:00 ・ 有効
```

### 概要

名前、説明、現在の実行状態、実行時の入力、主操作 `実行`、定期実行、直近の結果を表示する。
通常利用で必要な内容をここに集約し、実行後も同じ画面で進捗と結果へ切り替える。

定期実行は概要内の一セクションとする。未設定時は `定期実行は設定されていません` と `設定` を表示する。
設定済みの場合は頻度、次回予定、有効／停止中を表示し、編集はダイアログまたはインライン展開で行う。

### 手順

現在のステートマシン編集画面を配置する。工程カードと選択中工程の設定を使い、ユーザー向けには YAML、state、
transition などの内部語を通常表示しない。主操作は `保存` とし、`操作を記録`、`生成ファイル`、`構成を確認`
は補助操作へ置く。

### 履歴

手動実行と定期実行を一つの時系列に並べる。各行には開始日時、起動方法、結果、所要時間を表示する。
ログは行を選択したときだけ読み込む。履歴一覧と生ログを常時同時表示しない。

## ワークフロー領域

現在の `AIワークフロー` を主要領域へ昇格し、表示名を `ワークフロー` とする。説明文や空状態で、複数 AI の
分担、依存関係、人の確認を扱うことを伝える。

サイドバーには保存済みワークフローを表示し、実行履歴は選択中ワークフローの詳細へ置く。保存済み定義と
実行履歴を同じ一覧に混ぜない。

```text
ワークフロー                            ＋
  並列コードレビュー      実行中
  リリース準備            要確認
  調査と提案              未実行
```

中央は次の構造とする。

- 概要: 目的、工程の要約、必要な入力、主操作 `実行`、直近の状態。
- 編集: 工程、依存関係、AI、モデル、人の確認を編集する。
- 実行履歴: 実行単位の進捗、確認要求、工程別成果、最終成果、ログ。

ワークフローの実行中または確認待ちには、サイドバーの一覧と詳細の両方で状態を示す。色だけに依存せず、
`実行中`、`要確認`、`失敗`、`完了` の文言を表示する。

## 表示状態と遷移

主要領域は次の独立した状態として保持する。

```text
area: conversation | tasks | workflows
repo: selected repository
conversationView: chat | files
taskView: overview | steps | history
workflowView: overview | editor | runs
```

旧設定の `work` は `conversation`、`automation` は `tasks` として読み替える。保存済みの最後の領域が
`automation` でも、更新後に空画面へ遷移させない。

領域ごと、リポジトリごとに最後の対象を復元する。タスクからワークフローへ切り替えた際に、タスクの選択や
編集途中のスクロール位置をワークフロー側へ流用しない。

## 空状態とエラー

| 状態 | 中央の表示 | 主な操作 |
|---|---|---|
| リポジトリなし | 最初にリポジトリを追加する必要を一文で説明 | `リポジトリを追加` |
| 会話なし | 大きな依頼入力欄 | 依頼を送信 |
| タスクなし | 定型処理を保存して繰り返し実行できることを説明 | `タスクを作成` |
| ワークフローなし | 複数 AI へ工程を分けられることを説明 | `ワークフローを作成` |
| 実行環境不足 | 原因と不足している実行環境 | `設定を確認` |
| 実行中 | 現在の工程と進捗 | `停止` |
| 要確認 | 質問と判断に必要な要約 | 回答または承認 |
| 失敗 | 短い原因と次の操作 | `再実行`、`ログを見る` |

エラーは操作箇所の近くに表示し、コマンド、終了コード、生ログは詳細表示へ置く。

## レスポンシブ

- 1200px 以上: サイドバー 264px、中央詳細、必要なときだけ右側ドロワー。
- 760〜1199px: サイドバー 232px。タスクの手順編集は工程一覧と設定を一画面ずつ切り替える。
- 759px 以下: サイドバーをオーバーレイ化し、中央を一列にする。領域選択後はサイドバーを閉じる。
- すべての幅でページ全体の横スクロールを禁止する。コード、差分、ログだけ個別に横スクロールを許可する。
- 主要操作のタッチ領域は 44px 以上、一覧の行は最低 40px とする。

## 視覚・アクセシビリティ方針

- 現在の固定ニュートラル配色と青い主操作色を維持する。
- 青は現在地、主操作、操作可能なリンクに限定する。
- 選択、実行状態、失敗を色だけで表さない。
- 罫線の多重化を避け、背景差と余白で主要領域、一覧、詳細を分ける。
- サイドバー内に別のヘッダー、タブバー、フォルダペインを入れ子にしない。
- フォーカスリングを常に表示でき、Tab 順を視覚順と一致させる。
- `prefers-reduced-motion` を尊重し、進捗以外の装飾的なアニメーションを追加しない。

## 実装方針

最終形では agent-app がアプリケーションシェル、主要メニュー、リポジトリ選択、文脈一覧を所有する。
statemachine-maker の iframe が持つヘッダー、フォルダ一覧、ホームタブは表示しない。

ドメインロジックと保存形式は再利用し、ユーザー向けの画面だけを agent-app の三領域へ分離する。

```text
tools/agent-app/src/renderer/
├─ renderer.js       アプリシェル、会話、主要領域、共通リポジトリ
├─ tasks.js          タスク一覧、概要、手順、履歴、定期実行
├─ workflows.js      ワークフロー一覧、編集、実行状況、履歴
└─ styles.css        共通レイアウトと状態表現
```

既存 IPC の `automation.*` という内部名は、初回の UI 再編では維持してよい。表示名と内部 API 名を同時に
変更すると回帰範囲が広がるためである。UI が安定した後、必要なら別の変更として `tasks.*` と `workflows.*`
へ分割する。

## 実装計画

1. 既存表示名、DOM、保存状態の移行テストを追加する。
2. `area` を `conversation | tasks | workflows` へ拡張し、旧値を読み替える。
3. 大きな `新しい会話` を一覧見出しの作成操作へ移し、三領域で位置と挙動を統一する。
4. 共通リポジトリ選択をサイドバーへ置き、iframe 内のフォルダ一覧を撤去する。
5. 現在の `実行 / ワークフロー` をタスクの `概要 / 手順 / 履歴` へ再構成する。
6. 現在の `AIワークフロー` を主要領域の `ワークフロー` へ昇格する。
7. 定期実行をタスク概要内へ移し、一覧に次回予定と状態を表示する。
8. iframe の独立ヘッダーとホームタブを除去し、agent-app のシェルに統合する。
9. 375px、768px、1024px、1440px で表示とキーボード操作を検証する。
10. Electron smoke test で会話、タスク、ワークフローの移動、作成、実行、復元を検証する。

## テスト方針

- DOM: 三つの主要メニュー、`aria-current`、共通リポジトリ選択、文脈別作成操作。
- 移行: 保存済み `work / automation` から新しい領域へ安全に復元できる。
- 会話: 作成、送信、ファイル、変更、端末、worktree の既存回帰。
- タスク: 一覧、概要、手順編集、保存、手動実行、定期実行、履歴、ログ。
- ワークフロー: 一覧、作成、編集、実行、確認回答、停止、成果、履歴。
- アクセシビリティ: Tab、Enter、Space、Escape、フォーカス復帰、色以外の状態表示。
- レスポンシブ: サイドバー、長い名前、空状態、実行中、確認待ち、ログ表示。
- 実機: iframe 由来の二重ヘッダー、フォルダペイン、旧ホームタブが表示されないことを目視確認する。

## 検討した案

| アプローチ | 実装コスト | リスク | 保守性 | 拡張性 | 学習コスト | 推奨度 |
|---|---|---|---|---|---|---|
| A. 三領域＋共通リポジトリ選択 | 中 | 低 | 高 | 高 | 低 | ★★★ |
| B. リポジトリごとに全対象をグループ表示 | 中 | 中 | 中 | 高 | 中 | ★★☆ |
| C. アイコンレール＋領域別の第2サイドバー | 高 | 中 | 中 | 高 | 高 | ★☆☆ |

A は現在の機能数に対して最も単純で、作成操作、リポジトリ、対象一覧の位置を固定できる。B は多数の
リポジトリを同時監視する場合に有効だが、一覧が長くなり、領域とリポジトリの二軸が混ざる。C は主要領域が
大幅に増えた場合に有効だが、現時点では横幅とアイコン学習を増やす。

## 既存スキルとの関係

- `ui-designer`: 情報階層、作成操作の位置、レスポンシブ、アクセシビリティを具体化する。
- `webapp-testing`: 実装後の Electron 実機、複数幅、キーボード、コンソールエラーを検証する。
- `code-simplifier`: iframe 解消後に増える表示状態とイベント処理を整理する。
- `ltm-use`: 今回の用語と主要ナビゲーションの決定を、次回の機能追加時に再利用する。

既存スキルが agent-app 固有の情報構造を代替することはない。

## 非目標

- ステートマシン、agent-flow、agent-loop の実行契約変更
- 保存済みタスク、ワークフロー、履歴、スケジュールの形式変更
- 独立した自動化ダッシュボード、カレンダー、横断分析
- 通知、クラウド同期、GitHub 連携の追加
- アイコンだけの折りたたみナビゲーション
- テーマ、配色、レイアウトのユーザーカスタマイズ
