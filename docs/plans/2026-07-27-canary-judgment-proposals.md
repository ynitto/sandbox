## 1. §1.1 ランブック記録記入の段取り（人の作業を最小にする提案）

**現状**: `docs/guides/single-resident-canary.md` の記録欄はすべて空欄——
C1〜C10 の各「記録」行、§4 日次観測の 7 日 × 3 台の表、§5 欠陥記録、§6 終了判定の
チェックボックス 5 つ。

**提案する段取り**（メモが完全でない前提で、創作を避けつつ埋め切る）:

1. **メモから写せるものを先に写す**——C1〜C10 の「記録」行と §5 の欠陥記録。
   メモに無い項目は**空欄のまま残さず「未記録」と書く**。空欄は「未実施」と
   区別できないが、「未記録」は再実施の対象として数えられる。
2. **今からでも撮れるものは今撮る**——§4 の日次観測は過去に遡れないが、
   `agent-project status --json` と `agent-project doctor --json` の**現在値**は
   終了判定（二重実行 0 / doctor 指摘 0）の傍証になる。撮った日付を添えて記録する。
3. **「未記録」のうち再実施が安いものは再実施する**——C1（controller 引継ぎ）・
   C3（予定 drain）・C5（watchdog）・C7（スキル併走）・C8（板委譲往復）は
   通常運用の範囲で再現できる。C2（全台停止）・C4（突然死）・C9（VM 復帰）は
   次のフリート更新の停止ウィンドウに乗せると追加の停止が要らない（§6 判断 6 の
   確認と同じ回で済む）。
4. **§5 が空のままなら「ガイド外の操作は無かった」と 1 行書く**——ランブック自身が
   「ここが空のまま終わったらガイドが完成した証拠」と定義しているので、
   空欄と「空だった」の区別を記録に残すことに意味がある。

**根拠**: C1（成果と判断はチームのもの）。メモに無いものを埋めると記録でなく創作に
なる、という棚卸しの判断は維持しつつ、「未記録」を明示すれば再実施の判断材料になる。

## 2. §1.2 の 6 判断 — 材料と推奨

### 判断 1: host.yaml 検査 W5/W6/W7 の E 昇格・E6

**現状（コードで確認）**:

- 起動時は `resident_cli.host_config_findings()` が全所見を **warn**（起動は止めない）。
  docstring に「E への昇格は canary 明けの判断に回す」と明記。
- 所見はどれも**救済つき**——スカラは 1 要素へ畳む（W6-a）、型違い・未知キーは
  無視して**行き先を名指しで案内**（W5 系・W7）。誤動作ではなく縮退で済む設計。
- doctor は同じ純関数を呼ぶ（§2c-3 で配線済み・所見ごとに題が分かれ内訳が残る）。
- **E6（`projects[].config`）だけ強度が場所で割れている**: doctor は
  「E6: projects[].config は廃止」を **critical** で出す（`doctor.py`）のに、
  起動時は W7 の警告（誘導文つき）どまり。S1 §3.3 の宣言は E（エラー）。

**材料の取り方**: 全ノードで

```bash
agent-project doctor --json | python3 -c 'import json,sys; \
  fs=[f for f in json.load(sys.stdin)["findings"] if f["category"]=="config"]; \
  [print(f["severity"], f["title"]) for f in fs]'
```

警告の件数・内訳がそのまま判断材料（棚卸し §1.2 判断 1 の注記どおり）。

**提案**:

- **W5/W6/W7 の E 昇格は見送り（warn のまま閉じる）**。再訪条件は「同じ綴りの警告を
  直しても再発する実測が出たら」に置き直す。
- **E6 は条件付きで S1 §3.3 の宣言（E）へ戻す**: 全ノードの doctor で E6 所見が
  0 件なら昇格する（誰も書いていないなら誰も止まらない）。1 件でもあれば、
  該当 host.yaml を直してから昇格する。

**根拠**: W 系は救済＋案内＋doctor 集計で「設定したのに効かないことに気付けない」
（S1 の設計動機）は既に塞がっており、E にする追加の利得は fail-fast だけ。一方で
E は綴り 1 つでノードが起動しない＝フリートで**無言の不在**を作り、人の介入が必須に
なる（柱 2 と逆行）。E6 だけは「同じ判定の結果が場所（doctor / 起動時）で食い違う」
C7 の残り火なので、強度を揃える方向＝宣言どおり E へ寄せるのが筋。逆方向
（doctor を warn へ下げる）は S1 §3.3 の宣言との矛盾を作るので採らない。

### 判断 2: `max_concurrent` の意味変更（0 = 無制限）の影響

**現状（コードで確認）**: `agentcore.board.eligible()` は `inflight >= cap` で
**黙って False を返すだけ**——「枠の自己抑制で入札を控えた回数」はどこにも
数えられていない。観測は板の後追い（公示が open のまま残る × そのとき
`nodes/<id>.json` の inflight が cap に達していた）でしか成立しない。

**提案**: **現状維持で閉じる**（既定 4・`0` = 無制限の契約は正しく、スキーマとも
一致済み）。再訪条件は「板の仕事が滞留し、原因が枠の自己抑制だと特定される申告」。
控えた回数のカウンタ追加は新機能なので、その申告が出るまで足さない（契機待ちの
規律のまま）。

**根拠**: 材料（控えた回数）が実装上存在しない以上、この判断はいま「決めない」のが
正しい。カウンタを先回りで足すのは C1（先回りしない）に反し、申告が出れば
`engine/status.json` の board ブロックへ足す場所も自明。

### 判断 3: `workloads` を誰も宣言しない状態が続くか

**材料の取り方**: 板リポジトリの `nodes/*.json` を見る:

```bash
git -C <板のワークツリー> pull -q && \
python3 -c 'import json,glob; \
  [print(p, json.load(open(p)).get("workloads")) for p in glob.glob("nodes/*.json")]'
```

**提案**: 全ノードが `None`（未宣言）なら計画どおり**「契約に残す・運用の口は
増やさない」で閉じる**（doctor の workloads info は §4 の契機待ちのまま）。

**根拠**: 未宣言 = 「制限しない」は板の語彙どおりで、宣言の需要が観測されていない
機能に口を足すのは「どちらの柱にも効かない機能は足さない」（正典 §3）に反する。

### 判断 4: flow-planner 粒度ゲートの再評価

**現状**: [粒度設計](2026-07-25-flow-planner-granularity-design.md) Decision Record の
再評価条件は「work ノードの成功率や手戻りが改善しない／スコープ逸脱が多発する」。

**材料の取り方**: ①run の成否と heal 世代——dashboard のアーカイブ
（`flow-archive/`）と `agent-flow status`（failed / heal の回数）②手戻り——
needs の差し戻し票の頻度 ③スコープ逸脱——ゲートの reject ログ。

**提案**: 再評価条件が成立した**実測が無ければ案 A 維持で閉じる**。canary メモに
該当の観測が無い場合も「未成立」として閉じ、次に条件が成立したとき Decision Record
経由で再開する（判断を宙に浮かせない）。

**根拠**: 再評価条件は Decision Record に既に明文化されており、条件不成立の間に
判断を開いたままにする理由が無い（C4: 1 回で決めさせる）。

### 判断 5: 板の `local` publish 廃止後の速度

**提案**: **申告ベースで閉じる**。「板経由の仕事が遅くなった」という申告が canary 中に
無かったなら、それが答え（P2-2 の廃止は S3 の動機——ホスト固有の絶対パスを
配らない——の側が正）。申告が出たときの調べ方だけ残す: 請負ノードで該当リポジトリの
解決経路を確認し（host.yaml の `repos[].local` 宣言があるか、無ければミラー取得）、
遅いのが clone なら `repos[].local` の宣言を足すのが正規の直し方。

### 判断 6: graceful 停止の板残留時間 → **「away 宣言が効いているか」の確認へ**

**現状**: 棚卸し §1.2-6 のとおり、4 ステップ注入は実装済み（`BoardRepo.announce_away` /
`_board_away_announcer`）。判断は「残留時間を実測して直すか」から「新しい停止経路が
効いているかの確認」に変わっている。

**提案（確認手順）**: 次のフリート更新の停止ウィンドウで 1 回だけ確認する:

1. 委譲を落札・実行中のノードで graceful 停止（普段の停止手順どおり）
2. 板リポジトリで `status/<who>.json` が `away` になっていることを確認
3. 依頼側が lease 失効を**待たずに**再入札へ回ること（依頼側ログ）を確認

期待どおりなら判断 6 は閉じる。away が出ない場合だけ欠陥として起票する。

## 3. 旧版ノードの入札拒否の実機確認 — 今回の更新では自然には起きない（要注意）

**深掘りで見つかった事実**: `agentcore.board.CONTRACT_VERSION` は **1 のまま**で、
R2b を含む今回の変更はどれも版を上げていない（棚卸し §0c の契約差分は全部
「混在しても壊れない」性質で、上げる理由が無いのは正しい）。`contract_compatible` は
`declared == required` の完全一致判定なので、**1 台だけ旧版のまま残しても、その旧版は
version 1 を宣言したまま正しく入札する**——「入札拒否」は観測できない。

**提案**: 2 段で確かめる。

- **(a) 今回の更新で機構だけ確認する（推奨・すぐできる）**: 合成公示で fail-close を
  見る。`requires.contract_version: 2` を持つ公示を板に置き、**全ノードが入札しない**
  こと（誤動作でなく不参加）と、`requires` の無い公示・`contract_version: 1` の公示には
  従来どおり入札することを確認する。R2b でワーカーノードが実際に入札するように
  なったので、この確認はいま初めて端から端まで成立する。
- **(b) 本番シナリオは最初の実バンプで確認する**: 次に `CONTRACT_VERSION` を上げる
  更新のとき、1 台だけ旧版で残して「新しい公示に旧版が入札しない」を観測する。

**ランブック C10 の注記の扱い**: (a) が通ったら「板の請負 tick が未実装なので
確かめられない」という注記は**外せる**（その前提は R2b で消えた）。ただし外すときに
「実バンプ時の混在観測は未実施」と 1 行残し、(b) で完全に消す。
