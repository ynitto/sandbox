# agent-app に Opik 相当の機能（追跡・評価・評価セット）を入れる

作成: 2026-09-19。状態: **提案（画面の ASCII 承認待ち）**。CLAUDE.md の規則により、画面は承認を
得るまで実装しない。裏側（保存形・申告・IPC）も、どの段まで入れるかを §3 で決めてから着手する。

## 0. TL;DR

OSS の Opik（Comet）は LLM アプリの **追跡（trace / span）・評価（feedback score・LLM-as-judge）・
評価セットと実験（dataset / experiment）・プロンプト管理・ダッシュボード** を 1 つの Web UI に持つ。
agent-app には、このうち **追跡の材料と使用量の集計は既にある**。無いのは「1 回の応答を評価して
残す口」「その評価を集めて見る面」「同じ依頼を条件を変えて回し比べる面」の 3 つ。

方針は 3 つ。

1. **Opik のサーバもクライアント SDK も入れない。** 保存はいまの `sessions/<id>.json` と
   `audit-feed`、集計は agent-audit、判定は agent-herd の `judge`。数字は agent-app で作らない
   （§18 の不変条件をそのまま守る）。
2. **段を 3 つに切り、上から順に出す。** 段 1「評価を残す」は会話画面の既存の部品に 1 行足すだけで、
   新しい画面を作らない。段 2「自動で採点する」は設定の行を 1 つ足す。段 3「評価セットと実験」だけが
   新しい画面を持つ。
3. **Opik の機能を名前ごとに写さない。** プロンプト管理は「定型の依頼」「共通指示」が既にあり、
   Playground は会話そのもの。無理に別画面を作らず、対応表（§1）で「既にある」と言い切る。

読むべき人: 会話画面・設定・agent-audit の feed に手を入れる人。画面の承認だけをする人は §4 だけでよい。

## 1. Opik の機能と agent-app の対応

| Opik の機能 | 何をするか | agent-app のいま | 差分 |
|---|---|---|---|
| Trace / Span | 1 回の呼び出しを入力・出力・所要時間・トークン・入れ子の tool call で残す | 応答メッセージが `text` / `parts.thinking` / `parts.information`（command / file / skill）/ `elapsedMs` / `code` を持つ（spec §4.2〜4.3）。タスク・ワークフローは `run-history` | **ほぼある**。トークンは CLI が申告したときだけ。span の親子は無い（平坦な列） |
| Thread | 会話単位でまとめて見る | 会話そのもの。横断検索（spec「会話の横断検索」） | ある |
| Feedback score / Annotation | 人が応答に点と理由を付ける | **無い** | 段 1 |
| LLM-as-judge（Hallucination / Relevance / G-Eval …） | 別のモデルに採点させる | agent-herd `judge`（`score` 型・確率つき・確度不足は棄権）が遷移判定に配線済み（CHANGELOG 0.14.0） | **口はある**。応答の採点には未配線 → 段 2 |
| Heuristic metrics（Contains / Regex / JSON …） | 決定的な規則で採点 | 無い | 段 3 で評価セットの期待値として持つ |
| Online evaluation rules | 本番の trace を標本抽出して自動採点 | 無い | 段 2 |
| Dataset | 入力と期待値の組を集める | 無い | 段 3 |
| Experiment / Compare | 同じ dataset を条件を変えて回し、並べる | 無い（「フォーク」で 1 件ずつなら回せる） | 段 3 |
| Prompt library / versioning | プロンプトを版つきで保つ | 「定型の依頼」「共通指示」（設定）。版は git（リポジトリの `.agents/`）に任せる | **ある。作らない** |
| Playground | プロンプトとモデルを変えて試す | 会話の「直接指定」。ターンごとに CLI とモデルを変えられる | **ある。作らない** |
| Dashboard（件数・トークン・費用・スコア推移） | 集計を見る | 設定 > 利用状況（agent-audit の `--json`） | **ある**。評価の行を足す（段 1） |
| Cost tracking | 単価表でドル換算 | 無い。CLI の利用枠（%）は出す | **作らない**。契約が定額の CLI が主で単価が無い |
| Guardrails / Agent optimizer | 入出力の検閲、プロンプトの自動最適化 | 無い | 対象外 |

「作らない」を先に決めておく。Opik は API を呼ぶアプリの計測器で、agent-app は **人が CLI と会話する
場**なので、費用と Playground は形が合わない。

## 2. 目標と非目標

### 目標

- 応答 1 件に対して、その場で「良い / 悪い」と一言を残せ、それが会話の JSON と `audit-feed` の両方に
  残る（段 1）。
- 残した評価が設定 > 利用状況に「評価」として並び、AI・用途・モデルの軸で見られる（段 1）。
- 完了した応答を、人の手なしにローカルの判定 AI が採点し、確度が足りなければ**採点しない**（段 2）。
- 評価の良かった依頼を「評価セット」に集め、起動方針・AI・モデルを変えて回し、答えを並べて見られる（段 3）。

### 非目標

- Opik のサーバ（Java + ClickHouse）や Python SDK を同梱する・呼ぶこと。
- 費用（ドル）の換算。単価表を持たない。
- 集計・分布・平均を agent-app の JS で計算すること。agent-audit が出す。
- span の親子関係を CLI の出力から復元すること（adapter が出さない。平坦な列のまま）。

## 3. 段と、それぞれの中身

### 段 1: 評価を残す（人の feedback score）

**保存形。** 応答メッセージに `feedback` を 1 つ足す。

```js
{ at, role: 'assistant', text, ..., feedback: { score: 1 | 0 | -1, comment: '', at } }
```

`score` は 1（良い）/ -1（悪い）/ 0（未評価。省略と同じ）。Opik の 0〜1 の連続値にしない——画面で
押せるのは 2 つで足り、細かい段階は人が付けない。

**申告。** 評価を保存した直後に `audit.feedFeedback` で `audit-feed` に 1 行足す。行の形は既存の台帳と
同じで、`workload: feedback`、`ref` は会話 ID、`session_id` は CLI のネイティブ ID、足すのは
`feedback: { score, comment }` だけ。**元のターンの行は書き換えない**（追記専用の台帳なので）。
agent-audit 側は `usage` にスコアの集計軸（`feedback_positive` / `feedback_negative` / `feedback_rate`）を
足す。agent-app はその `--json` を並べるだけ。

**IPC。** `feedback:set { sessionId, index, score, comment }` を 1 つ。既存の `session:*` と同じ形で
`sessions/<id>.json` を原子置換する。

**画面。** §4.1。会話画面の応答の下、いまの「フォーク」と同じ行に置く。設定 > 利用状況の「使用量」の
下に「評価」の 1 行を足す（§4.2）。新しい画面は無い。

**テスト。** `feedback.test.js`（保存の正規化、台帳の行の形、申告の失敗が本体を止めない）、
`ui-consistency.test.js` に「評価のボタンは `.message-action` を使い、私物のクラスを作らない」を足す。

### 段 2: 自動で採点する（online evaluation）

**判定の口。** agent-herd `judge` を `score` 型の問い 1 つで呼ぶ。問いは固定文で、agent-app の
`src/main/evaluation.js` に置く（§18.2 と同じで、人が編集する設定にはしない）。

```text
answer_quality: { type: 'score', instructions: '依頼に対して回答が要点を押さえ、誤りが無いか', criteria: 3 段 }
```

**契機と標本。** 応答の保存直後に、`evaluation.sampleRate`（既定 0.2）で標本を取り、判定を
**監査の連鎖と同じ tick で**回す（ターン中・端末操作中は延期。`nice 19`）。判定は本人の作業を止めない。

**結果の置き場。** 段 1 と同じ `feedback` の隣に `judge: { score, confidence, method, model, at }` を置く。
確度が `--min-confidence` に届かず `abstained` なら**何も書かない**（0.5 を捏造しない）。
`audit-feed` には `workload: judge` で 1 行。

**agent-herd が無いとき。** 何もしない（ADR-11）。設定の行は薄くする。

**画面。** 設定 > 実行制御「遷移や振り分けの判定」の下に「応答の自動採点」の 1 行（§4.3）。応答の
実行情報に「採点」の 1 行（§4.1）。

### 段 3: 評価セットと実験

**評価セット。** リポジトリの `.agents/evalsets/<名前>.json`（公開の正典と同じ作法。git で版を持つ）。

```js
{ name, description, items: [{ id, prompt, attachments: [{ rel }], expected: { contains?: [], regex?: '', note?: '' }, origin: { sessionId, index } }] }
```

項目は会話の応答の「評価セットに足す」（§4.1 の `•••`）から入る。期待値は任意で、無ければ人が並べて
見るだけ。

**実験。** 評価セット 1 つに実行条件（起動方針 / AI / モデル / 権限は読み取り専用固定）を付けて回す。
実行は **既存のヘッドレス経路**（1 ターン 1 プロセス）で項目ごとに 1 回。結果は `userData/experiments/<id>.json`
に `{ evalset, condition, runs: [{ itemId, text, elapsedMs, tokens?, heuristic?: { pass, detail }, judge? }] }`。
heuristic は `expected` から決定的に出す（JS で書いてよい唯一の「採点」で、集計ではない）。

**比べる。** 実験を 2 つ選び、項目ごとに答えを左右に並べる（変更ビューの「並べて表示」と同じ器）。

**画面。** 新しい領域「評価」（§4.4）。段 3 は面が大きいので、段 1・2 の運用が回ってから別の設計で
ASCII を出し直す。ここには位置づけと器だけ書く。

## 4. 画面（ASCII。承認を得るまで実装しない）

### 4.1 会話画面: 応答の下の操作行

借りる形: 会話画面（`#chat`）の応答の下の「フォーク」（`.message-action`）と、「実行情報」の折りたたみ
（`responseDisclosure`）。**ボタンを 2 つ足し、実行情報に行を 1〜2 本足すだけ**で、新しい部品は無い。

```
┌──────────────────────────────────────────────────────────────────────────┐
│  claude · sonnet · 標準                                        14:02   │
│                                                                          │
│  変更前に既存テストを確認しました。`settings.test.js` は通っています。   │
│  …（回答本文）…                                                          │
│                                                                          │
│  ▸ 思考・進捗 (3)                                                        │
│  ▾ 実行情報 (4)                                                          │
│    ✓ 実行結果      12 秒 · 終了コード 0 · 入力 1.2k / 出力 0.4k tokens   │
│    ✓ 開始コマンド  npm test                                              │
│    ✓ 変更          src/main/settings.js                                  │
│    ✓ 採点          良い（確度 0.86 · gemma4:e4b）        ← 段 2 のときだけ │
│                                                                          │
│                              良い  悪い  理由…   フォーク                 │
└──────────────────────────────────────────────────────────────────────────┘
```

- 「良い」「悪い」は `.message-action`。押した方が `.on` になり、もう一度押すと外れる。
- 「理由…」は押すと同じ行が 1 行の入力欄に変わる（`.inline-editor`。設定のスキル追加と同じ）。
  Enter で保存、Esc で戻る。**常駐の textarea は置かない**（規則 5）。
- 実行情報の「実行結果」行にトークンを足す。CLI が申告しないときは今までどおり所要時間だけ。
- 「採点」は判定が書かれたときだけ 1 行。棄権したときは行そのものを出さない。

### 4.2 設定 > 利用状況: 「評価」の 1 行

借りる形: 同じ面の「使用量」「内訳」（`.row` + `.sub` + agent-audit の `--json` の行）。

```
│ 使用量                                             [今月 ▾]           │
│   回数 128 · 実測 210k / 推定 40k tokens · 成功率 91%                 │
│ 評価                                                                  │
│   良い 34 · 悪い 6（評価率 31%） · 自動採点 平均 2.4 / 3（採点 52 件）│
│ 内訳                                              [AIごと ▾]          │
│   claude   回数 80 · 良い 25 · 悪い 3 · 自動 2.5                      │
│   codex    回数 48 · 良い 9  · 悪い 3 · 自動 2.2                      │
```

- 数字は agent-audit の `usage --json` に足す列をそのまま並べる。agent-app は計算しない。
- 内訳の表に列を 3 つ足すだけ。行は増やさない。

### 4.3 設定 > 実行制御: 「応答の自動採点」の 1 行

借りる形: 同じ面の「遷移や振り分けの判定」（`.setting-field` + `<select>`）。

```
│ 遷移や振り分けの判定                         [ローカルのAIで作業しているときだけ ▾] │
│ 応答の自動採点                               [使わない ▾]                          │
│   完了した応答をローカルのAIが採点します        5 件に 1 件 / すべて / 使わない     │
```

- 「判定に使うモデル」は上の行と共有する。別の欄は作らない。
- agent-herd が無ければ行を薄くする（理由は出さない。既存の tier の行と同じ）。

### 4.4 新しい領域「評価」（段 3。位置づけだけ）

借りる形: 「タスク」の実行詳細（`.execution-card` の並び）と、変更ビューの「並べて表示」。

```
 サイドバー                 │ 評価セット: 設定の見直し            [実行 ▾]  ••• │
 ─────────                  │ 依頼 12 件 · 最終実験 9/18                          │
 会話                       ├──────────────────────────────────────────────────────┤
 タスク                     │ ┌ 実験 ──────────────────────────────────────────┐ │
 ワークフロー               │ │ 標準 / claude            9/18  合格 10/12  2.4 │ │
 評価           ◀           │ │ 節約 / herd              9/18  合格  7/12  1.9 │ │
 共有                       │ └─────────────────────────────────────────────────┘ │
                            │ ┌ 比べる ─── 標準 / claude  │  節約 / herd ──────┐ │
 評価セット                 │ │ 1. 既存テストを…  ✓        │  ✗ テストを飛ばした │ │
   設定の見直し             │ │ 2. …                        │  …                  │ │
   ログ整形                 │ └─────────────────────────────────────────────────┘ │
```

段 3 の ASCII は段 1・2 を入れたあとに改めて出す。ここでは領域を 1 つ増やすかどうかの判断だけを仰ぐ
（増やさず「タスク」の中に置く案もある。§6）。

## 5. 保存と契約の変更（段 1・2）

| 場所 | 変更 |
|---|---|
| `sessions/<id>.json` の応答メッセージ | `feedback` と `judge` を任意で足す。無い旧メッセージは今までどおり |
| `audit-feed/<YYYYMMDD>.jsonl` | `workload` に `feedback` / `judge` を足す。行の形は変えない |
| `config.json` | `evaluation: { mode: 'off' | 'sample' | 'all' }`（既定 `off`） |
| IPC | `feedback:set`、`evaluation:run`（手動 1 件。テスト用） |
| agent-audit | `usage --json` に評価の列。`workload` の 2 値を知る（知らない値は今も `failed` に倒すので、先に agent-audit を直す） |
| spec | §4.2 に `feedback` / `judge`、§18.1 の表に 2 行、§18.3 に「評価」の行 |

## 6. 判断を仰ぐ点

1. **段 1 の「良い / 悪い」だけで足りるか。** Opik は 0〜1 の連続値と複数の名前つきスコアを持つ。
   ここでは 2 値 + 一言に絞った。細かい段階が要るなら段 2 の自動採点（3 段）に任せる案。
2. **段 2 の標本率。** 既定を「5 件に 1 件」にした。すべて採点すると ollama が常に動き、本人の
   ローカル AI の作業と競合する。
3. **段 3 の置き場。** 領域を 1 つ増やす（§4.4）か、「タスク」の一覧に「評価セット」を種類として
   混ぜるか。領域は既に 5 つあり、増やすとサイドバーが長くなる。
4. **段 3 をやるか。** 「フォーク」で 1 件ずつ回すのと、評価セットで 12 件をまとめて回すのとで、
   本人の手間がどれだけ違うか。段 1 でどの依頼に「悪い」が付くかを見てから決めてもよい。

## 7. 却下した案

- **Opik を Docker で立てて agent-app から SDK で送る。** サーバ（Java・ClickHouse・MySQL・Redis）が
  要り、WSL の vhdx を圧迫する。監査ストアを Windows 側へ寄せた決定（2026-09-16）と逆行する。
- **agent-app の JS で平均・分布を出す。** §18 の「数字は画面で作らない」に反する。同じ数字が
  agent-audit の `usage` と画面で食い違う経路を作る。
- **応答ごとに 5 段階の星。** 人は付けない。付けても軸が揃わない。2 値 + 一言に落とした。
- **span の親子を CLI 出力から復元する。** adapter は平坦な列しか出さず、復元は推測になる。
  平坦なまま「実行情報」に出す（いまの形）。
- **プロンプト管理の画面を新設する。** 「定型の依頼」「共通指示」と git があり、二重になる。
