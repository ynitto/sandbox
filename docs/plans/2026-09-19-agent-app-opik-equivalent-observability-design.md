# agent-app に Opik 相当の機能（自動評価・履歴のまとめ評価・課題の提示）を入れる

作成: 2026-09-19。改訂: 2026-09-19（方針の変更。§0 の「決めたこと」）。状態: **実装済み（段 0〜3。agent-app 0.15.0）**。
§6 の判断は推奨のとおり（課題は受信箱、標本は 5 件に 1 件 + 失敗は必ず、まとめて評価はクラウドの AI も可、
渡した課題は受信箱から消す）。§3.3 の「終わったら受信箱に未読で 1 件」、§3.4 の「フォークのダイアログで
渡す」「根拠は元の会話へのリンク」も入れた。契約は仕様 §19。

## 0. TL;DR

OSS の Opik（Comet）は LLM アプリの **追跡（trace / span）・評価（feedback score・LLM-as-judge）・
評価セットと実験・プロンプト管理・ダッシュボード** を 1 つの Web UI に持つ。agent-app と agent-audit
には、このうち **追跡の材料、使用量の集計、そして「観測 → 洞察 → 改善タスク」の連鎖** が既にある。
無いのは「応答や実行を**評価して観測にする口**」「過去の会話を**まとめて評価する口**」「洞察を
**課題として人に見せる面**」の 3 つ。

**決めたこと（2026-09-19 の方針）:**

1. **人が画面で評価する機能（良い / 悪い のボタン）は入れない。** 評価は自動（応答・実行の完了時）か、
   会話の横断検索から**まとめて**行う。
2. **評価の目的は、スキル・タスク・ワークフロー・使っているツールの改善。** 応答 1 件の良し悪しを
   残すことではなく、「どの定型物・どのツールで、何が繰り返し起きているか」を出すこと。
3. **agent-app が出すのは課題まで。** 評価結果をまとめて課題として提示し、改善策は利用者がその課題を
   会話に渡して AI と決める。agent-app は改善案を作らず、自動で直しにも行かない。

方針は 3 つ。

- **Opik のサーバもクライアント SDK も入れない。** 評価は agent-herd の `judge`（ローカル）か、
  利用者が選んだ AI のヘッドレス 1 回。観測の保存と洞察への畳み込みは agent-audit（`extract` /
  `distill`）。agent-app は評価の起動・申告・表示だけを持つ（§18 の不変条件をそのまま守る）。
- **段を 3 つに切り、上から順に出す。** 段 1「自動で評価して観測にする」は画面が無い。段 2「履歴から
  まとめて評価する」は検索画面に操作を 1 つ足す。段 3「課題を見せて会話へ渡す」は受信箱に種類を
  1 つ足す。新しい領域は作らない。
- **Opik の機能を名前ごとに写さない。** feedback score（人の評価）は入れない。dataset / experiment は
  作らない（「まとめて評価」が同じ目的を、既にある会話で果たす）。prompt library は「定型の依頼」
  「共通指示」、Playground は会話そのもの。

読むべき人: 会話・検索・受信箱・agent-audit の feed と rules に手を入れる人。画面の承認だけをする人は
§4 だけでよい。

## 1. Opik の機能と agent-app の対応

| Opik の機能 | 何をするか | agent-app / agent-audit のいま | 差分 |
|---|---|---|---|
| Trace / Span | 1 回の呼び出しを入力・出力・所要時間・トークン・tool call で残す | 応答メッセージが `text` / `parts.thinking` / `parts.information`（command / file / skill）/ `elapsedMs` / `code` を持つ（spec §4.2〜4.3）。タスク・ワークフローは `run-history`。CLI ネイティブのセッションは agent-audit の `sessions` が読む | **ある**。ただし「どのスキル・ツールを使ったか」が申告の行に載っていない（§3.1） |
| Thread | 会話単位で見る | 会話そのもの。横断検索（アプリ外の CLI・VS Code の会話も対象） | ある |
| Feedback score / Annotation | 人が応答に点と理由を付ける | 無い | **入れない**（決めたこと 1） |
| LLM-as-judge | 別のモデルに採点させる | agent-herd `judge`（`score` / `choice` 型・確率つき・確度不足は棄権）。遷移判定に配線済み | **口はある**。評価には未配線 → 段 1・2 |
| Online evaluation rules | 本番の trace を標本抽出して自動採点 | 無い | 段 1 |
| Dataset / Experiment | 入力集合を条件を変えて回し比べる | 無い | **作らない**。過去の会話を対象に「まとめて評価」する（段 2）ことで代える |
| Insights / Optimization suggestions | 観測を畳んで改善提案にする | agent-audit `extract`（record → 観測）→ `distill`（観測クラスタ → 洞察: skill-improvement / config-fix / usage-optimization / rule-candidate）→ `tasks`（洞察 → 改善タスク JSON） | **連鎖はある**。agent-app は回すだけで見せていない → 段 3 |
| Prompt library / Playground | 版つきプロンプト・試し打ち | 「定型の依頼」「共通指示」と git。会話の「直接指定」 | ある。作らない |
| Dashboard | 件数・トークン・スコア推移 | 設定 > 利用状況（agent-audit の `--json`） | ある。評価の行を 1 つ足す（§4.3） |
| Cost tracking | 単価表でドル換算 | 無い。利用枠（%）は出す | 作らない（定額の CLI が主） |
| Guardrails / Agent optimizer | 入出力の検閲、プロンプトの自動最適化 | 無い | 対象外（決めたこと 3。改善は人と AI の会話で決める） |

## 2. 目標と非目標

### 目標

- 応答と実行が終わるたび、利用者の手なしに、ローカルの判定 AI が「品質」と「問題の種類と対象」を出し、
  観測として agent-audit に渡る。確度が足りなければ**出さない**（段 1）。
- 会話の横断検索で絞った会話（アプリ外の CLI・VS Code の会話を含む）を選び、まとめて評価できる。
  評価は本人の作業を止めず、終われば受信箱に結果が届く（段 2）。
- 洞察が「対象（スキル / タスク / ワークフロー / ツール）ごとの課題」として受信箱に並び、根拠の件数と
  元の会話へ辿れる。課題を 1 押しで新しい会話に渡せ、改善策はそこで AI と決める（段 3）。

### 非目標

- 人が画面で応答に点を付ける口。
- Opik のサーバ（Java + ClickHouse）や Python SDK を同梱する・呼ぶこと。
- 集計・分布・平均・クラスタリングを agent-app の JS で書くこと。agent-audit が出す。
- 改善案の生成、定型物やツールの自動修正。agent-app は課題を見せるまで。既存の `publish:improve`
  （適格性が落ちた成果物を直させる）は別経路のまま残す。
- 費用（ドル）の換算。span の親子関係の復元。

## 3. 段と、それぞれの中身

### 3.1 段 0（前提）: 申告の行に「何を使ったか」を載せる

いまの `audit-feed` の行（spec §18.1）は `workload` / `status` / `tokens` / `artifact`（タスク・ワークフロー
だけ）を持ち、会話のターンには**どのスキルを選び、どのコマンド・ツールを叩いたか**が無い。対象ごとに
束ねるには、これを行に足す。

```js
// audit.feedTurn に足す（既存の項目は変えない）
used: {
  skills:   ['statemachine-use', …],          // message.skillSelection の採用分
  commands: ['npm test', 'git diff', …],       // parts.information の type: command の先頭語（最大 20）
  tools:    ['browser', 'winauto', …],         // コマンドから引く既知のツール名（agents/*.json と tools/ の名前）
}
```

agent-audit 側は `used` を読んで観測の `group` 鍵に対象（`skill:<名前>` / `tool:<名前>`）を足す。
タスク・ワークフローは既存の `artifact` がそのまま対象になる。**これが無いと、段 1〜3 の評価が
「何を直せばよいか」に繋がらない。**

### 3.2 段 1: 自動で評価して観測にする（online evaluation）

**判定の口。** agent-herd `judge` に、固定の問いを 2 つ投げる（`src/main/evaluation.js` に置く。
人が編集する設定にはしない）。

```text
quality: { type: 'score', instructions: '依頼に対して回答・実行が要点を押さえ、誤りや無駄がないか', criteria: 3 段 }
issue:   { type: 'choice', instructions: '改善すべき点があれば、どこに原因があるか',
           choices: ['none', 'skill-gap', 'prompt-issue', 'tool-failure', 'config-issue', 'avoid'] }
```

`issue` の選択肢は agent-audit の観測の種類（`OBSERVATION_KINDS`）に `tool-failure` を足したもの。
**新しい語彙を作らず、あちらの語彙に合わせる**（agent-audit 側に `tool-failure` を 1 つ足す）。

**契機と標本。** 応答（`turn:done`）と実行（`run-history.append`）の直後に、`evaluation.mode` で決める。
`sample`（既定。5 件に 1 件）/ `all` / `off`。失敗・停止・非ゼロ終了の応答は**標本に関係なく必ず**評価する
（課題の材料はそこに集まる）。判定は監査の連鎖と同じ tick で回す（ターン中・端末操作中は延期。`nice 19`）。

**結果の置き場。** `audit-feed` に `workload: evaluation` で 1 行。元のターン・実行の行は書き換えない。

```js
{ ts, workload: 'evaluation', ref: <会話 ID | 実行 ID>, session_id, agent_cli, model,
  evaluation: { quality: 1|2|3, confidence, issue: 'skill-gap'|…|'none', method: 'logprobs'|'vote'|'text',
                judge_model: 'gemma4:e4b', used: {…同じ形…}, artifact: {…あれば…} } }
```

`issue` が `none` 以外なら、agent-audit の `extract` がその行を観測（`kind` = issue、`group` に対象）として
拾う。`confidence` が `--min-confidence` に届かず棄権したら**行を書かない**。

**agent-herd が無いとき。** 何もしない（ADR-11）。設定の行は薄くする。段 1 に他の AI は使わない
（常時回るものにクラウドの枠を使わない）。

**画面。** 設定 > 実行制御に 1 行（§4.1）。応答の実行情報には出さない（人に見せる面は段 3 の課題）。

### 3.3 段 2: 履歴からまとめて評価する

**入口。** 「会話を検索」の結果一覧に、既存の「保存データ」「スキル」の面と同じ作法で
**行のチェックと足元の操作 1 つ**を足す（§4.2）。検索の絞り込み（AI・日付・リポジトリ・取得元・モデル）が
そのまま評価の対象の絞り込みになる。**アプリ外の会話（CLI / VS Code）も対象**にできるのが、
検索画面から出す理由。

**実行条件。** 評価に使う AI は、他の画面と同じ実行設定のポップオーバーで選ぶ。既定は `herd`（ローカルの
判定 AI）。クラウドの AI を選んだときは、会話 1 件につきヘッドレス 1 回（読み取り専用）で、§3.2 と同じ
2 つの問いを JSON で返させる。上限は 1 回に 200 件（超えたら条件を絞る 1 行。検索の 2000 件と同じ作法）。

**進め方。** 評価はキューに積んで背景で 1 件ずつ回す（同時 1。ターン中は延期）。会話の本文は
agent-audit の `sessions --messages` か `sessions/<id>.json` から読み、判定 AI に渡す前に scrub を通す
（資格情報の伏せ字化は agent-audit の `scrub` と同じ規則。JS へ規則を写さず、`agent-audit scrub` の口を
1 つ足して呼ぶ）。

**結果の置き場。** §3.2 と同じ `workload: evaluation` の行。`ref` はアプリ外の会話なら agent-audit の
record id（`source::store::native_id`）。終わったら受信箱に「まとめて評価が終わった（n 件・課題 m 件）」を
未読として 1 件出す（§4.4 の行き先は「課題」）。

**画面。** §4.2。新しい画面は無い。

### 3.4 段 3: 課題を見せて会話へ渡す

**元になるもの。** agent-audit の洞察（`insights/*.json`。`statement` / `kind` / `suggested_action` /
`occurrences` / `observation_ids` / `confidence` / `review`）。agent-app は既に `audit.insights()` で読めるが、
IPC にも画面にも出していない。`suggested_action` は agent-audit の既定（決定的テンプレ）が短い定型文を
入れる。**agent-app はこれを「改善案」として見せない**——課題として見せるのは `statement`・対象・根拠で、
改善策は会話で決める（決めたこと 3）。

**対象の引き方。** 洞察の `scope` と観測の `group`（§3.1 の `skill:` / `tool:` / `artifact`）から
対象 `{ kind: skill|task|workflow|tool, name }` を引く。引けない洞察は「全体」の課題として出す。

**受信箱に種類を足す。** 受信箱は「人が結果を見るべきもの」の投影（spec §17）で、課題はまさにそれ。
`attention.js` の源泉に `insightSources` を足す。

| 種類 | 正典 | 結果 | 答え待ち | 実行中 | 行き先 |
|---|---|---|---|---|---|
| 課題 | `userData/audit/insights/*.json` | `updated_at`（改訂されれば再び未読） | なし | なし | `{ kind: issue, id: 洞察 id }` → 受信箱の本文に課題の詳細 |

`review.verdict` が `refuted` のものと、`exported` 済みのものは出さない（`tasks` と同じ規則）。

**会話へ渡す。** 課題の本文の操作は「会話で扱う」1 つ。押すと、既存の**フォークのダイアログ**
（リポジトリ・AI・モデル・権限を選ぶ）を開き、最初の依頼文に課題を載せた**新しい会話**を始める。
依頼文の形は `src/main/evaluation.js` の 1 か所（対象・statement・根拠の会話へのリンク・
「改善策を一緒に決めたい。まだ直さなくてよい」）。改善が決まって直すかどうかは、その会話の中で
利用者が決める。渡したら洞察に `exported: true` を書く（agent-audit の `tasks --mark-exported` と同じ
意味。書くのは agent-audit の口 `agent-audit tasks --mark-exported --id <id>` を 1 つ足して呼ぶ。
**agent-app は監査ストアに書かない**不変条件を守る）。

**画面。** §4.4。

## 4. 画面（ASCII。承認を得るまで実装しない）

### 4.1 設定 > 実行制御: 「応答と実行の自動評価」の 1 行

借りる形: 同じ面の「遷移や振り分けの判定」（`.setting-field` + `<select>`）。

```
│ 遷移や振り分けの判定                         [ローカルのAIで作業しているときだけ ▾] │
│ 応答と実行の自動評価                         [5 件に 1 件 ▾]                       │
│   終わった応答と実行をローカルのAIが評価し、    5 件に 1 件 / すべて / 使わない     │
│   課題を受信箱に出します                                                            │
```

- 「判定に使うモデル」は上の行と共有する。別の欄は作らない。
- agent-herd が無ければ行を薄くする（理由は出さない。既存の tier の行と同じ）。
- 失敗した応答・実行は標本に関係なく評価する。これは画面に書かない（README に書く）。

### 4.2 会話を検索: 結果一覧にチェックと足元の操作

借りる形: 設定 > スキルの一覧（行のチェック + 足元に操作 1 つ + 状態の 1 行）、実行設定の
ポップオーバー（`.run-settings`）。

```
┌ 会話を検索 ──────────────────────────────────────────────────── [閉じる] ┐
│ [会話のタイトル・内容を検索            ] [すべてのエージェント▾] [過去7日▾] …│
│ 調べた 412 件 · 一致 38 件                                                  │
├──────────────────────────────────┬───────────────────────────────────────┤
│ ☑ 設定画面の見直し    claude 9/18 │ 会話のプレビュー                       │
│ ☑ ログ整形の依頼      codex  9/18 │ …                                      │
│ ☐ README の更新       claude 9/17 │                                        │
│ ☑ 定期実行の失敗      herd   9/17 │                                        │
│ …                                │                                        │
├──────────────────────────────────┴───────────────────────────────────────┤
│ 選んだ 3 件                   [実行設定 ▾ herd]  [選んだ会話をまとめて評価] │
│ 評価は背景で進み、終わると受信箱に課題が届きます                            │
└──────────────────────────────────────────────────────────────────────────┘
```

- チェックは行の左。「すべて選ぶ」は置かない（検索の絞り込みで対象を決める。200 件までの上限を
  超えるときは足元の 1 行で伝える）。
- 「実行設定」は会話の入力欄と同じポップオーバー（AI・モデルだけ。権限は読み取り専用で固定）。
- 押したら足元の 1 行が「評価中 1 / 3」になり、画面を閉じても続く。主ボタンは面に 1 つ。

### 4.3 設定 > 利用状況: 「評価」の 1 行

借りる形: 同じ面の「使用量」「内訳」（`.row` + `.sub` + agent-audit の `--json` の行）。

```
│ 使用量                                             [今月 ▾]           │
│   回数 128 · 実測 210k / 推定 40k tokens · 成功率 91%                 │
│ 評価                                                                  │
│   評価 64 件 · 品質 平均 2.4 / 3 · 課題あり 11 件（スキル 4 · ツール 5 · 全体 2）│
│ 内訳                                              [AIごと ▾]          │
│   claude   回数 80 · 品質 2.5 · 課題 4                                │
│   codex    回数 48 · 品質 2.2 · 課題 7                                │
```

- 数字は agent-audit の `usage --json` に足す列をそのまま並べる。agent-app は計算しない。

### 4.4 受信箱: 種類「課題」

借りる形: 受信箱の一覧（他の領域と同じ `.list` の行。リポジトリ名の代わりに対象を添える）と、
タスクの概要の `.execution-card`（`<h3>` + 1 行の `<p>` + 右に `.status`、操作は下の `.row`）。

```
 受信箱                    │ 課題                                                      │
 要対応 1 · 未読 4         │ 対象ごとにまとめた課題。会話に渡して改善策を決めます        │
 ─────────                 ├───────────────────────────────────────────────────────────┤
 ● 定期実行の失敗  要対応  │ ┌───────────────────────────────────────────────────────┐ │
 ○ 設定画面の見直し  未読  │ │ スキル statemachine-use                    観測 6 件  │ │
 ○ まとめて評価 3 件 未読  │ │ 画面操作の見本を求める段で、記録の開始を 2 回以上     │ │
 ○ 課題: statemachine-use  │ │ やり直している                                        │ │
 ○ 課題: ツール browser    │ │ 根拠: 9/18 設定画面の見直し · 9/17 定期実行の失敗 · …  │ │
                           │ │                                        [会話で扱う]   │ │
                           │ └───────────────────────────────────────────────────────┘ │
                           │ ┌───────────────────────────────────────────────────────┐ │
                           │ │ ツール browser                             観測 4 件  │ │
                           │ │ …                                                     │ │
```

- 一覧の行は既存の受信箱の行。種類が「課題」の行は先頭に「課題:」と対象名。
- 本文はカードの並び。1 つの課題 = 1 カード。カードに置くのは対象・statement・根拠（元の会話への
  リンク。押すとその会話を開く）・「会話で扱う」だけ。**改善案の文は置かない。**
- 「会話で扱う」を押すとフォークのダイアログ（既存）が開き、リポジトリと AI を選んで新しい会話が
  始まる。渡した課題は受信箱から消える（`exported`）。
- 受信箱の件数の印には、課題も「未読」として数える。

## 5. 保存と契約の変更

## 6. 判断を仰ぐ点

1. **課題の置き場を受信箱にしてよいか。** 受信箱は「人が結果を見るべきもの」の投影で、課題はそれに
   当たると判断した。別案は「設定 > 利用状況」の中（集計と同じ面。ただし操作が設定の中に入る）。
2. **段 1 の標本率。** 既定「5 件に 1 件」+ 失敗は必ず。すべて評価すると ollama が常に動き、本人の
   ローカル AI の作業と競合する。
3. **段 2 でクラウドの AI を選べるようにするか。** 「まとめて評価」は利用者が明示的に押すので、クラウドの
   枠を使ってよいと判断した。ローカルだけに絞る案もある。
4. **課題を渡すときに `exported` を書いてよいか。** 渡した課題は受信箱から消える。消さずに「渡した」の
   札にする案もある。

## 7. 却下した案

- **応答ごとの「良い / 悪い」ボタン（初版の段 1）。** 方針の変更で外した。人が付ける点は軸が揃わず、
  改善の対象（どのスキル・ツールか）に繋がらない。
- **Opik を Docker で立てて SDK で送る。** サーバ（Java・ClickHouse・MySQL・Redis）が要り、WSL の vhdx を
  圧迫する。監査ストアを Windows 側へ寄せた決定（2026-09-16）と逆行する。
- **評価セットと実験（初版の段 3）。** 過去の会話を絞ってまとめて評価すれば、同じ目的（どこで何が
  起きているか）を既にある会話で果たせる。新しい領域も正典も要らない。
- **agent-app の JS で観測を束ねて課題にする。** agent-audit の `distill` と二重になり、同じ材料から
  違う課題が出る経路を作る。
- **課題に改善案を添える。** agent-audit の `suggested_action` は決定的テンプレの定型文で、改善策として
  弱い。改善策は会話で AI と決める（決めたこと 3）。
- **課題を自動で `publish:improve` に流す。** 改善策を人が決める前に直しに行く。既存の improve は
  適格性が落ちた成果物の経路として残し、課題からは繋がない。
