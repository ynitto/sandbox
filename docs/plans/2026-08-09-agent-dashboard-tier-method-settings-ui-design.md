# Agent Dashboard 段・実行手法設定 UI 設計

> **履歴資料**: この初期案の「段」「実行手法」「ON/OFF」と、検索一覧を常時表示する設計は
> 2026-08-11に見直した。現在の正典は
> [Agent Dashboard 統一実行方針 UI・agent-tools 共通制御設計](./2026-08-11-agent-dashboard-unified-execution-policy-design.md)
> の「UI用語」「作業ルールと実行方針の分離」とする。内部契約の `tier` / `methods` は維持する。

## 背景

全体設定の「実行制御」には、予算・同時実行数・稼働制御に加えて、段の定義、
自動切り替え条件、実行手法カタログが同居している。段の構成と切り替え条件の境界が
読み取りにくく、実行手法も表形式のため、目的の手法を探して有効化する操作に向いていない。

プロジェクトの実行カードでは run 全体の `running` だけを表示しているため、実際にノードが
動いている状態と、未着手ノードが順番を待っている状態を区別できない。参加カードでは説明を
切り詰めた結果、内容を確認する手段がなくなっている。

## 採用設計

既存の `agent-profiles` と `agent-tuning` 契約を維持し、表示と操作を再構成する。
全体設定には「段と実行手法」タブを追加し、段ごとのエージェント・モデル設定と、検索可能な
実行手法カタログをまとめる。「実行制御」には予算、同時実行数、稼働制御、段の自動切り替え
条件を残す。

| アプローチ | 実装コスト | リスク | 保守性 | 拡張性 | 推奨度 |
|---|---|---|---|---|---|
| 既存契約を保った UI 分離 | 低 | 低 | 高 | 中 | ★★★ |
| カスタム手法をカタログ JSON として保存 | 中 | 中 | 中 | 高 | ★★☆ |
| 新しい手法管理基盤を追加 | 高 | 高 | 低 | 高 | ★☆☆ |

## 全体設定の構成

### 段と実行手法

タブの上段に段の設定、下段に実行手法を置く。

段の設定は `profiles.tiers` を上位から表示する。各段では表示名と、優先順を持つ
エージェント・モデルの候補ペアを編集する。候補は行単位で追加・削除でき、段自体の追加・削除も
既存契約の範囲で維持する。残予算の割合やヒステリシスなど、選択条件はここへ置かない。

実行手法は検索欄を最初の操作として配置し、ID、説明、反映元を入力中に絞り込む。ロールと
有効状態でも絞り込める。結果はカードで表示し、説明、適用条件、反映元、ON/OFF 操作だけを
見せる。検索結果がない場合は、検索語や絞り込み条件を解除する案内を表示する。

### 実行制御

予算配分、同時実行数、機能ごとの稼働制御、設定の反映状況を維持する。自動切り替え設定では、
有効化、対象機能、段ごとの残予算条件、上限なしで使う段、ヒステリシス、最小保持時間、試算、
即時反映を扱う。段の表示名と候補エージェントは参照表示に留め、編集は「段と実行手法」へ集約する。

## カスタム実行手法

「カスタム手法を追加」ボタンで HTML `dialog` を開く。フォームには ID、説明、ロール、指示、
tier、用途、対象機能、エージェント、モデルの適用条件を持たせる。`origin` と `source` は
保存時にユーザーカスタムとして自動設定する。

ダイアログ上部の「作りたい手法」へ自由記述し、「AIで補完」を押すと、既存の画面内 AI 設定を
使って未入力項目へ構造化案を入れる。AI は保存を行わず、人が内容を確認して「追加」を押した
時だけ `tuning.json` を更新する。補完中はボタンを無効化し、失敗はダイアログ内の
`role="alert"` へ表示する。

追加後はプリセットと同じカード、検索、絞り込み、ON/OFF 操作を使う。既存 ID との重複は
上書きせず入力エラーにする。現在は無効化したカスタム手法を再度有効化できないため、
`setMethod` はカタログ項目に加えて既存カスタム項目も再有効化できるようにする。

## 実行カードの状態

run 全体の status だけでなく、表示用に集計済みのノード数を使う。非終端 run は次の優先順で
カード状態を決め、文字で明示する。

1. `parked > 0`: 承認待ち
2. `claimed > 0`: 実行中
3. `pending > 0`: 実行待ち
4. `waiting > 0`: 依存待ち
5. その他: run の phase

終端状態と要対応状態の既存判定は維持する。色だけに依存せず、カード先頭の状態ラベルで
区別できるようにする。

## 参加カード

カードを同じ固定高さにし、見出しと操作ボタンの位置を揃える。説明欄は最低 3 行分の高さを
確保し、残りの縦領域を使うスクロール領域とする。全文を DOM に保持して縦スクロールで読める
ようにし、横方向は折り返す。キーボードでも説明欄へ移動してスクロールできるよう、説明領域に
アクセス可能な名前とフォーカス先を与える。操作ボタンはカード下部に固定する。

## データフロー

- 段の保存は既存 `orchestration:profilesSave` を使い、段タブは `tiers`、実行制御は `policy` を編集する。
- 実行手法の ON/OFF と追加は既存 tuning 保存経路を使う。
- AI 補完は既存のエージェント解決・実行処理を再利用し、構造化 JSON だけを renderer へ返す。
- 実行カードと参加カードの変更は表示層だけで、保存契約を変更しない。

## エラーハンドリング

- 段の削除で切り替え条件が参照不能になる場合は、保存時に無効な参照を除く。
- カスタム手法は必須項目、ID 形式、条件値を main 側でも検証する。
- AI 応答は JSON 抽出後に許可フィールドだけを正規化し、不正な応答を保存しない。
- 検索結果なし、読み込み失敗、保存失敗を操作箇所の近くへ表示する。

## アクセシビリティとレスポンシブ

- タブは既存の `tablist` / `tab` / `tabpanel` と狭幅用 select に追加する。
- 検索欄と絞り込みには label、結果件数には `aria-live` を付ける。
- ダイアログは既存のフォーカス管理と Escape 閉じを使い、補完・保存中の重複操作を防ぐ。
- 手法カードは広幅で複数列、狭幅で 1 列にし、水平スクロールを発生させない。
- 参加カードの説明領域は可視フォーカスを持つ。

## テスト

- 「段と実行手法」タブが追加され、段と手法が「実行制御」から移動していること。
- 段候補の保存と自動切り替え条件の保存が互いの値を失わないこと。
- 手法の検索、ロール・状態絞り込み、結果なし表示、ON/OFF が動くこと。
- カスタム追加ダイアログの検証、AI 補完、追加後の表示、無効化後の再有効化が動くこと。
- 実行カードが `claimed`、`pending`、`waiting`、`parked` を正しく区別すること。
- 参加カードが固定高さで、説明を 3 行以上表示し、縦スクロールできること。
- 既存テスト、ESLint、差分チェックを通すこと。

## 実装計画

1. 全体設定タブと profiles UI を「段」と「自動切り替え条件」に分割する。
2. 実行手法を検索・絞り込み付きカードへ変更し、カスタム追加ダイアログを作る。
3. 既存 AI 実行経路へ手法補完モードを追加し、保存前の構造化提案を返す。
4. カスタム手法の重複検証と再有効化を修正する。
5. 実行カードの表示状態をノード数から導出する。
6. 参加カードを固定高さとスクロール可能な説明領域へ変更する。
7. 対象テストと全体テストを実行する。

## 既存スキルとの関係

- `ui-designer`: 検索を主操作にしたカード一覧、ダイアログ、キーボード操作に利用する。
- `webapp-testing`: タブ、検索、ダイアログ、スクロール領域の実画面確認と相性がよい。
- React 系スキルはプレーン Electron のため使用しない。
