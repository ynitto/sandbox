# agent-app 自動化ワークベンチ統合設計

> 作成: 2026-09-05  
> 対象: `tools/agent-app`  
> 参照実装: `tools/statemachine-maker`

## 背景

statemachine-maker が持つステートマシンの作成、編集、実行、定期実行を、agent-app の一機能として統合する。
agent-app はすでに登録済みリポジトリ、複数セッション、worktree、会話、ファイル、差分を扱うため、同じ
リポジトリをもう一度登録させる独立アプリ型の導線は避ける。一方で、会話やファイルは「選択中セッションの
表示」であり、自動化は複数回実行される独立した仕事の定義なので、両者を同じ階層のタブには置かない。

## 調査した一般的な構成

- GitHub Copilot app はサイドバーの主要領域として Sessions、Chats、Automations などを分ける。
  Automation 一覧には名前、予定、対象リポジトリ、最終状態を出し、定義からオンデマンド実行もできる。
  - https://docs.github.com/en/copilot/get-started/quickstart-copilot-app
  - https://docs.github.com/en/copilot/how-tos/github-copilot-app/using-automations
- Codex app は project 配下に thread を整理し、Automation の完了結果を review queue に送る。
  - https://openai.com/index/introducing-the-codex-app/
- Cursor は Background Agents を専用サイドバーで一覧化し、選択後に状態確認、追加指示、引き継ぎを行う。
  - https://docs.cursor.com/background-agent
- Devin は入力中の依頼から予定を作れる一方、管理は Schedules 一覧に集約し、頻度、最終実行、状態を示す。
  - https://docs.devin.ai/product-guides/scheduled-sessions

共通するのは、プロジェクト／リポジトリを仕事の境界にし、対話セッションと自動化を主要領域として分け、
実行の進捗と成果確認を同じ詳細画面へ集約する構成である。

## 目的

- agent-app だけで、対話型の作業と再利用可能な自動化を行き来できる。
- 登録済みリポジトリ、AI 定義、実行基盤を再利用し、設定の二重入力をなくす。
- statemachine-maker の全機能を、agent-app の情報構造に合う形で利用できる。
- 初見では「何を実行するか」「今どうなっているか」「次に何をすべきか」が分かる。
- 内部の YAML、state、transition、agent-loop の用語を通常画面へ露出しない。

## 採用する構成

### アプリ全体の主要領域

左サイドバーの最上部に `作業` と `自動化` の主要ナビゲーションを置く。

```text
agent-app
├─ 作業
│  ├─ リポジトリ
│  ├─ セッション
│  └─ 会話 / ファイル / 変更
└─ 自動化
   ├─ リポジトリ
   ├─ ワークフロー
   └─ 概要 / 実行 / 編集 / 履歴
```

`会話 / ファイル` は引き続き選択中セッションの表示切替とする。`自動化` はその横へ第 3 タブとして
追加せず、セッションより一段上の主要領域として扱う。

### 作業領域

既存の構造と操作を維持する。自動化統合のために、会話、ファイル、端末、変更、worktree の挙動を変えない。
領域を切り替えて戻ったときは、選択中リポジトリ、セッション、会話／ファイル表示、変更パネルを復元する。

### 自動化領域

左側は上から、主要ナビゲーション、登録済みリポジトリ、選択中リポジトリのワークフロー一覧とする。
会話一覧と会話専用の tmux／worktree 設定は隠す。中央は選択中ワークフローの詳細とし、次の順序で表示する。

1. 名前、目的、現在の状態、主操作 `実行`
2. 実行に必要な入力
3. 実行中の進捗、停止、結果
4. 次回予定と定期実行設定
5. 直近の実行履歴と、選択時だけ読むログ

一覧の各行には名前、短い状態、次回予定を表示する。状態は `実行中`、`要確認`、`失敗`、`完了`、
`未実行` を文言で示し、色だけには依存しない。`要確認` と `失敗` を上部のフィルターで絞れるようにするが、
検索、タグ、集計グラフは初版に入れない。

### 新規作成と編集

自動化領域の `新しい自動化` を入口にし、`AIで下書き` と `手動で作成` を選べるようにする。
操作記録は独立した主要入口にはせず、作成・編集中の `その他` から開く。

編集画面は statemachine-maker の情報設計を踏襲する。

- 左: 工程の流れ。カードには短い要約、実行方法、確認・記録の有無だけを表示する。
- 右: 選択中工程の設定。未選択時は次の操作を説明する。
- 上部: 戻る、名前、未保存、AIで見直す、保存。
- その他: 操作を記録、生成ファイル、構成を確認、実行環境。
- 保存済み定義の `実行` は、自動化詳細へ戻して行う。編集画面に別の実行ダイアログを重ねない。

狭い幅では工程の流れと設定を一画面ずつ表示する。中央領域全体の横スクロールは発生させない。

## 取り込む機能

statemachine-maker から次を取り込む。

- `.statemachine/<保存名>/` の一覧、読み込み、往復編集、保存
- 工程の追加、並べ替え、削除、分岐、完了確認、終了条件、入力変数
- 生成予定ファイルのプレビューと保存済みファイルの表示
- Playwright CLI と Windows automation による操作記録、記録テキストの取り込み
- AI による下書き、確認質問、候補表示
- AI による全体／工程の見直し、差分ごとの選択反映
- statemachine-use による構成確認
- agent-loop を入口にした手動実行、進捗、停止、結果
- 日次、週次、一定間隔の定期実行、開始／停止、未反映状態
- 手動／定期の共通履歴、ログの遅延読み込み
- Python、statemachine-use、操作記録ツール、agent-tools の接続診断

独立版のフォルダ登録機能は取り込まない。agent-app の登録済みリポジトリを唯一の対象一覧とする。

## 責務とデータ境界

- agent-app renderer は選択、入力、表示だけを担当する。
- ステートマシンの正規化、コンパイル、検査は statemachine-maker 由来の決定的な domain module が担う。
- 手動実行、定期発火、重複制御、状態、履歴は agent-loop を正典とする。
- AI と model の解決、statemachine harness、結果契約は agent-tools を正典とする。
- ワークフロー定義は登録済みリポジトリの `.statemachine/` 配下だけを読み書きする。
- agent-app の会話セッションと自動化の実行履歴は混ぜない。自動化の一回の実行は run として扱う。

agent-app の設定には、主要領域、リポジトリごとの最後のワークフロー、最後の自動化画面、実行環境の
上書きだけを追加する。statemachine-maker の roots 設定は移植しない。

## 実装構成

agent-app 内に `automation` 単位の境界を置く。

```text
tools/agent-app/src/
├─ main/
│  ├─ automation/       model、store、recording、AI、agent-loop adapter、runner、tools
│  └─ ipc.js            登録済み repo を検査して automation IPC へ委譲
├─ preload.js           api.automation.* を公開
└─ renderer/
   ├─ automation.js     自動化領域の状態、描画、操作
   ├─ automation.css    statemachine-maker を基準にした固定ニュートラル UI
   ├─ renderer.js       主要領域、repo 選択、既存セッションとの連携
   └─ index.html        主要ナビゲーションと automation host
```

初回は agent-app に自己完結した feature module として移植する。statemachine-maker は既存利用者と比較検証の
ため残す。同じ仕様を二重に独自発展させないよう、移植元の単体テストを agent-app 側へ持ち込み、互換 fixture
で往復結果を比較する。統合完了後、独立版の廃止または共通 package 化は別判断とする。

## 状態管理とデータフロー

主要領域は `work | automation`、作業内表示は `chat | files`、自動化内表示は
`overview | editor` として別々に保持する。一つの `view` 値へ詰め込まない。

1. repo 選択時、作業領域はセッション、AI、worktree を取得する。
2. 自動化領域は workflow 一覧、実行 snapshot、AI 候補を並列取得する。
3. workflow 選択時、概要は snapshot 内の軽量情報を先に表示する。
4. 編集開始時だけ定義本体を読む。
5. 履歴ログは利用者が `ログ` を開いたときだけ読む。
6. 実行中イベントは request ID と workflow ID が一致する場合だけ反映する。
7. 保存・実行・定期設定後に必要な範囲だけ再取得する。

## UX とアクセシビリティ

- 主操作は各画面で一つにする。概要は `実行`、編集は `保存`、新規作成は `下書きを作る` または `作成`。
- 高度な設定、生ログ、生成ファイル、操作記録は段階表示する。
- 非同期操作中は対象ボタンを無効化し、操作箇所の近くに進行状態を出す。
- エラーは短い原因と回復操作を先に示し、stderr、終了コード、コマンドは詳細内に置く。
- button、input、select には可視 focus を設け、DOM 順と見た目の順を一致させる。
- アイコンだけのボタンには `aria-label` を付け、主要操作のタッチ領域は 44px を目安にする。
- `role=status` と `role=alert` を使い分け、状態を色だけで表さない。
- 720px、980px、1440px で横スクロール、文字切れ、固定要素の重なりを検査する。
- 固定ニュートラル配色と青い主操作色を維持し、テーマ設定や装飾的なアニメーションは追加しない。

## エラーと回復

| 状態 | 表示 | 回復操作 |
|---|---|---|
| ワークフローなし | 自動化をまだ作っていません | 新しい自動化 |
| 実行環境不足 | 必要な実行環境を準備できません | 接続を確認 |
| 入力不足 | 対象欄の直下に理由 | 入力を修正 |
| 実行中 | 現在の工程と経過ログ | 停止、完了を待つ |
| 人の確認が必要 | 落ちた確認と要約 | 編集、再実行 |
| 定期設定を保存したが未反映 | 保存済み・未反映 | 再反映 |
| 定期実行停止 | 自動実行は停止中 | 自動実行を開始 |
| 壊れた結果契約 | 結果を確認できません | ログを見る、再実行 |

## セキュリティ

- すべての automation IPC は agent-app に登録済みの実在 repo を要求する。
- workflow の絶対パス、`..`、`~`、repo 外を指す symlink を拒否する。
- 外部コマンドは shell を介さず argv で起動する。
- renderer から受け取る agent、model、log path、machine ID を信用せず、許可済み一覧と snapshot で照合する。
- ログと入力値を HTML として解釈せず、表示時にエスケープする。
- AI はファイルを直接変更せず、未保存の候補を返し、人が選んで保存する。

## テスト方針

- domain: 正規化、compile、read-back、分岐、入力変数、移植性警告、既存定義保持。
- store: repo 境界、machine ID、atomic save、一覧、読み込み、生成ファイル。
- AI: envelope 検査、修復一回、scope、fingerprint、選択差分の適用。
- recording: browser／Windows の正規化、import、停止、異常入力。
- runtime: agent-loop snapshot、実行、停止、schedule、daemon、history、log path。
- IPC/preload: `api.automation.*` の対応、未登録 repo の拒否、イベントの request ID。
- UI: 主要領域切替、repo 切替、作成、編集、保存、実行、定期設定、要確認、空状態。
- regression: 既存 agent-app の会話、ファイル、差分、worktree、tmux の全テスト。
- smoke: Electron を起動し、作業と自動化の両領域が描画されることを確認する。

## 検討した案

| アプローチ | 実装コスト | リスク | 保守性 | 拡張性 | 学習コスト | UX | 推奨度 |
|---|---|---|---|---|---|---|---|
| A. サイドバーの主要領域としてネイティブ統合 | 中 | 中 | 中 | 高 | 低 | 高 | ★★★ |
| B. `会話 / ファイル` の第 3 タブとして統合 | 中 | 中 | 中 | 中 | 低 | 中 | ★★☆ |
| C. statemachine-maker を別ウィンドウで起動 | 低 | 低 | 高 | 低 | 中 | 低 | ★☆☆ |

A は一般的なエージェントアプリの情報構造に合い、選択中セッションと独立した自動化を混同しない。
B は画面変更が小さいが、セッション内表示とリポジトリ単位の定義が同じ階層になり、ヘッダーの操作も過密になる。
C は実装量が小さいが、リポジトリ選択や実行環境が二重になり、agent-app の一機能として一貫した体験を作れない。

## 既存スキルとの関係

- `brainstorming`: 統合案の比較、過去の設計判断、責務、非目標を確定する。
- `ui-designer`: 主要領域の分離、段階表示、フォーカス、レスポンシブ、回復可能なエラーを補強する。
- `agentic-search`: 一般的なエージェントアプリの現在の情報構造を公式資料で比較する。
- `ltm-use`: statemachine-maker と agent-dashboard の過去の責務分離を再利用し、今回の決定を保存する。
- `webapp-testing`: 実装後の Electron 実機、幅、操作、コンソールエラーの検証に使う。

既存スキル単体でこの統合を代替できるものはない。実装時は変更の境界をテストで固定し、失敗状態から仕上げる。

## 非目標

- agent-app 独自の scheduler、cron evaluator、run journal
- 会話セッションと自動化 run の統合
- 任意 cron、hook、webhook、Ralph、任意 shell command のビジュアル編集
- 分析ダッシュボード、利用量グラフ、コスト集計
- statemachine-maker 独立版の削除
- テーマ、配色、カード外観のカスタマイズ
- GitHub、クラウド、通知機能の新規追加
