## 0. 結論の先出し

- **方向の検討漏れは無い。** 15 本が「決定的ハーネス + 局所判断関数としての E4B」という同じ構図へ独立に収束していて、新規に採るべき打ち手は残っていない。詰まっているのは実行と、文書への反映である。
- **残件は 20 件。** 決定済みで実行だけが残っているものが 14 件、どの計画にも書かれていない穴が 6 件。依存ゼロで今日から着手できるのは 5 件しかなく、残りは前提待ちか実機待ちに並んでいる。
- **最も安いのは案 3（同役割の直列バッチ化）。** モデルもプロンプトも契約も触らないので品質側の再測が要らず、半日で採否が出る。それが 7 日間放置されている。
  **当たった**（§6）——prefill 合計で 3.0 倍差、実装は `pick_claimable` の 3 行。ただし節約は接頭辞ぶんの秒数で固定なので、**効くのは 1 呼び出しが十数秒の判定・抽出系だけ**で、コード仕事では誤差である。「一番安い」という見立ては正しく、「効果が小さい可能性」も半分当たっていた。
- **最も効くのは Phase 1（回数上限の統一・設定化）と T3splitgate の実測。** 前者は外部実測（state-harness の naive cap +35pp）が裏書きする唯一の施策で、後者は (b) 族 0/3 に対して数字が動く可能性のある唯一の腕である。
  **前者は外れた**（§6）。上限を 12 / 3 / 2 で引いても受入は 3 腕とも 0/3 で、+35pp はこの課題 × この層では再現しない。動いたのは壁時計だけ（中央値 600s → 51s）——**上限は品質のレバーではなく、失敗を安くするレバーだった**。外部実測を「裏付けが最も強い」と読んだ判断そのものは間違っていない（測る価値はあった）が、**裏付けの強さは自分の環境での再現を保証しない**。
  **後者は同日に測って当たった**（§6）——`T3splitgate` 3/3 対 `T3gate` 0/3。2026-08-13 以来 0/3 のままだった (b) 族が動いたので、**この一覧のなかで最も価値が上がったのは 08-24 案 IV（分解の機械化）**である。分解が効くかはもう問いではなく、機械が分解を書けるかだけが残っている。
- **塩漬けの構造が 2 つある。** C1（リランカー）は実機待ちの案 B にぶら下がったままで、A2 の再評価トリガは計測する実装が無い。どちらも待っていても永久に判定が出ない形なので、依存を切るか条件を書き換えるかを決める。**どちらも同日に閉じた**が、後者では 3 つ目の詰まり方が出てきた（§6）——集計を足しても入力の receipt が 1 件も来ていない。

## 2. どの計画にも書かれていない穴

### 2.1 A2 の再評価トリガを計測する実装が無い

08-22 §4.3 は、局所修正の適格判定を拒否へ配線しない代わりに「`local_patch_blockers`（観測）で不適格割り当ての頻度を数え、escalate した aider ノードの 1/3 以上が blockers 付きになったら再評価する」と決めた。

ところが数える実装が無い。`local_patch_blockers` は [`work.py:216`](../../tools/agent-flow/agent_flow/work.py) が claim メタへ書き、[`collect.py:840`](../../tools/agent-audit/agent_audit/collect.py) が receipt へ格納するところまでで終わっている。集計する関数も、dashboard の表示も、しきい値を判定する処理も存在しない。つまり保留の解除条件が原理的に発火しない。

副作用がもう 1 つある。同じ決定は「ハーネスの escalate 率は運用値ではなく上限として読む」と宣言したが、その読み替えの妥当性も頻度が分かって初めて確かめられる。いまは上限と実測の距離が誰にも見えていない。

**決めた（2026-08-29）**: 集計を 1 本足した（`agent-audit stats` の「局所修正の適格」節）。しきい値 1/3 に達したら再評価をうながす行が出る。

同時に前提が 1 つ崩れた。**「データは既に貯まっている」は、この機では成り立っていない**——`~/.agents/audit/records/` にあるのは ledger と session だけで、`kind: "result"` の receipt は 1 件も無い（`operation_class` も同様に 0 件）。つまりトリガは実装しても当面 0/0 のまま回る。集計側は 0/0 を「問題なし」と読ませない形（`samples` が 0 なら発火しない・出力に「材料がありません」と書く）にしてあるが、**発火させたければ先に flow の run を collect させる必要がある**。

もう 1 つ、receipt の側に「escalate」という状態が無い（flow の result status は done / failed の 2 値）。分母は **done しなかった aider ノード**と読み替えた。落ちたノードは再試行の梯子で上位候補か人へ回るので、08-22 の言う escalate と同じものを指しているが、読み替えであることは集計の docstring に書いた。

### 2.2 aider の interactive 定義が 08-11 設計の却下案と衝突している

`agents/aider.json` は `interactive` を持っている。中身は `agent-herd aider --tui` で、段 12（対話面の共通 TUI 統一）で入った。

[08-11 の tmux ハーネス設計](2026-08-11-agent-dashboard-routine-aider-tmux-harness-design.md)は「aider に偽の `interactive` 定義は追加しない」を本文の「変えないこと」と Decision Record の却下案に二重で書いている。理由は「素の対話 aider はスキル読込とコマンド実行を持たないのでステートマシンを完遂できない」ことだった。共通 TUI はツールループを外から与えるので、この反対理由はもう当たらないはずである。

問題は文書側で、08-11 を読んだ人はいまも「aider の interactive は禁止」と受け取る。

**決めた（2026-08-29）**: 08-11 の「変えないこと」と Decision Record の却下案の両方へ、却下対象は素の aider ペインへプロンプトを送る形であり、共通 TUI 経由の `interactive` は反対理由が当たらないことを書いた。

### 2.3 パッチモードをめぐる判断が 3 か所に分かれている

同じ問い（aider の SEARCH/REPLACE を機械適用型の編集に置き換えるか）に、3 つの文書が別々の根拠で答えている。

[08-10](2026-08-10-agent-ollama-quality-and-role-refit-proposals.md) §4.2 は取り下げた。「消える故障モードは corruption だけで、打ち切りの原因だったロジックの誤りは残る」。[08-24 radical ideas](2026-08-24-aider-gemma4-generalization-radical-ideas.md) 案 II は再提案した。「E4B は構造化に強く、編集だけが自由文プロトコルに残っている」。そして未決 5 が実際に対照実装（`agentcore/editagent.py`）を書いて実測し、aider を外さないと決めた。失うのは曖昧一致の階段ではなく編集プロンプト約 6.3 KB のほうで、T4 が 3/3 から 0/3 へ落ちた。

3 つとも妥当な判断だが、相互参照が無いので次に読む人は同じ検討を 4 回目から始める。

**決めた（2026-08-29）**: 08-24 の案 I / II / VI を実測結果つきで閉じ、§9 の実行順序表を残り 3 段（案 III → IV → V）へ改めた。案 VIII（ハーネス・レース）は 2 本目のハーネスが立たなかったので不成立として同じ表に残した。08-10 §4.2 の却下記録からも 08-24 の再提案と今回の実測を指して、往復を閉じた。

### 2.4 context_slice が Python 限定であることの扱い

`agentcore/context_slice.py` は標準ライブラリの `ast` を使う。install.sh のオフライン完結を壊さないための判断で、それ自体は妥当である。08-22 §4.1 も「他言語が要るのは Python で効くと分かってから」と書いた。

効くことは分かった（tokens −72〜87%・壁時計 −83%・受入同等）。それでも非 Python の扱いはどの計画にも書かれていない。いま非 Python のファイルを渡すと原本へ倒れるので、最大の実測資産が言語ごと丸ごと消える。倒れた事実は receipt に残るが、それを見て何をするかが決まっていない。

**決めた（2026-08-29）**: **Python 限定と明記する。** 他言語のパーサは install.sh のオフライン完結（標準ライブラリだけで入る）を壊すので、言語を増やさない。非 Python は原本へ倒れ、`unsupported-language` の receipt が残る——安全側に倒れるので、失うのは経済の取りこぼしだけである。08-22 §4.1 の「まず Python / JS」は、当時 Python でも効くか未証明だった前提で書かれていた。効くと分かったいま、判断材料は「JS の適格ノードがどれだけあるか」へ変わり、それを測る receipt がまだ無い——**依存を先に増やさない側に倒す**。再評価の条件は、非 Python の fallback が適格ノードの相当割合を占めると receipt で分かったとき。記録は 08-27 案 B と 08-22 §4.1。

### 2.5 探索の決定化に別解が 2 つあって調停されていない

同じ穴（対象ファイルが計画時に決まっていない task を局所化する）に、2 つの提案が別の解を出している。

レビュー P3 は「編集対象の import とシンボルから決定的に rg パターンを導出し、ヒット周辺のチャンクを読み材料へ事前割付する」。08-24 案 III は「シンボルカードを ast で索引化し、bge-m3 で候補検索して機械検算で確定する」。どちらを採るか、順序をどうするかを書いた文書が無い。レビューは 08-24 radical ideas を参照リストにすら入れていない。

**決めた（2026-08-29）: 案 III が先。ただし前提が 1 つ間違っていた——2 つは同じ穴に対する別解ではない。**

P3 は rg パターンを「**編集対象の** import とシンボルから」導出する。つまり**編集対象が既に決まっている**ことが前提で、置き換えるのは「決まった対象の周辺をモデルが read toolset で自走して探す」ところである。案 III の 1〜3 は、その手前——自然文の task から対象ファイルを確定する段——を埋める。**P3 は案 III の下流**であり、競合していない。

したがって「両方作らない」は誤りで、正しくは:

1. **案 III を先に作る。** 対象が決まっていない task は、いまは入口で不適格になる。ここを開けないと P3 の前提（対象が決まっている）に届かない task が残り続ける。新規実装はシンボルカード生成だけで、検索（bge-m3・B4 で受入基準達成）・検算（C2 実測でパス 3/3・テスト名 3/3・捏造 0）・スライス（実装済み・B2 で本番配線も済）は全部ある。
2. **P3 は自分の測定ゲートの後ろに置いたままにする。** レビュー自身が「(2) read toolset の探索ラウンド消費を eval ログで確定してから、(3) 消費が小さければ閉じる」と書いている。**測って閉じる可能性のある案**なので、先に作らない。

A2 の結果もこの順序を支持する。(b) 族が分割で動いた（§6）ことで 08-24 案 IV の価値が上がり、案 III は案 IV が扱う task の供給源にあたる。

### 2.6 C1（リランカー）が実機待ちの案 B にぶら下がっている

08-22 §4.2 C1 は「ollama に rerank の口が無い」という制約を根拠に保留され、「案 B（ランタイム）が通ればこの制約自体が動く」ので案 B の副次的な判定材料として並べた。

案 B は 23 日間動いていない。iGPU のある実機が要るので、待っていて自然に解決する類ではない。結果として C1 は「保留の保留」になっている。

**決めた（2026-08-29）**: 案 B から切り離し、**測らずに閉じた**。段構えが受入基準を満たしていて上積みの動機が弱く、費用（別モデル種別・1 クエリ数十秒の代用）に見合う取りこぼしも観測されていない。復活の条件は「段構えが落とす問いが実運用で出ること」で、ランタイムの都合ではない——同じ塩漬けへ戻さないために、解除条件をランタイムから切り離してある。記録は 08-22 §4.3 の C1 行と [ltm-use 設計の「やらないこと」](../designs/ltm-use-embedding-recall-design.md)。

## 5. 変わらない規律

- checker の無い自己申告完了を受け入れない。どのハーネスでも同じ。
- model / harness / policy / sampling を同時に変えない。腕は 1 軸ずつ、条件は台帳へ。
- `3/3` は存在の証明であって成功率 100% の推定ではない。率として読むなら n ≥ 10。
- 完成候補が回数制限のみの arm に勝たなければ、複雑な仕組みを採用しない（制限付き実行案 §6）。state-harness の外部実測が独立に同じ結論へ達している。

1. 塩漬けの 2 形（実機待ちにぶら下がる / 解除条件を測る実装が無い）は、どちらも
   「待ち先を切る」だけでは終わらなかった。C1 は切って閉じられたが、穴 2.1 は集計を
   足しても**入力が来ていない**という 3 つ目の詰まり方が出てきた——観測を配線した日に、
   その観測が実際に貯まっているかまで確かめていなかった。
2. **「実機待ち」も同じ疑い方をすべきだった。** C3（e2b 級サブモデルの arm）は
   「モデル取得待ち」として実機待ちの表に置いてあったが、`gemma4:e2b` はこの機に
   pull 済みだった。待ち物の有無を、文書ではなく実物で確かめる。
3. **1 本の実測が一覧の重み付けを変える。** A2（壁時計だけで済む腕）が当たったことで、
   08-24 案 IV は「効くか未知の案」から「効くと分かっている案の自動化」へ変わった。
   安い実測を先に引く順序は、それ自体が正しかった。
4. **外部実測は方向を教えるが、値は教えない。** 本書は A1 を「外部実測が裏書きする唯一の
   施策」として最優先に置いたが、引いてみると受入は動かず壁時計だけが動いた。
   **裏付けの強さは自分の環境での再現を保証しない**——だから測る、という順序は正しく、
   「裏付けがあるから入れる」で飛ばさなかったことがこの日の収穫でもある。
5. **観測を足すと、その日のうちに効く。** B6 で台帳へ `argv` を入れた直後、
   worker_eval のヘッダが**実行しない argv**（腕で差し替える前の定義値）を出していると
   気づけた。観測は「後で効く投資」ではなく、次の測定を守る道具である。
6. **実装の前に前提だけを測ると安い。** A3 はスケジューラの消化順を触る案だったが、
   前提（接頭辞キャッシュが効くか）だけを測る道具を先に書いたので、**成り立たなければ
   1 行も書かずに閉じられる**形になった。成り立ったので実装は 3 行で済んだ。
   「測って駄目なら捨てる」は、捨てる先を実装ではなく**前提**に置くと一番安い。
7. **測定道具そのものが 2 回間違えた。** (a) `prompt_eval_count` でキャッシュを判定しようと
   したが、当たっても数は落ちない。(b) 片方の接頭辞しか温めずに測り、初回 prefill を
   測定窓の中に入れて結論を反転させた。**道具を書いた直後の数字は、道具を疑う材料として
   読む**——どちらも「数字が予想と違う」ではなく「数字の出どころが変」で気づいた。
