# 設計・実装に合わせたテストの自動保守（提案）

- 日付: 2026-10-25
- 状態: 実装済み。既存の JSON/YAML の保守を拡張し、独立した入力変換・結果変換と実行例を追加した。
- 2026-10-26 変更: 入力変換（gherkin-cases）と結果変換（test-evidence）は testcase-lint に統合した（`.feature` の直接点検と `testcase-lint run`）。
  対応表・実行結果の形式と codd-agent 側は変えていない。経緯は [testcase-lint 設計](../designs/testcase-lint-design.md) にある。
- 目的: testcase-lint と codd-agent を独立した道具のまま使い、設計・実装の変更に応じて単体・API・E2E テストを追加・更新する。
- 前提: Cucumber/Gherkin、特定の言語、特定のテストランナーを必須にしない。

## 1. 役割と境界

| 担当 | 受け持つこと | 受け持たないこと |
|---|---|---|
| testcase-lint | ケースの曖昧さ、条件・期待結果、重複・矛盾、読み取れる仕様との整合を決定的に点検する | LLM による生成、テストコードの実装、テストの実行 |
| codd-agent | 変更の意図と根拠を読み、影響範囲を測り、ケース・テストコード・設計・実装を保守する | 各ランナーの構文や設定を本体に組み込むこと |
| プロジェクト側の設定・変換処理 | 実際のテストコマンド、個別テストの識別、ランナーの結果を共通の実行結果に変換する | 変更した仕様の正しさを決めること |

両ツールの本体は互いの名前や作業フォルダを知らない。組み合わせはプロジェクト側のコマンド・手順で行う。
Gherkin は必要なプロジェクトで入力として変換できるが、共通の中間表現にも実行条件にも採用しない。
自然文を任意の言語のテストへ機械的にコンパイルする仕組みは作らず、コード生成は既存のプロジェクトの書き方を読んだエージェントが行う。

## 2. 現状と追加するもの

根拠:

- [testcase-lint 設計](../designs/testcase-lint-design.md): LLM を使わない JSON/YAML の検査、独立性、共通形式の結果出力がある。
- [codd-agent 設計 §4.2・§4.3](../designs/codd-agent-design.md): 響くテストの検出、テスト変更計画、振る舞いとテストの対応、実行結果、変更前の実装での再現確認がある。
- [ケースの推奨スキーマ](../../tools/testcase-lint/schema/testcase.schema.json): ID・要件・条件・前提・手順・期待結果がある。実行先のフィールドは現在含まれない。

主な追加対象は、ケースと実際のテストとの明示的な対応、ケース単位の実行確認、変更理由に基づくテストの追加・更新判断である。
現在のファイル名・文字列による影響検出は候補探しに活かし、明示的な対応があるときはそれも使う。

## 3. 意図・対応・結果を分ける

### テストの意図

業務・契約としての条件と期待結果は、既存の JSON/YAML ケースで表す。
単体テストのために画面操作を書く必要はなく、操作には関数呼び出しや API リクエストも使える。
ファイル内で一意の既存 ID はそのまま使い、外から参照するときはリポジトリ・ファイル・ID の組で特定する。

```yaml
feature: 送料計算
cases:
  - id: SHIP-01
    title: 商品合計5000円の注文は送料無料になる
    requirement: REQ-12
    conditions: { 商品合計: 5000, 配送先: 東京都 }
    steps:
      - 商品合計5000円、配送先「東京都」の注文の送料を計算する
    expected:
      - 送料は0円になる
```

### 実際のテストとの対応

プロジェクト側に置く対応情報の例。
専用の実行構文は持たず、selector はプロジェクトの変換処理だけが解釈する文字列にする。
最初の実装では JSON を使う。codd-agent が Python 標準ライブラリだけで読めるようにするためである。

```json
{
  "version": 1,
  "bindings": [{
    "case": {"file": "tests/cases/shipping.yaml", "id": "SHIP-01"},
    "targets": [
      {"suite": "unit", "file": "tests/shipping.test.ts", "selector": "shipping/free-at-5000"},
      {"suite": "e2e", "file": "e2e/checkout.spec.ts", "selector": "checkout/free-shipping"}
    ]
  }]
}
```

- 1 ケースに複数のテストを対応させても、1 テストで複数のケースを確かめてもよい。
- 全単体テストに自然文ケースを要求しない。業務条件・公開契約など、追跡したいものから対応を持つ。
- fixture、mock、ブラウザの locator、起動方法は既存テストやプロジェクト側の手順に置く。
- testcase-lint の本体はこの対応ファイルを必須にしない。対応検査も、利用時に選べる独立した検査とする。
- ランナーの設定を推測できても、実行可能とみなす前に収集・実行で確認する。

### 実行結果

既存の evidence の役割を活かし、必要に応じて実行単位とケースへの対応を表せる契約を追加する。
共通契約の仕様と適合例は公開し、利用側はその形式を実装するだけにする。両ツールを同時に導入させる依存パッケージは作らない。

必要な意味は、実行 ID、対象コードとケースの版、suite、個別テスト ID、対応ケース、テストファイル、合否である。
鮮度は実行 ID と入力の識別値で確認し、時刻だけには依存しない。
作業中の変更も扱うため、HEAD だけでなく入力のハッシュ等で実行対象を識別する。複数リポジトリではそれぞれの版を持つ。
フィールドの追加・形式の版管理・旧版の扱いは、既存の読み手と書き手を確認し、§9 のとおり決めた。

重要な境界として、**lint の合格と、対象の振る舞いをテストして通った結果を区別する**。
現在の [lint 結果の出力](../../tools/testcase-lint/src/evidence.js) は、ファイルの点検結果も `kind: behavior` で出す。
[codd-agent の結果読取](../../tools/codd-agent/machine/codd.py) は `behavior` とファイルの対応を使うため、
ケースの点検結果を実行結果に混ぜる構成では、点検の成功を実行の成功として扱う余地がある。
lint/check と execution の目的を識別し、実行確認には execution だけを使う。既存形式の変更は互換性を考慮して移行する。
未知の合否、古い実行、別の版の結果、未対応の結果を成功として扱わない。

## 4. 変更時の流れ

1. 設計・実装の差分と依頼から、変える振る舞い・維持する振る舞い・根拠を挙げる。食い違いを実装に合わせて自動解消しない。
2. 既存の対応情報と影響検出で関連ケース・テストを探し、追加・更新・削除・変更不要を判断する。
3. 設計変更ならケースの期待結果を更新する。実装だけのリファクタなら期待結果を維持し、必要なテスト構造だけを変える。
4. ケースを testcase-lint で点検する。指摘の解消に仕様上の判断が必要なら、期待結果を推測して埋めない。
5. 既存のテストの書き方に合わせて、必要な層のテストコードと対応情報を追加・更新する。
6. プロジェクトに設定したコマンドで実行し、今回変更したケースに対応する個別テストの結果を確認する。
7. 不具合修正では、新しいテストが修正前の実装で意図した理由で落ち、修正後に通るかを確かめる。
8. どの仕様・ケース・テストを変え、何を実行し、何が未確認かをまとめる。

これは codd-agent の既存の plan/apply/verify を拡張する案である。無人実行や承認方針の変更は別の要件として扱う。

## 5. 単体・API・E2E をどう選ぶか

| 確かめる対象 | 主に使う層 |
|---|---|
| 計算・境界値・分岐・ドメインの状態遷移 | 単体 |
| HTTP 契約・永続化・認可・サービス間の接続 | API・結合 |
| 利用者の操作から結果までの重要な経路 | E2E |

層の名前・選択方針・利用できる実行環境はプロジェクト側で設定する。
5000 円の境界値は単体で広く確かめ、購入画面に送料が反映される経路を E2E で確かめるなど、責務を分ける。
全ケースに単体と E2E の両方を要求しない。画面の無いプロジェクトにブラウザ E2E を要求しない。

## 6. 自動更新の判定

| 変更 | ケース・期待結果 | テストコード |
|---|---|---|
| 仕様に基づく振る舞いの変更 | 根拠と変更前後を残して更新 | 新しい条件を検証するよう更新 |
| 振る舞いを変えないリファクタ | 維持 | 必要なら fixture・import・呼び出し方を更新 |
| 不具合の修正 | 正しい期待結果を維持・不足例を追加 | 再現するテストを追加 |
| 仕様からの機能削除 | 根拠を残して廃止 | 対応テストを削除・更新 |
| テスト実行の失敗 | 失敗した事実だけで期待値を変更しない | 原因を調べ、計画した意図との整合を確かめる |

テストの削除・skip・期待値の変更を「コマンドが通った」だけで承認しない。
現在の codd-agent には失敗後のテスト変更を止める仕組みがある。まずその仕組みを維持し、
最初から計画した仕様変更によるテスト更新と、失敗後に期待値を合わせる変更を区別する。
より自律的な修復を認める場合も、仕様根拠・変更した期待結果・対象テストを事前の計画と照合する。

## 7. 実装する順序

1. lint/check の結果と execution の結果を区別する契約・互換性方針を決める。
2. 既存ケースをそのまま使い、ケースと個別テストの対応情報を任意で置けるようにする。
3. codd-agent で対応情報を影響検出・計画・実行確認に使う。未対応プロジェクトは従来どおり動かす。
4. プロジェクト側に単体 1 種と E2E 1 種の結果変換例を置き、共通契約への適合を確認する。
5. 異なる言語・ランナーのサンプルでも、本体の変更なしで使えることを確認する。
6. 上記が成立したあと、独立した Gherkin の入力変換を追加する。Cucumber による実行やステップ定義の保守はその次とする。

受け入れ条件:

- Cucumber/Gherkin を導入せず、仕様変更からケース・単体テスト・必要な E2E を更新できる。
- ランナー固有の構文や相手ツールの名前を本体に追加せず、プロジェクト側の設定・変換処理だけで利用先を増やせる。
- ケースの lint 成功、ファイル内の別テストの成功、全 skip、過去の結果では、変更したケースの実行成功にならない。
- リファクタで期待結果が変わらず、仕様変更の根拠がない期待値の書き換えを検出できる。
- 対応情報や結果変換をまだ持たないプロジェクトも、従来の機能を利用できる。未確認の範囲は明示する。

「どんなプロジェクトでも使える」は、すべてを無設定で自動化する意味ではなく、
本体を変えずに、そのプロジェクトのコマンド・手順・結果変換を接続できる意味とする。

## 8. 既存実装への変更点

以下の名称と設定を追加した。利用手順は両ツールの README と独立した変換ツールの README に記す。

| 箇所 | 変更案 |
|---|---|
| `tools/testcase-lint/src/load.js` | JSON/YAML の既存読取は維持する。後続段階で入力元の位置情報を一般的な形で保持する |
| `tools/testcase-lint/src/report.js` | JSON 出力に正規化済み `cases` を追加する。現在は要約と指摘のみである |
| `tools/testcase-lint/src/evidence.js` | ファイルの点検結果に `purpose: check` を追加する。既存 ID・件数・合否は維持する |
| `tools/testcase-lint/schema/testcase.schema.json` | 後続段階で任意の入力元情報を許容する。既存ケースに新しい必須項目を増やさない |
| `tools/codd-agent/machine/codd.py` の設定読取 | 任意の `test_bindings` を受ける。未指定は空として従来の動作を維持する |
| 同ファイルの `affected_tests` | 既存の文字列・パス・グラフに加え、対応表からケースとテストを双方向にたどる |
| 同ファイルの `verify_plan_text` / `tests_plan_problems` | 関連ケース・テストを追加・更新・削除・変更不要のいずれかで計画に挙げたかを確認する |
| 同ファイルの `evidence_rows` / `behavior_result` / `unrun_problems` | 点検結果と実行結果を区別し、未知の status を成功と数えない |
| 同ファイルの `run_checks` / `cmd_verify_apply` | 実行 ID を発行し、対応する個別テストの今回の結果を検証する |
| `tools/codd-agent/machine/actions/plan.md` / `apply.md` と計画テンプレート | ケースと各層のテストを選ぶ手順、期待結果の変更根拠を明記する |
| 両ツールの README・設計書・既存テスト | 任意機能の設定、移行、保証の範囲を説明し、互換性を検証する |

testcase-lint が codd-agent の設定を読む変更は入れない。
codd-agent が YAML ケースの内部や Gherkin のキーワードを解釈する変更も入れない。

### 設定の例

```json
{
  "side": "impl",
  "refs": [{"name": "docs", "path": "../my-app-docs"}],
  "test_bindings": ["tests/test-bindings.json"],
  "test_catalogs": ["results/cases.json"],
  "test": {
    "unit": ["npm", "run", "test:unit:evidence"],
    "e2e": ["npm", "run", "test:e2e:evidence"]
  },
  "check": ["testcase-lint"],
  "evidence": ["results/unit.json", "results/e2e.json", "results/case-check.json"]
}
```

`test` の名前は報告用の既存機能を使う。結果の `suite` はプロジェクト側が書く値と対応表で照合する。
`test_bindings` のパスはプロジェクトルートからの相対とし、既存の設定読取方式に合わせて文字列または配列を受ける。
`test_catalogs` は任意の正規化した JSON のケース一覧を受け、変更が響くケースファイル内の追加ケースや ID の対応漏れを調べる。
一覧が無いプロジェクトでは明示した対応の実行だけを確認し、未登録のケースの完全性は主張しない。
対応先のファイルは、その側の `tests` が扱うパスに含める。任意の配置は `tests` を設定して扱える。

`case.side` を省略したときは対応表と同じ側とし、別リポジトリのケースは `"side": "docs"` のように明示する。
参照先の名前は利用側の設定に属するため、独立した結果変換に固定しない。共通結果では利用側が渡した側の識別子を使う。
同じファイル内での ID 重複、空の selector、存在しない側、リポジトリ外へのパス、壊れた対応表は設定エラーとする。
これから追加するテストは計画に存在すれば許容し、適用後には実在を要求する。

対応の削除やケースの廃止も変更として計画に残す。適用後だけを読んで消えた対応を見落とさないよう、変更前の対応表とも比較する。
最後の対応を廃止するときは `bindings: []` のファイルを残す。対応表ファイルの除去と機能の無効化は設定の変更として別に扱う。
実行すべき対象を減らす操作を、対応表を空にするだけで黙って通さない。

## 9. 共通結果の契約と互換性

既存の `version: 1` の items 形式へ、任意の項目を追加する案とする。
新しい厳密な実行確認は、この追加情報を持つ結果だけを対象にする。

```json
{
  "version": 1,
  "purpose": "execution",
  "run_id": "実行側が発行した今回限りの値",
  "inputs_digest": "対象のコード・ケース・設定の版を識別する値",
  "root": "..",
  "items": [{
    "id": "shipping/free-at-5000",
    "kind": "behavior",
    "suite": "unit",
    "file": "tests/shipping.test.ts",
    "status": "passed",
    "test_sha256": "実行したテストファイルのSHA-256",
    "cases": [{
      "side": "",
      "file": "tests/cases/shipping.yaml",
      "id": "SHIP-01",
      "sha256": "実行の前に読んだケースファイルのSHA-256"
    }]
  }]
}
```

- ルートの `root` は従来どおり結果ファイルからの相対。ケースの `file` は `side` が示すリポジトリからの相対とする。
- `cases` は配列にして、1 テストが複数のケースを確かめる対応も表現する。`item.id` は selector と完全一致で照合する。
- `kind: behavior` は従来の合否表示のために維持する。`purpose: check` は点検、`purpose: execution` は実行を表す。
- 合否は `passed` / `failed` / `skipped` のみ。未知の値は不正な結果として扱う。同じ対象について矛盾する重複結果も成功にしない。
- 実行 ID と入力の識別値は、テスト前に実行側が発行する。たとえば `TEST_EVIDENCE_RUN_ID` / `TEST_EVIDENCE_INPUTS_DIGEST` という一般的な環境変数で渡す。
- 入力の識別値には各リポジトリの作業中の変更を含める。既存の `snapshot` / `stamp` の再利用可否を確認し、生成される結果やキャッシュは除く。
- 変換処理は実行前に入力のハッシュを控える。終了後に変更されていれば、その結果を当該入力の証拠として採用しない。
- 結果ファイルの更新時刻だけで鮮度を判断しない。古いレポートのコピーや更新時刻の変更で通らないようにする。
- ランナーの終了コードが 0 でも、要求した selector が無い、全 skip、別 suite、入力の版違いなら未確認として止める。

これは正しいアサーションが書かれていることまで証明する契約ではない。
エージェントが任意に生成した「成功」の JSON を証拠としないよう、結果はプロジェクトが管理するランナー・変換処理から得る。
不具合修正では既存の修正前実装による再現確認を併用する。

### 移行順序

1. 読み手が `purpose` と既知の status を扱えるようにする。既存の文書への結果の写しは維持する。
2. 点検ツールの書き手に `purpose: check` を付ける。既存 ID と `kind` は変えない。
3. 任意の実行変換を導入し、個別テストの対応がある範囲だけ厳密な確認を有効にする。

`purpose` の無い旧結果は従来の報告に利用できるが、対応表を使う新しい厳密な確認の証拠にはしない。
対応表を導入していないプロジェクトに、新しい結果形式や変換処理を必須にしない。

## 10. Gherkin は独立した入力変換として追加する

第 1 段階の JSON/YAML による自動保守と結果照合が成立してから追加する。
初版は独立した変換コマンドとし、公式パーサーへの依存はその変換ツールだけに置く。
両ツール本体の必須依存・任意依存に Gherkin のパーサーや Cucumber の実行エンジンを追加しない。

```text
JSON / YAML ──────────────────→ 共通のケース表現 → lint・変更計画
.feature → 任意の入力変換 → JSON ─┘
```

変換コマンドは既存の load.js が読めるケースを出す。出力先やコマンド名はプロジェクト側で設定し、codd-agent の本体に固定しない。
`.feature` を直接 testcase-lint に渡す機能は初版では必須にせず、必要なら後続で一般的な入力アダプターの仕組みとして検討する。
現在の「given / when / then の項目名を JSON/YAML で受ける」機能と、`.feature` の構文を読む機能は別である。

| Gherkin の要素 | 共通表現への対応 |
|---|---|
| Feature / Rule | ケースのグループ |
| Scenario | 1 ケース |
| Given / When / Then | 前提 / 手順 / 期待結果 |
| And / But | 直前のステップの意味を継承 |
| Feature / Rule の Background | 適用される各ケースの前提・手順へ展開。操作や期待結果も黙って前提に変えない |
| Scenario Outline / Examples | 例の行ごとに値を展開した独立ケース |
| DataTable / DocString | 所属するステップの値として保持 |
| Tags | グループからの継承も含めたメタデータ。要件タグ・ケース ID の規約は変換側が扱う |

公式パーサーとその展開処理を使い、多言語キーワード・エスケープ・Rule の適用範囲を自作の正規表現で再解釈しない。
未対応の構文や曖昧な意味を黙って捨てず、変換エラーまたは診断として示す。

### ID と入力元の維持

- 通常のシナリオには `@case:SHIP-01`、要件には `@requirement:REQ-12` などの明示的な規約を用意する。
- Outline は `Examples` の `case_id` 列を推奨する。行の挿入・並べ替えで ID が変わらないようにする。
- ID の無い既存資産も読み取れるが、生成した ID の安定性は明示する。厳密な実行結果との対応には明示 ID を推奨する。
- 出力ケースには一般的な入力元情報 `origin` を任意で持たせ、元ファイル・シナリオ行・例の行・各フィールドの行を保持する。
- testcase-lint の共通読取はこの位置情報を使って元ファイルへの指摘を返す。Gherkin のキーワードには依存しない。
- 対応表と結果照合には元ファイル・展開済みケース ID を使う。生成 JSON の配置が変わっても別ケースとして扱わない。

この位置情報を追加する際は、推奨スキーマの許容項目と load.js のメタデータ処理を合わせて変更する。
未知の項目を前提として扱う現状の処理に origin を流し、その内容でケース比較が変わらないようにする。

### 自動更新の範囲

変換した JSON は生成物として再生成する。エージェントは仕様の正本である `.feature` と実際のテストコードを保守する。
生成 JSON を手で直し、元の `.feature` と別の期待結果を持たせない。
コメントや既存の記述を保つため、初版では AST 全体からの書き戻し・整形・双方向同期を導入しない。

Cucumber を使うプロジェクトは独立した実行変換を足して結果を共通形式へ渡せる。
pytest、Jest、Playwright などのテストを保守するために、Cucumber のステップ定義を作る必要はない。

## 11. 段階ごとの検証と完了条件

| 段階 | 実装する範囲 | 主な検証 |
|---|---|---|
| A: JSON/YAML の自動保守 | 対応表、影響検出、計画と更新手順、点検と実行の区別、個別結果の照合 | 仕様変更で期待結果と必要なテストが変わる。リファクタでは期待結果が維持される |
| B: 利用先の独立性 | 単体と E2E の結果変換例、別言語の利用例 | 本体を変更せずランナーを入れ替えられる。Cucumber/Gherkin 未導入で A が動く |
| C: Gherkin の入力変換 | `.feature` からの展開、明示 ID、入力元の位置情報 | 日本語・英語、Background、Rule、Outline の複数行、DataTable、DocString、構文エラー |

段階 A の必須の失敗ケース:

- lint 合格だけがある。
- 同じテストファイル内の別の selector だけが成功した。
- 必要な単体または E2E の suite が実行されなかった。
- 全 skip、未知の status、矛盾する重複、結果が 0 件だった。
- 古い実行 ID、古いコード・ケース・テストの版、別リポジトリの結果だった。
- 新規ケースに対応が無い、対応表に存在しないファイルが残る、廃止した対応が黙って消えた。
- 計画にない期待値変更やテスト削除で成功させようとした。

未対応の旧プロジェクトは既存のテストで互換性を確認する。
段階 C では、等価な YAML と Gherkin から同じ条件・操作・期待結果が得られること、
例の行を並べ替えても明示 ID が変わらないこと、指摘が生成物ではなく元の行に戻ることを確認する。

## 12. 今回の範囲外

- Cucumber のステップ定義・hooks の生成と保守。
- 全言語・全ランナー向けの変換処理の同梱、全テストの完全な意味理解。
- Gherkin と任意の自然文仕様・JSON/YAML の双方向同期。
- 無人実行、既存の承認方針の変更、対応表だけからの正しさの保証。
