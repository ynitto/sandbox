# agent-ollama の品質再点検 — 改善して残す範囲と、引き受けない範囲

> 作成 2026-08-10（同日改訂: worker のコード生成検証の打ち切り判断と、その波及を反映）
> 対象: `agentcore/ollama_*.py`・`agents/ollama{,-json,-read}.json`・agent-flow / agent-project の役割割当
> 関連: [`agent-herd-design.md`](../designs/agent-herd-design.md)（正典）/
> [`2026-08-08-agent-ollama-expansion-design.md`](./2026-08-08-agent-ollama-expansion-design.md) /

> 前提: マシンは現状のまま（スペックアップ無し）。モデルは qwen3.5:9b を既定とし、変更は可。

指摘されている 3 症状——**暴走によるターンの食いつぶし・空応答・生成物の品質劣化**——を
台帳と実装の実測へ突き合わせ、「改善して使い続けるか、違う用途へ回すか」を決める。

## 0. 結論の先出し

**二者択一にしない。** 3 症状を真因で割ると、答えが症状ごとに違う。

- **空応答は解決済み。** 真因は 2 つとも特定・修正済みで（think×format の衝突、
  JSON 契約役割の振替漏れ）、再発面は残っていない（§1）。追加の手当は不要。
- **暴走は半分だけ解決済み。** planner の write 誤配と think on ループは塞がったが、
  「規約内のコマンドを出し続けながら仕事が進まない」空回りを検知する口が**無い**。
  ここは改善で塞ぐ（§2）。小さい改修で、節約先としての価値がそのまま残る。
- **品質劣化は用途起因。** 1 発判断（text→text / JSON）では完走が成立し、ツールループの
  work と自然文基準の verify では成立していない——これはモデルの調整で埋まる差ではなく、
  引受範囲の間違いである。**用途を絞ることが最大の品質改善**（§4）。

**改訂で足した判断が 2 つある。** worker としての単一コード生成検証が「改善余地なし」で
打ち切られた事実を受けて:

- **生成系は取り下げる**（§4.2）。パッチモード（段 4・5）は救済策にならない——消える故障
  モードは「ファイルを壊す」だけで、打ち切りの原因である「ロジックが誤っている」は残る。
- **残す側も品質は 1 件も測っていない**（§3）。測れているのは完走性だけであり、その測定
  手段として設計が指名した**オフライン再生（expansion §10.3）は参照だけで存在しない**。
  以降のあらゆる検証の前提条件がここで欠けている。**最優先はハーネスの実装**。

つまり位置づけは「コスト 0 の節約先」のまま維持し、(1) ループへ無進捗検知を足し、
(2) 品質を測る道具を先に作り、(3) 引受範囲を「1 発判断 + read 調査」へ固定し、
(4) 生成系はクラウドへ返す。モデル変更は症状対策ではなく、別モデル**種別**まで含めた
条件付きの投資に置く（§6）。

## 1. 3 症状の真因分解 — どこまで手当済みか

| 症状 | 実測（出典） | 真因 | 手当の状態 |
|---|---|---|---|
| 空応答 | plain・think on・format json で本文空 39/39（expansion §4.2） | 文法制約が thinking チャネルの 1 トークン目から掛かり、答えが丸ごと思考側へ出る | **済**: think off + format json へ固定、`_payload` で format 優先（`test_format_wins_over_think`） |
| 空応答 | JSON 契約役割が制御語だけ返して heal ループ（expansion §4.3 改訂） | 一括 CLI 切替時に素の定義で呼ばれ、`json_variant` 振替が効かない | **済**: 振替を既定の挙動へ格上げ |
| 暴走 | 契約どおりの JSON を返すのにループ側が蹴り、30 ラウンド空回り × 4 run（expansion §5.2 改訂） | 読まない系役割への write 誤配（`--tools bash` が生える） | **済**: planner / evaluator の readonly 既定化 |
| 暴走 | tools・think on: 中央値 497 秒・p90 942 秒・600 秒超 21 件（expansion §4.2） | ラウンドごとの長考が品質に変換されない | **済**: write 側 think off（中央値 245 秒・600 秒超 0 件へ） |
| 暴走 | verifier 600 秒 × 3 回タイムアウト → 全基準 inconclusive → 人が再開してまた 90 分（settlement §1） | 自然文基準の verify が 9B の能力を超えており、時間を増やしても決着しない | **未**: §2.3・§4.2 |
| 暴走 | （構造上の穴）`max_rounds=30` × `command-timeout 900` を空回りで完走し得る | 無進捗検知が decode stall（180 秒）だけで、**ラウンド粒度の空回りを見ていない** | **済**（2026-08-10 実装）: §2.1・§2.2 |
| 品質劣化 | 思考 7700 トークン・12 分の末に if 本体が空の構文エラー（design §2） | ツールループの実行役に長考が効かない | **済**: write 側 think off |
| 品質劣化 | 偽 done・自己承認・パス捏造・タスク誤読（efficiency-plan・2026-08-09 品質診断） | work / 検証役としての能力不足 + 規律プロンプトの欠如 | **一部**: 封筒・機械検証は済。規律は手法パック（§5.2）、引受範囲は §4 |

R2 は「失敗検知の主役は経過時間でなく無進捗に置く」と宣言しているが、現行の無進捗検知は
トークン生成の停滞（decode stall）だけで、**トークンは出続けるのに仕事が進まない**形——
同じコマンドの再発行、同じエラーへの同じ対処——はどの層も検知しない。指摘の「暴走」の
残り半分はここにある。

## 2. 改善 — 暴走の残る穴を塞ぐ 3 本

### 2.1 ラウンド粒度の無進捗検知（`no_progress`）— 実装済み

直近ラウンドの `(command, exit_code, 出力ハッシュ)` を覚え、同じ組が連続 N 回
（`_MAX_REPEATS` = 3）並んだら `no_progress` で停止する（`ollama_loop.run_loop`）。

- 終了状態の語彙へ `no_progress` を 1 語足す。封筒 `{"ok": false, "issues": [...]}` と
  `@agent-note` は既存契約のまま（呼び出し側の判定コードは変えない）。
- `agents/ollama.json` の `errors` へ `no_progress` → **`env`** を足す。transient にしない——
  同一入力の再試行は同じ空回りへ同じ時間を焼く（`context_exhausted` を env に倒したのと
  同じ理由）。env なら再計画・タスク分割へ判断が渡る。
- 判定は完全一致から始める。類似度判定・意味的な停滞検知は**要るまで作らない**
  （偽陽性で正常な反復作業——テスト再実行など——を殺すほうが害が大きい。exit_code まで
  同じ完全一致なら、再実行に意味がある仕事とは区別できる）。

### 2.2 役割別のラウンド予算 — write ループの 30 は過大（実装済み）

現行は全ループ一律 `--max-rounds 30 --command-timeout 900`（理論最悪 7.5 時間）。
実測の空回り run は「ラウンドを増やせば畳めた」形跡がなく、30 まで回すことが
食いつぶしそのものになっている。定義ファイルだけで直る:

- `ollama`（bash write）: `--max-rounds 12` へ。9B が 12 ラウンドで畳めない編集仕事は
  30 でも畳めない、が実測の読みである。数値は運用値であり、台帳で `max_rounds` 到達率を
  見て調整する。
- `ollama-read`（調査）: 30 のまま。読取は 1 ラウンドが安く、探索の打ち切りは
  成果の欠落に直結する。
- `command-timeout` は据え置き（900 秒はビルド・テスト実行の正常系を含む）。

なお §4.2 で work をクラウドへ返すため、`ollama` の bash write ループが残るのは
「枯渇時の退避」の受け皿としてだけになる。予算縮小はその文脈でも意味を保つ
（止まるよりましの受け皿が、止まらないまま 7.5 時間焼くのは受け皿ではない）。

### 2.3 自然文基準の verify を ollama から外す

settlement の実測が示したのは「遅い」ではなく「**時間を増やしても決着しない**」である
（600 秒 → 1800 秒で 1 回 90 分になっただけ）。expansion §10.2 の「悪い役割は設定で
クラウドへ戻す」の最初の適用例として:

- 既定の割当から、自然文基準の verifier を ollama の候補から外す（クラウド CLI を既定へ）。
- ollama が verify を受けるのは**機械照合可能な基準**（コマンド実行と終了コードの照合、
  ファイル存在、形式検査）に限る——これは `ollama-read` の決定的ゲートと同じ向きで、
  read ループの得意領域に一致する。役割の組み替え方は §5.1 に書く。
- タスク単位の例外は settlement の `retry`（`verify_agent`）語彙に乗せる。本書で
  新しい迂回路は作らない。

## 3. 検証の現在地 — 測れているのは完走性だけで、測る道具が無い

**改訂で追加した節。** 本書の初版は引き受ける表（現 §4.1）を「実測で品質が成立している」と書いたが、
根拠を読み直すと成立していたのは**完走性**だけだった。

| 測れていること | 根拠 | 測れていないこと |
|---|---|---|
| 時間内に終わる | think off・plain の中央値 9.3 秒（expansion §4.2） | 返した分類・判断が**正しいか** |
| 壊れずに返る | `--format json` が文法レベルで構文故障を消す | JSON の**中身**が妥当か |
| 完走率 | tools・think off で 600 秒超 0 件 | 完走した成果の品質 |

expansion 設計自身が「R3『品質は時間で買う』は**まだ検証されていない**。ここまで測れたのは
所要時間と完走率だけ」と認めている。つまり段 0〜3 は**品質の実測なしに本番へ入っている**。

そして、その検証手段として設計が指名した口が存在しない。expansion §4.2 は
「検証は §10.2 の口ではなく、記録済みプロンプトの**オフライン再生**で行う（§10.3）」と
書いているが、**§10.3 という節は無い**（§10.1・§10.2 の次は §11。grep 確認済み）。
測り方を決めた場所が空白のまま運用が進んだ、というのが現在地である。

これが実質的なボトルネックになっている。ハーネスが無いので品質を測るたびにライブ実行
（verify なら 1 回 90 分）を焼くしかなく、だから測られない。**材料は既に揃っている**——
ループは `say()` が `message` イベントで会話本文を JSONL へ落としており
（`ollama_loop.py:599-605`）、初回の user タスクも含めて再生に必要な入力が残る。

- **オフライン再生ハーネス（実装済み・2026-08-10）**: `agent-ollama --replay`
  （`agentcore/ollama_replay.py`）。記録済み JSONL から最初の user メッセージを取り出し、
  `--arm model=…,think=…,format=…,repeat=N` で並べた設定へ同じ入力を当てる。出力は
  腕ごとの空応答率・失敗率・所要秒の中央値と、**腕をまたいだ一致率**。
  **再生は道具を持たない**（記録されたコマンドを再実行しない）——測定であって
  副作用の再現ではないので、この不変条件は腕の指定でも緩めない。
  失敗は記録に残して次へ進み、全滅のときだけ rc=1 で「これは測定結果ではない」と伝える。
- 正解ラベルとの一致率は出さない。ラベルは人が付けるもので、この口が引き受けるのは
  「同じ入力に対する出力」を再現可能な形で並べるところまで。
- **却下: 品質をライブ運用の台帳だけで測る。** それが現行方式であり、90 分 × 反復の
  コストゆえに 1 件も測れなかった。同じ方式に期待を掛け直さない。

## 4. 用途 — 引き受ける範囲を固定する

### 4.1 引き受ける（完走性が成立している側。品質は §3 の対象）

| 面 | 役割 | 根拠 |
|---|---|---|
| plain（think off） | agent-audit の extract / distill、agent-flow の classify / filter / judge / reduce / split / map | 中央値 9.3 秒で完走。1 発判断は材料が全部プロンプトにあり、能力の穴を踏まない |
| ollama-json | planner / evaluator / plan / adjudicate 等の JSON 契約役割 | `--format json` が故障モードを文法レベルで消し、修復リトライが要らない |
| ollama-read | 調査・読取・機械照合の verify | 決定的ゲートで権限の嘘が無く、explore は空回りしても書き壊さない |
| 枯渇時の退避 | プロファイル候補列の末尾 | 宣言だけで成立（expansion §2.4）。品質が足りない役割も「止まるよりまし」の受け皿にはなる |

**この表は「完走する」までの保証である。**「正しい」の保証は §3 のハーネスが出るまで
存在しない。表を根拠に引受範囲をこれ以上広げない。

### 4.2 引き受けない（実測で成立していない側）

- **work（コード生成・bash write ループ）**: 偽 done・パス捏造・構文エラー成果物の実測に
  加え、**worker としての単一コード生成検証が「改善余地なし」で打ち切られた**（2026-08-10）。
  クラウドへ返す。
- **自然文基準の verify**: §2.3。決着しない検証は節約でなく浪費になる。
- **探索型の planner / 新規性の高い設計判断**: expansion §12 の非目標のまま。

**段 4・5（edit セット / パッチモード）を取り下げる。** 初版は「着手条件を満たせば再検討」
として残したが、打ち切り判断がこれを無効にする。パッチモードの利点は
「適用が決定的なのでモデルがファイルを壊さない」ことであり、**消える故障モードは
corruption だけ**である。打ち切りの原因は corruption ではなく**生成されたロジックの誤り**
なので、決定的適用は救済にならない——壊れていないファイルに、誤ったコードが正確に
書き込まれるだけになる。制約条件が違うところへ効く対策なので、取り下げる。

- **却下: 対象ファイル確定型に絞ればパッチモードは成立する。** 絞っても生成するのは
  コードであり、binding constraint は動かない。絞り込みが効くのは探索の負荷であって
  生成の正しさではない。

### 4.3 検証の余地がある用途（打ち切りが波及しない形）

worker の打ち切りは **長い生成 + ツール操作 + 自己完了判定** の複合が成立しないことを
示すが、3 要素のどれが折れたかは切り分けていない。したがって**同じ要素が耐荷重に
なっていない用途**には波及しない。§3 のハーネスができ次第、次の順で測る価値がある。

| 用途 | 打ち切りとの違い | 優先 |
|---|---|---|
| **判定・分類**（classify / filter / judge / split） | 作らず選ぶだけ。出力空間が離散で小さく、材料は全部プロンプト内 | 高。節約の主力なのに未測定（§3） |
| **候補生成 + 決定的検算**（grep パターン・検索クエリ・パス候補・テスト名の列挙） | 捏造が存在チェックで無害化される。誤っても安全に捨てられる | 高。**パス捏造という既知の弱点が構造的に無効化される**形 |
| **事前トリアージ**（N 件のうちどれをクラウドへ回すか） | 誤りが回収可能。false negative はサンプリングで有界化できる | 高。クラウド入力トークンへ直接効く |
| **read 調査 → 材料生成** | 書き壊せない。出力の宛先を成果物でなく「人・上位モデルが読む材料」に限定 | 中。暴走コストが壁時計だけ |
| **機械照合可能な verify** | モデルに判定させず**証跡を集めさせ、判定は機械が行う**（§2.3） | 中。役割の組み替えが前提 |

**離散判定の多数決（self-consistency）は expansion §8 の却下対象と別物である。**
却下理由は「生成物を同じモデルに選ばせても自己相関で根拠が増えない」ことだったが、
多数決には選定者がおらず、効くのは分散低減である。ローカルは金銭コスト 0、
`OLLAMA_NUM_PARALLEL=1` で直列でも 9.3 秒 × 3 ≒ 28 秒なので、判定系に限れば
現実的な品質レバーとして検証に値する。生成物の best-of-N は却下のまま。

### 4.4 検証しても無駄な側

2026-08-09 の品質診断で出た**偽 done・自己承認**は、生成能力ではなく**判定能力**の欠如で
ある。したがって次は測るだけ無駄になる。

- 自然文基準の verify / evaluator の**最終判定**（証跡収集は別。判定を渡すのが駄目）
- 探索型 planner、新規性の高い設計判断
- パッチモードを含む生成系全般（§4.2）

## 5. 引受範囲の運用

### 5.1 verify の役割を「判定」から「証跡収集」へ組み替える

§2.3 で自然文 verify を外すと、ollama から verify が丸ごと消えるように見えるが、
組み替えれば読取の得意領域として残せる。**モデルに合否を言わせず、コマンドを実行させて
終了コードと出力を集めさせ、合否は外側の機械が決める。** 偽 done・自己承認は
「モデルの判定を信用する」構造から出る故障なので、判定を渡さなければ踏まない。

これは settlement の receipt 契約（証跡で決着させる）と同じ向きであり、
`ollama-read` の決定的ゲートとも噛み合う。新しい契約は作らない。

### 5.2 品質の底上げは手法パックで行う

efficiency-plan の methods プリセットのうち `restate-task` / `path-grounding` /
`output-contract-strict` / `no-self-approval` / `one-change-per-step` は、まさに今回の
3 症状の実測（偽 done・パス捏造・タスク誤読）から起こした規律である。ローカル段で
自動的に厚くなる設計（F17 連動）なので、agent-ollama 側に固有実装を足さずに済む。
引受範囲（§4.1）に対する品質投資はこちらへ集約し、効果は §3 のハーネスで測る。

測った結果は「どこへ効かせるか」まで含めて条件になった。出力へ何かを書かせる規律
（`restate-task` など）は、出力全体が 1 個の JSON に縛られる kind へ入れると本文ではなく
キーとして混入する。カタログ側で `when.purposes` から除いてある（2026-08-11 実測。
`tools/agent-tools/eval/README.md`）。

## 6. モデル — 変えるなら何を根拠に変えるか

スペックアップが無い以上、**物理 RAM が固定の上限**であり、expansion §8 の原則
（RAM に収まる最大級・スワップ厳禁）はそのまま効く。**マシンが資産であって、9B の生成
モデルはその一用途にすぎない**——この捉え方を入れると選択肢は 4 つになる。

| 案 | 内容 | 判断 |
|---|---|---|
| a. 現状維持（qwen3.5:9b） | 引受範囲の 1 発判断は完走性が成立している | **既定**。3 症状のどれもモデルが主因ではない（真因は配線と用途）ので、モデル変更は症状対策にならない |
| b. MoE へ載せ替え（qwen3 系 30B-A3B・アクティブ約 3B 級） | CPU の decode が軽いまま総パラメタが増え、判断系の品質余地が上がる | **条件付き**。Q4 量子化 + KV で 20 GB 級を要する。物理 RAM に収まらないなら検討自体が無効。収まるなら §4.3 の再測の軸に加える |

案 d が「違う用途で使う」の最も筋の良い形である。宛先は ltm-use / agent-audit の材料選別、
agent-flow の artifacts 参照解決あたりで、既存設計に埋め込み基盤は見当たらないため新規に
なるが、**「9B に何をさせるか」の袋小路とは独立に評価できる**のが利点。
本書は選択肢として立てるところまでとし、設計は別書に切る。

判断の口は既存のまま: `agent-audit --by model` の verify PASS 率 × 役割で測り、
載せ替えは台帳を根拠に人が行う。**症状が出たからモデルを変える、はやらない**——
3 症状はどれも、モデルを変えても配線が同じなら再発する形だった。
