# statemachine-maker AIティーチング・ワークスペース実装計画

> 作成日: 2026-09-06  
> 設計: [AIティーチング・ワークスペース設計](2026-09-06-statemachine-maker-ai-teaching-workspace-design.md)

## 方針

既存の工程モデル、決定的コンパイラ、保存、実行経路を維持し、その手前に「教示セッション」と「仕事の仕様」を追加する。旧UIは一度に削除せず、高度な編集として残したまま主経路をAI中心へ切り替える。

作業中の `statemachine-maker` 変更と競合しやすいため、各段階はデータ層、main/IPC、rendererの順に分け、段階ごとにテスト可能な状態を保つ。

## Phase 1: 教示セッションと仕事の仕様

### 1.1 データ契約を追加

新設候補:

- `src/main/teaching-model.js`
- `test/teaching-model.test.js`

実装内容:

- 教示セッションのversion付き正規形を定義する。
- 目的、会話、証拠、理解内容、承認待ち、試運転、候補世代を正規化する。
- 仕事の仕様として、入力、変数、期待結果、重要操作、成功条件、失敗方針、テストケースを定義する。
- 秘密値は保存可能フィールドへ入れず、入力先と参照名だけを許可する。
- 状態を `draft`、`needs-trial`、`awaiting-confirmation`、`ready` に限定する。
- AI候補から現在世代を作り、最後の成功世代へ戻す純粋関数を実装する。

検査:

- 旧version、欠損項目、未知列挙値、秘密値候補、不正な世代参照をテストする。
- 正規化とJSON往復で意味が変わらないことを固定する。

### 1.2 保存層を追加

変更候補:

- `src/main/store.js`
- `test/store.test.js`

実装内容:

- `maker.json`と同じワークフローフォルダへ教示セッションを併置する。
- 自動保存は一時ファイルへの書き込み後に置換し、中断で壊れないようにする。
- 既存ワークフローには空の教示セッションを遅延作成する。
- 移行成功までは既存YAMLと`maker.json`を変更しない。

検査:

- 新規、再開、破損ファイル、旧ワークフロー、世代復元をテストする。

## Phase 2: AI教示オーケストレーション

### 2.1 AI契約を拡張

変更候補:

- `src/main/ai.js`
- `src/main/ai-diff.js`
- `test/ai.test.js`
- `test/ai-diff.test.js`

実装内容:

- 既存のdraft/reviewを、教示セッション用の意図に段階移行する。
- 応答を `question`、`request-demonstration`、`request-approval`、`candidate`、`trial-assessment` に分類する。
- AIへ会話、秘密値を除いた証拠、現在の仕事の仕様、試運転結果を渡す。
- 候補には完全な仕事の仕様、maker候補、未確認の前提を必須にする。
- 追加の見本は曖昧な箇所と必要理由をAIが示した場合だけ要求できるようにする。
- AI出力を直接適用せず、正規化、コンパイル、構成検査、安全検査を通す。

検査:

- 基本ケースが1回の見本で候補になることを固定する。
- 固定値と変数が曖昧な場合だけ質問へ戻ることをテストする。
- 対象外変更、秘密値、無承認の重要操作、不正JSON、古い依頼IDを拒否する。

### 2.2 操作の安全分類と承認を追加

新設候補:

- `src/main/approval-policy.js`
- `test/approval-policy.test.js`

実装内容:

- 閲覧、移動、検索、画面取得、未送信入力を安全な操作として扱う。
- 送信、保存、更新、削除、購入、公開、外部連絡、権限変更を重要操作として扱う。
- 不明な操作は重要操作側へ倒す。
- 承認を操作内容、対象、影響、試行IDへ結びつける。
- 作成中の承認は一度限りとし、本番実行の承認設定とは分離する。

検査:

- 操作種別、曖昧な操作、承認の再利用拒否、別対象への流用拒否をテストする。

## Phase 3: 録画を「証拠」へ変更

変更候補:

- `src/main/recording.js`
- `src/main/ipc.js`
- `src/preload.js`
- `test/recording.test.js`
- `test/preload-contract.test.js`

実装内容:

- 既存の録画結果を工程列へ直結する入口を、教示セッションへの証拠追加へ切り替える。
- ブラウザとWindowsで共通の証拠形式を定義する。
- 時系列操作、対象の意味、画面遷移、入力値の秘密化情報を保存する。
- 録画後はAIへ解釈を要求し、生の操作列を通常UIへ返さない。
- 既存の記録変換は高度な編集向け互換経路として残す。

検査:

- パスワード等の値が証拠とAI入力へ残らないことを固定する。
- 録画の中断、空録画、途中再開、ブラウザ/Windows差異をテストする。

## Phase 4: 試運転と結果ベース判定

新設候補:

- `src/main/trial.js`
- `test/trial.test.js`

変更候補:

- `src/main/agent-loop.js`
- `src/main/model.js`
- `src/main/ipc.js`
- `test/agent-loop.test.js`
- `test/model.test.js`

実装内容:

- 代表入力、期待結果、実行範囲を持つ試運転を開始する。
- 既存のagent-loop/statemachine実行経路を再利用する。
- 直接観測できる結果、AI比較が必要な結果、人の確認が必要な結果を区別する。
- 重要操作へ到達したら承認待ちとして停止し、同じ試行を再開する。
- 構成検査、安全検査、結果検査をすべて通った世代だけ`ready`にする。
- 失敗結果を証拠へ戻し、次候補の材料にする。

検査:

- 成功、期待との差、重要操作の承認/拒否、途中再開、実行手段不足、成功版への復元をテストする。

## Phase 5: AI中心UI

変更候補:

- `src/renderer/index.html`
- `src/renderer/renderer.js`
- `src/renderer/styles.css`
- `src/preload.js`
- `test/app.test.js`
- `test/electron-smoke.test.js`

実装内容:

- 一覧の主要操作を「新しい仕事を教える」「変更を相談する」「試運転する」「実行する」にする。
- 作成画面を会話、AIの理解、試運転結果の3領域にする。
- 質問、見本依頼、承認、試運転、結果を専用カードで表示する。
- `目的を理解中 → 方法を確認中 → 試運転中 → 利用可能`を状態から描画する。
- 入力とAI結果のたびに下書きを自動保存する。
- 既存の工程編集、分岐、生成ファイルは「技術詳細／高度な編集」へ移す。
- 旧AI下書き、AI見直し、録画ダイアログは主導線から外し、教示セッションから同じ機能を呼ぶ。

検査:

- 760px、980px、1440pxで横スクロールが出ないことを確認する。
- キーボードだけで質問回答、録画開始、承認、試運転、結果承認ができることを確認する。
- 技術用語や生の操作列が通常画面へ露出しないことを静的・実機テストで固定する。

## Phase 6: 既存ワークフロー移行

実装内容:

- 既存の`maker.json`またはYAMLからAIが仕事の仕様を逆算する入口を追加する。
- 不明点だけを質問し、仕事の仕様と試運転候補を作る。
- 移行前の定義を成功世代として保持し、移行試運転の成功まで上書きしない。
- 利用状況を確認できるまでは旧ダイアログと直接工程編集を削除しない。

検査:

- maker.jsonあり、YAMLのみ、保持フィールドあり、自然言語条件あり、複数終端ありの既存例を移行する。
- 移行失敗時に元定義へ差分がないことを固定する。

## Phase 7: 結合・受け入れ検証

代表シナリオ:

1. ブラウザ: 一覧から対象を探して詳細を読み取る。
2. Windows: アプリへ入力し、保存直前で承認を求める。
3. ファイル: 入力ファイルを読み、成果ファイルの存在と内容を確認する。
4. 既存定義: 現在のワークフローを会話で変更し、元定義を保ったまま試運転する。

各シナリオで次を確認する。

- 工程、分岐、セレクター、確認スクリプトを利用者が入力しない。
- 基本ケースは目的説明、1回の見本、結果承認で完了する。
- 曖昧な場合だけ質問または追加の見本を要求する。
- 重要操作の直前で必ず停止する。
- 秘密値が保存物、AI入力、診断ログへ残らない。
- 完成物をmakerなしで実行できる。

実行する検査:

```bash
cd tools/statemachine-maker
npm test
npm run lint
npm run smoke
```

## 実装上の停止条件

- 現在の未コミット変更と同じ関数を大きく書き換える必要がある場合は、先に差分の所有者と統合方針を確認する。
- 重要操作を実行途中から安全に再開できない実行基盤であることが判明した場合は、承認後に工程を最初から再実行する案との比較へ戻る。
- Windows操作の証拠から秘密値を確実に除けない場合は、Windows録画の教示利用を無効にして設計を再評価する。
