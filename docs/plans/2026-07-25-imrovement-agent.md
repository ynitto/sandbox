# agent シリーズの改良点

## 目的
この文書はユーザーによる要件を記したものである。一件一葉として整理されたものではなく重複や関連性の高いものが多く含まれる。これらを整理し真の要求は何か分析した上で、設計に落とすこと。特にどこが責務として担うかは慎重に検討すること。

## 課題

* agent-project の管理対象フォルダを改めて整理したい。agent-project.yaml による状態専用リポジトリ設定をやっていたが、アーキテクチャの整理や状態専用リポジトリの分離強制に伴い、設定ファイルの書き方含めてシンプルにしたい。
* agent-dashboard で agent-project 管理対象フォルダ以外も扱いたい。具体的には kiro-loop やステートマシン設定ファイルを持つフォルダを登録して定常業務画面を操作させたい。
* kiro-flow/kiro-amigos が作業する際に git clone を行う。同じタスクグラフ上でだと、成果物をあげるリポジトリは同じため、リモート負荷的にも効率が悪い。何か効率化する施策が欲しい。
* agent-dashboard で cli 起動時の cwd を repos.json から選択したい。ただし、repos.json は git リモートに push するため、ローカルパスを記載することはできない。また、kiro-flow/kiro-amigos の作業にローカルフォルダを使うと git アクセス負荷低減になるので、上手く取り入れたい。
* kiro-dashboard の成果物のレビュー方法について。worker が /tmp に成果物を作成してリモートに push するため、検収画面でローカルを見ても見れない。GitHub PR/GitLab MR などリモート側の画面でレビューするでも良いが、人のレビューコメントを拾って差し戻しするタイミングを決めなければいけない。
* スペック駆動開発をどう組み合わせていくかを考えたい。一般的にスペック駆動は新規開発と相性がいいが、ブラウンフィールドのプロジェクトに対してはオーバーヘッドが大きく扱いづらい。そのギャップを埋める仕組みを考えたい。
* charter.md からの分解したバックログ、バックログから構成したタスクグラフがユーザーの期待とずれている。試行錯誤によって期待との乖離を埋めていくのが良いが、現状、バックログの中身が抽象的で計画レビューできない、バックログの再作成を行うと重複した内容のものができる、バックログを削除しても自動生成されてしまいユーザー作成が介入できない、など試行錯誤する環境が整っていない。また、バックログ分解、タスクグラフ構築するプロンプト・スキルが固定のためカスタマイズする余地がない。
* 突発的な追加要件に対応したい。外発的・内発的に関わらず、突発的に発生したバックログを処理できるようにしたい。ただし、既存のバックログやcharter/バージョンとの整合性をとる必要がある。特に類似したバックログを生む現象は極力避けたい。
* 人間の気になる観点を入力してバックログ分解できる機能もあるとよい。人間は不意に気になることがある。気になることを書き溜めて、人間の整理がついたタイミングで指示し、バックログ化できても面白い。
* agent-dashboard に board の UI が表示されない。状況確認と手動入札・キャンセルくらいができればいい
* agent-dashboard の診断のためのエージェント呼び出しは tmux/CLI チャット画面呼び出しにして、状況の可視化と対話ができるようにしたい
* agent-project/agent-flow で verify が機能していない。まず人がコマンドを入力するのは困難。エージェントに決めさせたところで、ノードや環境によってコマンドが殆どのケースで失敗するため、結局人レビューにフォールバックする。設計思想としては良いが、現実にはエージェントによるコマンドの試行錯誤によって成り立っているため、現システムにはマッチしない。
