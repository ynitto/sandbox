# 依頼に応じて定型業務を実行し、ステートマシンを作って育てる — agent-dots の「業務係」

> 作成 2026-11-23 ／ 状態: R0〜R2 実装（`tools/agent-dots/routines.py`）
> 前提: [`2026-11-22-resident-agent-dots-design.md`](./2026-11-22-resident-agent-dots-design.md)（agent-dots の D0〜D2）、
> statemachine-use スキル（作成モード・実行モード・`check`・`inputs`）、agent-app の依頼の振り分け（`requestRouting.js`）と教示の段
> 決定（2026-11-23、利用者）: 入口はハブの issue／実行は Copilot アプリの 1 回の会話（statemachine-use の実行モード）／
> 手持ちに無い業務は作って試運転し、確認してから登録／外へ書くスキルは登録時に一度だけ承認

## TL;DR

agent-dots の目標の 1 つを「業務係」にする（`policy.json` に `routines` を書く）。ハブの issue に `【業務】10 月の売上集計` と
書くと、次の順に進む。

1. **選ぶ**：業務係が、手持ちのステートマシンの一覧（`dot.py` が決定的に作り、依頼の語で並べる）から 1 つ選び、入力を依頼から埋めて
   `routine run` を提案する。`dot.py` が入力の宣言（`inputs`）と照らし、足りなければ質問する。
2. **回す**：次に起きたとき、Copilot アプリが statemachine-use の**実行モード**でそのマシンを最後まで回し、結果を `routine result` で返す。
   フックは、そのマシンが使う（登録時に承認した）スキルのスクリプトと statemachine-use のスクリプトだけを通す。
3. **作る**：合うものが無ければ `routine create` を提案する。statemachine-use の**作成モード**で `routines/<名前>/` に下書きを作り、
   `dot.py` が検証（`run_machine.py --dry-run`）して、元の依頼の入力で**試運転**する。試運転では、外へ書くスキルはフックで止め、
   書く中身を作るところまでにする。
4. **登録する**：試運転の結果と、使うスキル（外へ書くもの）の一覧をハブに出し、`承認 aN` で登録する（`.statemachine/<名前>/` へ置く）。
   これが「登録時に一度だけ承認」。以後の実行では聞かない。定義が承認後に変わったら、もう一度承認を求める。
5. **育てる**：実行ごとに記録（入力・終わったステート・成否・ステートごとの出力の 1 行目）を残す。失敗・`escalate`・
   `【業務】直す <名前> 理由` の返事・試運転の却下があると、**改善の回**を起こす。現行版を下書きに写して直させ、**失敗した回の入力で**
   試運転し直し、承認されたら版を上げて差し替える。前の版は残し、`【業務】戻す <名前>` で戻せる。

## 1. 部品の割り当て

| やること | 誰が | どこで |
|---|---|---|
| 一覧を作る・依頼の語で並べる | `routines.py`（LLM 不使用） | 依頼文に一覧の上位を載せる |
| どのマシンを使うか・入力の値を決める | 業務係（Copilot アプリ） | `routine run` の提案 |
| 入力が揃っているか・使ってよいマシンか | `routines.py` | `act` |
| ステートを回す・遷移を決める | Copilot アプリ（statemachine-use の実行モード。遷移は `next_state.py`） | 1 回の会話 |
| 使ってよいスクリプト | フック（`dot.py hook`） | 承認したスキルの置き場の中のスクリプトだけ |
| 作る・直す | Copilot アプリ（statemachine-use の作成モード、skill-selector） | `routines/<名前>/` だけに書ける |
| 下書きの検証 | `routines.py`（`run_machine.py --dry-run`） | `act` |
| 登録・版・戻し | `routines.py` | 承認（D1 の `承認 aN`）のあと |
| 記録と集計 | `routines.py` | `.dot/routines.json`・`.dot/runs/` |

## 2. 業務の台帳（`.dot/routines.json`）

マシンのフォルダには何も書かない（agent-app のタスクや、ほかのリポジトリの `.statemachine/` をそのまま使えるようにする）。台帳は目標の
フォルダの `.dot/` に置き、フックがエージェントからの書き換えを止める。

| 項目 | 中身 |
|---|---|
| `status` | `draft`（作っている）/ `trial`（試運転中）/ `awaiting`（確認待ち）/ `ready`（登録済み） |
| `path` | マシンのフォルダ |
| `digest` | 承認したときのフォルダの中身の指紋。変わっていれば承認し直す |
| `skills` | 使うスキル（名前・置き場・外へ書くか） |
| `version` / `history` | 版と、前の版の置き場 |
| `runs` / `ok` / `recent` / `state_failures` | 実行の回数・成功数・直近の成否・ステートごとの失敗数 |

## 3. 外へ書くスキル

- 外へ書くスキルは `policy.json` の `routines.write_skills` に利用者が書く（例 `outlook-use`・`redmine-use`）。業務係が作るときに
  申告した分（`created` の `writes`）も足す。足すだけで、申告で減らすことはできない。
- 試運転・改善の試運転では、外へ書くスキルのスクリプトはフックが止める。業務係は書く中身を作ってステートの出力にし、送らない。
- 登録の承認には、使うスキル・外へ書くスキル・試運転の結果の要約を出す。承認したら、そのマシンの実行では外へ書くスキルも通す。

## 4. 改善の回の起こし方

| きっかけ | どうなるか |
|---|---|
| 実行が失敗・`escalate` で終わった | ハブに結果と「直すなら `【業務】直す <名前> 理由`」を書く。同じマシンが直近 3 回で 2 回失敗したら、聞かずに改善の回を起こす |
| `【業務】直す <名前か rN> 理由` | 改善の回を起こす（理由と、その回の記録を依頼文に載せる） |
| 試運転・改善版の登録を却下（`却下 aN 理由`） | 理由を添えて改善の回を起こす（同じ下書きを直す） |

改善の回の試運転は、直すきっかけになった回の入力で回す（同じ失敗が直ったかを見る）。登録すると版を 1 つ上げ、前の版を
`.dot/routines-history/<名前>/v<版>/` に写す。`【業務】戻す <名前>` で 1 つ前の版に戻す。

## 5. 範囲外（今回はやらない）

- 複数の業務を同時に回す（1 つの目標で 1 件ずつ。急ぐなら業務係を分ける）
- 回の記録からの自動の回帰テスト（直近の成功した回の入力でも試運転する、は後で足す）
- agent-app の画面への表示（台帳は JSON なので、あとから読める）
