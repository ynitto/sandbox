# ローカル LLM（gemma4:e4b）の追加活用アプローチ提案と、koboldcpp 等ランタイムチューニングの検討

> 作成 2026-08-22
> 前提: CPU only / RAM 32 GB / ハードウェア増強なし（確定）。推論サーバは ollama、
> コード worker は `agents/aider.json`（gemma4:e4b + reliability policy v1）、
> テキスト・判定系は `agent-ollama` 系定義。
> 位置づけ: [2026-08-14 ローカル主体運転計画](2026-08-14-agent-tools-local-first-operation-plan.md)と
> [2026-08-18 agent-aider 改良余地の評価](2026-08-18-agent-aider-improvement-assessment.md)の**次の一手**を探す。
> 既に決まっている打ち手（P1〜P11・Gate 0〜2）とは重複させず、新規の軸だけを提案する。

## 0. 結論の先出し

- **追加活用の余地は「モデルを強くする」側ではなく、「決定的な機構で E4B の弱点を
  迂回する」側に残っている。** 実測で確定した E4B の性格——短い・局所的・構造化は強く、
  長い・横断的・メタ認知は弱い——を前提に、本書は 6 案を提案する。うち先行 2 案
  （**N 回抽選 + 決定的ゲート採択**、**決定的コンテキスト・スライシング**）は
  既存ハーネスでそのまま測れる。
- **koboldcpp は「モデルのチューニングツール」ではない**（llama.cpp 系の推論ランタイム
  であり、fine-tuning はできない）。得られるのは推論条件の追加レバーである。
  全面乗り換えの価値は**現時点では薄い**——decode 速度は同系エンジンでほぼ同等、
  我々の律速（受入率・再試行・prefill）のうち koboldcpp が直撃するのは prefill 再利用と
  文法制約だけで、その大半は ollama 側の既存レバーでまだ埋まる。
- ただし**条件付きで測る価値が 2 つある**: (1) 未検証のまま残っている
  [案 B（iGPU prefill）](2026-08-06-opencode-ollama-cpu-inference-proposals.md)の
  **最も安い検証ビークル**として（Vulkan 同梱・単一バイナリ）、(2) `--format json` より
  強い**任意文法（GBNF）制約**の効果測定として。どちらも「ランタイム差し替え」ではなく
  **独立した評価 arm** として扱い、基準線なしの載せ替えはしない（既存の規律のまま）。
- **追記（2026-08-23）: 新しい案より先に閉じるべきものがあった。** §4.2 の棚卸しで、
  (1) 本書の案 1 の効果範囲を決める前提が未測定であること、(2) 独立レバー 4 本
  （P7 / P8 / P9 / P11）が宣言されたまま着手記録を持たないこと、(3) 呼び出し面 42 のうち
  **34 が能力未測定**であることが分かった。実行順序は §4.2 末尾で改訂した。

## 1. 前提 — 実測で確定していることの再掲（判断の土台）

| # | 事実 | 出典 |
|---|---|---|
| 1 | E4B は「短い・局所的・構造化」で天井、「長い・横断的・メタ認知」で崩れる（T2 3/3 ⇔ T1 1/3・T3 0/3、MRCR 128K 25.4） | local-first 計画 §1.5 |
| 2 | 品質の守りはゲートにある: 決定的検査 + 再投入で 0/9 → 3/3。実機経路でも 3/3（中央値 313s） | 同 §1 事実 2・段 1 再測 |
| 3 | 実効 temperature は 0 だった。推奨 sampling（1.0/0.95/64）で失敗が揺れ、T1 0/3 → 1/3、対照 T2 3/3 維持 | P10 実測（2026-08-15） |
| 4 | filter / judge の多基準はプロンプト 5 レバー全滅 → 決定化（P4）で 3/3 に到達済み | E6 実測（2026-08-15） |
| 5 | 律速は decode 速度ではない（e4b 26.5 tok/s）。壁時計を焼くのは再試行・ラウンド数・prefill と、12b の停止性 | 同 §1 事実 1・9 |
| 6 | 所要秒 ≒ TTFT + 出力/11.7 で、**入力長はほぼ効かない**（現行の入力規模では）。ただし opencode 級の 1〜2 万 token prefill は別（数分〜10 分） | log_stats / 2026-08-06 §0 |
| 7 | `num_ctx` を上げることは E4B のレバーにならない。割るのが正解 | local-first 計画 §1.5 |

この土台から、残る改善余地は次の 3 象限に整理できる。

1. **受入率**: T1 型（実装 + テスト一括）1/3、レビュー網羅 2/3 帯の上積み。
2. **壁時計**: 直列運転（workers: 1）での回転数。再試行 1 回 ≒ 数分〜十数分。
3. **形式故障**: JSON / 編集形式の契約外れ（`format_retries` で拾えているが 0 ではない）。

## 2. 追加活用の提案（6 案・優先度つき）

### 案 1 ★ N 回抽選 + 決定的ゲート採択（best-of-N）— P10 の帰結を運用形にする

**何をするか。** 推奨 sampling で同じ局所 task を最大 N 回（N=2〜3）引き直し、
**採択は決定的 checker だけが行う**。全滅したときだけ escalate する。
`check_on_exhausted` の手前に「まず引き直す」段を正式に入れる形であり、
local-first 計画の事実 3 注記（「昇格前に推奨 sampling で引き直す段が選択肢に入る」）を
評価つきで確定させる。

**なぜ効くと考えるか。** P10 実測で、温度 0 の「9/9 同形失敗」が sampling で
3 様に揺れ、1 本は受入に達した（事実 3）。揺れる失敗は引き直しで拾える。
選択を checker に限定するので、多数決（judge 投票）が全滅した領域とは機構が違う——
あちらは**判定を** LLM に訊いた。こちらは**生成だけ** LLM に任せ、判定は機械が持つ。
候補生成 + 決定的検算という P4 の標準形の worker 版である。

**コストと境界。**

- コストは壁時計 × N（クラウド消費 0）。checker 通過で早期打ち切りするので、
  成功する課題には課金しない（ゲートと同じ性質）。
- 適用は checker が存在する局所 task に限る（2026-08-18 §5 の適格条件そのまま）。
  checker のない task で引き直すと「自己申告の試行回数だけ増える」ので対象外。
- sampling は arm として ledger に記録し、「未指定」と「既定値明示」を区別する
  （2026-08-18 §6 の規律を維持）。

**測り方。** worker_eval に `--resample N` の腕を足し、T1 / T1gate で
受入率と壁時計を baseline（N=1 + escalate）と比較する。採用条件は
「escalate 率が下がり、T2 対照に退行がない」こと。

### 案 2 ★ 決定的コンテキスト・スライシング — 「割るのが正解」をシンボル粒度まで下ろす

**何をするか。** aider へ渡す材料を「ファイル単位」から「シンボル単位」へ細くする。
tree-sitter / ctags 級の決定的なパーサで対象ファイルから関連シンボル
（編集対象の関数・その呼び出し元/先・参照される型）だけを抽出し、
抜粋ファイルを生成して `--read` に渡す。編集対象本体だけを `--file` に残す。
LLM は使わない——抽出は 100% 決定的な前処理である。

**なぜ効くと考えるか。** E4B の弱点は長文脈からの検索（MRCR 25.4）で、
「入れれば読める」が成り立たない（事実 7）。現行運用は read-only agent で
候補**ファイル**を絞っているが、1 ファイルが大きいとファイル内で同じ問題が起きる。
T1/T3 型の失敗（横断・複数成果物）の一部は「関連個所を見落とす」形であり、
見るべき範囲を機械が先に確定してやることは、リポジトリマップを切った判断・
`_SM_MAX_AUTO_READ_BYTES`・P1 の診断 2000 字制限と同じ線上の一手である。
prefill も削れるが、主目的は**能力の底上げ**（見落とし面積の縮小）にある。

**コストと境界。**

- 実装は agentcore 内の前処理モジュール 1 本（決定的・LLM なし・標準ライブラリ +
  パーサ 1 依存）。抽出失敗時はファイル全体へフォールバックし、黙って欠落させない。
- Python 以外の言語はパーサ対応分だけ順次。まず自リポジトリの主要言語（Python / JS）。
- 「対象が計画時に決まっている」適格条件は変えない。探索の代替ではない。

**測り方。** T1 / T3 セルでスライスあり / なしを比較。見るのは受入率・
tokens_in・見落とし系の失敗形（作業丸ごと欠落族が減るか）。

### 案 3 ○ 同役割の直列バッチ化 — プレフィックスキャッシュ命中率をスケジューラで上げる

**何をするか。** `OLLAMA_NUM_PARALLEL=1` の接頭辞キャッシュは「直前リクエストと
接頭辞が一致」したときだけ効く。役割が交互に来る（worker → judge → worker …）と
system prefix が毎回入れ替わり、固定 policy や役割プロンプトの prefill を毎回払い直す。
エンジンのキュー消化を**同役割で束ねる**（map の fan-out・独立 step の消化順を
役割別にソートする）だけで、接頭辞一致の連続が増える。

**なぜ効くと考えるか。** reliability policy v1 + 役割骨格は呼び出し間で不変であり、
命中すれば prefill から丸ごと消える。実装はスケジューラの消化順ソートのみで、
モデル・プロンプト・契約のどれにも触らない（= 品質側の再測が要らない）。

**コストと境界。** 依存のある step の順序は変えられないので、効くのは fan-out と
独立 step だけ。効果は log_stats の TTFT 分布で before/after を見る。TTFT が
入力長にほぼ依存しない現状（事実 6）では**効果が小さい可能性がある**——
だからこそ測定が安いこの案は「測って駄目なら捨てる」で良い。

### 案 4 ○ 小型サブモデル（e2b 級）の適材適所 — 天井の役割から壁時計を回収する

**何をするか。** E4B は MatFormer 系（実 4.5B・Effective 4B）で、系列に
より小さい実効 2B 級の配布がある。抽出・分類・split など **e4b で既に 6/6 の
天井に張り付いている役割**に限って e2b 級の arm を引き、同点なら小さい方を使う。

**なぜ効くと考えるか。** 直列運転（workers: 1）では 1 呼び出しの短縮が
そのまま回転数になる。天井の役割はモデルを下げても受入が動かない可能性が
高く、動かなければ decode がほぼ倍速になる分だけ得をする。浮いた壁時計は
12b 検証役や案 1 の N 回抽選の予算に回る。

**コストと境界。** 既存の規律どおり**基準線と並べて測ってから**
（`judge_eval` / `text_eval` の既存セルへ `--model` 差し替えで乗る。数時間)。
1 点でも退行した役割には使わない。コード worker には最初から使わない
（T2/T1 は e4b でも境界域であり、下げる理由がない）。

### 案 5 △ 台帳の few-shot 資産化 — 合格実例 1 本を定型 task の前置きに足す

**何をするか。** eval / 運用台帳には checker を通過した成果物が条件つきで
残っている。定型 task 種別ごとに**合格実例 1 本**（入力の骨格 + 受入した出力）を
決定的に選んで前置きする。検索は不要（task 種別 → 実例の固定対応表）で、
bge-m3 での動的検索は効果が出てから。

**なぜ測る価値があるか。** プロンプト手法パックが全滅したのは filter / judge の
**判断**領域であり、worker の**形式・手順の模倣**は未測定。few-shot は
指示追従より模倣に効くタイプのレバーで、E4B の「構造化は強い」側に乗る。
ただし prefill を数百〜千 token 増やすので、受入が動かなければ即取り下げる。

**測り方。** T2 / T1min で 1-shot あり / なし。見るのは受入率・形式故障率・
壁時計。判断系（F2/J1）には最初から適用しない（4 レバー全滅 + 決定化済みの
領域を蒸し返さない）。

### 案 6 △ 採用しない: ローカルでの fine-tuning（QLoRA / 蒸留）

「チューニング」の語で最初に連想される選択肢なので、明示的に**不採用**と書く。

- CPU only / 32 GB では 4B 級の QLoRA でも実用時間で回らない（日単位/epoch）。
  ハードウェア増強なしの制約と正面衝突する。
- 学習データ（合格台帳）はまだ小さく、過学習で「定型は上手いが少しずれると壊れる」
  モデルを作るリスクの方が大きい。
- 決定的ゲート + 再投入という守りは fine-tune 後も必要であり、fine-tune は
  ゲートを外す根拠にならない。つまり**得られるのは受入率の上積みだけ**で、
  それは案 1〜5 の方が桁違いに安く買える。

再評価条件: 合格台帳が数百件規模に育ち、かつ GPU 実行環境が制約から外れたとき。

## 3. koboldcpp 等によるチューニングの検討

### 3.1 用語の整理 — koboldcpp で「できること」

koboldcpp は llama.cpp のフォーク（単一バイナリの推論サーバ + UI）である。
**モデルの重みを変える機能はない**。「チューニング」として得られるのは
推論条件のレバーであり、ollama（同じ llama.cpp 系エンジン）との差分は次に絞られる。

| レバー | koboldcpp / llama.cpp server | ollama | 我々の律速に効くか |
|---|---|---|---|
| decode / prefill の素の速度 | 同等（同系エンジン） | 同等 | **効かない**（差がない） |
| KV 状態の保存・再利用（context-shift / slot save） | ○ 明示制御 | △ 直前接頭辞の暗黙キャッシュのみ | **効く**（ラウンド間・呼び出し間の再 prefill 削減） |
| 任意文法（GBNF）による出力制約 | ○ | ×（`format` の JSON / schema まで） | **効きうる**（SEARCH/REPLACE・リスト契約の形式故障を文法レベルで消せる） |
| 投機的デコード（draft model） | ○ | × | **薄い**（律速は decode ではない。事実 5） |
| Vulkan バックエンド（iGPU） | ○ 同梱・起動フラグのみ | △ 実験的 | **効きうる**（未検証の案 B を直撃。prefill は計算律速なので iGPU が効く） |
| スレッド / バッチ / NUMA の手動調整 | ○ 細かい | △ 環境変数で一部 | 限定的（既定で大きく外していない） |
| モデル管理・keep_alive・API | ollama の方が楽（pull / keep_alive / think フィールド） | — | 移行コスト側の論点 |

### 3.2 我々の律速との突き合わせ — 何が買えて、何が買えないか

§1 の 3 象限に当てると:

- **受入率**: ランタイムでは買えない。受入を動かした実績はすべて機構側
  （ゲート・分解・決定化・sampling）であり、koboldcpp に乗り換えても T1 は 1/3 のまま。
- **壁時計**: 買える可能性があるのは 2 箇所だけ。
  (a) **KV 状態の明示保存**——tool-loop のラウンド間・同役割呼び出し間の再 prefill を
  消せる。ただし案 3（直列バッチ化）が ollama のままで同じ狙いを安く部分達成するので、
  順序は案 3 が先。
  (b) **Vulkan での iGPU prefill**——2026-08-06 の案 B そのもので、効けば桁の改善だが
  実機検証が未了のまま残っている。**koboldcpp の最大の価値はこの検証を単一バイナリで
  即日試せることにある**（ROCm / ipex-llm の環境構築が不要）。
- **形式故障**: GBNF は `--format json` より強い保証を与える。特に aider の
  SEARCH/REPLACE 形式や `--format array` のリスト契約を文法で固定できれば、
  `format_retries` の消費と適用失敗リトライが減る。ただし現行の形式故障率は
  既に低く抑えられている（文法制約 + json_variant 振替で空応答 0/20）ので、
  期待値は「保険の強化」であって跳ねる類ではない。

### 3.3 移行コスト — 安くない、を先に言う

- `agent-ollama` 系は ollama API に密結合している: `/api/chat` の `think`
  フィールド、`format`、`keep_alive`、ストリーミング進捗（stall 検知の心臓部）、
  エラー分類の match 文字列。OpenAI 互換 API への載せ替えは**ハーネス変更**であり、
  既存の規律（model / harness / sampling を同時に変えない）に従えば
  **全基準線の再測**が伴う。
- aider 経路は litellm の `ollama_chat/` プロバイダ前提で、reliability policy の
  managed settings（`extra_params` / `num_ctx` / `num_predict`）もこの経路に
  合わせて実装済み。付け替えは Gate 0 相当の注入契約検証をやり直すことになる。
- koboldcpp は個人メンテ主体・チャット UI 寄りの既定を持つ。無人運転の
  バックエンドとして選ぶなら、同じ機能を持つ本家 llama.cpp の `llama-server` の方が
  保守的な選択で、GBNF・slot save・Vulkan はいずれも本家にある。

### 3.4 判断 — 検討価値の結論

**全面乗り換え: 現時点では価値が薄い（不採用）。** 受入率は動かず、decode は
同等で、壁時計の主因（再試行・ラウンド数）はランタイム非依存。移行コストは
基準線の再測込みで大きい。

**限定投入: 2 つだけ、独立 arm として測る価値がある。**

1. **案 B の検証ビークル（優先）。** koboldcpp（または llama.cpp の Vulkan ビルド）で
   gemma4:e4b を iGPU に載せ、§1 の計測手順（prefill / decode の内訳）を
   ollama 基準線と並べる。半日で終わる。prefill が数倍動けば、そのときはじめて
   「ランタイム移行の便益 > ハーネス再測のコスト」の判定台に乗る。
   動かなければ案 B ごと閉じられる——どちらに転んでも懸案が 1 つ減る。
2. **GBNF の形式保証（後続・任意）。** リスト契約（split の `--format array` 相当）を
   GBNF で固定した arm を 1 本引き、形式故障率と受入への影響を見る。
   ollama 側の schema 指定で足りているなら、それが答えで良い。

採用ゲート（どちらの限定投入にも共通）:

- ledger / manifest にランタイム・バックエンド・ビルド条件を記録し、
  model / policy / sampling と同時に変えない。
- 対照群（T2 / 抽出 6/6 セル）に退行がないこと。
- 「速くなった」だけでは採用しない——移行するなら stall 検知・usage 実測・
  エラー分類の契約が同等に成立することを Gate 0 相当で先に固定する。

## 4. 実行順序

| 段 | 内容 | コスト | 完了条件 |
|---:|---|---|---|
| 1 | **案 1**（N 回抽選 + ゲート採択）の worker_eval arm | 半日 + 壁時計 | T1 / T1gate で escalate 率低下・T2 無退行を確認し、`check_on_exhausted` の既定を更新 |

### 案 1 — `--resample N`（実装済み）

順序は **診断つき再投入 → 引き直し → escalate**。手順ごとに `max_retries` を使い切って
なお通らなければ、作業ツリーを**手順開始時点へ戻して**独立に引き直し、全滅したときだけ
escalate になる。戻すのが要点で、前の抽選の成果を残したまま引くと、既にある blind 腕
（診断を渡さない再投入）と同じものを測ることになる。

実装で確定した細部（設計時に決めていなかったもの）:

- **引き直すのはゲートのある手順だけ。** 採択する機械がいない手順を引き直しても、
  同じ課題を複数回呼んだだけになる（自己申告での採択は P1 が外した道）。
- **`--resample > 1` は sampling の宣言を要求する**（aider 経路）。実効 temperature は 0
  なので、宣言なしの引き直しは同じ壁時計を払って同じ出力を受け取るだけになる。起動前に
  落とし、対照として測りたい場合の逃げ道は `--temperature 0` の明示とした
  ——ハーネスは「未宣言」と「既定値を明示」を別物として扱う既存の規律に乗せた。
- **既定（`--resample 1`）は従来と 1 バイトも変わらない。** 控えも戻しも走らないことを
  契約テストで固定した。既存台帳との比較可能性はここで守る。
- 台帳へ `resample` / `draws` / `escalate` を追加。`retry_count` は**診断つき再投入の
  回数**を数える定義へ直した（引き直しは初回投入なので数に入れない）。引き直しの無い
  既存の腕では従来と同じ値を返す。
- 戻しは**リポジトリ本体に対しては実行しない**（worktree を渡し間違えた事故で作業中の
  変更ごと消えるため、実行前に落とす）。

残るのは実測——採用条件は「escalate 率が下がり、対照群 T2gate に退行がない」こと。

### 案 2 — `agentcore/context_slice.py`（中核のみ実装）

対象シンボルとその依存だけを `ast` で決定的に抜き出す。LLM は使わない。

- **tree-sitter ではなく標準ライブラリの `ast` を使った。** 対象が Python に限られる
  代わりに、install.sh のオフライン完結（外部依存なし）という既存の不変条件を壊さない。
  他言語が要るのは、Python で効くと分かってからでよい。
- **切れないときは切らない。** 構文が壊れている・対象が見つからないなら `None` を返し、
  呼び出し側は原本へ倒す。CLI も同じで、倒したことを stderr へ必ず出す
  ——静かに原本へ倒れると、抜粋が効いていない条件で測ってしまう。
- **省いたものを見出しへ書く。** 抜粋が「これで全部です」と読まれるのが、切り詰めで
  一番高くつく事故になる。落としたシンボル名を必ず並べる。
- 実寸（自リポジトリの `worker_eval.py` で `check_t1` を対象）: **802 行 → 83 行**。
  依存（`probe_humansize` → `_probe_cases` → `HUMANSIZE_CASES` / `_pytest` / `VENV_PY`）は
  自動で辿る。

**本番配線は意図的に保留。** `--read` の材料をこれへ差し替えるのは、`agents/aider.json`
経路の入力を変える行為であり、段 3 の T1 / T3 比較（受入率と見落とし族の増減）を通す前に
既定へ入れない。現時点の使い方は CLI 経由の明示利用に限る。

```bash
python3 -m agentcore.context_slice eval/billing.py --symbol prorate -o /tmp/excerpt.py
```

## 4.2 未検討項目の棚卸し（2026-08-23）

`docs/plans/` と `tools/agent-tools/eval/` を横断し、**どの計画にも入っていない項目**と

分類は 3 つ。**A は本書の案の前提**（先に潰さないと案 1・案 2 の測定が運用へ移らない）、

### A. 本書の案の前提（最優先）

#### A1. (b) 族に引き直しが効くかは未測定 — 案 1 の効果範囲そのもの

失敗には 2 族ある（[gate-generality](../../tools/agent-tools/eval/results/archive/2026-08-14-gate-generality-report.md)）。
**(a) 仕様の読み違い族**は真偽ゲート + 再投入で直る。**(b) 作業の丸ごと欠落族**は直らない
——T3gate は全 9 attempt が同一の `C3 fail: 契約テストが追加されていない` で 0/3。診断文が
毎回「何が欠けているか」を明示しているのに、モデルは一度もテストを書かない。

**P10 の sampling 実測が動かしたのは T1（a 族）だけで、(b) 族を推奨 sampling で引き直した
記録は無い**——台帳 `ledger-2026-08-15-p10-worker-sampling.jsonl` の 12 行は T1 と T2 だけで、
T3 / T3gate の行は 1 本も無い。ここが案 1 の採用条件に直撃する——採用条件は「escalate 率が下がること」だが、
escalate の主因が (b) 族なら、引き直しは同じ壁時計を払って同じ欠落を受け取るだけになる。

したがって案 1 の腕は **T1gate（a 族）と T3gate（b 族）を必ず分けて読む**。(b) が動かない
場合の答えは引き直しではなく、**成果物を 1 つに割る**（＝ A2 の適格条件を満たす形へ分解する）
である。この切り分けを腕の設計へ足す。

#### A2. 局所修正の適格判定が「記録」止まりで、「拒否」へ配線されていない

`agentcore.nodecontract.local_patch_blockers()` は適格条件を機械判定する（書込 1 ファイル・
成果物 1 つ・`verification.commands` あり・テスト / schema / 文書の新規作成でない・protected 外）。
だが**呼び出しは `agent_flow/work.py` の 1 か所だけで、claim / result のメタへ理由を残すだけ**
である（コード上のコメントも「事実として残す」）。`executionresolver.py` は blockers を読まない。

つまり [2026-08-18 assessment](2026-08-18-agent-aider-improvement-assessment.md) の Phase 4-1 /
4-2（「checker が無い場合は自動選択しない」）は**観測までしか入っていない**。同 assessment の
`[ ]` 表記も現状と合っていない——1・2 は半分入り、3・4（限定 retry と上限到達での昇格）は
statemachine 側に入っている。**assessment の Phase 4 チェックリストは実装と突き合わせ直す。**

効き方: 案 1 も案 2 も「適格な局所修正」を前提にした腕である。本番が不適格タスクへ aider を
割り当てられる限り、ハーネスで測った escalate 率はそのまま運用へは移らない。**拒否を配線するか、
配線しないなら「測定値は上限であって運用値ではない」と明記するか、どちらかを決める。**

#### A3. `run_suite.py` が腕の条件を通さず、manifest にも残さない

`run_suite.py` が `worker_eval.py` へ渡すのは `--model` / `--cli` / `--repeat` / `--wall` の
4 つだけである。`--tasks` / `--agent-policy` / `--num-ctx` / `--num-predict` / sampling、
そして新設の `--resample` はいずれも渡らず、`manifest.json` にも載らない。

README は manifest を「比較条件」と説明しているが、**腕を変える軸がそこに無い**。標準測定の
経路から腕を回すと、条件が manifest と食い違ったまま結果だけが `results/` に残る——本書が
案 1 で守った「条件を台帳へ必ず残す」規律が、1 階層上で破れている。引数の透過と manifest への
追記だけの小さい修正なので、案 1 の A/B を回す前に塞ぐ。
