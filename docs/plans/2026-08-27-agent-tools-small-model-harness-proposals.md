# 小型モデルを agent-tools で安全に使うための改善案

> 作成: 2026-08-27
>
> 状態: 提案。**Phase 1 の配線部分は 2026-08-29 に入れた**（§9 Phase 1）。
> 効果の実測（§6 の 4 腕比較）はこれから。
>
> 想定モデル: `gemma4:e4b` などの小型ローカル LLM

## 1. まず、何を変えたいのか

小型モデルに長い仕事を丸ごと任せると、次のような失敗が起きやすい。

- 最初の修正は合っていたのに、その後も作業を続けて壊す。
- 同じコマンドや同じ修正を繰り返す。
- テストを実行していないのに「完了した」と答える。
- 長いログや多数のファイルを渡すと、重要な箇所を見失う。

そこで、モデルを賢く見せるために指示を増やすのではなく、**モデルが一度にできることを一つに絞る**。

具体的には、モデルに次の一手だけを実行させる。

1. agent-tools が必要なファイルとエラーだけを集める。
2. 小型モデルが修正を一つ行う。
3. agent-tools がテストや差分を確認する。
4. 合格なら終了する。不合格なら、原因に合った情報だけを渡して一度だけ直させる。
5. 改善しない場合は、小型モデルを繰り返し呼ばず、上位モデルまたは人へ回す。

この方式を本文では **制限付き実行** と呼ぶ。

```text
依頼
  ↓
必要なファイルと検証方法を準備        ← agent-tools が行う
  ↓
修正を一つだけ実行                    ← 小型モデルが行う
  ↓
テスト・差分・終了コードを確認        ← agent-tools が行う
  ├─ 合格 → 完了
  ├─ 修正可能 → 必要なエラーだけ渡して、もう一度修正
  └─ 改善なし／上限到達 → 上位モデル・別ノード・人へ回す
```

重要なのは、**小型モデル自身に「続けるか」「合格か」を決めさせない**ことである。

## 2. 利用者から見ると何が変わるか

### 変更前の例

`gemma4:e4b` に「この不具合を調べて修正し、テストして」とまとめて依頼する。
モデルは調査、編集、テスト、再修正を自分の判断で繰り返す。途中で正しい修正ができても、
余計な編集や再試行によって結果を壊す可能性がある。

### 変更後の例

agent-tools が仕事を次のように制御する。

1. 変更してよいファイルを `src/parser.py` に限定する。
2. モデルには `src/parser.py` と失敗中のテストだけを渡す。
3. モデルに修正を一つだけ実行させる。
4. agent-tools が `pytest tests/test_parser.py` を実行する。
5. 成功し、範囲外の差分がなければ完了にする。
6. 構文エラーなら、そのエラーと該当箇所だけを渡して一度修復させる。
7. 同じ失敗が続いたら、上位モデルまたは人へ回す。

利用者が毎回この手順を指定する必要はない。実行方針で「制限付きローカル実行」を選ぶと、
agent-tools が自動で適用する形を目指す。

## 3. どのツールを、どう変えるのか

最初から全ツールを変更しない。まず共有部品を一つ作り、効果を確認してから接続先を増やす。

### 3.1 agentcore: 制限と停止判定を実装する

**変更する場所の候補**

- `tools/agent-tools/agentcore/agentcore/harness/toolloop.py`
- `tools/agent-tools/agentcore/agentcore/executioncontract.py`

**追加する動作**

- 一回のモデル呼び出しで実行できる操作を一つに制限する。
- モデル呼び出し回数、修正回数、再計画回数に上限を設ける。
- 同じ操作を繰り返していないかを判定する。
- 修正前後のファイル内容とテスト結果を比べ、進展があるかを判定する。
- 終了時に「合格」「上限到達」「同じ失敗を反復」「範囲外変更」などの理由を残す。

**影響**

agentcore の tool loop を利用する agent-loop と agent-herd に同じ制限を適用できる。
ツールごとに停止判定を別実装しないため、完了や失敗の意味が揃う。

**変えないこと**

- agentcore がプロジェクト固有のテストコマンドを決めることはしない。
- 既存の無制限に近い実行を直ちに廃止しない。最初は設定で有効にした実行だけが対象になる。

### 3.2 agent-flow: 局所的な実装タスクで使う

**変更する場所の候補**

- `tools/agent-flow/agent_flow/work.py`
- `tools/agent-flow/agent_flow/verifyplan.py`

**追加する動作**

- 小型モデルへ渡す作業に、変更可能なファイル、実行する検証、最大試行回数を付ける。
- 失敗時は全ログではなく、失敗したテストと関係する差分だけを再入力する。
- agentcore から返された停止理由を、agent-flow の result と実行記録へ残す。
- 上限到達時は同じモデルで再試行せず、既存の再試行規則（retry ladder）に従って上位候補へ回す。

**最初に対象とする仕事**

- 一つまたは少数ファイルの修正
- 失敗テストが明確な修復
- 抽出、分類など、出力形式が決まっている処理

**対象にしない仕事**

- リポジトリ全体の実装計画
- 多数の機能をまたぐ設計判断
- 曖昧な要求を分解する最上流 planner

**影響**

小型モデルで成功しやすい仕事だけを安全にローカルへ移せる。一方、agent-flow の DAG、既存 planner、
GitLab 実行、成果物の統合方法は変更しない。

### 3.3 agent-loop / agent-herd: 同じ操作の反復を止める

**変更する場所の候補**

- `tools/agent-loop/agent_loop/toolloop.py`
- 実処理は agentcore の `harness/toolloop.py` を利用し、agent-loop 側には重複実装しない。

**追加する動作**

- 制限付き実行を選んだ routine で、agentcore の回数上限と進展判定を有効にする。
- 終了理由を routine の結果へ表示する。

**影響**

自動実行中に小型モデルが同じ編集や確認を繰り返す問題を止められる。
通常の対話セッションや、クラウドモデルを使う既存 routine には自動適用しない。

### 3.4 検証機能: モデルの自己申告ではなく、実行結果で合否を決める

**利用する既存機能**

- `tools/agent-flow/agent_flow/verifyplan.py`
- `tools/agent-project/agent_project/verify.py`
- codd-gate
- `schemas/verification-plan.schema.json`

**変更内容**

検証は次の順で行う。

1. 必須ファイルが存在するか。
2. 許可されていないファイルを変更していないか。
3. test、compile、lint の終了コードが成功か。
4. ファイル内容や件数など、機械的に確認できる受入条件を満たすか。
5. 自然文でしか判断できない条件が残る場合だけ、読み取り専用の検証モデルを使う。

**影響**

小型モデルが「できた」と答えても、証拠がなければ完了にならない。既存の verification plan を
検証方法の正本として使うため、新しい検証システムは作らない。

### 3.5 agent-audit: 本当に効果があるか測る

**変更する場所の候補**

- `tools/agent-audit/agent_audit/qualifications.py`
- `tools/agent-audit/agent_audit/tuning.py`

**追加する記録**

- 使用したモデルと実行方針
- モデルを呼んだ回数
- 同じ操作を止めた回数
- テスト合格率
- 未検証なのに完了扱いした割合
- 上位モデルへ回した割合
- 所要時間とトークン数

**影響**

`gemma4:e4b` が使えるかどうかをモデル名だけで判断せず、
「局所修正を制限付きで実行した場合」のように仕事と実行方法の組み合わせで評価できる。
公開ベンチの数字は採用根拠にせず、このリポジトリの評価結果を使う。

### 3.6 agent-project: 実行方針と上位への振り替えを決める

**変更内容**

- 仕事に適用する実行方針として、評価済みの「制限付きローカル実行」を選べるようにする。
- 小型モデルが上限に達した場合、既存の候補選択に従い、上位モデル、別ノード、人への確認の順に回す。
- 品質検証を省略して安いモデルを使うことは認めない。

**影響**

agent-project は個々の編集を制御せず、「どの実行方法を使うか」と「失敗後にどこへ回すか」だけを
担当する。既存のバックログ、needs、納品フローは変更しない。

### 3.7 agent-dashboard: 設定と結果を人に説明する

**変更する場所の候補**

- `tools/agent-dashboard/src/features/orchestration/main/control.js`
- `tools/agent-dashboard/src/features/orchestration/main/qualifications.js`
- `tools/agent-dashboard/src/features/orchestration/main/recommendation.js`

**画面に追加する情報**

- 実行方針: 通常 / 制限付きローカル
- 最大モデル呼び出し回数と最大修正回数
- 現在の試行回数
- 停止理由
- 次に上位モデル、別ノード、人のどこへ回ったか
- この実行方針が評価済みか、試行中か、利用不可か

**影響**

利用者は「なぜ止まったのか」「失敗後に何が起きたのか」を画面で確認できる。
モデルの内部思考や長い生ログは表示しない。また、dashboard 自身がモデルの適格性を決めることはしない。

### 3.8 agent-amigos: 今回は後回しにする

agent-amigos の合議や曖昧な判断は、一回一操作にしにくい。そのため初期導入の対象外とする。
agent-flow と共有 tool loop で効果が確認できた後、形式が決まった成果物作成などに限定して検討する。

## 4. 変更範囲を一覧で確認する

| ツール | 初期段階で変更するか | 何が変わるか | 影響を受けない主な機能 |
|---|---|---|---|
| agentcore | はい | 回数上限、反復検知、進展判定、停止理由 | プロジェクト固有の検証内容 |
| agent-flow | はい | 対象タスクへの制限適用、失敗情報の絞り込み、上位への振り替え | DAG、planner、GitLab 実行、統合 |
| agent-loop / herd | はい | 明示的に有効化した定期処理で共有制限を利用 | 通常対話、未指定の定期処理 |
| verification / codd-gate | 小変更 | 証拠の確認順序と結果の参照 | 既存 verification plan の正本性 |
| agent-audit | はい | 実行方針別の評価と記録 | 既存評価 archive |
| agent-project | 後段 | 方針選択と上位候補・人への振り替え | backlog、needs、納品 |
| agent-dashboard | 後段 | 方針、試行回数、停止理由の表示 | 根拠の生成、実際の実行 |

## 5. 最初に実装する最小単位

一度にすべて作らない。最初の変更は次の四つに限定する。

1. agentcore の共有 tool loop に最大モデル呼び出し回数を追加する。
2. 操作内容、対象ファイル、修正前後のファイル内容から、同じ失敗の反復を検知する。
3. 合格、呼び出し上限、進展なし、範囲外変更を区別できる停止理由を記録する。
4. agent-flow の局所修正タスク一種類だけから、明示的に有効化して利用する。

この段階では schema、dashboard、agent-project の設定画面を増やさない。固定した評価条件で効果を測り、
効果がなければ共有 tool loop の変更だけを撤回する。

## 6. 効果の確認方法

同じモデル、同じ課題、同じリポジトリ revision、同じテストを使い、次を比較する。

| 比較対象 | 内容 |
|---|---|
| 現行方式 | モデルが現在の方法で作業する |
| 回数制限のみ | モデル呼び出しを最大 3 回にする |
| 回数制限 + 反復停止 | 最大 3 回に加え、進展のない同一操作を止める |
| 完成候補 | 上記に失敗別の再入力と検証順序を加える |

合格条件は次のすべてである。

- テスト合格率が現行方式より下がらない。
- 未検証の完了や範囲外変更が増えない。
- 平均モデル呼び出し回数、同じ操作の反復、または所要時間のいずれかが減る。
- 上限到達時に偽の完了にならず、上位モデルまたは人へ正しく回る。

「完成候補」が「回数制限のみ」より改善しなければ、複雑な仕組みは採用しない。

## 7. 失敗したときの扱い

| 起きたこと | agent-tools の対応 | 小型モデルへ再入力するもの |
|---|---|---|
| 出力形式が壊れた | 有効な形式を示して一度だけ再出力 | 形式エラーと利用可能な選択肢 |
| 構文・コンパイルエラー | 同じ修正を一度だけやり直す | 該当ファイルとエラー箇所 |
| テスト失敗 | 失敗テストに絞って一度修正する | 失敗テスト、関連差分、短いエラー |
| CLI や認証の問題 | モデルに直させず、待機または別ノードへ回す | 再入力しない |
| 同じ失敗を反復 | ローカル実行を停止し、上位へ回す | 再入力しない |
| 許可外ファイルを変更 | 変更を採用せず、停止する | 再入力しない |
| 原因不明 | 安いモデルで推測を繰り返さず、上位へ回す | 再入力しない |

## 8. 今回やらないこと

- 外部 OSS のハーネスを agent-tools の代わりに導入する。
- `gemma4:e4b` にリポジトリ分析、計画、実装、レビューをすべて任せる。
- モデルへ自由な shell と全ファイルを渡す。
- すべてのモデルとタスクを一律 3 回に制限する。
- モデルの「完了しました」を検証の代わりにする。
- 新しい workflow engine、memory DB、検証台帳を作る。
- 最初から dashboard や共有 schema を大規模に変更する。

## 9. 実装順序

### Phase 1: 小さく試す

agentcore に回数上限、反復検知、停止理由を追加し、agent-flow の局所修正一種類だけで評価する。

**2026-08-29 に配線を入れた。**「追加」ではなく**既存機構の統一・設定化**として実装している
——回数上限も反復検知も進展判定も 3 層（`harness/toolloop` / `harness/statemachine` /
`ollama_loop`）に実装済みで、無かったのは設定可能な上限・共通の綴り・結果への表出の 3 つ
だけだった（適用性レビュー §3-8）。同じ判定を 3 層へ重複させていない。

| 入れたもの | 置き場 |
|---|---|
| 上限の決まり方（宣言 ＞ 環境変数 ＞ 層の既定 8） | `harness/toolloop._tl_max_rounds` |
| ステート単位の宣言 `max_tool_rounds` | statemachine-use の state キー（`check_retries` と同階層） |
| 編集の周だけ締める腕 | `AGENT_MAX_TOOL_ROUNDS_WRITE`（`write:` を持つ state 限定）と `AGENT_MAX_TOOL_ROUNDS` |
| 停止理由の共通語彙 | `agentcore/stopreason.py`（`vocab.py` と同じ形。判定は移していない） |
| 結果への表出 | 各層の戻り値の `stopReason` / `stop_reason`、agent-loop の `RESULT` 行、ツールループの `goal_done` ログ |

環境変数を分けたのは E4B の推奨帯（編集は 2〜3 周）が**編集の周にだけ効く**ためで、
read 系・判定系まで一律に締めると調査の周が足りなくなる。

**宣言が環境変数に勝つ**ので、宣言を持つ経路は環境変数では締まらない——
`agents/ollama.json` の `write_args` は `--max-rounds 12` を宣言しているため、
`agent-ollama` の本番実行がまさにそれにあたる。腕を引くときは宣言側で引く
（`worker_eval.py --max-rounds`。台帳の `max_rounds` に残る）。測定条件が運用の宣言を
黙って上書きする形にはしない。

**まだ無いもの**: `out_of_scope`（許可外ファイルの変更）は語彙だけ置いて配線していない
——証跡ゲートは受入条件が名指しした path しか見ず、ハーネスは git を使わない
（スラッシュ再構成設計 段 9b への依存）。

### §6 の腕を引いた（2026-08-29）— 4 腕は 3 腕にしかならない

**4 腕のうち 2 本は現行実装に継ぎ目が無い。**

- 「回数制限 + 反復停止」を「回数制限のみ」から分離できない。反復停止（`_MAX_REPEATS`）は
  常時オンで、切る口が無い——**測定のためだけに安全装置のオフスイッチは足さない**
  （§5 の「既存の挙動を直ちに廃止しない」と同じ側の判断）。
- 「完成候補」の失敗別再入力は `_sm_check_note`（statemachine）に入っていて、
  evaluation harness のゲートループは元から短い診断しか渡していない。この経路で
  上乗せとして測れるものが無い。

引けたのは上限の 3 段（12 / 3 / 2）で、外部実測（state-harness の naive turn cap）が
測った軸そのものである。T2 × agent-ollama × gemma4:e4b × n=3:

| 腕 | 受入 | 中央値 | 終わり方 |
|---|---|---|---|
| 12（定義のまま） | 0/3 | 600s | timeout 3/3 |
| 3 | 0/3 | 600s | timeout 2/3・自己申告の未完了 1/3 |
| **2** | 0/3 | **51s** | 自己申告の未完了 3/3 |

**§6 の合格条件で読む。** (1) 合格率は下がらない——ただし 3 腕とも 0/3 なので**主張できる
差は無い**（n=3 は全滅 ⇔ 全通だけを差にする）。(2) 偽の完了・範囲外変更は増えない——
切れた腕は `self_reported_incomplete` で返り、無言の timeout より上位への振替が正しく起きる。
(3) 所要時間が減る——**600s → 51s（−92%）**。(4) 上限到達で偽の完了にならない——満たす。

**結論は 2 つ。** 上限は**品質のレバーではない**（受入は動かない。state-harness の +35pp は
この課題 × この層では再現しない）。上限は**失敗を安くするレバーである**（同じ壁時計予算で
11 回多く試せる・上位へ回せる）。

**副産物の発見**: 上限 12 と 3 は**到達しない**。1 周が 200〜300s かかるので壁時計（600s）が
先に切る——この経路で実際に効いたのは 2 だけだった。「回数上限」は、1 周が壁時計予算に対して
十分安いときにしか意味を持たない。**上限と壁時計は同じものの 2 つの表現ではない**。

§6 のゲート（「完成候補が回数制限のみに勝たなければ複雑な仕組みは採用しない」）は、
完成候補を作っていないので**そのまま効いている**——回数制限で止める。

### Phase 2: 失敗別の修復を追加する

構文エラーとテスト失敗に限り、必要な情報だけを渡す再試行を追加する。

**2026-08-29 に選別を入れた。** 検査が落ちた後の再投入は、それまで実出力の末尾 2000 字を
無選別で課題文へ足していた。いまは決定的パーサ 1 つが失敗した行だけを選ぶ——short summary の
`FAILED` / `ERROR` 行と、pytest が失敗の中身として印字する `E   ` 行（AssertionError・
SyntaxError・ImportError はすべてこの形）。**分類器は書いていない**（§7 の表は仕様として使い、
実装は既存機構への写像に留める）。選別できない出力は従来どおり末尾を渡し、そのときは
「省略した」と本文に書く——静かに落とすと、材料が足りなかったのかモデルが読めなかったのかを
後から分けられない。

置き場は `check_feedback_note`（statemachine-use の engine が正典）と、ハーネス側の
`_sm_check_note`。2 実装が同じ行を選ぶことは agentcore の契約テストが縛る。
効果（再試行の速さ・受入率）は Phase 1 の腕と同じ枠組みで測る。

### Phase 3: 評価済みの仕事へ広げる

抽出や分類など、決まった形式の仕事へ適用範囲を広げる。agent-audit で仕事ごとに適格性を記録する。

### Phase 4: 運用画面へ出す

効果が確認できた設定だけを agent-project の選択方針と agent-dashboard の表示へ追加する。

## 10. この提案が完了したと言える状態

- 利用者が、どの仕事に制限付き実行が使われたか確認できる。
- 小型モデルが何回呼ばれ、なぜ終了したか実行記録から分かる。
- テストまたは明示された受入条件を満たさない限り完了にならない。
- 同じ操作を繰り返しても、決められた回数で必ず停止する。
- 停止後は、品質基準を下げずに上位モデル、別ノード、人のいずれかへ回る。
- agentcore に停止判定の実装が一つだけあり、各ツールがそれを共有する。

## 11. agent-tools の方針との関係

この案は次の二点に効く。

- **人介在の最適化:** 機械で確認できる失敗を人へ持ち込まず、必要な場合だけ証拠と停止理由を揃えて渡す。
- **資源効率:** 小型ローカルモデルで処理できる仕事を増やしつつ、無駄な反復を止め、クラウドモデルを
  難しい判断へ温存する。

品質を下げて安いモデルを使う案ではない。どのモデルを使っても、完了の条件は既存の検証結果で決める。
