# ホームからの天気質問が回答されない不具合

## 確認した事実

2026-09-21 の会話 `bd1b3623-b3a6-4d3d-8f2f-c5a92b404449` を調査した。
入力は「今日の天気は？」、判定は answer（0.96）、自動選択は ollama / gemma4:e4b。
選択されたモデルは設定上の候補であり、選択そのものの失敗を示す証拠はなかった。

Ollama の 12:59:29 の実行ログでは `prompt_chars=0`、toolset=read。
空の `/find` で12ラウンドのローカル探索が始まり、その後も共通指示の各行が
別々の plain 実行になっていた。会話に保存された応答には入力エコーが混入し、
共通指示のサンプル `[集計結果](reports/result.xlsx)` が成果物リンクに見えていた。
実際にそのファイルを作った証拠はない。

## 原因

1. app の `paste-buffer -p` は受信側が bracketed paste に対応する前提。
   共通 TUI は行単位で読むうえ、readline の bracketed paste を無効にしていた。
   macOS の libedit も考慮せず、複数行の依頼を一件として送信できていなかった。
2. answer 判定を readonly に置き換え、herd の `/find`（ローカル調査）へ送っていた。
   この道具は最新の天気を取得できず、調査用指示には質問しない規則もある。
3. 回答中の相対パスを、実在確認なしに成果物ボタンとして表示していた。

## 修正

- 共通 TUI は起動時に `input=prompt-file-v1` を告知する。
  app は短い `@agent-prompt-file <JSON形式の絶対パス>` を端末へ送り、
  TUI が UTF-8 ファイル全体を読み込んだ後で既存のスラッシュ処理へ渡す。
  ファイルは CLI ホストの /tmp に UUID と mode 0600 で作成し、完了・送信失敗時に削除する。
  旧 TUI には複数行を送らず、更新・再起動が必要だと通知する。
- answer を `/ask` に写す。場所などが不足した場合は確認し、取得できない最新情報は推測しない。
  回答のみの依頼には成果物やフォルダ分岐の指示を付けない。
- 共通指示の架空の Excel リンク例を削除する。
- リポジトリ／worktree 内の実在する通常ファイルだけを成果物として表示する。
  欠落ファイルの Markdown リンクはテキストに戻す。外部への symlink も除外する。

## 検証

- 修正前に複数行入力、answer → /ask、成果物実在確認の回帰テストが失敗することを確認。
- tmux と共通 TUI の統合テストで、長い日本語の依頼が一度だけ欠落なく届き、
  回答に入力エコーが混入せず、一時ファイルが片付くことを確認。
- 実モデル gemma4:e4b に同じ質問を送信。plain モード、1ラウンド、約21秒で
  「リアルタイムの天気情報を取得できない」と説明し、具体的な場所を尋ねる回答が返った。
  空のローカル探索と架空の成果物リンクは発生しなかった。

- app の対象テスト66件、周辺テスト86件、成果物検査7件、agentcore の関連テスト141件が通過。
- 独立した Electron 成果物テストも通過（実在リンク・欠落リンク・ボタンを検証）。
- 既存の広範な reuse UI テストは成果物検査を通過した後、モデル入力欄 `#model` が
  非表示・無効のため停止した。今回はその別機能の画面ロジックを変更していない。

## 反映と制約

リポジトリの app と agentcore を修正。このPCの agent-herd / agent-ollama / agent-aider
にも共通 TUI の修正を反映した。稼働中の app と既存の TUI は再起動が必要。
過去の会話本文は書き換えていない。

この修正は天気情報の検索サービスを追加するものではない。道具なしのローカルモデルは
最新の天気を取得できないため、その制約を正しく答える。実測回答は一試行であり、
同じ文言の生成を保証するものではない。
