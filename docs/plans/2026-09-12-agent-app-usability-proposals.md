# agent-app: 手作業を減らす使い勝手の提案

日付: 2026-09-12 / 対象: `tools/agent-app` / 状態: **提案（未承認・未実装）**

## 0. 一文で

画面の部品は増やさず、**利用者が毎回自分の手でやっている往復**（端末へ行って y を打つ、前と同じ
依頼を打ち直す、ログを読んで編集の会話へ貼る、実行条件を打ち直す、終わったかを見に戻る）を、
既にある部品（`.message-action` / `.phase` / `.execution-card` / 設定の行）の上に**1 押しの操作か
既定値**として置く。新しい画面は作らない。

## 1. 守る境界（この提案が触らないもの）

README「持たないもの」と設計書 §1.2 はそのまま守る。

- ツール呼び出しの逐次承認 UI は作らない。CLI が端末で聞いたら答えるのは人。ここで足すのは
  **その答えを端末へ送る近道**であって、何を聞かれているかの意味解析ではない。
- アプリ自身は git へコミット・push しない。コミットしたいときも **CLI に頼む文を送る**だけ。
- LLM を追加で呼ばない（ADR-6 と同じ）。自動化は既定値・記憶・固定文で行う。
- 登録リポジトリの外を触らず、画面から生のパスを受け取らない（ADR-2）。

## 2. 手作業の棚卸し

実装（`renderer.js` / `automation/renderer.js` / `tmux.js`）と仕様書の「画面の使い方」から、
利用者が毎回自分の手で繰り返している操作を拾った。右の列は 1 回あたりの押す回数の目安。

| # | いまの手作業 | 根拠 | 押す回数 |
|---|---|---|---|
| A | CLI の y/n・許可の確認に答える: 会話一覧の「確認待ち」を見る → 会話を開く → 端末をクリック（端末操作へ） → `y` → Enter → Esc 2 回でメッセージへ戻る | 仕様書「会話する」3、`inputMode.js` | 6 |
| B | ターンが終わったあとの定型の依頼（「テストを回して」「コミットして」「変更を要約して」）を毎回打つ | 変更ビューは読むだけで、コミットは「CLI に頼む」と仕様書が案内 | 1 文 + 送信 |
| C | 前に送った依頼を少し変えて送り直す: 会話履歴を開く → 文を選択してコピー → 入力欄へ貼る | 利用者メッセージの操作は「この依頼をタスクにする」だけ（`renderer.js` 1078） | 4 |
| D | タスクの手動実行で「毎回変わる値」を打つ: 実行のたびに空欄（`state.run.parameters = {}`）。定期実行に書いた既定値は写るが、前回手で入れた値は残らない | `automation/renderer.js` 300, 681, 2066 | 値の数だけ |
| E | タスクが失敗したとき AI に直してもらう: 履歴の「ログ」を開く → 読む → 「手順」→「編集」で会話を起こす → 失敗の箇所を手で説明する | `automation/renderer.js` 1054–1057 | 5 + 1 文 |
| F | 応答が終わったか・確認待ちになったかを見に戻る: 別の会話や別のアプリにいる間は分からない | OS 通知・フレーム点滅の実装が無い（`Notification` を使っていない） | 随時 |
| G | 変更ビューで見たファイルを依頼に載せる: 差分を見る → ダブルクリックでビュアー → 「会話に添付」 | 変更ビューの行には添付が無い（`renderer.js` 1525） | 3 |
| H | 会話を探す: 一覧は更新順のみで、絞り込みも名前の変更も無い。名前は最初の依頼の先頭 60 字 | `store.js` 321 | スクロール |

A・F は「待つ・見に戻る」の往復、B・C・E・G は「同じ文・同じ所在を手で運ぶ」往復、D・H は
「前と同じ値を打ち直す・探す」往復である。

## 3. 提案

優先順位は「減る手作業 × 既存部品だけで組めるか」。上から 3 つ（3.1〜3.3）で棚卸しの A・B・C・F が
消える。各提案に、借りる既存画面の作法を併記する（CLAUDE.md の約束）。

### 3.1 確認待ちに、端末へ行かずに答える（A）

**提案。** 会話ヘッダーの「確認待ち」（`.phase`）を押せるようにし、`attentionDetail` が既に拾っている
聞かれている文（最大 1200 字）と、端末へそのまま送るキー 3 つを出す。送るのは端末操作モードと同じ
`send-keys`（`y` + Enter / Enter / Esc）で、新しい IPC は要らない。サイドバーの「確認待ち」の印にも
同じものを出せば、会話を開かずに答えられる。

```text
┌ 会話ヘッダー ──────────────────────────────────────────────────────┐
│ ログイン画面の工程を直す            [確認待ち ▾]     会話 | ファイル │
└─────────────────────────────────────┬──────────────────────────────┘
                                      │ ポップオーバー（.settings-popover と同じ形）
                                      ├──────────────────────────────┐
                                      │ 端末で確認を求めています      │ ← popover-head
                                      │ Allow Bash(npm test)?        │ ← attentionDetail の本文（.sub、等幅）
                                      │   1. Yes  2. Yes, don't ask  │
                                      │   3. No                      │
                                      │                              │
                                      │ [はい(y)] [Enter] [いいえ(Esc)]  [端末で答える] │ ← .row、.small
                                      └──────────────────────────────┘
```

- 借りる形: 入力欄の「実行設定」（`details.run-settings` + `.settings-popover`）。`.phase` を `summary` に
  するだけで、ボタンは `.small`。主ボタンは置かない（色は状態の区別にだけ使う）。
- 「端末で答える」は今の動き（端末操作モードへ切り替えて焦点を移す）。矢印で選ぶ CLI はこちら。
- 数字で選ばせる CLI（claude の `1. Yes`）には `1` を送る必要があるが、**文面の意味解析はしない**。
  送るキーは 3 つに固定し、合わなければ「端末で答える」。
- 触る場所: `renderer.js` の `renderHeader` / `renderSessions`、`index.html` の `#phase`、`styles.css`
  は既存クラスの組み合わせのみ。テスト: `test/app.test.js` に「確認待ちの 3 キーは端末操作と同じ
  `term:keys` を通る」を足す。
- 大きさ: 小。

### 3.2 ターンが終わったら「次の一手」を 1 押しで送る（B）

**提案。** 最後の応答の下に、設定で決めた**定型の依頼**を `.message-action` として最大 3 つ並べる。
押すと本文がそのまま入力欄に入る（送信はしない。「操作の見本」の `open` / `stop` と同じ作法。ADR-13）。
定型の文は「設定 > 共通指示」に**起動時アクションと同じ行の形**で持つ。既定は 2 つ
（「変更をコミットする」「テストを実行する」）で、コミットは CLI に頼む文なので git の境界は越えない。

```text
┌ 会話履歴 ──────────────────────────────────────────────────────────┐
│ ▸ 思考・進捗                                                       │
│ ┌────────────────────────────────────────────────────────────────┐ │
│ │ login の工程を 3 つに分け、dry-run を通しました。               │ │
│ └────────────────────────────────────────────────────────────────┘ │
│ ▸ 実行情報                                                         │
│ [変更をコミットする] [テストを実行する] [変更を要約する]   ← .message-actions（既存） │
└────────────────────────────────────────────────────────────────────┘

設定 > 共通指示
  ┌ 定型の依頼  回答の下に並べる。押すと入力欄に入る          [追加] ┐ ← .settings-group-head
  │ [変更をコミットする     ] [未コミットの変更を読み、1 つのコミットに…] [×] │ ← .startup-row と同じ
  │ [テストを実行する       ] [変更した対象のテストを実行し、結果を要約…] [×] │
  └──────────────────────────────────────────────────────────────────┘
```

- 借りる形: 「この依頼をタスクにする」「→ 分岐先」（`.message-actions` / `.message-action`）と、
  起動時アクションの行（`.startup-row`）。
- 出すのは**最後の応答の下だけ**（履歴の全応答に並べると画面が埋まる）。応答中は出さない。
- 触る場所: `settings.js` の `instructions.quickRequests`（正規化・上限 3）、`renderer.js` の
  `messageNode` と設定画面、`index.html` の設定 1 群。テスト: `test/settings.test.js` に正規化、
  `test/app.test.js` に「入力欄に入るだけで送らない」。
- 大きさ: 小〜中。

### 3.3 終わった・確認待ちになったことを OS の通知で知らせる（F）

**提案。** ウィンドウが前面に無いとき、ターン完了・確認待ち・送信失敗・タスクの手動実行の完了を
Electron の `Notification` で 1 行出す（会話名と状態だけ。本文は出さない）。押すとその会話を開く。
設定 > アプリに「バックグラウンドで通知する」のチェック 1 行。Windows はタスクバーの点滅
（`flashFrame`）も同時に行う。

```text
設定 > アプリ
  ☑ 対話セッションを維持        tmuxを使って、エージェントとの会話を継続します
  ☑ 会話ごとに作業を分離        Git worktreeで同時作業の変更が混ざらないようにします
  ☑ 前面に無いときに通知する    応答の完了と確認待ちを OS の通知で知らせます   ← 追加（.setting-check）
```

- 借りる形: 設定 > アプリの `.setting-check` 行。画面本体には何も足さない。
- 触る場所: `main.js`（`Notification` / `flashFrame`、`BrowserWindow.isFocused`）、`ipc.js` の phase 更新と
  `turn:done` の 1 か所、`settings.js` の `notify` 既定 ON。通知の文は「<会話名> · 確認待ち」のように
  `PHASE_LABEL` を使い、内部の綴りを出さない。
- 大きさ: 小。

### 3.4 タスクの「毎回変わる値」は前回の値を覚える（D）

**提案。** 手動実行で入れた値をタスクごとに `config.json`（`lastTaskInputs[<repo>][<保存名>]`）へ
覚え、次回は**前回の値を既定**にする。入力欄の横に「前回: 2026-08」と `.sub` で 1 行。優先順位は
「今回打った値 → 前回の値 → 定期実行の既定値」。保存するのは値だけで、パスは持たない。

```text
┌ .execution-card 手動実行 ─────────────────────────── [待機中] ┐
│ 実行条件                                                      │
│  month   [2026-08        ]  前回: 2026-08（8/31 実行）  ← .sub │
│  target  [sales          ]  前回: sales                      │
│  …（使う AI・実行ボタンは今のまま）                            │
└───────────────────────────────────────────────────────────────┘
```

- 借りる形: 今の「実行条件」（`.run-inputs`）。足すのは `.sub` の 1 行。
- 触る場所: `automation/renderer.js`（`state.run.parameters` の初期化 300 / 681 行）、`automation/ipc.js`
  の `configAdapter`、`settings.js`。テスト: `test/automation-app.test.js`。
- 大きさ: 小。

### 3.5 失敗した実行を、ログごと AI に渡す（E）

**提案。** 実行履歴の失敗した行に「ログ」の隣へ「AIに直してもらう」を足す。押すと「手順」→「編集」と
同じ会話を起こし、最初の依頼に**失敗した実行のログの所在**（リポジトリ内の相対パス。Windows は
WSL 表記へ直す）と「この失敗を直して」の固定文を入れて**入力欄に置く**（送るのは利用者。見本の
`stop` と同じ）。ログが agent-loop の外（userData）にあるときは添付として写す（既存の添付経路）。

```text
┌ .execution-card 実行履歴 ──────────────────────────────────────┐
│ 直近の手動実行と定期実行                                         │
│  [失敗] 手動実行  9/12 10:02 · claude     [ログ] [AIに直してもらう]  ← .tiny（既存） │
│  [完了] 定期実行  9/11 09:00 · herd       [ログ]                   │
└─────────────────────────────────────────────────────────────────┘
```

- 借りる形: 履歴の行と `.tiny` ボタン、「手順」→「編集」の会話（`task-launch`）。
- 触る場所: `automation/renderer.js` の履歴行、`taskTeaching.js`（編集開始時の初期本文）、
  `ipc.js` の `automation:teach:start` に `prefill` を 1 項目。テスト: `test/automation-teaching.test.js`。
- 大きさ: 中。

### 3.6 依頼を「入力欄に戻す」（C）

**提案。** 利用者メッセージの `.message-actions` に「入力欄に戻す」を足す（「この依頼をタスクにする」の
隣）。本文と、そのときの添付（写した ID が生きていれば）を入力欄へ戻す。送らない。

```text
│ ┌─ 利用者 ────────────────────────────────────────────────┐ │
│ │ ログイン画面の工程を 3 つに分けて                         │ │
│ └─────────────────────────────────────────────────────────┘ │
│ [この依頼をタスクにする] [入力欄に戻す]                        │
```

- 触る場所: `renderer.js` の `messageNode`（1077 行付近）のみ。
- 大きさ: 極小。

### 3.7 変更ビューの行から「会話に添付」（G）

**提案。** 変更ビューの行に、ファイルビュアーと同じ「会話に添付」を `.tiny` で足す。中身は
ビュアーの `viewer-attach` と同じ（相対パスを次の依頼に添える。写さない）。差分を見ながら
「このファイルを直して」と言える。

```text
┌ 変更 · feature-login ─────────── [作業ツリー|ブランチ] [並べて] [更新] ┐
│ M  src/renderer/taskTeaching.js                        [会話に添付] │
│ A  test/fixtures/login.md                              [会話に添付] │
└────────────────────────────────────────────────────────────────────┘
```

- 触る場所: `renderer.js` の変更ビュー（1520 行付近）。既存の添付関数を呼ぶだけ。
- 大きさ: 極小。

### 3.8 会話の絞り込みと名前の変更（H）

**提案。** 会話一覧の見出しの下に「名前で絞り込み」（ファイルツリーの `tree-filter` と同じ 1 行）。
「その他」に「会話名を変更」を足す（`prompt()` で十分。ダイアログは作らない）。一覧が 10 件を超える
リポジトリで効く。

- 借りる形: ファイル画面の `.tree-tools` の入力欄、「その他」のメニュー行。
- 大きさ: 小。

## 5. 検討して採らない案

| 案 | 採らない理由 |
|---|---|
| 確認の自動応答（「自動承認」設定のときは y を自動で送る） | CLI 側に既に `autoApprove` の起動引数がある。画面側で y を打つ自動化は、CLI が本当に聞いていることを読み違えると取り返せない |
| 聞かれている文を解析して選択肢をボタンにする | CLI ごと・版ごとに文面が違い、ADR-1 で退けた文言解析と同じ道。キーは 3 つに固定する |
| アプリ自身でコミット・push する | 「持たないもの」。CLI に頼む定型文（3.2）で同じ手数になる |
| 依頼テンプレートの一覧画面 | 画面が増える。起動時アクションと同じ設定の行で足りる |
| タスクの失敗を AI が自動で直す（無人の再試行） | 無人実行の承認・監査は ADR-9 の見直し条件で、会話の外に置き直す話。ここでは人が送る |
| 会話一覧のピン留め・フォルダ分け | 絞り込みで足りる間は足さない |
