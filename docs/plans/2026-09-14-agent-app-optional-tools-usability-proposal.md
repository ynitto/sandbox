# agent-app: 任意ツールを必要な場面だけ見せる案

日付: 2026-09-14 / 対象: `tools/agent-app` / 状態: **提案**

## 結論

agent-tools の機能一覧や導入画面は増やさない。利用者が今いる画面に、インストール済みの道具で次にできる操作を
**1 つだけ**足すのがよい。最初に実装するなら、手動実行が終わったタスクへ
`定期実行にする` を出す。agent-loop が無ければボタンごと出さず、従来の手動実行をそのまま使えるようにする。

この案は柱 2（判断の往復を減らす）と柱 3（手元の実行資源を使い切る）、原則 C2 と C6 に効く。
任意依存を主経路へ持ち込まないので、agent-app 単体で会話とタスクを作成・実行できる ADR-11 も崩さない。

## 現状の引っかかり

agent-app は agent-herd、agent-loop、agent-flow の有無を既に調べ、実行環境に表示している。ただし、利用者は
「何が入っているか」を読んでから「どの操作が増えるか」を自分で結び付ける必要がある。逆に未導入の環境では、
使えない機能の説明が増えるほど、会話や手動実行まで準備不足に見えやすい。

能力をまとめた新しい画面では、この問題はあまり改善しない。読む場所が 1 つ増えるだけだからだ。既存の
`agents.js`、接続診断、タスク詳細を使い、実行直後など意図が明らかな場所にだけ次の操作を置く。

## 最小の変更

### 1. 手動実行の完了後に `定期実行にする`

agent-loop が応答し、そのタスクが定期実行可能なときだけ、成功結果の下へ `定期実行にする` を 1 つ出す。
押した後は既存の定期設定欄へ移動する。時刻を推測して保存してはいけない。

```text
実行が完了しました
次回から自動で動かせます                      [定期実行にする]
```

これは最有力案である。利用者が「同じ仕事をもう一度回す」と判断できる瞬間にだけ出るため、常設の説明より
発見しやすい。実装も既存の可用性判定と画面遷移をつなぐだけで済む。

表示条件は次の論理積に固定する。

- agent-loop の capability が `available`
- 選択中のタスクが保存済みで、手動実行が成功した
- そのタスクに有効な定期設定がまだ無い

agent-loop が無い、診断がタイムアウトした、実行が失敗した、のいずれかなら何も足さない。「導入すれば使える」
という販売表示も通常画面には置かない。不足の説明は既存の実行環境だけで足りる。

### 2. 長い依頼の送信前に `手元の AI で実行`

agent-herd が利用可能で、直接指定を開いたときだけ `herd` を通常の AI 候補と同じ位置に出す。これは既にある
挙動を変えず、説明を「ローカル実行系」から `手元の AI（追加費用なし）` へ直す案である。モデル名や backend
選択は agent-herd に任せる。

自動で herd へ切り替えたり、文字数を根拠に節約を勧めたりはしない。仕事の難しさを本文の長さから判定すると
誤案内が多くなる。agent-herd が無ければ候補は今までと同じで、空の区切りや説明も残さない。

この変更は小さいが、現行の `herd` という内部名を利用者に覚えさせない効果がある。実装する場合も保存値は
`herd` のままとし、表示名だけを変える。

### 3. タスクが増えた後に `工程としてつなぐ`

agent-flow が利用可能で、同じリポジトリに利用可能なタスクが 2 件以上あるときだけ、ワークフローの空状態へ
`既存のタスクを工程としてつなぐ` を出す。押した後は既存のワークフロー教示へ移り、候補のタスク名を入力欄へ
置く。送信と定義保存は利用者が行う。

これは第 2 段でよい。候補名の引き渡しは便利だが、ワークフローを使わない人には不要で、最初から見せると
主メニューの学習量を増やす。agent-flow が無い場合は従来の「利用できない」という 1 行だけを維持する。

## capability の扱い

新しいプラグイン機構は作らない。main process が既に得ている可用性を、次の 3 値に正規化して renderer へ渡せば
足りる。

| 値 | 画面の扱い |
|---|---|
| `available` | 対応する操作を条件付きで表示する |
| `unavailable` | 操作を表示しない。実行環境では不足理由を表示してよい |
| `unknown` | `unavailable` と同じ。診断完了を待つ表示は増やさない |

起動時に各 CLI へ追加問い合わせはせず、既存の診断結果を使う。renderer はコマンド名や PATH を解釈しない。
操作を押した時点でも IPC 側で可用性を再確認し、途中でツールが消えていたら既存の実行環境へ案内する。

## 受入条件

1. agent-tools を PATH から外した fixture で、会話、タスク作成、手動実行の既存テストがそのまま通る。
2. `unavailable` と `unknown` では追加操作も空の見出しも表示されない。
3. agent-loop が使えるときだけ、成功した未設定タスクに `定期実行にする` が 1 つ出る。
4. 追加操作は既存画面へ移動するだけで、クリック時に実行、設定保存、AI への送信を行わない。
5. capability の取得失敗は通知を積まず、主機能のエラーにも昇格させない。

テストは `standalone.test.js` に「全部なし」、各 automation テストに該当ツールだけを `available` にした組合せを
加える。全ツールを同時に入れた Electron E2E は初回の受入条件にしない。

## 採らない案

| 案 | 理由 |
|---|---|
| agent-tools のマーケット画面 | インストール管理まで agent-app の責務になり、主経路が太る |
| 起動時のおすすめ導入バナー | 毎回の会話開始を邪魔し、未導入を異常に見せる |
| 不足ツールの自動インストール | 外部取得と PATH 変更を伴い、失敗時の責任範囲も広い |
| 全ツール共通の汎用 capability API | 3 操作には過剰。既存診断の小さな写しで始める |
| 利用可能なら自動で定期化、flow 化する | 実行頻度と工程分割は利用者の判断であり、可用性だけでは決められない |

## 実装順

まず `定期実行にする` だけを入れ、クリック率ではなく「手動実行後に定期設定まで迷わず到達できるか」を手動で
確認する。表示条件や再確認が複雑になるなら、この案は捨てる。2 と 3 は同じ条件表示で収まることを確認してから
別の変更として扱う。
