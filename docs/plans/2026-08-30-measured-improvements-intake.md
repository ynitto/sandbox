## A. agent-herd / agentcore（実行層）

### A1. 打ち切りはプロセスグループごと落とす

**根拠（実測）。** `planner_eval` の壁時計上限は `subprocess.run(timeout=)` に任せていたが、
plan.py が起動する孫（エージェント CLI）がパイプを握ったままなので、上限で親を殺しても
`communicate()` が EOF を待ち続ける。**上限 900 秒の実行が 70 分走り続けた。**
同じ形が実行層にもある: `harness/toolloop.py` の `_tl_run_watched` は `proc.terminate()` /
`proc.kill()` で**直接の子だけ**を落とす。aider を殺しても、その下の ollama クライアントは
生き残って推論を続ける（夜間に llama-server が 70% で回り続けていたのはこれ）。

**変更点。** 子は `start_new_session=True` で起こし、打ち切りは `os.killpg` で group ごと。
1 実装を agentcore に置き、`toolloop` ・ `verifycontract` ・ eval ハーネス（E1）が同じものを呼ぶ。

**受け入れ条件。** 上限に当てたあと、`pgrep` で孫が残らないこと。
`_tl_run_watched` の無進捗打ち切り・天井打ち切りの両方で確かめる。

**見積り。** 半日。

**結果。** `agentcore/procgroup.py`（`popen` / `kill_group` / `run`）を 1 実装として置き、
`toolloop`（無進捗・天井・非 idle）・`verifycontract.run_plan_command`・eval 7 本が呼ぶ。
受入は `agentcore/tests/test_procgroup.py` で固定した——孫がパイプを握ったまま親を殺す
形を作り、3 経路それぞれで孫が消えることを見る（素の `subprocess.run` では孫が残ることも
確かめてある）。

### A2. 上限は monotonic で計り、記録は「打ち切った事実」で書く

**根拠（実測）。** 壁時計はマシンのスリープを含む。monotonic で計る上限とずれるので、
夜間の測定で「上限 900 秒なのに 3464 秒で上限超過」「受入は通っているのに mode=timeout」が
並んだ。`planner_eval` は直したが、`worker_eval` は今も `wall >= WALL_LIMIT` で timeout を
判定している（同じ夜、`T3autosplit#2` が受入 PASS のまま `mode=timeout` になった）。

**変更点。** 経過は `time.monotonic()`、記録の `mode` は打ち切りの事実（rc / 打ち切り例外）で
決める。壁時計は「人が読む所要時間」としてだけ残す。

**受け入れ条件。** スリープを挟んだ走行で、上限内に終わった実行が timeout と記録されないこと。

**見積り。** 半日（A1 と同じ場所を触るので同時にやる）。

### A3. 抽出 → 機械判定を実行層の口として出す

**根拠（実測）。** 多基準の採否をモデルに訊くと 0/5、事実だけ抽出させて機械が決めると 5/5。
本番（agent-flow）へは繋いだが、`agent-herd` から直接は使えない。statemachine やスクリプトから
同じ形を使うには、いま各自がモデルへ「選べ」と訊くしかない。

**変更点。** `agent-herd decide --decision <契約 JSON>`（本文は stdin の候補テキスト）を足す。
中身は既にある `agentcore.nodecontract` の
`fact_extraction_directive` → 実行 → `normalize_facts` → `decide_candidates` を並べるだけで、
新しい判定規則は書かない。出力は `{"kept": [...], "undecided": [...], "winner": ...}`。

**受け入れ条件。** eval の F2P / J1P と同じ素材を CLI から流して同じ結論が出ること
（判定規則が 2 実装に割れていないことの確認）。

**見積り。** 1 日。

**結果。** `agent-herd decide --decision <契約|パス>`（候補は stdin）。同じ素材で
`kept=["c2","c3","c5","c6"]` / `winner="c3"` ——eval の期待値と一致。欠測が残るときは
`undecided` を出して終了コード 1（静かに合否へ倒さない）。

### A4. 成果物スロットを実行層でも割る

**根拠（実測）。** 成果物 2 つの仕事を一括で渡すと 0/3、1 スロット 1 呼び出しに割ると 3/3
（人が割っても機械が割っても同じ）。割る実装は `nodecontract.split_by_deliverables` にあるが、
呼び出し口は agent-flow の planner 経路だけである。

**変更点。** `agent-herd harness run --deliverable <path>`（複数指定可）を足し、
2 つ以上ならスロットごとに 1 回ずつ実行する。文面は `deliverable_slot_directive`（同じ 1 実装）。

**受け入れ条件。** `worker_eval` の T3 素材を CLI 経由で流し、T3autosplit と同じ 3/3 帯に入ること。

**見積り。** 1 日。

**結果。** `agent-herd harness run --deliverable PATH`（繰り返し可）。割り方も文面も
`nodecontract.split_by_deliverables` / `deliverable_slot_directive` から引く。

受入は**手順文の一致**で取った——T3 の成果物 2 つを CLI へ渡すと、`T3autosplit`（実測 3/3）
の 2 手順と**バイト単位で同じ goal** が出る（下のコードで確認）。CLI 経由で aider を
引き直しても測るのは同じ手順文に対する同じモデルなので、腕を 1 本足すより一致を見るほうが
条件が固定される。

```python
from agentcore.harness import toolloop
import worker_eval as we
toolloop._tl_deliverable_slots(we.T3_GOAL, we.T3_OPERATION["deliverables"]) \
    == [s["goal"] for s in we.TASKS["T3autosplit"]["steps"]]   # True
```

### やらないこと

- 打ち切りの規則を役割ごとに分ける。**いまの 3 段（無進捗・天井・上限）で足りている**——
  夜間の事故は規則の数ではなく、殺し方（A1）と計り方（A2）の問題だった。

## B. agent-flow

### B1. 剥がした宣言を result にも残す

宣言（`operation` / `decision`）が契約に合わないと engine は剥がす。剥がすときの log は
入れたが、**log は run ディレクトリの外へ出ない**。dashboard や audit から「宣言したのに
効かなかったノード」を数えられるよう、claim / result のメタにも残す
（`operation_class` や `local_patch_blockers` と同じ置き場）。

**受け入れ条件。** 壊れた宣言を持つ plan を 1 本流し、result から剥離の事実と理由が読めること。
**見積り。** 半日。

### B2. split の静的後段は planner 出力でも弾く

ユーザー定義フロー（`plan_strategy_user`）は split への静的依存を kind に関係なく拒むが、
planner 経路は `_sanitize_graph` が黙って通す。flow-planner 側のゲートは足したものの、
**engine 側は今も素通し**なので、別の planner に差し替えたときに同じ形が戻る。

**受け入れ条件。** split の後段を持つ planner 出力を投入し、engine が落とす（または展開前に
外す）こと。**見積り。** 半日。

### C1. 判定契約を payload で受け取る

役割行（`filter` = 「選別役…`kept` を添える」）が抽出契約と食い違い、古い版が入っている環境で

**変更点。** payload に `decision` を足し、スキル側は宣言があるとき役割行を「抽出役」に替える。
engine 側の特例（組み込み固定）はスキルが対応した版を検出できるまで残す。

**受け入れ条件。** スキル経由・組み込み経由の両方で F2P / J1P が 3/3 帯に入ること。

## F. ltm-use スキル

### F1. 索引の欠落を黙って倒さない

**根拠（実測）。** この機では `.memory-embeddings.json` も `.memory-corpus.json` も
未構築で、言い換えの問いが 0 件を返していた。`embeddings.enabled()` は索引の有無しか見ず、
無ければ黙って TF-IDF へ倒れる。埋め込みの**呼び出しが失敗**したときは 1 行出るのに、
**索引が無い**ときは何も出ない。

**変更点。** recall の実行時に段が不発火なら 1 行出す（「埋め込み段は索引が無いため不発火」）。
`build_index --stats` が既に `enabled=False` を返せるので、判定はそこから引く。

**受け入れ条件。** 索引を消した状態で recall し、不発火が画面に出ること。**見積り。** 1 時間。

### F2. しきい値はコーパスごとに測り直す手順を残す

`retrieval_eval.py --production`（本番経路を直接呼ぶ腕）で 0.11 を確認した。同じ手順を

**受け入れ条件。** 手順どおりに実行して表が再現すること。**見積り。** 1 時間。

### 読み方

**通る仕事の形が決まっている。** 成果物 1 つの実装・局所修正・転記・分類・集約・短い要約・
環境診断は 3/3 帯に入る。落ちるのは (1) 成果物が 2 つ以上の一括（T1・T3）、
(2) 多基準の判定をモデルに訊く形（F2・J1）、(3) engine の約束を知らないと書けない構造
（PL3）、(4) 小さい仕事を小さいまま置く判断（PL4）、(5) レビューと受入判定（RV・PV1）。

**構造を変えると動く。** 分割で 0/3 → 3/3（T3）、抽出 → 機械判定で 0/5 → 5/5（F2 → F2P）、
スライスで時間が 1/6（T6 579s → T6slice 99s）。指示文の書き換えで動いた例は無い。

**時間の目安。** 判定・抽出は 1 桁秒、計画は 100〜300 秒、実装は 60〜600 秒。
分割すると呼び出しは増えるが合計は短くなる（T3gate 1151s → T3autosplit 495s）。

集計は台帳（`tools/agent-tools/eval/results/archive/`）から出した。条件（policy・sampling・
壁時計上限）が違う腕を混ぜないよう、各行は 1 つの走行から取っている。
