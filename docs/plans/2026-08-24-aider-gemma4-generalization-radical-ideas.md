# aider + gemma4:e4b の汎用化・高度化 — 既存方針の外にある打ち手の探索

> 作成 2026-08-24
> 前提: CPU only / RAM 32 GB / 推論サーバ ollama / コード worker は `agents/aider.json`
> （gemma4:e4b + reliability policy v1）。
> 位置づけ: [2026-08-18 評価](2026-08-18-agent-aider-improvement-assessment.md)と
> [2026-08-22 追加活用提案](2026-08-22-local-llm-further-utilization-and-runtime-tuning-assessment.md)は
> 「aider を局所修正 worker として完成させる」側の文書だった。本書は逆側——
> **エージェント層の入れ替え（pi 級の最小ハーネス）や編集プロトコルの置換まで含めて、
> aider + e4b をより汎用的・高度に使う**ためのアイデアを、既存の教義に縛られずに洗い出す。
> 提案段階であり、実装・実測はまだ何もない。
> **2026-08-29 追記: 案 I・II・VI は実測で閉じた（不採用）。** 対照実装
> （`agentcore/editblock.py` + `editagent.py`）で aider を外した腕を測ったところ
> T4gate が 3/3 から 0/3 へ落ちた（[スラッシュ再構成設計](2026-08-27-agent-herd-cloud-cli-parity-slash-dispatch-design.md) §11 未決 5）。
> 残っているのは案 III・IV・V・VII・VIII で、実行順序は §9 を参照。

## 0. 出発点 — 「破ってよいもの」と「破れないもの」を先に分ける

既存文書の結論は一貫して「汎用エージェント化しない」だった。ただしその結論は
2 種類の根拠が混ざっている。**モデルの実測事実**（何度測っても再現する性質）と、
**ハーネス側の教義**（現行構成を前提にした設計判断）である。汎用化を考えるなら、
前者は土台として残し、後者だけを疑う。

### 0.1 破れない事実（モデル側・実測済み）

| # | 事実 | 含意 |
|---|---|---|
| F1 | E4B は短い・局所的・構造化に強く、長い・横断的・メタ認知に弱い（T2 3/3 ⇔ T1 1/3・T3 0/3、MRCR 128K 25.4） | 「賢く振る舞わせる」方向は全滅済み。汎用性をモデルに求めない |
| F2 | 品質の守りは決定的ゲート + 再投入（0/9 → 3/3）。自己申告完了は信用できない | どのハーネスに載せ替えても checker は外せない |
| F3 | (b) 族（作業丸ごと欠落）は診断つき再投入でも引き直し（resample）でも直らない（T3gate 27 attempt 同文欠落） | 再試行の強化はもう掘れない。**構造で殺すしかない**。2026-08-29 に実証: 成果物を 2 つへ割った `T3splitgate` は 3/3・再投入 0 回（同条件の T3gate は 0/3） |
| F4 | 材料サイズは壁時計へ倍々で効く（編集ループが毎ターン再送）。スライシングで tokens_in −72〜87%・壁時計 −83% | ターンごとに全材料を再送する会話型ループは E4B と相性が悪い |
| F5 | 律速は decode ではない（26.5 tok/s）。焼くのは再試行・ラウンド数・prefill | 速度レバーはランタイムでなく呼び出し回数・材料量にある |
| F6 | 実効 temperature 0 では同形失敗が続く。sampling は (a) 族だけ揺らす | 多様性が欲しいなら sampling 以外の軸（本書 案 VIII）が要る |
| F7 | 「候補生成 + 機械検算」は E4B で成立する（パス候補 3/3・テスト名 3/3・捏造 0） | 探索を任せられないが、**候補を出させて機械が確定する**のは任せられる |

### 0.2 疑ってよい教義（ハーネス側・設計判断）

| # | 教義 | 由来 | 本書で挑む案 |
|---|---|---|---|
| D1 | aider は単発（single-shot）worker。tool-loop を持たせない | 三重ループの停止性悪化を避けた | 案 I・VI（2026-08-29 に実測で棄却。教義は維持） |
| D2 | 編集プロトコルは aider の SEARCH/REPLACE のまま | Aider 本来の protocol を置換しない（policy 設計の制約） | 案 II（同上） |
| D3 | 対象ファイルは計画時に決まっている（自由探索させない） | E4B の探索能力が弱い | 案 III |
| D4 | repo map は既定 0 | prefill が高く、入れても読めない（F1/F4） | 案 VI（同上。slot / GBNF は案 B の独立 arm として残る） |
| D5 | 実装 + テスト一括は不適格。分解は「定型化済みの場合だけ」 | T1 1/12・T3 0/3 | 案 IV・VII |
| D6 | 12b は検証役のみ（code worker 昇格しない） | 停止性と収束の実測 | 案 V（昇格ではなく別役割） |

鍵になる視点は一つで、**汎用性はモデルにではなくハーネスに持たせる**。
「E4B を汎用エージェントにする」のではなく、「汎用の task を、E4B が適格な局所呼び出しの
列へ機械が変換する」——この変換器を強くすることが、実測事実と矛盾しない唯一の汎用化経路である。

## 1. 案 I ★ ~~エージェント層の入れ替え~~ — 不採用（2026-08-29 実測）

**結論。** aider は外さない。対照実装（`agentcore/editagent.py`、定義
`eval/agents/selfedit.json`）を書き、本番と同じ課題・同じ渡し方で測ったところ、
T2gate（既存テストの修理）は 3/3 で並んだが、T4gate（仕様どおりの新規実装）が
3/3 から **0/3** へ落ちた。落ち方は編集の当て損ないではなく中身の間違いである
（`ImportError`（関数名が仕様と違う）・`SyntaxError`・省略規則の取り違え）。台帳:
`eval/results/archive/worker/ledger-2026-08-29-selfedit-vs-aider-gemma4-e4b.jsonl`。

**本節の前提が 1 つ外れていた。** 「aider の長い編集プロトコル説明は E4B にとって逆風」と
読んでいたが、実際にはその約 6.3 KB（`main_system` + `system_reminder` + few-shot）が
T4 を支えていた。対照実装は書式の規約だけの約 0.5 KB で送っている。逆に、失うと
思っていた曖昧一致の階段は差にならない——上流の階段は 3 段（完全一致 → 先頭空白 →
`...` 中略）で、4 段目の difflib は `replace_most_similar_chunk` 途中の無条件 `return` で
到達しない（aider 0.86.2 を AST で確認）。次に測るならプロンプト側で、階段の移植を
やり直しても数字は動かない。詳細は
[スラッシュ再構成設計](2026-08-27-agent-herd-cloud-cli-parity-slash-dispatch-design.md) §11 未決 5。

以下は当時の提案の記録。対照実装は `--cli selfedit` で引き直せる。

**何をするか。** aider の代わりに、pi（badlogic の最小コーディングエージェント）級の
小さなハーネス——コア数百〜千行、tools は read / write / edit / bash 程度、プロンプトと
編集プロトコルが素直に差し替えられるもの——を第二のコード worker 候補として立てる。
OpenAI 互換エンドポイント経由で ollama に繋がるので、モデルはそのまま使える。
既製を採るか `agentcore` 内に自作するか（後述のとおり要件が特殊なので自作も現実的）は
評価後に決める。

**なぜ既存の教義の外か。** [2026-08-18 §8.3](2026-08-18-agent-aider-improvement-assessment.md)は
tool-loop の重複実装を禁じた。だがその根拠は「aider の reflection + 外側 retry + 独自 loop の
三重化」であって、**aider を外して一重にする**構成は検討していない。aider は GPT-4 級を
前提に設計されている——長い編集プロトコル説明、SEARCH/REPLACE の摩擦、reflection、
毎ターンの全材料再送（F4 の主犯）。E4B にとってこれらは全部逆風で、我々は
その逆風を policy 注入・map 0・スライシングで**外から**打ち消してきた。
最小ハーネスなら逆風を**設計から**消せる。

**E4B 専用に変えるべき点（aider では触れない部分）:**

1. **ターンを会話蓄積でなくステートレス再構築にする。** 各ターンのプロンプトを
   「task + 義務台帳（案 IV）+ 今要る抜粋 + 直前の診断」から毎回機械が組み立てる。
   会話履歴を積まないので材料は太らず（F4）、接頭辞が固定なのでプレフィックス
   キャッシュにも乗る（08-22 案 3 と同じ狙いがハーネス構造で達成される）。
2. **編集を schema 制約 JSON で受ける**（案 II）。
3. **reflection を持たない。** 判定は外部の決定的 checker（F2）。ハーネス内の
   「自分でうまくいったか考える」段は最初から作らない。

**Phase 5 の前倒しである。** 2026-08-18 §9 Phase 5 は「Pi 等との比較は同一モデルを使った
ハーネス比較として分離」とすでに宣言している。未着手のまま残っているだけで、
方針として新規ではない——本書はそれを「比較」から「E4B 最適化の母体候補」へ格上げする。

**測り方。** 同一モデル・同一 sampling・同一 task 群（T2 / T1 / T5 / T6 / T3gate）で
aider 腕と並べる。ledger に `harness` 軸を足す（model / policy / sampling と同時に変えない
規律はそのまま）。見るのは受入率・形式故障率・tokens_in・壁時計・停止性。
**採用条件**: T2 対照無退行 + いずれかのセルで受入か経済が明確に勝つこと。

**コストと危険。** 評価ハーネス側は worker_eval の headless_cmd 差し替えで足りる見込み
（agents/*.json の候補定義 1 本 + adapter 薄皮）。危険は「最小ハーネスの bash tool が
無制限であること」——readonly 強制・protected paths・timeout は `agents/` 定義の既存契約
（`readonly: enforced` 等）をそのまま課し、aider より緩い権限では走らせない。

## 2. 案 II ★ ~~編集プロトコルの置換~~ — 不採用（案 I と同時に閉じた）

**結論。** 本節自身が「案 I の最小ハーネス上で実装する方が安い」と書き、単独投入は
案 I が負けた場合の敗者復活戦と位置づけていた。その案 I が実測で退行したため
（§1）、敗者復活の前提も消えている——落ちたのは編集の当て方ではなく編集の中身で、
プロトコルを JSON schema へ変えても直らない側の故障だった。
[08-10 §4.2](2026-08-10-agent-ollama-quality-and-role-refit-proposals.md) が
パッチモードを取り下げたときの理由（「消える故障モードは corruption だけ」）と
同じ結論に、別の経路で到達したことになる。

以下は当時の提案の記録。

**何をするか。** 編集の受け渡しを「自由文の中の SEARCH/REPLACE ブロック」から、
**JSON schema で強制された編集オブジェクトの列**へ変える:

```json
{"edits": [{"file": "eval/billing.py", "anchor_before": "def prorate(", "old": "...", "new": "..."}]}
```

ollama の `format`（JSON schema 指定）で構造を強制し、適用は機械が行う。
`old` の不一致は適用側で機械的に検出して診断つき再投入へ回す（既存 gate と同型）。

**なぜ効くと考えるか。** F1 のとおり E4B は「構造化に強い」。JSON 契約の役割
（split / extract / judge）が決定化後 6/6 の天井に張り付いているのはこの性質で、
編集だけが自由文プロトコルに残っている。さらに編集プロトコルの説明文が
プロンプトから消えるので、固定 prefill も削れる（F5）。`--format json` より強い保証が
要る場合の逃げ道（GBNF / llama-server）も 08-22 §3.4 で限定投入候補として確保済み。

**どこで実装するか。** aider 内部（custom Coder）でも可能だが、D2 の制約
（policy 設計が「Aider 本来の編集 protocol を置換しない」ことを規則にした）と衝突し、
aider の update ごとに追随コストを払う。**案 I の最小ハーネス上で実装する方が安い**。
つまり案 II は案 I の一部として測るのが素直で、単独で aider に入れるのは
案 I が負けた場合の敗者復活戦とする。

**測り方。** 編集適用成功率（`old` 不一致率）・format_retries・受入率を、同一 task で
SEARCH/REPLACE 腕と比較。

## 3. 案 III ★★ 汎用化の本丸 — 「探索の決定化」パイプラインで適格範囲を広げる

**何をするか。** 現在の適格条件「対象ファイルが計画時に決まっている」（D3）が
汎用性の実質的な上限になっている。これを、**E4B に探索させずに**破る。
すでに実装・実測済みの部品を一本のパイプラインに繋ぐ:

1. **シンボルカード索引（新規・決定的）**: リポジトリを ast で走査し、シンボルごとに
   カード（シグネチャ + docstring + 呼び出し元/先 + パス）を生成。bge-m3
   （[B4 で実装済み](../designs/ltm-use-embedding-recall-design.md)、ltm-use で
   受入基準を両空間で満たした）で索引化する。
2. **候補検索（埋め込み・LLM なし）**: task 文 → 候補シンボル / ファイル上位 k。
3. **候補の機械検算（実測済みパターン）**: C2 実測でパス候補 3/3・テスト名 3/3・
   捏造 0（F7）。存在チェックと参照整合で候補を確定し、外れは無害化される。
   確信が持てないときは E4B に「候補を選ぶ」JSON 呼び出しを 1 回だけ挟む
   （判断ではなく選択——決定化済みの形式）。
4. **決定的スライシング（実装済み）**: `agentcore/context_slice.py` で対象シンボルと
   依存だけを抜粋（tokens −72〜87%）。
5. **局所編集**: 確定した `--file` / `--read` で aider（または案 I のハーネス）へ。

**なぜこれが「汎用化」か。** 入口の task が「`prorate` の按分バグを直せ」のような
**ファイル名を含まない自然文**でも、1〜4 が決定的に局所 task へ変換する。
モデルの適格範囲（F1）は 1 ミリも広げていないのに、**受け付けられる task の範囲**が
広がる。0.2 で述べた「汎用性はハーネスに持たせる」の最短の具体化であり、
新規実装はシンボルカード生成と接続だけ——検索・検算・スライスは全部既存部品である。

**測り方。** 新 task セル「T7: 対象ファイル非明示の局所修正」を作る
（既存 T5/T6 の課題からファイル指定を抜いた形でよい）。腕は
resolve なし（現行＝不適格で escalate）/ resolve あり。見るのは
「escalate せずに受入へ達した率」と、候補確定の誤り率（別ファイルを触った事故が 0 か）。

**危険。** 候補確定を誤ると「間違ったファイルを正しく編集する」事故になる。
protected paths と「書込 1 ファイル」の既存契約で爆風は限定されるが、
確定の確信度がしきい値未満なら**黙って進まず escalate する**規則を最初から入れる。

## 4. 案 IV ★★ b 族をアーキテクチャで殺す — 義務台帳と成果物スロット

**何をするか。** F3 は現在の最大の壁である——「実装 + テスト追加」を渡すと、
診断が「テストが無い」と毎回明示しても E4B は一度もテストを書かない（27/27）。
再試行・sampling・policy はすべて無力だった。残る手は**タスクの形を変えて、
省略という失敗を構造的に不可能にする**ことである。

1. **義務台帳（obligation ledger）**: 受入条件・verification.commands から、
   成果物の列挙（manifest）を**機械が**生成する。「`humansize.py` の実装変更」
   「`test_humansize.py` の新規テスト」の 2 義務、のように。生成規則は決定的
   （verification コマンドの対象・acceptance の名詞句）で、曖昧なら planner 呼び出し
   1 回で列挙させ、機械検算（F7 の形）で確定する。
2. **成果物スロット**: 義務 1 つ = E4B 呼び出し 1 つ。各スロットに専用 checker。
   テストのスロットは「テスト関数が n 個以上あり、対象を import し、失敗させると
   落ちる」を構造で検査する——空テストや省略はモデルの意思と無関係に落ちる。
3. **statemachine への定型追加**: 既存の gate + 再投入・`check_on_exhausted` は
   そのまま。「manifest → スロット直列消化」という node 形を 1 つ足すだけで、
   agent-loop / agent-flow の機構は変えない。

**なぜ効くと考えるか。** 実測の内訳がそのまま根拠になる。T1 の 3 方式で唯一 3/3 に
達したのは「分解 + 決定的 gate + 再投入」（952s）で、教義 D5 はこれを
「定型化済みの場合だけ」に限定した——分解を**人が**書く前提だったからである。
案 IV は分解の生成自体を機械化する。つまり「(b) 族が動かないなら成果物を 1 つに割る」
（[08-22 §4.2 A1](2026-08-22-local-llm-further-utilization-and-runtime-tuning-assessment.md)の
結論）を、その場しのぎでなく機構として常設する。

**測り方。** T3gate（現行 0/3）を manifest 分解ありで再測。1 本でも通れば
b 族に対する**初めて数字が動く打ち手**になる。壁時計は増える（952s 級を覚悟）ので、
採用条件は「escalate（クラウド消費）との交換レートで得」か。

**2026-08-29 に前提が 1 つ確かめられた。** 分解を**人が**書いた腕（`T3splitgate`：
schema 1 ファイルと契約テスト 1 ファイルの 2 手順・最終 checker と seed は T3gate と共通）で
**3/3**、同条件の T3gate は **0/3** だった（[eval README](../../tools/agent-tools/eval/README.md)）。
つまり「割れば通る」は成立している——**案 IV に残っているのは分解を機械が書けるかだけ**で、
分解が効くかどうかはもう問いではない。

覚悟していた壁時計の増加も出なかった。中央値は 561s 対 1151s で**分割側が安い**
（呼び出し 6 対 9）。一括側が高いのは、通らない手順へ再投入を 2 回積んでから escalate
するためである。したがって採用条件の「交換レート」は、当初思っていたより緩い。

## 5. 案 V ○ 二モデル非対称ループ — 12b を navigator、e4b を driver にする

**何をするか。** ペアプログラミングの構図で役割を割る。**12b = navigator**:
現在地（義務台帳・直近の診断・チェック結果）を見て「次の一手」を JSON 1 発で出す
（どのファイル・何をする・受入は何か）。**e4b + aider = driver**: その一手を局所実行。
checker が判定し、結果が navigator へ戻る。navigator の呼び出しは毎回単発 JSON なので、
12b の停止性問題は既存の stall 検知（180s・期待コスト 13s）と e4b への縮退配線
（[B3 で実装済み](2026-08-22-local-llm-further-utilization-and-runtime-tuning-assessment.md)）が
そのまま守る。

**なぜ既存の教義の外か。** D6 は「12b の code worker 昇格」を禁じたが、これは
12b に**編集させる**話だった。navigator は編集しない——長文文脈の理解と
「次に何をすべきか」というメタ認知だけを担う。つまり **E4B の弱点 2 つ
（長い・メタ認知）をちょうど 12b の強みで埋め、12b の弱点（停止性・編集の収束）を
使わない**分業である。案 IV の義務台帳が静的な分解だとすると、案 V は動的な分解
——途中の発見で手順が変わる task（調査しながら直す類）まで射程が伸びる。

**測り方。** T1 / T3 級で navigator あり / なし。壁時計は確実に増えるので、
見るのは受入率と escalate 率。navigator の一手が機械検算（案 III の候補確定と同じ形）を
通らない率も記録する——ここが高いと「12b の指示待ちで空転」になる。

## 6. 案 VI ○ ~~ランタイム移行を新ハーネスの前提として再評価~~ — 不採用（案 I と同時に閉じた）

**結論。** 本節の位置づけは「単独では引かない。案 I の腕の一変種として測る」だった。
案 I が閉じたので、この形での再評価も成立しない。ただし部品まで死んだわけではない——
案 B（iGPU prefill の計測）と GBNF は 08-22 §3.4 のとおり独立 arm として残っており、
実機が空いた時点でそちらの枠で測る（[残タスク棚卸し](2026-08-29-local-llm-open-items-inventory.md) C2）。

以下は当時の提案の記録。

**何をするか。** [08-22 §3.4](2026-08-22-local-llm-further-utilization-and-runtime-tuning-assessment.md)は
koboldcpp / llama-server への全面乗り換えを「受入率が動かないから不採用」と判定した。
この判定は**現行ハーネスのまま載せ替える**前提だった。案 I の最小ハーネスを
**llama-server 前提で**設計すると、判定の材料が変わる:

- **slot save（KV 状態の明示保存）**: repo 文脈・固定 policy・シンボルカードを
  一度だけ prefill して常駐させ、ターンごとの差分だけ払う。F4（材料再送が壁時計の主犯）と
  D4（repo map 0 の根拠 = prefill が高い）の**前提コストが消える**。「広い文脈を
  持った E4B エージェント」が、aider + ollama では成立しなかったコスト構造で成立しうる。
- **GBNF**: 案 II の編集 schema と tool-call を文法で固定。小型モデルの tool-loop の
  主故障（形式外れ）が文法レベルで消える。
- ollama 経路との共存: 判定・抽出系の既定は ollama のまま、コード worker 経路だけ
  llama-server を試す。stall 検知・usage 実測・エラー分類の契約同等性（Gate 0 相当）を
  先に固定する規律は 08-22 のまま。

**位置づけ。** 単独では引かない。**案 I の腕の一変種**（最小ハーネス × ollama /
最小ハーネス × llama-server+slot+GBNF）として測る。案 B（iGPU prefill）検証と
同じバイナリで済むので、半日枠を相乗りできる。

## 7. 案 VII △ 検証済みスキルの蓄積 — 解いた task を資産にする自己拡張

**何をするか。** checker を通過した task について、（task 種別 → 分解形・スライス規則・
checker・合格実例）を登録簿に残し、次回同種の task は**定型として**処理する。
Voyager 型スキルライブラリの決定的版——蓄積するのはプロンプトではなく
**手順と検査**である。D5 の「定型化済みの場合だけ候補」という限定が、
定型化が自動で増えることで時間とともに緩む。08-22 案 5（few-shot 資産化・未着手）は
この弱い形なので、統合して「実例 + 手順 + checker」を 1 レコードで持つ。

**なぜ後回しか。** 資産が効くには task の再来が要る。運用量がまだ小さい現在は
回収期間が読めない。**案 III・IV が入って処理量が増えた後**に、台帳から
同種 task の再来率を測ってから設計する。今やるのは「後で資産化できる形で
ledger に分解形と checker を残す」ことだけ（既存の記録規律でほぼ足りている）。

## 8. 案 VIII △ ハーネス・レース — 多様性を sampling でなくハーネスに求める

**何をするか。** resample（同一ハーネスで N 回抽選）は不採用だった——同形失敗を
同じ壁時計で N 回受け取るだけだった（F6・08-22 §4.3）。失敗を揺らすもう一つの軸は
**ハーネスの多様性**である: 同一 task を aider / 案 I の最小ハーネス /
CodeAct 形（編集を行う Python スクリプトを書かせて sandbox 実行し、diff を検査）で
並べ、決定的 checker が採択する。プロトコルが違えば失敗の形も違う——
sampling が動かせなかった族に対する、最後の「引き直し」である。

**境界。** 直列運転なので壁時計 × 本数。常用ではなく、**escalate 予定の task にだけ**
適用する（クラウド消費との交換で正当化する）。案 I の評価が終わってハーネスが
2 本以上になった時点で初めて成立する案なので、順序は最後。

## 9. 実行順序の提案

2026-08-29 に案 I・II・VI が閉じたので、残るのは 3 段と後続である。

| 段 | 内容 | 依存 | コスト | 判定 |
|---:|---|---|---|---|
| 1 | **案 III**: シンボルカード索引 + 候補確定 + 既存スライスの接続、T7 セルで A/B | 部品は全部実装済み | 2〜3 日 | ファイル非明示 task の受入率・誤ファイル事故 0 |
| 2 | **案 IV**: 義務台帳 + 成果物スロット、T3gate 再測 | statemachine の node 形 1 つ | 2〜3 日 + 壁時計 | b 族で初めて 0 が動くか |
| 3 | **案 V**: navigator/driver、T1/T3 級 | 案 IV の台帳表現 | 2 日 + 壁時計 | 受入率 vs 壁時計増 |
| 後続 | 案 VII（資産化） | 運用量 | — | — |
| 不成立 | 案 VIII（ハーネス・レース） | ハーネス 2 本 | — | 案 I が閉じたので 2 本目が無い |
| 閉 | ~~案 I・案 II・案 VI~~ | — | — | 実測で不採用（§1・§2・§6） |

案 III を先頭に置く理由: 新規実装が最少で、成功すれば**入口の汎用化**という
最も見えやすい成果になり、案 IV・V が扱う task の供給源にもなる。

案 III には競合がある。[適用性レビュー](../reviews/2026-08-27-gemma4-harness-plan-applicability-review.md) P3 が
同じ穴（対象ファイルが計画時に決まっていない task の局所化）に別解——編集対象の import と
シンボルから決定的に rg パターンを導出する——を出している。両方は作らない。
どちらを先に測るかは[残タスク棚卸し](2026-08-29-local-llm-open-items-inventory.md) 2.5 で決める。

案 VIII は「同一 task を複数ハーネスへ並べる」案なので、aider 以外のコード worker が
立たなかった時点で材料が無い。復活するとすれば案 I とは別の 2 本目が現れたときである。

## 10. 変わらない規律

- checker のない自己申告完了を受け入れない（F2）。どのハーネスでも同じ。
- model / harness / policy / sampling を同時に変えない。腕は 1 軸ずつ、条件は ledger へ。
- `3/3` は存在の証明、率として読むなら n ≥ 10（eval README「n の読み方」）。
- ローカル fine-tuning は不採用のまま（08-22 案 6）。本書の案はすべて機構側にある。
- 新ハーネスにも `readonly: enforced`・protected paths・timeout・stall 検知の契約を
  aider と同等以上に課す。権限の緩いハーネスで「汎用性が出た」ように見えるのは錯覚とする。
