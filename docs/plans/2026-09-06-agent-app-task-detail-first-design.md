# agent-app タスク詳細ファースト設計

> 作成日: 2026-09-06  
> 対象: `tools/agent-app`、`tools/statemachine-maker`  
> イメージ図: [2026-09-06-agent-app-task-detail-first-ui-mock.html](2026-09-06-agent-app-task-detail-first-ui-mock.html)  
> 関連: [agent-app AI教示タスク統合設計](2026-09-06-agent-app-ai-teaching-integration-design.md)、[statemachine-maker AIティーチング・ワークスペース設計](2026-09-06-statemachine-maker-ai-teaching-workspace-design.md)

## 背景

statemachine-use スキルでチャットから作ったステートマシン（`.statemachine/<名前>/workflow.yaml`）を
agent-app の「タスク」で開くと、教示画面が先に出て「下書き」「目的を理解中」と表示された。
定義は揃っていて実行できるのに、編集途中のように見える。

原因は 2 つ。

1. 共有ワークベンチ（`renderer.js` の `navigateEmbedded`）が、選択したタスクが `machine` を持つ限り
   教示画面を開いていた。ステートマシンは全部 `machine` を持つので、既存定義も必ず教示画面になる。
2. 教示一覧（`teaching.js` の `loadItems`）が、`teaching.json` の無い既存定義を一律 `needs-trial`
   （試運転が必要）にしていた。教示セッションを読むと空の `draft` が返るため、見出しは「下書き」になる。

教示ワークスペース設計は「利用可能は 3 段階の検査を通ったものだけ」と決めていたが、それは
**AIが作った候補**についての規則である。スキルや人が書いた既存定義は、それ自体が実行物であり、
教示を経なくても実行できなければならない（同設計の「完成した成果物は従来どおり単体で実行できる」）。

## 決定

**定義があるタスクは実行詳細から開く。教示は「AIに変更を相談」を押したときだけ開く。**

状態は 2 軸で決める。

| 軸 | 意味 | 由来 |
|---|---|---|
| 定義がある（published） | `workflow.yaml` が存在し、`.teaching-trial` ではない | `store.exists` |
| 変更が進んでいる（change） | `teaching.json` の status が `ready` 以外 | 教示セッション |

### ステート条件

| 表示 | 条件 | 実行 | 最初に開く画面 |
|---|---|---|---|
| 利用可能 | 定義がある。`teaching.json` が無い、または status が `ready` | できる | 実行詳細 |
| 利用可能 · 変更中（下書き／試運転待ち／確認待ち） | 定義があり、status が `ready` 以外 | できる（今の版） | 実行詳細（ボタンは「変更を続ける」） |
| 下書き | 定義が無く、候補（generation）も無い | できない | 教示 |
| 試運転待ち | 定義が無く、候補はあるが成功した試運転が無い | 試運転のみ | 教示 |
| 確認待ち | 定義が無く、成功した試運転がある | 「期待どおり」で公開 | 教示 |

判定は main 側の純粋関数 `teaching-model.presentStatus({ published, status })` に置き、
standalone の statemachine-maker と agent-app の埋め込みで同じ結果になる。
`teaching-store.list` は各下書きに `published` を返す。

### 画面

イメージ図の A〜C を正とする。

- **実行詳細**（既存の 概要／手順／履歴）の見出しに状態バッジを 1 つ置く。右に「AIに変更を相談」、
  「高度な編集」は従来どおり「手順」タブから。
- 変更が進んでいる定義は、印を「変更中 · 試運転待ち」のように増やし、ボタンを「変更を続ける」に変える。
  説明の帯は出さない（実行ボタンが押せることが「今の版は動く」の証拠で、同じ事実を 3 回言わない）。
- **教示画面**は、定義があるタスクでは見出しを「タスクの変更を相談」にし、状態は「利用可能」を保つ。
  進行バーは候補ができてから出す。「実行画面へ戻る」を常に置く。
- 定義が無い下書きは従来どおり教示画面から始まる（イメージ図 B-③）。
- 「期待どおり」で利用可能になったら、実行詳細へ移る（統合設計「教示完了後は同じタスクを選択した
  詳細画面へ遷移」）。
- サイドバー（agent-app）の下書き以外のタスクは、変更が進んでいるときだけ「変更中」を添える。

画面の状態語は 利用可能／下書き／試運転待ち／確認待ち の 4 つに揃える（flow.js の教示と同じ）。

### 文言の削減

同じ事実を 2 回言わない。今回の画面で削ったもの:

| 場所 | 削る前 | 削った後 |
|---|---|---|
| agent-app 埋め込みの教示ページ見出し | 「タスク」＋説明文＋「新しいタスクを教える」 | 非表示（サイドバーの「タスク」と「＋」が同じ役目） |
| 変更中の実行詳細 | 印＋バナー＋「変更を続ける」 | 印＋「変更を続ける」 |
| 既存タスクの相談画面の案内 | 「このタスクは利用可能です。変更したいことを伝えると、今の版を残したまま候補を作り、試運転で確認してから置き換えます。」 | 「変更したいことを伝えてください。今の版は、試運転で確認するまで置き換わりません。」 |

## 検討した案

| 案 | 実装コスト | リスク | 保守性 | 推奨度 |
|---|---|---|---|---|
| **1. 実行詳細を先に出し、教示は明示操作** | 低 | 低 | 高 | ★★★ |
| 2. 教示画面に実行カードを埋め込む | 中 | 中（縦に長く、狭い幅で崩れる） | 中 | ★★☆ |
| 3. 教示画面のラベルだけ直す | 低 | 高（会話欄が主役のままで「編集中に見える」根本が残る） | 中 | ★☆☆ |

1 を採用する。追加する画面は無く、既存の実行詳細と教示画面を接続し直すだけで済む。

## 検証

1. `workflow.yaml` だけの定義（スキル生成）を開くと実行詳細が出て、状態は「利用可能」。
2. 「AIに変更を相談」で教示画面へ移り、「実行画面へ戻る」で戻れる。
3. 定義があるタスクの教示中（候補あり）は、実行詳細に「変更中」の印と「変更を続ける」が出て、実行は引き続きできる。
4. `teaching.json` だけの下書きは従来どおり教示画面から始まる。
5. 「新しいタスク」と会話からの intent は従来どおり教示の作成画面を開く。
6. 両アプリの unit test と Electron 実機テストが通る。
