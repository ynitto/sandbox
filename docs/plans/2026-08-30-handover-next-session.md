## 0. 「3 時間終わらないタスク」の正体 — 待機ループの自己マッチ（解決済み）

**測定ではなく、私が起こした待機ループ 2 本だった。** どちらも
`until ! pgrep -f judge_eval >/dev/null; do sleep 30; done` の形で、**3 時間 08 分**
走り続けていた（pid 73674 / 73628・停止済み）。

**原因は自己マッチ。** 待機ループ自身のコマンド行に `judge_eval` という文字列が含まれるので、
`pgrep -f` が**自分を見つけ続ける**。条件が永久に成立しない＝止まる理由が無い。
測定そのものは正常に終わっていて（V3 5/5 は取得・commit 済み）、**残っていたのは
見張りだけ**である。実害は 20〜30 秒ごとの `pgrep` で、CPU も成果物も汚していない。

**待つならプロセスではなく成果物を見る。**

```bash
# 悪い（自己マッチで無限ループ）
until ! pgrep -f judge_eval >/dev/null; do sleep 30; done
# 良い（台帳の行数。待機ループ自身は台帳を増やさないので自己マッチしない）
until [ $(python3 -c "...len(rows)...") -ge 5 ]; do sleep 20; done
```

**同じ形の欠陥を実行層でも踏んでいる。** `procgroup`（子だけ殺して孫が残る）は
「止まる条件が実行されない」、これは「止まる条件が自分を数える」で、どちらも**停止条件の
設計ミス**である。背景タスクを起こしたら、**何が成立したら終わるのか**を 1 行で言えるか
確かめる。記憶: `pgrep-f-waiter-matches-itself-2026-08-30`。

**常駐は正常。** `ollama serve`（pid 902）と Ollama.app（pid 851）は 1 日 22 時間動いて
いるが CPU 0.0% の常駐サービス。eval ハーネス・`agent-herd`・`aider` の走行中プロセスは 0 件。

## 4. 測る前に必ず確かめる 3 点（この日 8 件踏んだ）

1. **その役割は本番にあるか。** PV1 は 08-24 に撤去済み（測っていたのは残骸）。
   S2（8 ファイルを 4 グループへ）は本番の split が要求しない形——本番は

2. **本番はどの argv で起こすか。** `command` だけでなく profile の引数まで含める
   （`engine.production_argv`）。`readonly` も本番の `_agent_readonly` に訊く
   ——`readonly=True` は `--tools` を落とすので、取り違えると道具の有無ごと変わる。
3. **本番はその出力をどう受けるか。** `verify` は本文の `verify=pass` / `verify=fail` も
   読む。`classify` の契約は `class=<ラベル>` の本文（JSON ではない）。
   `extract` / `retrieve` は契約検査に落ちたら**形式修復を 1 回**入れる。
   写さないとハーネスだけが厳しくなり、本番なら救えている出力を失点に数える。

**もう 1 つ: 診断に正解を混ぜない。** 再投入の材料は「本番の機械が言えること」だけ
（宣言された制約への違反・実行結果そのもの）。`GOLD_*` 由来の情報を返すと、
本番で再現しない助けを測ることになる。
