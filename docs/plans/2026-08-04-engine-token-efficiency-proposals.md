# エンジン側のトークン効率化 — 仕組みとしての利用量削減の比較検討

> 作成 2026-08-04
> 位置づけ: **提案・比較検討（実装前）**。採用案が決まってから各案の詳細設計を起こす。
> 先行して実装した「エンジン設定 `model_tiers:` による静的なモデル振り分け」（PR #666 初版）は
> 本検討により撤回（revert）——階層の定義はユーザー界面（agent-dashboard）の責務とし、
> エンジン側には「仕組みとしての効率化」を置く、という切り分けに合わないため。
> 対象: `agent-project` / `agent-flow` / `agentcore` / `agent-dashboard` / `agent-audit`
> 効く柱・原則: 柱1 / C1・C2・C3・C7（各案の欄に個別記載）

---

## 0. 要求の整理

1. **大中小（エージェント × モデルのセット）の定義はユーザー界面のもの。**
   agent-dashboard に置き、複数候補を定義できて、エージェント（ワークロード）ごとの
   トークン使用量に応じて**決定的に**自動選択できるとよい。エンジンは選択結果を既存契約
   （agent-control）で受け取るだけ——エンジン側に選択ロジックの複製を持たない。
2. **本質はエンジン側の「仕組みとしての効率化」。**
   例: 強いモデルがタスク分解するだけでなく**読むべきファイルまで指定**する。弱いモデルの
   コンテキスト圧迫を防ぎ、探索の無駄が消える。やり直しリスクは**途中から再開**で抑える。
3. すべて**オプトイン**。宣言しなければ既定挙動は不変。現状の設計（責務境界・解決経路・
   契約）は崩さない。

## 1. どこでトークンが消えているか（現状の構造）

削減案を比べる前に、消費の**原資**を現状の実装から分類する（実測は agent-audit
`--by workload / model` と node-budget 台帳で取れる——採用判断の前に必ず測る。§5）。

| # | 原資 | 現状の仕組み | 消え方 |
|---|---|---|---|
| (i) | **探索・読込** | agent-flow の worker は goal と repo の clone 指示だけを受け、**どのファイルを読むかは自分で探索**する（`execute_agent` は依存成果と作業指示のみ注入） | ls / cat / grep の試行錯誤が毎ノードで発生。弱いモデルほど探索が長い |
| (ii) | **中間成果の再注入** | 依存タスクの成果は**全文 inline**（`_dep_text` は無切り詰め）。reduce は `reduce_width` で木にするが、各段で全文が入り直す | 冗長な worker 出力が下流の全消費者に複製課金される |
| (iii) | **やり直し** | verify=fail / 失敗の retry は `[retry]` ノードとして**全作り直し**。前回の成果物は自動では渡らない（evaluator への指摘要約 1200 字のみ）。run 単位の再開（done ノード温存）はあるが、**ノード内の部分再開は無い** | 1 文字の修正で済む失敗でもタスク丸ごと再実行 |
| (iv) | **定常注入** | rules.md・charter・repo 文脈・brief・グローバル指示を全タスクへ常時・有界注入 | 呼び出し回数に比例。1 回あたりは有界だが総量は大きい |

kiro-loop 側の注入レベルの削減（rtk / caveman・`agent-tuning` 契約）は
[別提案](./2026-08-03-kiro-loop-token-reduction-proposals.md)で先行検討済み。本書は
**エンジン（project / flow）の実行構造**に絞る。

## 2. 案

### 案 A: コンテキスト割付契約 — 強いモデルが「読むべきファイル」まで指定する

**仕組み**: flow-planner（計画は既に strong に振れる）の出力ノードへ `context:` を追加する
（例 `{files: ["src/api/auth.py", "tests/test_auth.py"], note: "トークン検証だけを直す"}`）。
エンジンはこれを worker プロンプトへ「**まずこのファイルだけを読む。挙げた範囲で足りない
ときだけ追加探索し、その旨を成果に記す**」という決定的な描画で注入する。agent-project 側も
plan（バックログ分解）に同じ欄（task spec の `- files:`）を持たせ、実行要求 → flow へ伝搬する。

- **削減原資**: (i) 探索・読込（支配的な原資であることが多い）。副次的に (ii)（迷走した
  探索ログが成果に混ざらない）。
- **決定性**: 契約の描画・伝搬は決定的。ファイル選定自体は strong モデルの出力だが、それは
  現状の「計画」が持つ非決定性と同じ層で、新しい非決定性を持ち込まない。
- **リスクと緩和**: 割付漏れで worker が手詰まりになる → 割付は**助言**（探索を禁止しない）
  とし、失敗 retry は割付なしで組み立てる（案 B と組むとさらに安い）。planner の出力が
  肥大する → files は上限個数で切る（スコープ契約と同じ流儀）。
- **実装点**: flow-planner のプロンプト/出力契約・`execute_agent` の描画・agent-project の
  planner_skill / request 組み立て。既存のスコープ契約（粒度設計 2026-07-25）の自然な延長。
- **オプトイン**: `context_contract: true`（flow / project の yaml）。
- **原則**: C3（機械で渡せる文脈を探索させない）・C1（探索の無駄はそのまま財布から出る）。

### 案 B: 差分修復リトライ + 段階チェックポイント — やり直しを「途中から」にする

**仕組み**: 2 段階に分ける。

1. **差分修復リトライ（軽い・先行）**: verify=fail / 差し戻しの作り直しノードに、前回の
   成果物（バスの artifacts 参照——既にファイル渡しのプロトコルがある）と失敗理由を渡し、
   「全再作成ではなく**指摘箇所の修復**」を指示する。修復で直らなければ従来の全作り直しへ
   戻す（`max_retries` の予算内。修復は 1 系統 1 回まで）。
2. **段階チェックポイント（重い・後続）**: work ノードの実行を「調査 → 実装 → 自己検査」の
   段に分け、各段の成果をバスへ固定。途中失敗は**最後に通った段から再開**する。

- **削減原資**: (iii) やり直し。リトライ率が高い運用ほど効く。
- **決定性**: リトライ経路の組み立て（前回成果の参照・指示文）は決定的。
- **リスクと緩和**: 壊れた前回成果に引きずられて修復が収束しない → 修復は 1 回だけで
  全作り直しへフォールバック（既存のサーキットブレーカーの内側）。チェックポイントの
  段割りが浅いと効果がない → まず 1 の実測を見てから 2 に進む。
- **実装点**: 1 は continuation（retry ノードの組み立て）と worker プロンプトのみ。
  2 は worker skill と実行機の改修を伴い大きい。
- **オプトイン**: `repair_retry: true` / `staged_work: true`。
- **原則**: C7（必ず止まる: 修復回数も既存予算の内側）・C1。

### 案 C: 弱→強エスカレーションはしご — 失敗したときだけ強いモデルを使う

**仕組み**: 選んだ kind / purpose について、初回は弱いモデルで実行し、verify=fail や出力契約
違反の作り直しで**はしごを 1 段上る**（例 `ladder: [haiku, sonnet, opus]`）。静的な振り分け
（撤回した `model_tiers:`）と違い、**成果物を直接作る worker 系にも安全に適用できる**——
失敗したときのコスト（作り直し）が案 B で安くなっているほど、weak-first が現実的になる。

- **削減原資**: 呼び出し単価そのもの（弱いモデルで済んだ分）。(iii) と表裏。
- **決定性**: はしごは宣言（設定）から決定的に段が決まる。リトライ回数 → 段の対応は
  純関数。
- **リスクと緩和**: 弱い初回の失敗率が高いタスク種別では逆効果（2 回課金） → kind /
  purpose 単位のオプトインにし、agent-audit の実測（purpose × model の成功率・トークン）で
  対象を選ぶ。verify が甘いと弱い成果がすり抜ける → 適用条件を「verify を持つ系統に限る」
  とする（C5 の機械検証が受け皿にあるときだけ弱くする）。
- **実装点**: `_agent_for` にリトライ深度を渡す（深度は既存 `_retry_depth` にある）。
  設定は `agents:` の値を配列拡張するか `ladder:` を別キーで。
- **オプトイン**: `ladder:`（対象 purpose を明示した宣言のみ有効）。
- **原則**: C5（機械検証が受け皿）・C1・C7（段数有限）。

### 案 D: dashboard の大中小プロファイル — 使用量に応じた決定的自動選択（エンジン無改修）

**仕組み**: agent-dashboard に「実行エージェントのプロファイル」（大・中・小、各
`{agent_cli, model}` のセット、複数候補可）を定義する画面を置く。選択は dashboard が
**決定的に**行う: node-budget 台帳（ワークロード別のトークン消費・残量は既にある）を入力に、
しきい値表（例: 予算残率 ≥ 50% → 大、≥ 20% → 中、それ未満 → 小。境界にヒステリシスを
置いてフラッピングを防ぐ）から純関数で 1 つ選び、**既存の agent-control 契約
（control.json の `workloads[].agent_cli / model / agents / degraded`）へ投函する**。
エンジンは今日すでに control を最優先で適用するので、**エンジン改修はゼロ**。

- **削減原資**: 呼び出し単価。予算逼迫時の自動縮退は既存 `degraded` の一般化に相当する。
- **決定性**: 台帳スナップショット + しきい値表 → 選択、の純関数。同じ入力なら同じ選択。
  適用状況は既存の status ハートビート（`effective`）で可視化される。
- **リスクと緩和**: 使用量シグナルが荒いと選択が暴れる → ヒステリシス + 最小保持時間。
  選択根拠が見えないと不信になる → 画面に「いまの選択と理由（残率・しきい値）」を表示。
- **実装点**: dashboard のみ（設定画面 + 選択関数 + control.json 投函。書き手は今までどおり
  dashboard 1 つ＝C7）。スキーマ追加も不要（agent-control の既存語彙で表現できる）。
- **オプトイン**: プロファイル未定義なら何も書かない（現状のまま）。
- **原則**: C2（エンジンに選択ロジックを複製しない。契約の投函だけ）・C7・C1。
  ※ ユーザー要望 1 の直接の受け皿。エンジン側の案 A〜C とは独立に導入できる。

### 案 E: 中間成果のダイジェスト渡し — 依存成果の全文 inline をやめる

**仕組み**: 依存成果の注入を「決定的な切り詰めダイジェスト（上限バイト）+ artifacts の
ファイル参照」に切り替える（`dep_digest: <bytes>`）。全文はバスの artifact に既にあるので
情報は失われない——消費側が必要と判断したときだけファイルを読む。map → reduce の木
（`reduce_width`）と直交して効く。

- **削減原資**: (ii) 中間成果の再注入。fan-out の大きい run で効果大。
- **決定性**: 切り詰めは決定的（先頭 N バイト + 「全文はこのファイル」）。LLM 要約は
  使わない（要約コストと非決定性を持ち込まない）。
- **リスクと緩和**: ダイジェスト外に重要情報があると読み落とす → 参照ファイルを明示し
  「判断に足りなければ必ず全文を読む」を指示。reduce の件数整合は既存の
  `_reconcile_count` が受け皿。
- **実装点**: `execute_agent` の deps 描画のみ（artifacts プロトコルは既存）。
- **オプトイン**: `dep_digest:`（既定 0 = 従来どおり全文）。

### 案 F: 判断のメモ化 — 入力が変わらなければ呼ばない

**仕組み**: 「同じ入力なら同じ答えでよい」判断系 purpose（assess・route・prioritize の
安定部分・repo_map）について、正規化した入力のハッシュをキーに前回結果を再利用する。
repo_map の HEAD sha キャッシュ（既存）と同型の一般化。

- **削減原資**: 判断系の呼び出し回数そのもの。バックログの churn が小さい運用で効く。
- **決定性**: キャッシュヒット判定はハッシュ一致のみ（決定的）。
- **リスクと緩和**: 入力正規化の漏れで「変わったのに再利用」 → キーに rules.md 版・
  charter 版を含める。鮮度が要る判断（doctor 等）は対象外リストで除く。
- **実装点**: purpose 呼び出しの前後に薄いキャッシュ層（エンジンごと）。
- **オプトイン**: `memoize: [assess, route]`（対象を明示宣言）。

### 案 G: 判断のダイエット — LLM 判断の決定的代替とバッチ化

**仕組み**: 3 点セット。

1. 判断系 purpose に **`agent / heuristic / none` の統一スイッチ**を揃える。部分的には既に
   ある——prioritize は `planner: none`（priority 降順→最古）、ルーティングは
   `route_planner: none`、assess は失敗時に決定的ヒューリスティック（`_assess_heuristic`:
   cohort→c、avoid 類似→r、verify 有無→a）へ落ちる。これを「失敗時フォールバック」では
   なく**最初から heuristic を選べる**ようにする（例 `assess: heuristic`）。
2. 残す LLM 判断は**バッチ化**する。投入時採点は現状 1 タスク 1 呼び出し（`assess_task`）
   ——投入バッチを 1 呼び出し N タスク（上限つき・出力は id → 採点の JSON）にすれば、
   回数が 1/N になり定常注入 (iv) も償却される。
3. agent-audit で「LLM 判断と決定論の**結論一致率**」を測り、一致率の高い判断から順に
   引き下げる（LLM に聞く価値が実測で無い判断を、実測を根拠に落とす）。

- **削減原資**: 判断系の呼び出し回数そのもの + (iv) の償却。
- **決定性**: heuristic は完全決定的。バッチの組み立ても決定的。
- **リスクと緩和**: 判断の質低下 → 採点・優先順位は「情報のみ」で後段に人・ゲートが
  ある系だけを対象にする（実行可否や done を決める判断は対象外）。
- **実装点**: スイッチの整備 + assess のバッチプロンプト。小〜中。
- **オプトイン**: purpose ごとの明示宣言のみ有効。
- **原則**: C3 の裏返し（機械で決められることは LLM に**も**聞かない）・C7。

### 案 H: 安定プレフィックス化 — プロンプトキャッシュに適合する注入順の正規化

**仕組み**: プロンプトの組み立てを「**安定部**（rules.md・charter・repo 文脈・スキル前置
＝タスクに依らず同一）→ **可変部**（タスク・deps・brief）」の順に**同一バイト列**で並べる
規約をエンジンに敷く。プロバイダ側のプロンプトキャッシュは**先頭一致**で効くため、
キャッシュを持つ CLI / API では安定部の入力課金が大幅割引になる。エンジンがやるのは
並べ替えと正規化（順序・区切りの固定）だけで、**注入内容は 1 バイトも変えない**。

- **削減原資**: (iv) 定常注入の**実効単価**（量ではなく値段を下げる）。
- **決定性**: 完全に決定的。内容不変なので品質リスクは実質ゼロ。
- **リスクと緩和**: 効果が CLI / プロバイダのキャッシュ実装に依存する（効かない環境では
  中立）。注入順の変更でモデルの注意配分が変わりうる → before/after を計測して判断。
- **実装点**: プロンプト組み立て箇所の順序規約 + 並び順を固定するゴールデンテスト。小。
- **オプトイン**: `stable_prefix: true`（既定 off = 従来順）。

### 案 I: パイロット→レシピ量産 — exemplar-first の一般化

**仕組み**: 既存の `exemplar_first`（map の先頭 1 件を検証ゲートに通してから残りを展開）を
拡張し、パイロット成功時にその成果から**レシピ**（実行手順・読んだファイル・出力形式）を
抽出して残りの map ノードへ注入する。残り N−1 件は「レシピ追従」タスクになるので、
探索がほぼ消え、弱いモデル（案 C / J）や小さいコンテキストで安全に量産できる。
レシピ抽出はパイロット成果からの決定的切り出し（足りなければ 1 回だけの蒸留呼び出し）。

- **削減原資**: (i) 探索（N−1 件分）+ 単価（量産側を弱く）。fan-out が大きいほど効く。
- **決定性**: 展開は既存機構のまま。レシピ注入の描画は決定的。
- **リスクと緩和**: 要素の異質性でレシピが合わない → 既存の検証ゲートが受け皿。落ちた
  要素はレシピなしで retry（案 B と同じ「安い作り直し」の流儀）。
- **実装点**: orchestrate の exemplar 展開 + worker プロンプト。中。
- **オプトイン**: `exemplar_recipe: true`（`exemplar_first` 前提）。
- **案 A との関係**: A は「計画者が**事前に**絞る」、I は「実行者が **1 件で学んで**絞る」。
  同型反復のワークロードでは I の方が精度の高いスコープを作れる。

### 案 J: 採点連動の事前ルーティング — 既存 assess の転用

**仕組み**: 投入時採点（`- assess: c/r/a`・既存・現状は「情報のみ」）を実行にも使い、
`max(c,r,a)` の**表引き**で act のモデル段（や粒度）を決める（例: max=1 → 小、max=2 → 中、
max=3 → 従来どおり）。spec ルーティング（採点 → spec 前置）と同じ「**採点は情報、判定は
決定的表引き**」の流儀で、新しい判断層を作らない。

- **削減原資**: 単価（軽いタスクを軽く実行する）。
- **決定性**: 表引きは決定的。採点自体は既存の非決定性と同層（決定的 heuristic の選択肢も
  既にある——案 G と組めば採点も決定化できる）。
- **リスクと緩和**: 採点の過小評価で弱いモデルが難タスクに当たる → verify・
  delivery_review が受け皿。**案 C（事後はしご）と併用すると「事前に安く始め、失敗したら
  段を上る」が完成する**（J は入口、C は出口）。
- **実装点**: 実行要求の組み立てで採点 → モデルの表引き。小。
- **オプトイン**: `assess_routing:`（表を明示宣言したときだけ有効）。

## 2b. ブレストの全景と見送り案

案出しの枠: **消費 = 呼び出し回数 × (入力量 + 出力量) × 単価**。因子ごとに掃いた:

| 因子 | 案 |
|---|---|
| 回数を減らす | G（決定的代替・バッチ化）/ F（メモ化）/ B（やり直し削減） |
| 入力量を減らす | A（割付契約）/ E（ダイジェスト）/ I（レシピ）/（見送り: rules の関連度フィルタ） |
| 出力量を減らす | （見送り: 中間出力の簡潔契約 → kiro-loop 系へ統合） |
| 単価を下げる | C（はしご）/ D（プロファイル）/ J（採点連動）/ ローカルモデル退避（既存 `agents:` で表現可能） |
| 実効単価を下げる | H（キャッシュ適合） |

**検討して見送った案**（理由つき。前提が変われば再考する）:

1. **中間出力の簡潔契約**（caveman のエンジン版。機械間で受け渡す中間成果の散文を禁じ
   構造化・簡潔に）— 実現機構が kiro-loop 提案の `agent-tuning` 汎用化（injections）と
   同一になるため、**二重機構を作らずあちらの workloads 拡張（flow への適用）に乗せる**（C7）。
2. **rules.md の関連度フィルタ**（タスクの書込先 repo でルール注入を絞る）— learn / rules の
   適用範囲（スコープ）情報の整備が先。範囲の無い今はフィルタの根拠が作れない。
3. **プレイブック宣言**（頻出タスク型に計画テンプレを宣言して planner をスキップ）—
   効果がタスクの型再現性に強く依存。F（メモ化）+ I（レシピ）で大半を代替できるので、
   両者の実測後に再考。
4. **確信度カスケード**（判断を弱→強の二段にし、弱の確信度が低いときだけ強へ）—
   弱いモデルの自己申告確信度には信頼できる較正が無い。C のはしご（verify という
   **外部**シグナルで段を上る）で足りる。
5. **予算連動の fan-out 絞り**（予算残で granularity を coarse 化）— 分解の質へ直接効く
   わりに削減量が読めない。予算逼迫時の対応は D の縮退（degraded）で足りる。
6. **セッション再利用**（CLI の会話継続で文脈の再送を省く）— CLI ごとの挙動差が大きく、
   状態を持つ実行は再現性（C6）を壊す。H が**無状態のまま**同じ原資を狙える。

相互作用: **A・B・C（+I・J）は一つの物語になる**——強いモデルが計画とコンテキスト割付をし
（A / 同型反復なら I）、採点で軽いタスクは安く始め（J）、弱いモデルが絞られた入力で実行し
（C）、失敗しても前回成果から修復して（B）、それでも駄目なときだけ段を上る。
D は界面の話として独立、E・F・G は局所改善として独立、H は全案の下敷きにできる。

## 4. 推奨

1. **先に測る（着手前・小）**: agent-audit で purpose × model のトークン・失敗率を 1〜2 週
   実測し、(i)〜(iv) のどれが支配的かを確認する（C8: 配って終わりにしない、の着手前版）。
   併せて「LLM 判断と決定論の結論一致率」（案 G の刈り取り根拠）も取る。
   ここで支配的原資が想定（i, iii）と違えば、この推奨の順序を差し替える。
2. **Phase 1（即効・低リスク）**: **案 D**（エンジン無改修・ユーザー要望 1 の受け皿）+
   **案 B-1 差分修復リトライ**（小さくて単独で効く）+ **案 H**（品質リスク実質ゼロ・小）。
   計測結果が出しだい **案 G** の引き下げ対象を刈り取る。
3. **Phase 2（本丸）**: **案 A コンテキスト割付契約**。B が入っているので割付ミスの
   コストが小さい。fan-out 中心の運用なら **案 I** を並行。
4. **Phase 3**: **案 C はしご + 案 J 採点連動**（事前・事後の両輪。A+B の土台の上で
   weak-first が安全になってから）。**案 E**・**案 F** は計測が示す支配的原資に応じて随時。

## 5. 効果計測（全案共通）

- before/after を agent-audit（`--by workload` / `--by model`）と node-budget 台帳で比較する。
- 各案は適用の有無を run brief / ledger の帰属（既存の `agent_cli` / `model` 欄と同様）に
  残し、**効いていない・品質が落ちた**ことに気づける状態を保つ（C8）。
- 案 B・C は「リトライ率・修復成功率・段上がり率」を副指標に持つ（逆効果の検知）。
