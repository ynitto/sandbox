# 手分けして二巡するフロー（`two-wave-fan-out`）— 検討と設計

発端は「research-swarm を入れたい」という提案。OpenAI が 2026-09-08 に公開した
Navier–Stokes 問題の報告（約 1 万の同時エージェントを複数群に分け、途中で各群の
有用な知見をまとめて撒き直し、解法到達後に別途 Lean 形式化で検証した）を受けて、
4〜8 の探索 → 知見抽出 → 撒き直し → 第 2 波 → 独立検証を新しいパターンとして
足す、という案だった。

新しい swarm の実装を外から持ち込まない、という判断には同意する。本書はその上で
**「正典（`PATTERNS`）に入れるか、任意に選ぶ同梱フローに留めるか」を判定し、
名称と構成を用途から切り離して一般化した**記録である。実装済み。

## 検討

### 1. 何が新しいのか

提案の形を分解すると、次の 3 つに分かれる。

| 要素 | 既存にあるか |
| --- | --- |
| 多様な切り口で並列に探索する | ある（並列実行して統合・候補を生成して選別） |
| 並列の成果を 1 つに集約する | ある（統合・集約の工程） |
| **集約したものを、成果物ではなく次の並列の入力として撒き直す** | **無い** |
| 別工程が独立に検証する | ある（生成して検証） |

新しいのは 3 番目だけで、しかもこれは**既存の並列＋集約を 2 回つなぐ**ことで表現
できる。集約の出力先が「人が読む成果物」ではなく「次の並列工程の材料」だ、という
使い方の違いであって、実行機構の違いではない。

「知見の共有」「群」「第 2 波」に当たる仕組みはリポジトリ内に無い（討論の複数席が
前ラウンドを読む `rounds` / `topology` と、見本先行の `pilot-then-batch` が近いが、
前者は討論の枠組み、後者は手順の複製で、探索の知見を撒き直す形ではない）。
その意味で着想は新しい。新しくないのは**形**のほうである。

### 2. 正典に入れるかの判定

正典の 7 つが正典である理由は 2 つしかない。6 つは Claude Dynamic Workflows の
基本形で、7 つ目（分割して集約）は**実行時に展開数が決まるため静的なグラフでは
書けない**——エンジンの展開機構（`_expand_splits`）を必要とする。

提案は**新しい工程種別も、新しい実行機構も、新しい展開規則も要らない**。既存の
工程種別だけで静的なグラフとして最後まで書ける。実際、既存の合成形（並列調査 →
検証 → 統合など）は正典に入れず、planner が読むカタログの合成欄に置かれている。
提案はその合成形にもう一巡足したものなので、**同じ層に置くのが一貫している**。

判定: **既存の派生系。正典には入れず、利用者が任意に選ぶ同梱フローに留める。**
`PATTERNS` にも planner の合成カタログにも足さない（後者に足すと planner が自動で
選ぶようになり、「任意に選ぶ」を越える）。

### 3. 名称と構成の一般化

「research」も「swarm」も外す。研究に限る理由が無いためで、同じ形は次のどれにも
そのまま効く。

| 用途 | 一巡目 | 持ち寄るもの | 二巡目 |
| --- | --- | --- | --- |
| 調査・技術選定 | 別々の切り口で当たる | 確かめた事実・否定された筋 | 生きている筋を詰める |
| 不具合の切り分け | 別々の仮説を試す | 潰れた仮説と潰れ方 | 残った仮説を詰める |
| 移行・大規模改修の下調べ | 別々の対象で試す | 実際に効いた手順と落とし穴 | 残りへ広げる |
| 設計案の探索 | 別々の案を書く | 各案で効いた部分 | 組み合わせて練り直す |

共通して言えるのは「**一巡目は成果物ではなく偵察で、そこで分かったことを全員に
配ってから本番の一巡を回す**」こと。名称はこの形そのものを指す `two-wave-fan-out`
（画面表示は「手分けして二巡する」）とし、用途を名前に持たせない。

一般化の結果、切り口も用途非依存の 4 つにした——正攻法 / 前提を疑う / 最小の具体
から / 似た事例から借りる。どれも領域に依存しない当たり方で、上の表のどの用途でも
意味を持つ。二巡目も同様に、最有力 / 次点 / 行き止まりへの挑み直し / 組み合わせ、
の 4 役にした。最後の「組み合わせ」が、撒き直しの効果が出る唯一の席である。

## 目的

一度で答えが出ない依頼に対して、並列の一巡目を偵察に使い、そこで分かったことを
全工程へ配ってからもう一巡回す形を、利用者が選べる同梱フローとして提供する。
正典のパターン集合と planner の自動選択は変更しない。

## 変更対象

| 対象 | 変更 |
| --- | --- |
| `workflows/two-wave-fan-out.json` | 新規。11 工程（探索 4・持ち寄り 1・二巡目 4・検証 1・まとめ 1）と差し戻し 1 件 |
| `tools/agent-flow/tests/test_workflow_schema.py` | 同梱フローのグラフ不変条件・実行側の受理・撒き直し経路の 3 テストを追加 |
| `docs/specs/agent-dashboard-spec.md` | 同梱フローの用途と表示区分の記述を更新（同梱が設計用だけではなくなるため） |
| `tools/agent-dashboard/README.md` | 同上 |

`PATTERNS`（`tools/agent-flow/agent_flow/patterns.py`）と planner の合成カタログ
（`.github/skills/flow-planner/patterns-catalog.yaml`）は**変更しない**。

### 形

```
probe-direct   ─┐                           ┌─ refine-lead    ─┐
probe-doubt    ─┤                           ├─ refine-second  ─┤
probe-minimal  ─┼─→ harvest ────────────────┼─ refine-retry   ─┼─→ verify ─→ synth
probe-analogy  ─┘   （持ち寄り資料）        └─ refine-combine ─┘      ↑          ↑
                         ↑                                            └──────────┘
                         └──── 差し戻し（検証が通らなければ二巡目だけやり直す）
```

### 強制レイヤー

| 契約 | どこで強制されるか |
| --- | --- |
| 撒き直しの中身が要約で潰れないこと | 持ち寄り役の工程種別が「集約」であること。依存を全文で受け（`_FULL_DEPENDENCY_KINDS`）、かつ構造化データを成果として意図する種別（`STRUCTURED_KINDS`）でなければ、宣言した `summary` が立たず二巡目には本文の先頭 600 字しか届かない。テストで両方を固定した |
| 二巡目の受け手が要約で受けること | エンジンの既定（自由記述の工程は digest）。ライブラリ定義の工程は `dependency_input` を宣言できない（スキーマが `additionalProperties: false`）ため、全文で渡す抜け道は無く、`summary` に書く以外に配る手段が無い |
| 検証が独立であること | 検証工程が二巡目の 4 工程だけに依存し、自分で答えを作らない指示を持つこと。判定を書かない出力は失敗として扱われる（エンジンの判定正規化がフェイルクローズ） |
| 差し戻しが一巡目を巻き込まないこと | 差し戻しの戻り先を持ち寄り役にすること。実行側は「戻り先を祖先に持ち、かつ差し戻し元の祖先である」工程だけを置換対象にするので、探索の一巡目は温存され、まとめ工程は置換に追随して付け替わる |
| 開始・終了の宣言がグラフと一致すること | 保存側（各画面の正規化）が強制。同梱ファイルは保存を経ないため、テストで固定した |

## 受入基準

1. 同梱フローとして一覧に出る（`implementation` / `library`、出所は同梱）。
2. 投入形へ落としたとき実行側に受理される（11 工程・`{{request}}` が残らない）。
3. 持ち寄り役が一巡目の成果を全文で受け、二巡目の 4 工程が要約で受ける。
4. 検証が通らなかったとき、やり直すのは持ち寄り以降だけで、一巡目の探索は残る。
5. 正典のパターン一覧と planner の自動選択が変わらない。

## 検証方法

```
AGENT_FLOW_STUB_SLEEP_MAX=0 python3 -m unittest discover -s tools/agent-flow/tests
python3 tools/ci/check_user_docs.py
```

1〜4 は `tools/agent-flow/tests/test_workflow_schema.py` が機械で確かめる。
持ち寄り役の種別を自由記述側へ変える・終了の宣言をずらす、のどちらでもテストが
落ちることを確認済み。5 は既存の正典一覧テストが担保する（触っていない）。

## 積み残し

- **効果は未測定。** 二巡することが一巡＋検証より良い結果を出すかは、実際に走らせて
  比べるまで分からない。比較の材料として `tools/agent-flow/tests/pattern_cases.yaml`
  と同じ流儀のケースを足すのが次の一手。良いと分かってから、planner の合成カタログへ
  入れるかを改めて判断する（入れた時点で自動選択の対象になるため、順序を逆にしない）。
- 費用は素直な一巡の 2 倍強。持ち寄り役の出力が崩れると二巡目が丸ごと無駄になるので、
  小さい実行レベルで回すときは持ち寄り役だけ実行レベルを上げるか、出力の形を縛る
  作業ルールを当てる想定。
- 一巡目・二巡目の数は 4 で固定。件数を要求に応じて変えるには実行時の展開が要り、
  それは正典の「分割して集約」の領分になる。ここで抱え込まない。
