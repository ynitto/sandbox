# agent-app agent-flow ティーチング・ワークスペース設計

> 決定日: 2026-09-06  
> 対象: `tools/statemachine-maker`、`tools/agent-app`、`tools/agent-flow`  
> 関連: `2026-09-06-statemachine-maker-ai-teaching-workspace-design.md`、`2026-09-05-statemachine-maker-agent-flow-workflow-design.md`、`2026-09-05-agent-app-task-workflow-navigation-design.md`

## 背景

agent-app の「ワークフロー」領域には、agent-flow の定義、手動 DAG 編集、実行、停止、人への確認、履歴、成果表示がすでにある。一方、作成・変更は利用者が node kind、依存関係、human node を直接組み立てる方式であり、ステートマシン側で採用した「AI に仕事を教え、試運転結果を確認する」体験とは分かれている。

agent-flow はステートマシンと違い、定型手順を再現するものではない。入力や途中結果に応じて複数 AI が仕事を分解し、並列化し、失敗や評価を受けて再計画する。この違いを残したまま、入口、進行状態、試運転、承認、変更相談の UX を揃える。

## 目的

- 目的の説明から AI との対話だけで agent-flow ワークフローを作成・変更できる。
- ステートマシンと同じ進行状態と主要操作で利用できる。
- 固定工程ではなく、目的、適用範囲、制約、判断方針、品質基準を教えられる。
- 代表入力による実際の試運転と利用者承認を、利用可能にする条件とする。
- 入力ごとに分割数、個別作業、再計画を変えられる汎用性を保つ。
- 後工程から前工程への差し戻しを、通常の依存関係と混同しない形で編集・表示する。
- 既存の `.agents/workflows/*.json` と agent-dashboard の読み取り契約を維持する。

## ステートマシンとの違い

| 観点 | ステートマシン | agent-flow |
|---|---|---|
| 中心 | 手順の再現 | 目的達成の戦略 |
| 工程 | 原則固定 | 入力や途中結果に応じて変化可能 |
| 教える内容 | 操作、変数、成功条件 | 目的、制約、判断方針、品質基準 |
| 主な証拠 | 操作記録 | 依頼例、成果例、参考資料、過去の結果 |
| 分岐 | 事前定義 | 動的分解・評価・再計画を許容 |
| 試運転の確認 | 操作と結果が期待どおりか | 戦略、役割分担、確認、成果が許容範囲か |
| 承認後に固定するもの | 実行手順 | 目的、境界、確認条件、品質基準 |
| 高度な編集 | 工程と遷移 | DAG、node kind、依存、再作業ポリシー |

## 検討したアプローチ

| アプローチ | 実装コスト | リスク | 保守性 | 拡張性 | 学習コスト | 柔軟性 | 推奨度 |
|---|---|---|---|---|---|---|---|
| **A. 共通ティーチング UX とドメイン別モデル** | 中 | 低 | 高 | 高 | 低 | 高 | ★★★ |
| B. ステートマシン機能をそのまま複製 | 低 | 高 | 低 | 低 | 低 | 低 | ★☆☆ |
| C. 定義形式まで完全共通化 | 高 | 高 | 中 | 高 | 中 | 中 | ★★☆ |

A を採用する。会話、AI の理解、試運転、結果承認という画面骨格を共有し、ステートマシンの仕事仕様と agent-flow の適応型ワークフロー仕様は分ける。B は固定手順向けの概念を持ち込み、agent-flow の柔軟性を失う。C は既存実行契約への影響が大きい。

## 全体フロー

```text
目的を説明
   ↓
AI が適用範囲・制約・品質基準を整理
   ├─ 曖昧な点を質問
   ├─ 依頼例・成果例・参考資料を要求
   └─ 分解・確認・再計画方針を提案
          ↓
代表入力で agent-flow を実際に試運転
          ↓
戦略・確認・成果を利用者が確認
          ↓
利用可能
```

進行状態はステートマシンと同じ四つにする。

```text
下書き → 試運転が必要 → 確認待ち → 利用可能
```

## 画面構成

### 一覧

ワークフローごとに名前、目的、準備状況、直近の試運転または実行結果、人の確認の有無を表示する。主要操作は次に揃える。

- 新しいワークフローを教える
- 変更を相談する
- 試運転する
- 実行する
- 技術詳細／高度な編集

### 作成・変更

左を AI との会話、右を「AI の理解」とする。狭い画面では「会話」「理解内容」「試運転結果」を切り替える。

「AI の理解」には次を表示する。

- 達成したい目的
- 適用範囲と受け付ける入力
- 成果の形式
- 必ず守る制約と非目標
- 分解・並列化・再計画の方針
- 人に確認する条件
- 完了・品質の判定基準
- まだ曖昧な点

ステートマシンの「操作を見せる」は主経路にしない。代わりに代表的な依頼、良い成果と悪い成果の例、参考ファイル、守るルール、過去の実行結果を証拠として追加する。

### 試運転結果

最終成果を先に表示し、次に品質基準の評価、人への確認、実行時間を示す。戦略、node、再計画、ログは詳細表示へ置く。

試運転では次を確認する。

1. 依頼をどう解釈したか。
2. どのように分解・並列化したか。
3. 途中でどのような再計画をしたか。
4. 人への確認が適切だったか。
5. 最終成果が品質基準を満たしたか。

利用者は `期待どおり` または `修正を相談` を選ぶ。`修正を相談` は結果、失敗理由、採用戦略を会話へ戻す。

## 内部モデル

内部は三層に分ける。

```text
教えた内容
  ├─ 会話
  ├─ 依頼例・成果例
  └─ 参考ファイル・過去の結果
          ↓
適応型ワークフロー仕様
  ├─ 目的と適用範囲
  ├─ 入出力契約
  ├─ 制約と非目標
  ├─ 分解・並列化・再計画ポリシー
  ├─ 人への確認条件
  └─ 完了・品質基準
          ↓
標準 agent-flow 定義と実行時の動的展開
```

AI は具体的な作業項目を大量に固定せず、入力ごとに適応できる小さな制御骨格を生成する。単純な依頼では一つの `work` node も許し、必要性を説明できる場合だけ `classify`、`split`、`map`、`synthesize`、`verify`、`human` などを加える。

## 保存形式

実行定義は従来どおり `<root>/.agents/workflows/<id>.json` に保存する。AI に教えた意味情報と試運転履歴は、一覧探索へ混ざらない sidecar に置く。

```text
.agents/workflows/
├─ review-change.json
└─ .teaching/
   └─ review-change.json
```

sidecar は最低限、次を持つ。

- `version`、`workflowId`、`status`
- `messages`
- 依頼例、成果例、参考資料の `evidence`
- 目的、範囲、入出力、制約、非目標、分解、再計画、確認、品質基準、未確定事項の `understanding`
- 候補世代 `generations`
- `activeGenerationId` と `lastSuccessfulGenerationId`
- `runId`、代表入力、評価を持つ `trials`

node 出力やログ全文は複製せず、既存 agent-flow run の `runId` で参照する。AI はファイルを直接変更せず、完全な候補を返す。アプリが正規化、循環検査、node kind 検査、保存を行う。

## 世代と利用可能判定

AI が候補を作るたびに generation を追加する。generation は適応型仕様、コンパイル済み標準定義、構成検査結果、変更理由、前世代との差を持つ。

次の全条件を満たした generation だけを `利用可能` にする。

1. 標準 workflow 定義の構成検査に成功している。
2. 代表入力による実際の agent-flow run が完了している。
3. 必須品質基準を満たしている。
4. 未処理の人の確認が残っていない。
5. 利用者が結果を明示的に承認している。

承認時に教示仕様と実行定義の digest を記録する。目的、制約、品質基準、確認条件、実行 DAG を変更した場合は `試運転が必要` に戻す。表示名や説明文だけの変更は再試運転を要求しない。通常実行は最後に承認された generation、試運転は編集中の generation を使う。

## DAG エディタと差し戻し

通常の `deps` は常に非循環とする。後工程から前工程への差し戻しは依存 edge にせず、別の再作業ポリシーとして保持する。

### 表示

- 通常線は上から下へ流れる実線とする。
- 差し戻し線はグラフ外側の専用レーンを通す破線とする。
- 差し戻し元に `差し戻し`、戻り先に `再開` の文字ラベルを付ける。
- 線上に理由と最大回数を表示する。
- 複数線は専用レーンへ束ね、node や通常線を横切らせない。
- 色だけで区別せず、線種、矢印、ラベル、凡例を併用する。
- キーボードで線を選び、理由、戻り先、最大回数、上限後の動作を編集できる。

### 実行意味

差し戻しはプログラムカウンタを以前の node へ戻す動作ではない。差し戻し理由、前回成果、利用者の指摘、戻り先の論理工程を材料として、後続計画を新しい node として再生成する。実行時グラフは常に DAG のままとし、再計画履歴を残す。

差し戻しポリシーは次を持つ。

- 差し戻し元と論理的な再開地点
- 発火条件または評価結果
- 再計画へ渡す理由
- 最大回数
- 上限到達後の `人に確認`、`失敗終了`、`現在の成果で続行`

## エラーと回復

| 状態 | 表示 | 回復操作 |
|---|---|---|
| 目的や範囲が曖昧 | 判断に必要な情報が不足しています | AI の質問に回答 |
| 汎用化しすぎ | 対象範囲が広く品質を安定させられません | 対象例または制約を追加 |
| 固定的すぎる | この依頼例にしか対応できない可能性があります | 別の代表入力を追加 |
| 過剰な分割 | 分担コストが成果を上回る可能性があります | 制御骨格を簡略化 |
| 統合工程がない | 複数成果を一つにまとめられません | 統合工程を追加 |
| 差し戻し先が不正 | 戻り先が削除または移動されています | 戻り先を再選択 |
| 差し戻し上限なし | 終了しない可能性があります | 回数と上限後の動作を設定 |
| 試運転失敗 | 品質基準との差を表示 | 修正を相談、再試運転 |
| 実行環境不足 | 必要な AI または agent-flow を利用できません | 接続を確認 |

差し戻しは、戻り先が前の論理工程であること、最大回数と上限後の動作があること、理由が再計画へ渡ること、最終的な統合・検証へ到達できることを保存前に検査する。

## テスト方針

### ドメイン

- 教示セッションの正規化、上限、秘密情報除去。
- 適応型仕様から標準 workflow への変換。
- 単純作業、並列処理、動的分割、人の確認、差し戻しの生成。
- 通常依存が DAG であり、再作業ポリシーが `deps` に混入しないこと。
- generation と digest による試運転状態の無効化。

### UI

- タスクとワークフローで作成、変更、試運転、承認の位置が揃うこと。
- 720px、980px、1440px で横スクロールが発生しないこと。
- 差し戻し線が node と通常線を横切らず、複数線を安定配置できること。
- キーボード操作と、色なしでの識別ができること。

### 実行統合

- 差し戻しで新しい再計画 node が作られること。
- 指摘と前回成果が再計画へ渡ること。
- 最大回数で停止し、指定された上限後の動作へ移ること。
- 試運転 run と通常 run を識別できること。
- 承認済み generation だけが通常実行に使われること。

### 回帰

- 既存 `.agents/workflows/*.json` の往復互換。
- agent-dashboard からの参照。
- 現行の手動 DAG 編集、実行、停止、回答、成果表示。
- agent-app の会話・タスク領域と、ステートマシンのティーチング機能。

## 受け入れ条件

- 利用者が node kind や依存関係を理解せず作成・変更できる。
- ステートマシンと同じ進行状態・主要操作を使用する。
- 代表入力の試運転と利用者承認なしに `利用可能` にならない。
- 入力に応じて分割数や実行 node を変えられる。
- 差し戻し線がグラフ外側で明確に読める。
- 差し戻し後も実行時グラフが DAG を維持し、再計画履歴を追跡できる。
- 既存ワークフロー定義と agent-dashboard の契約を壊さない。

## 既存スキルとの関係

- `agent-flow`: node 種別、動的分解、再計画、human node、結果契約の正典。
- `statemachine-use`: 共通 UX の参考とするが、agent-flow の内部形式には流用しない。
- `brainstorming`: 共通化範囲とドメイン差の決定に使用した。
- `decomposition`: 承認後の実装計画を実行可能な単位へ分解する。
- `failure-driven-development`: 実装時に過剰分割、再計画停止、成果未統合などの失敗経路を固定する際に有効。

既存スキルだけでは教示 sidecar、適応型仕様、generation 管理、DAG 外の差し戻しポリシーを提供できないため、agent-flow の作成機能として実装する。

## 非目標

- ステートマシンと agent-flow の実行定義の共通化。
- 循環する `deps` の許可。
- AI による候補の無検査保存。
- すべての依頼を強制的に分割・並列化すること。
- 試運転なしの自動公開。
- agent-dashboard を新しい書き込み UI に変更すること。
- agent-flow の scheduler を新設すること。
