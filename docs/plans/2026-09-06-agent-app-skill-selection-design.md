# agent-app 依頼単位スキル選択 設計

## 目的

エージェント自身が適切なスキルを自動選択しない場合でも、会話とタスク手動実行で必要なスキルだけを確実に適用する。設定済みスキルをすべてプロンプトへ入れる方式は採用せず、コンテキスト消費と指示の競合を抑える。

## 現状と問題

- `instructions.skills` はスキル名の一覧として、現在は会話の各ターンとタスク手動実行の共通指示へ入る。
- 名前の提示だけでは、スキルを自動選択しないCLIで適用が保証されない。
- すべての `SKILL.md` を毎回展開すると、無関係な指示、競合、コンテキスト消費が増える。
- 「推奨スキル」と「起動時アクション」の役割が近く見え、候補と強制適用を区別しにくい。

## 決定

「自動選択の候補」から依頼単位でスキルを選ぶハイブリッド方式を採用する。

- 自動選択はプライマリ最大1件、補助最大2件とする。
- 関連スキルがない場合は0件とし、候補を無理に適用しない。
- ユーザーの明示指定と手動選択は自動判定より優先する。
- 会話とタスク手動実行に、同じ `自動 / 手動選択 / 使用しない` の選択UIを置く。
- 適用結果は実行情報へ記録し、どのスキルが使われたか確認できるようにする。
- スキル本文を全件一括でプロンプトへ入れない。

## 設定の役割

設定は次の3種類に分離する。

| 設定 | 適用タイミング | 用途 |
|---|---|---|
| 共通指示 | 依頼ごと | 常に守る短い運用方針 |
| 自動選択の候補 | 依頼ごとに選定 | 内容に応じて使う専門スキル |
| 起動時アクション | 新しいCLIセッションの開始時 | 必ず一度実行するスキルやコマンド |

既存の `instructions.skills` は「自動選択の候補」へ移行する。既存の `startupActions` の意味は変えない。

設定データの概念形は次のとおりとする。

```json
{
  "instructions": {
    "skillSelection": {
      "enabled": true,
      "defaultMode": "auto",
      "candidates": ["ui-designer", "self-checking"]
    }
  }
}
```

最大件数やコンテキスト予算は安全な内部既定値とし、初期UIでは詳細設定として公開しない。

## 選定ロジック

選定は送信直前にローカルで行い、追加のAI呼び出しを発生させない。これにより起動時間、利用量、ネットワーク障害を増やさない。

優先順位は次のとおり。

1. 今回の依頼で明示されたスキル
2. UIで手動選択されたスキル
3. 候補の `name`、`description`、`tags`、トリガー句と依頼内容の一致
4. タスク種別に対応する補助スキル

自動選択の構成は既存 `skill-selector` の規則に合わせ、プライマリ1件と補助2件までとする。補助スキルは成果物がある場合の `self-checking` と、条件に合う開発手法系スキル1件を上限とする。

会話では現在の入力と添付ファイル名を判定材料にする。過去の全会話は判定材料へ再投入せず、必要なら現在の依頼から参照された直近文脈だけを使う。

タスク手動実行では、タスク名、説明、種別、ステートマシンの手順、自由記述プロンプト、今回の入力パラメータを判定材料にする。判定材料はローカル処理にだけ使い、そのまま重複してプロンプトへ追加しない。

## コンテキスト予算

- 候補一覧と全スキル本文はモデルへ送らない。
- 選定したスキルだけを渡す。
- 明示指定、プライマリ、補助の順で優先する。
- 予算を超える場合は補助スキルを後順位から丸ごと外し、`SKILL.md` を途中で切らない。
- 外したスキルは実行情報に理由を表示する。
- 明示指定したスキルを適用できない場合は黙って続行せず、送信前にエラーとして示す。

エージェントやモデルのコンテキスト上限が不明な場合は保守的な既定予算を使用する。初期実装では件数上限を主要な防波堤とし、実測した使用量から予算値を調整する。

## CLI別の受け渡し

エージェント定義にスキル受け渡し能力を持たせ、画面側でCLI名を分岐しない。

| 能力 | 受け渡し方 |
|---|---|
| ネイティブなスキル呼び出しに対応 | CLI固有の呼び出し記号で、今回選定したスキルを依頼より前に明示する |
| 読み取り専用コンテキストに対応 | 選定した `SKILL.md` だけを読み取り専用資料として追加する |
| どちらにも対応しない | 予算内で選定スキルをインライン化する。適用不能なら警告する |

対話セッションでも選定はターンごとに行う。起動時アクションとは別物なので、同じCLIセッション内でも依頼内容が変われば選定結果を変える。

## 会話UI

会話入力部の実行設定に `スキル` コントロールを加える。

- 既定表示は `スキル · 自動`。
- ポップオーバー内で `自動`、`手動選択`、`使用しない` を選べる。
- 手動選択では候補を検索し、チェックで選択する。
- 自動選択時は入力内容に応じた候補をチップでプレビューする。
- 送信後はアシスタント回答の実行情報に、実際に適用したスキルと省略理由を残す。
- 選択は今回のターンだけに適用し、グローバル設定を書き換えない。

常設の長い説明文は追加せず、状態、チップ、選択操作で意味が分かる構成にする。

## タスク手動実行UI

会話と同じスキルコントロールを、手動実行のコンパクトな実行設定ポップオーバー内へ置く。

- タスクを開いた時点で自動選択結果をプレビューできる。
- 入力パラメータを変更した場合は候補を再計算する。
- `自動 / 手動選択 / 使用しない` の語彙と操作を会話側と統一する。
- 手動実行の選択は、その1回だけに適用する。
- 実行履歴に適用スキルを保存する。

定期実行への適用は今回の範囲外とする。手動実行で挙動を検証した後、無人実行時の失敗方針と合わせて別途決定する。

## データフロー

1. 設定から候補スキルを読む。
2. 会話入力またはタスク実行文脈を正規化する。
3. 明示選択を反映し、候補を採点する。
4. 件数とコンテキスト予算で選定結果を確定する。
5. エージェント定義の能力に応じて受け渡し形式へ変換する。
6. スキル指示を今回の依頼より前へ配置して実行する。
7. 選定結果、受け渡し方式、警告を実行情報と履歴へ保存する。

選定結果は次の形を基本とする。

```json
{
  "mode": "auto",
  "requested": [],
  "selected": [
    { "name": "ui-designer", "role": "primary", "reason": "UI変更" },
    { "name": "self-checking", "role": "support", "reason": "成果物の検証" }
  ],
  "omitted": [],
  "delivery": "native-command"
}
```

## エラー処理

- 候補スキルが削除済み: 自動選択では除外して実行情報に警告する。
- 手動選択したスキルが存在しない: 送信または実行を止め、選び直せる状態を保つ。
- ネイティブ呼び出しが失敗: 自動選択なら警告して本依頼を継続し、手動選択なら適用失敗を明示して止める。
- 予算超過: 補助スキルを丸ごと外し、外した理由を表示する。
- 選定結果が0件: 正常状態として、そのまま依頼を実行する。

## テスト方針

- 設定移行: `instructions.skills` が候補へ失われず移る。
- 選定: 明示指定、手動選択、自動選択、0件、最大件数を検証する。
- 予算: 補助から外れ、本文が途中で切られないことを検証する。
- CLIアダプター: ネイティブ、読み取り資料、インラインの各契約を検証する。
- 会話: ターンごとに再選定され、適用スキルが実行情報へ残ることを検証する。
- タスク: タスク文脈と入力パラメータから選定され、手動上書きが1回だけ有効なことを検証する。
- Electron: 会話とタスクで同じ語彙・操作になり、キーボードだけで選択できることを検証する。

## 実装順序

1. 選定結果とCLI受け渡し能力のデータ契約を追加する。
2. 既存設定を候補設定へ移行する。
3. 副作用のない選定サービスと予算処理を実装する。
4. CLI別受け渡しアダプターを実装する。
5. 会話の送信処理と実行情報へ接続する。
6. タスク手動実行の準備処理と履歴へ接続する。
7. 会話とタスクの共通UIパターンを実装する。
8. 実機テストで主要CLIごとの適用結果とコンテキスト使用量を測る。

## 対象外

- 定期実行への自動スキル選択
- リモートのスキル推薦サービス
- 選定専用の追加LLM呼び出し
- 全スキル本文の一括投入
- 初期UIでの細かなトークン予算調整
