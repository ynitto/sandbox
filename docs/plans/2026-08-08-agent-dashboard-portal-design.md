# agent-dashboard ポータル化 — agent-* ファミリー横断の入口 設計

> 決定日: 2026-08-08
> 対象: `tools/agent-dashboard/`
> 前提: [`docs/designs/agent-dashboard-design.md`](../designs/agent-dashboard-design.md)（骨格の正典）／
> [`docs/designs/agent-tools-concept.md`](../designs/agent-tools-concept.md)（上位文書）
> 状態: 第 1 段・第 2 段（領域ナビ）実装済み・残りは計画
> **効く柱・原則**: 柱2 / C4 — 横断ホームで「人の判断待ち」を 1 枚に集約し、
> 人の 1 回の介入の質と速さを上げる（介入の回数はエンジン側の契約が減らす。画面は質を上げる）

---

## 1. TL;DR

**何を変えるか**: agent-project 専用ビュアーとして育った画面を、agent-* ファミリー全体
（プロジェクト / 定常業務 / ミッション / 参加 / 利用状況）の**ポータル**へ整理する。

**主要な決定**:

1. 最初の画面を「ホーム（ポータル）」にする。どの制御面にも属さない base のタブで、
   横断の要対応キューと、各制御面のサマリーカードを並べる。
2. カードは 3 つ目の登録簿 `registerPortalCard` で差し込む（`registerFeatureTab` /
   `registerGlobalSettingsPanel` と同じ開放閉鎖）。**コアはどのカードが載るかを知らない**——
   agent-project も他の制御面と同じ 1 枚のカードになる。
3. ホームは discover() が既に持つデータだけで組む。**新しい取得経路・状態の書き手・
   判断根拠を 1 つも増やさない**（正典 §3.1 / §3.3 の護りはそのまま）。
4. アプリの見出しを「プロジェクト管理」から「エージェントポータル」へ改める
   （Electron の製品名 `Agent Dashboard` と整合。改称方針は
   [`agent-tools-rename-design.md`](../designs/agent-tools-rename-design.md)）。

**却下した主要案**: KiroCrew 型の Gateway（常駐プロセスが会話・承認・記憶を中央で持つ）を
このアプリに持ち込む案（§3.1）。agent-project の「概要」を拡張してホーム扱いにする案（§3.2）。
第 1 段でサイドバーごとワークロード別ナビへ作り替える案（§3.2）。

**読むべき人**: dashboard に制御面・カードを足す人。ポータル化の続き（第 2 段以降）をやる人。

## 2. 背景と課題

### 2.1 何が「特化しすぎ」だったか

このアプリは kiro-projects-viewer（agent-project 専用ビュアー）から育ったため、
制御面はソースツリーで対等（`src/features/` の 8 面）なのに、**画面の骨格だけが
agent-project を一等席にしたまま**だった。

- タブ列の先頭 5 本（概要 / タスク / 要対応 / 実行 / 成果）が agent-project 固定で、
  ミッション・定常業務・参加は hidden 始まりの「付け足しタブ」。
- 起動画面が「プロジェクトを選択してください」。agent-project のプロジェクトが無い端末では
  何もできない画面に見える（実際には定常業務・ミッション・利用状況が使える）。
- 見出しが「プロジェクト管理」。定常業務やミッションだけを使う人には自分の道具に見えない。
- 要対応（人の判断待ち）はプロジェクト単位のタブにしか無く、
  「このアプリを開いて最初に知りたいこと＝自分は何をすべきか」に答える画面が無い
  （正典 §8 の未実装項目「横断『要対応キュー』」）。

### 2.2 KiroCrew から何を借り、何を借りないか

参考にしたのは [KiroCrew](https://github.com/kirodotdev/KiroCrew)（kiro-cli を ACP で駆動する
常駐ワークスペース）。**借りたのは画面の思想**で、**アーキテクチャは借りない**。

| KiroCrew | 借りるか | 理由 |
|---|---|---|
| 入口はワークロード横断のダッシュボード（承認・実行・スケジュール・利用状況が 1 枚） | **借りる** | 柱2 / C4 そのもの。人が最初に見るのは「自分の判断待ち」と「全体の稼働」 |
| 各機能（会話・タスク・スケジュール・記憶・承認）が対等な面として並ぶ | **借りる** | 制御面の対等化。`registerPortalCard` の形にする |
| Gateway（常駐プロセスがセッション・承認・記憶・スケジュールを中央で保持） | 借りない | このファミリーは中央サーバを前提にしない（概念正典 §2）。状態の書き手は常駐体 1 つ・画面は契約の投函だけ（正典 §3.1）という既存の一本化が正 |
| 承認 UI が実行主体と同居 | 借りない | 承認は `commands/` 投函で本体が実行する既存契約のまま。画面へ実行権を寄せない |

### 2.3 目標と非目標

**やること**: (1) 最初の画面をファミリー横断のホームにする。(2) 制御面がコアを触らずに
ホームへ入口を出せる合成点を作る。(3) 要対応の横断ビューを置く。

**やらないこと**: 新しい IPC・状態の書き手・判断根拠の追加。エンジンの起動経路。
タブ・サイドバーの全面再構成（第 3 段で判断）。KiroCrew 型のセッション永続・会話面。

## 3. 主要な設計判断

### 3.1 ホームは base の画面。カードは登録簿で差し込む

**判断**: ホームは `data-feature="base"` のタブとして持ち、中身のカードは
`registerPortalCard(id, { order, html, wire })` の登録簿から並べる。カードの `html()` が
`''` を返したらそのカードは出さない（未利用の制御面を隠す判断を各 feature が持つ）。
定番の遷移はコアが 1 か所で配線する（`data-portal-tab` / `data-portal-settings` /
`data-portal-needs` 属性）。

**文脈**: 正典 §3.2 の列挙合成・§3.5 の 2 登録簿（フィーチャータブ・全体設定パネル）と
同じ形の 3 つ目。ホーム自身も `registerFeatureTab('home', …)` で自分を登録する
（コアの仕組みを自分でも使う）。

**選択肢と却下理由**:

- *agent-project の「概要」を拡張してホーム扱いにする*: 却下。特化の固定化そのもの。
  概要はプロジェクト 1 件の画面で、プロジェクト未選択・プロジェクト無しの端末で空になる
  構造は変わらない。
- *コアの renderHome にカードを直書きする*: 却下。制御面を足すたびにコアへ手が入る。
  登録簿ならマージ衝突も起きない（§3.2 と同じ理由）。
- *KiroCrew 型 Gateway の導入*: 却下（§2.2）。

**トレードオフ**: 登録は load 時実行なので、sections の「関数宣言のみ」契約と衝突する。
ホームの登録とコアカードの登録は bootstrap.js の `init()` が行い、feature モジュール
（participation / agent-audit）は従来どおり自分の load 時に登録する。

**確信度**: 高い。既存 2 登録簿で実証済みの形。

### 3.2 横断キューは discover() の範囲で組む

**判断**: ホームの「あなたの対応待ち」は discover() が全プロジェクト分を既に持つ
`needsCount` だけで組む（プロジェクト単位の件数・件数降順）。クリックで
そのプロジェクトの要対応タブへ飛ぶ。

**文脈**: 正典 §8 の「横断『要対応キュー』」は要対応 1 件単位・緊急度 × 滞留時間ソートを
構想している。それには全プロジェクトの `needs/*.md` を読む必要があり、ホームの描画の
たびに全プロジェクトを readProject するのはポーリング負荷と正典 §3.3（発見の根拠は
状況ファイル 1 枚）への追加経路になる。

**選択肢と却下理由**: *初手から per-need キュー*は却下ではなく**第 2 段へ送る**（§5）。
件数とジャンプだけでも「朝一にどこを見るか」には答えられ、滞留順は各プロジェクトの
要対応タブが既に持っている（SLA バッジ・滞留順ソート）。

**確信度**: 中。per-need 化の需要が確認できたら第 2 段で入れ替える。

### 3.3 起動時はホームに着地する。画面を移すのは人の選択だけ

**判断**: 起動時のアクティブタブをホームにする。前回選択プロジェクトの**復元**は裏で行い
（ヘッダとタブの文脈は温まる）、タブは奪わない。サイドバー・ディープリンクからの
**人の選択操作**だけが `reveal`（ホーム → そのプロジェクトの画面）で移す。

**文脈**: これまでの起動画面は前回プロジェクトの「概要」。ポータルの入口価値
（横断の判断待ちが最初に見える）は、着地しなければ生まれない。

**選択肢と却下理由**: *前回開いていたタブを復元する*は却下（保存していない現状維持でもある）。
復元先がプロジェクト固有タブだと、他プロジェクト・他ワークロードの判断待ちを見ずに
作業へ入る導線が残る。ホームからは 1 クリックで戻れる。

**確信度**: 中。日常運用で「ホームを飛ばしたい」が強ければ設定化する。

### 3.4 改名: プロジェクト管理 → エージェントポータル

**判断**: 画面の見出し（`<h1>` / `<title>`）を「エージェントポータル」にする。

**文脈**: Electron の製品名は改称設計で `Agent Dashboard` 済み。画面内の見出しだけが
旧役割（agent-project 専用）の名前で残っていた。UI 文言は利用者の言葉を使う方針のため
`Agent Dashboard` の直訳ではなく、役割（ファミリー横断の入口）を表す語にした。

## 5. 第 2 段 — 左メニューを領域ナビにする（実装済み）

第 1 段はホームを**タブ**として足しただけだったので、左（プロジェクト一覧しかない）と
右（他ツールのタブが混ざる）の対応が取れないままだった。人が最初に選ぶのは「どの道具の
話か」なので、そこを左メニューへ引き上げる。

### 5.1 判断: 第一ナビは領域、タブはその内部ナビ

**判断**: サイドバーを **領域（ワークロード）ナビ ＋ その領域の対象一覧** の二段にし、
右ペインのタブは選んだ領域の中の画面だけを出す。タブが 1 本しかない領域ではタブ列ごと畳む。

```
┌ サイドバー ──────────┐┌ メイン ───────────────────────────────┐
│ ホーム                ││ 領域の見出し（プロジェクト領域だけは対象名）│
│ プロジェクト     [6]  ││ ┌ その領域のタブ ────────────────────┐ │
│ 定常業務         [3]  ││ │ 概要 タスク 要対応 実行 成果  設定  │ │
│ ミッション       [2]  ││ └────────────────────────────────────┘ │
│ 参加             [4]  ││                                          │
│ 利用状況              ││   選んだ領域 × 選んだ対象の画面           │
│ ─────────────         ││                                          │
│ プロジェクト（一覧）  ││                                          │
│  ● 決済基盤リプレース ││                                          │
│ ─────────────         ││                                          │
│ 全体設定              ││                                          │
└───────────────────────┘└──────────────────────────────────────────┘
```

| 領域 | 左の対象一覧 | 右のタブ |
|---|---|---|
| ホーム | — | （1 画面） |
| プロジェクト | プロジェクト | 概要 / タスク / 要対応 / 実行 / 成果 / 設定 |
| 定常業務 | 作業フォルダ | 作業 / 実行の記録 / 設定 |
| ミッション | — | ミッション |
| 参加 | — | 参加できる仕事 / 参加の状況 |
| 利用状況 | — | 利用状況 |
| 全体設定 | — | （1 画面・中に分類タブ） |

どのタブがどの領域かは **HTML の `data-area` が正**で、`AREAS`（renderer.js）は列挙と
表示名だけを持つ。領域を足す手順は「`AREAS` に 1 行、タブに `data-area`」の 2 手。

**領域の絞り込みは `area-off`、feature の出し分けは `.hidden`** と別のしるしにする。
片方を使い回すと、領域を切り替えただけで feature 側の判断（募集が無いから参加タブを
隠す等）が消える。

**選択と領域は互いを横取りしない**。一覧はその領域の中にあるので、対象を選んでも領域は
動かない。領域をまたぐ遷移（ホームの対応待ち → プロジェクトの要対応、通知のディープ
リンク）は呼び出し側が明示し、`switchTab()` はタブの `data-area` から左メニューを合わせる。

### 5.2 判断: 起動導線は右ペイン、左メニューは選ぶだけ

**判断**: 左メニューは「どの道具か」「どの対象か」を選ぶだけで、**起動ボタンを置かない**。
起動は対象が確定した右ペインに置く。

**文脈**: 左は一覧で、押し間違いが起きやすく、どの対象に対する起動なのかも確定していない。
右ペインなら「いまこの作業を動かす」と対象付きで示せる。

**この端末で動かせるものと、動かせないもの**（設計 §2.1 の非目標との整合）:

| 領域 | この画面から起こせるか | 起動導線 | 実行結果のトレース |
|---|---|---|---|
| 定常業務 | **起こせる**（この dashboard 自身が実行側） | 作業タブの「今すぐ実行」 | 実行の記録タブ（履歴・ログ） |
| 利用状況 | **起こせる**（agent-audit CLI の LLM 非使用段） | 「今すぐ収集」 | 集計（利用量・実行品質） |
| 参加 | **起こせる**（人が押したときだけワーカー 1 つ） | 「参加する」 | 参加の状況タブ |
| ミッション | 起こさない（常駐体が実行） | 「依頼する」＝ `commands/` 投函 | ミッション詳細のやりとり |
| プロジェクト | 起こさない（常駐体が実行） | — （概要の「daemon の生存」で状況を見る） | 実行タブ（run の DAG） |

**実行エンジン（`agent-project serve`）を起こす経路は足していない。** 「単独起動」を
全領域へ揃えるなら常駐体の起動ボタンが要るが、それは §2.1 の非目標そのもので、
概念正典 §8 の作業ゲートに従い**設計を原則に合わせた**——起こせない領域では起動ボタンを
出さず、実行側が誰かと現在の状況を示すに留める。押せるのに何も起きないボタンを作らない。

### 5.3 判断: 設定は「効く範囲」で置き場所を分ける

**判断**: 全体設定に残すのは**端末のすべてのワークロードに効くもの**（エージェント /
共通指示 / 実行制御 / 同期と実行）と**このアプリ自身の設定**（アプリ / 外部連携）だけ。
特定の agent-* にだけ効く設定はその道具の領域へ移す。

| 設定 | 移動前 | 移動後 | 効く範囲 |
|---|---|---|---|
| 利用状況（agent-audit の収集設定と集計） | 全体設定の 1 節 | 利用状況領域 | agent-audit だけ |
| 定常業務（roots / loopProvider / 各コマンド） | 全体設定の 1 節 | 定常業務領域の設定タブ | cowork だけ |
| プロジェクト定義 | プロジェクト設定 | 変更なし | そのプロジェクトだけ |

**文脈**: 8 分類が 1 ページに並んでいると、どれが端末全体に効き、どれが 1 つの道具にしか
効かないのかが読めない。置き場所そのものを説明にする。

**移設のやり方**: 差し込みの仕組み（`registerGlobalSettingsPanel('usage', …)`）も HTML の
組み立て（`globalSettingsRoutineHtml()`）も**変えず、受け側だけを移した**。保存経路
（`saveGlobalSettingsSection`）は 1 本のままで、表示名だけ移設先の対応表から引く。

### 5.4 同時に消したもの

定常業務の実行履歴ダイアログ（`dlg-cowork-history`）を廃止した。動かす画面と結果を追う
画面が同じ領域の別タブに並んだので、同じ内容をダイアログでも出す理由が無くなった
（同じ話題の画面を 2 か所に置かない）。

### 5.5 文言と見た目の規律（UX パス）

領域ナビ導入後に、画面全体へ次の規律を通した。

- **1 画面に見出しは 1 つ**。領域の見出し（ヘッダー帯）とペイン内の見出しを重ねない。
  自分の見出しと操作ボタンを持つ画面（ミッション / 参加 / 全体設定）では領域ヘッダーを
  出さず（`AREAS` の `ownHeader`）、持たない画面（実行の記録 / 利用状況 / ホーム）では
  ペイン側の見出しを持たない。ホームの最初の 1 行は挨拶ではなく「あなたの対応待ち」。
- **タブは領域名を繰り返さない**。左メニューが「どの道具か」を示すので、タブは中身の
  名前だけにする（定常業務の設定 → 設定、プロジェクト設定 → 設定）。
- **同じ場所への入口は 1 つ**。全体設定へ行く歯車ボタンをサイドバー共通ヘッダーから
  外した（領域ナビ末尾の「全体設定」に一本化）。
- **UI 文言から内部語を消す**。「ワークロード」等は説明文に出さない。カードは
  キッカー（何を任せる面か）＋名前＋数字＋「開く」だけにし、説明の重複文を持たない。
- **色は意味にだけ使う**。地は無彩色 3 段（bg → bg2 → bg3）、accent=操作 / green=稼働 /
  yellow=要対応 / red=失敗。ボタンは既定が輪郭のみ、塗り（`.primary-inline`）は
  1 画面 1 つの主要操作だけ。

### 5.6 判断: バッジは在庫ではなく「手を打つべきもの」を数え、着地点をそこへ揃える

**判断**: 左メニューのバッジは**人が手を打つべきものだけ**を warn で数える。領域を開いた
ときは、その領域の一覧の中からバッジが数えた対象へ着地させる。

**文脈**: 「定常業務 [6]」と光っているのに、開くと右ペインが空、という状態が出ていた。
原因は 2 つあり、どちらも「数える対象」と「映す対象」がずれていたことに帰着する。

1. バッジは端末全体の登録数（在庫）を数えていた。右ペインは選択中フォルダ 1 つ分を映す。
   端末に 6 件あってもそのフォルダに 0 件なら、数字と中身は一致しない。
2. 選択（`selectedDir`）はアプリ全体で 1 つしか無い。領域を切り替えても前の領域で選んだ
   対象が残るので、定常業務を開いてもプロジェクトのフォルダが選ばれたままだった。
   タブの出し分けも選択中の対象で決まるため、逆向き（定常業務のフォルダを選んだまま
   プロジェクトを開く）では出せるタブが無くなり、ホームへ弾かれていた。

| 領域 | 数えるもの | 数えないもの |
|---|---|---|
| プロジェクト | 要対応（needs） | タスクの総数 |
| 定常業務 | 止まっている作業（`failed` / `error` / `blocked` かつ非実行中） | 登録した作業の総数・まだ動かしていない作業 |
| ミッション | 確認が必要な項目（`attentionCount` ＋ 一時停止中の担当） | 進行中のミッション数 |
| 参加 | 参加できる仕事（人が押せば動く） | — |

在庫の件数は**サイドバーの対象一覧とホームのカード**が持つ。同じ数字を 2 か所で違う
根拠から出さない。

**着地点を揃える**（`areaItems` / `alignAreaSelection`）: 領域の一覧と attention 件数を
1 つの式から取り、領域を開いたら「前に見ていた対象 → 手を打つべきものが多い対象 →
先頭」の順で選び直す。対象を合わせるのは**タブの出し分けより先**（順番が逆だと、前の
領域の対象で行き止まり判定をしてホームへ弾く）。

**同時に直したもの**: 定常業務専用フォルダ（`kind=routine` で agent-project のマーカーを
持たない）をプロジェクト領域の一覧から外した。選ぶとプロジェクトのタブが 1 つも出せず、
押しても何も起きない行き止まりになるため。作業の突き合わせキーを `repo || cwd` に揃えた
（作業タブと同じ式。手で登録した作業は `cwd` しか持たないことがある）。

固定: `test/routine-area-ui.test.js`。

### 5.7 判断: 定常業務は「窓を開けるか」で分岐し、対象フォルダは登録簿をまたいで 1 つの一覧にする

**判断**: 実行の分岐を OS 名（win32）から**別ウィンドウを開けるか**（`supportsRunWindow`）へ
変える。定常業務の対象フォルダは `cowork.roots` と実行エンジンのプロジェクトの**両方**を
並べ、実行時の cwd は登録したフォルダにする。

**文脈（症状と原因）**:

| 症状 | 原因 |
|---|---|
| 実行すると画面が固まる | ウィンドウ実行を `process.platform === 'win32'` で囲っていた。macOS / Linux は素通りして main プロセスの `spawnSync`（最大 60 秒）へ落ち、その間 IPC を 1 つも返せない。ウィンドウ経路の中身（スクリプトを書いて端末で開く）は最初から OS 非依存で、CLIチャットは同じ経路を全 OS で使っていた |
| 登録したフォルダしか対象に出ない | 走査（`discoverCoworkItems`）は `cowork.roots` ＋ 実行エンジンのプロジェクトの両方を回っているのに、画面は前者しか並べていなかった。プロジェクトのフォルダで回している定常業務は、一覧に無いフォルダの作業として現れる |
| 設定画面でプロジェクトのフォルダを解除できない | 登録簿が違う（`agent-project.host.yaml` 側）。**出さない**のではなく、出して押せない理由を書く——一覧から消すと、画面に出ている作業の出どころが読めない |
| 実行の cwd が設定ファイルのフォルダになる | 発見項目は設定ファイルのあるフォルダ（`repo`）しか持っていなかった。走査は登録フォルダの下へ潜れるので、両者は一致しない |

**役割を分ける**: 発見項目に `root`（登録したフォルダ）を足し、`repo`（設定ファイルのある
フォルダ）と使い分ける。**所属（画面でどのフォルダの下に出るか）と実行の cwd は `root`**、
プロンプト本文とログの読み取りは `repo`。同じものとして扱うと、サブフォルダに設定を置いた
作業がどのフォルダの一覧にも出てこない。

**選択の引き継ぎ**（§5.6 の続き）: 同じフォルダがプロジェクト領域と定常業務領域の両方に
並ぶようになったため、「その領域の一覧にあるならそのまま」では空のフォルダへ着地しうる。
優先順位を **領域ごとの記憶 → 持ち込んだ選択（その領域で中身を持つときだけ）→ 手を打つ
べきものが多い対象 → 中身のある対象 → 先頭** にした。

固定: `test/cowork.test.js`（窓を開けるかで分岐する・OS 名で分岐しない）、
`test/cowork-discover.test.js`（`root` と `repo` の使い分け）、`test/overview-ui.test.js`
（サブフォルダの作業は登録フォルダの一覧に出る）、`test/routine-area-ui.test.js`（対象は
両方の登録簿・選択の引き継ぎ）。

### 5.8 UX パス 2 巡目（画面名・常設・空の初期表示・設定の言い換え）

領域ナビが入ったあとの実利用で出た指摘をまとめて通した。判断は 4 つ。

**判断 1: 左メニューは出たり消えたりしない。** 参加は募集が 0 件でも領域とタブを出す
（`available: () => true`）。出たり消えたりするメニューは「さっきあった項目が無い」と探させ、
募集が無いこと自体も人が知りたい情報である。画面がそれを一言で言う。

**判断 2: 定常業務の対象にユーザーホームを常に含める。** kiro-loop の設定は
`~/.kiro/kiro-loop.yml` にも置かれ、そこはどの登録簿（`cowork.roots` / `host.yaml`）にも
載らない。ホームは登録簿と無関係に走査ルートと対象フォルダ一覧へ入れる（Windows では
WSL 側のホームも。定常業務のエンジンはそちらで動く）。**ホームだけは潜らない**——
ホームの下には無関係な木が広がっていて、登録フォルダと同じ深さで歩くと走査が数秒かかる。

**判断 3: 見る画面と決める画面をタブで分ける。** 利用状況を「利用量」と「設定」に割った。
併せて、面が見えているかの判定を**自分が入っているタブ**で行うよう直した（全体設定タブが
前面かを見ていた名残があり、利用状況を開いても初回の集計が走らず、人が「今すぐ収集」を
押すまで空だった）。一度も収集していない端末では、開いた時点で 1 回だけ自動収集する。

**判断 4: 設定画面は「人が決めること」だけを出す。**

| 変えたもの | 前 | 後 |
|---|---|---|
| 実行プロファイル | 「段の定義」と「予算残率 → 段」の 2 表。人が同じキーを両方へ手で書く | **1 段 = 1 行**（上から順に使う）。キーと順序は保存時にこちらが振る。細かい調整（ヒステリシス・最小保持・上限なしの段）は畳む |
| 「実行される内容を確認」 | 押すまで何も出ず、何を伝える枠か読めない | 削除（設定した行そのものが同じ画面にある）。取得経路（`sessionCommandsPreview`）も削除 |
| 「実行サービスへの反映状況」 | 共通指示とセッションコマンドに同じ表が 2 つ | 削除（同じ話題は実行制御の「設定の反映」列が持つ） |

そのほかの直し: アプリ名を「ポータル」に統一。プロジェクト共通チェックのコマンドを
独立ブロックにして枠内で横スクロール（素の `<code>` が見出しへ回り込んでいた）。
タスクグラフに高さの上限を与えて**グラフだけで縦に送れる**ようにした。定常業務の
「実行の記録」の選択 UI を作業タブと同じ部品に揃えた（検索・件数・状態つき）。
「まとめて依頼」は縦積みフィールドの型を借りるのをやめ、1 行の操作として組んだ。
参加のカードは依頼文の全文をやめ、見出し＋手がかり 1 行＋ボタンに絞ったうえで、
**何がここに出るのか**（未着手の工程が残っている実行・担当未定の役割・募集中の依頼）を
畳んだ説明として置いた。

固定: `test/ui-copy.test.js`（アプリ名）、`test/agent-audit.test.js`（利用量／設定の 2 タブ）、
`test/session-commands.test.js`・`test/overview-ui.test.js`（削除した 2 枠を戻さない）、
`test/cowork-roots.test.js`・`test/discover-engine.test.js`（ホームが常に走査ルートへ入る）。

### 5.9 判断: 稼働の根拠は心拍だけ／設定は 1 つの値に 1 つの欄

**判断 1: 「実行する PC」の生死は心拍で判定する。** この PC のノードは
`engine/status.json`（常駐体が毎周期書く心拍）で見る。

**文脈**: 稼働中の PC が赤丸（応答なし）で出る、という報告。調べると
`<project>/status/<node>.json` は**心拍ではなかった**——常駐体が実パスを進めたときに書く
状態のスナップショットで、定期更新は `--status-interval`（既定 0＝無効）を明示したときだけ。
6 日前に最後のタスクが終わった端末では、常駐体が毎秒心拍を書いていてもこのファイルは
6 日前のまま。画面はその経過時間を鮮度と読み、「応答なし」と断定していた。

他の PC は状態リポジトリ越しにこのファイルしか見えないので鮮度で見るしかないが、
**意味は「最後に作業が進んだ時刻」**なので「応答なし」とは書かない（待機中の PC を
故障のように見せない）。常駐体側で心拍のたびに書く手もあるが、それは git のコミットを
増やす方向で、待機中の負荷をゼロに保つ設計判断と衝突する——画面側で読み替える。

**判断 2: 定期実行の設定は「コマンド」1 つ。** 「種類（`loopProvider`）」と
「コマンド（`loopCommand`）」の 2 欄は、種類が「コマンド未指定時の既定値」以上の意味を
持たず、人に同じ文字列を 2 度書かせていた。種類の欄を廃止し、**未指定の既定を
`agent-loop`** にした（旧設定に種類だけが書かれていれば読み取りで拾う）。

**判断 3: 状態の丸は、その状態を持つものの隣にだけ置く。** 定常業務の作業フォルダ一覧から
稼働ドットを外した（プロジェクト一覧は据え置き）。丸が指していたのは agent-project の
常駐体の稼働で、定常業務の実行側はこのアプリ自身——別の道具の状態を隣に置くと読み違える。

**判断 4: 棒グラフは長い順。** 利用状況の「機能別」「エージェント別」を割合の降順に並べた
（実行数順ではない）。棒の長さで比べる表が長さ順に並んでいないと、比較そのものができない。

固定: `test/liveness-host.test.js`（心拍で自ノードを判定）、`test/overview-ui.test.js`
（応答なしと断定しない文言）、`test/feature-split.test.js`（既定は agent-loop・種類は無い）、
`test/agent-audit.test.js`（割合降順）。
