# 列挙駆動の分解 — バックログ粒度と内側タスクグラフのギャップ解消（設計提案）

## 背景（観測された問題）

「API のドキュメント化」のようなバックログに対し、API 単位のグラフノードが
出来ることを期待したが、実際には「まとめて調査するノード」しか生成されない。

対処として粒度ノブを回すと、どちらへ倒しても破綻する:

- バックログを**細かく**する → 人が API を列挙して 1 件ずつ起票・承認する羽目になり、
  ユーザー操作が煩雑になる（プランナーに任せた意味がない）
- バックログを**粗く**する → 内側タスクグラフが巨大化し、**単段の集約ノード**に
  全成果が集中して失敗する

## 原因分析（コードで確認した実際の挙動）

「まとめて調査するノード」はプランナーの気まぐれではなく、**現行カタログ・行列の
仕様どおりの出力**である。原因は 4 つに分解できる。

### 1. map-reduce が構造的に選ばれない

flow-planner（`.github/skills/flow-planner/scripts/plan.py`）の Phase 1 は
**要求文だけ**で属性を判定する。「API のドキュメント化」では:

- API 一覧はリポジトリに静的に存在する → `data_flow=static` と判定されやすい。
  Decision Matrix（patterns-catalog.yaml）で map-reduce が +3 されるのは
  `dynamic` のみで、`static` は fan-out-and-synthesize +2 が勝つ
- use_case_mapping は先頭一致で、「調査・調べ」が **deep-research 複合**
  （並列調査 → 検証 → 統合）に先にマッチする。map-reduce 行のキーワード
  （それぞれ/各/ごとに/一覧…）は要求文に現れないと当たらない

map-reduce の `when_to_use` には「API一覧」と明記されているのに、
選定経路がそこへ到達しない。

### 2. 「列挙する者」がどの層にもいない

per-API ノードを作るには API の列挙が必要だが:

- **外側**（agent-project plan）: プランナーが見られるのは有界の repo_map
  （`repo_map_context` 既定 1500 字 × 3 ファイル）のみ。API を列挙できないので
  `cohort_items` を書けず、粗い 1 タスクに畳むしかない
- **内側**（flow-planner）: Phase 1〜3 とも要求文のみで推論し、ワークスペースを
  一切見ない。対象が 5 件なのか 50 件なのか知らずに構造を決めている

split ノード（実行時列挙 → map×N 動的展開）はまさにこのための機構だが、
map-reduce が選ばれなければ発動しない。

### 3. 集約が単段で規模に耐えない

`_expand_splits`（agent_flow/continuation.py）は map N 件 → **reduce 1 件**の
固定構造。review gate も全 map に依存する 1 ノード。N が大きいと依存成果が
1 コンテキストへ集中し、集約ノードの作業量が増えて失敗する
（build_request のコメントにも「事後集約ノードは規模で破綻」と既知の問題として
記載があるが、run ブリーフによる緩和は一貫性の話で、集約そのものは単段のまま）。

### 4. 外側 cohort は計画時列挙が前提

pilot-then-batch（cohort）は「pilot 1 件を人がレビューして指示を固め、残りを
自動生成」という理想的な人ゲート付き量産機構だが、`cohort_items` を計画時に
列挙できることが前提。列挙にリポジトリ調査が要るバックログでは使えない。

## 設計方針

> **粒度は計画時に確定しない。「列挙」を第一級の実行時ステップにし、
> ノード数は列挙結果から導出する。**

バックログ粒度（ユーザー操作面）は今のまま粗く保つ。粒度ノブ
（coarse/fine/finest）はこの問題の解ではない — ノブは「1 ノードのスコープ上限」を
制御するもので、「対象数に応じたノード数」は列挙からしか導出できない。

## 提案（4 案・組み合わせ可能）

### 案1: enumerability 軸の導入（内側・本命）

Phase 1 の分析属性に **enumerable（列挙可能な同種対象への同一手順か）** を追加する:

```json
{
  "enumerable": {
    "is_enumerable": true,
    "target_kind": "API エンドポイント",
    "how_to_enumerate": "src/routes/ 配下の各ルート定義を走査",
    "estimated_count": "unknown"
  }
}
```

Phase 2 に**決定的ルール**を足す: `is_enumerable かつ（count 不明 or > 3）`
なら Decision Matrix のスコアに関わらず patterns に map-reduce を含める
（キーワード一致に頼らない。「ドキュメント化」「テスト追加」「バリデーション適用」
など動詞側の語彙は際限がないため、軸で判定する）。

Phase 3 では split ノードの goal に `how_to_enumerate` を埋め込む:

```
[scope] src/routes/
実際にワークスペースを走査し、ドキュメント化すべき API エンドポイントの
一覧を JSON 配列で出力する（推測で書かない）
```

split は worker がワークスペース付きで実行するため、**列挙は実行時に実リポジトリで
行われる**。以降は既存の `_expand_splits` がそのまま per-API の map ノードを生成する。

- 変更箇所: flow-planner の ANALYZE/SELECT/BUILD プロンプトと `plan()`、
  patterns-catalog.yaml（decision_matrix はそのまま。強制ルールはコード側）
- 粒度ゲートとの整合: split-only グラフは work 系ノード数検査の対象外
  （`gate_tasks` は work が無ければ合格）なので衝突しない

### 案2: 計画前の軽量 probe（案1 の補強・最小実装）

Phase 1 の前に**決定的な軽量列挙 probe**（LLM なし: glob / ctags 相当の走査、
または有界の 1 コール）で「対象候補のおおよその件数」だけ取得し、分析入力に渡す。

- 目的は列挙の完遂ではなく**規模の把握**（5 件なら静的 fan-out で十分、
  50 件なら map-reduce + 階層 reduce、と構造判断が数に基づく）
- agent-project 経由の run はワークスペースが手元にあるため追加 clone 不要
- 失敗・タイムアウトは「不明」のまま従来動作（計画を止めない）

### 案3: 階層 reduce ＋ 成果物ファイル契約（集約過負荷の解消）

集約ノードの失敗は選定改善だけでは消えない（正しく per-API に展開されるほど
N が増える）ため、集約側も直す。

**(a) 階層 reduce**: `_expand_splits` で `len(map_ids) > R`（既定 6〜8）なら
チャンクごとの中間 reduce を挟み、木構造にする:

```
map×20 → reduce-c1(m1..m7) ─┐
         reduce-c2(m8..m14) ─┼→ reduce（最終・入力は中間 reduce のみ）
         reduce-c3(m15..m20)─┘
```

決定的な展開ロジックの変更のみで LLM 側の変更は不要。review gate も
チャンク単位に分ける。

**(b) 成果物ファイル契約**: map の役割プロンプトを「成果物は
ワークスペース／アーティファクトのファイルへ書き、output には有界サマリと
ファイルパスのみを返す」に強化する。reduce の仕事を「全成果の生成」から
「索引・目次の生成と整合チェック」へ縮める。既存のアーティファクト参照
プロトコル（`artifact_instruction`）にそのまま接続できる。

ドキュメント化の例では: 各 map が `docs/api/<endpoint>.md` を書き、
reduce は目次と用語・様式の整合チェックだけを行う。

### 案4: 外側 cohort の実行時列挙（人ゲートが欲しい系統向け）

backlog-planner の契約に「対象を列挙できないときは `cohort_items` の代わりに
**`cohort_enumerate`（列挙手順の記述）** を出してよい」を追加する。
agent-project は enqueue 時（または初回 act 前）に、repo_map 生成と同型の
有界エージェント呼び出しで列挙を実行し、結果の JSON 配列を `cohort_items` へ
充填する。以降は**既存の pilot-then-batch がそのまま動く**。

- ユーザー操作はバックログ 1 件＋pilot 承認 1 回のまま
- board 上で per-API の進捗が見える。各対象が小さな独立タスク／run になるため、
  **集約ノード自体が不要になる**（最後に「索引生成」タスクを `after` で置く）
- 1 件の失敗が他を巻き込まない（リトライも対象単位）

### 使い分け（案1+3 と案4 の関係）

| 状況 | 推奨経路 |
|------|----------|
| 無人で 1 run に収めたい（調査・変換など） | 案1+3（内側 map-reduce + 階層 reduce）。大規模なら `exemplar_first` 併用 |
| 人が型を確定してから量産したい／進捗を backlog 面で見たい | 案4（外側 cohort 実行時列挙） |
| 対象が少数（≤3）と probe で判明 | 従来どおり静的 fan-out（変更なし） |

## 非目標

- 粒度ノブ（coarse/fine/finest）の意味・既定値の変更
  （2026-07-25 flow-planner 粒度設計を維持。本提案は直交する）
- バックログ表現（INVEST / verify 契約）の変更
- 全 run への probe 強制（列挙可能性が疑われるときだけ）

## 実装順序の提案

1. **案3(a) 階層 reduce** — 最小・決定的・単独で効く。既存の失敗を直接止める
2. **案1 enumerability 軸** — flow-planner のプロンプト＋強制ルール。
   「per-API ノードが出ない」の本丸
3. **案3(b) ファイル契約** — map/reduce 役割プロンプトの強化
4. **案2 probe** — 案1 の判定材料を実測に置き換える
5. **案4 cohort_enumerate** — 外側の人ゲート付き量産が必要になった系統から

1→2 だけでも「API 単位のノードが出て、集約が壊れない」は達成できる。

## リスクとトレードオフ

| 項目 | 内容 |
|------|------|
| split の列挙品質 | 列挙が漏れると map も漏れる。verify ノード（reduce 前 gate）の検査項目に「列挙の網羅性の抜き取り確認」を明記して緩和 |
| enumerable の誤判定 | 過剰に map-reduce 化すると小タスクにオーバーヘッド。count ≤ 3 は静的 fan-out へ倒す決定的ルールで抑制 |
| 階層 reduce の情報損失 | 中間集約で細部が落ちうる。ファイル契約(3b)により reduce は索引化のみ＝本文はファイルに残るため影響は限定的 |
| probe のコスト | 決定的走査を優先し、LLM probe は有界（timeout・失敗は不明扱い） |

## 判断を仰ぎたい点

1. 実装順序（上記 1→2 を先行し、4 は需要が出た系統から、で良いか）
2. 階層 reduce のチャンク幅 R の既定値（6〜8 を想定）
3. `cohort_enumerate` の列挙実行タイミング（enqueue 時 or 初回 act 前）
