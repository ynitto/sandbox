## 0b. 正典との突き合わせ（本改訂での優先度変更）

[コンセプト正典](../designs/agent-tools-concept.md)（柱 1 = チーム利用 / 柱 2 = 人介在の
最適化、原則 C1〜C7）を判定基準に全項目を見直した。**順序の骨格は変わらない**
（§1 → 観測 → R2b → 静止点 → 契機待ち）——初版の優先度は概ね正典と整合していた。
変更は次の 3 種類。

### 上げたもの — 原則に現に違反している経路は「契機待ち」にしない

「契機待ち」は先回りしない規律（C1・C7 と両立）だが、それが適用できるのは
**現状が原則の内側にある**項目だけ。既に原則の外にある状態を放置する理由には使えない。

| 項目 | 旧 → 新 | 根拠 |
|---|---|---|
| flow worker の `who` 名前空間化（§2b.3-1） | 観測改善 → **C7 不変条件の欠陥修正**（位置は実装の先頭のまま） | 共有バスで 2 台が同一パス（`claims/<node>/worker-1.json` 等）へ書ける状態は「同じ状態に書き手を 2 つ置かない」（C7）と agent-flow 設計書 付録 A の不変条件の破れ。観測のついでではなく不変条件の回復として入れる |
| G-2 の残件: 決定済み判断の needs 復活（§4 → §2c-2） | 契機待ち → **単独是正** | 「同じ判断を人に二度させない」（柱 2 / C3）の直接違反経路であり、人の注意力を最も高価とする前提（正典 §2-3）の下で復活の実観測を待つ理由が無い。なお初版以後の `f9d7081` で孤児票（タスク削除後の残留・復活）は解消済み——残るのは DR（`decisions/<id>`）参照の欠落だけ |
| doctor への `host_config_findings()` 配線（§4 → §2c-3） | 契機待ちの一項目 → **単独是正** | 「doctor は緑なのに起動時は警告」は同じ判定の結果が場所で食い違う状態（C7: 判断根拠は 1 か所）。かつ §1.2 判断 1（W→E 昇格）の材料（警告の件数・内訳）を doctor で数えられるようにする（C4: 材料を揃えて 1 回で決めさせる） |
| `flow.js` × `executors/gitlab.py` の突き合わせテスト（§5-13 → §2c-4） | 記録のみ → **単独是正** | C7 の明文「写しは正典と突き合わせるテストで縛る」そのもの。CONTRACT_VERSION / DIFF_CRITERION で 2 度踏んだ「2 実装が黙ってずれる」型の 3 度目を未然に塞ぐ |
| 実装計画 §7 の自己矛盾の訂正（§6-1） | 次に触るとき → **§1 の後始末と同時** | 正典の頭注「本書と各設計書が矛盾したら、直すまで作業を止める」。R2b は実装計画 §7 を進める作業なので、その文書自身の矛盾は着手前に直す（§6-2 の node_id 方針矛盾を §2・§3 の前提に置いたのと同じ扱い） |

### 正典で根拠が固まったもの — 順位は変えず、以後の再検討を閉じる

- **§1.1（記録記入）が最初**であること。canary の結果が実施者のメモにだけある状態は
  「成果と判断はチームのもの——個人の頭やローカルにだけ残さない」（C1）への違反状態。
  実装より先、は正典からの帰結。
- **R2b が本丸**であること。板を唯一の PC 間仕事獲得経路にする柱 1 の中核（agent-board）の
  完成であり、同時に運ぶ P4-b（下記）で柱 2 にも効く。両柱に同時に効く唯一の項目で、
  本丸の地位は正典が保証する。
- **P4-b（検証委譲の後半）の位置づけ**。`unverifiable` の人検収直行は、機械で試せる解決
  （板への公示）を試す前に人へ送る C3 違反であり、人の検収に品質判定を負わせる C5 違反の
  経路でもある。§2 に置かれているのは請負側（板の実行）の開通待ちという実装都合だけなので、
  **R2b の完了条件に含め、切り離して先送りしない**。
- **§2b.4 の既定 (c)（ステップ分散を入れない）**。板を唯一の分配経路とする C2・C7 と
  agent-flow の非目標に整合する唯一の既定。(b) 信頼フリートモードは `eligible()` の関門を
  迂回する第 2 の分配機構なので、採る場合は正典 §7-3(b) の手続き——正典の改訂を同じ PR で
  提案し人の承認を得る——を踏む。実装の中に例外を埋め込む形では入れない。
  (a) 板経由サブ委譲だけが正典改訂なしに採れる形。

### 据え置きを確認したもの

- **§4 の契機待ちの残り全件**。いずれも柱への直接寄与が無い衛生（CI 強化・R10 拡張・
  `diff2html` 撤去等）か、契機の設定が「止まらない自動化・先回りをしない」（C7・C1）と
  両立する。正典 §3 の「どちらの柱にも効かない機能は足さない」は、契機が来るまで
  着手しない判断も支持する。
- **P4-d（speculation）**。実装する場合は「誰の財布で投機するか」が C1 の審査対象になり、
  §3-3（枠の数え方）とセット。据え置きのまま、この条件だけ注記。
- **スキーマ検証の CI 投入**。C7 支援だが「まず 1 回流して違反量を見る」の段取りは維持。

## 2b. flow の work ノード PC 間分担と実行ノードの観測（canary の観測から。優先）

**canary で「flow（既定 CLI: kiro）の各 worker 処理を複数ノードで分担できているか」が
観測できなかった件の調査結果。結論: 分担は起きておらず（現行仕様）、観測手段も無い
（実装が要る）。**

### 2b.1 現状の事実（コードで確認）

- **分担の粒度は backlog タスク単位が仕様**。run（プランナーが分解した work ノード
  t1, t2, … を含む）は、`claim_request` で 1 台に確定し（`bus.py` — docstring が
  「どのデーモンがこの要求を orchestrate するかを 1 台に決める」）、落札した PC が
  orchestrator 1 本 + `workers` 個（既定 2）の worker を**自 PC 内の subprocess として**
  起こして丸ごと完走する（`run.py`）。[`multi-pc-operations.md` §4.2](../guides/multi-pc-operations.md)
  が「グラフ内の個々のステップが PC 間に散らないのは仕様」と明記している。
- **work ノード単位の claim/lease の下地は実装済み・分散テスト済み**（`bus.try_claim` は
  ノード単位。`test_claim_across_separate_clones_single_winner` が別クローンからの同一
  ノード claim で勝者 1 人を検証済み）。**しかし下地を駆動する主体が居ない**——旧 daemon の
  オンデマンド worker 起動（`_spawn_worker` + `run_claimable_count`）は常駐一本化で削除
  された（agent-flow 設計書 §注記に明記。`bus.active_runs` / `run_claimable_count` は
  呼び手ゼロで残存）。共有 git バス（`git_bus`）を設定しても、他 PC の participate は
  `run_exists()` ガードで既存 run を弾くため worker を 1 本も起こさない。
- **実行ノードの記録が PC 非依存**: worker の `who` は `run.py` が `worker-{i}` に固定
  するため、バス上の記録（`results/<node>.json` の `who`・`claims/<node>/<who>.json`・
  `events/<who>.jsonl`）も、`agent-flow status` の `@who` 表示も、dashboard の run 詳細も、
  全 PC で `@worker-1` / `@worker-2` になる。成果物リポジトリのコミット
  （`[agent-flow] t17-… (req-…)`）の author も `agent-flow <agent-flow@local>` 固定。
  **「どの PC がどの work ノードを実行したか」を知る手段が CLI・GUI・バスのどこにも無い**。
- **潜在バグ**: 仮に共有バスで 2 台が同じ run に参加すると、両者が `claims/<node>/worker-1.json`
  と `events/worker-1.jsonl` という**同一パス**へ書き、「ファイル名が衝突しないので
  add/add コンフリクトにならない」という設計の不変条件（agent-flow 設計書 付録 A）を破る。
  分担を実装するなら `who` の PC 名前空間化が前提。
- **kiro 固有の注意**: kiro はステートレス（1 呼び出し = 1 プロセス）なので分担の構造的
  障害にはならないが、**月間上限（quota）は 1 ノードでも踏むと run 全体が即 failed 終端**
  （`_env_failure_reason`。既定 `heal_quota: false` で auto-heal も効かない）。同一 kiro
  アカウントを複数 PC で使う限り、PC を増やしても実行総量は増えない。

### 2b.2 いま観測できるもの（実装を待たずに）

- **タスク単位の分担**は観測できる: `coordination.py` が実行 PC を backlog タスクの
  `- node:` フィールドへ記録する。dashboard の backlog 画面 / `agent-project status` で
  `- node:` が PC 間に散っていれば「タスク単位の分担」は効いている。**canary の分担確認は
  現状ここが唯一の観測点**。
- **暫定回避**（ステップ分担を手動で起こす）: `git_bus` を設定した共有バス構成で、
  dashboard「参加」タブの手動 worker 起動を他 PC から押すと、`dashboard-<hostname>-<rand>`
  名義の worker が同 run の pending ノードを拾い、`agent-flow status` の `@who` に PC 名が
  出る。ただし canary の標準構成（`single-resident-setup.md` / ランブック）に `git_bus` の
  設定手順は無く、手動起動は都度操作。

### 2b.4 設計思想との突き合わせ（ステップ分散を「復活」と書かない理由）

旧オンデマンド worker 起動をそのまま戻す案は、この改修系列の設計思想と 4 点で衝突する。
機構の是非ではなく「どの契約の下で入れるか」の問題なので、判断ごと記録する。

1. **「実行はローカル、状態の鏡だけ共有」の公理と正面衝突する**（agent-flow 設計書 §状態の鏡 /
   `multi-pc-operations.md` §4.2）。ステップ分散は実行層のバスそのものを PC 間の生きた
   調停チャネルにする（claim ごとに push/pull）。ガイド §4.2 の表は共有バス方式を
   「構成の変更」として案内しているが、公理側の記述と同居しており、どちらが正かの決着が
   そもそも付いていない——駆動部の削除で実装が公理側に倒れた、が現状の事実。
2. **板を唯一の PC 間仕事獲得経路とする R2a/R2b の契約を迂回する第 2 の分配機構になる**。
   バスの claim プロトコルには `eligible()` の関門（contract_version の fail-close・
   workloads・`max_concurrent` の自己抑制・agent_cli 照合）が**一つも無い**。共有バスで
   他 PC のステップを拾う経路を開くと、フリート更新の規律（C13「更新漏れノードは入札
   しない」）が効かない裏口ができ、P2-3 の枠の数え方（1 委譲 = 1 枠、板の status から
   数える）も破れる。「同じ規則の 2 実装」を潰し続けてきた系列（CONTRACT_VERSION /
   DIFF_CRITERION / repolocal）への逆行。なお dashboard の手動 worker（§2b.2）も
   NodeWorkerPool の座席外で走る——単発実行のセマフォ外問題（常駐一本化設計 C5）と同型。
3. **非目標との衝突**: agent-flow 設計書は「公平なタスク分配」を非目標と明記している
   （負荷分散は起動位相ずらしとジッタの heuristic のみ）。ステップ分散は負荷分散機構
   そのものなので、入れるなら非目標の再決定が先。
4. **実益が現状のセマンティクスでは薄い**: 既定 CLI（kiro）の月間上限は 1 ノードが
   踏んだ時点で run 全体が即 failed 終端（`heal_quota: false` 既定）。同一アカウント
   ならば PC を増やしても実行総量は増えず、別アカウント構成でも 1 アカウントの上限が
   他 PC で完走できたはずの run を道連れにする。分散の価値は失敗セマンティクスの
   再設計とセットでしか出ない。

**採りうる形**（R2b 設計回での選択肢）:
- **(a) 板経由のサブ委譲** — ステップ（またはサブグラフ）を板の公示として出し、
  `eligible()` の関門を通して請けさせる。検証委譲（P4-b）と同じ型で、契約が 1 本に保てる。
- **(b) 共有バスに版ゲートを足した「信頼フリート」モード** — claim プロトコルへ
  contract_version と枠の照合を追加したうえで、明示 opt-in の構成に限って開く。
  ただし「板を唯一の PC 間分配経路にする」原則（C2・C7）の例外になるため、採るなら
  正典 §7-3(b) の手続き（正典改訂を同じ PR で提案し人の承認を得る）とセット（§0b）。
- **(c) 入れない** — run を小さく切る既存のレバー（backlog タスクの分割・
  [flow-planner 粒度設計](2026-07-25-flow-planner-granularity-design.md)）で run 数を
  増やし、**run 単位の先着分散で足りる**と判断する。分担の既定粒度（タスク単位）の
  設計をそのまま強化する、最も思想に沿う形。

**契機**: run 内並列が 1 台の `workers` × `max_concurrent` の枠で実際に足りなくなった
実測（長大 run が 1 台を占有し、他 PC が遊ぶ状態の観測）が出るまでは (c) を既定とする。
観測（§2b.3-1/2）が入れば、この実測自体が可能になる。
