# agent-app シンプルナビゲーション UX 再設計

> 作成: 2026-09-05  
> 対象: `tools/agent-app`  
> 前提設計: `docs/plans/2026-09-05-agent-app-statemachine-integration-design.md`

## 背景

agent-app は会話、ファイル、差分、端末、worktree、自動化を一画面で扱える一方、現在は主要機能の切替、
リポジトリと会話の選択、実行設定、補助操作が同じ強さで並んでいる。特にヘッダーにはエージェント、モデル、
Ask、作業フォルダ、端末、変更、フォルダ、削除が並び、利用者が「依頼を書く」「結果を見る」という主作業へ
集中しにくい。

また、`作業 / 自動化` を横並びタブとして実装したため、今後レビュー、スキル、実行履歴などの主要領域が
増えると、幅と階層の両方が破綻する。主要領域はタブではなく、拡張可能なアプリケーションメニューとして
扱い直す。

## 調査結果

- GitHub Copilot app は Sessions、Chats、Automations などをサイドバーの機能領域として持ち、セッションを
  リポジトリ単位で整理する。モデル、モード、実行場所は依頼入力欄の近くで選ぶ。
  - https://docs.github.com/en/copilot/how-tos/github-copilot-app/agent-sessions
- Codex app はプロジェクト配下にスレッドを置き、会話、進捗、差分レビューを選択中タスクの詳細へ集約する。
  - https://openai.com/index/introducing-the-codex-app/
- Cursor はエージェント一覧を専用サイドバーに置き、選択後の詳細で状態確認、追加指示、引き継ぎを行う。
  - https://docs.cursor.com/background-agent

共通点は、主要機能を常設ナビゲーションに置き、対象一覧をサイドバー、選択した対象の作業を中央へ分ける
ことである。agent-app では機能数がまだ少ないため、アイコンだけのレールを追加せず、文字ラベル付きの単一
サイドバーへまとめる。

## 目的

- 起動直後に「リポジトリを選ぶ」「新しい会話を始める」のどちらをすべきか迷わない。
- 通常時は会話、依頼入力、進捗、変更確認だけへ注意を向けられる。
- 高度な実行設定を利用できるが、初見の利用者へ常時露出しない。
- 主要機能が増えても、横幅やタブ数を増やさずナビゲーションへ追加できる。
- 既存機能と保存データを維持し、見せ方と操作階層だけを改善する。

## 採用する情報構造

### アプリケーションシェル

左側を幅 272px 前後の単一サイドバーとし、上から次の順に配置する。

1. アプリ名
2. 選択中領域に応じた主操作
3. 主要メニュー
4. リポジトリ
5. 選択中領域の対象一覧
6. 設定

主要メニューは `会話` と `自動化` を縦に並べる。これはタブではなくページナビゲーションであり、
`aria-current="page"`、アイコン、文字ラベル、選択背景で現在地を示す。将来の機能は同じメニューへ行として
追加する。アイコンだけの折りたたみレールは初版に含めない。

主操作は領域に応じて `新しい会話` と `新しい自動化` を切り替える。リポジトリは両領域の共通文脈として
同じ位置に残す。対象一覧だけを、会話では `最近の会話`、自動化では `自動化一覧` に切り替える。

### 会話画面

中央上部は二段以上に折り返さず、次だけを表示する。

- 会話名
- 実行状態
- `会話 / ファイル` の表示切替
- `変更を確認`
- 補助操作メニュー

`会話 / ファイル` は同じセッションの表示を切り替えるため、ここではタブ表現を維持する。端末、フォルダを
開く、会話を削除は補助操作メニューへ移す。端末が開いている、または再起動が必要な場合だけ、状態に近い
操作を直接表示する。

依頼入力欄は会話画面の主操作とし、下部に固定する。入力欄の下には `添付`、現在の実行条件を示す短い要約、
`送信` を置く。実行条件を押すと、エージェント、モデル、Ask、作業フォルダを編集できるポップオーバーを
開く。選択内容は `Codex · 通常 · 分離フォルダ` のように要約し、ラベルの無いアイコンだけでは表さない。

### 設定

サイドバー最下部の `設定` からアプリ設定ダイアログを開く。次を通常画面から移す。

- tmux で対話起動
- 会話ごとに作業フォルダを分ける
- WSL ディストリビューション
- 実行環境の状態

設定ダイアログは短いラベルを主にし、技術的な説明は補足文または詳細表示へ置く。worktree の作成・削除は
実行設定内の `作業フォルダを管理` から既存ダイアログへ進める。

### 空状態

リポジトリ未登録時は、中央に `リポジトリを追加` の主操作だけを置く。リポジトリ選択済みで会話が無い場合は、
大きな依頼入力欄と短い例を表示し、別の「会話を作る」手順を要求しない。説明は一画面一文を上限の目安とする。

## コンポーネントと状態

- 既存の `area-work` / `area-automation` ID と `work | automation` 状態は維持し、DOM と見た目だけをメニューへ
  変更する。表示名 `作業` は目的が曖昧なため `会話` に変更する。
- 実行設定は既存の `cli`、`model`、`readonly`、`worktree` を同じ DOM ID のまま入力欄付近へ移す。
- 設定ダイアログは既存の `use-tmux`、`use-worktree`、`wsl-distro` を再利用する。
- 補助操作メニューはネイティブな `details` または同等のキーボード操作可能な開閉要素とし、外側クリック、
  Escape、項目選択で閉じる。
- 既存の IPC、保存形式、agent-tools のエージェント定義、agent-loop の自動化実行契約は変更しない。

## レスポンシブ

- 1200px 以上: サイドバー 272px、中央、必要時だけ右側の変更パネル。
- 760〜1199px: サイドバー 240px。変更は中央へ重なるドロワーとし、ヘッダーを折り返さない。
- 759px 以下: サイドバーをオーバーレイで開閉し、中央を一列にする。主操作のタッチ領域は 44px 以上とする。
- すべての幅でページ全体の横スクロールを禁止し、コード、差分、ログなど必要な内容領域だけを個別に
  スクロール可能にする。

## 視覚方針

- OS 標準フォントと固定ニュートラル配色を維持し、テーマ・色カスタマイズは追加しない。
- 青は主操作と現在地に限定する。通常の補助操作はニュートラル、削除だけを危険色とする。
- 罫線より余白と背景差で階層を作る。カードの多用、グラデーション、装飾的な影は避ける。
- Lucide 相当の一貫した線画 SVG を使い、絵文字は使わない。アイコンには原則文字ラベルを併記する。
- フォーカスリング、4.5:1 以上の文字コントラスト、`prefers-reduced-motion` を保証する。

## エラーと回復

| 状態 | 表示 | 主な回復操作 |
|---|---|---|
| リポジトリなし | リポジトリが必要であることを一文で表示 | `リポジトリを追加` |
| 会話なし | 依頼入力をそのまま表示 | 依頼を送信 |
| CLI なし | 実行設定の近くに短いエラー | `設定を開く` |
| 実行中 | 会話名付近と送信欄で状態表示 | `停止` |
| 確認待ち | 会話一覧と本文の両方に文言で表示 | 回答または許可 |
| 端末停止 | 状態の近くに表示 | `再起動` |
| 変更なし | 変更ドロワー内に空状態 | ドロワーを閉じる |

エラー本文には次に行う操作を先に示し、コマンド、終了コード、生ログは詳細表示へ置く。

## テスト方針

- DOM: 主要メニューの `aria-current`、主操作の文脈切替、実行設定・補助操作・設定ダイアログの開閉。
- 回帰: 会話、ファイル、差分、端末、worktree、添付、自動化の既存テストを維持。
- キーボード: メニュー、表示タブ、ポップオーバー、ダイアログ、送信まで Tab と Escape で操作できる。
- レスポンシブ: 375px、768px、1024px、1440px で文字切れ、固定要素の重なり、ページ全体の横スクロールが
  無いことを確認する。
- 実機: Electron を起動し、未選択、会話、自動化、ファイル、変更ドロワー、設定を目視確認する。

## 検討した案

| アプローチ | 実装コスト | リスク | 保守性 | 拡張性 | 学習コスト | 推奨度 |
|---|---|---|---|---|---|---|
| A. 単一サイドバーの文字付きメニュー＋文脈一覧 | 低 | 低 | 高 | 高 | 低 | ★★★ |
| B. アイコンレール＋第2サイドバー | 中 | 中 | 中 | 高 | 中 | ★★☆ |
| C. 機能カードを並べたホーム画面 | 高 | 中 | 中 | 中 | 中 | ★☆☆ |

A は現在の2機能に対して最も単純で、将来の追加にも縦方向で対応できる。B は機能数が多い場合に有効だが、
現時点ではアイコンの意味を覚える負担と横幅を増やす。C は入口を一枚増やし、頻繁な切替に余分な操作が生じる。

## 既存スキルとの関係

- `ui-designer`: 情報階層、アクセシビリティ、タッチ領域、レスポンシブ、段階表示を具体化する。
- `webapp-testing`: Electron 実機と複数幅での操作・表示回帰を検証する。
- `code-simplifier`: 実装後、表示制御やCSSが過度に複雑化していないか確認する。
- `ltm-use`: 今回の主要ナビゲーション決定を次回の機能追加時に再利用する。

既存スキルがagent-app固有の画面再設計を代替することはない。

## 非目標

- IPC、セッション保存、agent-tools、agent-loop の契約変更
- 新しい主要機能の追加
- テーマ、配色、レイアウトのユーザーカスタマイズ
- アイコンだけの折りたたみナビゲーション
- 分析ダッシュボードや利用量グラフ
