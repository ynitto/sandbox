# agent-tools をローカル LLM 主体で動かす — 常用ローカル・例外クラウドの運転計画

> 作成 2026-08-14
> 前提: クラウド CLI のトークン枠が逼迫し、「上位モデルを温存する」ではなく
> 「クラウドをほぼ使えない」が新しい平常になった。ハードウェアは増強しない（制約・確定）。
> 根拠はすべて実測 — [`tools/agent-tools/eval/results/archive/`](../../tools/agent-tools/eval/results/archive/)
> の 3 レポートと台帳、および [`eval/README.md`](../../tools/agent-tools/eval/README.md) の測定記録。

## 0. 結論の先出し

- **ローカル主体運転は未知への挑戦ではない。** archive の実測は、agent-flow の役割の
  大半（work / 抽出 / 分析 / 構造化要約 / split / reduce / evaluator / レビュー）で既に
  合格ラインを出している。足りないのは能力ではなく、**配線 1 箇所**（P1: statemachine の
  検査コマンド）と**ルーティングの宣言**（P2）である。
- **クラウドは「段」ではなく「例外処理」にする。** 持久運転設計
  （[2026-08-12](2026-08-12-agent-flow-basic-tier-emergency-operation-design.md)）は
  「残予算 20% で切り替え、判断役はクラウド維持」を想定したが、枠の逼迫はその前提を
  越えた。本計画は配分を一段進め、**平常からローカルで運転し、クラウドはリトライ上限
  到達時の昇格受けと、短い出力の判断（planner・多基準 judge）だけに絞る**。
- **経済の根拠は出力トークンの偏りにある。** log_stats の実測（LLM 呼び出しなし）で、
  トークンを焼くのは worker 系（出力 p50 3,583〜5,187 tok）で、判断系は 1 桁小さい
  （planner 437・evaluator 312・adjudicate 16）。**高消費の役割ほどローカルの合格が
  実測で出ている**ので、「長い出力＝ローカル、短い判断＝クラウド極小」の分業は
  そのまま枠の節約率に変換される。
- **品質の守りはモデルではなくゲートに置く。** 決定的検査 + 再投入で、ローカル worker の
  受入は 0/9 → 3/3 に上がった（T1gate）。逆に検査の無い分解は下がる（T1seq 0/3）。
  プロンプト手法・多数決で直らない失敗（filter / judge の基準取り違え）も特定済みで、
  そこは**決定化（P4）かクラウド**であり、ローカルモデルの上積みに賭けない。

## 1.5 外部評価との突き合わせ（2026-08-14 追記）

Gemma 4 E4B の性格について外部の評価を得た。**独立した観察が我々の実測とほぼ完全に
収束している**ので、単なる裏取り以上の価値がある——事実の並びだった §1 に、
**まだ測っていない仕事の成否を予測する軸**が入る。

| 外部評価「強い」 | 対応する我々の実測 |
|---|---|
| 短い回答・分類・要約・structured output | 抽出 6/6・分析 6/6・reduce 6/6・evaluator 5/6（事実 4・5） |
| コード生成・小規模な修正 | T2（落ちるテストを直す）3/3・約 100s（事実 1） |
| サブエージェント | worker として T1gate 3/3（事実 2） |

| 外部評価「急に弱い」 | 対応する我々の実測 |
|---|---|
| 大規模 repo 理解 | リポジトリマップを既定で切っている（1,777 ファイルで文脈が尽きる） |
| 曖昧な要求からの設計 | planner をクラウドに残した判断（§2） |
| **長時間の agent loop** | agent-ollama の tools ループが不合格の一因（T2 が層の交換だけで 1/3 → 3/3） |
| 複数ファイルを跨ぐ設計判断 | T1（実装 + テスト）1/3・T3（複数成果物）0/3（事実 1） |
| **長大な tool result** | 大きな成果物の自動再投入を止めている（`_SM_MAX_AUTO_READ_BYTES`） |
| 何段階もの自己修正 | (b) 族は再投入で直らない・9/9 同形（事実 3） |
| **メタ認知（本当にこれでよいか）** | レビュー 2/6「1 件見つけて満足」・filter/judge が確信して間違える（事実 4・5） |

**公式ベンチマークも同じ形をしている**（外部評価が引いた Google 公式値。**我々の基準線では
ないので採用判断には使わない**が、なぜ「一発の問題は解けるのに実務で微妙」になるかの
説明としては整合する）。

| 能力 | E4B | 12B | 26B A4B |
|---|---:|---:|---:|
| MMLU Pro | 69.4 | 77.2 | 82.6 |
| LiveCodeBench | 52.0 | 72.0 | 77.1 |
| GPQA Diamond | 58.6 | 78.8 | 82.3 |
| **Tau2（エージェント）** | **42.2** | **69.0** | **68.2** |
| BB Extra Hard | 33.1 | 53.0 | 64.8 |
| **MRCR 128K（長文検索）** | **25.4** | 43.4 | 44.1 |

読みどころは 3 つ。

- **E4B は「一発で解く力」と「文脈を維持して実務を進める力」の差が大きい。**
  LiveCodeBench 52.0 に対し Tau2 42.2。我々の実測の形（T2 3/3 なのに T1 1/3・T3 0/3）と一致する。
- **E4B の「4B」は Effective 4B。** 実パラメータ 4.5B・embedding 込みで約 8B の
  エッジ向けモデルで、**「12B を小さくしたもの」ではない**。数字ほど賢く感じないのは
  この期待値のズレでもある。
- **MRCR 128K が 25.4 —— 長い文脈は持てても、その中から引ける保証がない。**
  これは運用に直結する: **`num_ctx` を上げることは E4B に対するレバーではない。**
  我々が既にやっていること（リポジトリマップを切る・ツール結果を詰める・
  大きな成果物を自動再投入しない・P1 で診断を 2000 字で切る）は全部この線で正しく、
  逆に「入らないなら文脈を広げる」方向の対処は効かない。**割るのが正解**である
  （`context_exhausted` を分割で受ける既存の非目標とも一致）。

**得られた予測軸。** 失敗の境目は「難しい / 易しい」ではなく
**「短い・局所的・構造化」⇄「長い・横断的・メタ認知」**である。これは
[§5 の loop 移行順](#5-実行順序)を決める道具になる——10 本のステートマシンを
1 本ずつ実測する前に、**各ステートがどちら側かで当たりを付けられる**。
P1 の「検査を置ける単位で割る」とも噛み合う: 検査コマンドで測れる単位は、
たいてい短く局所的な単位でもある。

### 指摘 1（最重要）— sampling が我々の測定に交絡している可能性

**「コードだから低 temperature」は Gemma 4 では能力を殺しうる。推奨 sampling を使え。**
自分たちの設定を確認した結果、**放置してはいけない形で当てはまる可能性がある**。

- 我々が `temperature: 0` を明示しているのは `agents/ollama-list-thinking.json`（split 用）の
  1 か所だけ。コード worker 経路（`agents/aider.json`）には温度指定が無い。
- **したがって aider 自身の既定が効いている。** `worker_eval.aider_settings()` が渡すのは
  `edit_format` / `use_repo_map` / `num_ctx` / `num_predict` だけで、温度は一度も見ていない。

ここが効くと、我々の結論の 1 つが揺れる。T1 分解レポートは実装ステップの初回失敗が
**13/13 で同一**だったことを「ばらつきではなくこのモデルの決定的な癖」と読んだ。
だが**貪欲デコード（temperature 0）なら同じ入力に同じ出力が返るのは当たり前**である。
つまり「決定的な癖」はモデルの性質ではなく**サンプリングの性質かもしれない**。

含意は 2 つあり、どちらも打ち手を変える。

- **(b) 族「引き直しても揺れない」が再評価対象になる。** 温度 0 なら揺れないのは当然で、
  推奨 sampling なら引き直しが効く可能性がある。効くなら、上限到達の既定を
  `escalate`（段を上げる）から「まず引き直す」へ変える余地が出る——クラウド消費に直結する。
- **ゲートの価値は変わらない。** 検知と再投入で 3/3 になった事実は動かない（再投入時は
  課題文が変わるので、温度 0 でも出力は変わる）。P1 の配線はそのままでよい。

**確認は安い。** `aider --model ollama_chat/gemma4:e4b --verbose` で実効パラメータを出すか、
モデル設定へ `extra_params: {temperature: ...}` を足した腕を worker_eval で 1 本引く。
Gemma 系の推奨は温度を下げない側（Gemma 3 は temperature 1.0 / top_k 64 / top_p 0.95）なので、
**対照群（T2 = 収束する課題）を必ず置く**——上限や温度は失敗を安くすると同時に合格を壊しうる、
というのは `--num-predict` で既に踏んだ轍である。

### 指摘 2 — 欲しいのは「12B より賢い」ではなく「12B の賢さで E4B 並みに速い」

Gemma 4 26B A4B は総 25.2B・**active 約 3.8B** の MoE である。上の表を正しく読むと、
**エージェント能力（Tau2）では 12B 69.0 と 26B A4B 68.2 がほぼ同じ**で、MoE が跳ねるのは
知識・推論側（MMLU Pro / GPQA / BBEH）である。

だから MoE の価値は「12B より賢いこと」ではない。**12B と同じエージェント能力を、
E4B 並みの active parameter 数で出せること**——つまり**速度**である。

そしてそれこそが我々の測定したボトルネックである。dense の gemma4:12b が敗れた原因は
能力ではなく停止性だった——負けは全部タイムアウトで、wall 600 でも 1800 でも 0 完走
（事実 1・4）。**12B は「能力は足りていたが間に合わなかった」**ので、同じ能力を速く出せる
なら、それだけで我々の問題は解ける。P8（12b の生成暴走を根治する）より筋が良い可能性が
あるのはこの意味においてである——P8 は壊れているものを直す作業だが、MoE は壊れていない
ものを使う作業になる。

ただし**制約は RAM で、ここは越えられない**（ハードウェア増強なし・確定）。MoE は
active が小さくても**全 expert が常駐する**ので、必要なのは総パラメータ分のメモリである。
25.2B は q4 で概ね 14〜15GB + KV キャッシュ。実効 16GB なら**成立するか際どいかの境界**で、
`agent-ollama` README の運用上限（「KV キャッシュ込みで物理 RAM に収まること。
スワップに落ちた瞬間、遅いではなく停滞になる」）にそのまま当たる。
**したがって順序は「RAM 実測 → 話はそれから」**であり、これは品質再点検 §6 の候補 b
（MoE は RAM 次第）が最初から置いていた条件そのものである。

### 指摘 3 — Thinking。temperature と**同型の交絡**がもう 1 つある

外部評価は「Gemma 4 は Thinking を使う前提が重要で、Ollama では system prompt 先頭の
`<|think|>` で有効化する。マルチターンでは過去ターンの thought を履歴へ再投入しない」と
指摘している。両方をコードで確認した。**片方は既に正しく、片方は交絡している。**

**(a) 過去 thought の再投入 — 問題なし。** `ollama_loop.say()` が履歴へ積むのは
`content` だけで、`thinking` は積んでいない（本文と思考は API の `thinking` フィールドで
分離済み）。ここは対処不要。

**(b) think=off の全役割焼き込み — 別モデルの実測を一般化していた。** README は
「`agents/*.json` は think をヘッドレスの全役割で off に焼き込んである」とし、根拠を
**2026-08-10・ログ 236 本**の実測（write 経路 p90 942 秒・readonly 中央値 1000 秒・
`--format json` 併用で本文が空 39/39）としている。だが台帳を確認すると:

| 日付 | 台帳 | モデル |
|---|---|---|
| 2026-08-10 | `ledger-2026-08-10-qwen35-9b.jsonl` | **qwen3.5:9b のみ** |
| 2026-08-11 | `ledger-2026-08-11-worker-aider.jsonl` | gemma4:e4b が初登場 |

**think=off の決定は gemma4 がこのリポジトリに入る前日に、qwen で測って下されている。**
temperature とまったく同じ構図——ある条件で測った結論が、別の条件へ黙って持ち越されている。

しかも**反証が自リポジトリ内にある**。`agents/ollama-list-thinking.json` は
「Aider/Gemma 4 の split。文法制約を外して Thinking を使い、`temperature=0` で
意味的な完全被覆を安定させる」という定義で、**gemma4 に対しては Thinking が効くと
既に判断されている**。全役割 off の焼き込みと、この 1 定義は整合していない。

さらに**機構そのものが違う可能性**がある。我々の `--think on|off` は API の `think`
フィールドへ直結している（`ollama_loop._payload` が `body["think"]` を設定）。外部評価が
言う Gemma 4 の作法は **system prompt 先頭の `<|think|>`** で、こちらなら
`--format json` との併用で本文が空になる問題（文法制約が thinking の 1 トークン目から
掛かる）も起きない可能性がある。**もしそうなら、JSON 契約の役割で Thinking を
使えないという我々の制約は、Gemma 4 には当てはまらない。**

判定系の実測（filter/judge がプロンプトでは直らない・確信して間違える）は
**すべて think off で取ったもの**なので、ここが動くと §1 の事実 5 の読み方も変わる。

**確認は P10 に同居させる**（同じハーネス・同じ対照群で 1 度に測る）。見るのは 3 点:
`<|think|>` 方式で thinking が実際に発生するか、`--format json` と併用しても本文が
返るか、判定系（RV1/RV2・F2・J2）の正解率が動くか。**動かなければ現状維持でよい**
——測っていないものを「効くはず」で入れない規律は変えない。

### 取り込まないもの

- **ベンチマーク数値を採用判断の根拠にしない。** 「基準線の無いモデル差し替え」は
  次期評価計画の「やらないこと」に入れてある。候補として測る価値は上がったが、
  測らずに載せ替える理由にはならない。
- **「E4B を worker に、より強い planner/reviewer を別に置く」という構成の提案そのものは
  既に §2 でそうしている。** 外部評価はその配置が妥当だという独立の裏取りであって、
  新しい指示ではない。差分は「より強い側を何にするか」だけで、そこが指摘 2 になる。

## 2. 運転方針 — 役割×モデルの割り当てマップ（実測準拠）

原則: **長い出力を作る役割はローカルへ、短い出力で run の形を決める判断だけをクラウドへ。**
ローカル側の品質保証はモデルに求めず、決定的ゲート + 再投入 + 昇格で持つ。

| 役割帯 | 割り当て | ガード（受け） | 根拠 |
|---|---|---|---|
| コード worker（定型・分解済み） | **gemma4:e4b + aider** | 決定的ゲート + 再投入（max_retries 1〜2）→ 上限到達でクラウド昇格 | 事実 1・2・3 |
| 抽出・分析・構造化要約・分類 | **e4b 単発 JSON**（`ollama-json`） | JSON 文法制約 + チェッカー | 事実 4 |
| split | **e4b**（`ollama-list` / `--format array`） | 配列スキーマ強制 | 事実 5 |
| reduce・evaluator | **e4b 単発 JSON** | 形式検査。evaluator の誤 replan は継続予算の上限で受ける | 事実 5 |
| レビュー・検証・違反特定（テキスト） | **gemma4:12b 単発 JSON** | `--stall-timeout` + timeout 再投入 1 回（暴走は確率的・再投入で回収可能な頻度） | 事実 4 |
| 単基準 filter（基準が材料に明示） | **e4b** | 基準は 1 つに絞ってから渡す（P4） | 事実 6 |
| 多基準 filter / judge | **決定化パイプ（P4）**。組み替え不能な判定だけクラウド | 決定的な前処理で候補を削り、モデルには残りの単基準だけを訊く | 事実 5・6 |
| 制約つき生成（字数・予算・必須言及） | **e4b + 決定的ゲート**（長さ・合計値・言及検査）+ 再投入 | ゲートは機械検査 | 事実 6 |
| planner（新規性の高い仕事の形決め） | **クラウド温存**（出力 437 tok/回と安い）。定型は statemachine の事前分解で planner 自体を不要化 | 未測定のままローカルへ移さない（事実 10） | 事実 9・10 |
| リトライ上限到達の昇格受け | **クラウド**（per-incident） | 上限 1〜2 で早期に宣告される（事実 3） | 事実 3 |
| 記憶検索（recall） | **bge-m3 埋め込み**（生成モデルと独立） | lexical は現行 TF-IDF 維持・paraphrase のみ埋め込み | 事実 7 |
| コード worker としての 12b | **使わない**（禁止） | 生成暴走の根治（P8）まで凍結 | 事実 1 |

この表で**クラウドに残るのは 3 つだけ**——新規 planner・組み替え不能な多基準判定・昇格受け。
いずれも出力数百トークン級で、消費の主因（worker 系の数千トークン）はすべてローカルへ移る。

## 3. 提案（優先度: ★=先行 ○=並行可 △=後続）

### P1 ★ statemachine の検査コマンド — 自己申告を遷移材料から外す（実装済み・2026-08-14）

t1-decomposition レポートが特定した**唯一の中心実装**。これが無い限り、ローカル worker の
偽 done が機械層を素通りする（事実 8）ので、ルーティングだけ変えても品質が持たない。

- state に「ハーネスが実行する検査コマンド」を宣言し、その **exit code** を
  `condition_rule` のコンテキストへ入れる（statemachine-use のスキーマ拡張を含む）。
- 落ちたら同じ state をやり直す（既存 `max_retries` をそのまま使う。上限 1〜2）。
- 上限到達は fail ではなく **`escalate`**（tier 昇格のシグナル）として区別して返す——
  「この tier では無理」を機械が宣告する口（事実 3）。
- 検査 stdout を再試行の課題文へ足すのは後段の速度最適化（28%）。**先に真偽だけで動かす**。
- 完了後、t1-decomposition の同一セル（T1gate 相当）を**実機経路で再測**して配線を検証する
  （ハーネス側の手順模擬との差分を潰す。レポートの未着手項目）。
  **→ 再測済み（2026-08-15）: 3/3・中央値 313s・escalate 0。** 素通しは 0/3 帯で、模擬との
  配線差分 3 件（check 遷移を知らない機械契約・制御周へ戻る再投入・割付を制御席に訊く）を
  修正して到達した。うち 3 件目は state の `write:` 割付宣言（スキーマ拡張）。詳細は
  [eval/README](../../tools/agent-tools/eval/README.md)「実測 2026-08-15 — 段1 実機再測」。

**実装記録（2026-08-14）。** 配線は入った。残るのは実機再測（下記）。

| 置き場 | 入れたもの |
|---|---|
| `statemachine-use/scripts/engine.py` | `check` の正規化（`normalize_check`）・結果のコンテキスト契約（`check_context`）・実行（`run_check`）・検証。非同期エンジン側のゲートと再投入 |
| `statemachine-use/scripts/next_state.py` | `--state-check`（正規化済み宣言の照会口）。外部ハーネスが YAML を読み直さずに済ませ、正規化を 1 実装に保つ |
| `agent-loop/agent_loop/statemachine.py` | 本番経路のゲート実行・再投入・`escalate` 返却。検査結果を `--context` へ載せて遷移を確定させる |
| 契約 | `check_status` / `check_ok` / `check_output` の 3 キー（正典は `references/schema.md`） |

宣言の形（`state.check`）は 3 つ受ける（文字列・配列・`{command,args,timeout_sec}`）。
**シェルは介さない**（argv 直接実行）ので、メタ文字入りの宣言は投入前にエラーにする——
黙って別物を実行するより落とす。失敗時の動作は `check_on_exhausted` が決める:
`escalate`（既定・実行を止めて `escalate: true` + 終了コード 3）/ `continue`（検査結果を
コンテキストへ入れて遷移評価へ進む）/ `error`（通常の失敗）。

**壊れやすい 2 点をテストで塞いだ**——(a) モデルが「OK」と書いても検査が落ちれば進まないこと、
(b) 検査を宣言していないステートから `check_ok` で分岐する定義は**検証エラーにする**こと。
(b) を通すと、決定的に見ているつもりの遷移が `evaluate_condition_rule` の
キー不在フォールバックで静かに LLM 評価へ落ち、P1 以前の状態に戻る。

テスト: `statemachine-use/tests/test_check.py`（34 件）・
`agent-loop/test/test_statemachine.py` の `CheckGateTest` / `CheckContextContractTest` /
`EscalationExitCodeTest`（19 件）。既存 967 件は無変更で通る（宣言の無いステートは素通り）。
作例は `statemachine-use/examples/gated_implement.yaml`。

### P2 ★ ルーティング宣言の更新 — 割り当てマップを 1 実装に落とす

§2 の表を宣言として固定する。エンジンに選択の知能を足さない（既存不変条件のまま）。

### P3 ★ 持久運転を「常用運転」へ — 発動条件の反転

持久運転設計（2026-08-12・段階 1〜5）の実装を最優先で進めた上で、**発動閾値を
「残予算 20%」から「常時」へ倒せるプリセットを足す**（例: 実行方針「ローカル主体」）。

- 設計の骨格（決定関数を agentcore へ 1 実装・エンジンがサイクル先頭で評価・
  補償機構は「作業段が basic か」で発火）はそのまま使う。変えるのは方針プリセットの宣言だけ。
- 判断役の段は設計どおり据え置くが、**evaluator は実測 5/6（事実 5）を根拠に
  ローカル降格を許す**選択肢を方針に持たせる（planner / 多基準 judge は据え置き）。
- クラウド枠は node-budget 上で「昇格・planner 専用」の配分として温存する
  （worker 系へ流れない形にする）。

### P4 ○ 判定の決定化 — 多基準を「決定的前処理 + 単基準」へ組み替える

プロンプト・多数決の 4 レバーが全滅した領域（事実 5）への、実測が示す唯一のローカル解。

- 多基準 filter / judge を、(1) 機械が測れる基準（テスト通過・行数・依存の有無・予算合計）は
  **決定的チェッカーで先に足切り**し、(2) モデルには**残った候補 × 基準 1 つ**だけを訊く
  パイプへ組み替える（F1 3/3 の形に寄せる）。
- 「候補生成 + 決定的検算」（誤りが存在チェックで無害化される形）を判定系の標準形にする。
- 組み替えても残る本質的に多基準な判定（トレードオフの裁定）だけをクラウド行きにする。

### P5 ○ 制約つき生成のゲート — 長さ・予算・必須言及の機械検査

SM2 / PR1 型の弱点（両モデル 1/3〜2/3）は決定的に測れる制約なので、P1 の検査コマンドに
長さ・合計値・必須語の検査を足し、再投入で受ける。text-eval の含意そのまま。

### P6 ○ クラウド消費の規律 — 使う場所を 3 つに固定し、台帳で守る

- クラウド呼び出しは (1) 新規 planner、(2) 組み替え不能な多基準判定、(3) 昇格受け、に限る。
- 評価用の参照ラベル生成（next-eval-plan §3 の 3）は**一度だけ払って資産化**する。
- agent-audit の台帳でクラウド消費を役割別に見えるようにし、worker 系へクラウドが
  流れた run を検出できるようにする（規律の破れを事後に気付ける形）。

### P7 ○ bge-m3 の recall 投入 — クラウド非依存の独立レバー

実測済み（事実 7）。訊き方で振り分ける（lexical=現行 TF-IDF・paraphrase=埋め込み。
素朴な RRF 併用は害）。宛先と索引の持ち方は別途設計書（ltm-use 側）へ切る。

### P10 ★ 推論条件の確認 — 我々自身の測定条件を先に潰す（§1.5 指摘 1・3）（実測済み・2026-08-15）

**実測記録（2026-08-15）。** 結果は [eval/README](../../tools/agent-tools/eval/README.md)
「実測 2026-08-15 — 段0 の結果」節と `results/archive/ledger-2026-08-15-p10-*.jsonl`。要点 3 つ:
(1) **実効 temperature は 0 だった**（aider が既定で明示送信）——「13/13 同形」は貪欲デコードの
帰結で、推奨 sampling（1.0/0.95/64）では失敗が揺れて T1 0/3 → 1/3、対照群 T2 は 3/3 のまま。
(2) **think=prompt は JSON 契約と併用でき、空応答 0/20・速度ペナルティなし**——qwen で決めた
制約は gemma4 には当てはまらない。(3) **正解率はレビュー網羅（RV1 0/3 → 2/3）だけ動き、
基準の取り違え（F2/J1）は誤答まで同一**——決定化（P4）行きは確定。§1 の事実 2・3・5 に注記済み。

**新規・最優先。安い上に、他のすべての実測の読み方を変えうる。**
**sampling と Thinking の 2 つは同じ性格の交絡**（ある条件で測った結論が別の条件へ
黙って持ち越されている）なので、同じハーネス・同じ対照群で 1 度に測る。

**(1) sampling** — コード worker 経路の実効 temperature を確認し、推奨 sampling の腕を引く。

- 確認: `aider --verbose` の実効パラメータ、または `aider.model.settings.yml` へ
  `extra_params: {temperature: …}` を足した腕。
- **対照群を必ず置く**（T2 = 収束する課題）。上限や温度は失敗を安くすると同時に合格を
  壊しうる（`--num-predict` で実証済み）。
- 追加で見るのは**同一入力の再現性**。温度 0 の貪欲デコードなら初回失敗が同形になるのは
  当然なので、「決定的な癖」がモデルの性質かサンプリングの性質かはここで分かれる。
- 結果が (b) 族の揺れを生むなら、`check_on_exhausted` の既定を再考する
  （引き直しで直るなら、段を上げる前にまず引き直す方が安い）。P1 の配線は変えない。

**(2) Thinking** — gemma4 に対する think の扱いを測り直す。現行の全役割 off は
qwen で取った実測（2026-08-10）の一般化であり、gemma4 では反証が自リポジトリ内にある
（`ollama-list-thinking`）。見るのは 3 点。

- `<|think|>`（system prompt 先頭）方式で thinking が実際に発生するか。現行の
  `--think on|off` は API の `think` フィールド直結なので、**機構が違えば結論も違う**。
- `--format json` と併用して本文が返るか。現行実装は `--format` を渡した時点で
  think を強制 off にしている（本文が空になる 39/39 の回避）。ここが解けるなら、
  **JSON 契約の役割で Thinking が使えない**という制約自体が外れる。
- 判定系（RV1/RV2・F2・J2）の正解率が動くか。§1 の事実 5（プロンプトでは直らない・
  確信して間違える）は**全部 think off で取った数字**なので、動けば読み方が変わる。

**動かなければ現状維持。** 測っていないものを「効くはず」で入れない規律は変えない
（think を on へ戻すなら記録済みプロンプトの再生で先に示すこと、という既存の条件も生きている）。
壁時計の懸念も残る——qwen で p90 942 秒だったのは`agent_timeout` 600 秒を超えるので、
**速度の対照も同時に取る**（gemma4 は decode 26.5 tok/s で qwen の 2 倍以上速い）。

### P11 ○ MoE 候補の RAM 実測と評価（§1.5 指摘 2）— P8 に優先する

active parameter が E4B 並みで能力が上の MoE（例: Gemma 4 26B A4B）は、我々が測った
ボトルネック（dense 12b は能力でなく停止性で敗れた）を直撃する。順序を守る。

1. **RAM が先。** 総パラメータ分が常駐する（active が小さくても減らない）。
   q4 の重み + KV キャッシュが物理 RAM に収まるかを実測する。**収まらなければここで終わり**
   ——スワップは「遅い」ではなく「停滞」で、ハードウェア増強は制約上できない。
2. 収まるなら `judge_eval` / `text_eval` / `worker_eval` の既存セルへ `--model` を差し替えて
   基準線（e4b・12b）と並べる。**ベンチマーク数値は採用根拠にしない。**
3. 通れば、レビュー/検証役（現 12b）と昇格先の候補になる。

### P8 △ gemma4:12b の生成暴走の根治 — P11 の結果を見てから

12b の敗因は能力でなく停止性（事実 1・4）。`num_predict` 上限・stop 条件・ollama
テンプレートの順で原因を潰し、`--replay` のオフライン再生で先に効果を示してから
適用範囲を再検討する。**根治まで 12b はコード worker に使わない**。

**優先度を下げた**（○ → △）。P11 が通れば 12b を直す動機はほぼ消える——壊れているものを
直すより、壊れていないものを使うほうが筋が良い。P11 が RAM で落ちたときの次善策として残す。

### P9 △ 未測定面の最小 eval — planner と project / dashboard / amigos

`coverage.json` の missing のうち、ローカル移行の判断に効く順で最小セルを足す:
planner（構成的正解の分解課題）→ project:verify → dashboard の doctor 系。
**基準線の無いままローカルへ移さない / モデルを替えない**（next-eval-plan の規律を維持）。

## 6. やらないこと

- **ハードウェア増強**（制約・確定）。RAM に収まらない `num_ctx` / モデルも同義で不採用
  （スワップは「遅い」ではなく「停滞」になる——agent-ollama README の運用上限）。
- **gemma4:12b のコード worker 起用**（P8 の根治まで）。wall 600 / 1800 の両方で 0 完走。
- **worker のモデル再測・格上げ探し**。e4b + ゲートで受入が出ており、課題は配線側。
- **圧縮して続行するループ**。既存非目標のまま（`context_exhausted` は分割で受ける）。
- **本番ライン観察での品質測定**。3 日かけて何も出なかった方式に戻らない。
- **プロンプト手法による filter / judge の救済続行**。4 レバー空振りで打ち止め。決定化（P4）へ。
- **基準線の無いモデル差し替え**（P9 の規律）。外部評価のベンチマーク数値も同じ扱い
  （§1.5 指摘 2）——候補として測る優先度は上げるが、測らずに載せ替える根拠にはしない。
- **RAM に収まらないモデルの採用**。MoE は active が小さくても全 expert が常駐するので、
  「active 3.8B だから軽い」は**メモリには当てはまらない**。

## 7. リスクと再評価条件

| リスク | 受け |
|---|---|
| 昇格が頻発してクラウド消費が戻る | 台帳で昇格率を役割別に観測。特定の定型で昇格が続くなら、その課題は (b) 族＝ローカル不適として定型から外す（事実 3 の使い方そのもの） |
| 実機経路の再測でハーネス模擬との差が出る | 段 1 の完了条件に含めた。差が出たら statemachine 側の配線を先に直す（ルーティング反転は保留） |
| planner 未測定のままクラウド枠がさらに縮む | P9 の planner セルを前倒しし、定型の事前分解（planner 不要化）の適用範囲を広げる |
| 12b の暴走頻度が想定より高い | 検証役の再投入上限を 1 → 2 にせず、e4b + 決定化ゲートへの縮退を先に試す（レビュー網羅性は落ちるが停止性は保つ） |
| 壁時計 2.1 倍が定型の回転数を落とす | 対象定型の棚卸しで「繰り返し回数 × 節約クレジット > 壁時計」の順に投入。全部を移すことは目的にしない |

| 実効 sampling / think が測定を交絡していた（§1.5 指摘 1・3） | 段 0（P10）で先に潰す。影響が出るのは「決定的な癖」の解釈・(b) 族の扱い・判定系の読み方で、**ゲートの有効性そのものは動かない**（再投入時は課題文が変わるため）。判明したら §1 の事実 2・3・5 に注記を足し、`check_on_exhausted` の既定と JSON 契約役割の think 制約を見直す |
| MoE が RAM に入らない | そこで終わり（ハードウェア増強は制約上できない）。次善は P8（12b の停止性の根治）で、レビュー役の現状維持は成立している |

再評価条件: 昇格率が恒常的に高い（クラウド消費が §4 の概算から乖離する）、
実機再測で受入が 3/3 帯を割る、**段 0 で sampling の交絡が確認された**、
または P11 / P8 で「強くて速い」候補が手に入ったとき。
