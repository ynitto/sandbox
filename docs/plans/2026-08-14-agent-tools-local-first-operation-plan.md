# agent-tools をローカル LLM 主体で動かす — 常用ローカル・例外クラウドの運転計画

> 作成 2026-08-14
> 前提: クラウド CLI のトークン枠が逼迫し、「上位モデルを温存する」ではなく
> 「クラウドをほぼ使えない」が新しい平常になった。ハードウェアは増強しない（制約・確定）。
> 根拠はすべて実測 — [`tools/agent-tools/eval/results/archive/`](../../tools/agent-tools/eval/results/archive/)
> の 3 レポートと台帳、および [`eval/README.md`](../../tools/agent-tools/eval/README.md) の測定記録。

## 0. 結論の先出し

- **ローカル主体運転は未知への挑戦ではない。** archive の実測は、agent-flow の役割の
  大半（work / 抽出 / 分析 / 構造化要約 / split / reduce / evaluator / レビュー）で既に
  合格ラインを出している。足りないのは能力ではなく、**配線 1 箇所**（P1: statemachine の
  検査コマンド）と**ルーティングの宣言**（P2）である。
- **クラウドは「段」ではなく「例外処理」にする。** 持久運転設計
  （[2026-08-12](2026-08-12-agent-flow-basic-tier-emergency-operation-design.md)）は
  「残予算 20% で切り替え、判断役はクラウド維持」を想定したが、枠の逼迫はその前提を
  越えた。本計画は配分を一段進め、**平常からローカルで運転し、クラウドはリトライ上限
  到達時の昇格受けと、短い出力の判断（planner・多基準 judge）だけに絞る**。
- **経済の根拠は出力トークンの偏りにある。** log_stats の実測（LLM 呼び出しなし）で、
  トークンを焼くのは worker 系（出力 p50 3,583〜5,187 tok）で、判断系は 1 桁小さい
  （planner 437・evaluator 312・adjudicate 16）。**高消費の役割ほどローカルの合格が
  実測で出ている**ので、「長い出力＝ローカル、短い判断＝クラウド極小」の分業は
  そのまま枠の節約率に変換される。
- **品質の守りはモデルではなくゲートに置く。** 決定的検査 + 再投入で、ローカル worker の
  受入は 0/9 → 3/3 に上がった（T1gate）。逆に検査の無い分解は下がる（T1seq 0/3）。
  プロンプト手法・多数決で直らない失敗（filter / judge の基準取り違え）も特定済みで、
  そこは**決定化（P4）かクラウド**であり、ローカルモデルの上積みに賭けない。

## 2. 運転方針 — 役割×モデルの割り当てマップ（実測準拠）

原則: **長い出力を作る役割はローカルへ、短い出力で run の形を決める判断だけをクラウドへ。**
ローカル側の品質保証はモデルに求めず、決定的ゲート + 再投入 + 昇格で持つ。

| 役割帯 | 割り当て | ガード（受け） | 根拠 |
|---|---|---|---|
| コード worker（定型・分解済み） | **gemma4:e4b + aider** | 決定的ゲート + 再投入（max_retries 1〜2）→ 上限到達でクラウド昇格 | 事実 1・2・3 |
| 抽出・分析・構造化要約・分類 | **e4b 単発 JSON**（`ollama-json`） | JSON 文法制約 + チェッカー | 事実 4 |
| split | **e4b**（`ollama-list` / `--format array`） | 配列スキーマ強制 | 事実 5 |
| reduce・evaluator | **e4b 単発 JSON** | 形式検査。evaluator の誤 replan は継続予算の上限で受ける | 事実 5 |
| レビュー・検証・違反特定（テキスト） | **gemma4:12b 単発 JSON** | `--stall-timeout` + timeout 再投入 1 回（暴走は確率的・再投入で回収可能な頻度） | 事実 4 |
| 単基準 filter（基準が材料に明示） | **e4b** | 基準は 1 つに絞ってから渡す（P4） | 事実 6 |
| 多基準 filter / judge | **決定化パイプ（P4）**。組み替え不能な判定だけクラウド | 決定的な前処理で候補を削り、モデルには残りの単基準だけを訊く | 事実 5・6 |
| 制約つき生成（字数・予算・必須言及） | **e4b + 決定的ゲート**（長さ・合計値・言及検査）+ 再投入 | ゲートは機械検査 | 事実 6 |
| planner（新規性の高い仕事の形決め） | **クラウド温存**（出力 437 tok/回と安い）。定型は statemachine の事前分解で planner 自体を不要化 | 未測定のままローカルへ移さない（事実 10） | 事実 9・10 |
| リトライ上限到達の昇格受け | **クラウド**（per-incident） | 上限 1〜2 で早期に宣告される（事実 3） | 事実 3 |
| 記憶検索（recall） | **bge-m3 埋め込み**（生成モデルと独立） | lexical は現行 TF-IDF 維持・paraphrase のみ埋め込み | 事実 7 |
| コード worker としての 12b | **使わない**（禁止） | 生成暴走の根治（P8）まで凍結 | 事実 1 |

この表で**クラウドに残るのは 3 つだけ**——新規 planner・組み替え不能な多基準判定・昇格受け。
いずれも出力数百トークン級で、消費の主因（worker 系の数千トークン）はすべてローカルへ移る。

## 3. 提案（優先度: ★=先行 ○=並行可 △=後続）

### P1 ★ statemachine の検査コマンド — 自己申告を遷移材料から外す

t1-decomposition レポートが特定した**唯一の中心実装**。これが無い限り、ローカル worker の
偽 done が機械層を素通りする（事実 8）ので、ルーティングだけ変えても品質が持たない。

- state に「ハーネスが実行する検査コマンド」を宣言し、その **exit code** を
  `condition_rule` のコンテキストへ入れる（statemachine-use のスキーマ拡張を含む）。
- 落ちたら同じ state をやり直す（既存 `max_retries` をそのまま使う。上限 1〜2）。
- 上限到達は fail ではなく **`escalate`**（tier 昇格のシグナル）として区別して返す——
  「この tier では無理」を機械が宣告する口（事実 3）。
- 検査 stdout を再試行の課題文へ足すのは後段の速度最適化（28%）。**先に真偽だけで動かす**。
- 完了後、t1-decomposition の同一セル（T1gate 相当）を**実機経路で再測**して配線を検証する
  （ハーネス側の手順模擬との差分を潰す。レポートの未着手項目）。

### P2 ★ ルーティング宣言の更新 — 割り当てマップを 1 実装に落とす

§2 の表を宣言として固定する。エンジンに選択の知能を足さない（既存不変条件のまま）。

- `agents/` に 12b のテキスト検証役定義を追加（`ollama-json` 系・think off・
  `--stall-timeout` + timeout 時 1 回再投入を errors 分類で宣言）。
- dashboard の `flow-tiers.js` カタログと `tiers.basic` 候補へ反映（basic=e4b 系、
  検証役=12b 系）。verify（テキスト）は「軽量＝ローカル 12b」で適格にする。
- コード worker は正典どおり `agents/aider.json`（e4b）。12b をコード側の候補に**入れない**。

### P3 ★ 持久運転を「常用運転」へ — 発動条件の反転

持久運転設計（2026-08-12・段階 1〜5）の実装を最優先で進めた上で、**発動閾値を
「残予算 20%」から「常時」へ倒せるプリセットを足す**（例: 実行方針「ローカル主体」）。

- 設計の骨格（決定関数を agentcore へ 1 実装・エンジンがサイクル先頭で評価・
  補償機構は「作業段が basic か」で発火）はそのまま使う。変えるのは方針プリセットの宣言だけ。
- 判断役の段は設計どおり据え置くが、**evaluator は実測 5/6（事実 5）を根拠に
  ローカル降格を許す**選択肢を方針に持たせる（planner / 多基準 judge は据え置き）。
- クラウド枠は node-budget 上で「昇格・planner 専用」の配分として温存する
  （worker 系へ流れない形にする）。

### P4 ○ 判定の決定化 — 多基準を「決定的前処理 + 単基準」へ組み替える

プロンプト・多数決の 4 レバーが全滅した領域（事実 5）への、実測が示す唯一のローカル解。

- 多基準 filter / judge を、(1) 機械が測れる基準（テスト通過・行数・依存の有無・予算合計）は
  **決定的チェッカーで先に足切り**し、(2) モデルには**残った候補 × 基準 1 つ**だけを訊く
  パイプへ組み替える（F1 3/3 の形に寄せる）。
- 「候補生成 + 決定的検算」（誤りが存在チェックで無害化される形）を判定系の標準形にする。
- 組み替えても残る本質的に多基準な判定（トレードオフの裁定）だけをクラウド行きにする。

### P5 ○ 制約つき生成のゲート — 長さ・予算・必須言及の機械検査

SM2 / PR1 型の弱点（両モデル 1/3〜2/3）は決定的に測れる制約なので、P1 の検査コマンドに
長さ・合計値・必須語の検査を足し、再投入で受ける。text-eval の含意そのまま。

### P6 ○ クラウド消費の規律 — 使う場所を 3 つに固定し、台帳で守る

- クラウド呼び出しは (1) 新規 planner、(2) 組み替え不能な多基準判定、(3) 昇格受け、に限る。
- 評価用の参照ラベル生成（next-eval-plan §3 の 3）は**一度だけ払って資産化**する。
- agent-audit の台帳でクラウド消費を役割別に見えるようにし、worker 系へクラウドが
  流れた run を検出できるようにする（規律の破れを事後に気付ける形）。

### P7 ○ bge-m3 の recall 投入 — クラウド非依存の独立レバー

実測済み（事実 7）。訊き方で振り分ける（lexical=現行 TF-IDF・paraphrase=埋め込み。
素朴な RRF 併用は害）。宛先と索引の持ち方は別途設計書（ltm-use 側）へ切る。

### P8 △ gemma4:12b の生成暴走の根治 — 直れば適用範囲が広がる

12b の敗因は能力でなく停止性（事実 1・4）。`num_predict` 上限・stop 条件・ollama
テンプレートの順で原因を潰し、`--replay` のオフライン再生で先に効果を示してから
適用範囲（テキスト検証役の再投入頻度低減、将来のコード側）を再検討する。
**根治まで 12b はコード worker に使わない**。

### P9 △ 未測定面の最小 eval — planner と project / dashboard / amigos

`coverage.json` の missing のうち、ローカル移行の判断に効く順で最小セルを足す:
planner（構成的正解の分解課題）→ project:verify → dashboard の doctor 系。
**基準線の無いままローカルへ移さない / モデルを替えない**（next-eval-plan の規律を維持）。

## 4. 期待効果の概算

log_stats の実寸（事実 9）から、1 run のクラウド消費は次のように変わる:

| 運転 | クラウドに残る出力 | 概算 |
|---|---|---|
| 現行（全役割クラウド） | worker 3,583 + verifier 5,187 + 判断系 ≈ 800 | 〜9,500 tok/run + 入力 |
| 本計画（ローカル主体） | planner 437（新規時のみ）+ 昇格分（上限到達時のみ） | **平常 0〜500 tok/run** |

定型タスクはクラウド 0 で回る（T1gate 実測: 壁時計 2.1 倍を払い、クラウド消費 0）。
壁時計はローカル GPU の時間であり、節約したいのはクレジットなのでこの交換は成立する
（t1-decomposition「費用」節の結論を踏襲）。対象は本当に繰り返す定型に絞る
（1 タスク 15 分の天井はそれ自体は消えない）。

## 5. 実行順序

| 段 | 内容 | 完了条件 |
|---:|---|---|
| 1 | **P1**（検査コマンド）+ **P2**（ルーティング宣言） | T1gate 相当を実機経路で再測し 3/3 帯を確認 |
| 2 | **P3**（常用ローカルのプリセット） | 定型 flow がクラウド 0 で完走し、昇格だけがクラウドを呼ぶことを台帳で確認 |
| 3 | **P4** + **P5**（判定の決定化・制約ゲート） | filter/judge の多基準ケースが決定化パイプで F1 並みに通る |
| 独立 | **P7**（bge-m3） | 段 1〜3 と依存なし。いつでも |
| 後続 | **P8**（12b 根治）・**P9**（未測定面 eval） | replay / 最小セルの実測が出てから適用判断 |

段 1 が終わるまで段 2 を入れない——ゲート無しのローカル降格は偽 done を量産する
（T1seq 0/3 と statemachine の自己申告素通りが実測済み）。

## 6. やらないこと

- **ハードウェア増強**（制約・確定）。RAM に収まらない `num_ctx` / モデルも同義で不採用
  （スワップは「遅い」ではなく「停滞」になる——agent-ollama README の運用上限）。
- **gemma4:12b のコード worker 起用**（P8 の根治まで）。wall 600 / 1800 の両方で 0 完走。
- **worker のモデル再測・格上げ探し**。e4b + ゲートで受入が出ており、課題は配線側。
- **圧縮して続行するループ**。既存非目標のまま（`context_exhausted` は分割で受ける）。
- **本番ライン観察での品質測定**。3 日かけて何も出なかった方式に戻らない。
- **プロンプト手法による filter / judge の救済続行**。4 レバー空振りで打ち止め。決定化（P4）へ。
- **基準線の無いモデル差し替え**（P9 の規律）。

## 7. リスクと再評価条件

| リスク | 受け |
|---|---|
| 昇格が頻発してクラウド消費が戻る | 台帳で昇格率を役割別に観測。特定の定型で昇格が続くなら、その課題は (b) 族＝ローカル不適として定型から外す（事実 3 の使い方そのもの） |
| 実機経路の再測でハーネス模擬との差が出る | 段 1 の完了条件に含めた。差が出たら statemachine 側の配線を先に直す（ルーティング反転は保留） |
| planner 未測定のままクラウド枠がさらに縮む | P9 の planner セルを前倒しし、定型の事前分解（planner 不要化）の適用範囲を広げる |
| 12b の暴走頻度が想定より高い | 検証役の再投入上限を 1 → 2 にせず、e4b + 決定化ゲートへの縮退を先に試す（レビュー網羅性は落ちるが停止性は保つ） |
| 壁時計 2.1 倍が定型の回転数を落とす | 対象定型の棚卸しで「繰り返し回数 × 節約クレジット > 壁時計」の順に投入。全部を移すことは目的にしない |

再評価条件: 昇格率が恒常的に高い（クラウド消費が §4 の概算から乖離する）、
実機再測で受入が 3/3 帯を割る、または P8 の根治で 12b の適用範囲が変わったとき。
