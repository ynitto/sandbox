# agent-ollama 次の計画 — worker 不合格の次に何を測るか

> 作成 2026-08-11
> 前提: [`tools/agent-tools/eval/README.md`](../../tools/agent-tools/eval/README.md) の実測
> （2026-08-10・qwen3.5:9b の worker 受入 2/21 で不合格）と、
> [`2026-08-10-agent-ollama-quality-and-role-refit-proposals.md`](./2026-08-10-agent-ollama-quality-and-role-refit-proposals.md)
> の引受範囲の整理。マシンのスペックアップは無し、モデルの変更は可。

worker は決着した。**次に測るべきは、本番で既に使っているのに一度も測っていない役割**である。

## 0. 結論の先出し

- **worker は再測しない。** 不合格の判断に加えて、失敗の中身が「間違ったコードを書いた」
  ではなく「**書き終える前に予算が尽きた**」だと分かった（§1）。これは能力とスループットの
  両方が同じ向きに効いており、いまのマシンで動く手が無い。
- **次は判定・分類を測る。** classify / filter / judge / split / extract は**段 0 で既に
  本番へ入っている**のに、正しさを 1 件も測っていない。しかも worker が枯渇させた資源
  （decode 量）をこれらはほぼ使わない——**worker の不合格はこれらの不合格を意味しない**（§2）。
- **ハーネスは worker_eval の型を再利用する。** 3 日かけて何も出なかった観察を 1 時間で
  決着させた設計（決定的チェッカー・同一タスクの反復・使い捨て worktree・判定役ゼロ）は
  そのまま効く。変える必要があるのは「正解をどこから持ってくるか」だけ（§3）。
- **測る前に 1 つ確かめる。** 「1 発判断は 9.3 秒で完走」の根拠になった実行のプロンプト長を
  確認する。本番の planner / judge プロンプトは材料を丸ごと inline するので桁が違い、
  そこが違えば 9.3 秒は本番を代表していない（§4）。**最も安く、最も判断を変えうる 1 手**。

## 1. 実測から何が言えるか — 「能力」の中身を 1 段掘る

README の結論（予算でも粒度でも暴走でもなく能力）は動かない。その上で、台帳 21 行の
`note` を数えると打ち手の選び方が変わる。

| 失敗の中身 | 件数 | 読み |
|---|---:|---|
| 成果物のファイルが 1 つも無い | 9 | 書き**始める前**に予算が尽きた |
| 構文が壊れている（Indentation / Syntax / IndexError） | 3 | 書いたが完成させられない |
| 振る舞いが仕様と違う | 1 | 完成したが誤り |
| T3 の部分成果（schema 無し・schema 不正・契約テスト無し） | 3 | 複数成果物のうち一部で力尽きる |
| 自己申告の未完了 | 2 | 自分で未完了と申告（封筒は機能している） |
| 受入 | 2 | — |

**「間違ったコードを書く」より「書き終わらない」が主**である（9 + 3 = 12/21）。
decode 11〜12 tok/s × 600 秒 ≒ 7000 トークンという予算は、読んで・考えて・ファイルを
書いて・テストを回す往復には足りない。予算 3 倍（1800 秒 ≒ 21000 トークン）でも 0/3 だった
ので、時間を積んでも往復の質が上がらない——**能力とスループットが同じ向きに効いている**。

この読みが次の計画に効くのは 2 点。

- **スループットが効かない用途を選べば、能力の壁だけと向き合える。** 判定・分類の出力は
  10〜50 トークン、decode 数秒である。worker が枯渇させた資源をそもそも使わない。
- **`no_progress`（2026-08-10 実装）は worker を救わない。** あれは空回りを早く止める改良で、
  失敗を安く・読みやすくするが、受入率は上げない。再測の理由にはならない。

## 2. 次に測る対象 — 本番に入っていて未測定のもの

優先順位は「本番で既に使っているか」×「worker の失敗要因を踏まないか」で決める。

| 順 | 対象 | 本番状況 | worker の失敗要因を踏むか |
|---:|---|---|---|
| 1 | **判定・分類**（classify / filter / judge / split） | 段 0 で投入済み | 踏まない（出力 10〜50 トークン・材料は全部プロンプト内・ツール往復なし） |
| 2 | **抽出・要約**（agent-audit の extract / distill） | 段 0 で投入済み | 踏まない（同上。ただし出力はやや長い） |
| 3 | **JSON 契約の planner / evaluator** | 段 1 で投入済み | 一部踏む（出力が構造化され長い。プロンプトも大きい） |
| 4 | **候補生成 + 決定的検算**（grep パターン・パス候補・テスト名） | 未投入 | 踏まない（誤りが存在チェックで無害化される） |
| 5 | **read 調査 → 材料生成** | 段 3 で口はある | 踏む（ツール往復あり）。1〜4 の結果を見てから |

1 と 2 を最初の 1 本にまとめる。どちらも「材料は全部プロンプトにあり、短い答えを返す」
同型で、チェッカーの作りも共通にできる。

## 3. ハーネス — worker_eval の型を継ぐ

`judge_eval.py`（仮）として `tools/agent-tools/eval/` に置く。**worker_eval から変えないもの**:

- 決定的チェッカーだけで合否を出し、**走行中に判定役（LLM）を呼ばない**
- 同一タスクを反復し、`--model` の差し替えだけで別モデルを測れる
- 1 run 1 行の JSONL 台帳、失敗様式（`timeout` / `returned` / `empty` / `cli_error`）
- 本番との同一性を argv・プロンプト・上限で固定し、**argv は定義ファイルから読む**
  （写しは 2026-08-10 の当日にずれた。README に記録済み）

**変えるのは正解の出どころだけ。** worker は「テストが通るか」で正解が自明だったが、
判定・分類にはラベルが要る。3 つを組み合わせる。

1. **構成的に正解が決まる例**（第一選択）。入力を作るときに正解を決めておく——
   「この差分は docs だけを触る → 分類は `docs`」のように、生成規則から答えが従う形。
   T1 の「仕様 6 ケースで突き合わせる」と同じ発想で、ラベル付けの手間がゼロになる。
2. **本番ログからの採取 + 人の確認**。`agent-ollama --replay`（2026-08-10 実装）で
   記録済みプロンプトを集められる。**実入力の分布を代表する**のが利点で、
   §4 の確認とも材料を共有できる。ラベルは人が付ける（1 件数秒の作業を数十件）。
3. **クラウドモデルの出力を参照ラベルに使う**（補助）。一度だけ払って作れば以後ずっと
   使い回せる資産になる。**「判定役を使わない」原則は破らない**——禁じているのは
   *走行中に* 自己申告を合否へ混ぜることで、事前に固定したラベルは**データ**であって
   その場の判定ではない。ただし参照が誤っている可能性は残るので、1 と 2 で作った分と
   食い違う件は人が見る。

台帳に載せる指標は 4 つ。**一致率だけを見ない**——本番で効くのは「間違えないこと」より
「間違いを検出できること」なので、迷いの表明が使えるかまで見る。

| 指標 | なぜ見るか |
|---|---|
| 正解一致率 | 主指標。ラベルとの一致 |
| 空応答率 | 最初に潰した症状。設定を変えると最初に再発する |
| 自己一貫性 | 同じ入力を 3 回引いたときの割れ方。割れるなら多数決が効く余地がある |
| 壁時計（prefill / decode 別） | §4 の本題。本番プロンプト長での実測 |

自己一貫性と壁時計は `--replay` が既に出せるので、`judge_eval.py` はラベルとの
突き合わせに集中する。

## 4. 先に確かめる 1 点 — 9.3 秒は本番を代表しているか

引受範囲を「1 発判断は成立している」と判断した根拠は**中央値 9.3 秒で完走**である。
だがこれは所要時間であって正しさではなく、しかも**プロンプト長に強く依存する**。

- 判定・分類の decode は 10〜50 トークン ≒ 数秒。つまり 9.3 秒の大半は prefill である。
- 本番の planner / judge / adjudicate プロンプトは、charter・notes・context/*.md・依存成果を
  inline で束ねる。数千〜万トークン規模になる。
- prefill が仮に 100 tok/s でも、8000 トークンなら 80 秒。**9.3 秒の実行とは別の生き物**。

やること: 既存ログの `run_start.prompt_chars` の分布を役割別に出す。**LLM を 1 回も
呼ばずに済み、数分で終わる。** ここで本番プロンプトが 9.3 秒の実行より桁で大きいと
分かれば、§3 のハーネスは最初から**本番相当のプロンプト長**で測らなければならない
（小さい入力で測って「速い」と結論するのが、いま一番踏みやすい落とし穴）。

あわせて prefill / decode の実効スループットを 1 回測る（`llm_end` の `tokens_in` /
`tokens_out` / `duration_sec` から出る）。これが分かると、**任意の役割について
「その入力長なら何秒か」が机上で出せる**ようになり、測る前に落とせる候補が決まる。

## 5. モデル差し替えの扱い

worker が不合格でも、判定・分類で別モデルを試す価値は残る。ただし**順番を守る**——
先に qwen3.5:9b でラベル付きの成績を出し、それを基準線にする。基準線が無いまま
モデルを替えると、良くなったのか悪くなったのかが分からない（worker で 3 日溶かしたのと
同じ形）。ハーネスは `--model` の差し替えだけで動くので、基準線さえあれば追加コストは
実行時間だけである。

候補の優先は品質再点検 §6 のまま（a 現状維持 / b MoE は RAM 次第 / c 第 2 生成モデルは却下
/ d 埋め込み・リランカーは独立に評価）。**d は判定・分類の成績とは無関係に進めてよい**
——生成品質の問題を迂回する筋なので、1〜4 の結果を待つ理由が無い。

## 6. 進め方

| 段 | 内容 | 要るもの | 目安 |
|---:|---|---|---|
| 1 | 本番プロンプト長の分布と prefill/decode スループットを出す（§4） | 既存ログのみ。LLM を呼ばない | 数分 |
| 2 | ラベル付きの評価セットを作る（§3 の 1 → 2 の順。まず構成的な例で骨を作る） | 人の確認が数十件 | 半日 |
| 3 | `judge_eval.py` で qwen3.5:9b の基準線を出す | 実機の ollama | 1〜2 時間 |
| 4 | 結果で分岐: 通れば候補生成 + 決定的検算・事前トリアージへ / 割れれば判定系もクラウドへ戻す | — | — |
| 5 | 別モデル種別（埋め込み・リランカー）の評価 | 独立に進めてよい | 別途 |

段 1 は**今日できて、段 2・3 の設計を変えうる**ので必ず先に置く。

## 7. やらないこと

- **worker の再測**（§1）。`no_progress` もラウンド予算の縮小も受入率を上げる改良ではない。
- **段 4・5（edit セット / パッチモード）の再検討**。品質再点検 §4.2 のとおり取り下げ済みで、
  今回の失敗様式（書き終わらない）はパッチモードでも同じく踏む。
- **走行中の LLM 判定役**。ラベルは事前に固定したデータとして持つ（§3）。
- **本番ラインでの観察による品質測定**。3 日かけて何も出なかった方式に期待を掛け直さない。
- **基準線の無いモデル差し替え**（§5）。
