# Agent Dashboard 計画リビジョングラフ設計

## 背景

現在の工程グラフは `graph.json` の最新ノードと依存関係だけを描画する。再計画で追加された工程も初期計画と同じ見た目になり、`synth` 完了後に `t11-rebase-uxfix` が追加された理由をグラフから理解できない。

一方、依存関係のない追加工程へ因果線を引くと、実際には存在しない依存を表示してしまう。再計画は依存線ではなく、計画の版が切り替わった境界として表示する。

## 目的

- どこで計画が変更されたかをグラフだけで把握できる。
- 変更理由と変更内容を必要なときだけ確認できる。
- 追加、差し替え、再試行、fan-out、人の指摘などを同じ表示規則で扱う。
- 実在するタスク依存関係と、計画変更の因果を混同しない。

## 採用案: 計画の変遷と依存関係の2ビュー

工程画面を、目的の異なる2ビューへ分ける。

- **計画の変遷**: 初期計画と再計画を上から下へ時系列表示する。再計画では変更された工程だけを表示する。
- **依存関係**: 最新の全工程を従来のDAGとして表示する。線は `deps` に存在する依存関係だけを描画する。
- 再計画がないrunではビュー切替を表示せず、依存関係グラフだけを表示する。
- リビジョンまたは工程を選択すると、既存の右側詳細ペインへ内容を表示する。

今回の run では、初期計画の `synth` の後に次の境界を置く。

```text
初期計画（14工程）
    │
    ▼
計画を更新 #1 / 09:24:24
未解決事項を受けて3工程を追加
t11-rebase-uxfix → gate3-uxverify → synth2-dashboard
```

変遷ビューでは `synth` と `t11-rebase-uxfix` の間に依存線を描かない。実在する依存関係は依存関係ビューだけで表す。

### 既存案を見直す理由

当初はリビジョンと依存深度をともに横軸へ置いた。しかし実データでは再計画2回でも横幅が大きくなり、変更境界へ到達するまで横スクロールが必要になった。「なぜ計画が変わったか」と「何に依存するか」を別ビューへ分け、それぞれ一つの意味だけを持つ表示にする。

## 共通データモデル

UIは再計画の種類を分類しない。agent-flowのイベントを次の共通モデルへ正規化する。

```text
PlanRevision
  revision: number
  timestamp: string | null
  reason: string
  added: string[]
  replaced: { old: string, next: string }[]
  updated: string[]
  removed: string[]
```

この差分モデルで、検証失敗による再試行、data-driven fan-out、人の指摘による追加・差し替え、待機工程の更新を同じコンポーネントで表示する。

### agent-flow側の記録

新しいイベントでは、再計画時点で既に存在する情報を失わず記録する。

```json
{
  "kind": "replan",
  "iteration": 1,
  "reason": "未解決事項を修正して再検証する",
  "changes": {
    "added": ["t11-rebase-uxfix", "gate3-uxverify", "synth2-dashboard"],
    "replaced": [],
    "updated": [],
    "removed": []
  }
}
```

`inflight_amend` など既存工程を書き換えるイベントも同じ `changes` を持たせる。UIは `kind` ごとの表示分岐ではなく、`changes` の有無を基準に扱う。

### 既存runとの互換

- `planned.tasks` をリビジョン0へ割り当てる。
- 旧 `replan.added` を各リビジョンの `added` として読む。
- 理由がなければ「実行結果を受けて工程構成を見直しました」と表示する。
- 旧イベントから復元できない差し替え・更新は推測しない。
- イベントが欠けているノードは初期計画へ安全にフォールバックする。

## 表示構成

### 計画の変遷

- リビジョンを上から下へ時系列順に並べる。
- 初期計画は工程数と状態の要約を表示する。
- 再計画は「計画を更新 #N」「理由の要約」「変更件数」「時刻」を表示する。
- 再計画の中には、そのリビジョンで追加・差替・更新された工程だけを簡潔なノード列で表示する。
- 対象が多い場合は先頭だけを表示し、全件は右側詳細ペインで確認する。
- 色は警告色にせず、中立のアクセント色を使う。再計画は異常とは限らないためである。

### 依存関係

- 最新の全工程を左から右のDAGとして表示する。
- リビジョン境界や計画変更カードは混ぜない。
- タスク間の線は `deps` に存在する依存関係だけを描画する。
- 横幅が必要な場合のスクロールはこのビューだけに限定する。

### 詳細ペイン

タスク選択時は従来の工程詳細、変遷ビューのリビジョン選択時は計画変更詳細を表示する。

1. 変更理由
2. 追加・差し替え・更新・削除の件数
3. 対象工程名
4. 変更日時

対象が多い場合は最初の数件だけ表示し、残りは折りたたむ。

### アクセシビリティ

- ビュー切替とリビジョンはキーボードで選択可能にする。
- インタラクティブ要素には内容を要約したラベルと可視フォーカスを付ける。
- 色だけで区画や変更種別を区別しない。
- タブ順は上から下のリビジョン順にする。

## データフロー

1. agent-flowが計画変更イベントへ理由と差分を記録する。
2. dashboard main側が `events/*.jsonl` から計画変更だけを読み、`PlanRevision` に正規化する。
3. `flow:run` が `run.planRevisions` としてrendererへ返す。
4. rendererが同じ `run.planRevisions` から縦方向の変遷ビューを描画する。
5. 依存関係ビューは既存の `nodes` と `deps` だけからDAGを描画する。

イベント数は `max-iterations` により小さいため、専用キャッシュや新しい依存ライブラリは追加しない。

## エラー時の扱い

- 壊れたイベント行は従来どおり無視する。
- 未知の工程IDは詳細に表示できる文字列として扱い、グラフを壊さない。
- リビジョン番号が欠ける場合は時刻順で連番を付ける。
- 同じ工程が複数リビジョンに現れる場合は、最後の変更を現在所属するリビジョンとする。
- 変更理由が長い場合はグラフ上で省略し、詳細ペインでは全文を表示する。

## テスト方針

- main: 新旧イベントを `PlanRevision` へ正規化できる。
- main: added、replaced、updated、removed、理由欠落を同じ契約で扱える。
- renderer: 複数回の再計画が上から下へ時系列順に並ぶ。
- renderer: 変遷ビューは変更された工程だけを表示し、偽の依存線を描かない。
- renderer: 依存関係ビューは `deps` だけから線を描く。
- renderer: リビジョンを選択すると理由と変更差分を表示する。
- accessibility: ビュー切替とリビジョンがキーボード選択可能で、ラベルを持つ。
- regression: 再計画イベントのないrunはビュー切替を出さず従来のグラフを表示する。

## 実装順序

1. agent-flowの計画変更イベントに `reason` と `changes` を追加する。
2. dashboard main側へリビジョン正規化を追加する。
3. 現在の横方向リビジョン配置を、縦方向の変遷ビューへ置き換える。
4. 依存関係ビューをリビジョン表示なしのDAGへ戻し、ビュー切替を追加する。
5. リビジョン選択と既存の工程詳細を両ビューで接続する。
6. 新旧イベント、複数再計画、アクセシビリティを検証する。

## 見送るもの

- 再計画を疑似タスクとして依存線へ挿入すること。
- UI側で「再試行」「fan-out」「人の指摘」などを推測分類すること。
- 全イベントをグラフへ表示すること。
- リビジョンごとに独立した横スクロール領域を持たせること。
- 初期実装でリビジョンの編集機能を追加すること。

## 既存スキルとの関係

- `agent-flow`: 再計画イベントの正典と動的ワークフローの制約を確認する。
- `ui-designer`: 常時表示する要約と要求時に開く詳細を段階表示する。
- `brainstorming`: 依存線、疑似ノード、リビジョン境界の比較と意思決定を管理する。
