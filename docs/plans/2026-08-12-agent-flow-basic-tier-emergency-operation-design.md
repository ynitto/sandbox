# tier:basic を予算逼迫時の持久運転へ使う 設計

## 背景

main の `e46ad89`（計画承認ゲートと tier:basic のお膳立て）で、agent-flow に
`workloads.flow.tier=basic` を前提とした補償機構が入った。

| 補償 | 実装 | 効果 |
|---|---|---|
| 分解の細かさ | `tier_planning_granularity`: auto→finest | ノードを「1つの短い手順」まで割る |
| 計画指示 | `tier_planner_directive` | goal に対象パス・期待成果・確認方法まで書かせる |
| 評価指示 | `tier_evaluator_directive` | 能力不足の失敗を大きな作り直しでなく分割で対処 |
| 検証 | `tier_review_decision`: auto→常時ON | basic の成果を無検証で集約・終端しない |

一方、管理面（agent-dashboard）は basic を一度も宣言しない（`POLICY_TIERS` は
`small/medium/large`、3プリセットの最下段はすべて `small`）。**エンジンの補償機構は
管理面から到達する経路が無い。**

## 中心となる洞察: 予算が切れてからでは遅い

補償機構をよく見ると、basic 運転は判断役の**負荷を増やす**。

- finest 分解は並列ノード数を ×3 にする → planner の仕事が増える
- review 常時 ON → verify ノードが増える
- 能力不足由来の失敗を「より小さく明確な手順への分割」で対処 → evaluator の仕事が増える

つまり basic 運転とは「**作業を安く・判断を厚く**」への配分変更である。
予算が尽きてから切り替えると、**厚くすべき判断役を養う原資が残っていない**。
結果、判断役まで basic へ落ちて補償が崩れる（自己矛盾）。

したがって切り替えは**残予算があるうちに**行い、
**残った有償枠を planner / evaluator / verify のために温存する**。
これは緊急停止の代替（＝最後の悪あがき）ではなく、**持久運転**である。

```
残予算  100% ─────────── 20% ──────────── 0%（超過）
今日     medium           │ small（一律）  │ degrade / pause / stop
                          │
提案     medium           │ 持久運転       │ 作業は無償で継続可能
                          │  作業  → basic（ローカル・コスト0）
                          │  判断  → small/medium を維持（残予算はここへ）
```

作業系がローカル（`relative_cost: 0`）へ移ると消費速度が急落するため、
残予算は判断役のためだけに使われ、同じ残量がはるかに長く保つ。これが持久運転の原理である。

## 設計判断（確定）

### D1. 判断役は basic へ落とさない。落とさないために早く切り替える

`planner` / `evaluator` / `verify` は持久運転中も basic へ落とさない。
`judge` / `synthesize` / `split`（横断比較・フロー形状の決定）も同様に据え置く。
そのための原資を残すことが、切り替えを前倒しする理由そのものである。

| 役割・機能 | 平常時の下限 | 持久運転 | 理由 |
|---|---|---|---|
| classify / filter / extract / map | 単純作業 | 単純作業 | 変更なし |
| work / generate / reduce / retrieve | 軽量 | **単純作業** | finest 分解で 1 手順へ割れる（補償が効く） |
| verify | 軽量 | **軽量（据置）** | 検証を増やす方針なので検証役は落とさない |
| synthesize / judge / split | 標準 | **標準（据置）** | 横断比較は分解で代替できない |
| planner / evaluator | 標準 | **標準（据置）** | 補償機構そのものを支える |
| カスタムフローのノード | カタログどおり | **緩めない** | 無補償のため（後述 §制約） |

段は「workload ごとに 1 つのスカラー」ではなくなり、**作業段と判断段の組**になる。

### D2. basic はローカル原則・宣言は任意・未宣言なら発動しない

- basic 候補は原則ローカル（`relative_cost: 0`）。クラウド CLI を含む場合は
  **保存時に警告**（エラーにはしない）。
- `tiers.basic` の宣言は**任意**。ローカルモデルを持たない環境が普通に存在するため、
  未宣言なら持久運転は**発動しない**（平常どおり最下段 small で動く）。
- 現在の `profiles.save` は「方針が参照する tier に候補が無ければ入力エラー」だが、
  basic だけはこの規則の**例外**とする（任意の段＝無ければその段を飛ばす）。

理由: 必須にすると、ローカルモデルの無い端末で方針そのものが保存できなくなる。
持久運転は「使える環境では効く」上乗せであって、前提条件ではない。

### D3. 決定はエンジン側で行う（中央集権を持たない）

dashboard は**宣言と確認のビュー**に徹し、実行時の段の決定は各エンジンが
自分のサイクル先頭で行う。詳細と実現可能性は次章。

## D3 の実現可能性: 可能。ただし「1実装」を守る形でのみ

### なぜ可能か

必要な材料はすべて既に各エンジンから見えており、しかも**すでに毎回読んでいる**。

| 材料 | 置き場 | エンジンからの現状アクセス |
|---|---|---|
| 消費実績・上限・配分 | node-budget（共有台帳） | `_node_budget_state()` を `run_agent` ごとに呼んでいる |
| 宣言（方針・段の候補・pin） | agent-control | `_CONTROL_CACHE`（mtime 監視）で読んでいる |
| 現在の段 | agent-control | `agentcore.methods.current_tier()` で読んでいる |
| CLI ごとの枠・クォータ | node-budget | 同上（`allocation.agents` / `computed`） |

つまり**追加の I/O はほぼ発生しない**。今 dashboard の `profiles.decide()` が
やっている計算を、同じ入力でエンジン側が行うだけである。

決定的に重要なのは、`decide()` が**既に純関数**（時刻・usage・宣言だけを引数に取り、
ファイル I/O も乱数も持たない）だということ。純関数なら、
**同じ台帳を見る全エンジンが独立に計算しても同じ答えに着く**。
調整（コーディネーション）を決定性で置き換えられるので、中央の裁定者が要らない。

### 既存の不変条件との関係

現在の不変条件は「**エンジンは agent-profiles を読まない**。選択ロジックは dashboard の
1 実装に閉じる（柱1 / C2・C7）」。この条項の目的は**選択ロジックの 2 実装を防ぐこと**であって、
「dashboard が唯一の計算主体であること」自体が目的ではない。

`agentcore` は既に agent-flow / agent-project / agent-amigos が共有する Python ライブラリで、
`agentcli` / `methods` / `nodecontract` などの共通実装がここに 1 つだけ置かれている。
**決定関数を agentcore へ 1 実装として置けば、不変条件の目的は保たれる**——
プロセスが増えるだけで、実装は 1 つのままである。

不変条件は次のように書き換える:

> 選択ロジックの実装は 1 つ（`agentcore`）に閉じる。dashboard もエンジンも、
> その 1 実装を呼ぶ。**どちらも独自の解決経路を持たない。**

### 唯一の実装上の壁: JS と Python

dashboard は JS（Electron）、エンジンは Python。純関数を literal に共有できない。

| 案 | 実装 | 評価 |
|---|---|---|
| **決定関数を agentcore（Python）へ置き、dashboard は試算時にそれを呼ぶ** | 1 | ★★★ dashboard は既に `exec.shInWsl` で WSL 側へ日常的に問い合わせている（`agent-flow patterns --json` 等）。同じ流儀 |
| エンジンが `node scripts/resource-control.js --decide` を呼ぶ | 1 | ★☆☆ エンジン側ホストに node を要求する |
| JS/Python の 2 実装 + golden fixture で固定 | 2 | ★★☆ 本リポジトリに既存の idiom（`methods-source-hash.golden.json` 等）だが 2 実装は不変条件の趣旨に反する |

採用は第 1 案。dashboard の `profiles.decide()` は agentcore 呼び出しの薄い皮になり、
「試算」ボタンと実行時が**同じ関数**を通ることが保証される（今は別実装ではないが、
将来ずれる余地が消える）。

### 分散化がむしろ D1 を解決する

前版の設計では、planner / verify を basic から守るために dashboard が
`workloads.flow.agents.<purpose>` へ投函する必要があり、
「Dashboard の通常 UI からは `agents.<purpose>` を編集しない」という既存決定と衝突していた。

エンジン側で決定するなら、**この衝突は消える**。
purpose（planner / worker / verify）を知っているのはエンジン自身なので、
dashboard は「持久運転 ON・basic 候補はこれ」とだけ宣言し、
**役割ごとの段の割り振りはエンジンがローカルに適用する**。
`agents.<purpose>` への投函は不要になり、既存決定を破らずに済む。

### 分散化のトレードオフ（正直な評価）

| 論点 | 評価 |
|---|---|
| 可観測性 | control.json 1 か所を見れば分かる、が失われる。代わりに各エンジンが既に書いている `status/<tool>-<pid>.json` の `effective` を dashboard が集約表示する。**「申告」でなく「事実」を見る**ことになるので、むしろ改善 |
| 同時性 | エンジンごとに評価タイミングがずれる。ただし同じ入力なら同じ出力なので、ずれるのは適用時刻だけ。今も pull 型なので本質は変わらない |
| ヒステリシス・最小保持の state | 今は profiles.json の `state` に集約。分散後はエンジンごとに持つ。**これは正しい**——フラッピング防止はそのプロセスの安定性の話なので、プロセス単位で持つ方が意味が合う |
| dashboard 不在時 | 現在も「最後に適用した control が残る」だけ。分散後は**dashboard が居なくても追従し続ける**ので改善 |
| デバッグ | 「なぜこの段になったか」が分散する。`selection_reason` を status へ書く既存契約をそのまま使う |

## workload ごとの適用範囲（D3-b）

補償機構を持つのは現時点で agent-flow だけである。

| workload | 持久運転の既定 | 理由 |
|---|---|---|
| flow | **ON にできる** | `e46ad89` の補償が揃っている |
| project / amigos / audit | **既定 OFF（宣言で ON）** | 役割の区別はあるが、finest 分解・review 常時 ON に相当する補償が無い。補償を実装してから既定 ON へ |
| routine（agent-loop） | **セッション開始時のみ** | 対話 CLI は実行中に差し替えられない（既存の `restart_required` 契約どおり） |
| dashboard 内 AI | 検討外 | 画面内 AI は対話的で、人が待っている |

既存の `workloads.<wl>.on_exhausted` と同じく**機能別上書き**の枠組みへ載せるので、
契約の形は増やさない。

## 段階的な実装計画

各段階が単体で意味を持ち、途中で止めても壊れないように割る。

1. **宣言だけ先に足す**（契約・後方互換）
   `tiers.basic` を任意の段として受け付ける（未宣言なら飛ばす）。ローカル判定の警告。
   持久運転の ON/OFF を workload ごとに宣言できるようにする。まだ誰も読まない。
2. **決定関数を agentcore へ 1 実装で置く**
   `agentcore` に純関数として実装（入力: 台帳・宣言・現在時刻、出力: purpose 別の段と候補）。
   単体テストはここで固定する。
3. **agent-flow が自サイクル先頭で評価する**
   `_agent_for(purpose)` の解決へ組み込む。`e46ad89` の補償機構は
   「作業段が basic か」で発火するよう条件を合わせる。status の `effective` へ実績を書く。
4. **dashboard を試算と集約ビューへ寄せる**
   `profiles.decide()` を agentcore 呼び出しへ置き換え、
   「今どうなっているか」は status の集約で表示する（control からの再推測をやめる）。
5. **project / amigos / audit へ横展開**
   同じ agentcore 関数を呼ぶだけ。補償の実装状況に応じて既定を切り替える。

段階 1〜2 は既存動作を一切変えない。段階 3 で初めて挙動が変わる。

## 制約と未解決点

- **カスタムフローには補償が無い。** 補償は planner 経路（`_plan_strategy` / `_plan_initial`）
  にしか掛からず、`plan_strategy_user`（dashboard のワークフロービルダー）は人がグラフを
  固定しているので finest 分解も planner 指示も適用されない。
  よって**カスタムフローのノードは持久運転でも下限を緩めない**（PR #698 のカタログが
  そのまま防波堤になる）。将来、ビルダー側で「持久運転時はこのノードを分割する」と
  宣言できるようにする余地はある。
- **コストが逆転しうる。** finest ×3・review 常時 ON で呼び出し回数は確実に増える。
  basic 候補がローカルでない場合、持久運転は small より高くつく。D2 の警告で伝える。
- **判断役の消費はゼロにならない。** 持久運転でも予算は減り続ける（減速するだけ）。
  最終的な上限到達時の挙動は従来どおり `on_exhausted` が決める。
- **切り替え閾値の妥当性は未実測。** 既存の下段境界（おまかせなら残 20%）を初期値として
  流用するが、「判断役を養い切れる残量」が実際にどれくらいかは運用データが要る。

## 契約テスト観点

- CT1: `tiers.basic` 未宣言なら持久運転は発動せず、方針の保存もエラーにならない。
- CT2: basic 候補にクラウド CLI が含まれると保存時に警告が出る（保存は成功する）。
- CT3: 持久運転中、work / generate / reduce / retrieve が basic へ落ちる。
- CT4: 持久運転中も planner / evaluator / verify / judge / synthesize / split が basic へ落ちない。
- CT5: 持久運転は残予算が尽きる前に発動する（下段境界で切り替わる）。
- CT6: 同じ台帳・同じ宣言なら、どのエンジンが評価しても同じ段になる（決定性）。
- CT7: dashboard の試算とエンジンの実行時決定が同じ関数を通る。
- CT8: カスタムフローのノードは持久運転でも適格性が緩まない。
- CT9: 持久運転 OFF の workload は従来どおり一律の段で動く。
- CT10: 持久運転を解除すると元の段構成へ戻る（冪等・往復可能）。
