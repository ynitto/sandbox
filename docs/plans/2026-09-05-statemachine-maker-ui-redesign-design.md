# statemachine-maker UI 再設計

> 決定日: 2026-09-05  
> 対象: `tools/statemachine-maker`  
> 既存設計: `docs/plans/2026-09-04-statemachine-maker-design.md`

## 背景

現行画面には次の問題がある。

- 工程カードをその場で展開するため、編集するたびに全体の位置が変わり、縦スクロールが長くなる。
- 分岐行や2列フォームが固定幅を前提としており、文字のはみ出しや横スクロールが起きる。
- すべてのダイアログが同じ幅で、生成ファイルや実行ログには狭く、単純な入力には広い。
- 説明文が常時表示され、操作より説明を読む負担が大きい。一方で「中身」「結果の名前で」など、短くても意味が伝わらない文言がある。
- 色、密度、文字サイズ、種類別の色、任意 CSS の設定は、ワークフロー作成という主目的から外れている。

本変更ではデータ形式、コンパイル、保存、実行の契約を変えず、画面の情報設計と見た目だけを組み直す。

## 調査

一般的なワークフロー編集アプリの公式資料を比較した。

- Zapier Visual Editor はフロー全体を中央に保ち、選択した工程の設定を右サイドバーへ出す。
  https://help.zapier.com/hc/en-us/articles/16722578092429-Use-the-editor-to-build-and-view-your-Zap-workflows
- Power Automate の新デザイナーはカードを小さくして全体の移動を容易にし、設定を別ペインへ出す。
  https://learn.microsoft.com/en-us/power-automate/flows-designer
- n8n はグループを折り畳み、名前と短い説明だけで大きなフローを把握できるようにする。
  https://docs.n8n.io/build/understand-workflows/workflow-components/canvas-groups
- Make はよく使う標準項目を先に見せ、高度な項目を必要なときだけ開く。
  https://help.make.com/module-settings

共通する原則は「全体像を動かさない」「設定は選択対象の近くか専用ペインに置く」「高度な項目を初期表示しない」である。

## 検討した案

| 案 | 実装コスト | リスク | 保守性 | 狭幅対応 | 学習コスト | 推奨度 |
|---|---|---|---|---|---|---|
| A. コンパクトな縦型フロー＋右側編集パネル | 中 | 低 | 高 | 高 | 低 | ★★★ |
| B. 現行のカード展開方式を改善 | 低 | 中 | 中 | 中 | 低 | ★★☆ |
| C. 自由配置キャンバス＋編集パネル | 高 | 高 | 低 | 低 | 高 | ★☆☆ |

A を採用する。既存の工程順と分岐表示を保ったまま、カードの再配置と長い縦スクロールを解消できるためである。C は複雑な分岐には有利だが、ドラッグ、ズーム、接続線、座標保存、キーボード操作が新たに必要になり、現在の用途には過剰である。

## 情報構造

### 一覧

- 登録フォルダを左サイドバー、選択フォルダのワークフローを主領域に置く。
- 画面上の呼称は「ステートマシン」ではなく「ワークフロー」に統一する。
- カードは名前、目的の要約、工程数だけを表示する。
- 長い名前は2行まで表示し、パスは1行省略と `title` で全文を確認できるようにする。
- 720px 幅でもサイドバーと1列カードが収まり、横スクロールを発生させない。

### 編集

```text
┌ 戻る　ワークフロー名　　　操作を記録　テスト・実行　保存　… ┐
├─────────────────────┬────────────────────┤
│  1  ブラウザ               │ 工程 2                         │
│     申請一覧を開く          │ 実行方法                       │
│         ↓                   │ 工程名                         │
│  2  AI                     │ 操作内容                       │
│     内容を確認する  選択中  │ 次の工程                       │
│         ↓                   │                                │
│  3  コマンド               │ ────────────────── │
│     結果を保存する          │ ↑移動　↓移動          削除     │
└─────────────────────┴────────────────────┘
```

- 左のフローはコンパクトな工程カードと、その間の行き先だけを表示する。
- カードには番号、実行方法、2行以内の要約、対象、確認・記録の状態を表示する。
- カードを選ぶと右側約400pxの編集パネルへ設定を表示する。カード自身は展開しない。
- 900px未満では編集パネルを主領域全面に表示し、「フローへ戻る」で閉じる。
- 選択中の工程、エラー、成功は色だけでなく枠、文字、アイコンでも区別する。
- 工程間の追加ボタンは残す。種類選択は長いピル列ではなく、短いメニューとして開く。
- 完了・中止はフロー末尾に簡潔に表示する。

## 編集パネル

初期表示する標準項目は次だけとする。

1. 実行方法
2. 工程名
3. URL・アプリ・スキル・コマンドなど、実行方法固有の対象
4. 操作内容
5. 完了確認（対応する工程のみ）
6. 次の工程

工程記号、再試行回数、記録した生の操作は「詳細設定」に格納する。補助説明は、誤入力が起きやすい項目に1文だけ置く。説明を読まなくても、ラベルと入力例だけで通常操作を完了できるようにする。

分岐は文章として読める行にする。

```text
もし [回答が指定の言葉で始まる] [APPROVED] なら [完了]
```

狭いパネルでは条件、値、行き先を縦に積む。固定ピクセル幅の4列グリッドは使わない。

## ヘッダーと文言

ヘッダーの常設操作は「操作を記録」「テスト・実行」「保存」に絞る。「生成ファイル」「AIで補完」「実行環境」は `…` メニューへ置く。狭幅では「保存」以外をメニューへまとめる。

| 現在 | 変更後 |
|---|---|
| 新しいステートマシン | 新しいワークフロー |
| 中身 | 生成ファイル |
| AI | AIで補完 |
| 動かす | テスト・実行 |
| 種類 | 実行方法 |
| 名前（任意） | 工程名 |
| 次にどこへ行くか | 次の工程 |
| 結果の名前で | 回答が指定の言葉で始まる |
| 文章の条件で | 条件に当てはまる |
| 条件式で | 詳細条件 |
| 点検する | 構成を確認 |

内部形式を直接編集する項目だけは等幅フォントを使い、「詳細設定」であることを明示する。

## ダイアログ

全ダイアログを同じ760px幅にする方式をやめ、用途別にする。

| 用途 | 基準幅 | 構造 |
|---|---:|---|
| 操作の記録 | 640px | 入力と開始・終了を1列で表示 |
| 実行環境 | 720px | 通常設定、詳細設定、準備状況 |
| 生成ファイル | 1040px | ファイル一覧と内容表示 |
| AIで補完 | 960px | 操作と指示文プレビュー |
| テスト・実行 | 960px | 実行条件とログ |

- 幅は常に `viewport - 32px` 以下、高さは `viewport - 32px` 以下にする。
- ヘッダーと操作列を固定し、内容領域だけを必要時に縦スクロールさせる。
- `min-width: 0` と `min-height: 0` を各グリッド・フレックス子へ指定する。
- コード、パス、ログは折り返しを既定とし、ユーザーが横スクロールしなくても読めるようにする。
- フォームは720px未満で1列にする。スクロール可能な親を重ねない。
- エラーは対象の近くに `role="alert"` で表示し、長いエラーがダイアログ幅を広げないよう折り返す。

## 固定デザインシステム

カスタマイズ UI、`theme.json`、`custom.css` の読み込みと IPC を撤去する。既に userData にあるファイルは削除せず、以後無視する。

CSS変数はユーザー設定ではなく、内部デザイントークンとして残す。

| 用途 | 色 |
|---|---|
| 背景 | `#f6f7f9` |
| 面 | `#ffffff` |
| 本文 | `#172033` |
| 補助文 | `#566074` |
| 境界 | `#dde2ea` |
| 主操作 | `#2563eb` |
| 成功 | `#16784a` |
| 警告 | `#9a6700` |
| エラー | `#c93c37` |

- 工程の種類ごとの虹色はやめ、種類は中立色のラベルと名称で示す。
- 主要ボタン以外は白または透明背景にする。
- 本文14px、主要要約15px、ラベル13pxを基準にする。
- フォーカスリングは常に表示し、通常テキストは4.5:1以上のコントラストを確保する。
- 外部アイコン依存は追加せず、必要な操作アイコンは同じ線幅のインラインSVGに揃える。意味が伝わりにくい操作は文字ラベルを併記する。
- `prefers-reduced-motion` ではスクロールやトランジションを即時にする。

## コンポーネントとデータフロー

- `renderer.js` の `open` は「展開中の工程」ではなく「選択中の工程」として扱う。
- `editorHtml` はフロー領域と編集パネルを兄弟要素として描画する。
- 入力変更は従来どおりメモリ上の `spec` に即時反映し、明示的な「保存」でファイルへ書く。
- `model.js`、`store.js`、`recording.js` のデータ契約は変更しない。
- 見た目用の `theme.js`、IPC、preload API、renderer の状態と初期化を撤去する。
- 実行環境の設定と準備確認は残し、見た目設定から分離する。
- 既存の保存前検証、未保存表示、削除確認、実行ログの契約は維持する。

## エラーと空状態

- 保存エラーはフロー下部だけでなく、編集パネル上部の要約と該当項目付近に表示する。
- ダイアログ内の失敗はダイアログ内に残し、トーストだけに依存しない。
- 工程が無い場合は「最初の工程を追加」と実行方法の選択だけを示す。
- フォルダが無い場合は「フォルダを追加」と、そのフォルダにワークフローが保存されることを1文で示す。
- 長い説明で空状態を埋めない。

## テスト

1. 静的テスト
   - 見た目設定の IPC、preload API、custom CSS 差し込み口が残っていない。
   - 新しい文言と情報構造を固定する。
   - 不明瞭な旧文言が renderer に残っていない。
2. DOM・レイアウトテスト
   - 760px、980px、1440px 幅で `scrollWidth <= clientWidth` を確認する。
   - 全ダイアログを開き、境界が viewport 内に収まることを確認する。
   - 意図しない水平スクロールと、ダイアログ内の二重縦スクロールが無いことを確認する。
   - 狭幅で編集パネルが全面表示へ切り替わることを確認する。
3. 操作テスト
   - 工程の選択、編集、追加、移動、削除、分岐、保存を確認する。
   - キーボードでカード選択、編集パネルの閉じる操作、ダイアログ操作ができることを確認する。
4. 回帰テスト
   - 記録、生成ファイル、AI補完、構成確認、実行、保存の既存テストを通す。
   - Electron実機で起動し、コンソールエラーが無いことを確認する。

## 実装順序

1. 新情報構造とカスタマイズ撤去を失敗テストで固定する。
2. theme IPC・preload・renderer 初期化・設定 UI を削除する。
3. 一覧を左サイドバー構成へ変更する。
4. 編集画面をフロー＋編集パネルへ分離する。
5. 分岐、工程追加、ヘッダー、文言を整理する。
6. ダイアログを用途別レイアウトへ変更する。
7. 固定デザインシステムとレスポンシブ規則を適用する。
8. 760px・980px・1440px のレイアウト検査、機能テスト、実機煙試験を行う。

## 既存スキルとの関係

- `ui-designer`: 固定デザインシステム、アクセシビリティ、レスポンシブ基準に利用する。
- `agentic-search`: 競合UIの公式資料を反復調査し、共通パターンを抽出する。
- `webapp-testing`: 実装後の幅別レイアウトと操作回帰の検証に利用できる。
- 既存機能と重複する新しい機能は追加しない。
