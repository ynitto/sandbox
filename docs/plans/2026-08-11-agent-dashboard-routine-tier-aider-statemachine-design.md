# Agent Dashboard: 定常業務の段選択と Aider ステートマシン実行設計

> **更新（2026-08-11）**: 本設計の「Aider 用ステートマシン実行器」（dashboard in-process）は
> [tmux 化と agent-loop ハーネス設計](2026-08-11-agent-dashboard-routine-aider-tmux-harness-design.md)
> で agent-loop 側の `statemachine` サブコマンドへ移行した。段選択・限定ツール契約・
> statemachine-use 正典の判断は引き続き有効。

## 背景

定常業務の「今すぐ実行」は、全体設定で現在選ばれているエージェント CLI とモデルを使って
直ちに起動する。実行ごとに大・中・小などの段を選びたい場合も、全体設定を書き換える必要がある。

また、`statemachine-use` は対話 CLI がスキルを読み、ファイル操作やコマンド実行を行うことを
前提としている。Aider は headless なファイル編集 CLI として有効だが、対話セッションや任意の
ツール実行ループを持たない。そのままステートマシン実行文を送っても、スキルの読み込み、
コマンド実行、状態遷移を完遂できない。

## 要件

- 「今すぐ実行」の前に段を選択できる。
- 段の選択は今回の実行だけに適用し、全体設定や自動選択状態へ保存しない。
- 選択した段の候補は既存の段定義と予算・quota判定から決定する。
- 初版は `statemachine-use` の Aider 実行だけを対象にする。
- 将来、同じ実行境界へ他のスキルを追加できる。
- Aider が必要とするコマンドは、実行開始の承認範囲内で自動実行する。
- コマンドは作業フォルダを cwd とし、シェルを介さない argv、タイムアウト、ログ記録を必須とする。

## 検討した案

| アプローチ | 実装コスト | リスク | 保守性 | 拡張性 | 学習コスト | 推奨度 |
|---|---|---|---|---|---|---|
| Dashboard 管理のステートマシン実行器と限定ツールループ | 中 | 中 | 高 | 高 | 中 | ★★★ |
| ツール対応 CLI が監督し Aider へ編集を委譲 | 低 | 低 | 中 | 高 | 中 | ★★☆ |
| `tech-harvester` 専用処理 | 低 | 低 | 低 | 低 | 低 | ★☆☆ |

Dashboard 管理の実行器を採用する。ステートマシンの遷移を既存ハーネスへ集約したまま、
Aider に不足するツール実行だけを狭い契約で補える。監督 CLI 方式は実行主体が選択した段と
食い違い、専用処理は次のスキルで同じ問題を作り直す。

## 採用設計

### 実行前ダイアログ

既存の定常業務パラメータダイアログを拡張し、「今すぐ実行」では常にダイアログを開く。

- 段の選択欄を最初に表示する。
- 現在の `routine` ワークロードで有効な段を初期選択する。
- 各選択肢には段の表示名と、選択可能な先頭候補の `agent_cli / model` を表示する。
- 必須パラメータがある場合は同じダイアログの下に既存入力欄を表示する。
- 実行、キャンセル、Escape、二重送信防止は既存ダイアログの動作を維持する。

Renderer は `{ itemId, parameters, tier }` を IPC へ渡す。段は一回限りの値であり、
Renderer の状態、`profiles.json`、`control.json` へ保存しない。

### 段と候補の解決

main プロセスは受け取った段を信用せず、`profiles.resolveTier(config, tier)` で再解決する。

- 存在しない段、候補がない段、quota が枯渇した段は起動前に拒否する。
- 明示した段から別の段へ降格しない。`resolveTier` の既存仕様を維持する。
- 解決済み `{ agent_cli, model }` は今回の起動計画へだけ渡す。
- 段未指定の旧 IPC 呼び出しは従来の `routine` ワークロード解決を使う。

### 実行経路の選択

解決した CLI が対話実行を提供する場合は、既存の tmux・Terminal・WSL 起動経路を使う。
Aider には偽の `interactive` 定義を追加せず、`agents/aider.json` と
`agentCli.headlessCmd` を使う専用の headless 経路へ送る。

初版の headless 入口は `runSkill({ skillId, ... })` とし、受理する `skillId` は
`statemachine-use` だけに限定する。二つ目のスキルを追加するまではプラグイン登録基盤を作らず、
同じ入力・結果契約へハンドラを追加できる関数境界だけを維持する。

### Aider 用ステートマシン実行器

Dashboard が次のループを管理する。

1. `workflow.yaml` を検証し、現在状態と現在アクションだけを取得する。
2. アクション本文に正確なスキル名がある場合、インストール済みスキルから対応する
   `SKILL.md` と必要な参照ファイルを解決する。
3. Aider を readonly で呼び、現在アクションに必要なツール要求またはファイル割当要求を
   構造化応答として得る。
4. Dashboard が要求を検証して実行し、結果を次の Aider 呼び出しへ返す。
5. 編集対象が確定したら `--file`、参照対象は `--read` として明示し、Aider を write モードで呼ぶ。
6. アクションの最終出力を既存 `next_state.py` へ渡し、条件評価と遷移を確定する。
7. terminal、`NONE`、最大ステップ、再試行規則は workflow の既存設定に従う。

Aider に遷移先を選ばせず、次の状態のアクションも先読みさせない。

### 限定ツール契約

初版で許可する要求は次に限定する。

- `read_files`: 読み取り対象の相対パス。
- `write_files`: 編集対象の相対パス。
- `run`: `{ command, args, timeout_sec }`。シェル文字列は受け付けない。
- `final`: 現在アクションの出力契約に従った最終応答。

検証規則:

- cwd は登録済み作業フォルダへ固定する。
- 相対ファイルは作業フォルダ内へ正規化し、`..` やシンボリックリンクによる逸脱を拒否する。
- 実行ファイルは PATH 上、または解決済みスキルのディレクトリ以下に限定する。
- コマンドの標準出力・標準エラーは画面用に上限を設け、全量を実行ログへ保存する。
- timeout とツール往復回数に固定上限を設ける。workflow の再試行とは別に無限再試行しない。
- 実行した argv、cwd、終了コード、時間、生成・変更ファイルを履歴へ残す。

外部コマンドが作業フォルダ外へ副作用を起こさないことまでは OS sandbox なしに保証できない。
初版は argv・cwd・実行ファイル・パス検証と監査ログを境界とし、強制隔離が必要になった場合に
OS sandbox を追加する。

### Aider・Ollama 向けの文脈制御

- workflow 全体や全状態を毎回渡さず、現在のアクションと必要なスキルだけを渡す。
- 大きい入力ファイルはプロンプト本文へ展開せず、Aider の `--read` で渡す。
- 参照ファイルと編集ファイルを分離し、Aider が「チャットに追加されていない」状態を作らない。
- コマンド出力は短い要約とログパスを返し、大量出力を次のコンテキストへ入れない。
- Aider の timeout は CLI 定義を正とし、timeout 時は既存の transient 分類と workflow の
  再試行規則へ渡す。

この処理はツール不足を補うものであり、小型モデルの文脈理解や長文生成能力そのものは保証しない。

## データフロー

```text
今すぐ実行
  → 実行前ダイアログ（段 + パラメータ）
  → IPC { itemId, parameters, tier }
  → main で段を再検証・候補解決
    → interactive 対応 CLI: 既存起動経路
    → Aider + state-machine: headless skill runner
       → workflow/action/skill 解決
       → Aider tool request
       → argv 実行 / file allocation
       → next_state.py
       → terminal
  → 履歴・ログ・画面状態
```

## エラー処理

- 段・候補を解決できない: 起動せず、ダイアログ内に理由を表示する。
- スキルまたは参照ファイルを解決できない: 現在状態を失敗として記録する。
- 不正なツール要求、作業フォルダ外パス、シェル要求: 実行せず拒否理由を Aider と履歴へ返す。
- コマンド失敗・timeout: workflow の現在状態の再試行規則へ渡す。
- Aider の不正応答・空応答: agent CLI の既存エラー分類を使い、現在状態を失敗にする。
- `next_state.py` が `NONE`: workflow の `on_no_transition` に従う。
- Renderer の再読込後も結果を確認できるよう、実行履歴とログを正とする。

## テスト方針

- 実行前ダイアログに段が表示され、現在段が初期選択される。
- 段の選択とパラメータが一度だけ IPC へ渡され、設定へ保存されない。
- main が存在しない段、候補なし、quota 枯渇を拒否する。
- 明示段は同じ段内だけで候補を解決し、下位段へ降格しない。
- interactive 対応 CLI の既存経路を変更しない。
- Aider は headless 経路を使い、`--read` と `--file` が割当どおりになる。
- argv 実行、パス逸脱、シェル要求、timeout、出力上限、ログ保存を検証する。
- スタブ Aider とスタブコマンドで複数状態、再試行、成功終端、失敗終端を検証する。
- `tech-harvester-digest` 相当の fixture が fetch、Markdown生成、検証を完走する。
- agent CLI のゴールデンテストと定常業務の既存テストを通す。

## 実装計画

1. Cowork overview に実行可能な段と現在段を追加し、既存ダイアログへ段選択を統合する。
2. IPC / preload / Renderer の実行契約へ一回限りの `tier` を追加する。
3. main で `resolveTier` を使う起動上書きと、既存 interactive 経路への適用を追加する。
4. `statemachine-use` の検証・現在状態・条件遷移を呼ぶ headless runner を追加する。
5. Aider の構造化ツール要求、ファイル割当、argv 実行、ログ保存を追加する。
6. Aider 経路を `runStateMachine` から選択し、既存履歴・状態表示へ結果を接続する。
7. UI、候補解決、ツール境界、状態遷移の最小回帰テストを追加する。
8. 対象テスト、全テスト、ESLint、実画面で `tech-harvester-digest` を確認する。

## 既存スキルとの関係

- `statemachine-use`: workflow 検証、状態遷移、出力契約の正典として再利用する。
- `agent-cli-proxy`: Aider と Ollama の起動定義・エラー分類を再利用する。
- `failure-driven-development`: timeout、コマンド失敗、不正応答、パス逸脱のテスト設計と相性がよい。
- `webapp-testing`: 実行前ダイアログ、段選択、エラー表示の実画面確認に利用できる。
- `ponytail`: 初版は `statemachine-use` の一経路だけを追加し、汎用プラグイン基盤と OS sandbox は
  必要になるまで追加しない。
