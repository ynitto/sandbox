## 0. 結論を先に

いまの検索は **「1 ページ＝候補 200 件まで調べて、一致 50 件まで返す」** という決め方をしている。
キーワードで絞るほど 1 ページの一致数はゼロに近づき、利用者は**空の結果と「次へ」を何十回も
往復する**。これは走査量を減らして速さを買った結果であり、速さと網羅性のトレードオフが
そのまま利用者の指の運動になっている。

解決は 3 段で、**どれも単独で効き、上の段から順に入れられる**。

```
  いま                                   これから

  [検索]                                 [検索]
    ↓ 候補 200 件だけ調べる                 ↓ 検索中だけ生きるワーカーが候補を流し続ける
  一致 0 件 → 空表示                       見つかった端から一覧に積む
    ↓ 利用者が「次へ」                      ↓ 自動で最後まで（中止はいつでも）
  候補 200 件だけ調べる                    「12,480 件を調べました · 47 件一致」
    ↓ 一致 0 件 …（最大 100 往復）
                                         ＋ 段2: 本文を解析する前に安いふるいで落とす（実測 38 倍）
                                         ＋ 段3: 常設の索引を持ち、2 回目以降は即答（実測 4 ms）
```

| 段 | やること | 効果（実測） | 大きさ |
|---|---|---|---|
| 1 | ワーカーを検索の間だけ生かして逐次表示。「次へ／前へ」を廃止 | 空ページが原理的に消える。プロセス起動 400 回 → 保存先ごとに 1 回（起動費 約 60 秒 → 0.2 秒） | 中 |
| 2 | 本文解析の前に生バイトのふるい | 1 件あたり 4.20 ms → 0.07 ms（**38 倍**。1,000 件が 4.2 秒 → 0.11 秒） | 小 |
| 3 | 保存先ごとの常設索引（SQLite FTS5 trigram） | 2 回目以降は全件が **4 ms**、総件数も正確。索引の更新は変更分だけ | 大 |

実測は本書 §5（`tools/agent-audit` の実コードに合成データ 1,000 会話・67 MiB を食わせたもの）。

## 1. いまの仕組みと、手間の出どころ

処理は 2 段構えになっている。

- **候補列挙（`mode: inventory`）** — 本文を読まず、保存先・パス・更新日時だけを集める。最大 20,000 件。安い。
- **本文検索（`mode: search`）** — 候補 1 件ごとに**ファイル全体を解析**する。JSON/JSONL の構文解析、
  VS Code の追記ログの復元、`scrub_text` による秘匿処理まで通して初めて一致判定ができる。高い。

`sessionBrowser.js` の 1 ページはこう決めている（`search()` 内のループ）。

```js
// Inspect at most 200 candidates, and return at most 50 matches per request.
while (offset < page.candidates.length && records.length < 50 && inspected < 200) {
```

ここから、利用者が感じている手間がそのまま出てくる。

1. **一致率が低いほど空ページになる。** キーワードが 1% の会話にしか無ければ、1 ページの期待一致数は
   2 件。20,000 件の保存先なら「次へ」は **最大 100 回**。
   いまのテスト `tools/agent-app/test/session-browser.test.js:120` は、この挙動
   （200 件読んで 0 件・続きあり）を**仕様として固定している**。
2. **1 ページごとにプロセスを起動し直している。** バッチは最大 50 件で、バッチごとに保存先の数だけ
   `wsl.exe -d <distro> bash -lc python3 …` を起動する。1 ページ＝4 バッチなので、
   20,000 件を見るには **約 400 回**の起動。WSL 越しの起動は 1 回あたり数百 ms かかるため、
   実際の待ち時間の相当部分がこの起動コストになる。
3. **総件数が出せない。** `totalExact: false` のまま「続きがあります」としか言えない。
   利用者は「あと何回押せば終わるのか」が分からない。
4. **同じ会話を何度も解析し直す。** 条件を少し変えるたびに全部やり直す。索引が無いので、
   昨日と同じ会話に今日も同じ解析コストを払う。

## 2. 目標と、やらないこと

**目標**

- キーワード検索で、利用者の操作は「打つ」「待つ（見つかった端から出る）」「止める」だけにする。
- 取りこぼさない。ふるいは必ず**上位集合**（確実に不一致のときだけ落とす）。
- いつでも中止でき、中止しても位置を失わない。
- 元の履歴を書き換えない（読み取り専用の原則は維持）。

**やらないこと**

- 検索語の意味解釈（同義語・ベクトル検索）。いまの部分一致の意味論を変えない。
- 履歴ファイルの移動・正規化・書き戻し。
- 画面に説明文を増やすこと（CLAUDE.md の約束どおり、出すのは操作と状態の 1 行だけ）。

## 3. 段1 — 検索中だけのワーカーと逐次表示（「次へ」を無くす）

### 3.1 ワーカーは「検索の間だけ」生かし、結果を流す

保存先ごとに Python を **1 プロセスだけ**起動し、標準入出力で NDJSON をやり取りする。

```
JS →  {"mode":"stream","query":{…},"descriptors":[… 最大 2,000 …]}
Py →  {"hit":{…会話1件のメタと抜粋…}}
      {"hit":{…}}
      {"progress":{"scanned":1350}}
      {"done":{"errors":[…]}}
```

**プロセスの数と寿命**（アプリが動いている間ずっと居座る常駐にはしない）。

| | いま | 段1 |
|---|---|---|
| 同時に生きている数 | 保存先の数（通常 1、WSL が複数ならその数） | 同じ |
| 1 回の検索で起動する回数 | バッチごと。20,000 件なら**約 400 回** | **保存先の数だけ（＝ 1 回ずつ）** |
| 寿命 | バッチ 1 つ分 | **その検索が終わるまで**。完了・中止・条件の打ち直し・画面を閉じる、のどれでも確実に終了 |
| 常駐か | — | **常駐ではない**。検索していない間はプロセスがゼロ |

同時に走る検索は 1 件だけ（新しい検索を始めると前の検索は今と同じく殺す）。並列数は増えない。

起動費の実測（Linux。`bash -lc` 経由の起動が 154 ms、Python の import が 0.086 秒、常駐中の
メモリは 16 MiB）。いまの約 400 回はこれだけで **約 60 秒**になり、段2 で走査が 2.2 秒まで
縮んでも**起動費が支配してしまう**。Windows では `wsl.exe -d <distro> bash -lc …` を通るため
1 回あたりはさらに重い（実機で要測定）。ここを 1 回に畳むのが段1 の実利。

段3（常設索引）を入れて、索引をアプリ側（`userData`）に置ければ、**検索でワーカーを起動しなく
なる**（main プロセス内の SQLite 照会だけで完結し、ワーカーは索引更新のときだけ動く）。
Node 22 では `node:sqlite` が標準で使えることを確認したが、Electron 43 の同梱 Node で使えるかは
実機で確認が要る。使えない場合は索引を保存先側に置き、検索ごとに短命プロセスを 1 回起こす
（照会自体は数 ms なので、起動費だけが乗る）。

- 応答の 32 MiB 上限は「1 行あたり」に読み替える。行単位に解析するのでメモリは積み上がらない。
- 60 秒の上限は「1 窓（後述）あたり」に付け替える。止まったワーカーは殺して次へ。
- 付随して、`wsl.exe --list --quiet` の結果をそのまま保存先にしているため `docker-desktop` の
  ようなディストロまで走査している。会話の保存先が無いディストロは 1 回目の候補列挙が空になった
  時点で以後の対象から外す。

### 3.2 並び順を保つ「窓」

候補は JS 側で更新日時の降順に統合済み。これを **2,000 件ごとの窓**に切り、窓の中だけを
保存先へ並列に配る。窓が終わったら、その窓の一致を日時降順に整えて画面へ送る。
窓の境界が順序を保証するので、画面は**常に新しい順のまま下へ伸びる**。

### 3.3 IPC と画面の更新

```
main → renderer   sessions:search:hit       {requestId, sessions:[…]}
                  sessions:search:progress  {requestId, scanned, total, matched}
                  sessions:search:done      {requestId, matched, errors, partial}
```

- `sessions:search` は「開始」を返すだけにし、結果は上の 3 本で流す。`sessions:cancel` は現状のまま。
- 画面は先頭 100 件を描き、末尾までスクロールしたら次の 100 件を描く（描画の追加であって、再検索ではない）。
- 未描画の一致が 500 件を超えたら走査を一時停止し、消費されたら再開する（広い条件でも DOM が荒れない）。
- **「次へ」「前へ」は削除する。** 内部のページ機構（再開位置）は共有検索が使うので残す。

### 3.4 共有（他ノード）検索

`sharedSessionSearch.js` はページ方式のまま内部に残し、取得した分を同じ `hit` の流れへ合流させる。
1 回に 2 ノードという制限は維持する（相手の負荷を増やさない）。画面から見た挙動は同じ。

## 4. 段2 — 本文を解析する前の、安いふるい

一致しない会話に**構文解析・ログ復元・秘匿処理を払わない**。落とすのは「確実に不一致」と
言えるときだけ。

| 条件 | ふるい | 落として安全な理由 |
|---|---|---|
| キーワード | ファイルを生バイトで読み、needle の UTF-8 形・JSON エスケープ形（`\uXXXX`）・大小両形のどれも含まれなければ不一致 | 本文は必ずファイル中にそのいずれかの形で存在する。判断に迷う形（正規化違い等）は**通す** |
| 開始日（更新日時基準） | `mtime < since` なら不一致 | 実際の更新日時は必ず mtime 以下。逆向き（`until`）は安全でないので**ふるいに使わない** |
| エージェント・取得元・アーカイブ | 候補のパスと provider だけで判定 | いまも同じ判定を「解析した後」にやっている。前に出すだけ |
| Kiro（SQLite） | `LIKE` で会話行を先に絞る | 本文は DB 内にあり、SQL で同じ部分一致が引ける |

キーワードが空のときはふるいが効かないが、そのときは一致率が高いので画面はすぐ埋まる。

## 5. 段3 — 常設索引（トレードオフの根治）

### 5.1 置き場所と形

既定は**アプリ側**（`userData`）に 1 つ。検索がワーカーを起こさずに済み、保存先をまたいだ
総件数もそのまま出せる（`node:sqlite` が Electron 43 で使えることの確認が前提。使えなければ
保存先ごとにそのホーム配下の `~/.agent-audit/session-index.db` へ置き、検索のたびに短命の
ワーカーを 1 回起こす。どちらでも SQLite の形と更新の手順は同じ）。

```sql
CREATE TABLE files(                      -- 会話 1 件 = 1 行
  id INTEGER PRIMARY KEY, path TEXT UNIQUE, provider TEXT, size INT, mtime REAL,
  native_id TEXT, repo TEXT, model TEXT, title TEXT,
  created_at REAL, updated_at REAL, archived INT, messages INT, body TEXT);
CREATE VIRTUAL TABLE texts USING fts5(   -- 本文は files 側に 1 つだけ持つ（外部コンテンツ）
  body, content='files', content_rowid='id', tokenize='trigram');
CREATE INDEX i_updated ON files(updated_at);
```

`trigram` トークナイザを選ぶのは、**いまと同じ部分一致**（日本語の語中一致を含む）を保つため。
語分割を入れると検索結果の意味が変わってしまう。

### 5.2 更新（変更分だけ）

`mode: index` を追加する。候補列挙（安い）の `(path, size, mtime)` を索引と突き合わせ、
**新規と変更だけ**解析して差し替え、消えたパスの行を削除する。
検索画面を開いたときと、アプリが暇なときに背景で走らせ、進捗を状態の 1 行に出す。

### 5.3 索引が無い・古い間（ハイブリッド）

索引済みの範囲は SQL で即答し、**まだ索引に無い候補だけ**段1＋段2 の走査で埋める。
初回でも画面は今より速く、索引が育つほど走査はゼロに近づく。索引を作らない設定も残す
（その場合は段1＋段2 の動作になる）。

### 5.4 上限と捨て方

- 1 会話あたりの索引本文は 512 KiB まで（超過分は索引せず、その会話は走査対象に残す）。
- DB 全体の目安 1 GiB。超えたら**更新日時の古い会話から索引を落とす**（消えるのは索引だけで、
  会話は走査で見つかる）。
- 格納するのは `scrub_text` 済みの本文だけ。索引は各ホームの中に閉じ、共有しない。
- FTS5 や trigram が使えない環境では、`files.body` の `LIKE` 走査に落とす（解析を省けるので十分速い）。
- 2 文字以下のキーワードは trigram が使えないため、同じく `LIKE` で引く（実測 19 ms / 1,000 会話）。

### 5.5 実測（`tools/agent-audit` の実コード＋合成データ 1,000 会話・67 MiB）

| 測ったもの | 結果 |
|---|---|
| いまの本文検索（全件解析） | 4.20 秒 / 1,000 件（**4.20 ms/件**） |
| 段2 のふるい → 残りだけ解析 | 0.11 秒 / 1,000 件（ふるい **0.07 ms/件**、**38 倍**速い） |
| 段3 の索引作成（初回・全件） | 6.5 秒 / 1,000 件（2 回目以降は変更分だけ） |
| 段3 の検索（3 文字以上・上位 50 件＋抜粋） | **3.8 ms** |
| 段3 の検索（2 文字・`LIKE` 走査） | **19 ms** |
| 索引の大きさ | 本文 67 MiB に対し DB 94.8 MiB（本文 1 + 索引 0.42） |

20,000 件へ単純に伸ばすと、いまの全件走査 84 秒に対し、ふるいで 2.2 秒、索引なら数 ms。
（実機の WSL 越しではディスクが遅い分これより落ちるが、比率は変わらない）

## 6. 画面（承認をいただきたい形）

借りる作法: 検索画面（`#session-search`）の既存構造をそのまま使う。状態の 1 行は
いまの `#search-status`（`.sub` + `.row` + `中止` ボタン）を使い、部品は足さない。
**変更は「次へ／前へ」を消し、状態の 1 行に走査の進みを出すことだけ。**

```text
会話を検索                                                        [閉じる]
[ 会話のタイトル・内容を検索                                            ]
[すべてのエージェント v] [日付指定なし v] [すべてのリポジトリ    ]
[絞り込み v] [共有も検索] [条件を解除]
3,200 / 12,480 件を調査 · 18 件一致                                 [中止]
--------------------------------------------------------------------------
検索結果                                  | 会話のプレビュー
請求書の取り込みが落ちる                   | 会話を選ぶと内容を確認できます
claude · CLI                              |
sandbox · 09/14 18:20                     |
…invoice の取り込みで例外が…              |
                                          |
月次レポートの集計漏れ                     |
copilot · VS Code                         |
report-repo · 09/13 10:42                 |
…集計の対象月が…                          |
（見つかった端から下へ伸びる。押す操作なし） |
```

状態の 1 行は 3 つの言い方しかしない。

```text
走査中   3,200 / 12,480 件を調査 · 18 件一致                        [中止]
完了     12,480 件を調べました · 47 件一致
索引あり 47 件一致（全 12,480 件）              ← 段3 導入後。総件数が正確になる
```

（索引を作っている間だけ、同じ 1 行に `索引を更新しています 4,200 / 12,480 件` を出す）

## 8. 段取り（PR の分け方）

1. **PR1（段1）** — 検索中だけのワーカー＋逐次表示、「次へ／前へ」削除。ここで利用者の手間は消える。
2. **PR2（段2）** — ふるい。PR1 の「最後まで走る」を現実的な時間に収める。
3. **PR3（段3）** — 常設索引とハイブリッド。総件数が正確になり、2 回目以降が即答になる。

段1 だけでも利用者の操作は解決する。段2 まで入れれば体感も解決する。段3 は「毎回解析し直す」
という構造そのものを畳む。

## 9. 残る判断（承認をいただきたい点）

1. 画面は §6 の形でよいか（「次へ／前へ」を消して、状態の 1 行に集約する）。
2. 段3 の索引を既定で作ってよいか。作る場合の置き場所はアプリ側（`userData`）、上限は
   1 会話 512 KiB / 全体 1 GiB でよいか。
3. 段1 → 段2 → 段3 の順に 3 本の PR で出す進め方でよいか（段1 だけで止める判断もできる）。
