# Agent Dashboard 相談導線の領域別再配置 設計

## 背景

柱2（人介在の最適化）／柱3（資源効率）・C7・C9・C10 に効く。相談の対象フォルダを領域ごとの
既存状態から一意に引き、相談で使うエージェントとモデルを実行方針の配下へ入れて利用量を実測する。

相談の導線は現在 3 系統ある。本設計が扱うのは 1 つ目だけである。

| 導線 | 実体 | 本設計の対象 |
|---|---|---|
| 「この作業を相談」（ヘッダー） | 選んだフォルダで対話型エージェント CLI を外部ウィンドウへ開く | 対象 |
| 「相談する」（サイドバー） | Doctor。画面から渡した文脈を読み取り専用で診断する | 対象外 |
| 「AIに相談」（要対応の項目別） | 対象が 1 件の need に固定された Doctor 呼び出し | 対象外 |

「この作業を相談」はヘッダーに 1 組だけ置かれ、プロジェクト領域だけを前提に組まれている。
4 領域のうち 3 領域で意図どおり動かない。

1. 対象フォルダが `selectedProjectFolder()` に固定されている
   （[renderer.js:1336](../../tools/agent-dashboard/src/renderer/renderer.js:1336)、
   [renderer.js:2395](../../tools/agent-dashboard/src/renderer/renderer.js:2395)）。
   ワークフローとミッションは左ペインでフォルダを選ぶ領域ではなく、
   `alignAreaSelection` の対象一覧も持たない
   （[renderer.js:1589](../../tools/agent-dashboard/src/renderer/renderer.js:1589)）。
   その結果、前の領域で選んだプロジェクトや作業フォルダが選択として残ったままボタンが活性になり、
   **画面で見ている対象とは別のフォルダで CLI が開く**。無効になるのではなく、黙って違う対象を掴む。
2. 定常業務は左ペインの作業フォルダ選択が `state.selectedDir` を共有するため起動はできるが、
   起動先候補はプロジェクトの repos レジストリ前提で計算される
   （[agent.js:242](../../tools/agent-dashboard/src/features/agent-project/main/agent.js:242)）。
   レジストリを持たない作業フォルダでは候補が 1 件になり、しかも「プロジェクト（状態リポジトリ）」と
   名乗る。対象の実体と表示名が一致しない。
3. `openInteractiveChat` が `workload` を渡さないため、agent-control の実行方針を素通りする
   （[agent.js:350](../../tools/agent-dashboard/src/features/agent-project/main/agent.js:350)）。
   さらに次段のアプリ設定層（`agent.cli` / `agent.model`）には**編集画面が無い**。全体設定の画面内AI
   パネルは待ち時間だけを扱い、「エージェントとモデルは実行方針から自動設定されます」と明言している
   （[orchestration.js:828](../../tools/agent-dashboard/src/renderer/sections/orchestration.js:828)）。
   実際には相談だけが実行方針へ接続されておらず、プロジェクト設定か既定の `kiro` へ落ちる。
   宣言と挙動が食い違い、消費も `dashboard` workload へ記帳されない。

`workloads.dashboard` と purpose 別解決の契約は
[統一実行方針設計](./2026-08-11-agent-dashboard-unified-execution-policy-design.md)で定めており、
下書き・Doctor などの画面内 AI は既に接続済みである。相談だけが接続から漏れている。

## 置き換える既存判断

相談コントロールを全領域共通のヘッダーへ 1 組だけ置く現在の構成を廃止する。ヘッダーは
プロジェクト領域の見出しと同居しているのに、領域を切り替えても同じ 1 組が残り続ける。左で選んだ
対象と右の主題を一致させるという
[ワークフロー実行画面再設計](./2026-08-14-agent-dashboard-workflow-run-ux-redesign-design.md)の
情報構造と噛み合わない。

ヘッダーという置き場自体を否定するわけではない。プロジェクト領域に限れば、対象は左ペインで選び
リポジトリ選択もヘッダーにあるため、ヘッダーは対象を決める場と一致している。廃止するのは
「1 組をすべての領域で使い回すこと」であり、プロジェクト領域での配置は据え置く。

## 採用方針

| アプローチ | 実装コスト | リスク | 保守性 | 拡張性 | 学習コスト | 操作性 | 推奨度 |
|---|---|---|---|---|---|---|---|
| A. 共通コントロールを領域別の対象フォルダ解決へ接続 | 中 | 低 | 高 | 高 | 低 | 高 | ★★★ |
| B. 領域ごとに独立した相談ボタンを実装 | 中 | 中 | 低 | 低 | 中 | 中 | ★★☆ |
| C. ヘッダー 1 組のまま活性条件だけ緩める | 低 | 高 | 中 | 低 | 低 | 低 | ★☆☆ |

案 A を採用する。ボタン、フォルダ選択、起動処理は 1 実装のままとし、対象フォルダを供給する
アダプターだけを領域ごとに用意する。案 C は対象フォルダの決め方が領域で違うという本質を
扱えず、無効の理由も説明できない。案 B は同じ操作が 4 実装へ分かれ、片方だけが育つ。

## 対象フォルダの解決

領域ごとに「その領域で対象を決めている既存の状態」を唯一の入力にする。相談のために新しい
選択状態を持たない。

| 領域 | 対象フォルダの出どころ | 起動先候補 | 既定 |
|---|---|---|---|
| プロジェクト | 選択中プロジェクトの repos レジストリ | 状態リポジトリ＋このノードにクローンがある成果物リポジトリ | 状態リポジトリ |
| ワークフロー | 実行フォームの対象フォルダ入力、または選択中 run の cwd | 入力値＋既存の cwd 履歴 | 現在の入力値 |
| ミッション | 依頼フォームの作業フォルダ入力、または選択中ミッションの workspace | 入力値＋既存の cwd 履歴 | 現在の入力値 |
| 定常業務 | 左ペインで選択中の作業フォルダ | 選択中の作業フォルダ | 選択中の作業フォルダ |

プロジェクトの候補計算は現在の実装を維持する。レジストリに載っていてもクローンが無いものは
消さずに非活性と理由付きで並べる既存の扱いを変えない。

ワークフローとミッションは自由入力を持つ領域なので、入力欄が空のときはボタンを無効にし、
「対象フォルダを入力してください」と文字で示す。入力途中の未確定パスで起動しない。

定常業務は候補が 1 件なので選択コントロールを出さず、対象フォルダ名だけを表示する。

領域をまたいで同じフォルダを選んだ場合は同じセッションへ再 attach する。セッションキーは
現在の `<cli>:<cwd>` を維持し、領域名を混ぜない。領域が違っても作業対象が同じなら会話は 1 本にする。

## コントロールの配置

配置規則を 1 つに定める。**相談ボタンは、その領域で対象フォルダを決めているコントロールの隣に置く。**
領域につき 1 組だけ置く。

| 領域 | 配置 |
|---|---|
| プロジェクト | ヘッダーの現在位置を維持する。対象は左ペインで選び、リポジトリ選択はヘッダーにあるため、決定の場と一致している |
| ワークフロー | 作成画面の対象フォルダ入力の直下。run 詳細画面では、その run の cwd を対象としてヘッダー操作群へ並べる |
| ミッション | 依頼フォームの作業フォルダ入力の直下。ミッション詳細では workspace を対象としてヘッダー操作群へ並べる |
| 定常業務 | 作業タブの対象フォルダ表示の隣 |

ヘッダーの共通コントロールは、プロジェクト領域以外では描画しない。領域を切り替えたときに
前の領域の対象が残らないようにする。

配置と同時に、相談で実際に使うエージェントとモデルを起動前に読めるようにする。ボタン近傍へ
実効エージェント名、モデル名、決定の由来を文字で表示する。起動してからトーストで初めて知る
状態にしない。

## エージェントとモデルの決定

相談は `workload: dashboard`、`purpose: chat` として解決する。ボタンの隣に選択 UI は設けない。

既定は実行方針が決めた値とする。`resolveAgent` の解決順
（[agent.js:85](../../tools/agent-dashboard/src/features/agent-project/main/agent.js:85)）は変更せず、
相談が `workload` を渡していない現状だけを直す。

カスタマイズは全体設定 ＞ アプリへ「相談で使うエージェント」を 1 組だけ置く。既定値は「実行方針に
従う」で、明示的に選んだときだけ固定する。この入力の保存先は `control.json` の
`workloads.dashboard.agents.chat` とし、`agent_cli` と `model` を書く。設定用のキーを新設しない。

保存先を control 側に寄せるのは、実行方針とアプリ設定という 2 つの決定元を作らないためである（C7）。
`null` と空文字は「この機能では指定しない」印として既に扱われている
（[agent.js:67](../../tools/agent-dashboard/src/features/agent-project/main/agent.js:67)）ので、
「実行方針に従う」は空を書くことで表現でき、下位の解決へそのまま委ねられる。

アプリ設定層（`cfg.agent.cli` / `cfg.agent.model`）は編集画面を持たないまま残っているため、この設計で
新たに使わない。既存の値が入っている環境では従来どおり下位フォールバックとして働く。

画面内AI の待ち時間は全体設定 ＞ エージェントに残る。相談のエージェント選択をアプリへ置くと画面内AI
の設定が 2 か所に分かれるが、相談は領域をまたぐアプリ全体の操作であり、待ち時間はエージェント呼び出し
一般の設定であるため、置き場を分ける。両パネルから互いへの参照を 1 行ずつ張り、片方だけを見て
設定し終えたと誤解させない。

相談の消費は `dashboard` workload として node-budget へ記帳し、利用量画面へ含める。対話セッションは
終了時刻が確定しないため、記帳は起動時の 1 件とし、トークン実測は台帳の既存経路に委ねる。

## エラー処理

- 対象フォルダが未確定の領域ではボタンを無効にし、理由を文字で示す。無効の見た目だけで済ませない。
- 実在しないパスは起動前に弾く。既存の存在チェックを維持する。
- 起動先候補の取得に失敗しても既定フォルダで開ける。候補が出せないことを相談できない理由にしない。
- 実行方針で指定されたエージェントの定義が見つからない場合、黙って別 CLI で起動しない。警告を出し、
  由来表示に「指定のエージェントが見つかりません」を反映する。
- 外部ターミナルの起動失敗は、対象フォルダとエージェント名を含めて表示する。
- 起動処理中はボタンを無効化し、二重起動を防ぐ。

## 用語

共通ラベルは「この作業を相談」を維持する。要対応の項目別ボタン「AIに相談」は対象が 1 件の need で
あり別物なので据え置く。`index.html` に「AIに相談」を出さない既存の文言テストを維持する。

## 既存テストへの影響

`test/user-centered-ui.test.js` は、`btn-cli-chat` がプロジェクトヘッダーの内側にあり `disabled` で
出荷されることを検査している。理由として「相談は対象が分かるプロジェクトヘッダーに置きます」と
書かれており、本設計の配置規則はこの理由をそのまま 4 領域へ広げたものである。検査は次へ差し替える。

- ヘッダーの 1 組はプロジェクト領域の対象と対にする（現在の検査を領域限定として残す）。
- 残る 3 領域については、対象フォルダを決めるコントロールと相談ボタンが同じ節にあることを検査する。

`test/adhoc-flow.test.js` の設計セッション検査、`test/amigos.test.js` の作業フォルダ必須検証、
`test/portal-home.test.js` の領域とタブの対応は、本設計では変更しない。

## アクセシビリティとレスポンシブ

- ボタンとフォルダ選択は 44px 以上の操作領域を持つ。
- ラベルを placeholder だけで表現しない。
- 無効理由と実効エージェントは `aria-live` で通知する。
- 狭幅ではボタンとフォルダ選択を縦積みにし、横スクロールを発生させない。
- 375px、768px、1024px、1440px を確認幅とする。

## テスト

1. 4 領域それぞれで、その領域の対象フォルダが相談の起動先になる。
2. プロジェクトでは repos レジストリの候補が並び、クローンが無いものが理由付きで非活性になる。
3. ワークフローとミッションで入力が空のときボタンが無効になり、理由が文字で表示される。
4. 定常業務では選択中の作業フォルダが対象になり、プロジェクト前提の候補計算を通らない。
5. 領域を切り替えると、前の領域の対象フォルダが残らない。
6. 相談の起動が `workload: dashboard` / `purpose: chat` で解決される。
7. 全体設定の「相談で使うエージェント」が既定の「実行方針に従う」のとき、実行方針の決定が実効値になる。
8. 明示的にエージェントを選ぶと `control.json` の `workloads.dashboard.agents.chat` へ保存され、
   それが実効値になる。設定用の別キーを作らない。
9. 「実行方針に従う」へ戻すと空が書かれ、下位の解決へ委ねられる。
10. 実効エージェント、モデル、由来が起動前に表示される。
11. 実行方針で指定されたエージェントの定義が無い場合、別 CLI で黙って起動しない。
12. 同じフォルダなら領域が違っても同じセッションへ再 attach する。
13. 相談の起動が `dashboard` workload として利用量へ記帳される。
14. 実在しないパス、候補取得失敗、外部ターミナル起動失敗を安全に扱う。
15. ボタンとフォルダ選択が 44px 以上の操作領域を持つ。
16. 375px、768px、1024px、1440px で不要な横スクロールがない。
17. 既存のプロジェクト相談、要対応の項目別相談、Doctor、定常業務のウィンドウ起動が回帰しない。

## 非目標

- 相談の会話内容の取り込み、記録、要約
- 設計セッション（設計書を成果とするラウンド制の経路）との統合。相談は対話 CLI を開くだけであり、
  成果物契約を持たない
- Dashboard 内へ埋め込むチャット UI。外部ウィンドウ方式を変えない
- エージェント CLI の選択 UI を相談ごとに設けること
- node-budget、agent-control、agent-profiles の契約変更

## 実装計画

1. 対象フォルダを供給する領域別アダプターを定義し、相談コントロールの唯一の入力にする。
2. ヘッダーの共通コントロールをプロジェクト領域限定にし、他 3 領域へ配置規則どおり組み込む。
3. `openInteractiveChat` と起動先候補の取得へ `workload` と `purpose` を渡す。
4. 全体設定 ＞ アプリへ「相談で使うエージェント」を追加し、`control.json` の
   `workloads.dashboard.agents.chat` へ保存する。画面内AI パネルとの相互参照を張る。
5. 実効エージェント、モデル、由来の事前表示を追加する。
6. 無効理由の文字表示と `aria-live` 通知を追加する。
7. 相談の起動を `dashboard` workload の利用量へ記帳する。
8. `test/user-centered-ui.test.js` の配置検査を領域別の検査へ差し替える。
9. 領域別の対象解決、実行方針の優先順、設定の保存先、セッション再 attach、レスポンシブのテストを
   追加し、既存テストと ESLint を実行する。

本設計は[ワークフロー実行画面再設計](./2026-08-14-agent-dashboard-workflow-run-ux-redesign-design.md)の
作成画面と run 詳細画面の分離を前提に配置を決めている。そちらが未実装のまま着手する場合は、
ワークフロー領域の配置を現在の実行タブ内へ読み替える。

## 既存スキルとの関係

- `ui-designer`: 配置規則、44px 操作領域、無効理由の文字表示、由来表示へ反映した。
- `contract-driven-development`: 領域別アダプターの入出力契約と workload / purpose の受け渡しに利用できる。
- `failure-driven-development`: 未確定フォルダ、定義欠落エージェント、起動失敗の境界設計に利用できる。
- `webapp-testing`: 4 領域の起動経路と狭幅表示の実画面検証に利用できる。
