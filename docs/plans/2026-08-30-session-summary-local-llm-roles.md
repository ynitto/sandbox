## 1. 結論

**e4b で代替できない役割は 2 つに絞れた。** レビュー（RV 1/3。12b は 3/3 なので割り当てで
解ける）と、regex の生成（CG1。実行結果を見せて投げ直しても戻らない）。

**この日の最後に 3 つ目が出て、その場で閉じた。** 統合役が**依存の申告した欠落を運ばない**
（SY2 0/5）。手当てを決める前に本番で欠落がどこに載るかを読むと、`{"ok": false}` の依存は
failed になって集約役まで届かず、done の依存が構造化して申告できるのは契約の `warnings` /
`issues` だけと分かった。**同じ事実を散文から `warnings` へ移すだけで 0/5 → 3/5**、
さらに機械（`carry_dependency_gaps`）が転記して **5/5**。閉じ方は他の 4 例と同じ型である。
散文にしか無い欠落だけは今も 0/5 で、これは機械にも手が無い（本文から抽出する規則が書けない）。

**それ以外の「落ちる」はすべて、モデルではなく形の問題だった。** 直し方は 1 つの型に
収まる——**ゲートで 1 度言わせ、それでも残るぶんは機械が形を直す**。この日だけで 4 例:

| 何が落ちていたか | 機械が何をしたか | 実測 |
|---|---|---|
| split の後ろに静的な map/reduce を書く | 下流ごと外して運ぶ | PL3 0/3 → **3/3** |
| 1 行の修正を「読む→特定→直す→適用」に割る | 同じファイルを触る成果ノードを畳む | PL4 1/3 → **3/3** |
| 予算を超える組合せを選ぶ | 転記だけさせて総当たりは機械が回す | PR1 0/3 → PR1P **3/3** |
| `filter` に使われない `tie_break` を書く | その 1 語だけ落として decision は運ぶ | PL6 1/3 → **3/3** |
| 依存が申告した欠落を統合結果から落とす | 依存の `warnings` を成果へ転記する | SY2W 3/5 → SY2P **5/5** |

**指示文の書き換えで動いた例は 1 つも無い。** モデルは 5 例とも、作り直しを命じられても
同じ形を書き続けた。動いたのは運搬（機械が形を直す）を足したときだけである。
統合役ではもう 1 つ効いた手がある——**事実を載せるチャネルを変える**（散文 → 契約の
`warnings`）だけで 0/5 が 3/5 になった。文面ではなく、置き場所を変えている。

**捏造は、疑った 3 面のどこでも起きなかった。** 検証役（V1〜V3）・抽出役（EX1F）・取得役
（RT1・RT2）は、いずれも本番の機械検査が器しか見ない＝捏造すれば素通りする面だが、実測では
35 回の走行で 0 件。該当が無い問い（RT2）でも空の `sources` を返し、それらしい source を
作らなかった。
PV1（撤去された charter verifier）が捏造したのは道具が無かったからではなく、
**手元に材料が何も無かった**からである——材料がプロンプト内にあれば e4b は「無い」と言える。

**測定面は 11 → 17 に増えた**（`coverage.json` の direct）。増えたのは verify・classify・
map・extract・retrieve・synthesize の 6 面。未測定は 22 面（§6 に棚卸し）。

**そして最後に測った 2 面が、それまでの数字の前提を崩した。** `retrieve` を測るために
起動形を本番から取り直したところ、ハーネスは定義の `command` だけを読んでいて、profile が
足す道具とラウンド上限を落としていた（§5-6）。**base へ振り替わる面は道具ループの中で走る**
——直して引き直すと `classify` は 5/5 → 4/5、`map` は 5/5 → **1/5** へ落ちた。道具を持った
e4b は、シェルで解こうとして失敗を重ね、最後に散文とフェンスで返す。本番の `extract_json` は
それを拾えない。**「読んで指す族は足りた」は、道具の無い条件でだけ成り立っていた。**

## 3. 測っていたものが本番に無かった 2 件

**役割の可否より先に、「その役割は本番にあるか」を見る。** この日 2 件見つかった。

**受入判定（PV1）。** 08-23 に「道具なしの verifier は成立しない」（e4b は捏造 pass 12/12、
12b は契約違反で全 fail）と測り、**その結果を根拠に 08-24 で自然文 verifier ごと撤去された**
（コミット `5de9a23ec`）。いま `acceptance` が自動判定するのは charter の決定的コマンドだけで、
自然文は milestone の検収チェックリストへ回る。ハーネスは本番関数の消滅で `AttributeError` に
なる残骸だったので、理由を告げて終了するようにした。**モデルを替えても戻らない**——
役割そのものが無い。

**ファイル分配（S2）。** 0/5 のままだが、本番の split は「独立に処理できる小片のリストへ
分解」で、engine は要素 1 つにつき map ノード 1 つを作る。まとめる方向の宣言はどこにも無い。
N 件を K 組へ配るのは算術で、モデルに訊く仕事ではない。割り当て表からは外した。

## 4. 検証役 — 見立てが外れた 1 件

**測る前の見立ては「危ない」だった。** 本番の `verify → ollama-verify` は `file_flag` も
`read_flag` も `tools` も宣言しておらず、割り付けたファイルが 1 つも届かない。PV1 と同じ
構造で、しかも flow 側の `_normalize_verify` には証跡の要求が無い。

**それでも 5/5・5/5・5/5 だった。** PV1 と同形に寄せた V3（完了条件がファイルを名指し・
中身はプロンプトに無い）でも、e4b は `ok=false` を選び「証跡が無い」と書いた。

**差は材料の在り処にある。** PV1 は「ワークスペースを見て判定せよ」と言われて手元に
何も無く、捏造で埋めた。flow の verify は依存の成果がプロンプト内にあり、中身が無い場合でも
「無い」と言える。**「道具なしの verifier は成立しない」を一般則にしてはいけない**
——新しい検証面を疑うときは、まず材料がプロンプトに入るかを見る。

## 5. 測定側で直した欠陥 8 件

**数字より先に、数字の出どころが壊れていた。** 5 件のうち 3 件は同じ形——
**ハーネスが本番より厳しい**。本番は救っている出力をモデルの失点として数えるので、
「この役割は落ちる」という誤った結論を作る。

1. **診断に正解を混ぜていた。** CG1 の再投入診断の初版が `GOLD_GREP` から「当てるべき行を
   落とす 5 行（例 `billing.py:4`）」を返していた。本番の機械は正解を持たないので、これは
   本番で再現しない助けである。走らせかけた測定を止め、実行結果だけ（コンパイル可否・
   当たった行）へ直した。**同じ罠が既存の `text_eval --repair` にもある**——PR1 の診断は
   `期待 p1+p4=効果 120/予算 10` と正解そのものを渡している（それでも 1/3 が外れていた）。
2. **verify を本番より厳しく採点していた。** JSON を抽出できないと `unparsable` で不合格に
   していたが、本番のゲートは本文の `verify=pass` / `verify=fail` も読む。本番なら正しく
   fail へ倒れる出力をモデルの失点として数えていた（V3 の 1 本目がこれ）。
3. **パス抽出が日本語を巻き込んでいた。** `_mentioned_paths` の `\w` が助詞を拾い
   `をREADME.md` を 1 語にしていた。**既存の宣言剥がしにも効く欠陥**で、要求が
   「README.mdを直す」と空白なしで書くと、正当に宣言された成果物が「要求に無い」と
   判定されて落ちる。パス文字を ASCII に限った。
4. **classify を JSON 契約として採点していた。** 本番契約は `class=<ラベル>` の**本文**で、
   振り替え先も `ollama`（`--format json` が付かない）。JSON 抽出の失敗で落としていた。
5. **extract の形式修復を写していなかった。** 本番（`agent.py`）は契約検査に落ちたら
   形式修復を 1 回入れる（split と同じ）。1 本目の腕の 2/5 はこれで、**器だけ**が崩れて
   中身の証跡は正しかった。写して引き直すと 5/5 で、修復は一度も発火しない
   ——器の崩れは揺れであり、系統的な外し方ではなかった。

**2 と 4 と 5 は同じ形である。** 本番の受け方（本文も読む・JSON 契約でない・1 回修復する）を
写していないと、ハーネスだけが厳しくなる。新しい面を測るときは、合否のロジックを書く前に
**本番がその出力をどう受けるか**を読む。

**残り 3 件は逆で、受け方ではなく起動形がずれていた。** `retrieve` / `synthesize` を測る前に
見つけたもので、出力の採点以前に**別の条件で走らせていた**。

6. **道具ゼロの起動形で測っていた。** `judge_eval` は `agents/<name>.json` の `command` だけを
   読んでいたが、道具とラウンド上限は profile 側の引数で付く——`retrieve` は
   `--tools read --max-rounds 30`、base（`classify` / `map` / `synthesize`）は
   `--think off --tools bash --max-rounds 12`。**読みに行く役割を読めない条件で測っていた**
   ことになる。組み立ては本番の `headless_cmd` を呼び、`readonly` も本番の `_agent_readonly`
   に訊くようにした（`readonly=True` は `--tools` を落とすので、ここを取り違えると道具の
   有無ごと変わる）。
7. **出力契約の後置を写していなかった。** 導入済みの flow-worker スキルは `extract` も
   `retrieve` も知らず、役割行を出さない。本番（`agent.py`）はそれを検出して
   `【出力契約】<役割行>` を後置するが、ハーネスは後置していなかった——**契約なしの
   プロンプト**で測ることになる。役割行は `agent_flow.WORKER_ROLES` を読む（写さない）。
8. **素材の在り処が本番と食い違っていた。** 道具付きの起動形はワークスペースの中で走るので、
   測定も一時ディレクトリを cwd にした。ところが `map` のケースは素材をプロンプトにだけ
   置いており、道具を持ったモデルは名指しされた `ITEM-07.md` を**ディスクへ探しに行って**
   空のディレクトリで詰んだ。本番の map はワークスペースで走る＝名指ししたファイルは実在
   するので、同じ本文をディスクへも配るようにした。

**6 が効く範囲は狭いが深い。** 起動形が変わったのは base へ振り替わる役割だけ
（`classify` / `map` / `synthesize`）で、`ollama-json` / `ollama-list` / `ollama-verify` の
argv は `command` と一致する——つまり過去の測定のうち動いたのは `classify` と `map` の
2 面だけである。ただしその 2 面の数字は動いた（§2）。

（`map` 1/5）、そして**統合役は欠落を運ばない**（SY2 0/5）。残りの内訳と見込み:

### 未測定 24 面の棚卸し

**この日の実測から、見込みは 3 つに分かれる。** ○ の公算（材料がプロンプト内にあり、
既に測った族と同型）、12b 側の確認（レビュー族）、そして**チェッカーの設計から要る**
（正解が構成的に決まらない下書き系）。最後の群がいちばん重い——測るのが難しいのは
モデルの問題ではなく、「何を正解と呼ぶか」を先に決められないためである。

| ツール | 面 | 見込み | 根拠 |
|---|---|---|---|
| agent-flow | `generate`（indirect） | ○ | work と同じ実行族。T1min / T4 で間接的に測れている |
| agent-project | `review`・`adjudicate` | **12b 側の確認** | レビュー族（RV は e4b 1/3・12b 3/3）。e4b で通す前提を置かない |
| agent-project | `assess`・`prioritize`・`distill` | 判定族。**決定化の候補** | 多基準の採否をモデルに訊く形なら F2 / J1 と同じ 0 帯になる。先に `decision` 契約で書けるかを見る |
| agent-project | `route` | ○ の公算 | 単一基準の分類族（CL1 5/5・F1 5/5） |
| agent-project | `plan`・`repo_map` | 計画族 | `planner_eval` と同型のチェッカーが要る（構造で測る） |
| agent-project | `doctor` | ○ の公算 | dashboard の doctor 4 面が 3/3（DR1〜DR4） |
| agent-dashboard | `method-draft`・`acceptance-draft`・`charter/draft`・`charter/refine` | **チェッカーから要る** | 下書き生成。正解が一意でないので、決定的に測れる制約（器・必須項目・素材外の値を書かない）へ落とす設計が先 |
| agent-dashboard | `followup-suggest`・`enqueue-assist`・`task-guide`・`source-task-candidates` | **候補生成族** | CG2 / CG3（選ぶ）は 3/3、CG1（作る）は 0/3。**素材から選ぶ形なら通り、作る形なら落ちる**——どちらの形かで見込みが割れる |
| agent-amigos | `team-builder`・`conductor`・`acceptance`・`debate`・`role-actions` | **未評価** | 複数エージェントの合議で、1 呼び出しの正解が構成的に決まらない。測るなら合議の**手続き**（発言の順序・役割の宣言・打ち切り）を決定的に見る形になる |

**直すものが 2 つあり、1 つは閉じた。**

1. **`map` に形式修復か変種振り替えを付ける（未着手）。** 1/5 の落ち方は中身ではなく器で、
   道具ループが答えを散文とフェンスに変えて `extract_json` が拾えなくなる。本番で 1 回修復が
   入るのは split / extract / retrieve だけで、`map` には無い。`ollama-json` への振り替え
   （`variants` に 1 行）でも同じ穴を塞げる——**どちらが効くかは測れば分かる**。
2. **統合役の欠落運搬（着手・完了）。** `carry_dependency_gaps` を実装して本番の
   `execute_agent` へ入れた。依存の `warnings` / `issues` を統合結果へ転記し、モデルが
   既に書けている欠落は重ねない。SY2W 3/5（機械なし）→ SY2P **5/5**。
   残るのは**散文にしか申告が無い**場合で、手当ては上流側にある——`work` / `generate` の
   完了 envelope は `{"ok": ...}` をそのまま data へ入れるので、`{"ok": true,
   "warnings": [...]}` と書かせれば同じ経路に乗る。**言わせて直るかは未測定**なので、
   プロンプトへ足す前に測る（この日の 5 例は全部「言わせても直らない」だった）。

**面としての次は agent-project の `route` / `doctor`。** どちらも ○ の公算（単一基準の
分類族・dashboard の doctor 4 面が 3/3）で、チェッカーを新しく設計しなくてよい。

**測る前に必ず確かめること。** この日 9 回踏んだ——**その面は本番にあるか**（PV1 は撤去済み、
S2 は本番が要求しない形）、**本番の受け方を写しているか**（verify は本文も読む・classify は
JSON 契約でない・extract は 1 回修復する）、そして**本番の起動形で走らせているか**
（道具・ラウンド上限は `command` でなく profile 側に付く・素材はプロンプトかディスクか）。
前の 2 つを外すとハーネスだけが厳しくなり、3 つ目を外すと**別の条件の数字**が残る
——後者のほうが危ない。厳しすぎる測定は「落ちる」と言うだけだが、起動形のずれは
`map` 5/5 のように**通ったという結論**を作る。

**手が無いと分かったもの。** regex の生成（CG1）は、落ち方が「regex を書く仕事だと
読めていない」で、しかも機械が代わりに書けない。判定・分割・併合が閉じたのは
「モデルが外しても機械が形を直せる」からで、生成そのものが要る仕事にはその手が使えない。
統合役の欠落伝達（SY2）は作って閉じた——`carry_dependency_gaps` が依存の `warnings` /
`issues` を成果へ転記する（SY2P 5/5）。残るのは**散文にしか申告が無い**場合で、
手当ては上流側（申告を契約に載せる）にある。
