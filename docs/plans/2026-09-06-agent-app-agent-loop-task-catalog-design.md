# agent-app agent-loop統合タスク一覧設計

> 作成: 2026-09-06  
> 対象: `tools/agent-app`、`tools/agent-loop`、`tools/statemachine-maker`  
> 更新対象: `2026-09-05-agent-app-task-workflow-navigation-design.md`

## 背景

従来のagent-appでは、選択中リポジトリの`.statemachine/`にある定義だけを「タスク」として扱っていた。
一方、実際の定期実行はagent-loopの設定に置かれ、設定エントリには次の種類が混在する。

- `statemachine`でリポジトリ内の定義を起動するエントリ
- 自由記述の`prompt`をエージェントへ送るエントリ
- `slash`コマンドを送るエントリ
- `hooks`または`event_hook`で入力を生成するエントリ

agent-loopは、起動リポジトリに対して次の順で設定を解決する。

1. `<repo>/agent-loop.yaml`などのリポジトリ直下設定
2. `<repo>/.agents/agent-loop.yaml`などのリポジトリ設定
3. `~/.agents/agent-loop.yaml`などの共通設定

agent-appが独自の設定探索や実行処理を持つと、画面に見えるタスクとagent-loopが実際に動かすタスクがずれる。
そこで、設定探索、エントリの正規化、実行、履歴はagent-loopを正典としたまま、ステートマシン定義と設定
エントリをUI向けの一つのタスクカタログへ統合する。

## 目的

- 選択中リポジトリで実行できる仕事を、種類にかかわらず一つのタスク一覧で確認できる。
- ステートマシン本体と、それを起動する複数の定期設定を重複表示しない。
- 自由プロンプト、コマンド、フックもステートマシンと同じ場所から手動実行・状態確認できる。
- 手動実行では会話と同じ実行方針、エージェント、モデル、共通指示、開始アクションを使える。
- 定期設定の保存先を、リポジトリ設定と共通設定から明示的に選べる。
- agent-loopの既存設定探索、スケジューラ、実行履歴を壊さない。

## タスクの集合

選択中リポジトリのタスクは次の和集合とする。

```text
選択中リポジトリの .statemachine 定義
  ＋
agent-loopが認識する設定エントリのうち、実効cwdが選択中リポジトリと一致するもの
```

`cwd`を省略したエントリは、そのagent-loopを起動するリポジトリを実効cwdとする。明示された`cwd`は
`~`、mapping参照、相対パスをagent-loopと同じ規則で解決し、実行ホスト側の正規パスで比較する。
Windows版agent-appからWSL上のagent-loopを使う場合も、比較はWSL側のパス空間で行う。

## 統合規則

### ステートマシン

`.statemachine/<name>/workflow.yaml`を一つの主タスクとする。設定エントリの`statemachine`が同じ定義を
参照する場合、そのエントリを別タスクにせず、主タスク内の定期実行へ結合する。

- 同じ定義を参照するエントリが複数あれば、定期実行を複数表示する。
- 定期設定がなくても、ステートマシン本体を手動実行できる。
- 設定が存在しても定義ファイルがなければ、参照エラーを持つタスクとして残す。
- 同名エントリを許容し、名前を内部識別子として使わない。

### 自由プロンプト、コマンド、フック

`statemachine`を持たない各設定エントリを独立したタスクとする。表示種別は内容から決定する。

| 条件 | 表示種別 |
|---|---|
| `prompt`または`slash` | プロンプト |
| `hooks`、`event_hook` | フック |
| 上記の組み合わせ | 主たる実行経路に応じてプロンプトまたはフック |

エントリの内部IDは、設定ファイル、配列位置、正規化内容の指紋から生成する。更新要求には読込時の指紋を
含め、外部編集後の古い画面から上書きしない。

## 設定探索と表示対象

agent-appは設定ファイルを直接探索しない。agent-loopの機械向け`inspect`境界を拡張し、リポジトリに対する
次の情報を一度に取得する。

- agent-loopが解決した実効設定と設定ファイル
- リポジトリ設定と共通設定に存在する関連エントリ
- 各エントリの実効cwd、実効性、未適用理由
- ステートマシンとの対応、実行予定、実行状態、履歴
- 壊れた参照、構文エラー、利用できない実行条件

実効設定に含まれるタスクを通常一覧へ出す。優先度の高いリポジトリ設定に隠された共通設定は、重複タスクに
せず、対応するタスクの定期実行一覧へ`未適用`として残す。

## 情報構造

タスク領域は既存の共通リポジトリ選択を維持する。サイドバーには種類の異なるタスクを一つの一覧で表示する。

```text
タスク
  リリース確認       ステートマシン  毎日 09:00
  コードレビュー     プロンプト       30分ごと
  Resource Control   フック           実行中
```

並び順は、要対応、実行中、次回実行が近い順、名前順とする。種類と状態は色だけでなく文言で示す。

選択したタスクのタブは種類に応じて変える。

| 種類 | タブ |
|---|---|
| ステートマシン | 概要、手順、履歴 |
| プロンプト／コマンド | 概要、内容、履歴 |
| フック | 概要、設定、履歴 |
| 参照エラー | 概要、設定 |

## 概要と手動実行

概要の主操作は常に`実行`とする。手動実行欄は、会話の実行条件コンポーネントを再利用する。

- `おすすめ / 節約 / 品質重視 / 直接指定`
- 方針から解決したエージェントとモデル
- 直接指定時のエージェント・モデル選択
- ステートマシンの入力パラメータ、または自由プロンプトの実行内容

手動選択は今回の実行だけに適用し、定期設定を書き換えない。初期値はエントリの`agent_cli`と`model`を
優先し、未指定ならagent-appの実行方針から解決する。

手動実行時は次の順で実行計画を作る。

1. agent-appの共通指示
2. agent-appの開始コマンド
3. agent-appの開始スキル
4. タスク固有の`slash`、フック結果、自由プロンプト
5. ステートマシンの場合は定義と入力パラメータ

agent-appはタスク実行を再実装しない。agent-loopに機械向けの一回実行境界を設け、エントリ解決、フック、
ステートマシンハーネス、状態、停止、履歴記録をagent-loopへ集約する。共通指示と開始アクションは設定ファイルを
変更しない実行時オーバーレイとして渡す。

## 定期実行と保存先

概要内の定期実行セクションに、結合された全予定を表示する。

```text
定期実行
  毎日 09:00   有効     このリポジトリ
  月曜 10:00   未適用   共通設定
```

追加・編集パネルでは、最初に意味で保存先を選ぶ。

```text
保存先
  このリポジトリ  <repo>/.agents/agent-loop.yaml
  共通設定          ~/.agents/agent-loop.yaml
```

リポジトリ直下など既存のローカル設定が使われている場合、`このリポジトリ`はその実ファイルを指す。
ローカル設定がない状態で選択した場合は`.agents/agent-loop.yaml`を作る。共通設定へ保存する場合は、対象が
曖昧にならないよう正規化済みの`cwd`を記録する。

新しいローカル設定を作ると、agent-loopの探索順位により共通設定全体が隠れる。このため、現在の実効設定を
ローカル設定へ引き継いでから対象予定を保存し、既存動作を維持する。共通設定より優先されるローカル設定が
ある場合、共通側へ保存した予定は`未適用―リポジトリ設定が優先`と表示する。

保存先の変更では`コピー`と`移動`を区別する。移動は新しい保存先への原子的保存が成功した後に元エントリを
削除し、同一予定の二重実行を防ぐ。

## 状態表現

定期実行は次の状態を表示する。

- `反映済み`
- `保存済み・再読込待ち`
- `未適用―リポジトリ設定が優先`
- `無効`
- `設定エラー`

デーモン稼働中は、実効設定を変更した場合だけreloadを要求する。未適用の設定ファイルだけを変更した場合は
稼働中デーモンを再読込しない。

## エラーと回復

| 状態 | 表示 | 回復操作 |
|---|---|---|
| 設定構文エラー | 設定元と短い原因 | 設定ファイルを開く、再読込 |
| ステートマシン参照切れ | 定義が見つからない | 手順を作成、参照を変更 |
| 外部編集競合 | 読込後に変更された | 再読込して編集し直す |
| 保存先が未適用 | 優先する設定元 | 保存先を移す |
| 実行環境不足 | 利用できないCLIまたは基盤 | 設定を確認 |
| 手動実行失敗 | 短い原因と最終工程 | 再実行、ログを見る |

構文エラーがある設定を部分的に推測して保存しない。未知フィールド、他リポジトリのエントリ、設定順は保持し、
対象エントリだけを更新する。

## アクセシビリティと視覚設計

- 既存agent-appの固定ニュートラル配色と青い主操作色を維持する。
- 一覧を種類別の大きなセクションに分断せず、種類は短いラベルで補助する。
- 保存先、適用状態、実行状態を色だけに依存させない。
- タブ、保存先選択、実行方針はキーボード操作と可視フォーカスに対応する。
- 非同期の保存・実行中は対象ボタンを無効化し、同じ場所に進行状態を出す。
- 主要操作は44px相当の操作領域を確保し、`prefers-reduced-motion`を尊重する。
- 生のYAMLは通常画面へ常設せず、設定元を開く補助操作から確認できるようにする。

## テスト方針

- config resolution: 3段階の探索順位、拡張子、実効設定、隠された共通設定。
- catalog: cwd一致・不一致・省略、複数予定、自由プロンプト、slash、フック、参照切れ。
- identity: 同名エントリ、外部変更指紋、古い更新の拒否。
- persistence: ローカル／共通保存、実効設定の引継ぎ、コピー、移動、原子的失敗回復。
- execution: エージェント・モデルの一時上書き、共通指示、開始コマンド、開始スキル。
- runtime: reload条件、停止、履歴、ログ、フック、ステートマシン。
- path: macOS/Linux、Windows/WSLのホスト側正規化。
- UI: 種類別詳細、保存先、未適用表示、キーボード、狭幅、空状態、エラー。
- regression: 会話、tmux、ファイル、差分、ワークフロー領域の既存テスト。

Windows/WSL実機試験は有用な確認項目だが、リリース必須条件にはしない。

## 検討した案

| アプローチ | 実装コスト | リスク | 保守性 | 拡張性 | 学習コスト | UX | 推奨度 |
|---|---|---|---|---|---|---|---|
| 統合タスクモデル | 中 | 低 | 高 | 高 | 低 | 高 | ★★★ |
| 種類別セクション | 低 | 中 | 中 | 中 | 低 | 中 | ★★☆ |
| YAML中心の一覧 | 中 | 高 | 低 | 中 | 高 | 低 | ★☆☆ |

統合タスクモデルは、利用者に保存場所の違いを理解させずに日常操作を行え、必要なときだけ設定元と適用状態を
確認できる。種類別セクションは実装しやすいが、同じステートマシンと予定を別物に見せる。YAML中心の一覧は
正典に近い一方、未スケジュールのステートマシンが見えず、自由プロンプトとの違いも理解しにくい。

## 既存スキルとの関係

- `brainstorming`: 複数の設定源とタスク種別を一つの概念へ整理する。
- `ui-designer`: 一覧の密度、段階表示、状態表現、アクセシビリティを補強する。
- `systematic-debugging`: 実装時に既存agent-loopとUIの解決結果の差を追跡する。
- `test-driven-development`: 設定探索、結合、保存、実行オーバーレイを契約テストから実装する。
- `webapp-testing`: Electron上の一覧、編集、実行、エラー回復を検証する。

既存スキルだけでこの統合を代替するものはない。

## 非目標

- agent-loopの設定探索順位の変更
- agent-app独自スケジューラの追加
- 全YAML項目をフォームで編集する汎用YAMLエディタ
- タスクを会話セッションへ変換する機能
- 未適用設定の自動削除
- Windows/WSL実機試験のリリース必須化
