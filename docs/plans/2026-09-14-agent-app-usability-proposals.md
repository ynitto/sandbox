# agent-app: 次に迷いと取りこぼしを減らす使い勝手の提案

日付: 2026-09-14 / 対象: `tools/agent-app` / 状態: **提案**

## 0. 結論

次に効くのは機能を増やすことではなく、**書きかけを失わない、現在地と次の操作が分かる、頻繁な移動を
キーボードで短くする**ことである。優先順位は次の通り。

1. 入力内容を会話ごとの下書きとして自動保存する
2. 初回だけ「依頼を送るまで」を案内し、環境不足はその場で直し方を示す
3. `Ctrl/Cmd+K` のクイック移動を追加する
4. エラー通知を「失敗した事実」から「次にできる操作」へ変える
5. 実行中の仕事を横断して確認できる小さな一覧を設ける

前回の提案は「繰り返し手作業」を減らし、3.1〜3.8 まで実装済みである。本提案はそれと重ならない
**入力の保全・学習・移動・回復**に範囲を絞る。

## 1. 現状から見える摩擦

実装と利用者向け説明を突き合わせ、次の摩擦を優先対象とした。

| 摩擦 | 現状の根拠 | 利用者への影響 |
|---|---|---|
| 長い依頼を書いている途中で会話や領域を切り替えると、どこまで保全されるか分からない | 会話・タスク作成・ワークフロー作成はそれぞれ別の入力欄を持つ。入力先も「メッセージ / 端末操作 / 共有」に切り替わる | 誤操作や再起動を恐れ、別画面を確認しづらい。消えた場合の再入力コストが大きい |
| 初回に選択肢が多い | 主メニュー、リポジトリ、会話、実行方針、入力先、添付、タスク、ワークフローが同じアプリにある | 「まず何をすればよいか」と「高度な設定か必須設定か」の区別を学ぶ必要がある |
| 会話検索はあるが、領域をまたぐ移動はマウス中心 | `#session-search-open` は会話専用。タスク、ワークフロー、設定、現在のリポジトリへの横断入口はない | 会話・タスク・ワークフローを往復する熟練者ほどクリックと視線移動が増える |
| 通知はあっても、失敗からの復帰方法が場所ごとに異なる | 全体通知は `#notice`、自動化は各カード、CLI の停止は会話ヘッダー付近に出る | エラーを理解しても「設定を開く」「端末を見る」「再試行する」のどれかを探す必要がある |
| 並行作業の状態が領域ごとに分散する | 会話一覧には応答中・確認待ち、タスクとワークフローには個別の実行状態がある | 待ち時間に別作業へ移ると、何が実行中で何が人待ちかを一度に確認できない |

前回実装した「確認待ちへ移動」「OS 通知」「定型依頼」「会話の絞り込み」はそれぞれの局所操作を短くした。
今回はそれらを置き換えず、アプリ全体で迷わないための薄い層を足す。

## 2. 設計原則

- **通常画面に常設の説明を増やさない。** 初回案内は完了後に消え、詳細は必要な場所でだけ開く。
- **入力は明示的な送信まで利用者のもの。** 自動保存しても勝手に送信しない。
- **既存の画面へ着地する。** クイック移動やエラー操作のために、機能を複製した新画面を作らない。
- **推測して自動実行しない。** エラーからの回復候補は提示するが、CLI の再起動や設定変更は利用者が押す。
- **本文・ファイルパスを通知へ出さない。** OS 通知と同じプライバシー境界を維持する。
- **アプリ自身は git 操作を担わない。** コミット・push は引き続き CLI に依頼する。

## 3. 提案

### 3.1 会話ごとの入力下書きを自動保存する（最優先）

入力欄の本文、添付、選択中の入力先を「リポジトリ + 会話」ごとに保存し、画面切替やアプリ再起動後に戻す。
タスク作成とワークフロー作成も、それぞれの作成セッション ID をキーに同じ仕組みを使う。

```text
┌ 入力欄 ─────────────────────────────────────────────────┐
│ 認証エラー時の再試行を追加して、既存の…                  │
│                                                         │
│ 添付 2件                         下書きを保存しました     │
└─────────────────────────────────────────────────────────┘
```

- 500 ms の debounce で保存し、送信成功時だけ削除する。送信失敗時は残す。
- 保存中を常時アニメーションにせず、保存直後だけ「下書きを保存しました」を薄く表示する。
- 空文字の下書きは保存しない。会話削除時は対応する下書きも削除する。
- 添付は既存 ID がまだ有効なものだけ復元し、読めない添付は黙って消さず「1件を復元できません」と示す。
- 端末へ送るキー入力は保存しない。「端末操作」で複数行を組み立てている場合の本文だけを対象とする。
- 保存先は既存設定ストア配下とし、本文の上限を 64 KiB、添付を既存上限までにする。

**受入条件**

1. 会話 A に入力 → 会話 B → A と戻ると本文と添付が戻る。
2. アプリを終了・再起動しても未送信本文が戻る。
3. 送信成功後は戻らず、送信失敗後は残る。
4. 会話 A の下書きが B、タスク作成、ワークフロー作成へ混ざらない。

**実装候補:** `src/renderer/renderer.js` の composer 状態、`taskTeaching.js`、`flowTeaching.js` を薄い
`drafts.js` に寄せ、preload 経由で main の store に保存する。DOM の入力イベントだけで完結させず、保存上限と
削除規則を main 側で正規化する。

### 3.2 初回案内と実行環境の「直し方」を文脈内に出す

初回起動に全機能ツアーは出さない。空状態を 3 ステップにし、最初の依頼を送ったら自動的に完了とする。

```text
はじめる
  1  リポジトリを追加       [追加する]
  2  利用する AI を確認      Codex 利用可能
  3  依頼を書く              [入力欄へ]

タスクとワークフローは、必要になったとき左のメニューから作れます。
```

- リポジトリ未登録なら 1、登録済みで利用可能 CLI がなければ 2、それ以外は 3 を主操作にする。
- CLI / tmux / Python / agent-loop / agent-flow の不足は、機能名ではなく**したいこと**を先に書く。
  例: 「会話は使えます。定期実行には agent-loop が必要です」。任意依存をアプリ全体の失敗に見せない。
- 「直し方を見る」で、検出に使ったホスト（ローカル / WSL）とコピー可能な導入コマンドを開く。
- 初回依頼後は案内を消す。「設定 > アプリ > はじめ方をもう一度表示」で再表示できる。
- バージョン更新のたびに再表示しない。新機能紹介はこの仕組みに混ぜない。

**受入条件:** リポジトリなし、CLI なし、tmux なし、通常利用可能の 4 状態で、主操作が常に 1 つだけ見える。

### 3.3 `Ctrl/Cmd+K` で会話・タスク・ワークフローへ移動する

会話検索を置き換えず、熟練者向けのクイック移動を追加する。検索対象は「操作」と「名前」であり、本文の全文検索は
既存の「会話を検索」へ委ねる。

```text
┌ クイック移動 ───────────────────────────────────────────┐
│ > ログイン                                               │
│   会話      ログイン画面の工程を直す        repo-a       │
│   タスク    ログイン確認                     repo-a       │
│   操作      新しい会話                                   │
│   操作      設定を開く                                   │
└─────────────────────────────────────────────────────────┘
```

- 候補: 最近の会話、タスク、ワークフロー、リポジトリ切替、新規作成、設定、会話の全文検索。
- 入力なしでは「最近使った順」、入力ありでは表示名の部分一致。本文やファイルを新たに索引しない。
- 上下キー、Enter、Escape、Tab 移動を保証する。ショートカットは入力欄フォーカス中でも開ける。
- `Ctrl/Cmd+P` は OS や CLI と衝突しやすいため使わない。既存送信キーや端末入力は変えない。
- モーダル内でさらにモーダルを開かず、設定などへ移動するとクイック移動を閉じる。

**受入条件:** キーボードだけで別リポジトリの会話、タスク、設定へ到達でき、Escape で元のフォーカスへ戻る。

### 3.4 エラー表示に回復操作を 1 つだけ付ける

エラー文を増やすのではなく、既知の失敗を少数の回復カテゴリに分け、最も安全な次操作を 1 つ表示する。

| カテゴリ | 例 | 主操作 | 詳細 |
|---|---|---|---|
| 環境不足 | CLI / tmux / Python がない | `直し方を見る` | 検出ホスト、確認結果 |
| セッション停止 | tmux / CLI が終了 | `再接続する` または `新しく起動` | 終了コード、端末末尾 |
| 一時失敗 | 読み込み、検索、通知 | `もう一度試す` | 技術的なエラー |
| 入力不備 | 必須値、壊れた定義 | `該当欄へ移動` | 検証結果一覧 |
| 権限・確認待ち | CLI が入力待ち | `端末で答える` | 現在の端末 |

- 主操作を複数並べない。破壊的な回復（削除、強制停止）は「詳細」に置く。
- 生の例外メッセージを見出しにせず、「何が完了しなかったか」を日本語で書く。
- 再試行中は同じ操作の連打を防ぎ、結果が変わらなければ新しい通知を積み重ねず更新する。
- 未分類エラーは従来どおり詳細を表示し、誤った回復操作を推測しない。

**受入条件:** 代表的な 5 カテゴリのテスト fixture で、見出し・主操作・技術詳細の対応が固定されている。

### 3.5 「進行中」だけを横断表示する

分析ダッシュボードは作らない。サイドバー上部に、いま注意が必要なものの件数だけを出す。

```text
進行中  3
  確認待ち   会話: ログイン画面…        [開く]
  実行中     タスク: 月次レポート        [開く]
  共有待ち   会話: API を調査            [開く]
```

- 対象は `確認待ち / 応答中 / タスク実行中 / ワークフロー実行中 / 共有待ち` のみ。完了履歴は出さない。
- 0 件ならセクションごと隠す。通常の会話・タスク一覧は変更しない。
- 表示は既存状態を集約するだけで、新しいポーリングや実行管理を足さない。
- 並びは「人の入力待ち → 失敗 → 実行中 → 待機中」、同順位は更新時刻順。
- 行を押すと既存の対象画面へ移動する。停止や承認を一覧上で実行させない。

**受入条件:** 複数リポジトリをまたいだ状態が重複なく表示され、完了すると一覧から消える。

## 4. 優先順位と段階導入

| 順 | 提案 | 主な価値 | 大きさ | リスク | 推奨リリース |
|---:|---|---|---|---|---|
| 1 | 入力下書き | 入力喪失の防止 | 中 | 保存データと添付の寿命 | 第1弾 |
| 2 | 初回案内・直し方 | 初回成功率の向上 | 中 | OS / WSL ごとの案内差 | 第1弾 |
| 3 | クイック移動 | 熟練者の移動短縮 | 中 | フォーカス管理 | 第2弾 |
| 4 | 回復操作付きエラー | 自力復旧率の向上 | 中〜大 | エラー分類の肥大化 | 第2弾 |
| 5 | 進行中一覧 | 並行作業の見落とし防止 | 中 | 状態集約の整合性 | 第3弾 |

第1弾は「最初の依頼を安全に送れる」、第2弾は「速く移動して失敗から戻れる」、第3弾は「並行作業を見失わない」
という独立した価値単位になる。5 件を一度に実装しない。

## 5. 効果の測り方

外部分析基盤や本文収集は追加しない。手動ユーザビリティテストと、端末内の匿名カウンターだけで判定する。

| 指標 | 現状値の取り方 | 目標 |
|---|---|---|
| 初回起動から最初の依頼送信まで | 5 人の操作テスト | 全員 3 分以内、案内なしの質問 0 回 |
| 未送信本文の再入力 | 画面切替・再起動シナリオ | 0 回 |
| 別領域の対象を開く操作数 | 会話 → タスク、タスク → 設定の操作テスト | `Ctrl/Cmd+K` を含め 4 操作以内 |
| 既知エラーから復帰できた割合 | fixture 5 種の操作テスト | 4/5 以上を説明なしで復帰 |
| 確認待ちの見落とし | 3 件並行シナリオ | すべて「進行中」から発見 |

端末内カウンターを実装する場合も、保存するのは `onboarding_completed`、`draft_restored_count`、
`quick_open_used_count`、`recovery_action_used_count` の数値だけとし、依頼本文、パス、会話名、CLI 出力は保存しない。
利用者が設定でリセットでき、外部送信はしない。

## 6. 今回は採らない案

| 案 | 採らない理由 |
|---|---|
| 常設のホームダッシュボード | 起動時に一段増え、会話をすぐ再開する既存利用者を遅くする。「進行中」だけで十分 |
| 全機能を順に説明する製品ツアー | 読まないと操作できない設計になる。初回成功に必要な 3 ステップだけにする |
| 自然言語の万能コマンドパレット | 入力意図の解釈と実行確認が必要になり、既存の会話入力と役割が重なる |
| エラーの AI 自動修復 | 追加コストと意図しない変更が発生する。既存の「AIに直してもらう」は人が送る境界を維持する |
| 全操作へのショートカット割当 | 覚える負担と衝突が増える。まず入口を `Ctrl/Cmd+K` の 1 つに限定する |
| 下書きのクラウド同期 | agent-app のローカル完結・登録フォルダだけを見る境界を越える |

## 7. 実装前に決めること

1. 下書きを既存 `config.json` に含めるか、サイズ上限を独立管理できる `drafts.json` に分けるか。
2. 初回案内の導入コマンドをエージェント定義に持たせるか、対応 OS ごとの静的説明に留めるか。
3. クイック移動で別リポジトリを選んだとき、現在の未送信入力が自動保存されたことをどのタイミングで示すか。
4. 「進行中」が参照する状態を renderer 内で集約するか、main process の snapshot として返すか。

このうち 1 は第1弾の着手前に必須。2〜4 は各リリースの設計時に決めればよい。
