# agent-dashboard ワークフロー依頼の設計書化支援（設計セッション） 設計

## 背景

柱2（人介在の最適化）/ C3・C4 — 人が依頼文を書き切る前に、必須節の機械チェックと設計フローで材料を下ごしらえする。

ワークフロー画面の依頼欄は 4 行の自由記述で、agent-flow が期待通り動く粒度（何を・どこまで・どう検証するか）まで書き切るのはユーザーの負担が大きい。短い依頼で投入すると planner の解釈揺れがそのまま run の品質揺れになる。

入口は 2 つある。

- **経路A**: 別のエージェント CLI/IDE で要件定義〜詳細設計まで済ませ、設計 Markdown を持っているケース。これを読み込ませて「実行」だけ押したい。
- **経路B**: 短文のやりたいことしか無いケース。dashboard 上で要件定義から詳細設計まで詰めたい。対話的に詰める手法と全自動の手法の両方が要る。

どちらの経路でも「設計書までブレイクダウンした状態」から agent-flow を開始することがゴール。

用語は [tools/agent-dashboard/CONTEXT.md](../../tools/agent-dashboard/CONTEXT.md) を正とする（設計書・設計フロー・設計セッション・ラウンド・設計 run・実行前チェック）。

## 採用方針

**合流点を依頼欄の 1 か所に絞る**。経路A は設計書を依頼欄へ流し込む取り込み口、経路B は依頼欄の内容を設計書へ育てる設計セッション。実行前チェックは依頼欄の内容へ常時かかるため、両経路と手書き依頼のすべてに 1 実装で効く。

- 設計書は**全文を依頼テキストとして** agent-flow へ渡す。agent-flow 本体は無変更。
- 「実行可能な設計書」= 必須 4 節（目的・変更対象・受入基準・検証方法）を備えた Markdown。決定的チェックで不足を**警告表示のみ**（実行はブロックしない）。
- 設計セッションは **agent-flow run のステートレス連鎖**で回す（ADR: [0001](../../tools/agent-dashboard/docs/adr/0001-design-session-as-agent-flow-run.md)）。human ノードは使わない。
- 設計 run と実装 run は分離し、「この設計で実行」のワンクリックで引き継ぐ。

## 1. 設計書の受け渡し契約

設計書 Markdown の**全文が依頼テキスト**。dashboard は inbox 投入時に加工しない。

- サイズガードのみ: 100KB 超で警告（投入は可能）。
- 却下案 — repo 内パス参照: 未コミットの設計書が workspace clone に存在せず動かない。コミット済み判定の分岐を持つ価値が初版には無い。
- 却下案 — `--reference` 配線: reference は「参照資料」の意味論で、設計書=仕様の正典という強さが planner に伝わらない。読まれる保証も薄い。

planner への「設計書入力モード」追加は、全文依頼で精度が足りないと実測で分かってから検討する。

## 2. 実行前チェック

依頼欄の内容に対する決定的な必須節チェック。LLM は使わない。

- 必須 4 節と同義語（見出しレベル不問・大文字小文字不問）:
  - 目的 / 狙い
  - 変更対象 / 対象 / スコープ
  - 受入基準 / 完了条件
  - 検証方法 / 検証 / テスト方法
- 不足節は依頼欄脇にバッジで警告。実行ボタンは無効化しない。外部 CLI/IDE 産の書式は多様で、ブロックすると取り込みの摩擦が支援の価値を上回る。
- 空欄時の補助として必須 4 節のテンプレ挿入ボタンを置く。
- 却下案 — LLM 判定つきゲート: 遅い・非決定的・判定自体の検証が要る。初版に入れない。

## 3. 経路A: 設計書の取り込み

- ファイル選択ボタン + 依頼欄へのドラッグ&ドロップ + 貼り付け（textarea ネイティブ）の 3 口。いずれも依頼欄へ全文流し込むだけで、専用の保存先や添付スロットは作らない。
- 4 行 textarea に長文は窮屈なので、折りたたみ表示と展開エディタを足す。
- 却下案 — 依頼欄と別の「設計書」添付スロット: 2 入力の連結順とどちらが正典かという新しい問いを生む。合流点を増やさない。

## 4. 経路B: 設計セッション

### 方式 — run のステートレス連鎖

1 ラウンド = 1 短命 run。dashboard がラウンドを決定的に制御する。

```
依頼欄の短文 →「設計を練る」→ [ラウンド run] → 設計書 + 質問リスト
      ▲                                             │
      │  回答フォーム入力 →「次ラウンド」            ▼
      └──────────────────────────  いつでも「この設計で実行」
```

- ラウンド run の入力: 元要望 + 現行設計書 + 前ラウンドの質問と回答。dashboard がテンプレで決定的に組み立てて依頼テキストにする。
- ラウンド run の成果: 更新した設計書 + 次の質問リスト。
- ラウンド数は無制限。やめ時はユーザーの「この設計で実行」。毎ラウンド完全な設計書が返るため、どこで止めても実行可能。

却下案が 2 つある。

- **human ノード内蔵型**（run 内で park して回答を待つ）: `PLANNER_KINDS = VALID_KINDS - {"human"}`（agentcore/nodecontract.py）により評価役の replan は human を追加できず、ラウンド可変にならない。また park 中 run の timeout・リース・孤児回収を設計セッションが背負う。
- **agent-flow 本体へループ機構追加**: 本体無変更の方針に反する上、「人待ちを勝手に増やさない」という agent-flow の設計原則を破る。

### ラウンド成果の契約 — Markdown 規約

構造化 JSON ではなく Markdown の節規約で受ける。

- sink ノード出力 = 設計書 Markdown。末尾にレベル 2 見出し `## 質問` があれば、その配下の番号付きリスト（`1.` 形式）を質問として扱う。
- dashboard は `## 質問` 見出しで決定的に分割し、質問行をフォーム項目にする。見出しが無ければ収束（質問なし）とみなす。
- 却下案 — JSON 契約: 長文 Markdown を JSON 文字列に内包させると小型モデルが壊す（ollama の JSON モード実測）。Markdown 規約なら分割に失敗しても全文表示で読めるという劣化安全がある。

### セッション状態

- cwd・元要望・現行設計書・ラウンド履歴（質問と回答）を dashboard の専用ファイルに保存する。
- 複数セッション並行可。実行履歴と同様の一覧で再開・破棄できる。
- agent-flow 側にセッション概念は無い。run から見れば毎回独立した依頼。

## 5. 同梱設計フロー

カスタムフローの探索に「同梱」スコープを足し、リポジトリ直下の `workflows/*.json` を読み取り専用で読む（パッケージ版は extraResources、手法カタログ `methods/` と同じ配布規則）。優先順位はリポジトリ共有 → ユーザー共通 → 同梱で、同じ id をユーザー共通に保存すれば同梱版を隠せる。トーン違い（ブレスト風・深掘り風）は手法（methods）の差し替えで作る。

| フロー | 構成 | 用途 |
|---|---|---|
| 対話型 | 1 ノード（設計更新 + 質問生成） | 設計セッションのラウンド run |
| 全自動型 | 3 ノード（要件展開 → 設計 → 自己レビュー反映） | 短文から一発で設計書。質問ゼロのセッションとして同じ機構に乗る |

- どちらも読み取り専用系 kind のみで構成し、workspace へ書き込まない。`evaluate` は off。
- 成果は run の result（sink ノード出力）から取得する。`af/` ブランチを作らない。
- 却下案 — 設計書を `af/<run-id>` へコミット: 設計 run のたびにブランチが増える。repo に設計書を残したい場合は実装 run の受入基準に「設計書を docs/ へ保存」と書けば実装側で残る。
- 同梱を 2 本に絞る理由: 対話/全自動の軸だけ示せば、バリエーションは methods とユーザーのカスタムフローで表現できる。カタログを増やすほど維持が重くなる。

## 6. 実装 run への引き継ぎ

- セッションビューと設計 run 詳細に「この設計で実行」ボタン。result 全文を依頼欄へ流し込み、実行フォームへ遷移する。
- 実装 run のフロー選択は従来通り（自動 / 標準パターン / カスタム）。設計書は依頼であってフローではない。
- 却下案 — 設計→承認→実装を 1 run で繋ぐ: 承認 park が長時間化しやすく、設計だけ捨てて撤退する動線を失う。望むユーザーはカスタムフローで組める。

## 7. 実装スコープ

agent-flow 本体・flow-planner スキルは無変更。変更は dashboard と同梱カタログに閉じる。

- `workflows/design-interactive.json` / `workflows/design-auto.json`: 同梱設計フロー 2 本。
- `tools/agent-dashboard/package.json`: `workflows/` を extraResources へ追加。
- `src/features/adhoc-flow/main/adhoc.js`: 同梱スコープの探索と、読み取り専用スコープの保存・削除拒否。
- `src/features/adhoc-flow/main/design-session.js`（新規）: セッションの永続化、ラウンド run の投入、成果の取り込み（`## 質問` 分割・sink 出力の抽出）。
- `src/features/adhoc-flow/main/ipc.js` / `preload.js`: `designSession:list|get|start|delete`。
- `src/renderer/features/adhoc-flow.js`: 取り込み UI・実行前チェックバッジ・展開エディタ・雛形ボタン・設計セッションカード。
- テスト: `test/adhoc-flow.test.js`（実行前チェック、`## 質問` 分割、ラウンド入力の組み立て、sink 出力の抽出、ラウンドの投入と取り込み、失敗時の扱い）、`test/packaging-assets.test.js`（同梱フローの同梱指定）、`test/no-git-writes.test.js`（読み取り専用スコープの保存・削除拒否）。

## 検証方法

- `npm test` が通る（上記ユニットを含む）。
- 手動: 経路A（MD 取り込み→警告バッジ→実行）、経路B（短文→対話 2 ラウンド→この設計で実行、全自動 1 run→実行）の 2 本をなぞる。
