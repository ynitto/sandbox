# ワークフロー設定再編設計

## 目的

全体設定の「ワークフロー」タブを解体し、設定を利用場面に近い場所へ移す。実行能力に関する設定は全体設定の「実行制御」へ、フローと作業ルールの管理はワークフロー画面の「設定」へまとめる。

## 画面構成

### 全体設定

- 「ワークフロー」タブを削除する。
- 「実行レベルの構成」を「実行制御」タブへ移す。
- 「実行レベルの構成」は「実行のキャパシティ」の直前に置く。
- 見出しと説明は、内部契約ではなく利用者が行う操作を表す平易な言葉にする。

### ワークフロー画面の設定

以下を同じ設定画面へまとめる。

1. フローと作業ルール
2. 実行履歴を残す期間

フローと作業ルールは同じ保存場所・編集可否の表現を使う。画面では「管理ルール」「編集ポリシー」などの内部的な語を避け、「保存場所」「編集できます」「読み取り専用」「自分用にコピー」と表示する。

## フローと作業ルールの共通管理規則

| 保存場所 | 探索条件 | 利用 | 直接編集・削除 | コピー |
|---|---|---:|---:|---:|
| ユーザーホーム | 常に対象 | 可 | 可 | 可 |
| 登録済みフォルダ | 登録されている場合だけ | 可 | 不可 | ユーザーホームへ可 |
| 組み込み定義 | 常に対象 | 可 | 不可 | ユーザーホームへ可 |

- 未登録フォルダ内の `.agent-flow/workflows` と `.agent-flow/methods` は探索しない。
- 同じ ID が複数の保存場所にある場合、実行対象として選んだ登録フォルダの定義を優先する。
- 一覧と詳細に保存場所と編集可否を表示する。
- 読み取り専用の定義を変更したい場合は「自分用にコピー」でユーザーホームへ別 ID の定義を作る。
- コピー元は変更しない。

## Git の責務

Dashboard は登録済みフォルダを読み取るだけとし、次の Git 操作を行わない。

- pull / fetch
- add / commit
- push
- branch / checkout

共有定義の更新と配布は、通常のリポジトリ作業または既存の CI・同期手段が担う。

## データと処理の境界

- フローのユーザーホーム保存契約は既存の `~/.agents/workflows/*.json` を維持する。
- 作業ルールのユーザー編集可能な定義はユーザーホームへ保存し、実行時に現在の tuning 契約へ反映する。
- 登録フォルダ内のフローと作業ルールは読み取り専用のソースとして扱う。
- コピー操作は読み取り専用ソースを正規化し、新しい ID とユーザーホーム由来情報を付けて保存する。
- 保存・コピー後は対象一覧だけを再取得し、編集中の別設定を失わない。

## エラー表示

- 未登録フォルダは探索・コピー対象として受け付けず、「先にフォルダを登録してください」と示す。
- 読み取り専用ソースへの保存・削除要求は main 側でも拒否する。
- コピー先 ID の重複は上書きせず、新しい名前を求める。
- 壊れた定義は一覧全体を止めず、その項目だけ利用不可として理由を表示する。

## テスト

- 全体設定から「ワークフロー」タブが消えていること。
- 実行レベル設定が実行制御内でキャパシティ設定より前にあること。
- ワークフロー設定にフロー、作業ルール、履歴保持が表示されること。
- 未登録フォルダを探索しないこと。
- 登録フォルダと組み込み定義を直接編集・削除できないこと。
- 読み取り専用定義をユーザーホームへコピーできること。
- Dashboard の保存経路が Git コマンドを呼ばないこと。
- 既存のフロー実行、作業ルール適用、tier 設定保存が維持されること。
