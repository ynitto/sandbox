# 検証の決着（verification settlement）— 詰まった検証から人が抜ける道の統一

> 効く柱・原則: **柱2 / C3・C4・C7**。C5（人の承認を品質保証に使わない）と C10（品質ゲートは降格しない）は
> 緩めない——なぜ緩めずに済むかを §5 に書く。

## 1. 背景と課題

検証が決着しないまま人へ戻ってくるタスクがある。2026-08-09 の実測:

- `document-msbqiswv-1` の verifier（agent-ollama qwen3.5:9b）が 600 秒 × 3 回でタイムアウトし、
  4 基準すべてが `inconclusive`。receipt は採用できず local runner へ落ち、自然文基準は判定できないので
  全部 `unverifiable`。「検証不能」として人へ。人が再開すると、同じノードで同じ 30 分をもう一度焼く。
  タイムアウトを 1800 秒へ上げた後は 1 回あたり 90 分になった。
- クラウド CLI に振れば済む話ではない。**クラウドでも verify が決着しないケースは以前からあり**、
  トークン制限でそもそも振れない時間帯もある。

問題は遅さそのものではなく、**詰まったときに人が選べる道が 2 つの極端しかない**ことにある。

- 承認して同じ条件でやり直す（何も変わらないので、また同じところで止まる）
- 強制完了で締める（検証を全部捨てる）

中間が無いので、詰まるたびに「この CLI のときだけ」「このエラーのときだけ」の回避を足したくなる。
パッチが積む構造そのものが課題である。

## 2. 問題の再定義 — 欠けているのは機能ではなく語彙

人がやりたいことを数え、既存の口と突き合わせると、足りないものは 1 つしかない。

| やりたいこと | 既存の口 | 詰まったカードから見えるか |
|---|---|---|
| 同じ条件でやり直す | needs の [x] / `approve` | ○ |
| 別のノードで検証する | `revise` の `- node:` / 板への検証委譲 | ✗ |
| 受入基準を書き直す | `revise` の `acceptance`（正規形へ置換される） | ✗ |
| 止めて他を進める | `hold`（同じ環境要因の反復で自動化済み） | △ |
| 未検証と明示して締める | `force-complete` | ○ |
| **使う CLI・モデル・待ち時間を変えて検証する** | **無い** | ✗ |

6 つのうち 4 つは既に実装されている。にもかかわらず「検証不能」のカードからは見えず、人が押せるのは
承認と強制完了だけ。これは C4（人に出すときは材料を揃えて 1 回で決めさせる）への違反であって、
機能不足ではない。実際に起きたのは、見えている 2 択のうち安全に見えるほうを押し続けて 90 分を
何度も焼く、という行動だった。

## 3. 判断

**「検証が決着しない」を 1 つの状態として名前を付け、そこから出る道を 4 つの語彙に固定する。
新しい迂回路は作らない。**

決着の語彙（disposition）は次の 4 つで、これ以上増やさない。

1. **`retry`** — 実行条件を変えて再検証する。何で（CLI・モデル）・どこで（ノード・板）・どれだけ待つか。
2. **`amend`** — 受入基準を書き直して再検証する。
3. **`park`** — このタスクを止めて、他のタスクを進める。
4. **`accept-unverified`** — 未検証と明示して締める。統合はしない。

1〜3 は receipt 契約をそのまま通る。ゲートは 1 ミリも緩まない。4 だけが「done は機械検証だけが根拠」の
唯一の例外で、これは既存の `force-complete` そのものである。**新しい例外は作らない。**

エージェントの種類はこの語彙に出てこない。失敗の種類（タイムアウト・空応答・証跡不足・委譲の不決着）も
出てこない。それらは *材料* であって *出口* ではない。ここが、種類ごとの回避が積まないための構造的な担保になる。

## 4. 唯一の新規実装 — 検証の実行条件を plan に載せる

verifier をどう起動するかは、いまノードのグローバル設定（agent-control・yaml）からしか来ない。
`verification_plan` は「何を確かめるか」を持つが「何で確かめるか」を持たない。だから人はタスク 1 件に対して
条件を変えられず、`retry` が「同じ条件でもう一度」にしかならない。

```jsonc
"policy": {
  "confirm": 1,
  "timeout_sec": 600,
  "agent": { "agent_cli": "codex", "model": null, "timeout_sec": 1800 }   // 追加
}
```

- `policy` は digest の計算対象に入っている。条件を変えた検証は**別の plan** になり、古い receipt は
  検算で自動的に落ちる。フェイルクローズがそのまま効く。違う条件で確かめたものを同じ判定として
  混ぜないという意味論としても、これが正しい。
- receipt 側は「どの条件で確かめたか」を返す（`verified_with`）。人が次の一手を選ぶ材料になり、
  「クラウドでやり直せば通るのか」を推測ではなく記録から判断できる。
- タスクには `- verify_agent:` として保存し、`revise` の編集対象へ加える。つまり `retry` の実体は
  新しいコマンドではなく、既存の revise 1 本になる。

これだけが新規である。残りは既存の操作を 1 枚のカードへ集めるだけの仕事になる。

## 5. 「品質を落として止めない」の正直な表現は 2 つしかない

道は 3 つあるように見える。

- **(a) 要求を下げる** → `amend`。書き直した基準がタスクに残り、後から「何を諦めたか」が読める。
- **(b) 未検証と明示して締める** → `accept-unverified`。FORCED として納品書・決定記録に残り、
  成果ブランチは統合しない。
- **(c) ゲートを黙って緩める** — `inconclusive` を一定回数で pass 扱いにする、N 回失敗したら自動で
  done にする、など。

**(c) は採らない。** これは品質を落とす方法ではなく、品質が落ちたという事実を記録から消す方法である。
done の意味が壊れ、後から (a) や (b) と区別できなくなる。C5 と C10 に正面から反する。

裏を返すと、最終手段は既にある。それが (b) であり、詰まったカードから 1 手で到達できるようにするのが
この設計の仕事で、新設は要らない。

## 6. 人へ出すカード

「検証不能」のカードに、判断に要る材料を揃える。

- どの基準が決着しなかったか、その理由（時間切れ / 証跡不足 / 判定不能）
- 何で検証したか——CLI・モデル・実際にかかった時間（receipt の `verified_with`）
- 同じ基準・似た基準が過去にどう決着したか（`decisions/` の再利用）
- 4 択と、それぞれの見積り。「codex で再検証: 約 5 分」「保留: 他 3 件が進む」
  「未検証で締める: 統合しない」

新しい失敗の種別が出ても、増えるのは材料だけで出口は 4 つのまま。

## 7. 自動側との接続

人へ出す前の順序は既存のまま変えない。transient の in-place 再試行 → 板への検証委譲 → 人。
2026-08-09 に入れた「同じ環境要因が連続したら保留」は、いまは黙って保留にするだけだが、
**この 4 択カードを出す契機**として使う。保留は 3 番目の選択肢が自動で選ばれた状態であり、
人はカードから 1・2・4 へ乗り換えられる。

## 8. 却下した案

- **`inconclusive` を N 回で pass に倒す。** §5 の (c) そのもの。
- **verify が失敗したら自動で安いモデルへ降格して再検証する。** 降格の向きが逆。verifier は道具を使って
  証跡を集める「読む系」で、安くすると decisive にならず `inconclusive` が増えるだけ。降格して品質を
  買えるのは worker であって verifier ではない（C9 の格付けは仕事の性質で決める）。
- **失敗の種別ごとに専用の回避操作を足す。** いま避けたいものそのもの。種別は材料であって出口ではない。
- **「検証しなくてよいタスク種別」を作る。** 宣言できるようにすると、投入時にそう書かれる。
  C5 の入口が広がるだけで、詰まったタスクは救われない。
- **ノード単位の調整だけで済ませる。** 既に agent-control にある。これでは「この 1 件だけクラウドで」が
  表せず、1 件のために全プロジェクトの検証を高いモデルへ寄せることになる。

## 9. 段取り

1. ✅ **実装済み（2026-08-09）** — `policy.agent` の契約（`verification-plan` /
   `verification-receipt` の両スキーマ）と、agent-project・agent-flow の同時更新。
   `verified_with` を receipt へ。
2. ✅ **実装済み（2026-08-09）** — `- verify_agent:` を `REVISE_FIELDS` へ。dashboard の
   revise も同じキーを送る。この 1 行だけの revise は成果を作り直さず**検証だけ**やり直す
   （`verify_only` の fast path に載せた——成果を作り直すと元の詰まりごと再現する）。
3. ✅ **実装済み（2026-08-09）** — 決着カード。needs の frontmatter に `settlement`（機械可読）
   と本文の案内を書き、dashboard が 4 つのボタンとして描く。CLI 運用者向けには本文へ
   具体的なコマンドを並べる（`commands/` の指示は増やしていない——4 つとも既存の
   revise / hold / force-complete へ写る）。
4. ✅ **実装済み（2026-08-09）** — 反復による保留からカードを出す接続。保留は 4 択のうち
   park が自動で選ばれた状態なので、カードからは `park` を落として残り 3 つを出す。

1 と 2 で今回の詰まりは抜けられる（人が `verify_agent` を書いて revise する）。3 は
「押せる場所に無いものは無いのと同じ」を解く仕事で、C4 の本体はこちら。

### 1・2 で入った経路（2026-08-09）

```
人（dashboard の revise / CLI）
  └─ - verify_agent: codex
       └─ build_task_verification_plan → policy.agent（digest に入る＝別 plan）
            └─ agent-flow の verifier が run_agent(..., agent=plan_agent(plan))
                 └─ receipt.verified_with = {agent_cli, model, timeout_sec, elapsed_sec, source}
```

明示指定は agent-control・yaml・縮退のどれよりも強い。ノード全体の設定に負けると、
詰まったタスク 1 件のために全プロジェクトの検証を高いモデルへ寄せることになり、この口が
用を成さない。読めない指定は revise の時点で人へ返す（plan へ載る前に弾く）。

### 3・4 で入った経路（2026-08-09）

```
検証が決着しない（unverifiable / 委譲も不決着）
  └─ _env_block … 同じ理由の連続を数える（上限超で保留）
       └─ settlement_record … 材料（決着しなかった基準・verified_with・連続回数）＋ 出口
            ├─ needs/<id>.md の frontmatter `settlement:`（機械可読）
            │    └─ dashboard: 材料 ＋ 4 ボタン → revise / showTaskDialog / hold / force-complete
            └─ needs/<id>.md の本文（md を直接読む人・CLI 運用者向けに同じ 4 つをコマンドで）
```

出口の集合を決めるのは agent-project 側だけにした（保留中なら `park` を落とす、等）。
viewer は運ぶだけで、どれを出すかを自分で判断しない——同じ判断を 2 か所ですると、
片方だけが育ってズレる（C7）。「判定を緩めて通す」ボタンはどちらにも無い。

## 10. トレードオフと確信度

`policy` を digest に含めたまま条件を足すので、**検証条件を変えると過去の receipt はすべて無効になる**。
成果が変わっていなくても再検証が要る。これは意味論として正しいが、条件を試行錯誤すると検証コストが
線形に増える。カードに見積りを出すのはこの理由でもある。

確信度は高い。新規は契約 1 フィールドと revise 1 キーで、残りは既存操作の再配置に閉じる。
不確かなのは 4 択の見積りの精度で、`verified_with` の実測が溜まるまでは幅を持たせた表示にする。
