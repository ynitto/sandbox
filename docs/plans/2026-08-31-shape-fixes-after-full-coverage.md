## 2. A: `plan` の出力を短く固くする

**いま何が起きているか。** 必須セクション 6 つ（why / desc / scope / risks / acceptance /
size）× 複数タスクを **1 回の JSON 配列**で出させており、実測 5 回のうち 4 回は
出力が途中で切れて `_extract_json_array` が 0 件を返した（成功した 1 回は 119 秒・4 件）。
本番はここで「タスクが 1 件も出なかった」として plan を諦め、人へ回す。

**直し方（採用）。** タスクを 1 件ずつ出させ、機械が集める。`split` → `map` と同じ形で、
planner には「次の 1 件だけを出せ」と言い、件数の制御は本体が持つ。

**却下した案。**
- *セクションを 2 回に割る（why/desc を先、残りを後）*: 呼び出しが倍になるうえ、
  2 回目が 1 回目のタスク集合を復唱する必要があり、取り違えの面を増やす。
- *`--format json` の変種へ振り替える*: 出力長の問題であって器の問題ではない
  （切れているのは JSON として妥当な途中まで）。器を固めても長さは縮まない。

**受入基準（測り方）。** `project_eval.py` の `PP1` をそのまま使う——本番の
`_validate_backlog_spec` が全タスクで通り、charter に無い書込先を書かないこと。
**3/5 以上で採用**（現状 1/5）。分割の実装は本体側（`plan_via_agent`）に入れ、
ハーネスは触らない。

## 3. B: `repo_map` の前置きを機械が落とす

**いま何が起きているか。** モデルは**リポジトリを読めている**（`ingest` / `pytest` /
`Makefile` に言及する）のに、返すのが要約ではなく作業メモになる回が多い
（「以下の手順で、収集…」で終わる）。本番はその本文を `.strip()[:4000]` してそのまま
`context/<repo>.md` に保存し、planner へ渡す——**前置きが計画の材料になっている**。

**直し方（採用）。** 出力契約のゲートを 1 つ足す。プロンプトは既に
「出力は要約本文のみ（前置き・後書きなし）」と言っているので、**言わせるのは済んでいる**。
残りを機械が落とす: 見出し（`## 構造` 等）で始まる最初の塊より前を捨て、捨てた量を
journal に残す。落とした結果が空なら保存しない（前と同じ「生成なし」へ倒す）。

**却下した案。**
- *セクション見出しを JSON キーにして構造化する*: `repo_map` の成果は人と planner の
  両方が読む散文で、構造化すると planner プロンプトの組み立て側も変える必要がある。
  A（`plan` の分割）と同時に触ると、どちらが効いたのか測れない。

**受入基準。** `RM1` の判定はそのまま（実在する構成へ言及）。加えて、**前置き落としの
前後で同じ出力を採点し直し**、落とした後だけ通る回を数える——機械が拾えた分がそのまま
効果になる。**3/5 以上で採用**（現状 1/5）。

## 4. C: `review` に材料を届ける

**いま何が起きているか。** `_review_prompt` に入るのは **charter だけ**である。
「現状の成果物がまだ満たせていない点を洗い出せ」と問いながら、成果物の状態は 1 文字も
渡らず、CLI（`ollama-json`）は道具も持たない。**PV1（撤去された charter verifier）と
同じ構造**で、モデルは推測するしかない。実測 2/5 の落ち方も推測の形で、`workspace` に
ファイル名（`ingest.py`）を書く。

**直し方（採用）。** 材料を 2 つ足す。どちらも本番が既に持っている決定的な情報である:

1. **acceptance の判定結果**（charter の決定的コマンドの PASS/FAIL）
2. **backlog と archive の要約**（何が done で何が残っているか。`plan` は既に受け取っている）

**却下した案。**
- *道具（`--tools read`）を与えてワークスペースを読ませる*: `retrieve` で測ったとおり
  道具は使えるが、レビューは**何を読むべきか**が決まっていない面で、探索に 30 ラウンドを
  払う価値が実測で示せていない。材料を渡すほうが安く、先に試す順序として正しい。
- *面ごと撤去する*: PV1 と違い `review` は opt-in で人が明示的に回す面であり、
  材料さえ届けば判断の当否を測れる。撤去は材料を足しても直らなかったときの次善。

**受入基準。** 材料を足したうえで `RV1` の判定を**当否まで広げる**——charter の
deliverables のうち意図的に未達にした 1 件を指摘できること。**3/5 以上で採用**。
材料を足しても 0〜1/5 なら、モデルではなく面の設計を疑い、撤去を検討する。

## 5. 先に測る 2 つ（実装より前に数字が要る）

**`map` の道具を外せるか。** `map` は本番の起動形（`--tools bash`）で 2/5、道具ゼロの
起動形では 5/5 だった。材料がプロンプト内で完結する `map` ノードは道具が要らないので、
`node.readonly` を宣言すれば `--tools` が落ちる。ただし **split がファイルを配る flow では
読み取りが要る**ので、役割ごと `READONLY_ROLES` に足すのは誤り。測るのは
「planner が材料の在り処を見て `readonly` を宣言できるか」——`planner_eval` に 1 ケース。

**上流に欠落のチャネルを作れるか。** 統合役の欠落運搬は `carry_dependency_gaps` で閉じたが
（SY2P 5/5）、**散文にしか申告が無い場合**は機械にも手が無い（SY2 0/5）。`work` / `generate`
の完了 envelope は `{"ok": ...}` をそのまま `data` へ入れるので、`{"ok": true,
"warnings": [...]}` と書かせれば同じ経路に乗る。**ただし言わせて直るかは未測定**で、
この日の 5 例は全部「言わせても直らない」だった。プロンプトへ足す前に測る。

## 10. クラウド CLI への波及の手当て（2026-08-31 追記）

この計画の A・B と llmjson のフェンス優先（`72817a26`）は**バックエンド無条件の共有コード**に
入っていたため、クラウド CLI（kiro / claude / codex / copilot）で走る構成に 3 つの波及が
あった。直した（テストは全 8 スイート緑・数字はどれも実挙動の確認で、e4b の実測は動かして
いない）:

1. **plan の 1 件ずつはオブジェクト限定の器に限る。** 真因（`--format json` はオブジェクト
   しか返せない）はローカルの器の性質なのに、配列を返せる器にも 1 件ずつを課すと
   タスク K 件に K+1 回の呼び出し（毎回 charter 全文）を払う。器の性質は定義の宣言
   `json_object_only`（ollama の json profile が true）で読み、**argv の綴りでは判定しない**。
   スキルへは入力 `contract`（single / array）で運ぶ——一般則「`--format json` の面に
   配列契約を書かない」の対偶で、配列を返せる面から配列契約を取り上げる理由も無い
2. **repo_map の前置き落としは長い作業報告に限る。** 短い概要段落（200 字以内）は要約の
   書き出しなので残し、**散文だけの要約は全捨てしない**（読めているのに「生成なし」へ
   倒れていた。B の実測の失点は本文ゼロ・`no_command` で、この変更が拾い直す面ではない
   ——機械の適用範囲を実測の失敗の形へ絞っただけ）
3. **llmjson は地の文の JSON をフェンスより先に見る。** フェンスは例示・引用の器でもあり、
   自由文の器は「本文に成果・後ろに例のフェンス」で書く——フェンス優先だと例を成果として
   静かに誤採用する。地の文＝フェンスと行内引用を潰した本文で、道具ループの実測の形
   （フェンスの最終成果・行内引用の成果・後続の制御封筒）はどれも隠れない
