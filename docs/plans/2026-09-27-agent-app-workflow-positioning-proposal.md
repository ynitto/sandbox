# agent-app ワークフローの打ち出し案 — タスクとの違いと、複数 AI にする意味

> 作成: 2026-09-27
> 対象: `tools/agent-app`（ワークフロー領域・ホームの振り分け・定型化）、README の説明
> 状態: 提案（画面は ASCII のイメージまで。実装は承認後）

## 1. いま何が伝わっていないか

コードと README を読むと、タスクとワークフローは**作り方も見た目も同じ**になっている
（ADR-7「ワークフローもタスクと同じ教示の骨格で作る」）。骨格が同じこと自体は正しいが、その結果、
利用者から見える差が名前しか残っていない。

| 場所 | いまの言い方 | 伝わらないこと |
|---|---|---|
| 作成画面 | `新しいタスク` / `新しいワークフロー`（`teaching.js:109` / `flow.js:240`）。見出し以外は同じ | どちらを選べばよいか |
| ワークフローの作成の例文 | 「変更依頼を調査し、並列に実装して、品質を確認したい」 | 「並列」「品質」がなぜ複数 AI で良くなるのか |
| ワークフロー一覧の先頭 | 「依頼から実行」「工程は依頼から決めます」 | 会話で頼むのと何が違うか |
| 定型化の分類（`shared/reuse.js`） | 「複数担当の分担・独立レビュー・並列処理が必要な作業」 | 基準は AI への依頼文にだけあり、画面と README には無い |
| ホームの振り分け | タスク・ワークフローを**流用**できるかだけを見る | 「この依頼は複数 AI の方が向く」とは言わない |
| 実行結果 | 工程の進捗と最終結果 | 複数 AI にした**見返り**（誰が何を落としたか）が見えない |

要するに、ワークフローは「工程の多いタスク」に見えている。工程の数で選ぶと、ほとんどの仕事は
タスクで足り、ワークフローは使われない。

## 2. 一般的なエージェントアプリの動向

| 動き | 例 | agent-app への示唆 |
|---|---|---|
| 並列起動はもう当たり前 | Cursor は worktree で最大 8 本、Codex app もリポジトリをまたいで並列。Superset などは 100 本規模を売りにする | 「たくさん同時に回せる」は差別化にならない。agent-app も worktree の会話でもう持っている |
| 並列は**分けられる仕事でだけ**得をする | Google Research（2026-01）: 並列化できる仕事で最大 +81%、直列の仕事では −39〜70%。Anthropic の multi-agent research: 単独の会話の約 15 倍のトークン。向くのは「並列度が高い・1 つの文脈に収まらない」仕事で、文脈を強く共有する仕事は向かない | 「何でも複数 AI」は逆効果。**向く形を名指しして**勧めるのが正しい |
| 並べた結果の比べ方は未解決 | 並列の本数は増えたが、エージェント間の調整や best-of-n の選び方は各ツールとも人任せ | agent-flow には `judge` / `filter` の**機械判定の契約**（`decision`）と、終端の `verify` が緑でないと完了にしない決まりが既にある。ここは先行している |
| 別の AI に確かめさせる | 書いた AI と別の AI にレビューさせる形が定着しつつある（VS Code のマルチエージェント、Addy Osmani の "code agent orchestra"） | agent-app は copilot / claude / codex / kiro / herd を**同じ画面で混ぜられる**。ベンダーをまたいだ確認は単一ベンダーのアプリにはできない |

出典は末尾。

## 3. 打ち出しの軸

### 3.1 一言で分ける

> **タスクは手順を覚える。ワークフローは役割を分ける。**

| | タスク | ワークフロー |
|---|---|---|
| 繰り返すもの | 手順（同じ入力なら同じ動き） | 分担（作る・確かめる・比べる・まとめる） |
| 担当 | 1 つの AI が最初から最後まで | 役割ごとに別の AI（別のモデル・別のベンダーでもよい） |
| 良くなるもの | 再現性・手数の少なさ・定期実行 | 結果の確からしさと幅 |
| 完了の決め方 | 最後の工程まで進んだ／確認コマンドが通った | **別の担当の確認が通った**とき（通らなければ作り直す） |
| 費用 | 少ない | 多い（担当の数だけ）。だから向く形でだけ使う |
| 向かない仕事 | 自分の成果を自分で確かめても意味がない仕事 | 1 本の文脈で順に進める仕事（分けると遅く・悪くなる） |

「工程が多いか」では選ばない（これは `reuse.js` の分類でもすでに守っている原則）。

### 3.2 複数 AI が効く 3 つの形

ワークフローを「複数の AI を動かす仕組み」として売るのではなく、**効き方で 3 つに名前を付けて**売る。
agent-flow の 7 パターンを利用者の言葉で束ねたもの。

| 画面の言葉 | 何が良くなるか | 中身（agent-flow のパターン） | 向く例 |
|---|---|---|---|
| **別の目で確かめる** | 作った AI の見落としを、別の AI が落とす。確認が通るまで作り直す | adversarial-verification、loop-until-done（`generate`/`work` → `verify` → 差し戻し） | 修正と別ベンダーのレビュー、仕様書と実装の突き合わせ、翻訳の検品 |
| **並べて比べる** | 複数の案を出させ、決めた基準で機械的に選ぶ。「1 回目がたまたま悪い」を避ける | tournament、generate-and-filter（`judge`/`filter` の判定契約） | 設計案・命名・文面の候補出し、失敗しやすい修正を 3 通り試す |
| **分けて広く進める** | 1 つの AI の文脈に入りきらない量を、分けて同時に進め、最後にまとめる | fan-out-and-synthesize、map-reduce、classify-and-act | 多数ファイルの調査、Issue の一括仕分け、複数リポジトリの横断確認 |

3 つとも**「1 つの AI ではできない、または自分で自分を確かめても意味がない」**ことが共通点で、
ここがタスクとの境目になる。

### 3.3 agent-app ならではの強み（ほかのアプリと比べたときの打ち出し）

1. **ベンダーをまたいだ確認**。書くのは codex、確かめるのは claude、のように担当ごとに AI を変えられる。
   同じモデルの自己レビューは同じ癖で見落とすので、「別の目」を本当に別にできる。
2. **比べ方が人任せではない**。候補の採否は宣言した基準で機械が決め（`decided_by: machine`）、
   決めきれなければ黙って選ばずに止まる。「8 本並べたが、どれを取るかは人が全部読む」にならない。
3. **完了の意味が違う**。全工程が終わっただけでは完了にせず、確認の担当が合格を出して初めて完了。
4. **数はローカル、要所はクラウド**。候補出しや広く分ける担当は手元の AI（herd。何回呼んでも費用が
   増えない）に回し、まとめと最終確認だけクラウドの AI に任せる。タスクで既に持っている
   「費用で回し方を変える」考え方（README「タスクの回し方は、選んだ AI で自動的に変わる」）の延長。

## 4. 画面への落とし込み（イメージ。承認前）

新しい部品は作らない。すべて既存の形を借りる。

### 4.1 ワークフローの作成画面に「形」を 3 つ並べる

借りる形: `.blank.teaching-create`（「新しいワークフローを教える」そのもの）。形の選択は `.row` に
並べた `button.small`（選んだものだけ `is-on`）。説明は各ボタンの `title` に置き、画面には常駐させない。

```text
┌───────────────────────────────────────────────────────────────┐
│  新しいワークフロー                                            │  ← 既存の <h2>（ワークベンチが持つ）
│  どう分担させますか                                            │  ← eyebrow 相当の 1 行（.sub）
│                                                               │
│  [別の目で確かめる] [並べて比べる] [分けて広く進める] [おまかせ] │  ← .row の button.small（1 つ選ぶ。既定はおまかせ）
│                                                               │
│  実現したいこと                                                │
│  ┌─────────────────────────────────────────────────────────┐  │
│  │ 例: 不具合を直し、別の AI に確かめさせる                  │  │  ← 例文は選んだ形に合わせて差し替える
│  └─────────────────────────────────────────────────────────┘  │
│  保存名（任意）                                                │  ← 既存どおり小さく畳む
│                                                               │
│  (編集設定 ▾)                          [手動で作成] [編集開始] │  ← 既存の .task-actions。主ボタンは 1 つ
└───────────────────────────────────────────────────────────────┘
```

- 選んだ形は最初の依頼文（`flow-teaching-prompt`）に 1 行足すだけ（例:「作る担当と確かめる担当を分け、
  確かめる担当は別の AI にする。確認が通らなければ作り直す」）。定義の形式は変えない。
- 「おまかせ」は今の動き（AI が目的から決める）。
- タスクの作成画面には何も足さない。差は**ワークフロー側だけが問いを持つ**ことで出す。

### 4.2 「依頼から実行」のカードにも同じ 3 つを置く

借りる形: `.execution-card` + `.execution-card-head`（いまの「依頼から実行」カードのまま）。

```text
┌ 依頼から実行 ──────────────────────────────────── 待機中 ┐
│ 工程は依頼から決めます                                   │  ← 既存の 1 行
│ [別の目で確かめる] [並べて比べる] [分けて広く進める] [おまかせ] │
│ ┌──────────────────────────────────────────────────────┐ │
│ │ 依頼内容を入力                                        │ │
│ └──────────────────────────────────────────────────────┘ │
│ (実行設定 ▾)                                     [実行] │
└──────────────────────────────────────────────────────────┘
```

選んだ形は planner への要求に 1 行足す（パターンの指定）。規模・計画の確認は今の実行設定のまま。

### 4.3 実行結果に「分担と確認」カードを足す（見返りを見せる）

借りる形: 「履歴」の実行詳細にある `.execution-card`。行は `.row` + `.sub`、状態は `.status`。
複数 AI にした意味は、ここで**事実として**見せる。宣伝文は書かない。

```text
┌ 分担と確認 ─────────────────────────────────────── 合格 ┐
│ 3 つの AI で進め、確認で 1 回作り直しました              │  ← 1 行の <p>
│                                                          │
│  作る      codex  (gpt-5.x)        2 回                  │
│  確かめる  claude (sonnet)         1 回目 不合格 → 2 回目 合格 │
│  まとめる  herd   (ローカル)       1 回                  │
│                                                          │
│  候補 3 件 → 採用 1 件（基準で決定）            [候補を見る] │  ← 並べて比べたときだけ出る
└──────────────────────────────────────────────────────────┘
```

- 材料は agent-flow が既に書いている `final.json`（`verification`）、ノードの `kind` と担当、
  `judge`/`filter` の `data`（`kept` / `winner` / `decided_by`）。新しい記録は足さない。
- 確認で何も落ちなかったときも「確認 1 回で合格」と出す（黙ると確認していないように見える）。

### 4.4 ホームの振り分けで「複数 AI 向き」を言う

借りる形: 振り分けが既に残す「案内の 1 枚」と実行情報の 1 行。

```text
  振り分け：会話で実行 ／ 別の AI に確かめさせる形が向きます [ワークフローで実行]
```

- いまの判定（答えるだけ / 会話 / 流用）に「形の提案」を 1 つ足す。**送信は止めない**
  （流用と違って確度が低いので、実行情報の 1 行にとどめる）。
- 押すと 4.2 のカードに本文と形が入った状態で開く。

### 4.5 定型化の提案理由を 3 つの形の言葉にそろえる

`reuse.js` の分類と、定型化ダイアログに出る「提案理由」を、3.1 の表と 3.2 の 3 つの言葉にそろえる。
「複数担当の分担・独立レビュー・並列処理」を「別の目で確かめる／並べて比べる／分けて広く進める」に言い換える。

## 5. 言葉

| 使う | 使わない（内部名・抽象語） |
|---|---|
| 別の目で確かめる | adversarial-verification、verify ノード、独立レビュー |
| 並べて比べる | tournament、best-of-n、generate-and-filter、judge |
| 分けて広く進める | fan-out、map-reduce、並列処理 |
| 作る／確かめる／まとめる（担当） | worker、evaluator、synthesize |
| 作り直し | rework、差し戻しノード |
| 基準で決定 | decision 契約、decided_by: machine |

README では「マルチエージェント」も使わず、「複数の AI で分担する」と書く。

### 効いたかを見る数字（既存の記録から取れるもの）

- 定型化で AI が提案した種類を利用者が変えた割合（使い分けが伝わっていれば下がる）
- ワークフローの実行のうち、確認で 1 回以上作り直しになった割合（「別の目」が実際に何かを落としている証拠。
  ほぼ 0 なら確認担当が甘いか、ワークフローにする必要のない仕事）
- 並べて比べたときに「決めきれず停止」になった割合（基準の書き方の問題を見つける）

## 7. やらないこと

- **並列の本数を売りにしない**。「同時に 8 本」の表示やスライダーは持たない。本数ではなく形で選ばせる。
- **AI 同士の自由な会話（チーム・チャット）は持たない**。受け渡しは工程の成果物だけ。文脈を共有させるほど
  直列の仕事と同じ弱点を持つため。
- **候補を人が並べて読み比べる画面は作らない**。比べ方は基準の宣言で決める（「候補を見る」は確認用）。
- タスクの側に複数 AI の機能を足さない。境目がまたぼやける。タスクの結果を別の AI に確かめさせたい
  ときは、既存の「フォーク」でワークフローへ移す。

## 追補（0.43.0）: 積み残しの対応

- 振り分けの `routine` / `team` は会話を起こしてから訊く（送る前は `--ask handling,task,flow,skills`）。応答の保存前に
  届けばその応答の実行情報に、保存後なら保存済みの応答に足して画面へ読み直させる（`session:updated`）。
- 4.4 の [ワークフローで実行] を実行情報の行に付けた（部品は生ログの「端末を操作」と同じ `button.small`）。依頼から実行を
  本文と形入りで開くだけで、実行はしない。
- 依頼から実行で形を選んだときは、効かない「規模」を実行設定の要約・選択肢・依頼から外す。
- 実機のスモークテストを今の画面に合わせて通した。途中で見つけたタスク編集の見出しの跳ね（端末を起こすと 135px 上がる）と、
  ワークフロー概要の見出し（タスクと同じ「手動実行」へ）を直した。
- 選択肢の切り替え（`.seg`）は、親画面の「つなげた切り替え」に統一した（0.44.0）。ワークベンチ側も同じ形にし、
  入力欄の中では欄の幅に合わせて均等に並べる。工程の「実行方法」は短い呼び名で 1 行に収めた。作成画面の保存名は
  今のまま（最初に出す）。
