# Agent Dashboard: 定常業務の実行パラメータ入力ダイアログ設計

## 背景

Agent Dashboard の「今すぐ実行」は、入力が必要な定常業務でも直ちにエージェント CLI を起動する。
現状は起動プロンプトへ「不足する入力を人へ質問する」よう追記しているが、agent-ollama などの
弱いモデルでは質問漏れや仮値での実行が起こり得る。入力要否の判定、入力受付、未入力の拒否、
プロンプトへの反映をプログラム側で決定的に行う。

## 調査結果

- agent-loop の `prompts[]` には入力パラメータを宣言する正式フィールドがない。
- statemachine-use の正式スキーマには `{{input}}` と `{{context.KEY}}` があるが、必須入力一覧はない。
- 現行 Dashboard は `workflow.yaml` 本文中の `{{input}}` と空の `context` 値を推測している。
- 現行判定は `action_file` / `condition_file` を読まないため、入力参照を見落とす。
- 空の `context` 値を必須入力とみなす規則は statemachine-use の正式スキーマにはない。

## 検討した案

| アプローチ | 実装コスト | リスク | 保守性 | 拡張性 | 学習コスト | 推奨度 |
|---|---|---|---|---|---|---|
| 既存テンプレート参照を解析する | 低 | 低 | 高 | 中 | 低 | ★★★ |
| agent-loop / statemachine-use に入力宣言スキーマを追加する | 高 | 中 | 高 | 高 | 中 | ★★☆ |
| LLM への質問指示を継続する | 低 | 高 | 低 | 低 | 低 | ★☆☆ |

初版は既存テンプレート参照の解析を採用する。新しい設定契約を増やさず、すでに書かれている
実行時参照を入力要否の根拠にする。入力型は文字列だけとする。

## 採用設計

### パラメータ検出

agent-loop の定常業務は、解決済み `prompt` に含まれる `{{key}}` を入力パラメータとして抽出する。
同じキーの複数出現は一項目へまとめる。

statemachine-use は YAML パーサで `workflow.yaml` を読み、正式スキーマに従って次を検査する。

- インラインの `action` / `condition` / `on_enter` / `on_exit`
- `action_file` / `condition_file` と自動探索されるアクション・条件ファイル
- `{{input}}`
- `{{context.KEY}}` のうち `context.KEY` に非空の初期値がないもの

`{{last_output}}`、`{{current_state}}`、`{{step_count}}`、`{{history.*}}`、ステートの
`output_key` は実行中に生成されるため入力欄にしない。設定ファイルを読めない、YAML を解析できない、
参照ファイルが定義ルート外を指す場合は入力なしと推測せず、実行を止めて定義エラーを表示する。

### HTML ダイアログ

OS 標準ダイアログや Electron の `dialog` API は使用しない。Renderer の HTML 層へ既存画面と同じ
`<dialog>` 要素を追加し、「今すぐ実行」のクリック時に必要な場合だけ `showModal()` する。

- パラメータキーを関連付けた `<label>` と必須の `<input type="text">` を表示する。
- 最初の入力欄へフォーカスし、Tab 順は表示順と一致させる。
- 全項目が非空になるまで実行ボタンを無効化する。
- Escape、キャンセル、閉じる操作では何も起動しない。
- エラーは該当入力の近くへ表示し、実行中は二重送信を防ぐ。

入力項目がなければダイアログを開かず、従来どおり直ちに実行する。

### 実行データフロー

1. Cowork overview が各項目へ検出済みのパラメータキーを付ける。
2. Renderer は「今すぐ実行」でキーの有無を確認する。
3. キーがあれば HTML ダイアログで値を受け取り、なければ既存経路を使う。
4. IPC は `{ itemId, parameters }` を main プロセスへ渡す。
5. main プロセスは定義を再読込し、必須キー不足と未知キーを拒否する。
6. agent-loop は `{{key}}` を値へ置換してから起動する。
7. statemachine-use は `input` と `context.KEY` を区別した構造化入力ブロックを起動指示へ組み込む。

Renderer の値を信頼せず main プロセスで再検証する。HTML 生成時はキーと値をエスケープし、
入力値をシェルコマンドへ直接連結しない。

### エラー処理

- 設定解析失敗: 実行せず、対象ファイルと短い理由を表示する。
- 必須値不足・未知キー: IPC 側で拒否し、ダイアログ内へエラーを戻す。
- 起動失敗: 既存の実行失敗バナーと履歴を使う。
- キャンセル: 状態・履歴・キャッシュを変更しない。

現行の LLM 向け入力質問補助は、検出できた入力を質問させる用途から外す。入力定義そのものを
確認できない場合も LLM へ丸投げせず、設定エラーとして扱う。

## テスト方針

最小の回帰テストとして次を追加する。

- agent-loop prompt の複数・重複プレースホルダーを抽出できる。
- statemachine-use のインライン定義と外部ファイルから入力キーを抽出できる。
- 組み込み変数、出力キー、初期値済み context を入力扱いしない。
- 設定解析失敗、定義ルート外参照、必須値不足、未知キーを拒否する。
- パラメータなしは直接実行し、ありは HTML ダイアログを開く。
- キャンセルでは IPC を呼ばず、入力完了後だけ一度実行する。
- agent-loop の置換結果と statemachine-use の構造化入力ブロックを確認する。

## 実装計画

1. Cowork main に入力仕様の抽出・検証・agent-loop 置換・statemachine 入力整形を追加する。
2. overview と IPC / preload の既存契約へ `parameters` を最小限追加する。
3. `index.html` に入力用 `<dialog>`、Renderer に表示・検証・実行処理、既存 CSS に必要なスタイルを追加する。
4. Cowork の既存テストへ抽出・実行・HTML 操作の回帰テストを追加する。
5. Agent Dashboard の対象テストと全テストを実行する。

## 既存スキルとの関係

- `statemachine-use`: 入力参照と外部ファイル解決の正典として使用する。
- `ui-designer`: HTML フォームのラベル、フォーカス、エラー表示、二重送信防止へ適用する。
- `ponytail`: 新規入力スキーマや依存関係を初版では追加せず、既存テンプレート契約を再利用する。
