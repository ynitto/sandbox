# ワークフロー機能の改善提案 — adhoc-20260815-235229-7532 の解析から

`af/adhoc-20260815-235229-7532` は、agent-dashboard のワークフロー機能が「設計フローと実装フローの分離」を
12 並列タスク（t1〜t12）とレビューラウンド（r13 / r14 / r16）で実装した run の成果ブランチである。
その後エージェント CLI セッションが 1 コミット（設計 run の readonly 契約を agent-flow 本体まで実装）で
後追い修正し、さらに今回 5 件のバグ（CI 赤・画面間のダイアログ差異・冗長な説明文・編集タブの用途間差異・
プリセットの見た目）を個別修正した。本書は「なぜ後追い修正が必要な成果になったか」を解析し、
ワークフロー機能そのものへの改善案をまとめる。個別バグの修正内容は本書の対象外（修正コミット参照）。

## 解析 — 後追い修正が必要になった 4 つの構造要因

### 1. タスク分割が「1 ファイル = 1 エージェント」だった

t1=adhoc.js、t2=design-session.js、t3=preparation.js、t4=ipc+preload、t5=renderer/adhoc-flow、
t6=renderer/backlog、t7=styles.css、t8〜t11=テスト、t12=docs と、分割単位がほぼファイル境界に一致する。
この分割は並列化しやすい反面、**利用者から見える 1 つの振る舞いが複数エージェントへ水平に裂ける**:

- 同じ用途の「設計フローを選ぶ UI」を t5（ワークフロー画面）と t6（プロジェクト画面)が別々に実装し、
  カード構成・既定選択・エラーメッセージが食い違った（ダイアログ差異バグ）。
- マークアップ担当と分離されたスタイル担当（t7）が、同梱プリセットのカードへ保存済みカードの
  見た目（wf-saved-card）を与え、プリセットが利用者の保存物に見えた（プリセット表示バグ）。
- テスト担当（t8）は実装担当の実行前提（profiles.json の tier 候補宣言）を知らず、fixture 不足の
  テストを書いてそのままコミットした（CI 赤バグ）。

### 2. 「全体が緑」を完了条件にする工程が無かった

t8 が入れたテストは一度もグリーンにならないままブランチ終端まで残った。レビューラウンドは
契約整合の修正（r13: main プロセス、r14: 準備契約とテスト追随）を行ったが、**スイート全体の実行結果を
run の完了条件にしていない**。成果物の CHANGELOG が掲げる「契約検証」も `node --test` 2 ファイルの
実行であり、CI（dashboard の npm test 全体 + python + docs 検査）とは一致しない。r15 は成果の無い
欠番で、何を試して何が出なかったのかも残っていない。

### 3. 契約は定義したが「見せ方」を契約にしていない

purpose / libraryVisibility / scope / snapshot という**データ契約**は設計書・CONTEXT.md まで
一貫して実装された。一方「既存画面との一貫性」「文言の量」「内部語彙を画面に出さない」という
**表現の契約**は無く、各エージェントが説明文で自衛する UI を作った — 「保存済み（library）」という
ストレージ語彙の見出し、カードへの sha256 digest 表示、常設の制約バナー、互換設定の折りたたみ、
選択内容の pre ダンプなど（冗長文言・編集タブ差異バグ）。禁止事項は選択肢の制限（human / split を
候補から外す等）で既に守られており、説明文は二重の防衛だった。

### 4. レイヤーを跨ぐ契約が run の範囲外に落ちた

「設計 run は読み取り専用」という契約は、ワークフロー成果では dashboard の文言と plan 生成
（readonly フラグ付与）までで、実行エンジン（agent-flow の run_agent → headless_cmd）には強制が
なかった。エージェント CLI の後追いコミットが Python 側へ readonly を配線してはじめて実効化した。
run の変更対象が dashboard 配下に閉じており、**契約がどのレイヤーで強制されるかを設計段階で
確認する工程が無かった**。

## 改善案

優先度は、再発時の被害（CI 赤・利用者の誤認）が大きい順。

### P1: 統合検証ノードを実装系テンプレートへ標準装備する

並列タスクのマージ後に、対象パッケージのテストスイート全体（この repo なら CI と同じ系統）を
実行する verify ノード（`continuation: retry`）をワークフロー終端の既定にする。テストを追加する
ノードには「追加したテストを単独実行して緑を確認した出力」を成果へ含める契約を足す。
run の完了条件を「全ノード done」から「終端 verify が緑」へ寄せ、赤のまま終端した run は
公開失敗と同じ復旧可能状態として表示する。

### P2: 分割単位を「ファイル」から「利用者から見える振る舞い」へ

plan 生成時の分割方針として、UI を持つ振る舞いはマークアップ・スタイル・呼び出し側（複数画面に
現れるなら全画面）を 1 ノードが縦に持つことを既定にする。複数画面で同じ用途の UI が要る場合は、
先に共有部品（または共有 HTML ビルダー）を切り出すノードを置き、各画面のノードはそれを消費する。
ファイル単位の水平分割は、衝突回避が必要な大規模変更に限る明示オプションとする。

### P3: UI 一貫性の作業ルール（methods）を同梱する

「同じ用途の既存 UI を探し、構造・文言量・状態表現を揃える」「scope 名・digest・visibility などの
内部語彙を画面へ出さない」「禁止事項は常設の説明文ではなく選択肢の制限で守り、説明は操作時の
通知に限る」を worker 向け作業ルールとしてカタログへ追加し、UI を変更する purpose のノードへ
自動付与する。今回の冗長文言・語彙露出はいずれもこのルールで書く前に防げた種類のものである。

### P4: レビューラウンドへ観点（レンズ）を割り当てる

r ラウンドを「契約整合」の 1 本槍にせず、二重実装の検出（同用途 UI・同型ロジックの重複）、
画面間・用途間の表現差異、文言量の 3 観点を別ノード（または順番の異なるチェックリスト）として
回す。成果が無かったラウンドも「何を見て何が出なかったか」を run 履歴へ残し、r15 のような
無言の欠番を無くす。

### P5: レイヤー境界の強制点を設計成果の必須項目にする

設計書テンプレートの「## 変更対象」へ「契約ごとの強制レイヤー」を書かせる（例: readonly は
agent-flow の CLI 起動引数で強制、dashboard は表示のみ）。設計 run の自己点検・実装後の verify に
「文言でしか守られていない契約は無いか」を確認する項目を足し、プロンプト上の約束と実行時の
強制を区別して扱う。

### P6: run 終端で CI 相当の結果を成果へ添付する

P1 のローカル統合検証に加え、公開（ブランチ push）後の CI 結果を run の delivery へ取り込み、
赤なら要対応として表示する。ワークフロー機能はすでに公開失敗を構造化して復旧操作を出せるため、
同じ器へ「公開は成功したが CI が赤」を載せるのが自然な拡張になる。

## 検証方法（提案を実装する場合）

- P1 / P4 / P6: 既存の adhoc-flow.test.js の run 契約テストへ、終端 verify ノードの既定化と
  完了条件の変化を追加する。
- P2 / P3: plan 生成（テンプレート・methods 自動付与）の単体テストで分割方針とルール付与を固定する。
- P5: 設計成果の必須節検査（REQUIRED_DESIGN_SECTIONS）に追加項目の検査を足す。
