> 対象: `agent-project` / `agent-flow` / `agent-amigos` / `agentcore`
> 効く柱・原則: **柱1 / C1・C7・C8** — プロンプト境界の JSON 描画を圧縮して個人クレジットの
> 消費を下げる。描画規約は agentcore に 1 実装（C7）、効果は before/after で計測して残す（C8）。

「JSON はトークン量的に冗長」という意見を、実際のやり取り箇所と実測で確認した。結論を先に:

1. **冗長さの大半は JSON そのものではなく `indent=2` と、日本語の ascii エスケープ回避の
   不徹底にある。** 整形をやめるだけで実測 −28〜−35%。ここは中身が 1 ビットも変わらない
   純粋な無駄で、最初に刈るべき原資である。
2. **均質な dict 配列（キーが全行で同じ）だけは、表形式描画（TOON 風）でさらに −20〜−40% 取れる。**
   それ以外の形（入れ子・散文混じり）では compact JSON が最有力で、YAML への置換に一貫した
   優位は無い。
3. **LLM の出力契約は JSON のまま変えない。** 出力側の置換は契約違反→修復再呼び出しの
   期待コストが節約分を食い潰す構造にあり、割に合わない（§4.3）。
4. スキーマ（`schemas/` のデータ契約）は変えない。**保存・転送は今日どおり JSON、変えるのは
   プロンプト境界での「見せ方」だけ**で、描画は決定的・可逆（キー集合を保存）にする。

## 1. 前提の切り分け — どの JSON がトークンを消費するのか

ファミリーの JSON は 3 つの層にあり、トークンを消費するのは 1 層だけである。

| 層 | 例 | トークン消費 |
|---|---|---|
| 保存・転送（git / バス / 契約ファイル） | board の bid/award、node-budget 台帳、tasks、run メタ、`schemas/` 準拠の全契約 | **ゼロ**（LLM に入らない限り課金されない） |
| プロンプトへの注入（エンジン → LLM） | doctor の稼働シグナル、deps の構造化 data、amigos の納品 MANIFEST | **入力トークンとして毎回課金** |
| 出力契約（LLM → エンジン） | planner のタスクグラフ、evaluator の decision、verify 封筒、assess 採点 | **出力トークンとして毎回課金**（単価は入力より高い） |

したがって「JSON が冗長」への正しい応答は、**契約ファイルや schemas をいじることではなく、
プロンプト境界の描画だけを変えること**である。これは「スキーマは変えない」という制約とも
一致する——データモデルと正典（`schemas/`）はそのまま、シリアライズ表現だけの話にする。

### 1.1 プロンプト境界の現状の棚卸し

**注入側（エンジン → LLM）**

| 箇所 | 現状の描画 | 規模 |

JSON 前提で整備済み**である。

## 2. 実測

### 2.1 方法

実在の接点を模した現実的ペイロード 6 種（日本語の goal・detail を含む）を、描画形式だけ変えて
トークン数を比較した。トークナイザは tiktoken `o200k_base` / `cl100k_base` と、参考として
Claude v1 系レガシートークナイザ（litellm 同梱の `anthropic_tokenizer.json`）の 3 種。
現行 Claude のトークナイザは非公開のため**絶対値は代理値**だが、3 系で相対傾向が一致して
おり、形式間の比較には十分と判断する。

比較した形式:

- `json indent=2` … doctor が今日使っている整形
- `json 既定` … `json.dumps` 既定（`", "` / `": "` 区切り）。deps 注入が今日これ
- `json compact` … `separators=(",", ":")` + `ensure_ascii=False`
- `json compact ascii` … compact + `ensure_ascii=True`（反面教師）
- `yaml` … PyYAML `safe_dump(allow_unicode=True)`
- `toon 風表形式` … 均質な dict 配列を「ヘッダ 1 回 + CSV 行」に畳む描画
  （例: `items[30]{file,line,kind}:` の下にカンマ区切り行。非均質部分はキー: 値のまま）

### 2.2 結果（o200k トークン数。括弧は indent=2 比）

| ペイロード | indent=2 | json 既定 | compact | compact ascii | yaml | toon 風 |
|---|---|---|---|---|---|---|
| doctor 稼働シグナル（runlog 20 件・blocked 4 件） | 1825 (100%) | 1571 (86%) | 1310 (72%) | 2035 (112%) | 1469 (81%) | **1123 (62%)** |
| planner 出力 6 ノード | 364 (100%) | 292 (80%) | **242 (67%)** | 481 (132%) | 273 (75%) | 305 (84%) |
| reduce の deps 注入（均質 30 件） | 1576 (100%) | 1300 (83%) | 1029 (65%) | 1099 (70%) | 1207 (77%) | **651 (41%)** |
| evaluator 出力 | 170 (100%) | 142 (84%) | **124 (73%)** | 238 (140%) | 131 (77%) | 144 (85%) |
| verify 封筒 | 44 (100%) | 36 (82%) | 33 (75%) | 77 (175%) | 33 (75%) | 33 (75%) |
| assess 採点 | 23 (100%) | 18 (78%) | **13 (57%)** | 13 (57%) | 15 (65%) | 15 (65%) |

追試: タスクグラフを 24 ノードに増やし、`deps` をセミコロン結合して表形式化した場合
（`tasks[24]{id,goal,deps,kind}:`）— indent=2: 1286 / compact: 879 / 表形式: **684**
（compact 比 −22%、indent=2 比 −47%）。

cl100k・Claude v1 系でも順位は同じ（例: doctor シグナルの compact 化は cl100k で
1953→1404、Claude v1 系で 1938→1413）。

### 2.3 実測から言えること

1. **`indent=2` が最大の無駄。** doctor の注入は整形をやめるだけで −28%。しかも注入は
   `[:6000]` のバイト切り詰めの内側なので、compact 化は**同じ上限内に載る情報量も増やす**
   （5009→3678 バイトに縮み、切り詰めに掛かりにくくなる）。
2. **`ensure_ascii=False` は死守。** ascii エスケープすると日本語ペイロードで +40〜75%。
   ファミリーは既に全箇所 `ensure_ascii=False` で統一されており、これは「守るべき現状」。
3. **均質な dict 配列だけ、表形式が圧倒的。** キー名の反復が消えるため、行数が多いほど効く
   （30 件で compact 比 −37%）。逆に**均質でない・入れ子が深い・散文が長い**データでは
   表形式の利得は小さい（planner 6 ノードで compact に劣後）。
4. **YAML は一貫した優位が無い。** compact JSON に勝つ場面（深い入れ子）と負ける場面
   （配列中心）が割れ、置換の根拠にならない。加えて PyYAML は同一オブジェクト参照を
   アンカー（`&id001`）に畳む等、プロンプト用途では事故要素もある。
5. **小さい定型契約（verify 封筒・assess）は触る価値が無い。** 絶対差が 1 呼び出し
   あたり 10 トークン前後で、形式変更のリスクに見合わない。

## 3. 案

### 案 K-1: プロンプト注入の compact 正規化（即効・リスク実質ゼロ）

**やること**: プロンプトへ注入する JSON の描画を
`json.dumps(v, ensure_ascii=False, separators=(",", ":"))` へ統一する。描画関数
`dumps_prompt(v)` を **agentcore に 1 実装**（C7。kiro-loop 等の同型ニーズも同じ関数を使う）
置き、注入箇所（§1.1 の表の doctor ×2・deps data・MANIFEST）をそこへ寄せる。

- **削減**: doctor −28%、deps 注入 −15〜20%（既定区切り→compact）。切り詰め上限内の
  実質情報量も増える。
- **決定性・可逆性**: 完全（同じ dict → 同じバイト列。`json.loads` で元に戻る）。
  スキーマ・キー・値は 1 ビットも変わらない。
- **リスク**: 実質ゼロ。LLM にとって整形空白は可読性に寄与しない（インデントで構造を読む
  モデル依存性は確認されていない）。既存テストへの影響はプロンプト文字列のゴールデンのみ。
- **オプトイン扱い**: 内容等価のため既定 on でよいが、doctor の before/after を §5 の指標で
  1 サイクル観測してから他所へ広げる。

### 案 K-2: 均質配列の表形式描画（TOON 風・注入側のみ・オプトイン）

**やること**: 「キー集合が全要素で同一の dict 配列」を検出したときだけ、
`名前[件数]{キー,…}:` ヘッダ + カンマ区切り行へ畳む決定的描画 `render_table(v)` を
agentcore に 1 実装置く。対象は**注入側の均質配列だけ**:

- agent-flow: deps の構造化 data（reduce/map の中間成果——最も膨らむ経路）
- doctor ×2: `runlog_tail` / `blocked` / `recent` / `stuck` / `failed` / `errors`
- 均質でない要素が 1 つでもあれば**その配列は compact JSON へフォールバック**（描画の分岐も
  決定的）。値にカンマ・改行を含むセルは JSON 文字列としてクォート（可逆性の担保）。

- **削減**: 均質 30 件で compact 比 −37%（indent=2 比 −59%）。行数に比例して効く。
- **リスク**: 表形式は JSON よりモデルの読解学習が薄く、**読み違いは理論上あり得る**。
  ゆえに (a) 注入側限定（出力契約には使わない）、(b) `prompt_table: true` のオプトイン、
  (c) ヘッダに件数を明記して欠落を検出可能にする、(d) §5 で verify 一発通過率の悪化を
  監視し、悪化したら off に戻す（C8）。
- **既存の前例**: evaluator への `results_summary` は今日すでに JSON でなく行形式
  （`- nid (kind) [status]: output`）で渡しており、「状態を表形式で LLM に見せる」こと自体は
  ファミリーの新機軸ではない。

### 案 K-3: 出力契約は JSON のまま（積極的な見送り）

LLM の**出力**を TOON / YAML / 独自形式にする案は**採らない**。理由:

1. **失敗コストが非対称。** 出力契約違反は `_repair_json_output` の修復再呼び出し（プロンプト
   全文 + 前回出力を再送）を誘発する。planner 1 回の節約は数十トークン、修復 1 回の追加は
   数百〜数千トークンで、**違反率がわずかに上がるだけで期待値が負ける**。
2. **JSON は最も契約違反率が低い形式である。** モデルは JSON 生成の学習が最も厚く、
   構造化出力支援（スキーマ強制・JSON モード）を持つ CLI も JSON 前提。独自形式はこの
   支援の外に出る。
3. **既存資産が JSON 前提。** 寛容パーサ・修復リトライ・`_coerce_tasks` などの防御層を
   形式ごとに複製することになり C7 に反する。
4. 小型契約（verify・assess）は §2.3-5 のとおり削減余地自体が無い。

なお出力側で唯一検討に値するのは「**冗長な散文を出させない**」方向（例: reduce の items を
必要最小のキーに絞る指示）だが、これは形式の話ではなく比較検討 2b-1「中間出力の簡潔契約」
（kiro-loop の injections 系へ統合済みの見送り案)の領分なので、ここでは扱わない。

### 見送り: YAML への全面置換・キー短縮辞書・gzip/base64 類

- **YAML 置換**: §2.3-4 のとおり一貫した優位が無く、置換コストだけが確実に掛かる。
- **キー名の短縮辞書**（`"parallelism"→"p"` 等の別名マップ）: 描画層で可逆にはできるが、
  実質「もう 1 つのスキーマ」を運用することになり（辞書が正典と別に育つ＝C7 違反の温床）、
  利得はキー反復の消える案 K-2 と重複する。均質配列以外ではキーは 1 回しか現れず、
  数トークンしか取れない。
- **バイナリ・圧縮エンコード**（gzip+base64 等): LLM が読めない／トークン化で逆に膨らむ。
  論外だが「圧縮」という語からの連想で提案されがちなので明記しておく。

## 4. 既存案との関係

| 既存案 | 関係 |
|---|---|
| 案 E（中間成果のダイジェスト渡し） | 直交・相乗。E は「量を絞る」、K は「同じ量を安く描く」。deps 注入では両方効く（E で件数を絞り、K-2 で残りを表に） |
| 案 G（判断のダイエット・バッチ化） | バッチ採点の入出力が均質配列そのものなので、採用時は K-2 の描画に載せる |
| 案 H（安定プレフィックス化） | 直交。K は可変部の削減、H は安定部の単価削減。K-1 の描画統一は H のゴールデンテストを書きやすくする副次効果あり |
| kiro-loop トークン削減（rtk/caveman） | あちらは注入する**文章**のレベル選択、こちらは**構造化データ**の描画。同じ `dumps_prompt` / `render_table` を共有できる |

## 5. 効果計測と受け入れ条件（C8）

- 計測は既存の agent-audit（`--by workload` / `--by model`）と node-budget 台帳で before/after
  を取る。新しい計測基盤は作らない。
- K-1: doctor 1 呼び出しの `tokens_in` が下がること（実測どおりなら −25% 前後）。品質指標
  （doctor 所見の parse 失敗率）が悪化しないこと。
- K-2: 対象 run の `tokens_in` 低下に加え、**verify 一発通過率・修復リトライ率が悪化して
  いない**こと。悪化したら off（オプトインの意味）。
- 受け入れ条件（実装 PR に課す）:
  - 描画は agentcore の 1 実装のみ（各エンジンに複製しない。写しを置く場合は突き合わせ
    テスト必須——C7）
  - `render_table` は可逆性テスト（描画→パースで元の dict 配列へ戻る）と、非均質配列の
    compact フォールバックのテストを持つ
  - K-2 は既定 off。off のときプロンプトが従来とバイト一致

## 6. 実測の再現方法

tiktoken の語彙は `TIKTOKEN_CACHE_DIR` にオフライン配置（litellm ホイールが
`litellm_core_utils/tokenizers/` に cl100k・o200k のキャッシュと Claude v1 系
`anthropic_tokenizer.json` を同梱しており、ネットワーク遮断環境でも取り出せる）。
ペイロードは §1.1 の各接点の実装（`doctor.py:collect_doctor_signals` の形・
`patterns.py:289` / `continuation.py:376` の出力契約・`agent.py:845` の deps 注入）を模した
現実的データを使い、§2.1 の 6 形式 × 3 トークナイザで `len(encode(s))` を比較する。
