# Agent Dashboard 設計・実装ライフサイクル統合設計

## 背景

現在の Agent Dashboard では、設計が次の三つの意味で同時に露出している。

- ワークフロー設定で編集するフロー定義
- タスク作成時に選ぶ「設計フロー」
- 要望を実装可能な状態まで育てる業務上の設計フェーズ

同梱の `design-interactive` と `design-auto` は設計セッションを動かす内部フローだが、一般の
ワークフロー探索へ混ざるため、ワークフロー設定の「保存済み」に通常フローと同列で表示される。
また、プロジェクトとワークフローには、設計セッション、設計の始め方、タスク候補生成が別々の
操作として存在し、設計結果から実装へ移る際に入力と材料を選び直す必要がある。

設計を必要としない仕事、別のエージェントで完成させた設計書を使う仕事もある。したがって設計runと
実装runを一本化するのではなく、同じ仕事の任意フェーズとして連続して扱う必要がある。

## 目的

- 利用者が追う単位を内部runではなく「実装したい一つの仕事」にする。
- 要望入力後に、内容に応じた準備経路を推奨し、利用者が変更できるようにする。
- エージェント設計、外部設計の利用、設計省略の三経路を同じ実装待ち状態へ合流させる。
- 選択したファイルやプロジェクトデータを設計から実装まで引き継ぐ。
- プロジェクトでは、一つの要望を複数バックログ候補へ分解し、各候補が独立して
  設計runから実装runへ進めるようにする。
- 設計用の内部フローを一般ワークフローの編集ライブラリから分離する。

## 非目標

- agent-flow のrun契約、ブランチ契約、実行エンジンを一本化すること。
- 設計をすべてのバックログへ必須化すること。
- 外部設計書の原本をDashboardから自動更新すること。
- 複数人による設計書の同時編集や自動マージ。
- agent-project の物理的な `backlog/` を計画ごとに分割すること。

## 採用方針

### アプローチ比較

| アプローチ | 実装コスト | リスク | 保守性 | 拡張性 | 学習コスト | 業務の連続性 | 推奨度 |
|---|---|---|---|---|---|---|---|
| A. 共通の作業準備ライフサイクル | 中 | 中 | 高 | 高 | 低 | 高 | ★★★ |
| B. 設計と実装を一つのrunへ結合 | 高 | 高 | 低 | 中 | 中 | 中 | ★☆☆ |
| C. 既存画面間へ引継ぎボタンだけ追加 | 低 | 高 | 低 | 低 | 中 | 低 | ★☆☆ |

案Aを採用する。Dashboardに「作業準備項目」を導入し、設計runと実装runの間を状態と成果で結ぶ。
内部runは従来どおり別々に実行する。案Bは設計不要・外部設計・人の回答待ちを一つのrunへ背負わせ、
既存の短命run方針を壊す。案Cは画面上の概念重複を残すため、今回のパッチ的修正禁止に反する。

## ドメインモデル

### 作業準備項目

作業準備項目（Preparation Item）は、最終的に一つの実装単位へ渡す仕事を表す。プロジェクトでは
バックログ候補、ワークフローでは一つの実行待ちタスクに対応する。

```json
{
  "version": 1,
  "id": "prep-...",
  "target": "project",
  "projectDir": "/path/to/project",
  "packageId": "pkg-...",
  "title": "...",
  "goal": "...",
  "route": "agent-design",
  "routeRecommendation": {
    "route": "agent-design",
    "reasons": ["受入基準が未確定"],
    "warnings": []
  },
  "materials": [],
  "phase": "design-ready",
  "design": {
    "sessionId": "ds-...",
    "document": "",
    "runIds": []
  },
  "handoff": {
    "taskId": "",
    "implementationRunIds": []
  },
  "createdAt": "...",
  "updatedAt": "..."
}
```

`route` は次の三つに限定する。

| 経路 | 設計run | 用途 |
|---|---:|---|
| `agent-design` | 1回以上 | エージェントと設計を詰める |
| `external-design` | 0回 | 別エージェント等で作成済みの設計書を使う |
| `direct` | 0回 | プロンプトと材料をそのまま実装へ渡す |

### 材料バンドル

材料は経路選択後に指定し、作業準備項目へスナップショットとして保存する。

```json
{
  "id": "document:api-design.md",
  "kind": "document",
  "name": "api-design.md",
  "content": "# ...",
  "sourcePath": "/path/to/api-design.md",
  "sourceHash": "...",
  "selectedFor": ["design", "implementation"]
}
```

- プロジェクト: 自由入力、マスター憲章、計画バージョン、メモ、ドキュメント。
- ワークフロー: 自由入力、対象フォルダ、Markdown、関連ファイル。
- 読み込んだ原本は変更せず、読み込み時点の内容を保持する。
- 設計結果は `kind=design-result` の材料として追加する。
- 実装前に材料を追加・除外できる。設計に使った材料は既定で実装にも引き継ぐ。
- 秘密情報や巨大ファイルを無差別に収集せず、利用者が明示選択したものだけを保存する。

### 準備パッケージ

プロジェクトの一つの要望を複数バックログへ分解する場合、親として準備パッケージを作る。
親は共通材料と分解runの履歴を持ち、子の作業準備項目を束ねる。親の分解runは、各子の設計runを
完了したことにはしない。

```text
準備パッケージ
  ├─ 共通材料
  ├─ 分解run
  └─ 作業準備項目
      ├─ 子A: agent-design → 実装待ち → 実装run
      ├─ 子B: external-design → 実装待ち → 実装run
      └─ 子C: direct → 実装待ち → 実装run
```

子は親の材料を継承し、項目固有の材料を追加できる。親の材料を後から変更しても、実行済み子項目の
スナップショットを暗黙に書き換えない。

## 状態モデル

作業準備項目の主要状態は次とする。

```text
draft
  ↓ 入力確定
route-selection
  ↓ 経路選択
materials
  ├─ agent-design ─→ designing ─→ design-review ─┐
  ├─ external-design ───────────→ readiness-review ─┤
  └─ direct ────────────────────→ readiness-review ─┘
                                                   ↓
                                             implementation-ready
                                                   ↓
                                                  queued
                                                   ↓
                                             implementing
                                                   ↓
                                                completed
```

設計runの失敗は `designing` 内の回復可能なエラーとして扱い、項目と材料を失わない。利用者は再試行、
外部設計への切替、直接実装への切替を選べる。実装へ渡した後も準備項目は削除せず、handoff先とrun履歴を
表示する。

## 経路の推奨

経路推奨だけのためにLLM runを起動しない。入力と材料に対する決定的な充足度チェックを使う。

- 完成済み設計書が指定され、目的・対象・受入基準・検証方法が揃う: `external-design`。
- 自由入力または候補に目的・対象・受入基準・検証方法が揃う: `direct`。
- 必須情報が不足、矛盾、複数の実装単位が混在: `agent-design`。

推奨理由と不足項目を文字で表示する。推奨はゲートではなく、利用者が三経路のどれへも変更できる。
`direct` を選んだ場合も不足警告は残すが、実装開始を禁止しない。

プロジェクト分解後は各子候補を個別に判定する。十分に具体的な子へ設計runを重複して要求せず、
不足のある子だけに設計を推奨する。

## UX設計

### 共通の作成フロー

プロジェクトとワークフローは、次の順序と用語を共有する。

1. **やりたいこと** — まず要望を入力する。入口で内部方式を選ばせない。
2. **進め方** — 充足度に基づく推奨と理由を表示し、三経路から選ぶ。
3. **材料** — 選んだ経路に必要なファイルとデータを指定する。
4. **確認** — 実装単位、材料、警告、次に起こるrunを確認する。

複数ステップでは現在位置を文字と番号で示す。戻った場合も入力、経路、材料選択を保持する。
カード、入力、主要操作は44px以上、可視フォーカスを持ち、選択は色だけで表さない。

### 設計中の画面

`agent-design` は作成ダイアログ内で完了まで待たせない。作業準備項目を先に保存し、その詳細画面で
次を扱う。

- 現在の設計書
- エージェントからの質問と回答
- 設計runの状態と履歴
- 材料の追加・除外
- 「この設計で実装待ちへ進む」
- 「外部設計へ切り替える」「設計を省略する」

設計書が更新されても元材料は失わない。設計結果を実装材料へ追加する操作は既定で有効にする。

### ワークフロー画面

「実行待ち」だけでなく、設計中と確認待ちを含む「作業準備」一覧を主画面にする。一覧行には仕事名、
現在フェーズ、選択経路、次の操作、警告数を表示する。`implementation-ready` の項目だけに「実行」を
主要操作として表示する。実行開始後は既存run詳細へ遷移し、準備項目との関連を表示する。

### プロジェクト画面

「タスクを追加」は共通作成フローを開く。単一候補は一つの作業準備項目を作る。複数候補へ分解した
場合は準備パッケージと子項目を作り、計画バージョンごとにグループ表示する。

各子項目は独立して経路を変更し、材料を追加し、設計を進められる。実装準備が完了した子だけを既存の
整合入口から `inbox/` へ投入する。準備中候補を物理backlogへ先に置かないため、agent-projectが
設計完了前に実装を開始することを防ぐ。投入後は既存の計画レビュー、重複・墓標照合、実行サイクルを
維持する。

## ワークフロー設定の再分類

フロー定義へ利用目的と公開範囲を加える。

```json
{
  "purpose": "design",
  "libraryVisibility": "internal"
}
```

- `purpose`: `implementation` または `design`。
- `libraryVisibility`: `library` または `internal`。
- 同梱 `design-interactive` / `design-auto` は `design/internal` とする。
- ワークフロー設定の保存済み一覧は `library` のみを表示する。
- `internal` は設計セッションの実行時解決には残すが、通常フローとの編集・複製対象にはしない。
- 既存定義で項目がない場合は `implementation/library` として読む。

これにより保存場所の見た目だけで例外処理せず、ドメイン上の役割に基づいて分類できる。

## 内部処理との境界

- 設計runは既存 `design-session.js` と同梱設計フローを使う。
- 実装runはワークフローでは既存 `adhoc.submit`、プロジェクトでは既存 `inbox/` 投入と
  agent-project実行サイクルを使う。
- Dashboardの作業準備ストアが材料、推奨、状態、設計セッションID、handoff先を管理する。
- 設計runと実装runのIDを同じrunグループへ偽装しない。UI上は同じ仕事の履歴として時系列表示する。

## 保存と移行

- 既存ワークフロー実行待ちタスクは `route=direct`、`phase=implementation-ready` の作業準備項目として
  読み取る。ファイルの一括書換えはしない。
- 既存設計セッションは対応する準備項目がなければ「未関連の設計」として一覧化し、仕事へ関連付けるか
  破棄できる。
- 既存プロジェクトbacklogは移行しない。新しい作成経路から生成した候補だけを準備ストアへ置く。
- 保存は一時ファイルとrenameで行い、部分書込みを避ける。

## エラー処理

- 材料の読込失敗は該当材料だけをエラーにし、他の選択を保持する。
- 原本のmtimeまたはhashが変わっても自動マージせず、再読込か保持を選ばせる。
- 設計run失敗後も設計書、回答、材料、経路を保持する。
- 外部設計に必須節が足りない場合は不足を表示し、設計runへ切り替えられるようにする。
- プロジェクト分解で一部候補だけ保存に失敗した場合は、成功済みIDを記録して未保存だけ再試行する。
- 実装handoffに失敗した項目は `implementation-ready` に残し、二重投入を防ぐ反映IDを保持する。

## テスト方針

- 入力内容から三経路を決定的に推奨し、利用者の上書きを許す。
- 材料の正規化、重複排除、設計結果の実装材料への引継ぎ。
- 親パッケージから複数子項目を作り、子ごとに異なる経路を持てる。
- 設計完了前のプロジェクト候補は `inbox/` へ投入されない。
- 外部設計と直接実装では設計runを起動しない。
- `agent-design` だけが設計セッションを開始し、完了後に実装待ちへ進む。
- 既存実行待ちタスクの互換読込。
- 内部設計フローが設定ライブラリに表示されず、設計実行時には解決できる。
- 失敗、再試行、経路切替で材料と入力が失われない。
- 375px、768px、1024px、1440pxで作成ステップと準備一覧を確認する。

## 既存スキルとの関係

- `ui-designer`: 入力を先に置く段階表示、進捗表示、44px操作領域、可視フォーカスへ反映した。
- `contract-driven-development`: 作業準備項目、材料、パッケージ、handoff契約を将来拡張する際に有効。
- `failure-driven-development`: 部分保存、設計run失敗、handoff再試行の検証を拡張する際に有効。
- `webapp-testing`: 共通作成フロー、経路切替、狭幅表示の実画面回帰に利用できる。
