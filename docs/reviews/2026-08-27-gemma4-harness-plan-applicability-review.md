## 0. 結論の先出し

- **計画メモの「7 つの補助輪」のうち、agent-tools に未実装なのは実質 3 つ半。**
  2（one-step 実行）と 4（外部 verifier）は実装済み。1・3・5・6・7 は部分実装で、
  計画メモが暗黙に置く「ゼロから作る」前提は現行コードと合わない。
- **計画メモの中心線「モデルに判断させる範囲を削る」は、リポジトリ内の提案 3 本が既に走っている。**
  スラッシュ設計はツール選択の 1 語化・未知コマンド fail fast、改善案は割り当てと材料の決定化、
  そして制限付き実行案は回数上限・反復検知・失敗別再入力・escalate——つまり
  **初稿で本レビューが計画メモから抽出した採用候補 P1（ラウンド上限）と P2（失敗選別注入）は、
  制限付き実行案が Phase 1〜2 としてほぼ同じものを提案している**。適用先は新設ではなく合流になる。
- **裏付けが最も強い施策は、最も地味な「ターン上限の引き締め」である。**
  原典（state-harness）の実測は「naive なターン上限だけで Gemma4:E4B が +35pp」。
  しかも同じ原典は「凝ったハーネス（state-harness 本体）は naive 上限と有意差なし」と報告している。
  制限付き実行案 §6 の採用ゲート「完成候補が回数制限のみより改善しなければ複雑な仕組みは
  採用しない」は、この外部実測と**独立に一致**しており、本レビューはこのゲートを強く支持する。
- **引用の裏付け結果はまだら。** 「Better Harnesses, Smaller Models」「state-harness」
  「MagenticLite」「SmallCTL」は実在確認。**Argus の「E4B 83% vs 58%」は確認できず**、根拠にしない。
- **結論として、計画メモから直接採るものはもう無い。** 残る価値は
  (a) 制限付き実行案の Phase 1〜2 と §6 ゲートを外部実測で裏書きすること、
  (b) E4B 固有のパラメータ（write 系は上限 2〜3）を評価 arm に足すこと、
  (c) 提案 3 本の間の**重複と依存**（§4.4）を先に解消すること——である。

## 3. 批判的レビュー

### 計画メモに対して（1〜7）

1. **最強の裏付けは「構造の追加」ではなく「回数の削減」を支持している。**
   state-harness の原典は、監視・分類・安定性解析を持つハーネス本体が naive cap に勝てなかったと
   自ら報告している。計画メモの図が示唆する多段機構への投資は、引用元の実測とむしろ逆向き。
   本リポジトリ側では `schema.md:105-107` の実測（全欠落級は 9/9 同一失敗 → tier 引き上げ）と
   制限付き実行案 §6 のゲートが同じ側に立っている。
2. **数値の確度が引用ごとに大きく違うのに、メモ内では等価に並んでいる。**
   Argus の 83% は確認不能、state-harness は小規模・要再現、Better Harnesses は査読前だが
   設定が明確。裏付け強度で重み付けし直すと、優先順位は計画メモの並び（FSM が 1 番）から
   「上限（7）→ 失敗別注入（6 の一部）→ 検索の決定化（5）」へ入れ替わる。
3. **schema 制約の全面適用は劣化リスクと prefill 費の両方に反する**（§1 の両論、
   `ollama_loop.py:16-22`、smolagents 17 KB 却下と同根）。GBNF arm の実測で裁く。
4. **`expected_result` は検証の重複。** 外部 oracle（check / SHA-256 / receipt 再導出）が既にあり、
   モデル自己申告の期待値は oracle にならない。宣言外変更の検知はスラッシュ設計 段 9b の
   git 差分観測が oracle 側で解く。
5. **反復性の限定（ρ=−0.96）を引き継ぐ必要がある。** 定型役（extract/classify/split、6/6 実測）には
   合うが、open-ended な実装ステートへ同じ期待を持ち込む根拠はない。制限付き実行案 §3.2 が
   対象を「局所修正・失敗テスト明確・形式固定」に絞り、planner 系を除外しているのは
   この限定と正しく一致する。
6. **計画メモは本リポジトリの実測資産と提案群を参照していない。** 方向が独立に収束していること
   自体は傍証だが、計画メモ固有の寄与は「外部実測による裏書き」と「E4B 固有パラメータ」に縮んだ。
7. **適用先を間違えると採択済み設計と衝突する。** ルート表の設定ファイル化・edit toolset 新設・
   外部エージェント実装の持ち込みはスラッシュ設計 §8 と制限付き実行案 §8 の非目標。

### 制限付き実行案に対して（8〜10）——今回の突合で追加

8. **§3.1 の「追加する動作」は、半分以上が分散実装済みである。**
   回数上限は `_TL_MAX_TOOL_ROUNDS = 8`（`toolloop.py:50`）/ `DEFAULT_MAX_ROUNDS = 12`
   （`ollama_loop.py:60`）に定数として、反復検知は `successful_runs` 拒否
   （`statemachine.py:387-397`）と `_round_signature` + `_MAX_REPEATS = 3`
   （`ollama_loop.py:733-740`）に二重に、進展判定は SHA-256 指紋
   （`toolloop.py:740-753`、無変更 write の拒否 `statemachine.py:471-482`）に、停止理由は
   `no_progress` / `context_exhausted` / `tool_denied` / escalate exit 3 に、それぞれ既にある。
   **本当に無いのは「設定可能な上限」「層をまたいで統一された停止理由の語彙」「flow / audit /
   dashboard への表出」の 3 つ**であり、Phase 1 は新規実装ではなく既存機構の統一・設定化として
   実装すべきである。toolloop.py へ素朴に書き足すと、同じ判定が 3 層に重複する。
9. **§3.4-2「許可されていないファイルを変更していないか」は現行機構では検知できない。**
   証跡ゲートは受入条件が名指しした path の指紋しか見ず、ハーネスは git を 1 か所も使っていない
   （スラッシュ設計 §7.3 B が同じ指摘）。この行はスラッシュ設計 段 9b（`git status --porcelain`
   差分）への**依存**として明記すべきで、独立には実装できない。
10. **停止理由の表出はスラッシュ設計 段 7（ペインへの失敗トリアージ・quota 観測）と重複する。**
    制限付き実行案 §3.3・§3.7 が求める「終了理由を routine の結果と画面へ」は、段 7〜8 の
    配線（classify_error の全経路化・session_log 正典化）と同じ器で運ぶべきで、別配線を
    引くと観測面がまた分裂する。

## 4. 適用提案（効く順）

初稿の P1・P2 は制限付き実行案 Phase 1〜2 とほぼ同内容だったため、**独立提案から
「制限付き実行案への合流 + 差分」へ改める**。P3 は引き続きどの提案にも無い。

### P1 ★★★ 制限付き実行案 Phase 1 に合流し、3 つの差分を足す

制限付き実行案 Phase 1（回数上限・反復検知・停止理由を agentcore に置き、agent-flow の
局所修正 1 種で評価）を土台として支持した上で:

1. **新規実装ではなく既存機構の統一・設定化として実装する**（§3-8 の一覧が対象）。
   宣言の置き場は statemachine YAML の state 単位キー（`max_steps` / `check_retries` と同階層）
   か、スラッシュ設計 種別 C 宣言の frontmatter `options:`。新フィールドの発明はしない。
2. **E4B 固有パラメータ**: 一律 3 回ではなく、`write:` を持つステート限定で上限 2〜3 の arm を
   引く（state-harness の推奨と +35pp の実測はこの範囲）。read 系・判定系は現行上限のまま。
3. **測定規律**: 制限付き実行案 §6 の 4 arm 比較（現行 / 回数制限のみ / +反復停止 / 完成候補）を
   そのまま使い、スラッシュ設計 段 12〜13 と同じ単一軸対照（model / policy / sampling /
   プロンプトを同時に変えない）で測る。「完成候補が回数制限のみに勝たなければ採用しない」
   ゲートは外部実測（state-harness）が裏書きしており、**絶対に緩めない**。

### P2 ★★ 同 Phase 2（失敗別再入力）の実装位置を固定する

制限付き実行案 Phase 2（構文エラー・テスト失敗に限り必要な情報だけ渡す再試行）は、
`_sm_check_note()`（`statemachine.py:622-633`、現在は末尾 2000 字を無選別注入）への
**決定的パーサ 1 つ**として実装する。抽出不能時は現行の末尾切り詰めへ fallback し、
省略の事実を明示する（context_slice の 2 原則、改善案 案 C の P4 型と同じ規律）。
§7 のルート表は**仕様**として使い、実装は既存機構への写像（形式壊れ→nudge、CLI・認証→
classify_error env、反復→既存検知、原因不明→escalate）に留める——新分類器は書かない。
スラッシュ設計 段 13（`observation_template`）導入後は整形を宣言側へ移す。

### P3 ★★ ハーネス側検索（rg → 抜粋供給）— 案 B の後、`/find` の裏側として

制限付き実行案 §3.2「モデルには対象ファイルと失敗テストだけを渡す」の**入力をどう作るか**は
同案の範囲外であり、ここだけが 3 本のどの提案にも無い。現在モデルが `read` toolset で自走する
探索（`ollama_loop.py:96`）を、ハーネス側の「決定的 rg → ヒット周辺チャンク → 読み材料へ
事前割付」で置換する opt-in 経路を足す。語彙は変えず、スラッシュ設計の `/find`（種別 B）と
`retrieve` 用途（種別 C）の裏側実装として差し替える。**rg パターンはモデルに書かせない**
（案 C 実測: e4b はパス・テスト名 3/3、regex 0/3）——編集対象の import / シンボルから
決定的導出する（context_slice と同じ素材・同じ規律）。
順序: (1) 改善案 案 B（`read_files=` 配線）が先、(2) read toolset の探索ラウンド消費を
eval ログで確定してから、(3) 消費が小さければ閉じる。

### 4.4 提案 3 本の間で先に解消すべき重複・依存

| 論点 | 重複 / 依存 | 解消の向き |

## 6. まとめ

計画メモの構図（決定的ハーネス + 局所判断関数としての Gemma）は、agent-tools の現行実装と
リポジトリ内提案 3 本（改善案・スラッシュ設計・制限付き実行案）が既に多重に採っている構図で
あり、**計画メモから直接採る新規項目は無くなった**。4 者が独立に同じ方向へ収束していること
自体が方向の強い傍証である。計画メモ（と本レビューの裏付け調査）の残る寄与は、
(a) 制限付き実行案 §6 の採用ゲートを外部実測（state-harness の「naive cap に勝てない複雑機構は
不要」）で裏書きすること、(b) E4B 固有の上限値 2〜3 という具体パラメータ、の 2 点に純化した。
一方で今回の突合により、**提案 3 本の間の重複（回数上限・停止理由の表出）と依存
（許可外変更検知 → 段 9b、材料最小化 → 案 B）**が新たな主要リスクとして浮かんだ——
§4.4 の統一を先に決めないと、同じ判定が 3 層・観測が 2 系統に分裂する。
