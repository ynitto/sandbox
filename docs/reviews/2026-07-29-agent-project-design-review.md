設計書を批判的に読んだ結果。よく煮詰まっているのは「done はゲート」「git を CAS」「親子常駐」「needs は投影」「削除≠却下」「板は常駐だけが書く」あたりで、個別の失敗から学んだ跡が強い。一方で、鉄則の適用範囲と分散時の時間・予算・クラッシュ・二系統の実行経路が概要のままなことが、設計書としての最大の穴。

---

## 致命に近い不変条件の穴

### 1. 最重要不変条件がプロジェクト層で破れている

タスク done は「証跡付き verify」なのに、charter `## acceptance` は一発合成のまま（本文も残課題と明記）。一方で「プロジェクトの done は人が確定する」とも書いてあり、**done の定義がタスク／プロジェクト／人検収の三層で揃っていない**。鉄則の適用範囲が文書として曖昧。

### 2. verifier の「証跡」は真正性を保証しない

無い証跡は fail にするが、**捏造されたコマンド出力・参照ファイルの存在チェックまでは設計に無い**。生成と検証が同じ弱点を持つ問題を「言葉ではなく証跡」で避けたつもりが、証跡そのものが LLM 生成物になりうる。red-green / flake は fast path 専用なので、**acceptance 経路の弁別力の無い検証はこの護りを受けない**。

### 3. 弱い verify / acceptance の流入門がない

プランナーが `acceptance` を必須生成し、それが done ゲートになる。**基準の強さ・環境依存・偽緑のしやすさを投入時に決める契約が無い**。旧「合成 verify」の失敗理由（人が良し悪しを判断できない）が、形を変えて `acceptance` 文面に残っている。

### 4. 外部検証の受理が信頼境界を持たない

他ノードの `verifications/<id>/<rev>.external.json` を「誰が確かめたかで分岐させない」として受け入れる。**弱い／悪意ある／環境の違うノードが緑を返すと、依頼側はそれを done 根拠にできる**。板の請負でワーカーを増やしたほど、この穴は広がる。

### 5. 削除前提の依存解釈が危険

物理削除後、`unmet_deps` は「無い id ＝満たし」。**前提タスクを消すと後続が実行可能になる**。却下と違い再審査もしない。ダイアログ表示に依存する人の注意力が、実行安全性の一部になっている。

## 分散・同期の穴

### 6. 時計 skew を却下したのにリースは時間依存

mtime 調停をクロックスキュー理由で却下しつつ、controller / claim / board リースは時間で失効する。**ノード間の時刻ずれ時の二重実行・早期奪取の扱いが設計に無い**（git CAS は push 時点の保護で、リース寿命の解釈は別問題）。

### 7. fencing `unknown` → 人隔離のスケール設計が無い

不安定ネットでは `unknown` が連発しうる。成果は捨てない方針は妥当だが、**隔離キューの上限・自動再試行・budget との関係・人が追いつかない場合の停止条件が未定義**。人送り回避の三段と衝突しうる。

### 8. クラッシュ一貫性が未設計

settle は archive / 納品書 / needs / claim / verifications / push など複数ファイル＋リモート。**途中死・途中 push 失敗後の「どちらが正か」の復旧契約が本文に無い**。git CAS は「通った変更」の原子性であり、ローカル多段更新の原子性ではない。

### 9. 予算の共有モデルが不明

サイクル／トークン／コスト上限と throttle→report があるが、**複数 PC で共有状態を回すとき予算はノード別かプロジェクト共有か**が書かれていない。一方が throttle でも他方が実行し続ける、二重計上、などの挙動が未定義。

### 10. プロジェクト内割当と板委譲の二系統

controller 割当（`task_runnable_here`）と `location: board` 委譲が併存。**同一タスクが両方の意味で「実行中」になる窓、offloaded と fencing の関係、検証だけ委譲と実装委譲の区別**が十分に閉じていない。

### 11. claims 非同期と「二重実行しない」目標

`claims/` は同期しない局所実行権。調停の正は state 上の doing + fencing とされるが、**局所 claim と remote 正本のずれ・孤児 claim・突然停止後の回収手順**が運用依存のまま。

## 目標・モードの矛盾

### 12. 「人なしで回り続ける」と charter モードが両立しない

目標は backlog 空か予算まで無人運転。charter では再分解は人明示のみ、未達 acceptance は awaiting-plan で人へ、プロジェクト done も人。**目標駆動モードでは人が律速になることが設計の中核なのに、目標節はそれを非目標化していない**。

### 13. review の正がフォージなのに GitLab のみ

MR が正、未対応はボタン決着に倒れる。**フォージ有無で done/review の意味と監査可能性が変わる**。回線断は reject しない方針と、dashboard 同時操作時の競合裁定も薄い。

### 14. learn 自動適用と「policy が勝つ」

詰まり解消の一段目が過去 learn の決定的適用。**誤った／陳腐化した learn が再適用され続ける抑制（無効化・期限・スコープ）が設計に薄い**。三段目の裁定ゲート自体も LLM で、「人を要るか」を機械が決める循環がある。

## 検証・副作用の仕様ギャップ

### 15. `verify_side_effects: network` の強制手段が無い

「HTTP 到達は可、DB/外部書き込みは不可」。verifier は試行錯誤する LLM なので、**禁止の enforce（サンドボックス、許可コマンド、監査）が設計に無い**と、制約はプロンプト上のお願いになる。

### 16. `DIFF_CRITERION` と正当な無差分タスク

常設の差分存在基準は偽緑防止だが、**調査・方針・ドキュメントのみ・「変更しないこと」系のタスクとの衝突の逃げ道が無い**（または未記載）。

### 17. S3 の「回帰・パス保護・進捗」が名前だけ

正準ループでゲート列挙されるが、本書では契約・失敗時の retry/review 分岐・verify との優先順位が無い。**done 直前の実質的な合否が本文から再現できない**。

### 18. `verify_template:` が一言だけ

fast path の一形態として出るが、展開規則・ノード差・red-green 対象かが未定義。

## データモデル・運用の穴

### 19. 日本語タイトルの重複防衛が実質無効

既知の天井として明記済みだが、カスタム `planner_skill` 前提だと**投入側 Jaccard が最終防衛として機能しない**。墓標は正規化タイトル完全一致のみで、言い換え再提案はプランナー任せ——差し替え可能スキルと組み合わせると、鉄則級の護りではない。

### 20. host.yaml トップレベル綻びが警告のみ

フリート一斉起動不能を避ける判断は分かるが、**誤配置キーが警告のまま「効いているつもりで効かない」運用事故**を許す。doctor 計上と起動続行の関係が、失敗モードとして閉じ切っていない。

### 21. 人が押した入札の選別素通し

意図的だが、**能力外ノードへの手動落札・枠超過・検証委譲の品質**に対するガードが「lease だけ」。board の fail-close 思想と部分的に逆向き。

### 22. 状態リポジトリの成長・保持

verifications / archive / journal / run-log / recipes が増え続ける。`gc` コマンドはあるが、**保持契約・肥大時の同期失敗・clone 時間**が設計判断として無い（git 同期路の運用限界）。

### 23. 断片 exec 合成は「死んだ経路に気づけない」構造

棚卸し節自体が、テスト緑のまま配線切れが起きうることを示している。**合成名前空間＋CLI 入口必須は、設計上の観測可能性の穴が再発するクラス**として残っている（個別バグではなくアーキテクチャの性質）。

### 24. 関連設計との接点が本書で弱い

ヘッダは codd-gate / agent-flow を指すが、本文は E2 regression や負債ラチェット acceptance との関係をほぼ書かない。codd-gate 設計は acceptance に決定的コマンドを載せる前提で、**本書の「acceptance は自然文→一発合成が残課題」と読み合わせると、推奨連携経路がどちらが正典か不明**。

---

## 小さめだが設計として閉じていない点

- **controller 延長スレッド死亡**と act 継続時のリース切れ後の成果扱い
- **全 PC 同時停止からの一斉復帰**（lease 争奪・割当ストーム）
- **複数 charter 並行時の優先・予算・同一 repo への書き込み競合**
- **マスター憲章とバージョン憲章の制約衝突の解決主体**
- **物理削除が実行側 write に負ける窓**（確信度中と自認）を、いつ閉じるかの成功条件が無い
- **「コメントのみは検収に使わない」**と、人が MR コメントだけで差し戻す運用のギャップ

---

## 総評

既に「残課題」「窓」「確信度: 中」と自覚されている箇所は概ね妥当。そこに加えて、次が未自覚の境界として次に壊れやすい線だと見る。

1. 証跡の真正性
2. 削除＝依存充足
3. verifier 副作用の enforce
4. 予算の共有単位
5. done 鉄則の適用範囲（タスク verify vs charter acceptance vs 外部検証 vs 人のプロジェクト done）の一本化
