共有名前空間フラグメントを実モジュールへ深化

強く推奨プロセス内
agent_flow/__init__.py:4–15, 33–71 · agent_flow/*.py · tests/*.py

現状 — 浅い

深化後

課題

29個のファイルは独立したモジュールではなく、全シンボル・読み込み順・global再束縛がインターフェースになっており、実装と同じ幅の浅い構造です。

解決案

機械分割を責務単位の実モジュールへ畳み直し、共有名前空間と読み込み順を実装の内側へ閉じ込めます。

  • 局所性: 変更先が一箇所
  • レバレッジ: 小さいインターフェース
  • テスト面: private参照を削減
根拠: __init__.py 自身が「単体 import しない」「1つの共有名前空間へ exec」「privateシンボル参照を維持」と明記。テストには kf._* / patch.object(kf,...) が377箇所あります。
削除テスト: フラグメントの仕組みを削除してもドメイン複雑性は消えず、元の単一ファイルへ戻るだけです。現在のファイル分割は複雑性を隠していません。

ワークノード実行を一つの深いモジュールへ

強く推奨ローカル差替可能
agent_flow/work.py:40–218 · waits.py · workspace.py · plugins.py · bus.py

現状 — 順序制約が漏れる

深化後

課題

cmd_work がclaim、待機、workspace、heartbeat、executor、失敗分類、claim喪失、結果確定の順序をすべて知り、バグの局所性がありません。

解決案

ワークノード1回の試行と確定を一つの深いモジュールへ畳み、executorだけを既存のシームとして残します。

  • 局所性: 順序不変条件を集中
  • レバレッジ: 一試行で全処理
  • テスト面: 結果だけを検証
根拠: work.py:98–215 に「claim後にheartbeat開始」「park時はheartbeat停止後にwait記録」「claim喪失後に結果上書きを抑止」という異なる失敗経路の順序制約が集中しています。agent / stub / plugin の複数アダプタがあるためexecutorシームは本物です。
削除テスト: 現在の小関数群を削除すると複雑性は cmd_work に残るだけです。反対に、ノード試行を削除すると同じ順序制約が全worker経路へ再出現するため、ここには深いモジュールの価値があります。

run起動契約をargv転記から深化

探索価値ありプロセス内
agent_flow/run.py:246–307, 352–395 · config.py:271–287 · cli.py

現状 — 浅い転記

深化後

課題

同じrun要求を複数のargv組み立てが別々に転記し、引数の位置・JSON化・既定値まで呼び出し側のインターフェースへ漏れています。

解決案

子プロセス起動の構築と検証を一つの深いモジュールへ集め、run要求の追加が一箇所で完結する形にします。

  • 局所性: 転記規則を集中
  • レバレッジ: 一要求で全起動
  • テスト面: 起動契約を一面化
根拠: run.py:246–273 と 352–395 が同種のargvを別々に構築し、コメント自身が引数位置の誤りで子が即死すると説明します。config.py:271–287 は可変 args に設定を注入し、生設定を別口で保持しています。
削除テスト: _child_base を削除すると共通引数の転記が二つの起動経路へ戻ります。既に価値はありますが、残る重複を吸収し切れていないため浅いままです。
