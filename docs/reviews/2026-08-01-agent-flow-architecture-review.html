課題

27フラグメントが一つの共有名前空間を持つため、独立import・シンボル所有・テスト面がファイル構造からは判別しにくい状態です。

解決案

実測でナビゲート摩擦が変更コストを上回る場合だけ、互換性とzipapp配布を保ちながら責務単位の実モジュール化を検討します。

  • 局所性: 変更先が一箇所
  • レバレッジ: 小さいインターフェース
  • テスト面: private参照を削減
根拠: __init__.py:4–15 と README.md:441–462 は、LLMの読み込み量、既存のモンキーパッチとglobal再束縛、zipapp配布を保つための意図的な判断だと明記しています。privateシンボルを直接使うテストが広く存在するため、移行面は大きいままです。
削除テスト: フラグメント合成を削除しても実行時の複雑性は消えません。一方、現方式は読み込み量と互換性を実際に隠しているため、単なる素通しとも判定できません。

初回／auto-healの子プロセス起動を一箇所へ深化

強く推奨プロセス内
agent_flow/run.py:12–29, 367–395, 458–478

現状 — 固有argvが重複

深化後

課題

共通argvは _child_base に集約済みですが、orchestratorとworkerの固有argvは初回起動とauto-heal再起動で重複し、設定伝搬の不変条件が二箇所へ漏れています。

解決案

初回とauto-healが同じ子プロセス起動構築を使う形へ畳み、固有オプションの追加を一箇所で完結させます。

  • 局所性: 転記規則を集中
  • レバレッジ: 一要求で全起動
  • テスト面: 起動契約を一面化
根拠: run.py:367–395 と 458–478 が同じorchestrator／workerの固有argvを組み立てています。auto-heal側のコメントは、過去に --review の伝搬を落とすとheal後だけ挙動が変わることを不変条件として明記しています。
削除テスト: _child_base は削除すると共通argvが二箇所へ再出現するため既に深い一方、固有argvの重複を削除しても同じ複雑性が二経路に残ります。深化対象は後者だけです。

最優先候補

初回／auto-healの子プロセス起動を一箇所へ深化 — 実際に重複する二つの実行経路へ限定でき、設定伝搬漏れを一度の修正と一つのテスト面へ局所化します。
